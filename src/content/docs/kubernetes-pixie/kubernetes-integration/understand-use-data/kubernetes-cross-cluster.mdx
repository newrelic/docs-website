Modern Kubernetes environments have evolved into complex, **multi-cluster fleets**, but traditional observability tools often provide only a fractured, siloed view of individual clusters. This Kubernetes cross-cluster UI provides a unified command center that transforms this multi-cluster complexity into fleet-wide clarity.

This unified view helps Platform Engineers and SREs to:
* **Unify fleet-wide observability** on a single dashboard that's compatible with clusters monitored by New Relic agents or OpenTelemetry.
* **Accelerate root cause analysis** with a guided triage workflow.
* **Reduce costs** by identifying wasted resources across the entire fleet.
* **Empower developers** with an application-centric view for self-service.

## Access the UI [#access]

This is the default Kubernetes experience in New Relic. To open it:

1. Go to <DNT>**[one.newrelic.com > All capabilities](https://one.newrelic.com/all-capabilities) > Kubernetes**</DNT>

If you need the previous Kubernetes entity explorer, use the view toggle to switch to it. The same toggle returns you to the default experience, and switching views preserves your filter and time range context.

## Main components of the UI [#components]

The UI is structured to provide both a high-level overview and deep-dive capabilities into your entire Kubernetes fleet. The main components include:

* **Feedback button**: Lets you easily share feedback on your experience with the UI.
* **Entity filters**: Filter and triage issues using **tags and values** at the **cluster or node level**.
    * **Cluster filter**: Filter to isolate the UI to a single or smaller set of Kubernetes clusters.
* **Colored scorecards**: Display relevant high-level metrics to surface the most important issues that need attention across the entire fleet.
    * Clicking a scorecard **orders the table** in the context of that metric, surfacing the clusters and nodes with the most critical issues at the top.
    * It also enables a **line chart** to visualize the metric's evolution over the selected time range.
* **Line chart**: Provides the **evolution of the metric** over the selected time frame for trend analysis.
* **Table**: Lists all entities in the fleet and provides **detailed metric data** for each cluster under the five main tabs.
    * **Health focus**: The table provides a filter to only list "unhealthy" entities to focus your attention where it is really needed.
    * **Search**: A text search bar allows you to filter table rows based on **free text** entered.
    * **Color-coding**: Like the scorecards, table cells are color-coded (Yellow, Red) to quickly draw attention to entities with issues that meet a specific **severity threshold**.
    * **Column chooser**: The Workloads tab ships a lean default column set and lets you add or remove columns. Your column selection persists across sessions.
* **Workload type selector**: Narrow the Workloads tab to a specific workload type, such as Deployments, DaemonSets, or StatefulSets.

## Multi-account fleet visibility [#multi-account]

Clusters from the New Relic accounts you have access to appear together in the same fleet view, so monitoring a fleet that spans multiple accounts doesn't require switching account context. Use the account selector to narrow the view to a subset of accounts.

## Entity popovers [#popover]

Selecting an entity in the table opens a popover that gives you context on that entity without leaving the fleet view:

* **Related entities**, grouped and sorted by type, which you can open in a stacked view alongside your current context.
* **Links to related applications**, marked with an external link icon where they open the APM experience rather than a stacked view.
* **Object description**, which opens the manifest for the selected Kubernetes object.
* **Warning events** for the entity.

## Correlate with APM, Prometheus, and alerts [#correlate]

The fleet view is designed so that you don't have to abandon it to get application or alerting context:

* **APM insights**: The Workloads view surfaces application performance data for the applications running in a workload, so you can move between infrastructure health and application performance in one place.
* **Prometheus insights**: Prometheus data for a workload is surfaced alongside your Kubernetes telemetry.
* **Alerts**: Open alerts are surfaced against clusters, nodes, and workloads, including alert indicators in the Workloads tab. Open alerts appear regardless of the time range you have selected, so an active alert is never hidden by a narrow time picker.

## Kubernetes Maps [#maps]

From the fleet view you can open Kubernetes Maps to visualize the physical and logical relationships between your entities, which helps you understand the blast radius of a failure.

## Drill-down capabilities for triage [#drill-down]

The cross-cluster UI is specifically designed to accelerate root cause analysis with a **guided triage workflow**. The primary mechanism for this deep investigation is the ability to drill down from a fleet-wide metric to a single cluster's view:

* **From scorecard to cluster ranking:** When you click a **colored scorecard** (e.g., Unhealthy Pods), the clusters table immediately re-sorts. This places the clusters with the worst performance for that specific metric at the top, enabling you to identify where the issue is most critical across your entire fleet.
* **From table metric to Kubernetes navigator:** Click a metric value within any cell of the table for a specific cluster or node to automatically launch the **Kubernetes navigator**. The navigator's view is automatically **predefined/filtered** for that specific cluster and metric of interest, allowing you to continue your investigation with a deep dive. Namespace filters you have applied in the fleet view are carried over, so you don't have to reapply them.
* **From warning events to Kubernetes events:** Warning event counts link through to the Kubernetes events view in a stacked view, so you can read the underlying events in the context of the entity you were triaging.

## Tab-specific metrics [#tab]

The UI is organized into five main tabs: 

* [Overview](#overview) 
* [Health](#health)
* [Performance](#performance)
* [Resources](#resources)
* [Workloads](#workloads)


Each tab provides specific metrics both at the aggregate (Scorecard) and cluster/node (Metric) level, along with their associated color-coded thresholds for quick triage.

`Warning Events` is surfaced across tabs rather than only in the Overview tab, and its severity thresholds are applied per tab, so the same warning event count can be color-coded differently depending on which tab you are viewing.
