New Relic's OCI integration connects your Oracle Cloud Infrastructure environment to New Relic, so you can monitor OCI resources and applications from the same observability platform you use for the rest of your stack. New Relic collects OCI metrics and logs using specialized infrastructure agents, on-host integrations, and cloud integrations built specifically for OCI. Once connected, your OCI resources appear as entities in New Relic, alongside the applications and hosts running on them.

## Capabilities [#capabilities]

New Relic collects two types of OCI data:

- **Metrics**: Real-time metrics tracking health, capacity, and performance for your OCI resources
- **Logs**: OCI service and audit logs

## Compatibility and requirements [#requirements]

### You need

Before you begin, make sure you have:

- A New Relic account with [infrastructure monitoring permissions](/docs/accounts/accounts-billing/new-relic-one-user-management/user-permissions/#infrastructure), in a supported region (US, EU, or JP)
- A valid New Relic [ingest license key](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key) and [user key](/docs/apis/intro-apis/new-relic-api-keys/#user-api-key)
- An OCI tenancy with an Identity and Access Management (IAM) domain, and temporary administrative access to that domain and the root compartment, enough to complete Workload Identity Federation (WIF) setup, the mechanism New Relic uses to authenticate without storing long-lived credentials. You can revoke this access once setup is complete.
- Your OCI tenancy OCID and home region (for example, `us-ashburn-1`)
- An OCI API signing key (only if you're deploying with Terraform)

## Guided installation [#ui-install]

Guided installation is available at <DNT>**[one.newrelic.com](https://one.newrelic.com) > Integrations & Agents > Oracle Cloud Infrastructure**</DNT>. The UI walks you through connecting your OCI account, then instrumenting the namespaces and log groups you want to monitor.

<Steps>

<Step>

### Choose data type(s)

Follow these steps:

1. Select the data type as Metrics (for performance and usage statistics), Logs (for detailed event and audit records), or both, depending on your monitoring needs. Choosing both sends both metrics and logs, so you can correlate them for the same OCI resources.
2. Click <DNT>**Continue**</DNT>.

</Step>

<Step>

### Choose your integration method and configure the integration

Select your preferred integration method to ingest OCI data into New Relic based on your organizational needs:

<CollapserGroup>
  <Collapser title="Monitor OCI with Oracle Resource Manager">
    Runs Oracle Resource Manager stacks to provision what the integration needs, instead of you creating each piece by hand in the OCI console. Depending on your setup, this involves deploying up to two separate stacks:

    **Stack 1: Set up Workload Identity Federation (WIF)**. Once you've chosen a [trust type](#wif), if it isn't already configured, select <DNT>**Set up WIF with Oracle Resource Manager**</DNT>, then:

      1. Click <DNT>**Deploy to OCI**</DNT>. This redirects you to the Oracle Cloud console to apply the stack.
      2. If you don't have the Identity Domain Administrator role required to apply it, copy the stack URL and share it with your OCI Identity Domain administrator instead.
      3. Once the stack finishes applying, return to New Relic, enable the <DNT>**WIF stacks**</DNT> toggle, and click <DNT>**Continue**</DNT>.

    **Stack 2: Create connection**. Provide your license key and user key, then click <DNT>**Set up stack**</DNT> to deploy the ORM stack for your compartment, policies, and service connectors (metrics and/or logs).

    Follow the on-screen prompts at each step. You'll return to New Relic between stacks before setup continues.

    Use this if you have a specific reason to avoid Terraform and don't want to configure OCI manually. It takes the least manual work in the OCI console.
  </Collapser>
  <Collapser title="Automate with Terraform (recommended)">
    Declares the compartment, policies, service connectors, and WIF trust as code, using New Relic's OCI Cloud Integrations module, instead of creating each piece by hand in the OCI console or through an OCI-side ORM stack.<br />
    Use this unless you have a specific reason to configure OCI manually or through ORM. It keeps the integration in the same version-controlled, repeatable workflow as the rest of your infrastructure, rather than introducing a manual, out-of-band step.<br />
    Apply the module with your license key, user key, and WIF details as inputs, then verify the integration in New Relic. See the [OCI cloud integration guide](https://registry.terraform.io/providers/newrelic/newrelic/latest/docs/guides/cloud_integrations_guide#oci) for the resource reference.
  </Collapser>
  <Collapser title="Manually integrate your OCI account">
    Step through creating the required policies and service connectors in the OCI console yourself.

    1. <DNT>**Create a compartment**</DNT>. In OCI, create a dedicated compartment for the new resources the New Relic integration creates. Name the compartment `newrelic_compartment_DO_NOT_REMOVE`.
    2. <DNT>**Create a dynamic group**</DNT>. In OCI, create the dynamic group in the root compartment, under the default domain.<br />
       Add two rules, `resource.type = 'serviceconnector'` and `resource.type = 'fnfunc'`.<br />
       These rules group your OCI Service Connectors and Functions together into a single dynamic group. This allows you to apply one security policy that grants both resources the necessary permissions to send data to New Relic.
       Ensure that you select the **Match any rules defined below** checkbox.
    3. <DNT>**Set up key vault secret**</DNT>: Create a key vault to securely store your New Relic license key and user key for authentication.<br />
       1. **Create a key vault**. In the OCI console, locate and access the **Key Management and Vault services** and create a vault in the compartment you created earlier, naming it (for example, `newrelic-vault`) and choosing a standard or virtual private vault based on your security requirements.<br />
       2. **Create a master encryption key**. In the vault, create a master key named (for example) `newrelic-encryption-key`, using the `AES` algorithm and a `256`-bit key length.<br />
       3. **Create secrets for your API keys**. Create a secret for your New Relic ingest license key, named (for example) `newrelic-ingest-key`, selecting the master key you just created and pasting your ingest license key as the secret content. Repeat to create a second secret for your New Relic user key, named (for example) `newrelic-user-key`, pasting your user key as the secret content.
    4. <DNT>**Create a policy**</DNT>. In the root compartment, use the manual editor to create the policy statements for the data type(s) you selected.

       **If you're sending metrics**

       ```
       Allow dynamic-group your_dynamic_group_name to use fn-function in tenancy
       Allow dynamic-group your_dynamic_group_name to use fn-invocation in tenancy
       Allow dynamic-group your_dynamic_group_name to read secret-bundles in tenancy where any { target.secret.id = 'your_ingest_secret_ocid', target.secret.id = 'your_user_secret_ocid' }
       Allow dynamic-group your_dynamic_group_name to inspect dns-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect goldengate-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect network-firewall-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect cloudevents-rules in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect integration-instance in tenancy
       Allow dynamic-group your_dynamic_group_name to read metrics in tenancy
       ```

       Replace the placeholder OCIDs in the secret-bundles statement with the ingest and user secret OCIDs you created in <DNT>**Set up key vault secret**</DNT>. This scopes the permission to only those two secrets, rather than every secret in the tenancy.

       **If you're sending logs**

       ```
       Allow dynamic-group your_dynamic_group_name to use fn-function in tenancy
       Allow dynamic-group your_dynamic_group_name to use fn-invocation in tenancy
       Allow dynamic-group your_dynamic_group_name to read secret-bundles in tenancy where any { target.secret.id = 'your_ingest_secret_ocid', target.secret.id = 'your_user_secret_ocid' }
       Allow dynamic-group your_dynamic_group_name to inspect dns-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect goldengate-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect network-firewall-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect cloudevents-rules in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect integration-instance in tenancy
       Allow dynamic-group your_dynamic_group_name to read log-content in tenancy
       ```

       Replace the placeholder OCIDs in the secret-bundles statement with the ingest and user secret OCIDs you created in <DNT>**Set up key vault secret**</DNT>. This scopes the permission to only those two secrets, rather than every secret in the tenancy.

       **If you're sending both metrics and logs**

       ```
       Allow dynamic-group your_dynamic_group_name to use fn-function in tenancy
       Allow dynamic-group your_dynamic_group_name to use fn-invocation in tenancy
       Allow dynamic-group your_dynamic_group_name to read secret-bundles in tenancy where any { target.secret.id = 'your_ingest_secret_ocid', target.secret.id = 'your_user_secret_ocid' }
       Allow dynamic-group your_dynamic_group_name to inspect dns-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect goldengate-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect network-firewall-family in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect cloudevents-rules in tenancy
       Allow dynamic-group your_dynamic_group_name to inspect integration-instance in tenancy
       Allow dynamic-group your_dynamic_group_name to read metrics in tenancy
       Allow dynamic-group your_dynamic_group_name to read log-content in tenancy
       ```

       Replace the placeholder OCIDs in the secret-bundles statement with the ingest and user secret OCIDs you created in <DNT>**Set up key vault secret**</DNT>. This scopes the permission to only those two secrets, rather than every secret in the tenancy.
    5. <DNT>**Set up a network**</DNT>: Create network infrastructure to support the deployment of functions and service connector hubs for secure connectivity.<br />
       - Navigate to the networking service and locate the <DNT>**Virtual Cloud Networks**</DNT> option.
       - Use the VCN creation wizard to create a VCN with internet connectivity.
       - Name the VCN using the pattern `newrelic-{region}-vcn`, where `{region}` is your deployment region.
       - Select the `newrelic-compartment` created in earlier steps.
       - Choose a CIDR block for the VCN, for example `10.0.0.0/16`.
       - Configure CIDR blocks for public and private subnets, for example `10.0.0.0/24` for private and `10.0.1.0/24` for public subnets.
       - Verify all configuration details and create the VCN.
    6. <DNT>**Set up metrics function**</DNT>: Create a serverless application and deploy the New Relic function that processes and forwards your OCI metrics.<br />
       1. **Create a serverless application**
          - Access the <DNT>**Functions**</DNT> service under <DNT>**Developer Services**</DNT> in the OCI console.
          - Create a new application with this configuration:
            - **Name**: a descriptive name (for example, `NewRelicMetricsApp`)
            - **Compartment**: your designated New Relic compartment
            - **VCN**: the VCN created for the New Relic integration
            - **Subnet**: the private subnet, for secure connectivity
            - **Shape**: the compute shape matching your Docker image architecture (ARM or x86)
       2. **Configure environment variables**
          - Within the application settings, add these configuration variables:
            - `FORWARD_TO_NR`: set to `True` to enable data forwarding to New Relic
            - `LOGGING_ENABLED`: set to `False` to disable verbose logging (optional)
            - `NR_METRIC_ENDPOINT`: the New Relic endpoint, using `newrelic-metric-api` for US accounts, `newrelic-eu-metric-api` for EU accounts, or `newrelic-jp-metric-api` for JP accounts
            - `VAULT_REGION`: the region where you created your key vault
            - `SECRET_OCID`: the OCID of your New Relic ingest secret from the key vault
            - `TENANCY_OCID`: your OCI tenancy OCID
          - Save the configuration variables.
       3. **Create and deploy the function**
          - Within the application, create a new function with these specifications:
            - **Function name**: a descriptive name (for example, `newrelic-metrics-function`)
            - **Image source**: the New Relic Docker image from Container Registry
            - **Memory allocation**: appropriate memory (for example, 256 MB)
          - For the Docker image, use Container Registry authentication: authenticate with your regional Container Registry endpoint, pull the New Relic Docker image (`{region}.ocir.io/axcvnhglb9ao/public-newrelic-repo:latest`), tag and push it to your namespace if required, then reference it in your function configuration.
          - Complete the function creation and deployment process.
    7. <DNT>**Set up logs function**</DNT>: Create a serverless application and deploy the New Relic function that processes and forwards your OCI logs.<br />
       1. **Create a serverless application for logging**
          - Access the <DNT>**Functions**</DNT> service under <DNT>**Developer Services**</DNT> in the OCI console.
          - Create a new application with this configuration:
            - **Name**: a descriptive name (for example, `newrelic-logging-function-app`)
            - **Compartment**: your designated New Relic compartment
            - **VCN**: the VCN created for the New Relic integration
            - **Shape**: `GENERIC_X86`, for the application shape
          - Save the application configuration.
       2. **Configure environment variables for logging**
          - Within the application settings, go to the configuration section and add these variables:
            - `VAULT_REGION`: the region where you created your key vault
            - `DEBUG_ENABLED`: `false` for production use (or `true` for debugging)
            - `NEW_RELIC_REGION`: your New Relic region (`US`, `EU`, or `JP`)
            - `SECRET_OCID`: the OCID of your New Relic license key secret from the key vault
            - `CLIENT_TTL`: `30` seconds, for the license key refresh interval
          - Save the configuration variables.
       3. **Deploy the logging function**
          - Prepare the New Relic logging Docker image: authenticate with your regional Container Registry endpoint, pull the New Relic logging image from the public repository, then tag and push it to your namespace if required.
          - Create a new function within the application with these specifications:
            - **Function name**: a descriptive name (for example, `newrelic-logging-function`)
            - **Image source**: the New Relic logging Docker image from Container Registry
            - **Memory allocation**: at least 128 MB
            - **Timeout**: 300 seconds, for adequate processing time
          - Complete the function creation and deployment process.
       4. **(Optional) Enable function logging**
          - Access the monitoring settings for your function application.
          - Enable function invocation logs by selecting or creating an appropriate log group, configuring log retention and access policies, and activating log collection for the function.
    8. <DNT>**Set up metrics connector**</DNT>: Forwards OCI metrics to the New Relic platform for monitoring and analysis.<br />
       - Create a <DNT>**Service Connector Hub**</DNT> with appropriate naming conventions.
       - Configure <DNT>**Monitoring**</DNT> as the source to collect metrics from the specified compartments and namespaces.
       - Set the target as the New Relic function you created in the previous step.
       - Apply region-specific settings for multi-region deployments, if required.
    9. <DNT>**Set up audit logs connector (optional)**</DNT>: In the Connector Hub, create a connector with **Logging** as the source and **Functions** as the target, using the `_Audit` log group and the logs function you created earlier. Skip this step if you don't need audit log ingestion.
    10. <DNT>**Set up logs connector**</DNT>: Forwards OCI logs to the New Relic platform for monitoring and analysis.<br />
        - Create a <DNT>**Service Connector**</DNT> with an appropriate name and description.
        - Configure the source to specify the origin of the data.
        - Configure the target to route data to the New Relic platform.
    11. <DNT>**Set up WIF**</DNT>. Create the two OCI Identity Domain applications (a temporary admin app for setup, and a no-privilege app for routine token exchange), the service user and group (for UPST) or claim-based principal (for RPST), and the identity propagation trust linking your domain to New Relic's JWT issuer. See your [trust-type choice](/docs/infrastructure/oci/introduction/#wif) below.
    12. <DNT>**Create connection**</DNT>. Return to New Relic and enter the details as shown on the UI then click <DNT>**Continue**</DNT>.
    13. <DNT>**Test your connection**</DNT>. Confirm New Relic can reach your OCI tenancy before moving on to instrumentation.
  </Collapser>
</CollapserGroup>

#### Workload Identity Federation [#wif]

All three setup methods also require Workload Identity Federation (WIF), the trust relationship New Relic uses to authenticate to your tenancy without storing long-lived credentials. During the **Set up WIF** step, you make two choices in order:

1. **Trust type**: **UPST** impersonates a dedicated service user, and we recommend it for most accounts. **RPST** uses claim-based, ephemeral access instead, and fits if multiple New Relic accounts monitor one tenancy, or you hit OCI's IAM policy-statement limit.
2. **Configuration source**, for whichever trust type you picked:
   - **Use existing WIF configuration**: If you already have WIF set up for that trust type, enter its client ID, client secret, and domain URL.
   - **Set up WIF with Oracle Resource Manager**: If you don't, deploy an ORM stack that provisions the OAuth apps, IAM group, policies, and identity propagation trust for you. This requires the Identity Domain Administrator role, which you can revoke once setup finishes.

</Step>

<Step>

### Instrument your metric namespaces and log groups

Once you create the connection, the OCI page in New Relic shows separate views for metrics and logs, each with its own **Add instrumentation** control:

1. Click **Add instrumentation**, filtered to **Not instrumented** tab by default.
2. Expand a compartment to see its individual metric namespaces (or log groups), and select the ones you want to monitor. For logs, you can also turn on **Enable audit logs** to include OCI audit logs.
3. Confirm your selection. New Relic shows a summary of how many compartments and namespaces (or log groups) you're about to instrument. Then click **Deploy to OCI**.
4. After the deployment finishes in OCI, the compartment moves to the **Instrumented** tab, and its data appears at <DNT>**[one.newrelic.com](https://one.newrelic.com) > Infrastructure > OCI**</DNT>.
5. If you selected both metrics and logs during setup, switch to the **Logs** view and repeat steps 1–4 there.

Data can take up to 30 minutes to appear. If you don't see it after that, check the deployment status in the OCI console.

To instrument additional namespaces or log groups later, return to the OCI page in New Relic and repeat these steps.

</Step>

<Step>

### Find and use your data

Once your data starts appearing at <DNT>**[one.newrelic.com](https://one.newrelic.com) > Infrastructure > OCI**</DNT>, confirm the integration is working and put it to use:

1. Verify that your OCI account appears in the integrations list.
2. Confirm that you're receiving data (metrics and/or logs).
3. [Create alert conditions](/docs/alerts/create-alert/create-alert-condition/alert-conditions) for key OCI metrics to get proactive notifications about performance issues.
4. [Build custom dashboards](/docs/query-your-data/explore-query-data/dashboards/introduction-dashboards/) to visualize your OCI infrastructure data and monitor performance trends.

If you don't see data after 30 minutes, see [Troubleshooting](/docs/infrastructure/oci/troubleshoot).

</Step>

</Steps>
