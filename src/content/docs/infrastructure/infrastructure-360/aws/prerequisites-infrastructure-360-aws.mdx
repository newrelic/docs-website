Before enabling [<DNT>Infrastructure 360</DNT>](/docs/infrastructure/infrastructure-360/introduction-infrastructure-360) for <DNT>AWS</DNT>, ensure you have:

* Auto-discovery enabled for the <DNT>AWS</DNT> account.
* The `cloudformation:StartResourceScan` permission, which the <DNT>CloudFormation</DNT> stack grants during setup.
* Resources in a region that <DNT>Infrastructure 360</DNT> scans (see [scan frequency](#scan-frequency) below).

## What auto-discovery covers on AWS [#coverage]

Auto-discovery scans your connected <DNT>AWS</DNT> accounts and creates a New Relic entity for every supported resource, then works out how those resources connect to each other and records those connections as relationships. Auto-discovery doesn't require an agent. Resources appear whether or not they're instrumented.

Auto-discovery creates entities and relationships, not telemetry. A discovered resource gets an entity, tags, its <DNT>AWS</DNT> configuration, and a place on your maps, but auto-discovery doesn't send metrics or events for it. To get charts and alerts, connect <DNT>AWS</DNT> metrics or install an agent as well.

If you already monitor a resource another way (for example, the infrastructure agent on an EC2 instance, or CloudWatch Metric Streams on an RDS instance), auto-discovery adds to that existing entity rather than creating a duplicate.

Auto-discovery supports 66 <DNT>AWS</DNT> resource types, mapping to 65 entity types.

## Relationships [#relationships]

As well as creating entities, auto-discovery works out how your resources connect and records those connections as relationships. Relationships are what your maps draw, and what lets you trace a slow request from a load balancer down to the database behind it.

Every relationship consists of a source, a relationship type, and a target. For example, `VPC CONTAINS Subnet` or `S3 bucket TRIGGERS Lambda function`. The order matters: it tells you which way the connection goes.

There are eight relationship types:

<table>
  <thead>
    <tr>
      <th style={{ width: "150px" }}>Type</th>
      <th style={{ width: "350px" }}>Means</th>
      <th>Example</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>`CONTAINS`</td>
      <td>The source is a boundary the target sits inside.</td>
      <td>VPC `CONTAINS` Subnet</td>
    </tr>
    <tr>
      <td>`SECURES`</td>
      <td>The source controls access to, or encrypts, the target.</td>
      <td>Security Group `SECURES` RDS instance</td>
    </tr>
    <tr>
      <td>`CONNECTS_TO`</td>
      <td>The two are attached or wired together, with no direction of traffic implied.</td>
      <td>RDS Proxy `CONNECTS_TO` RDS instance</td>
    </tr>
    <tr>
      <td>`CALLS`</td>
      <td>The source sends requests to the target and waits for a response.</td>
      <td>ELB application load balancer `CALLS` ECS service</td>
    </tr>
    <tr>
      <td>`TRIGGERS`</td>
      <td>Activity in the source starts work in the target.</td>
      <td>S3 bucket `TRIGGERS` Lambda function</td>
    </tr>
    <tr>
      <td>`MANAGES`</td>
      <td>The source controls the target's lifecycle by creating, scaling, or replacing it.</td>
      <td>ECS cluster `MANAGES` ECS service</td>
    </tr>
    <tr>
      <td>`PRODUCES`</td>
      <td>The source writes messages or records that the target receives.</td>
      <td>SNS topic `PRODUCES` SQS queue</td>
    </tr>
    <tr>
      <td>`HOSTS`</td>
      <td>The source runs the target's code.</td>
      <td>CloudFront distribution `HOSTS` Lambda function</td>
    </tr>
  </tbody>
</table>

Auto-discovery records most relationships in one direction only, since many <DNT>AWS</DNT> connections have no natural direction (a VPC and a subnet are simply related). Maps still draw the connection correctly from either end, regardless of how auto-discovery recorded it.

Auto-discovery reads most relationships directly from a resource's configuration, but in some cases infers them. For example, it connects a load balancer target group to the right host when the target group routes to IP addresses rather than named instances, by matching target IPs against your network routing.

## Scan frequency [#scan-frequency]

Auto-discovery rescans a region based on your account's metrics polling interval, with a default frequency of 24 hours. You can configure rescanning to run every 8, 12, or 16 hours instead. Minimum interval length is 8 hours. If you set an interval below 8 hours, it automatically defaults to 8 hours.
