You can use [our NerdGraph API](/docs/apis/nerdgraph/get-started/introduction-new-relic-nerdgraph) to create and manage Pathpoint flows programmatically, instead of building them in the UI.

## Overview [#overview]

For an introduction to Pathpoint itself, see [Get started with Pathpoint](/docs/pathpoint/get-started-pathpoint).

A flow represents one business journey — checkout, authentication, or onboarding — and it's the unit you create and manage through the API. Flows are [entities](/docs/new-relic-solutions/new-relic-one/core-concepts/what-entity-new-relic), so each one has an entity <DNT>GUID</DNT> you use to read, update, or delete it.

Every flow follows a four-tier hierarchy, with KPIs attached at the flow level, the stage level, or both:

```
Flow
└── Stages
    ├── Stage KPIs
    └── Levels
        └── Steps
            └── Signals (entity GUIDs, alert condition GUIDs, or a dynamic query)
```

Use NerdGraph when you want to provision flows from a CI/CD pipeline, copy a flow between accounts, or read live health status into another system. If you'd rather manage flows as code, see the [`newrelic_pathpoint_flow`](https://registry.terraform.io/providers/newrelic/newrelic/latest/docs) resource in the New Relic Terraform provider.

## Before you begin [#requirements]

You need:

* A New Relic <InlinePopover type="userKey"/> to authenticate your requests.
* Pathpoint enabled on the account you're targeting.
* Your [account ID](/docs/accounts/accounts-billing/account-structure/account-id).

To run these examples interactively, open the [NerdGraph GraphiQL explorer](https://api.newrelic.com/graphiql) and search the schema for `pathPoint`.

Each example below shows a GraphQL operation and the JSON variables to send with it. Using variables rather than inlining values keeps the operation readable, which matters for flows because the input nests several levels deep.

## Flow CRUD operations [#crud-operations]

These operations create, read, update, duplicate, and delete an entire flow, including its stages, levels, steps, signals, and KPIs.

### Create a flow [#create-flow]

Pass the account scope alongside the nested stages, levels, steps, and signals that make up the flow. Only `name` and `stages` are required.

A step gets its signals in one of three ways, and you can combine them:

* <DNT>**A dynamic query**</DNT> (`entitySearchQuery`) — evaluated at each refresh, attaching whatever entities match.
* <DNT>**A pinned entity**</DNT> (`type: ENTITY`) — one specific entity, identified by its GUID.
* <DNT>**A pinned alert condition**</DNT> (`type: ALERT`) — one alert condition, identified by its entity GUID.

The `type` field is optional — the GUID itself is enough to identify whether a signal is an entity or an alert condition.

<CollapserGroup>
  <Collapser
    id="mutation-create-flow"
    title="Create a flow with two steps"
  >
    ```graphql
    mutation CreateFlow($scope: PathPointScopeInput!, $input: PathPointFlowInput!) {
      pathPointCreate(pathpoint: $input, scope: $scope) {
        guid
        name
        version
        message
        excludedKpis
        stages {
          totalCount
          items {
            id
            name
            levels {
              items {
                id
                steps {
                  items {
                    id
                    name
                  }
                }
              }
            }
          }
        }
      }
    }
    ```

    And here are the variables to use with this mutation:

    ```json
    {
      "scope": {
        "id": YOUR_ACCOUNT_ID,
        "type": "ACCOUNT"
      },
      "input": {
        "name": "Checkout flow",
        "description": "End-to-end checkout journey",
        "category": "E-Commerce",
        "refreshInterval": "FIVE_MINUTES",
        "stages": [
          {
            "name": "Frontend",
            "healthRollup": "AUTOMATIC_ROLL_UP",
            "levels": [
              {
                "steps": [
                  {
                    "name": "Login page",
                    "entitySearchQuery": {
                      "query": "domain = 'BROWSER' AND type = 'APPLICATION' AND name = 'Login'"
                    }
                  },
                  {
                    "name": "Cart service",
                    "signals": [
                      {
                        "guid": "ENTITY_GUID",
                        "name": "Cart service",
                        "type": "ENTITY"
                      }
                    ]
                  }
                ]
              }
            ]
          }
        ]
      }
    }
    ```
  </Collapser>

  <Collapser
    id="mutation-create-flow-kpis"
    title="Create a flow with KPIs"
  >
    KPIs at the top level apply to the whole flow. KPIs inside a stage (`stageKpis`) apply to that stage only. Both use the same schema.

    Each KPI's `timeWindow` takes either a `relativeRange` built from fixed durations or a `customRange` holding a raw NRQL time expression — not both.

    ```graphql
    mutation CreateFlow($scope: PathPointScopeInput!, $input: PathPointFlowInput!) {
      pathPointCreate(pathpoint: $input, scope: $scope) {
        guid
        name
        version
        excludedKpis
        kpis {
          id
          name
          category
          query {
            from
            where
            select {
              aggregationType
              attribute
              alias
            }
            timeWindow {
              customRange
              relativeRange {
                since
                compareAgainst
              }
            }
          }
        }
      }
    }
    ```

    And here are the variables to use with this mutation:

    ```json
    {
      "scope": {
        "id": YOUR_ACCOUNT_ID,
        "type": "ACCOUNT"
      },
      "input": {
        "name": "Checkout flow",
        "refreshInterval": "FIVE_MINUTES",
        "kpis": [
          {
            "name": "Order success rate",
            "category": "Revenue",
            "description": "Orders completed successfully",
            "query": {
              "from": "Transaction",
              "where": "transactionType = 'Web' AND name = 'checkout'",
              "select": {
                "aggregationType": "COUNT",
                "alias": "orders"
              },
              "timeWindow": {
                "relativeRange": {
                  "since": "TWENTY_FOUR_HOURS",
                  "compareAgainst": "SEVEN_DAYS"
                }
              }
            }
          }
        ],
        "stages": [
          {
            "name": "Payment",
            "stageKpis": [
              {
                "name": "Payment errors",
                "category": "Reliability",
                "query": {
                  "from": "TransactionError",
                  "select": {
                    "aggregationType": "COUNT",
                    "alias": "errors"
                  },
                  "timeWindow": {
                    "customRange": "SINCE 30 minutes ago"
                  }
                }
              }
            ],
            "levels": [
              {
                "steps": [
                  {
                    "name": "Payment gateway",
                    "config": {
                      "healthRollup": "WORST_STATUS_WINS",
                      "thresholdType": "FIXED",
                      "thresholdValue": 1
                    },
                    "entitySearchQuery": {
                      "query": "domain = 'APM' AND name = 'PaymentGateway'"
                    }
                  }
                ]
              }
            ]
          }
        ]
      }
    }
    ```
  </Collapser>
</CollapserGroup>

<Callout variant="important">
  A KPI's `accountId` defaults to the flow's account. If you set it to a different account, the KPI isn't created and no error comes back. Check the `excludedKpis` field in the response to see which KPIs were skipped.
</Callout>

### Read a flow [#read-flow]

Read a flow by its entity GUID to get its full configuration plus the current health status of the flow, each stage, each level, and each step. `healthStatus` appears only on reads.

Stages, levels, and steps return 50 items per page. When a `nextCursor` comes back non-null, pass it to fetch the next page.

```graphql
query ReadFlow($accountId: Int!, $guid: EntityGuid!) {
  actor {
    account(id: $accountId) {
      pathPoint {
        flow(guid: $guid) {
          guid
          name
          description
          category
          refreshInterval
          healthRollup
          healthStatus
          version
          message
          kpis {
            id
            name
            category
            accountId
            query {
              from
              where
              select {
                aggregationType
                attribute
                alias
                threshold
              }
              timeWindow {
                customRange
                relativeRange {
                  since
                  compareAgainst
                }
              }
            }
            metricQuery
          }
          stages {
            totalCount
            nextCursor
            items {
              id
              name
              link
              healthRollup
              healthStatus
              isExcluded
              related {
                source
                target
              }
              levels {
                totalCount
                nextCursor
                items {
                  id
                  healthStatus
                  steps {
                    totalCount
                    nextCursor
                    items {
                      id
                      name
                      healthStatus
                      isExcluded
                      scopedAccounts
                      config {
                        healthRollup
                        thresholdType
                        thresholdValue
                      }
                      entitySearchQuery {
                        query
                        isExcluded
                      }
                      signals {
                        guid
                        name
                        type
                        isExcluded
                      }
                    }
                  }
                }
              }
            }
          }
          metadata {
            createdAt
            createdBy {
              name
              email
            }
            updatedAt
            updatedBy {
              name
              email
            }
          }
        }
      }
    }
  }
}
```

And here are the variables to use with this query:

```json
{
  "accountId": YOUR_ACCOUNT_ID,
  "guid": "FLOW_GUID"
}
```

Request fewer fields if you don't need the whole tree — reading just `name` and `healthStatus`, for example, is enough to poll a flow's status.

### Update a flow [#update-flow]

`pathPointUpdate` is a diff-based operation. It compares the payload you send against the flow's current state and acts on each stage, level, step, and KPI according to whether you included its ID:

* <DNT>**ID included**</DNT> — updates the existing object.
* <DNT>**ID omitted**</DNT> — creates a new object.
* <DNT>**Object left out of the payload entirely**</DNT> — deletes it from the flow.

<Callout variant="caution">
  Because omission means deletion, always [read the flow](#read-flow) first, modify the payload you get back, and send the complete intended state. Sending a partial payload deletes everything you left out.
</Callout>

The `version` field is required. It's the flow's last-updated timestamp in epoch milliseconds, used for optimistic concurrency control — so read the current `version` and pass it back with your update.

<Callout variant="tip">
  Updates match each stage, level, and step to its existing counterpart by name first, then by position in the list. Renaming and reordering items in the same request can associate IDs unexpectedly, so do them in separate requests.
</Callout>

    ```graphql
        name

              }
            }
          }
        }
      }
    }
    ```

### Duplicate a flow [#duplicate-flow]

Duplicating copies either the structure alone or the whole flow:

* `STRUCTURE` — copies stages, levels, and steps, without signals or KPIs.
* `WHOLE_FLOW` — copies the entire configuration, including signals and KPIs.

Any property you set in the input overrides the source flow's value. Omit a property to inherit it.

<CollapserGroup>
  <Collapser
    id="mutation-duplicate-flow"
    title="Duplicate a flow in the same account"
  >
    ```graphql
    mutation DuplicateFlow($sourceGuid: EntityGuid!, $pathpoint: PathPointDuplicateInput!) {
      pathPointDuplicate(sourceGuid: $sourceGuid, pathpoint: $pathpoint) {
        guid
        name
      }
    }
    ```

    And here are the variables to use with this mutation:

    ```json
    {
      "sourceGuid": "SOURCE_FLOW_GUID",
      "pathpoint": {
        "name": "Checkout flow (copy)",
        "category": "E-Commerce",
        "refreshInterval": "TEN_MINUTES",
        "duplicateType": "WHOLE_FLOW"
      }
    }
    ```
  </Collapser>

  <Collapser
    id="mutation-duplicate-flow-cross-account"
    title="Duplicate a flow into another account"
  >
    To copy a flow into a different account, add a `scope` and set its `id` to the target account. Omit `scope` to duplicate within the source account.

    ```graphql
    mutation DuplicateFlow(
      $sourceGuid: EntityGuid!
      $scope: PathPointScopeInput!
      $pathpoint: PathPointDuplicateInput!
    ) {
      pathPointDuplicate(
        sourceGuid: $sourceGuid
        scope: $scope
        pathpoint: $pathpoint
      ) {
        guid
        name
      }
    }
    ```

    And here are the variables to use with this mutation:

    ```json
    {
      "sourceGuid": "SOURCE_FLOW_GUID",
      "scope": {
        "id": TARGET_ACCOUNT_ID,
        "type": "ACCOUNT"
      },
      "pathpoint": {
        "name": "Checkout flow",
        "duplicateType": "WHOLE_FLOW"
      }
    }
    ```
  </Collapser>
</CollapserGroup>

### Delete a flow [#delete-flow]

Deleting a flow cascades: it removes the flow along with all its stages, levels, steps, and KPIs. The signals themselves — the entities and alert conditions the flow pointed at — stay in your account.

<Callout variant="caution">
  Deleting a flow is permanent.
</Callout>

```graphql
mutation DeleteFlow($guid: EntityGuid!) {
  pathPointDelete(guid: $guid) {
    guid
    name
  }
}
```

And here are the variables to use with this mutation:

```json
{
  "guid": "FLOW_GUID"
}
```

## Partial failures [#partial-failures]

A create or update can succeed overall while individual objects fail. Two fields in the response tell you when that happened:

* `message` — details of any stages, levels, or steps that failed. It's `null` when everything succeeded.
* `excludedKpis` — the names of KPIs that weren't created, most commonly because the KPI's `accountId` didn't match the flow's account.

Request both fields in your mutations so you don't treat a partial success as a complete one.

## Type reference [#type-reference]

These enums appear in the operations above. Each row lists the accepted values, followed by what they control:

  <thead>
    <tr>
      <th>Enum</th>
      <th>Values</th>
    </tr>

  <tbody>
    <tr>
      <td>`RefreshInterval`</td>
      <td>`ONE_MINUTE`, `FIVE_MINUTES`, `TEN_MINUTES`, `FIFTEEN_MINUTES`, `THIRTY_MINUTES` — how often flow, stage, level, and step health refresh.</td>
