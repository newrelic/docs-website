Monitor your MySQL database performance with comprehensive metrics collected by the NRDOT Collector. By default, New Relic collects the metrics referenced in the [Default metrics](#default) section. You can enhance your monitoring by enabling your desired metrics listed in the [Full-feature metrics](#full-feature) section.

## Log events [#log-events]

<CollapserGroup>

  <Collapser
    id="query-sample"
    title="Query samples"
  >

Real-time visibility into currently-running database statements: a point-in-time snapshot taken every scrape, not a complete execution log. Disabled by default.
You can set the `db.server.query_sample` to `true` to enable query sampling.

Use the `query_sample_collection` block to tune its behavior:

```yaml
query_sample_collection:
  max_rows_per_query: 100
  allowed_comment_keys: [nr_service_guid]
```

**Available parameters**

<table>
  <thead>
    <tr>
      <th>Parameter</th>
      <th>Description</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>`max_rows_per_query`</td>
      <td>The maximum number of rows to collect per scrape. The default value is set to `100`</td>
    </tr>
    <tr>
      <td>`allowed_comment_keys`</td>
      <td>Keys to extract from leading SQL comments for APM-DB correlation</td>
    </tr>
  </tbody>
</table>

**Attributes collected**

<table>
  <thead>
    <tr>
      <th>Attribute</th>
      <th>Description</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>`db.system.name`</td>
      <td>`mysql`</td>
    </tr>
    <tr>
      <td>`mysql.threads.thread_id`</td>
      <td>Unique identifier for the thread executing the statement</td>
    </tr>
    <tr>
      <td>`mysql.session.id`</td>
      <td>`PROCESSLIST_ID`: the connection ID visible via `SHOW PROCESSLIST`</td>
    </tr>
    <tr>
      <td>`user.name`</td>
      <td>Foreground-thread user; empty for background threads</td>
    </tr>
    <tr>
      <td>`db.namespace`</td>
      <td>Thread's current database (`processlist_db`)</td>

    <tr>
      <td>`mysql.threads.processlist_command`</td>
      <td>Command type, or `Sleep` if idle</td>
    </tr>
    <tr>
      <td>`mysql.threads.processlist_state`</td>
      <td>Current action/state of the thread</td>
    </tr>
    <tr>
      <td>`db.query.text`</td>
      <td>SQL statement text</td>
    </tr>
    <tr>
      <td>`mysql.events_statements_current.digest`</td>
      <td>SHA-256 statement digest</td>

    <tr>
      <td>`mysql.events_statements_current.timer_start`</td>

    </tr>
    <tr>
      <td>`mysql.events_statements_current.timer_wait`</td>
      <td>Elapsed execution time, in seconds</td>
    </tr>
    <tr>
      <td>`mysql.events_waits_current.timer_wait`</td>
      <td>Elapsed wait time, in seconds (requires the `events_waits_current` consumer)</td>
    </tr>
    <tr>
      <td>`mysql.wait_event_type`</td>
      <td>Top-level wait classification derived from the wait event name (`io`, `lock`, `synch`), or `CPU`/`User sleep`/`other` when not actually waiting. Paired with `mysql.wait_event`.</td>

    <tr>
      <td>`mysql.wait_event`</td>
      <td>Detailed wait breakdown: the wait event name with its category segment stripped (for example, `table/sql/handler`, `mutex/innodb/checkpoint_state`), or `CPU`/`User sleep`/`other` when not actually waiting. Paired with `mysql.wait_event_type`.</td>
    </tr>
    <tr>
      <td>`mysql.wait_type`</td>
      <td>Raw, unprocessed name of the instrument that produced the wait event. For the parsed/categorized breakdown, see `mysql.wait_event_type` / `mysql.wait_event`.</td>

      <td>`mysql.session.status`</td>
      <td>`waiting`, `running`, or `other`</td>

      <td>`client.address` / `client.port`</td>
      <td>Client host/port (port populated on MySQL 8.0.22+ only, else `0`)</td>

      <td>`network.peer.address` / `network.peer.port`</td>
      <td>Same, as network-layer attributes</td>
    </tr>
    <tr>
      <td>`mysql.blocking.blockers`</td>
      <td>JSON array of `{thread_id, session_id}` tuples, one per concurrent InnoDB row-lock blocker for this session (not just the first, if more than one exists). `"[]"` when not blocked; a blocker's `session_id` is `null` if it disconnected before it could be resolved.</td>
    </tr>
    <tr>
      <td>`mysql.blocking.blocker.count`</td>
      <td>Integer count of concurrent blockers. `0` means not blocked.</td>
    </tr>
    <tr>
      <td>`mysql.session.client_name`</td>
      <td>Client driver's self-reported identity (for example, `MySQL Connector/J`), from `session_connect_attrs`. Empty if the driver doesn't send connect attributes.</td>

</Callout>

  <Collapser
    id="top-query"
    title="Top queries"
  >

The queries consuming the most execution time, aggregated server-side by MySQL's own `performance_schema.events_statements_summary_by_digest`: a true per-digest execution counter, not a sample count. Disabled by default.
You can set the `db.server.top_query` to `true` to enable top query collection.

Use the `top_query_collection` block to tune its behavior:

```yaml
top_query_collection:
  lookback_time: 60
  max_query_sample_count: 5000
  top_query_count: 200
  collection_interval: 60s
  query_plan_cache_size: 1000
  query_plan_cache_ttl: 1h
  allowed_comment_keys: [nr_service_guid]
```

**Available parameters**

<table>
  <thead>
    <tr>
      <th>Parameter</th>
      <th>Description</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>`lookback_time`</td>
      <td>The time window, in seconds, in which to query for top queries. Queries that finished execution outside the lookback window aren't included in the collection. Increasing this value helps capture long-running queries. The default value is 2 times the `collection_interval`</td>
    </tr>
    <tr>
      <td>`max_query_sample_count`</td>
      <td>The maximum number of records to fetch in a single run. The default value is set to `1000`</td>
    </tr>
    <tr>
      <td>`top_query_count`</td>
      <td>The maximum number of active queries to report in a single run. The default value is set to `200`</td>
    </tr>
    <tr>
      <td>`collection_interval`</td>
      <td>The interval at which top queries are emitted by this receiver. The default value is set to `60s`</td>
    </tr>
    <tr>
      <td>`query_plan_cache_size`</td>
      <td>The size of the query plan cache used to store EXPLAIN results. The default value is set to `1000`</td>
    </tr>
    <tr>
      <td>`query_plan_cache_ttl`</td>
      <td>How long a cached query plan stays valid before the receiver re-runs EXPLAIN to refresh it. The default value is set to `1h`</td>
    </tr>
    <tr>
      <td>`allowed_comment_keys`</td>
      <td>Keys to extract from leading SQL comments for APM-DB correlation</td>
    </tr>
  </tbody>
</table>

  <Collapser
    id="query-plan"
    title="Query plans"
  >

Execution plan for a statement, reported as its own event so the plan can be filtered, routed, or dropped independently of `top_query`'s/`query_sample`'s own statistics. Requires at least one of `db.server.top_query` or `db.server.query_sample` to also be enabled. Once enabled, `mysql.query_plan` is no longer carried on `db.server.top_query`/`db.server.query_sample` records. See [Execution plan collection](#explain) for `EXPLAIN` mechanics.
You can set the `db.server.query_plan` to `true` to enable query plan collection.

<table>
  <thead>
    <tr>
      <th>Attribute</th>
      <th>Description</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>`db.system.name`</td>
      <td>`mysql`</td>
    </tr>
    <tr>
      <td>`db.namespace`</td>
      <td>The default database/schema for the query. On query samples this is the thread's current database (`processlist_db`); on top queries it's the digest's `SCHEMA_NAME`. Empty when no default database was selected.</td>
    </tr>
    <tr>
      <td>`mysql.query_plan.hash`</td>
      <td>Set to the same value as `mysql.events_statements_summary_by_digest.digest` (query digest) by design</td>
    </tr>
    <tr>
      <td>`mysql.query_plan.source`</td>
      <td>The event the plan was reported for (`db.server.top_query` or `db.server.query_sample`), so plans can be routed or dropped per source event</td>
    </tr>
    <tr>
      <td>`mysql.query_plan`</td>
      <td>The query plan for the statement, if available</td>
    </tr>
  </tbody>
</table>

If a captured statement is truncated (ends in `...`), `EXPLAIN` is skipped on every version. See [Recommended server parameters](/docs/opentelemetry/db360/mysql/compatibility#params).

<table>
  <thead>
    <tr>
      <th>`explain_mode`</th>
      <th>Behavior</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>`inline` (default)</td>
      <td>Runs `EXPLAIN FORMAT=json <statement>` directly; sufficient for `SELECT`-only workloads</td>
    </tr>
    <tr>
      <td>`procedure`</td>
      <td>Routes through a `SQL SECURITY DEFINER` procedure (`<schema>.explain_statement`) so write statements (`UPDATE`/`DELETE`/`INSERT`/`REPLACE`) can be explained without granting DML to the monitoring user. Falls back to `inline` if the procedure is missing. Requires the one-time setup step per schema. See [Query plans for write statements](/docs/opentelemetry/db360/mysql/optional#query).</td>
    </tr>
  </tbody>
</table>

<Callout variant="important">
`mysql.query_plan` is the raw `EXPLAIN FORMAT=json` output, wrapped in a one-element JSON array before caching, so New Relic's log ingest doesn't auto-flatten and destroy it. Parse index `[0]` to recover the plan object.
</Callout>
