Troubleshoot common issues you may encounter when monitoring your PostgreSQL with the NRDOT Collector.

## Test connectivity

### Test network connectivity to PostgreSQL

```bash
psql --host=<YOUR_DB_HOST> --port=<YOUR_DB_PORT> --username=<YOUR_DB_USERNAME> --dbname=<YOUR_DATABASE_NAME> --command 'SELECT 1;'
```

A successful connection and result confirms the monitoring user, host, and port are reachable before troubleshooting the collector itself.

### Test OTLP endpoint connectivity

Verify the NRDOT Collector can reach New Relic's OTLP endpoint:

```bash
curl -v <YOUR_NEWRELIC_OTLP_ENDPOINT>
```

## Common issues

<CollapserGroup>

<Collapser
  id="no-query-events"
  title="No db.server.query_sample or db.server.top_query events"
>

**Symptoms:** Missing query sample and top query log events in New Relic.

**Possible causes:**
- Query events not enabled in receiver configuration
- `pg_stat_statements` extension missing
- Insufficient database privileges

**Solutions:**

1. **Enable query events in receiver configuration:**
   ```yaml
   events:
     db.server.query_sample:
       enabled: true
     db.server.top_query:
       enabled: true
   ```

2. **Verify `pg_stat_statements` extension exists:**
   ```sql
   SELECT * FROM pg_extension WHERE extname = 'pg_stat_statements';
   ```
   If missing, create it in each database:
   ```sql
   CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
   ```

3. **Check database privileges:**
   ```sql
   SELECT * FROM pg_roles WHERE rolname = '<YOUR_DB_USERNAME>';
   ```
   Should show `pg_monitor` role membership.

</Collapser>

<Collapser
  id="missing-extensions"
  title="pg_stat_statements extension not available"
>

**Symptoms:** Error creating `pg_stat_statements` extension or `db.server.top_query` events missing entirely.

**Cause:** `shared_preload_libraries` doesn't include `pg_stat_statements` or PostgreSQL restart required.

**Solutions:**

**For self-managed PostgreSQL:**
1. Add to `postgresql.conf`:
   ```ini
   shared_preload_libraries = 'pg_stat_statements'
   ```
2. Restart PostgreSQL:
   ```bash
   sudo systemctl restart postgresql-*
   ```

{/* **For AWS RDS:**
1. Modify your RDS parameter group to include:
   ```
   shared_preload_libraries = pg_stat_statements
   ```
2. Apply the parameter group and restart the RDS instance. */}

</Collapser>

<Collapser
  id="missing-query-plans"
  title="Query plans missing for some queries"
>

**Symptoms:** `postgresql.query_plan` is empty for some queries in `db.server.top_query` events.

**Possible causes:**
- PostgreSQL version < 12 (parameterized EXPLAIN unsupported)
- Write statements without EXPLAIN helper function
- Query text truncated due to parameter limits

**Solutions:**

1. **For PostgreSQL < 12:** Query plans for parameterized queries aren't supported. Upgrade to PostgreSQL 12+ for full EXPLAIN functionality.

2. **For write statements (UPDATE/INSERT/DELETE):** Create the EXPLAIN helper function:
   ```sql
   CREATE OR REPLACE FUNCTION otel.explain_statement(l_query text)
   RETURNS json
   LANGUAGE plpgsql
   SECURITY DEFINER
   AS $$
   -- [Function body from hosted.mdx setup guide]
   $$;
   GRANT EXECUTE ON FUNCTION otel.explain_statement(text) TO otelu;
   ```
   
   Reference it in collector config:
   ```yaml
   top_query_collection:
     explain_function_name: otel.explain_statement
   ```

3. **For long queries:** Increase PostgreSQL parameters:
   ```sql
   ALTER SYSTEM SET track_activity_query_size = 4096;
   SELECT pg_reload_conf();
   ```

</Collapser>

<Collapser
  id="missing-function-metrics"
  title="postgresql.function.calls always empty"
>

**Symptoms:** Function call metrics missing or dashboard "Function Calls/min" widget empty.

**Cause:** `track_functions` not set to `pl` or `all` in `postgresql.conf`.

**Solutions:**

1. **For self-managed PostgreSQL:**
   Add to `postgresql.conf`:
   ```ini
   track_functions = all
   ```
   Restart PostgreSQL.

{/* 2. **For AWS RDS:**
   Modify your RDS parameter group:
   ```
   track_functions = all
   ```
   Apply and restart the RDS instance. */}

3. **Enable the metric in collector config:**
   ```yaml
   metrics:
     postgresql.function.calls:
       enabled: true
   ```

</Collapser>

<Collapser
  id="dashboard-widgets-empty"
  title="Several dashboard widgets empty despite metrics flowing"
>

**Symptoms:** Core metrics appear but specific dashboard widgets show no data.

**Cause:** Dashboard metrics are disabled by default and must be explicitly enabled.

**Solution:**
Enable required dashboard metrics:
```yaml
metrics:
  postgresql.database.locks:
    enabled: true
  postgresql.deadlocks:
    enabled: true
  postgresql.function.calls:
    enabled: true
  postgresql.query.conflicts:
    enabled: true
  postgresql.sequential_scans:
    enabled: true
  postgresql.temp.io:
    enabled: true
  postgresql.temp_files:
    enabled: true
```

</Collapser>

<Collapser
  id="entity-missing"
  title="PostgreSQL entity doesn't appear or app→PostgreSQL relationship doesn't resolve"
>

**Symptoms:** 
- PostgreSQL entity missing from Entity Explorer
- APM application doesn't show database relationships

**Cause:** Missing `server.address` and `server.port` resource attributes required for entity synthesis.

**Solution:**
Add a transform processor to your collector configuration:
```yaml
processors:
  transform/postgresql_server_attrs:
    metric_statements:
      - context: resource
        statements:
          - set(resource.attributes["server.address"], Split(resource.attributes["service.instance.id"], ":")[0])
          - set(resource.attributes["server.port"], Int(Split(resource.attributes["service.instance.id"], ":")[1]))
    log_statements:
      - context: resource
        statements:
          - set(resource.attributes["server.address"], Split(resource.attributes["service.instance.id"], ":")[0])
          - set(resource.attributes["server.port"], Int(Split(resource.attributes["service.instance.id"], ":")[1]))

service:
  pipelines:
    metrics:
      receivers: [nrpostgresql]
      processors: [transform/postgresql_server_attrs, batch]
      exporters: [otlphttp/newrelic]
    logs:
      receivers: [nrpostgresql]
      processors: [transform/postgresql_server_attrs, batch]
      exporters: [otlphttp/newrelic]
```

</Collapser>

<Collapser
  id="connection-errors"
  title="Connection refused or authentication errors"
>

**Symptoms:** 
- "Connection refused" errors
- "Access denied" authentication failures

**Solutions:**

**For connection refused:**
1. Verify PostgreSQL is running:
   ```bash
   systemctl status postgresql-*
   ```
2. Check firewall rules allow connections on PostgreSQL port (default 5432)
3. Verify `listen_addresses` in PostgreSQL configuration allows connections from collector host

**For authentication errors:**
1. Verify user exists and has correct privileges:
   ```sql
   SELECT rolname, rolsuper FROM pg_roles WHERE rolname='<YOUR_DB_USERNAME>';
   \du <YOUR_DB_USERNAME>
   ```
2. Check password is correct
{/* 3. For RDS, ensure security group allows inbound connections */}

</Collapser>

{/* <Collapser
  id="rds-specific-issues"
  title="AWS RDS specific issues"
>

**RDS parameter group issues:**
- Verify `shared_preload_libraries = 'pg_stat_statements'` in your RDS parameter group
- Changes require an instance restart, not just a parameter reload
- Use RDS console or CLI to apply parameter group changes

**RDS extension limitations:**
- Extensions must be created per database individually
- Some extensions may not be available depending on RDS PostgreSQL version
- Check AWS documentation for supported extensions

**RDS network security:**
- Ensure your RDS security group allows inbound traffic on port 5432 from the NRDOT Collector's IP address or security group
- Verify VPC routing if collector is in different subnet

**RDS monitoring limitations:**
- Some system-level metrics may not be available compared to self-managed PostgreSQL
- WAL metrics (`postgresql.wal.age`, `postgresql.wal.lag`) require replication setup

</Collapser> */}

<Collapser
  id="empty-comment-tags"
  title="db.query.comment_tags.nr_service_guid always empty"
>

**Symptoms:** APM correlation tags are not being extracted from SQL comments.

**Cause:** Comment tag extraction is not configured.

**Solution:**
Add `allowed_comment_keys` to both collection blocks in your configuration:
```yaml
query_sample_collection:
  allowed_comment_keys: [nr_service_guid]
top_query_collection:
  allowed_comment_keys: [nr_service_guid]
```

Comment tag extraction is empty by default for security reasons.

</Collapser>

<Collapser
  id="table-metrics-missing"
  title="Table/index/function metrics missing for some tables"
>

**Symptoms:** Metrics available for some tables but not others in the same database.

**Cause:** Monitoring user lacks `SELECT` privileges on those tables/schemas.

**Solution:**
Grant access to additional schemas:
```sql
GRANT USAGE ON SCHEMA <schema_name> TO otelu;
GRANT SELECT ON ALL TABLES IN SCHEMA <schema_name> TO otelu;
```

Note: `pg_monitor` grants stat-visibility, not object-level `SELECT` privileges.

</Collapser>

## NRQL query examples

Use these NRQL queries to troubleshoot and verify your PostgreSQL monitoring:

### Check for blocked queries
```sql
FROM Log SELECT * WHERE event.name = 'db.server.query_sample' 
AND postgresql.blocking.pids IS NOT NULL 
SINCE 1 hour ago
```

### Find slowest queries
```sql
FROM Log SELECT db.query.text, 
postgresql.total_exec_time,
postgresql.calls
WHERE event.name = 'db.server.top_query'
ORDER BY postgresql.total_exec_time DESC
LIMIT 10
```

### Verify entity synthesis
```sql
FROM Metric SELECT uniqueCount(entity.guid) 
WHERE metricName LIKE 'postgresql.%' 
FACET server.address, server.port
SINCE 1 hour ago
```

### Check connection usage
```sql
FROM Metric SELECT latest(postgresql.backends) 
WHERE metricName = 'postgresql.backends' 
FACET db.namespace 
TIMESERIES
```

## Getting help

If you continue experiencing issues:

1. Check the NRDOT Collector logs:
   ```bash
   journalctl -u nrdot-collector -f
   ```

2. Verify your configuration syntax:
   ```bash
   nrdot-collector --config-validate --config-file=<your-config-file>
   ```

3. Review our [compatibility requirements](/docs/opentelemetry/database/postgresql/compatibility)

4. Contact New Relic support with your collector logs and configuration (remove sensitive information like passwords)
