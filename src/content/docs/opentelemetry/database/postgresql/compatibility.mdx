Before you begin monitoring your PostgreSQL with NRDOT, ensure your environment meets these requirements.

## Prerequisites

Before you begin, ensure you have the following:

* PostgreSQL `14` and above
* Valid New Relic [license key](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key)
* Network connectivity between the NRDOT Collector and your database
* Postgres additional supplied modules installed. For most installations, this is included by default, but less conventional installations might require an additional installation of your version of [the postgresql-contrib package](https://www.postgresql.org/docs/current/contrib.html)
* This integration is available as a part of New Relic public preview program. Check with your Organization Manager to opt in from the [Previews & Trials](https://one.newrelic.com/admin-portal/promotion-management/home) page


## Required grants

### Cluster-wide grants (one-time setup)

The monitoring user needs these cluster-wide privileges:

```sql
CREATE USER otelu WITH LOGIN PASSWORD '<USER_PASSWORD>';
GRANT SELECT ON pg_stat_database TO otelu;
GRANT pg_monitor TO otelu;
```

The `pg_monitor` role (PostgreSQL 10+) grants access to `pg_read_all_stats`, `pg_read_all_settings`, and full `pg_stat_activity`/`pg_locks` visibility, required for `db.server.query_sample`.

### Per-database grants

Some grants must be repeated **in every database** you want to monitor, as PostgreSQL privileges and extensions are database-scoped:

```sql
GRANT USAGE ON SCHEMA public TO otelu;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO otelu;
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

For additional schemas beyond `public`:
```sql
GRANT USAGE ON SCHEMA <schema_name> TO otelu;
GRANT SELECT ON ALL TABLES IN SCHEMA <schema_name> TO otelu;
```

### Optional grants for enhanced monitoring

For pgvector metrics (requires PostgreSQL 13+ and pgvector extension):
```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

## Recommended server parameters [#params]

Configure the following [parameters](https://www.postgresql.org/docs/current/config-setting.html) and then restart the server for the settings to take effect. For more information about these parameters, see the [Postgres documentation](https://www.postgresql.org/docs/current/pgstatstatements.html).

### Self-hosted

Configure these parameters in the `postgresql.conf` file.

**Required parameters**

<table>
  <thead>
    <tr>
      <th>Parameter</th>
      <th>Recommended value</th>
      <th>Why</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>`shared_preload_libraries`</td>
      <td>`pg_stat_statements`</td>
      <td>Enables collection of query metrics using the [pg_stat_statements](https://www.postgresql.org/docs/current/pgstatstatements.html) extension</td>
    </tr>
    <tr>
      <td>`track_activity_query_size`</td>
      <td>`4096`</td>
      <td>Required for collection of larger queries. Increases the size of SQL text in `pg_stat_activity`. If left at the default value, queries longer than `1024` characters aren't collected</td>
    </tr>
    <tr>
      <td>`pg_stat_statements.track`</td>
      <td>`ALL`</td>
      <td>Enables tracking of statements within stored procedures and functions</td>
    </tr>
    <tr>
      <td>`pg_stat_statements.max`</td>
      <td>`10000`</td>
      <td>Increases the number of normalized queries tracked in `pg_stat_statements`. Recommended for high-volume databases that see many different types of queries from many different clients</td>
    </tr>
    <tr>
      <td>`pg_stat_statements.save`</td>
      <td>`on`</td>
      <td>Saves statistics across server restarts</td>
    </tr>
  </tbody>
</table>

**Optional parameters**

<table>
  <thead>
    <tr>
      <th>Parameter</th>
      <th>Recommended value</th>
      <th>Why</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>`track_functions`</td>
      <td>`all`</td>
      <td>Required for `postgresql.function.calls` — without it, `pg_stat_user_functions` stays empty</td>
    </tr>
    <tr>
      <td>`pg_stat_statements.track_utility`</td>
      <td>`off`</td>
      <td>Disables tracking of utility commands like `PREPARE` and `EXPLAIN`, so only queries like `SELECT`, `UPDATE`, and `DELETE` are tracked</td>
    </tr>
  </tbody>
</table>

<Callout variant="important">
On RDS/Aurora, `track_activity_query_size` and `pg_stat_statements.max` are static parameters — even when applying them via a parameter group at instance creation, AWS requires `apply_method: pending-reboot` for them (immediate apply fails with `InvalidParameterCombination`). A reboot is required for these two to take effect either way.
</Callout>

<Callout variant="important">
On Aurora, the DB parameter group family name encodes the major version (for example, `aurora-postgresql14`, `aurora-postgresql16`) and must match the cluster or instance's engine version exactly — AWS rejects instance creation with `InvalidParameterCombination` if they don't match. There is no single family that works across versions.
</Callout>
