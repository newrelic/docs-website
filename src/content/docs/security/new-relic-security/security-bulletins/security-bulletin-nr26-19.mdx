<DNT>**Vulnerability Identifier:**</DNT> NR26-19

<DNT>**Priority:**</DNT> Critical

## Summary

On November 18, 2026, nginx disclosed vulnerabilities in its HTTP/2 module, known together as "nginx2root". F5 rates the two main issues 9.2 (Critical) under CVSS v4.0.

CVE-2026-123007 affects nginx 1.9.5 through 1.31.8. When nginx processes specially crafted HTTP/2 traffic, its flow-control window can exceed the allowed limit, which can cause a heap buffer overflow. An unauthenticated attacker can crash the nginx worker process or corrupt its memory. If ASLR is disabled or the attacker can bypass it, the attacker can also run code.

CVE-2026-123633 affects nginx 1.19.7 through 1.31.8 when nginx accepts HTTP/2 client connections and proxies requests to a backend. A specially crafted request can cause a use-after-free in a worker process that is running low on `worker_connections`. This can lead to a denial of service or, with an ASLR bypass, code execution.

Fixes for both vulnerabilities are in nginx 1.30.7 (stable) and 1.31.9 (mainline), and in NGINX Plus PLS.37.0.8.1 and PLS.37.3.0.1. The same release fixes several other nginx vulnerabilities, some of which do not involve HTTP/2. A later release, nginx 1.30.8 and 1.31.10, also fixes CVE-2026-132779. Public exploit details are available. As of November 24, 2026, CISA's Known Exploited Vulnerabilities catalog does not list these vulnerabilities.

**New Relic agents and integrations, including the New Relic nginx integration (nri-nginx), do not include nginx and are not affected.** New Relic has updated nginx on its internet-facing services that use it. New Relic has not identified evidence of exploitation in its environment.

## Action Recommended

No action is required for your New Relic services or for New Relic agents and integrations you have installed. Nonetheless, New Relic strongly encourages customers who run nginx with HTTP/2 enabled on their own environment upgrade to the latest nginx release (1.30.8 stable or 1.31.10 mainline), to NGINX Plus PLS.37.0.8.1 or PLS.37.3.0.1 or later, or to a Linux distribution package that includes the fixes.

### Recommendations

- Upgrade internet-facing servers with HTTP/2 enabled first. HTTP/2 is enabled when a `listen` directive includes `http2` or when `http2 on;` is set.
- Restart nginx after upgrading so the patched binary runs.
- Rebuild and redeploy container images that include nginx. Patching the host does not update nginx inside containers.
- **Linux distribution packages:** distributions often add fixes without changing the upstream version number. Ubuntu published fixed packages for all supported releases on November 19, 2026. For other distributions, check your vendor's advisory for CVE-2026-123007 and CVE-2026-123633.
- Products that embed nginx, such as Kubernetes ingress controllers, gateways and appliances: check with the vendor or project for a release that includes the fixes.
- If you deployed one of the example or demo applications that New Relic publishes on GitHub and it uses the public nginx image, rebuild it from a current nginx image.

## Temporary Mitigation

Only an upgrade fully fixes these vulnerabilities, along with the others fixed in the same release. Until you can upgrade:

- Disable HTTP/2 on affected listeners and reload nginx. Both vulnerabilities require HTTP/2. To disable it, remove `http2` from `listen` directives or set `http2 off;`. Clients fall back to HTTP/1.1.

## Frequently asked questions

1. **Does this affect New Relic's agents or integrations?**

   No. New Relic agents and integrations do not include nginx. The New Relic nginx integration (nri-nginx) collects metrics from the nginx server you run. It does not include nginx.

2. **Do I need to update the New Relic nginx integration?**

   No. Upgrade nginx itself.

3. **Some New Relic Helm charts reference an image named `ingress-nginx/kube-webhook-certgen`. Is it affected?**

   No. That image is a certificate-generation utility from the Kubernetes ingress-nginx project and does not contain nginx.

4. **How do I know whether my nginx is affected?**

   First, check whether HTTP/2 is enabled: run `nginx -T | grep http2`. Then check the version:

   - If you installed nginx from nginx.org or built it yourself, run `nginx -v`. You are affected if the version is 1.9.5 or later and earlier than 1.30.7 (stable) or 1.31.9 (mainline).
   - If you installed nginx from your Linux distribution, the version number alone doesn't tell you whether you're protected. Compare the installed package version (for example, `dpkg -l | grep nginx` or `rpm -q nginx`) with your distribution's advisory.

5. **How can I tell if my systems have been targeted?**

   The malicious HTTP/2 traffic does not show up as normal requests in access logs. Exploitation attempts typically crash an nginx worker process. Watch the nginx error log for worker processes that exit on signal 11 (a segmentation fault). If you forward nginx logs to New Relic, you can create an alert on this message. Also look for nginx worker processes that start shells or other unexpected child processes.

6. **Has New Relic seen evidence of exploitation?**

   We haven't identified indicators of exploitation of these vulnerabilities in our environment.

7. **I have questions about these vulnerabilities. Who should I contact?**
