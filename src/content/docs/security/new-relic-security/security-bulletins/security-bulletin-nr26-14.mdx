<DNT>**Vulnerability Identifier:**</DNT> NR26-14

<DNT>**Priority:**</DNT> High

## Summary

Between October 17 and October 20, 2026, researchers disclosed that the private keys for eight intermediate certificate authority (CA) certificates issued by eMudhra can be recovered (CVE-2026-111943). Anyone with those keys can create certificates that software would accept as genuine if it still trusts them. Browsers and operating systems have blocked the certificates, but software that carries its own list of trusted CAs, including some container images, needs to be updated.

New Relic has updated the Kubernetes components below so they no longer accept certificates issued by these CAs. The updated versions are not picked up automatically. Customers need to upgrade to the versions listed below.

## Technical vulnerability information

[CVE-2026-111943](https://www.cve.org/CVERecord?id=CVE-2026-111943)

Eight intermediate CAs that chain to the emSign ECC Root CA - G3 and, through cross-signing, to AAA Certificate Services, are affected.

- The fixed Alpine-based images are built on Alpine 3.24.3 with ca-certificates 20261020-r0, which removes emSign ECC Root CA - G3 and AAA Certificate Services from the CA bundle.
- k8s-agents-operator 0.54.0 is built on a distroless base with both roots removed.
- prometheus:v3.15.1 (upstream) also ships a CA bundle without either root.
- New Relic Kubernetes integration binaries are built with Go 1.27.3, whose TLS library refuses certificate chains that contain the eight affected keys, even if the root is still trusted. Some on-host integrations bundled in infrastructure-bundle use earlier Go versions; their CA bundle is still fixed.
- The exposure is limited to connections that use the public root store: the agents' connections to New Relic endpoints and to any configured proxy. Connections inside the cluster (Kubernetes API server, kubelet, control plane) use the cluster's own CA and aren't affected.
