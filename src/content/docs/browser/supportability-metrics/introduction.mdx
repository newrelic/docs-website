Browser supportability metrics are a specialized set of metrics that help you understand the health and performance of your New Relic browser agents. They're distinct from [APM supportability metrics](/docs/apm/supportability-metrics/introduction) and [mobile supportability metrics](/docs/mobile-monitoring/supportability-metrics/introduction): browser supportability metrics are specific to the browser agent, providing insight into how the agent operates within your users' browsers.

These metrics are automatically collected by the browser agent about its own operation, offering insight into agent behavior, feature adoption, and the effectiveness of your monitoring configuration across your web applications.

<Callout variant="important">
  You're charged for supportability metric ingest as part of your New Relic data consumption. These metrics provide valuable troubleshooting and optimization information that can help you resolve issues faster and improve page performance.
</Callout>

## What are browser supportability metrics used for? [#what-are-browser-supportability-metrics]

Browser supportability metrics provide essential data for maintaining optimal monitoring of your web applications. They help you:

* **Troubleshoot monitoring issues**: Identify why certain data might not be appearing in your New Relic dashboards for your browser apps
* **Validate configuration**: Confirm that features like Session Replay, Session Trace, or SPA monitoring are working correctly in your users' browsers
* **Monitor agent performance**: Track harvest success rates and identify when data is being dropped or buffered
* **Optimize feature usage**: Understand which agent APIs and frameworks your application is using
* **Track agent health**: Monitor connection status to New Relic's beacon and collector endpoints, and the success rates of data transmission from your browser agent

## Identifying browser supportability metrics [#identifying-metrics]

Unlike other New Relic agents, browser supportability metrics use a `Browser/Supportability/` prefix (rather than a bare `Supportability/` prefix). You can identify and query them using [NRQL](/docs/nrql/get-started/introduction-nrql-new-relics-query-language/) by searching for this prefix.

<Callout variant="tip">
  In New Relic's Data Explorer, browser supportability metrics are listed under the **Metrics** section rather than **Timeslice**. Filter by your Browser application and search for `Supportability` to explore which metrics your agent is actually reporting.
</Callout>

## Common categories and examples of browser supportability metrics [#metric-categories]

### API usage metrics

Track which browser agent JavaScript APIs your application is calling.

**Example metrics:**
* `Browser/Supportability/API/addPageAction/called`: Tracks `addPageAction()` calls
* `Browser/Supportability/API/noticeError/called`: Tracks `noticeError()` calls
* `Browser/Supportability/API/setCustomAttribute/called`: Tracks `setCustomAttribute()` calls
* `Browser/Supportability/API/setUserId/called`: Tracks `setUserId()` calls
* `Browser/Supportability/API/setPageViewName/called`: Tracks `setPageViewName()` calls
* `Browser/Supportability/API/setErrorHandler/called`: Tracks custom error handler registration
* `Browser/Supportability/API/addToTrace/called`: Tracks `addToTrace()` calls for custom trace timing
* `Browser/Supportability/API/recordCustomEvent/called`: Tracks `recordCustomEvent()` calls
* `Browser/Supportability/API/interaction/called`: Tracks manual SPA `interaction()` calls
* `Browser/Supportability/API/recordReplay/called` and `pauseReplay/called`: Track manual Session Replay start/pause calls
* `Browser/Supportability/API/logging/{level}/called`: Tracks manual logging calls by level (`error`, `warn`, `info`, `debug`, `trace`)
* `Browser/Supportability/API/register/called`: Tracks usage of the micro-agent registration API, with sub-metrics like `Browser/Supportability/API/register/addPageAction/called` for calls made through a registered instance

### Harvester and data transmission metrics

Track whether the agent could successfully send data to New Relic.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/Harvester/Retry/Failed/{status code}` | A harvest retry failed with a given HTTP status (for example, `429`, `500`, `503`) | Repeated failures for a given status code indicate a persistent connectivity or server-side issue |
| `Browser/Supportability/Harvester/Retry/Succeeded/{status code}` | A harvest retry succeeded after initially failing with a given HTTP status | High retry-success counts suggest transient network issues rather than a hard failure |
| `Browser/Supportability/Harvester/Retry/Attempted/{event type}` | A retry was attempted for a specific data type (for example, `ajax`, `jserrors`, `session_replay`, `session_trace`, `spa`) | Helps identify which data type is experiencing delivery problems |

### Session metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/Session/Duration/Ms` | Duration of the browser session in milliseconds | Useful for understanding typical session length across your user base |
| `Browser/Supportability/Session/Expired/Seen` | A browser session expired | Expected behavior over time; sudden spikes can indicate unusually short user sessions |
| `Browser/Supportability/Session/Inactive/Seen` | A browser session was marked inactive | High volumes can indicate many idle tabs or background sessions |
| `Browser/Supportability/Session/Expired/SessionReplay/Seen` | A session expired while Session Replay was active | Helps correlate replay availability with session length |
| `Browser/Supportability/Session/RaceCondition/Seen` | A race condition was detected in session handling | Non-zero values can indicate multiple tabs modifying session state simultaneously |

### Ajax metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/Ajax/Events/Excluded/Agent` | An AJAX event was excluded by the agent itself | Expected for requests to the agent's own beacon/collector endpoints |
| `Browser/Supportability/Ajax/Events/Excluded/App` | An AJAX event was excluded by your application's configuration | Confirms your `ajax.deny_list` or similar filtering configuration is active |
| `Browser/Supportability/Ajax/Events/GraphQL/Bytes-Added` | GraphQL-specific metadata was added to an AJAX event payload | Confirms GraphQL request/response capture is active |
| `Browser/Supportability/Ajax/CrossApplicationTracing/Header/Seen` | A legacy cross-application tracing header was seen on an AJAX request | Indicates an upstream or downstream service still using the deprecated CAT protocol instead of distributed tracing |

### Generic and feature-detection metrics

Confirm which loader type, distribution method, runtime, and page features the agent detected.

**Example metrics:**
* `Browser/Supportability/Generic/LoaderType/spa/Detected`, `.../pro/Detected`, `.../lite/Detected`: Identify which agent loader type is running
* `Browser/Supportability/Generic/DistMethod/NPM/Detected` and `.../CDN/Detected`: Identify how the agent was installed
* `Browser/Supportability/Generic/Runtime/Browser/Detected`, `.../Worker/Detected`, `.../IFrame/Detected`: Identify the JavaScript runtime context the agent is running in
* `Browser/Supportability/Generic/BFCache/PageRestored`: Tracks pages restored from the browser's back/forward cache
* `Browser/Supportability/Generic/Performance/mark/Seen` and `measure/Seen`: Track usage of the Performance API's custom marks and measures
* `Browser/Supportability/Generic/TimeKeeper/ClockDrift/Detected`: Flags detected drift between the browser's clock and New Relic server time
* `Browser/Supportability/Generic/WebDriver/Detected`: Flags automated/headless browser traffic (for example, from test suites or bots)
* `Browser/Supportability/Generic/Resources/Ajax/Internal` and `.../External`: Track first-party versus third-party AJAX resource usage

### Framework detection metrics

The agent detects common frontend frameworks so it can apply framework-specific instrumentation.

**Example metrics:**
* `Browser/Supportability/Framework/React/Detected`
* `Browser/Supportability/Framework/NextJS/Detected`
* `Browser/Supportability/Framework/Vue/Detected`
* `Browser/Supportability/Framework/Angular/Detected`
* `Browser/Supportability/Framework/Ember/Detected`
* `Browser/Supportability/Framework/Svelte/Detected`

<Callout variant="tip">
  Framework detection metrics are useful for confirming [SPA monitoring](/docs/browser/single-page-app-monitoring/get-started/introduction-single-page-app-monitoring/) is correctly identifying your application's frontend stack.
</Callout>

### Logging metrics

Track the health of [browser logs](/docs/browser/browser-monitoring/browser-pro-features/browser-logs/view-browser-logs/) collection.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/Logging/Harvest/Failed/Seen` | A log harvest failed | Non-zero values indicate log data is being lost |
| `Browser/Supportability/Logging/Event/Dropped/Sampling` | A log event was dropped due to sampling | Expected under high log volume; consider adjusting your logging configuration if too much data is dropped |
| `Browser/Supportability/Logging/Event/API/Added` | A log event was added via the logging API | Confirms manual logging calls are being captured |
| `Browser/Supportability/Logging/Event/Auto/Added` | A log event was automatically captured (for example, from `console`) | Confirms automatic log capture is active |
| `Browser/Supportability/Logging/Abort/Reset` | Logging was aborted and reset | Investigate if this correlates with missing log data |

### Session Replay metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/SessionReplay/Abort/Entitlement` | Session Replay was aborted because the account isn't entitled to the feature | Confirms whether your subscription includes Session Replay |
| `Browser/Supportability/SessionReplay/Abort/Too-Many` | Session Replay was aborted because too many sessions were recording concurrently | Review your sampling rate configuration |
| `Browser/Supportability/SessionReplay/Abort/Too-Big` | Session Replay was aborted because the recording exceeded size limits | Indicates a page with very high DOM mutation volume |
| `Browser/Supportability/SessionReplay/Abort/Cross-Tab` | Session Replay was aborted due to a conflict across multiple tabs | Expected when a user has multiple tabs of your app open simultaneously |
| `Browser/Supportability/SessionReplay/EnabledNotEntitled/Detected` | Session Replay is enabled in configuration but the account isn't entitled | Check your Session Replay entitlement and configuration |
| `Browser/Supportability/SessionReplay/Harvest/Attempts` | Number of Session Replay harvest attempts | Baseline for comparing against harvester failure metrics |

### SPA and soft navigation metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/Spa/Interaction/InitialPageLoad/Duration/Ms` | Duration of the initial page load interaction | Useful for understanding SPA startup performance |
| `Browser/Supportability/Spa/Interaction/RouteChange/Duration/Ms` | Duration of a SPA route-change interaction | High values can indicate slow client-side route transitions |
| `Browser/Supportability/SoftNav/Interaction/InitialPageLoad/Duration/Ms` | Duration of the initial page load, tracked via soft navigation detection | Compare against the legacy SPA metric if migrating between monitoring modes |
| `Browser/Supportability/SoftNav/Interaction/RouteChange/Duration/Ms` | Duration of a soft-navigation route change | High values can indicate slow client-side route transitions |
| `Browser/Supportability/SoftNav/Interaction/TimeOut` | A soft navigation interaction timed out | Non-zero values can indicate interactions that never reach a stable end state |

### Error and event buffer metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/Internal/Error/Rrweb` | An internal error occurred in the Session Replay recording library | Non-zero values can indicate a Session Replay recording issue on specific pages |
| `Browser/Supportability/Internal/Error/Other` | An unclassified internal agent error occurred | Investigate agent console warnings for more detail |
| `Browser/Supportability/EventBuffer/Combined/Dropped/Bytes` | Bytes dropped across all event buffers because they exceeded capacity | Non-zero values indicate data loss; consider reducing event volume or increasing harvest frequency |
| `Browser/Supportability/EventBuffer/ajax/Dropped/Bytes` | Bytes dropped from the AJAX event buffer | Indicates AJAX data loss specifically |

### User action metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/UserAction/RageClick/Seen` | A rage click (rapid repeated clicks) was detected | High volumes can indicate a frustrating or broken UI element |
| `Browser/Supportability/UserAction/DeadClick/Seen` | A dead click (a click with no visible effect) was detected | High volumes can indicate unresponsive UI elements |
| `Browser/Supportability/UserAction/ErrorClick/Seen` | A click that triggered a JavaScript error was detected | Correlate with JS error data to find problematic UI interactions |

### Connect and beacon response metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Browser/Supportability/BCS/Error/{status code}` | The browser configuration service (BCS) returned an error on connect | Non-200-series values indicate the agent couldn't retrieve its configuration |
| `Browser/Supportability/BCS/Error/Duration/Ms` | Time taken for a failed BCS connect request | High values can indicate network latency to the configuration endpoint |

## Querying browser supportability metrics [#querying-metrics]

Use NRQL to analyze your browser supportability metrics.

<CollapserGroup>
  <Collapser
    id="query-api-usage"
    title="See which browser agent APIs are being used"
  >
    ```sql
    SELECT uniques(metricName)
    FROM Metric
    WHERE metricName LIKE 'Browser/Supportability/API/%/called'
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-harvester-failures"
    title="Check for harvest failures by status code"
  >
    ```sql
    SELECT count(*)
    FROM Metric
    WHERE metricName LIKE 'Browser/Supportability/Harvester/Retry/Failed/%'
    FACET metricName
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-session-replay"
    title="Find why Session Replay recordings were aborted"
  >
    ```sql
    SELECT count(*)
    FROM Metric
    WHERE metricName LIKE 'Browser/Supportability/SessionReplay/Abort/%'
    FACET metricName
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-all-browser-supportability"
    title="List all supportability metrics for your account"
  >
    ```sql
    SELECT uniques(metricName)
    FROM Metric
    WHERE metricName LIKE 'Browser/Supportability/%'
    SINCE 1 day ago
    LIMIT MAX
    ```
  </Collapser>
</CollapserGroup>

## Troubleshooting with browser supportability metrics [#troubleshooting]

| Problem | What to check | Key metrics to monitor |
|---------|---------------|------------------------|
| **Data not appearing in dashboards** | Harvest failures and beacon connectivity | `Browser/Supportability/Harvester/Retry/Failed/*`, `Browser/Supportability/BCS/Error/*` |
| **Session Replay not recording** | Entitlement, abort reasons, and configuration | `Browser/Supportability/SessionReplay/Abort/*`, `Browser/Supportability/SessionReplay/EnabledNotEntitled/Detected` |
| **SPA interactions missing or inaccurate** | Framework detection and interaction timeouts | `Browser/Supportability/Framework/*/Detected`, `Browser/Supportability/SoftNav/Interaction/TimeOut` |
| **Logs missing from browser logs** | Harvest failures and sampling drops | `Browser/Supportability/Logging/Harvest/Failed/Seen`, `Browser/Supportability/Logging/Event/Dropped/Sampling` |
| **Data loss under high traffic** | Event buffer capacity | `Browser/Supportability/EventBuffer/Combined/Dropped/Bytes` |

### Creating effective dashboards and alerts

To proactively manage your browser application monitoring:

* **Build custom dashboards**: Visualize critical agent health metrics such as harvest success rates, Session Replay abort reasons, and event buffer drops
* **Set up [NRQL alert conditions](/docs/alerts/create-alert/create-alert-condition/create-nrql-alert-conditions/)** for critical supportability metrics, for example:
  * Repeated harvester retry failures for a given data type
  * Spikes in `EventBuffer` dropped bytes
  * Unexpected `SessionReplay/Abort` reasons at scale
  * BCS connect errors indicating configuration delivery problems

## Data retention and costs [#retention-costs]

Browser supportability metrics follow the same [data retention rules](/docs/data-apis/manage-data/manage-data-retention) as other metric data in your New Relic account, and you're charged for their ingest as part of your New Relic data consumption. When planning your monitoring strategy, consider:

* **Volume**: The browser agent reports a significant number of supportability metrics per page view and per session
* **Frequency**: Most metrics report as the related feature or API is used, rather than on a fixed interval
* **Cost optimization**: Use targeted querying and alerting to focus on the most valuable metrics for your specific needs
