Our iOS agent supports distributed tracing. This lets you see how your mobile app activity connects to related services.

## Requirements [#requirements]

To use distributed tracing, you need iOS agent version 7.3.0 or higher. We recommend you use the most recent agent.

## How to set up distributed tracing [#setup]

Distributed tracing is enabled by default — you don't need to do anything to turn it on.

If you prefer to turn it off, see [Distributed tracing](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/configure-settings/#ios-dt) in the mobile SDK API guide, or [Disable distributed tracing](#disable) below.

Distributed tracing headers go out on every instrumented request regardless of other settings. However, for the trace to be linked to a reported `MobileRequest` event (and so show up correlated with your app's network activity in the UI), you also need [Network Request Events](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/configure-settings/#ios-networking) enabled. This is on by default, so it only matters if you've explicitly turned it off.

## Distributed tracing headers [#headers]

Starting with iOS agent version 7.7.8, the agent adds only the [W3C Trace Context](/docs/distributed-tracing/concepts/how-new-relic-distributed-tracing-works/#headers) headers, `traceparent` and `tracestate`, to outgoing network requests. It no longer sends the proprietary `newrelic` header. Earlier agent versions send all three headers.

New Relic APM agents that support W3C Trace Context use these headers to continue the trace, so requests from your app stay connected to the backend services they call. W3C Trace Context is supported in these APM agent versions and higher:

<Callout variant="important">
  If a service, proxy, or gateway between your app and your backend requires the `newrelic` header, update it to accept `traceparent` and `tracestate` instead. </Callout>

## Which requests get distributed tracing automatically [#automatic-instrumentation]

The agent automatically swizzles `NSURLSession` and `NSURLConnection`, so distributed tracing headers are added to requests made through either one with no setup required.

<Callout variant="important">
  If your app uses Swift's `async`/`await` `URLSession` APIs (for example, `data(for:)` or `data(from:)`), they are **not** covered by the default instrumentation. You must explicitly enable `NRFeatureFlag_SwiftAsyncURLSessionSupport` (disabled by default as of agent version 7.4.5) for the agent to add distributed tracing headers to those calls:

The agent does not automatically add distributed tracing headers to:

* `WKWebView`. Web content loaded in a `WKWebView` makes its network requests from within the WebKit process, outside the app's `NSURLSession`/`NSURLConnection` swizzling, so those requests aren't traced automatically. (The agent's separate `WKWebView` instrumentation, on by default, covers page-load timing only, not network headers.)
* Third-party networking libraries that don't route through `NSURLSession` or `NSURLConnection`.
* WebSockets.
* gRPC or other custom transports.

For any of these, use manual propagation.

## Manually propagate distributed tracing [#manual]

If you make a request through an API the agent doesn't auto-instrument, you can still add distributed tracing headers and report the request yourself.

### If something else reports the request

Some frameworks (for example, a native networking library used by a hybrid framework) send the request and report it to New Relic separately. In this case, generate the headers and attach them yourself. Whatever reports the request will recover the trace identity from the W3C headers.

        ```objectivec
        NSMutableURLRequest *request = [NSMutableURLRequest requestWithURL:url];
        NSDictionary<NSString *, NSString *> *headers = [NewRelic generateDistributedTracingHeaders];
        for (NSString *field in headers) {
            [request setValue:headers[field] forHTTPHeaderField:field];
        }
        ```
      </td>
    </tr>

    <tr>
      <td>
        Swift
      </td>

      <td>
        ```swift
        var request = URLRequest(url: url)
        let headers = NewRelic.generateDistributedTracingHeaders()
        for (field, value) in headers {
            request.setValue(value, forHTTPHeaderField: field)
        }
        ```
      </td>
    </tr>
  </tbody>
</table>

### If you both send and report the request

If the same code sends the request and reports it to New Relic (for example, a cross-platform agent), use `generateDistributedTracingContext` instead. It returns one dictionary with the W3C headers to set on the request (`traceparent`, `tracestate`) plus the trace's identity (`trace.id`, `id`, `guid`) to hand back when you report the request, so the reported event is attributed to that trace rather than a new one.

Pass that same dictionary as the `traceHeaders` parameter of [`noticeNetworkRequestForURL:`](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/network-request-success/) or [`noticeNetworkFailureForURL:`](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/network-request-failures/) (select the iOS tab) when you report the completed request — see those pages for the full parameter reference.

## Enable Infinite Tracing [#infinite-tracing]

If your mobile apps have some downstream services that use our tail-based distributed tracing called [Infinite Tracing](/docs/distributed-tracing/infinite-tracing/introduction-infinite-tracing), you should enable this feature for your mobile apps. This ensures that your root span (the initiating mobile app) is included in the rest of the spans tracked by Infinite Tracing.

To set this up, see the [Infinite Tracing steps](/docs/distributed-tracing/infinite-tracing/set-trace-observer) to create a trace observer and to select which mobile apps (data sources) should report spans.

## Find data [#find-data]

Mobile spans appear in any [New Relic distributed tracing UI](/docs/understand-dependencies/distributed-tracing/ui-data/additional-distributed-tracing-features-new-relic-one/) where those spans are part of a trace.

Here are some tips for finding and querying data:

* You can find end-user-originating traces in any [New Relic distributed tracing UI](/docs/understand-dependencies/distributed-tracing/ui-data/additional-distributed-tracing-features-new-relic-one).
* In the distributed tracing UI, end-user spans are indicated with the <img title="New Relic distributed tracing mobile span icon" alt="New Relic distributed tracing mobile span icon" src="/images/mobile_icon_icon.webp" style={{height: "30px", width: "30px"}}/> icon.
* To see a span's attributes, select [a span in the UI](/docs/apm/distributed-tracing/ui-data/understand-use-distributed-tracing-data#span-details).
* Spans are reported as [Span data](/attribute-dictionary/?event=Span), and can be [queried in New Relic](/docs/using-new-relic/data/understand-data/query-new-relic-data).

For example, to find mobile spans for a specific app:

```sql
SELECT count(*) FROM Span WHERE mobileApp.name = 'YOUR_APP_NAME' SINCE 1 day ago
```

To find traces that connect a mobile span to a backend APM span:

```sql
SELECT * FROM Span WHERE mobileApp.name IS NOT NULL AND appName IS NOT NULL SINCE 1 day ago
```

## Troubleshooting [#troubleshooting]

If you don't see mobile spans where you expect them, check these in order:

* **Distributed tracing is disabled.** Confirm you haven't called `disableFeatures` with `NRFeatureFlag_DistributedTracing`. See [How to set up distributed tracing](#setup).
* **The request isn't auto-instrumented.** Requests made through anything other than `NSURLSession` or `NSURLConnection` — including Swift `async`/`await` `URLSession` calls — need either `NRFeatureFlag_SwiftAsyncURLSessionSupport` enabled or [manual propagation](#manual). See [Which requests get distributed tracing automatically](#automatic-instrumentation).
* **The backend APM agent is too old.** If the receiving service's APM agent doesn't support W3C Trace Context yet, it starts a new trace instead of linking to your app's. Check the [minimum APM agent versions](#headers).
* **A proxy or gateway strips the headers.** Anything sitting between your app and the backend needs to pass through `traceparent` and `tracestate` unmodified.
* **`tracestate` is dropped because the trusted account key doesn't match.** If a backend service belongs to a different New Relic account than your mobile app, confirm the account is in the same trust relationship, or the `tracestate` entry may be ignored.

For broader distributed tracing issues, see [Troubleshooting](/docs/apm/distributed-tracing/troubleshooting/troubleshooting-missing-trace-data).
