New Relic Android <InlinePopover type="mobile"/> agents support distributed tracing. This lets you see how your mobile app activity connects to related services.

## Requirements [#requirements]

To use distributed tracing, you need at least Android agent version 6.0.0. We recommend you use the most recent agent.

## How to set up distributed tracing [#setup]

Distributed tracing is enabled by default — you don't need to do anything to turn it on. Distributed tracing headers go out on every auto-instrumented request regardless of other settings.

If you prefer to turn it off, see [Disable distributed tracing](#disable) below.

To see the trace correlated with your app's network activity in New Relic (the reported `MobileRequest` or `MobileRequestError` event), you need [AnalyticsEvents](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/configure-settings/#android-analytics-settings) enabled — this is on by default, and it's a prerequisite for sending any of your app's analytics events, not something specific to distributed tracing.

## Distributed tracing headers [#headers]

Starting with Android agent version 7.8.3, the agent adds only the [W3C Trace Context](/docs/distributed-tracing/concepts/how-new-relic-distributed-tracing-works/#headers) headers, `traceparent` and `tracestate`, to outgoing network requests. It no longer sends the proprietary `newrelic` header. Earlier agent versions send all three headers.

New Relic APM agents that support W3C Trace Context use these headers to continue the trace, so requests from your app stay connected to the backend services they call. W3C Trace Context is supported in these APM agent versions and higher:

## Which requests get distributed tracing automatically [#automatic-instrumentation]

The Android agent's Gradle plugin instruments your app's bytecode at build time, so distributed tracing headers are added automatically to requests made through:

* `OkHttp` (versions 2 and 3)
* Apache `HttpClient`
* `HttpURLConnection`
* Retrofit

Because this instrumentation weaves the call sites of those libraries directly, code that wraps them — including Kotlin coroutines and suspend functions — is covered automatically too; there's no separate flag to enable, unlike some other platforms' async APIs.

The agent does not automatically add distributed tracing headers to:

* Volley. There's no Volley support in the agent at all, so Volley requests need [manual propagation](#manual) if you want them traced.
* `WebView`. The agent's `WebView` instrumentation covers page-load timing, not network request headers, so requests made from web content loaded in a `WebView` aren't traced automatically.
* Any other third-party networking library or custom transport that doesn't route through the libraries listed above.

For any of these, use manual propagation.

## Manually propagate distributed tracing [#manual]

If you make a request through a library the agent doesn't auto-instrument, you can still add distributed tracing headers and report the request yourself.

First, create a trace context and get its headers to attach to your outgoing request:

## Disable distributed tracing [#disable]

```java
NewRelic.enableFeature(FeatureFlag.DistributedTracing)
NewRelic.disableFeature(FeatureFlag.DistributedTracing)
```

## Enable Infinite Tracing [#infinite-tracing]

If your mobile apps have some downstream services that use our tail-based distributed tracing called [Infinite Tracing](/docs/distributed-tracing/infinite-tracing/introduction-infinite-tracing), you should enable this feature for your mobile apps. This ensures that your root span (the initiating mobile app) is included in the rest of the spans tracked by Infinite Tracing.

To set this up, see the [Infinite Tracing steps](/docs/distributed-tracing/infinite-tracing/set-trace-observer) to create a trace observer and to select which mobile apps (data sources) should report spans.

## Find data [#find-data]

Mobile spans appear in any [New Relic distributed tracing UI](/docs/understand-dependencies/distributed-tracing/ui-data/additional-distributed-tracing-features-new-relic-one/) where those spans are part of a trace.

Here are some tips for finding and querying data:

* You can find end-user-originating traces in any [New Relic distributed tracing UI](/docs/understand-dependencies/distributed-tracing/ui-data/additional-distributed-tracing-features-new-relic-one).
* In the distributed tracing UI, end-user spans are indicated with the <img title="New Relic distributed tracing mobile span icon" alt="New Relic distributed tracing mobile span icon" src="/images/mobile_icon_icon.webp" style={{height: "30px", width: "30px"}}/> icon.
* To see a span's attributes, select [a span in the UI](/docs/apm/distributed-tracing/ui-data/understand-use-distributed-tracing-data#span-details).
* Spans are reported as [Span data](/attribute-dictionary/?event=Span), and can be [queried in New Relic](/docs/using-new-relic/data/understand-data/query-new-relic-data).
* Query tips:
  * Query by name by setting `mobileApp.name` to the mobile app name.
  * Query for traces containing at least one mobile app span with `mobileApp.name is not null`.
  * Query for traces containing at least one backend app with `appName is not null`.
  * Query for traces containing both mobile and backend spans by combining the two previous conditions.

For example, to find mobile spans for a specific app:

```sql
SELECT count(*) FROM Span WHERE mobileApp.name = 'YOUR_APP_NAME' SINCE 1 day ago
```

To find traces that connect a mobile span to a backend APM span:

```sql
SELECT * FROM Span WHERE mobileApp.name IS NOT NULL AND appName IS NOT NULL SINCE 1 day ago
```

## Troubleshooting [#troubleshooting]

If you don't see mobile spans where you expect them, check these in order:

* **Distributed tracing is disabled.** Confirm you haven't called `disableFeature` with `FeatureFlag.DistributedTracing`. See [How to set up distributed tracing](#setup).
* **AnalyticsEvents is disabled.** Headers still go out, but the correlated `MobileRequest`/`MobileRequestError` event won't be sent. See [How to set up distributed tracing](#setup).
* **The request isn't auto-instrumented.** Requests made through Volley, a `WebView`, or any library other than `OkHttp`, Apache `HttpClient`, `HttpURLConnection`, or Retrofit need [manual propagation](#manual). See [Which requests get distributed tracing automatically](#automatic-instrumentation).
* **The backend APM agent is too old.** If the receiving service's APM agent doesn't support W3C Trace Context yet, it starts a new trace instead of linking to your app's. Check the [minimum APM agent versions](#headers).
* **A proxy or gateway strips the headers.** Anything sitting between your app and the backend needs to pass through `traceparent` and `tracestate` unmodified.
* **`tracestate` is dropped because the trusted account key doesn't match.** If a backend service belongs to a different New Relic account than your mobile app, confirm the account is in the same trust relationship, or the `tracestate` entry may be ignored.

For broader distributed tracing issues, see [Troubleshooting](/docs/apm/distributed-tracing/troubleshooting/troubleshooting-missing-trace-data).
