This guide provides patterns for setting up role-based access control (RBAC) for <DNT>Fleet Control</DNT> operations. It covers three implementation patterns, from basic to enterprise, with both UI and <DNT>NerdGraph</DNT> examples.

<Callout title="Need help deciding which pattern fits your organization?" variant="tip">
  If you're managing <DNT>Fleet Control</DNT> across multiple autonomous business units, or dealing with contractor delegation, see [delegating Fleet Control with multiple business units](#business-units) for a detailed example comparing separate organizations against RBAC within a single organization.
</Callout>

## Prerequisites [#prerequisites]

Before implementing any of the patterns below:

* **Full platform users:** every <DNT>Fleet Control</DNT> permission requires the full platform [user type](/docs/accounts/accounts-billing/new-relic-one-user-management/user-type). Core and basic users cannot hold them, whatever roles they're assigned.
* **Pro or Enterprise edition:** required to create the custom roles and custom groups these patterns use.
* **Authentication domain manager role required for access grants:** only users with the <DNT>**Authentication domain manager**</DNT> role can create access grants, which assign groups and roles to specific fleets. This is a New Relic platform requirement for all access grant operations.
* **Initial <DNT>Agent Control</DNT> setup:** requires the <DNT>**Authentication domain manager**</DNT> role, one time, to create system identities.
* **Creating fleets and configurations:** requires the <DNT>**Organization product admin**</DNT> role, which is automatically granted to anyone in the default <DNT>**User**</DNT> group. This is less restrictive than many teams expect.
* **Running deployments:** requires the <DNT>**Organization manager**</DNT> role, which is automatically granted to anyone in the default <DNT>**Admin**</DNT> group. Alternatively, the <DNT>**Fleet manager**</DNT> role or a custom role carrying <DNT>**Deploy**</DNT> grants it on specific fleets, without organization-wide reach.

<Callout title="Common misconception about role requirements" variant="important">
  Many teams assume <DNT>**Authentication domain manager**</DNT> is needed for all <DNT>Fleet Control</DNT> operations. **This is not true.**

  <DNT>**Authentication domain manager**</DNT> is only required for:

  1. **Initial <DNT>Agent Control</DNT> setup**, one time, which creates system identities.
  2. **Creating access grants**, which assigns groups to fleets.

  **Ongoing fleet management**, meaning creating fleets and creating configurations, only requires <DNT>**Organization product admin**</DNT>, which most users already have.
</Callout>

## How Fleet Control permissions are organized [#permissions]

When you create a custom role, <DNT>Fleet Control</DNT> permissions appear as a grid: a row for the resource, and columns for <DNT>**Read**</DNT>, <DNT>**Modify**</DNT>, <DNT>**Delete**</DNT>, and <DNT>**Other**</DNT>. Each checkbox covers a set of related actions rather than a single one, and which row you get depends on the role's scope.

Organization-scoped roles get the <DNT>**Fleets (all)**</DNT> row, covering every fleet in the organization:

| Permission | What it covers |
|:-----------|:---------------|
| <DNT>**Read**</DNT> | View fleets, the agents on their managed entities, configurations and their contents, fleet membership, and the approval policy |
| <DNT>**Modify**</DNT> | Create and update fleets, author configurations and add versions, plus everything in Read |
| <DNT>**Delete**</DNT> | Delete fleets, configurations, and deployments |
| <DNT>**Other: Deploy**</DNT> | Create, edit, run, and delete deployments, and change which managed entities are in a fleet |
| <DNT>**Other: Approve configurations**</DNT> | Approve, request changes on, or deny a configuration version |
| <DNT>**Other: Configure organization governance**</DNT> | Set and change the approval policy |

Entity-scoped roles targeting a fleet get the <DNT>**Fleets (individual)**</DNT> row, covering only the fleets the role is granted on:

| Permission | What it covers |
|:-----------|:---------------|
| <DNT>**Modify**</DNT> | Rename the fleet, edit its description, and view its membership |
| <DNT>**Delete**</DNT> | Delete the fleet |
| <DNT>**Other: Deploy**</DNT> | Create, edit, run, and delete deployments for the fleet, and change which managed entities are in it |

<Callout title="Fleet-scoped roles build on read access rather than replacing it" variant="important">
  The <DNT>**Fleets (individual)**</DNT> row has no <DNT>**Read**</DNT> permission. A fleet-scoped role grants the ability to act on a fleet, not to see <DNT>Fleet Control</DNT> in the first place.

  Users also need read access from an organization-scoped role, which they normally have through the default <DNT>**User**</DNT> group. If you grant a fleet-scoped role to a group whose members have nothing else, they won't be able to see anything to act on.
</Callout>

Approving configurations and setting the approval policy are available only to organization-scoped roles, so approval authority can't be scoped to a particular fleet. See [config approvals](/docs/new-relic-control/fleet-control/manage-fleets/#config-approvals) for the details and [delegate approval authority](/docs/new-relic-control/fleet-control/manage-fleets/#delegate-approval-authority) for how to grant it.

## Basic pattern: single fleet permission (FGA) [#basic-pattern]

**Use case:** grant a team access to manage a specific fleet without giving them access to all fleets in the organization.

**Concept:** <DNT>Fleet Control</DNT> supports fine-grained access (FGA) through entity-scoped access grants. The built-in <DNT>**Fleet manager**</DNT> role can be scoped to specific fleet entities, which gives a group full operational control of those fleets, deployments included, without <DNT>**Organization manager**</DNT>.

### UI walkthrough [#basic-ui]

1. **Create the fleet**, if not already created:
   * Navigate to <DNT>**All capabilities → New Relic Control → Fleets**</DNT>
   * Click <DNT>**Create a fleet**</DNT>
   * Name it, for example `production-us-east-fleets`
   * Save and note the fleet GUID
2. **Create or identify the target group**:
   * Navigate to <DNT>**Administration → Access management → Groups**</DNT>
   * Create a new group, for example `prod-us-east-fleet-operators`, or use an existing one
   * In the <DNT>**Create a group**</DNT> modal, add users now via the <DNT>**Add users**</DNT> dropdown, or add them later by editing the group
   * Note the group ID
3. **Grant entity-scoped access**:
   * Go to <DNT>**New Relic Control → Fleets**</DNT>
   * On the fleet's row, open the kebab menu and select <DNT>**Fleet permissions**</DNT>
   * In the <DNT>**Fleet permissions**</DNT> modal, pick a group and select <DNT>**Fleet manager**</DNT> as the role. Add as many group and role pairs as needed
   * Click <DNT>**Save**</DNT>, which creates one access grant per pair

<Callout title="If Fleet permissions is missing or opens locked" variant="important">
  The <DNT>**Fleet permissions**</DNT> menu item requires the <DNT>**Authentication domain manager**</DNT> role. Without it, the action either doesn't appear on the fleet's row or the modal opens locked rather than partially available.

  Grants can also be attached at fleet creation time through the <DNT>**Create fleet**</DNT> dialog.
</Callout>

**Result:** members of `prod-us-east-fleet-operators` can now run deployments and manage members for `production-us-east-fleets` only. They cannot modify other fleets. They will still see that other fleets exist, because read access comes from their organization-scoped role rather than from this grant.

### NerdGraph automation [#basic-nerdgraph]

```graphql
mutation GrantFleetAccess {
  authorizationManagementGrantAccess(
    grantAccessOptions: {
      grantee: { type: GROUP, id: "YOUR_GROUP_ID" }
      entityAccessGrants: {
        entity: { id: "YOUR_FLEET_GUID", type: "fleet" }
        roleId: "YOUR_ROLE_ID"
      }
    }
  ) {
    accessGrants {
      id
    }
  }
}
```

**How to find IDs:**

* **Fleet GUID:** visible in the fleet details page URL, or query fleets via the [<DNT>NerdGraph Fleet Control</DNT> tutorial](/docs/apis/nerdgraph/examples/nerdgraph-fleet-control-tutorial)
* **Group ID:** <DNT>**Administration → Access management → Groups**</DNT>, click the group, ID is in the URL
* **Role ID:** query for it using the workaround in [known issues](#known-issues)

## Advanced pattern: custom roles for lifecycle separation [#advanced-pattern]

**Use case:** separate who can change a fleet's definition and membership from who can run deployments, while both groups work on the same fleets.

**Concept:** create two custom entity-scoped roles with different <DNT>Fleet Control</DNT> permissions, then grant each to a different group on the same fleet entities. <DNT>**Fleet manager**</DNT> carries Modify, Delete, and Deploy together, so when that's more authority than a group should have, split it.

### Custom roles design [#role-design]

Both roles are entity-scoped and target <DNT>**Fleet**</DNT>:

| Role | Permission | What holders can do | Assigned to |
|:-----|:-----------|:--------------------|:------------|
| `Fleet author` | <DNT>**Modify**</DNT> | Rename the fleet, edit its description, view its membership | Platform Ops teams |
| `Fleet deployer` | <DNT>**Other: Deploy**</DNT> | Create, edit, run, and delete deployments, change which managed entities are in the fleet | App teams and contractors |

Neither role can delete a fleet, since <DNT>**Delete**</DNT> is a separate permission you leave unchecked.

Configuration authoring isn't part of either role, because configurations in <DNT>Fleet Control</DNT> are organization-level objects rather than belonging to a fleet. Authoring them comes with <DNT>**Organization product admin**</DNT>, which the default <DNT>**User**</DNT> group already has. In practice, your authors write configurations and these fleet-scoped roles control what gets deployed where.

### UI walkthrough [#advanced-ui]

1. **Create the custom roles.** For each one:
   * Navigate to <DNT>**Administration → Access management → Roles**</DNT>
   * Click <DNT>**Add a role**</DNT>
   * For the role's scope, choose <DNT>**Single item or entity**</DNT>, then click <DNT>**Next**</DNT>
   * Under <DNT>**Select what you want to configure access to**</DNT>, choose <DNT>**Fleet**</DNT>
   * Name the role, for example `Fleet author`
   * Under <DNT>**Set permissions**</DNT>, expand <DNT>**Fleet Control**</DNT> and select what the role carries on the <DNT>**Fleets (individual)**</DNT> row: <DNT>**Modify**</DNT> for the author role, or <DNT>**Deploy**</DNT> under <DNT>**Other**</DNT> for the deployer role
   * Save, then repeat for the second role
2. **Create groups for each role**:
   * Create group `fleet-architects` for the authors, adding the relevant users via the <DNT>**Add users**</DNT> dropdown in the <DNT>**Create a group**</DNT> modal, or later by editing the group
   * Create group `fleet-deployment-operators` for the deployers, the same way
3. **Grant entity-scoped access for each group**:
   * Go to <DNT>**New Relic Control → Fleets**</DNT>, open the kebab menu on the target fleet, and select <DNT>**Fleet permissions**</DNT>
   * Add a group and role pair: `fleet-architects` with <DNT>**Fleet author**</DNT>
   * Add a group and role pair: `fleet-deployment-operators` with <DNT>**Fleet deployer**</DNT>
   * Save, and both grants are created together

<Callout title="Custom roles don't pick up new permissions on their own" variant="important">
  A custom role contains only what an administrator added to it. Standard roles receive the permissions for new organization-scoped features as they ship, so if <DNT>Fleet Control</DNT> adds capabilities later, someone has to add them to each custom role that should have them.

  For users who should get new <DNT>Fleet Control</DNT> features automatically, assign a standard role instead.
</Callout>

### NerdGraph automation [#advanced-nerdgraph]

Custom roles are created in the UI. Role creation takes internal permission identifiers rather than the permission names shown on the checkboxes, so there's no practical API path for building the roles themselves.

Once the roles exist, grant them with the same mutation as the [basic pattern](#basic-nerdgraph), passing each role's ID.

**Result:** fleet authors can shape the fleets they own but cannot run deployments. Deployment operators can run deployments but cannot redefine or delete a fleet.

## Enterprise pattern: delegated group management [#enterprise-pattern]

**Use case:** allow team leads to add and remove members from their team's groups without needing full <DNT>**Authentication domain manager**</DNT> privileges.

**Concept:** use the <DNT>**Group admin**</DNT> role with group-scoped grants to delegate group membership management.

### UI walkthrough [#enterprise-ui]

1. **Create a managers group**:
   * Navigate to <DNT>**Administration → Access management → Groups**</DNT>
   * Create group `fleet-team-leads`
   * Add the team leads as members
2. **Grant the Group admin role over target groups**:
   * Go to <DNT>**Administration → Access management → Access grants**</DNT>
   * Click <DNT>**Create new grant**</DNT>
   * Choose a group grant, which is the grant type that targets other groups
   * Select group `fleet-team-leads`
   * Role: <DNT>**Group admin**</DNT>
   * Select the groups that team leads should be able to manage, for example `fleet-architects` and `fleet-deployment-operators`
   * Save

**Result:** members of `fleet-team-leads` can now add and remove users from `fleet-architects` and `fleet-deployment-operators` without needing the <DNT>**Authentication domain manager**</DNT> role.

<Callout title="Important limitation" variant="caution">
  <DNT>**Group admin**</DNT> can manage *who* is in a group, but cannot create new access grants or assign groups to new fleets. When a new fleet is created, someone with <DNT>**Authentication domain manager**</DNT> must still create the access grant for that fleet.
</Callout>

### NerdGraph automation [#enterprise-nerdgraph]

```graphql
mutation DelegateGroupManagement {
  authorizationManagementGrantAccess(
    grantAccessOptions: {
      grantee: { type: GROUP, id: "YOUR_TEAM_LEADS_GROUP_ID" }
      groupAccessGrants: [
        {
          groupId: "YOUR_TARGET_GROUP_ID"
          roleId: "YOUR_GROUP_ADMIN_ROLE_ID"
        }
      ]
    }
  ) {
    accessGrants {
      id
    }
  }
}
```

## Delegating Fleet Control with multiple business units [#business-units]

This section outlines a scenario we've seen with customers who have multiple autonomous business units and need to delegate <DNT>Fleet Control</DNT> management. It provides both the recommended solution and alternative approaches using the patterns above.

### The scenario [#scenario]

**Example:** ByteFlix Entertainment is a large media company with multiple autonomous business units operating under a single New Relic organization:

* **ByteFlix+**, a streaming service
* **BBS**, the ByteFlix Broadcast System, a broadcast network
* **PixelTV**, a cable network

#### Organizational structure [#org-structure]

**Central IT:**

* Only two or three people have the <DNT>**Organization manager**</DNT> and <DNT>**Authentication domain manager**</DNT> roles
* They manage New Relic licensing and governance
* They **do not** configure or create monitoring entities
* They are a bottleneck for access management changes

**Business units:**

* Each unit has separate accounts under the same New Relic organization
* Each unit manages its own observability independently
* Many units use contractors to administer New Relic infrastructure

#### The challenge [#challenge]

ByteFlix wants to adopt <DNT>Fleet Control</DNT> but runs into friction:

1. **Strict business unit isolation required:** ByteFlix+ teams must not manage BBS or PixelTV infrastructure
2. **Contractor delegation:** unit leads need to onboard contractors without involving central IT
3. **Lifecycle separation:** Platform Ops should shape fleets and App Teams should deploy, but App Teams shouldn't be able to delete or redefine fleets
4. **No broad admin grants:** central IT won't grant <DNT>**Authentication domain manager**</DNT> to unit teams due to security concerns

### Recommended solution: separate organizations [#separate-orgs]

Based on ByteFlix's organizational structure, multi-tenancy is the ideal solution.

#### What this means [#multi-tenancy-meaning]

Instead of one organization with multiple accounts, ByteFlix creates three separate New Relic organizations:

* **ByteFlix+ organization**, with its own accounts
* **BBS organization**, with its own accounts
* **PixelTV organization**, with its own accounts

Each business unit becomes its own isolated New Relic organization.

#### Benefits [#multi-tenancy-benefits]

1. **Complete business unit isolation:** organization-scoped features, including <DNT>Fleet Control</DNT>, only see data within that unit's organization
2. **No cross-unit visibility:** ByteFlix+ users cannot see BBS or PixelTV entities, guaranteed by organizational boundaries
3. **Autonomous administration:** each unit has its own authentication domain managers and organization managers without affecting the others
4. **Contractor delegation:** each unit can grant contractor access without involving central IT or the other units
5. **Simpler permissions:** no entity-scoped grants or custom roles needed to enforce isolation

#### What about shared services? [#shared-services]

New Relic's [account sharing](/docs/accounts/accounts-billing/account-structure/multi-tenancy/share-accounts) feature allows accounts to cross organizational boundaries. If ByteFlix has shared platform services, such as centralized logging or shared infrastructure, that need visibility across units, those accounts can be shared into multiple organizations.

For example, central IT maintains a shared observability organization with the shared platform accounts, and the ByteFlix+, BBS, and PixelTV organizations each have read access to those accounts via account sharing.

#### Trade-offs [#multi-tenancy-tradeoffs]

**Pros:**

* Strongest isolation model, enforced by organizational boundaries
* Simplest permission model, with no entity-scoped grants needed
* Each unit operates completely autonomously

**Cons:**

* Requires organizational restructuring, not just permission changes
* Separate billing and licensing per organization, which may affect contract structure
* Shared services require account sharing setup
* Some cross-organization reporting requires custom dashboards or Data Plus features

#### Next steps for separate organizations [#multi-tenancy-next-steps]

To pursue this model, see [multi-tenancy](/docs/accounts/accounts-billing/account-structure/multi-tenancy/intro-to-multi-tenancy), then contact your account representative to work through shared service workflows, a migration plan for moving units to separate organizations, account sharing for any shared platform services, and the contract and billing implications.

### Alternative solution: RBAC patterns within a single organization [#rbac-single-org]

If ByteFlix **cannot** move to separate organizations, because of contract constraints, timeline, or organizational resistance, they can achieve similar outcomes using the RBAC patterns in this guide within a single organization.

#### Pattern 1: entity-scoped access (FGA) [#bu-pattern-1]

**What it solves:** business unit separation within a single organization.

**How it works:** use fine-grained access to grant each unit's groups access only to their specific fleet entities.

**Example:**

* `byteflix-plus-platform-ops` granted the <DNT>**Fleet manager**</DNT> role, scoped to the `byteflix-plus-prod-k8s` fleet only
* `bbs-platform-ops` granted the <DNT>**Fleet manager**</DNT> role, scoped to the `bbs-prod-k8s` fleet only

**Result:** ByteFlix+ teams can act only on ByteFlix+ fleets, and BBS teams only on BBS fleets.

**Limitation:** this requires <DNT>**Authentication domain manager**</DNT> to set up the initial access grants via the <DNT>**Fleet permissions**</DNT> UI. Once established, unit leads cannot grant access to new fleets without involving central IT.

**Reference:** [basic pattern](#basic-pattern).

#### Pattern 2: custom lifecycle roles [#bu-pattern-2]

**What it solves:** lifecycle separation, with Platform Ops shaping fleets and App Teams deploying.

**How it works:** create two custom entity-scoped roles targeting <DNT>**Fleet**</DNT>:

* **Fleet author**, carrying <DNT>**Modify**</DNT>, assigned to Platform Ops teams
* **Fleet deployer**, carrying <DNT>**Deploy**</DNT>, assigned to App Teams and contractors

Both roles are then granted to their groups on specific fleet entities using Pattern 1.

**Result:** Platform Ops shape the fleets they own, App Teams run deployments, and neither can delete a fleet.

**Limitation:** creating custom roles requires Pro or Enterprise edition. Granting them on fleets requires <DNT>**Authentication domain manager**</DNT>, via the <DNT>**Fleet permissions**</DNT> UI.

**Reference:** [advanced pattern](#advanced-pattern).

#### Pattern 3: Group admin delegation [#bu-pattern-3]

**What it solves:** contractor delegation without <DNT>**Authentication domain manager**</DNT>.

**How it works:** grant unit leads the <DNT>**Group admin**</DNT> role scoped to their unit's operational groups.

**Example for ByteFlix+:**

* Group: `byteflix-plus-bu-leads`
* Role: <DNT>**Group admin**</DNT>
* Scope: can manage membership of `byteflix-plus-platform-ops` and `byteflix-plus-app-teams`

**Result:** unit leads can add and remove contractors from groups **without involving central IT** and **without needing <DNT>Authentication domain manager</DNT>**.

**Limitation:** unit leads can manage *who* is in a group, but cannot create new access grants or assign groups to new fleets. When a new fleet is created, central IT must still create the access grant for it.

**Reference:** [enterprise pattern](#enterprise-pattern).

#### Combined RBAC architecture [#combined-architecture]

Using all three patterns together within a single organization, ByteFlix's architecture looks like this:

```
Organization: ByteFlix Entertainment

├── ByteFlix+ (Streaming BU):
│   ├── Groups:
│   │   ├── byteflix-plus-bu-leads (Group admin over operational groups)
│   │   ├── byteflix-plus-platform-ops (Fleet author role)
│   │   └── byteflix-plus-app-teams (Fleet deployer role, includes contractors)
│   └── Fleets (entity-scoped to ByteFlix+ groups only):
│       ├── byteflix-plus-prod-k8s
│       └── byteflix-plus-stage-k8s
│
├── BBS (Broadcast BU):
│   ├── Groups:
│   │   ├── bbs-bu-leads (Group admin)
│   │   ├── bbs-platform-ops (Fleet author role)
│   │   └── bbs-app-teams (Fleet deployer role)
│   └── Fleets (entity-scoped to BBS groups only):
│       ├── bbs-prod-k8s
│       └── bbs-stage-k8s
│
└── PixelTV (Cable BU):
    ├── Groups:
    │   ├── pixeltv-bu-leads (Group admin)
    │   ├── pixeltv-platform-ops (Fleet author role)
    │   └── pixeltv-app-teams (Fleet deployer role)
    └── Fleets (entity-scoped to PixelTV groups only):
        ├── pixeltv-prod-k8s
        └── pixeltv-stage-k8s

Custom entity-scoped roles, created once by central IT:
├── Fleet author (Modify)
└── Fleet deployer (Deploy)
```

#### RBAC trade-offs [#rbac-tradeoffs]

**Pros:**

* No organizational restructuring required
* Single contract and billing relationship
* Achieves operational separation between units with correctly configured grants

**Cons:**

* Requires initial setup by central IT, meaning authentication domain manager involvement
* New fleets still require central IT to create access grants, an ongoing dependency
* A more complex permission model than separate organizations
* Separation depends on correct access grant configuration, and is not enforced by organizational boundaries

<Callout title="This model controls who can act on a fleet, not who can see it" variant="important">
  Because fleet-scoped roles carry no <DNT>**Read**</DNT> permission, everyone working in <DNT>Fleet Control</DNT> needs organization-scoped read access. ByteFlix+ users will see that BBS and PixelTV fleets exist, even though they cannot act on them.

  If your business units must not see each other's fleets at all, separate organizations is the only model that delivers that.
</Callout>

### Role requirements clarification [#role-clarification]

There's often confusion about what actually requires which role. Here's the breakdown.

#### For Agent Control initial setup [#req-agent-control]

**Requirement:** <DNT>**Authentication domain manager**</DNT>

**Why:** setting up <DNT>Agent Control</DNT> includes creating a system identity and assigning it permissions, actions reserved for administrators.

**Who needs this:** central IT or designated platform admins performing the initial <DNT>Agent Control</DNT> setup.

**Frequency:** one time per environment.

#### For ongoing fleet management [#req-fleet-management]

**Requirement:** <DNT>**Organization product admin**</DNT>, not <DNT>**Authentication domain manager**</DNT>

**What this means:** once <DNT>Agent Control</DNT> is set up, day-to-day fleet management, meaning creating fleets and creating configurations, only requires <DNT>**Organization product admin**</DNT>, which is automatically assigned to anyone in the default <DNT>**User**</DNT> group.

**Clarification:** many teams assume they need <DNT>**Authentication domain manager**</DNT> for ongoing fleet work. This is not true. That role is only needed for the initial <DNT>Agent Control</DNT> setup and for creating access grants.

#### For deployment [#req-deployment]

**Requirement:** <DNT>**Organization manager**</DNT>, or <DNT>**Fleet manager**</DNT> on specific fleets

**Why:** deployment is a high-risk action, since it modifies production infrastructure.

**Who has this:** anyone in the default <DNT>**Admin**</DNT> group has <DNT>**Organization manager**</DNT> automatically.

**Alternative:** grant the <DNT>**Fleet manager**</DNT> role on specific fleets, or create a custom entity-scoped role carrying only <DNT>**Deploy**</DNT>, to give deployment rights on individual fleets without organization-wide privileges. Either way, an <DNT>**Authentication domain manager**</DNT> creates the grant.

#### For access grants [#req-access-grants]

**Requirement:** <DNT>**Authentication domain manager**</DNT>

**Why:** access grants control user permissions, which is a privileged operation.

**Workaround:** use <DNT>**Group admin**</DNT> delegation, [Pattern 3](#bu-pattern-3), to let unit leads manage group *membership* without granting full <DNT>**Authentication domain manager**</DNT>. Group admin cannot create new access grants, only manage who is in groups that already have them.

#### Summary table [#summary-table]

| Action | Role required | Frequency | Notes |
|:-------|:--------------|:----------|:------|
| **Initial <DNT>Agent Control</DNT> setup** | Authentication domain manager | One time | Creating system identity |
| **Create/update fleets** | Organization product admin | Ongoing | Auto-granted to <DNT>**User**</DNT> group |
| **Create configurations** | Organization product admin | Ongoing | Auto-granted to <DNT>**User**</DNT> group |
| **Deploy fleets** | Organization manager, or Fleet manager per fleet | Ongoing | Auto-granted to <DNT>**Admin**</DNT> group, or use a custom role carrying Deploy |
| **Delete fleets and deployments** | Organization manager, or Fleet manager per fleet | Occasional | Deleting configurations is organization-scoped only |
| **Approve configurations, set approval policy** | Organization manager | Ongoing | Organization-scoped only, cannot be scoped per fleet |
| **Create access grants** | Authentication domain manager | Per new fleet | Assign groups to fleets |
| **Manage group membership** | Group admin, delegated | Ongoing | Add and remove users from groups |

Roles are additive, so a user who holds several has the sum of their permissions. For what each standard role covers, see [user management concepts](/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#standard-roles).

### Recommendation summary [#recommendation-summary]

**If you can pursue separate organizations:** do. It provides the strongest isolation, the simplest permissions model, and complete business unit autonomy.

**If you cannot:** use the RBAC patterns with these caveats:

* Central IT must perform a one-time setup of custom roles and initial access grants
* Group admin delegation, Pattern 3, enables contractor onboarding without central IT
* New fleets still require central IT to create access grants, an ongoing dependency
* Separation depends on correct configuration, and fleets remain visible across units

**Key clarification:** many teams overestimate the <DNT>**Authentication domain manager**</DNT> requirement. Ongoing fleet management only requires <DNT>**Organization product admin**</DNT>, which is already granted to most users. <DNT>**Authentication domain manager**</DNT> is primarily needed for the initial <DNT>Agent Control</DNT> setup, one time, and for creating access grants when new fleets are created.

If you take the RBAC path, pilot it with one business unit to validate the model, roll out to the remaining units, and document the access grant process for when new fleets are created.

## Known issues and workarounds [#known-issues]

### Cannot query role IDs directly [#role-ids]

**Problem:** <DNT>NerdGraph</DNT> doesn't provide a direct query to list role IDs by name.

**Workaround:** read them off the groups that already hold the role:

```graphql
{
  actor {
    organization {
      authorizationManagement {
        authenticationDomains(id: "YOUR_AUTH_DOMAIN_ID") {
          authenticationDomains {
            groups {
              groups {
                displayName
                roles {
                  roles {
                    roleId
                    displayName
                  }
                }
              }
            }
          }
        }
      }
    }
  }
}
```

### Finding fleet GUIDs [#fleet-guids]

**Problem:** fleet GUIDs are not easily discoverable via the UI.

**Workaround:** navigate to the fleet details page, where the GUID is in the URL after `/fleets/`. To query fleets instead, see the [<DNT>NerdGraph Fleet Control</DNT> tutorial](/docs/apis/nerdgraph/examples/nerdgraph-fleet-control-tutorial).

## Automation script template [#automation-script]

For teams managing multiple fleets and groups at scale, here's a template using the [New Relic CLI](/docs/new-relic-solutions/tutorials/new-relic-cli). It creates a group, creates a fleet, and grants the group access to that fleet.

Create the custom roles in the UI first, as described in the [advanced pattern](#advanced-ui), and pass the role ID into the script.

```bash
#!/bin/bash
set -euo pipefail

# Prerequisites:
#   - New Relic CLI installed and profile configured with a user key
#   - The Authentication domain manager role, required to create access grants
#   - A role created in Administration > Access management > Roles, and its ID

AUTH_DOMAIN_ID="YOUR_AUTH_DOMAIN_ID"
ACCOUNT_ID="YOUR_ACCOUNT_ID"
ROLE_ID="YOUR_ROLE_ID"
GROUP_NAME="fleet-architects"
FLEET_NAME="production-us-east-k8s"

# 1. Create the group. Note the returned group ID.
echo "Creating group ${GROUP_NAME}..."
newrelic nerdgraph query 'mutation CreateGroup($authDomainId: ID!, $displayName: String!) {
  userManagementCreateGroup(createGroupOptions: {
    authenticationDomainId: $authDomainId
    displayName: $displayName
  }) {
    group { id displayName }
  }
}' --variables "{\"authDomainId\": \"${AUTH_DOMAIN_ID}\", \"displayName\": \"${GROUP_NAME}\"}"

# 2. Create the fleet. Note the returned fleet GUID.
echo "Creating fleet ${FLEET_NAME}..."
newrelic nerdgraph query 'mutation CreateFleet($name: String!, $scopeId: ID!) {
  fleetControlCreateFleet(fleetEntity: {
    name: $name
    description: "Created by setup script"
    managedEntityType: KUBERNETESCLUSTER
    scope: { type: ACCOUNT, id: $scopeId }
  }) {
    entity { id name }
  }
}' --variables "{\"name\": \"${FLEET_NAME}\", \"scopeId\": \"${ACCOUNT_ID}\"}"

# 3. Grant the group access to the fleet, using the IDs returned above.
GROUP_ID="GROUP_ID_FROM_STEP_1"
FLEET_GUID="FLEET_GUID_FROM_STEP_2"

echo "Granting entity-scoped access..."
newrelic nerdgraph query 'mutation GrantFleetAccess($groupId: ID!, $fleetGuid: ID!, $roleId: ID!) {
  authorizationManagementGrantAccess(grantAccessOptions: {
    grantee: { type: GROUP, id: $groupId }
    entityAccessGrants: {
      entity: { id: $fleetGuid, type: "fleet" }
      roleId: $roleId
    }
  }) {
    accessGrants { id }
  }
}' --variables "{\"groupId\": \"${GROUP_ID}\", \"fleetGuid\": \"${FLEET_GUID}\", \"roleId\": \"${ROLE_ID}\"}"

echo "Setup complete."
```

Pass values with `--variables` rather than building query strings by hand, so names containing spaces or quotes don't break the request. To run the steps unattended, capture each response and read the IDs out of it before the next call.

For a fuller set of fleet operations, including updating and deleting fleets and managing deployments, see [<DNT>Fleet Control</DNT> APIs and CLI](/docs/new-relic-control/fleet-control/apis-and-cli).

## Summary [#summary]

This guide covered three patterns for <DNT>Fleet Control</DNT> RBAC:

1. **Basic pattern:** the entity-scoped <DNT>**Fleet manager**</DNT> role for single-fleet access control
2. **Advanced pattern:** custom entity-scoped roles separating authoring from deployment
3. **Enterprise pattern:** delegated group management using the <DNT>**Group admin**</DNT> role

All three are supported in the UI, and grants can be created through <DNT>NerdGraph</DNT> for automation and infrastructure-as-code. The UI is the recommended approach for one-time setups, and <DNT>NerdGraph</DNT> for bulk operations. Choose the pattern that matches your organizational structure and delegation requirements.
