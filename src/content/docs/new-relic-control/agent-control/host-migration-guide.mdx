This guide covers the most common questions and pitfalls when moving from a standalone agent installation (for example, an Infrastructure Agent with on-host integrations managed by the OS package manager) to agents managed by Agent Control and Fleet Control.

<Callout variant="important">
  This guide covers concepts, configuration mapping, and rollback for **Linux and Windows hosts**. For step-by-step migration procedures on all platforms (including Kubernetes), see [Instrument your systems with Agent Control](/docs/new-relic-control/agent-control/instrumentation#migrate-a-previously-instrumented-system).
</Callout>

## Before you start: the monitoring gap

<Callout variant="caution">
  **Installing Agent Control removes the standalone Infrastructure Agent.**

  The OS package that installs Agent Control removes or stops the previously installed Infrastructure Agent. From that moment, the host has no running agent until Agent Control connects to Fleet Control, receives the deployment configuration, and successfully starts the Infrastructure Agent as a managed sub-agent. If Fleet Control is not configured correctly, if there is a connectivity issue, or if the deployment config has an error, you are left with no agent on the host and a gap in monitoring.
</Callout>

**Do not install Agent Control on a host until all of the following are true:**

1. Fleet Control has a policy with an Infrastructure Agent deployment targeting that host whose config mirrors your existing `newrelic-infra.yml` and `integrations.d/` files exactly — same settings, same integration configs, same log forwarding rules. See [Configuration migration](#configuration-migration) for how to translate each piece.
2. You have validated the deployment config on at least one non-production host first.
3. Agent Control can reach the Fleet Control endpoint and the OCI registry from the target host. Check firewall rules and proxy settings in advance.
4. You have the rollback steps ready in case the deployment does not come up. See [Rollback](#rollback).

The gap between Agent Control installation and the first successful managed agent start is typically a few seconds when everything is configured correctly. It can become indefinite if there is a misconfiguration, making preparation before the cut-over critical.

## Entity continuity and dashboards

**Your existing dashboards, alerts, and workloads keep working without any changes.**

New Relic entity GUIDs are derived from stable attributes (primarily the hostname, CloudInstanceId, the account ID, and the integration identity) not from how the agent was installed or what is supervising its process. When Agent Control starts the Infrastructure Agent on the same host with the same configuration, the agent reports the same attributes it always did. New Relic resolves those attributes to the same entity GUIDs as before, so:

- The host entity in the Infrastructure UI is the same entity.
- On-host integration entities (MySQL, NGINX, and so on) keep their GUIDs.
- Any dashboard widget, alert condition, or workload that queries or filters by those entities continues to work.
- Golden signal history is preserved. There is no gap or duplication in the entity's metric timeline, provided the migration is done without a prolonged overlap or gap in agent execution.

The only scenario where entity continuity breaks is if the hostname itself changes during the migration (for example, the host is reprovisioned or renamed). That is unrelated to Agent Control and breaks entity identity regardless of the installation method.

## Configuration migration

### Infrastructure Agent main config

The Infrastructure Agent main config (`newrelic-infra.yml`) maps directly to the `content` block of the Infrastructure Agent sub-agent configuration in Fleet Control. Any key accepted by `newrelic-infra.yml` is accepted there. Fields like `license_key`, `display_name`, `custom_attributes`, and `log` all carry over unchanged.

When Agent Control manages the Infrastructure Agent, it writes the effective configuration to disk on every remote config update. The agent reads from that path. You do not need to maintain the standalone `newrelic-infra.yml` after the migration.

<Callout variant="tip">
  Do not delete `newrelic-infra.yml` or the `integrations.d/` files until you have confirmed that managed agents are reporting data correctly. Keeping the originals on disk is what makes the [rollback procedure](#rollback) possible.
</Callout>

### On-host integrations

Integration configuration files need to be moved into the Fleet Control configuration for the Infrastructure Agent sub-agent. Each integration config becomes a file entry in the remote config, delivered to the same `integrations.d` directory on the host.

- **Linux:** `/etc/newrelic-infra/integrations.d/`
- **Windows:** `C:\Program Files\New Relic\newrelic-infra\integrations.d\`

If you have custom integration definition files (`/etc/newrelic-infra/definitions.d/` on Linux, `C:\Program Files\New Relic\newrelic-infra\custom-integrations\` on Windows), those also need to be included in the remote config or pre-deployed on the host independently.

## Rollback

If Agent Control is not working as expected after installation, you can safely return to the standalone Infrastructure Agent at any time, as long as the original config is still available.

<Tabs>
  <TabsBar>
    <TabsBarItem id="rollback-linux">Linux</TabsBarItem>
    <TabsBarItem id="rollback-windows">Windows</TabsBarItem>
  </TabsBar>
  <TabsPages>
    <TabsPageItem id="rollback-linux">
      1. Uninstall Agent Control:
         ```bash
         sudo sh /usr/lib/newrelic-agent-control/uninstall.sh
         ```
         The script stops the service, detects the package manager, and purges all Agent Control files.
      2. Reinstall the Infrastructure Agent package if it was removed. Your `newrelic-infra.yml` and `integrations.d/` files are preserved on the host as long as you did not delete them before the migration.
    </TabsPageItem>
    <TabsPageItem id="rollback-windows">
      1. Open PowerShell with Administrator privileges and uninstall Agent Control:
         ```powershell
         PowerShell.exe -ExecutionPolicy Bypass -File "C:\Program Files\New Relic\newrelic-agent-control\uninstall.ps1"
         ```
         The script stops the service, removes the service registration, and deletes Agent Control files.
      2. Reinstall the Infrastructure Agent using the MSI installer if it was removed. Your `newrelic-infra.yml` and `integrations.d\` files are preserved on the host as long as you did not delete them before the migration.
    </TabsPageItem>
  </TabsPages>
</Tabs>

**Entity continuity is preserved on rollback.** Because entity GUIDs are derived from hostname and account (not from how the agent is managed) the host entity and all integration entities (nri-redis, nri-flex, and so on) are the same ones that were reporting before. Dashboards, alerts, and workloads resume working immediately with no gaps or duplicated history visible in the UI.
