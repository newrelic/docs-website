Supportability metrics help you understand how your Ruby agent is performing and identify potential issues with your application monitoring. These metrics provide valuable insights into agent behavior, feature adoption, and configuration effectiveness.

<Callout variant="important">
  You're charged for supportability metric ingest as part of your New Relic data consumption. These metrics provide valuable troubleshooting and optimization information that can help you resolve issues faster and improve application performance.
</Callout>

## What are supportability metrics? [#what-are-supportability-metrics]

Supportability metrics are specialized metrics that the Ruby agent automatically collects about its own operation. They help you:

* **Troubleshoot monitoring issues**: Identify why certain data isn't appearing in your dashboards
* **Validate configuration**: Confirm that features like distributed tracing or Infinite Tracing are working correctly
* **Monitor agent performance**: Track resource usage from features like the thread profiler
* **Optimize feature usage**: Understand which agent API methods your application is using

All supportability metrics use the `Supportability/` prefix in their metric names, making them easy to identify and query with [NRQL](/docs/nrql/get-started/introduction-nrql-new-relics-query-language/).

## Distributed tracing metrics [#distributed-tracing-metrics]

These metrics help you troubleshoot distributed tracing configuration and connectivity issues between your services.

### New Relic payload metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/DistributedTrace/CreatePayload/Success` | Successfully created a tracing payload for an outbound request | Low values relative to outbound request volume may indicate configuration issues |
| `Supportability/DistributedTrace/CreatePayload/Exception` | Failed to create a tracing payload due to an error | Any non-zero values indicate problems |
| `Supportability/DistributedTrace/AcceptPayload/Success` | Successfully processed an incoming tracing payload | Should track with inbound traced request volume |
| `Supportability/DistributedTrace/AcceptPayload/Exception` | Failed to process an incoming tracing payload | Investigate non-zero values for configuration or version mismatches |
| `Supportability/DistributedTrace/AcceptPayload/ParseException` | A payload couldn't be parsed | Indicates malformed headers from an upstream service |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/Null` | A null payload was passed to the accept API | Check instrumentation or custom code calling the API |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/Multiple` | A payload was ignored because one was already accepted on this transaction | Expected in nested call scenarios; high volumes may indicate unexpected re-entrancy |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/CreateBeforeAccept` | A payload was ignored because one was already created on this transaction | Check for calls that create outbound trace headers before accepting inbound ones |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/MajorVersion` | A payload was ignored due to an unsupported major version | Indicates an incompatible upstream agent version |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/UntrustedAccount` | A payload was ignored because it came from an untrusted account | Check your distributed tracing trust configuration |

### W3C TraceContext metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/TraceContext/Create/Success` | Created W3C-compliant trace headers | Should match outbound request volume |
| `Supportability/TraceContext/Create/Exception` | Failed to create W3C trace headers | Any non-zero values indicate problems |
| `Supportability/TraceContext/Accept/Success` | Processed incoming W3C trace headers | Should match inbound traced request volume |
| `Supportability/TraceContext/Accept/Exception` | Failed to process incoming W3C trace headers | Non-zero values indicate header format issues |
| `Supportability/TraceContext/Accept/Ignored/Multiple` | A `traceparent` header was ignored because a trace was already accepted | Expected in nested call scenarios |
| `Supportability/TraceContext/Accept/Ignored/CreateBeforeAccept` | A trace context was ignored because a payload was already created on this transaction | Check for calls that create outbound trace headers before accepting inbound ones |
| `Supportability/TraceContext/TraceParent/Parse/Exception` | Failed to parse a `traceparent` header | Check upstream services for malformed headers |
| `Supportability/TraceContext/TraceState/Parse/Exception` | Failed to parse a `tracestate` header | Check upstream services for malformed headers |
| `Supportability/TraceContext/TraceState/NoNrEntry` | No New Relic entry was found in `tracestate` | Expected when the upstream service isn't a New Relic agent |
| `Supportability/TraceContext/TraceState/InvalidNrEntry` | The New Relic entry in `tracestate` was invalid | Check for version mismatches between agents |

<Callout variant="tip">
  Compare `Create/Success` and `Accept/Success` counts with your actual request volume. A low ratio may indicate that not all services in your trace have distributed tracing enabled.
</Callout>

## Data harvest and event metrics [#event-harvest-metrics]

These metrics track how much data the agent collects versus how much is actually sent, which helps identify data loss due to reservoir limits.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/EventHarvest/ReportPeriod` | How often the agent reports data to New Relic | Validate against your configured harvest cycle |
| `Supportability/EventHarvest/AnalyticEventData/HarvestLimit` | Configured reservoir limit for transaction events (`analytics_events.max_samples_stored`) | Compare against your actual transaction event volume |
| `Supportability/EventHarvest/ErrorEventData/HarvestLimit` | Configured reservoir limit for error events (`error_collector.max_event_samples_stored`) | Compare against error event volume |
| `Supportability/EventHarvest/CustomEventData/HarvestLimit` | Configured reservoir limit for custom events (`custom_insights_events.max_samples_stored`) | Compare against `Supportability/Events/Customer/Seen` and `/Sent` |
| `Supportability/EventHarvest/SpanEventData/HarvestLimit` | Configured reservoir limit for span events (`span_events.max_samples_stored`) | Compare against `Supportability/SpanEvent/TotalEventsSeen` and `TotalEventsSent` |
| `Supportability/Events/TransactionError/Seen` | Total error events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/TransactionError/Sent` | Total error events transmitted | Should be close to `Seen` |
| `Supportability/Events/Customer/Seen` | Total custom events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/Customer/Sent` | Total custom events transmitted | Should be close to `Seen` |
| `Supportability/Events/Customer/Dropped` | Custom events dropped before harvest | Non-zero values indicate reservoir limits are being hit |
| `Supportability/SpanEvent/TotalEventsSeen` | Total span events collected | Compare with `TotalEventsSent` to check for data loss |
| `Supportability/SpanEvent/TotalEventsSent` | Total span events transmitted | Should be close to `TotalEventsSeen` |
| `Supportability/SpanEvent/Discarded` | Span events discarded before harvest | Non-zero values indicate reservoir limits are being hit |

<CollapserGroup>
  <Collapser
    id="example-data-loss"
    title="Example: Detecting data loss"
  >
    If you see these values in your metrics:

    * `Supportability/Events/Customer/Seen`: 10,000
    * `Supportability/Events/Customer/Sent`: 2,000

    This indicates your agent collected 10,000 custom events but only sent 2,000 to New Relic. The remaining 8,000 events were dropped due to reservoir size limits. Consider increasing your `custom_insights_events.max_samples_stored` configuration.
  </Collapser>
</CollapserGroup>

## Infinite Tracing metrics [#infinite-tracing-metrics]

If you use [Infinite Tracing](/docs/distributed-tracing/infinite-tracing/introduction-infinite-tracing/), these metrics help you monitor the gRPC connection used to stream spans.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/InfiniteTracing/Span/Seen` | Spans seen by the agent and eligible for streaming | Baseline for comparing sent/error counts |
| `Supportability/InfiniteTracing/Span/Sent` | Spans successfully streamed to the trace observer | Should closely track `Span/Seen` |
| `Supportability/InfiniteTracing/Span/AgentQueueDumped` | The agent's internal span queue was dumped, discarding buffered spans | Non-zero values indicate the connection to the trace observer was lost for an extended period |
| `Supportability/InfiniteTracing/Span/Response/Error` | The trace observer returned an error response | Non-zero values indicate issues with the trace observer connection |
| `Supportability/InfiniteTracing/Span/gRPC/{status}` | The trace observer returned a specific gRPC status | Non-`OK` statuses indicate connection or compatibility issues |

## Environment and utilization metrics [#environment-metrics]

These metrics track errors and results from gathering environment and cloud/platform utilization data at startup.

| Metric name | Description | Use case |
|-------------|-------------|----------|
| `Supportability/utilization/aws/error` | Error gathering AWS utilization data | Non-zero values indicate the agent couldn't reach the AWS metadata endpoint |
| `Supportability/utilization/azure/error` | Error gathering Azure utilization data | Non-zero values indicate the agent couldn't reach the Azure metadata endpoint |
| `Supportability/utilization/gcp/error` | Error gathering GCP utilization data | Non-zero values indicate the agent couldn't reach the GCP metadata endpoint |
| `Supportability/utilization/pcf/error` | Error gathering Pivotal Cloud Foundry utilization data | Non-zero values indicate the agent couldn't reach the PCF environment variables |
| `Supportability/utilization/docker/error` | Error gathering Docker utilization data | Non-zero values indicate the agent couldn't read container metadata |
| `Supportability/EnvironmentReport/success` | The agent successfully gathered a full environment report | Baseline for comparing against `empty` and `error` |
| `Supportability/EnvironmentReport/success/{key}` | A specific environment attribute was successfully gathered | Confirms a specific environment detail (for example, Gemfile or framework version) was captured |
| `Supportability/EnvironmentReport/empty/{key}` | A specific environment attribute returned no data | Expected for attributes that don't apply to your environment |
| `Supportability/EnvironmentReport/error/{key}` | An error occurred gathering a specific environment attribute | Non-zero values can indicate a problem with that detection method on your host |

## Logging metrics [#logging-metrics]

These metrics report which [application logging](/docs/logs/logs-context/configure-logs-context-ruby/) features are enabled, and confirm which logging library your application is using.

| Metric name | Description | What it means |
|-------------|-------------|---------------|
| `Supportability/Logging/Metrics/Ruby/enabled` or `/disabled` | Whether log-derived metrics (`Logging/lines`, `Logging/lines/{SEVERITY}`) are enabled | Confirms whether the agent is generating metrics from your log volume |
| `Supportability/Logging/Forwarding/Ruby/enabled` or `/disabled` | Whether log forwarding to New Relic is enabled | Confirms whether your application's logs are being sent to New Relic |
| `Supportability/Logging/LocalDecorating/Ruby/enabled` or `/disabled` | Whether local log decoration (adding `NR-LINKING` metadata to your log output) is enabled | Confirms whether logs are being decorated for linking when you forward them yourself |
| `Supportability/Logging/Labels/Ruby/enabled` or `/disabled` | Whether custom labels are being attached to forwarded log events | Confirms whether your configured labels are being applied to log data |
| `Supportability/Logging/Forwarding/Seen` | Total log events seen by the agent | Compare with `Sent` to check for data loss |
| `Supportability/Logging/Forwarding/Sent` | Total log events forwarded to New Relic | Should be close to `Seen` |
| `Supportability/Logging/Ruby/{library}/enabled` or `/disabled` | A specific logging library (for example, `Logger`, `Logging`, `LogStasher`, `SemanticLogger`, or `RailsEventLogger`) was detected as enabled or disabled for instrumentation | Confirms which logging library in your application the agent is instrumenting |
| `Supportability/{library}/Invoked` | A specific logging library's instrumentation (for example, `Logger`, `Logging`, `LogStasher`, or `SemanticLogger`) was actually invoked | Confirms the instrumentation path is executing, not just installed |

## Instrumentation and runtime metrics [#instrumentation-metrics]

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/PrependedModules/{class}` | Number of times the agent used `Module#prepend` to instrument a given class | Helps confirm whether prepend-based instrumentation is active for a given framework class |
| `Supportability/Instrumentation/{library}/Prepend` | A library (for example, `Redis` or `NetHTTP`) was instrumented using `Module#prepend` | Confirms which installation method the agent used for that library |
| `Supportability/Instrumentation/{library}/MethodChaining` | A library was instrumented using method chaining (aliasing) instead of `prepend` | Typically used as a fallback when `prepend` isn't suitable for that library/Ruby version combination |
| `Supportability/ThreadProfiler/DroppedBacktraces` | Backtraces dropped by the thread profiler | Non-zero values indicate the profiler couldn't keep up with the polling interval |
| `Supportability/ThreadProfiler/PollingTime` | Time spent polling thread backtraces | High values can indicate thread profiler overhead |
| `Supportability/ThreadProfiler/Skew` | Difference between the expected and actual thread profiler poll interval | High values indicate the profiler is falling behind schedule |

## Querying supportability metrics [#querying-metrics]

Use these NRQL queries to analyze your supportability metrics:

<CollapserGroup>
  <Collapser
    id="query-distributed-tracing"
    title="Monitor distributed tracing health"
  >
    ```sql
    SELECT
      sum(`Supportability/TraceContext/Create/Success`) AS 'Successful Outbound Traces',
      sum(`Supportability/TraceContext/Accept/Success`) AS 'Successful Inbound Traces'
    FROM Metric
    WHERE metricName LIKE 'Supportability/TraceContext%'
    SINCE 1 hour ago
    TIMESERIES
    ```
  </Collapser>

  <Collapser
    id="query-data-harvest"
    title="Check for custom event data loss"
  >
    ```sql
    SELECT
      sum(`Supportability/Events/Customer/Seen`) AS 'Events Collected',
      sum(`Supportability/Events/Customer/Sent`) AS 'Events Sent',
      sum(`Supportability/Events/Customer/Dropped`) AS 'Events Dropped'
    FROM Metric
    WHERE metricName LIKE 'Supportability/Events/Customer%'
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-infinite-tracing"
    title="Monitor Infinite Tracing span delivery"
  >
    ```sql
    SELECT
      sum(`Supportability/InfiniteTracing/Span/Seen`) AS 'Spans Seen',
      sum(`Supportability/InfiniteTracing/Span/Sent`) AS 'Spans Sent',
      sum(`Supportability/InfiniteTracing/Span/Response/Error`) AS 'Response Errors'
    FROM Metric
    WHERE metricName LIKE 'Supportability/InfiniteTracing%'
    SINCE 1 day ago
    TIMESERIES
    ```
  </Collapser>

  <Collapser
    id="query-environment-report"
    title="Audit environment report collection"
  >
    ```sql
    SELECT uniques(metricName)
    FROM Metric
    WHERE metricName LIKE 'Supportability/EnvironmentReport/error%'
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-logging-config"
    title="Confirm which application logging features are enabled"
  >
    ```sql
    SELECT uniques(metricName)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Logging/%/Ruby/%'
    SINCE 1 day ago
    ```
  </Collapser>
</CollapserGroup>

## Troubleshooting with supportability metrics [#troubleshooting]

| Problem | Metrics to check | Solution |
|---------|------------------|----------|
| Missing distributed traces | `Supportability/TraceContext/Create/Success` and `Accept/Success` | Verify distributed tracing is enabled on all services |
| Custom events missing | Compare `Events/Customer/Seen` vs `Sent`/`Dropped` | Increase your `custom_insights_events.max_samples_stored` configuration |
| Thread profiler data looks incomplete | `Supportability/ThreadProfiler/DroppedBacktraces`, `Skew` | Reduce profiling frequency or investigate host CPU contention |
| Infinite Tracing spans dropped | `Supportability/InfiniteTracing/Span/Response/Error`, `AgentQueueDumped` | Check connectivity to the configured trace observer |
| Environment details missing from APM | `Supportability/EnvironmentReport/error/{key}` | Check agent logs for the specific environment detection error |
| Logs not forwarding to New Relic | `Supportability/Logging/Forwarding/Ruby/enabled`, `Forwarding/Seen` vs `Sent` | Confirm `application_logging.forwarding.enabled` is `true` and check which logging library is active |
| A library isn't being instrumented as expected | `Supportability/Instrumentation/{library}/Prepend` or `/MethodChaining` | Confirm the library and version are supported, and that instrumentation wasn't disabled in configuration |

### Creating alerts for supportability metrics

Monitor critical supportability metrics with [NRQL alert conditions](/docs/alerts/create-alert/create-alert-condition/create-nrql-alert-conditions/):

<CollapserGroup>
  <Collapser
    id="alert-data-loss"
    title="Alert on custom event data loss"
  >
    **Alert condition**: Data loss detection

    ```sql
    SELECT
      sum(`Supportability/Events/Customer/Dropped`) / sum(`Supportability/Events/Customer/Seen`) * 100
    FROM Metric
    WHERE metricName LIKE 'Supportability/Events/Customer%'
    ```

    **Threshold**: Alert when data loss exceeds 10%
  </Collapser>

  <Collapser
    id="alert-infinite-tracing-errors"
    title="Alert on Infinite Tracing response errors"
  >
    **Alert condition**: Trace observer response errors

    ```sql
    SELECT sum(`Supportability/InfiniteTracing/Span/Response/Error`)
    FROM Metric
    WHERE metricName = 'Supportability/InfiniteTracing/Span/Response/Error'
    ```

    **Threshold**: Alert when errors exceed 5 in 5 minutes
  </Collapser>
</CollapserGroup>
