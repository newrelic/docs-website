Supportability metrics help you understand how your Java agent is performing and identify potential issues with your application monitoring. These metrics provide valuable insights into agent behavior, feature adoption, and configuration effectiveness.

<Callout variant="important">
  You're charged for supportability metric ingest as part of your New Relic data consumption. These metrics provide valuable troubleshooting and optimization information that can help you resolve issues faster and improve application performance.
</Callout>

## What are supportability metrics? [#what-are-supportability-metrics]

Supportability metrics are specialized metrics that the Java agent automatically collects about its own operation. They help you:

* **Troubleshoot monitoring issues**: Identify why certain data isn't appearing in your dashboards
* **Validate configuration**: Confirm that features like distributed tracing or span events are working correctly
* **Monitor agent performance**: Track resource usage and identify potential bottlenecks caused by instrumentation
* **Optimize feature usage**: Understand which agent features and APIs your application is using

All supportability metrics use the `Supportability/` prefix in their metric names, making them easy to identify and query with [NRQL](/docs/nrql/get-started/introduction-nrql-new-relics-query-language/).

## Distributed tracing metrics [#distributed-tracing-metrics]

These metrics help you troubleshoot distributed tracing configuration and connectivity issues between your services.

### New Relic payload metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/DistributedTrace/CreatePayload/Success` | Successfully created a tracing payload for an outbound request | Low values relative to outbound request volume may indicate configuration issues |
| `Supportability/DistributedTrace/CreatePayload/Exception` | Failed to create a tracing payload due to an error | Any non-zero values indicate problems |
| `Supportability/DistributedTrace/AcceptPayload/Success` | Successfully processed an incoming tracing payload | Should track with inbound traced request volume |
| `Supportability/DistributedTrace/AcceptPayload/Exception` | Failed to process an incoming tracing payload | Investigate non-zero values for configuration or version mismatches |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/Multiple` | A payload was ignored because one was already accepted on this transaction | Expected in nested call scenarios; high volumes may indicate unexpected re-entrancy |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/MajorVersion` | A payload was ignored due to an unsupported major version | Indicates an incompatible upstream agent version |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/UntrustedAccount` | A payload was ignored because it came from an untrusted account | Check your distributed tracing trust configuration |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/Null` | A null payload was passed to the accept API | Check instrumentation or custom code calling the API |
| `Supportability/DistributedTrace/AcceptPayload/ParseException` | A payload couldn't be parsed | Indicates malformed headers from an upstream service |
| `Supportability/DistributedTracing` | Distributed tracing is enabled | Confirms the feature is active |

### W3C TraceContext metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/TraceContext/Create/Success` | Created W3C-compliant trace headers | Should match outbound request volume |
| `Supportability/TraceContext/Create/Exception` | Failed to create W3C trace headers | Any non-zero values indicate problems |
| `Supportability/TraceContext/Accept/Success` | Processed incoming W3C trace headers | Should match inbound traced request volume |
| `Supportability/TraceContext/Accept/Exception` | Failed to process incoming W3C trace headers | Non-zero values indicate header format issues |
| `Supportability/TraceContext/TraceParent/Ignored/NullHeaders` | No `traceparent` header was present | Check that upstream services are sending W3C headers |
| `Supportability/TraceContext/TraceParent/Ignored/Multiple` | Multiple `traceparent` headers were found and ignored | Check upstream services or proxies for header duplication |
| `Supportability/TraceContext/TraceParent/Ignored/InvalidFieldCount` | A `traceparent` header had an unexpected number of fields | Check upstream services for proper W3C implementation |
| `Supportability/TraceContext/TraceParent/Parse/Exception` | Failed to parse a `traceparent` header | Check upstream services for malformed headers |
| `Supportability/TraceContext/TraceState/InvalidNrEntry` | The New Relic entry in `tracestate` was invalid | Check for version mismatches between agents |
| `Supportability/TraceContext/TraceState/NoNrEntry` | No New Relic entry was found in `tracestate` | Expected when the upstream service isn't a New Relic agent |
| `Supportability/TraceContext/TraceState/Ignored/UntrustedAccount` | The `tracestate` entry came from an untrusted account | Check your distributed tracing trust configuration |
| `Supportability/TraceContext/TraceState/Parse/Exception` | Failed to parse a `tracestate` header | Check upstream services for malformed headers |

<Callout variant="tip">
  Compare `Create/Success` and `Accept/Success` counts with your actual request volume. A low ratio may indicate that not all services in your trace have distributed tracing enabled.
</Callout>

## Agent collector communication metrics [#collector-metrics]

These metrics monitor communication between your agent and New Relic's data collection service.

| Metric name | Description | What it means |
|-------------|-------------|---------------|
| `Supportability/Agent/Collector/HTTPError/{response code}` | An HTTP error was returned by the collector | Non-200-series values indicate connectivity, proxy, or authentication issues |
| `Supportability/Agent/Collector/{endpoint method}/Attempts` | Number of attempts to call a given collector endpoint | High retry counts can indicate network instability |
| `Supportability/Agent/Collector/{endpoint method}/Duration` | Time spent calling a given collector endpoint | High durations may point to network latency between the host and New Relic |
| `Supportability/Agent/Collector/Connection/New` | A new connection to the collector was opened | Frequent new connections (instead of reuse) can add overhead |
| `Supportability/Agent/Collector/Connection/Reused` | An existing connection to the collector was reused | Healthy connection pooling shows high reuse relative to new connections |
| `Supportability/Agent/Collector/MaxPayloadSizeLimit/{endpoint}` | A payload exceeded the maximum size limit and was dropped | Indicates data loss; consider reducing harvest limits for that data type |
| `Supportability/Agent/Collector/Connect/BackoffAttempts` | The agent backed off and retried its initial connection | Non-zero values indicate the agent had trouble establishing its initial connection |
| `Supportability/Agent/Collector/MissingEventHarvestConfig` | The collector didn't return event harvest configuration on connect | May indicate a collector-side configuration issue |

## Data harvest and event metrics [#event-harvest-metrics]

These metrics track how much data the agent collects versus how much is actually sent, which helps identify data loss due to reservoir limits.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/EventHarvest/ReportPeriod` | How often the agent reports data to New Relic | Validate against your configured harvest cycle |
| `Supportability/EventHarvest/AnalyticEventData/HarvestLimit` | Configured reservoir limit for transaction events | Compare against `TotalEventsSeen`/`TotalEventsSent` to check for data loss |
| `Supportability/EventHarvest/ErrorEventData/HarvestLimit` | Configured reservoir limit for error events | Compare against error event seen/sent counts |
| `Supportability/EventHarvest/CustomEventData/HarvestLimit` | Configured reservoir limit for custom events | Compare against `Supportability/Events/Customer/Seen` and `/Sent` |
| `Supportability/EventHarvest/SpanEventData/HarvestLimit` | Configured reservoir limit for span events | Compare against `Supportability/SpanEvent/TotalEventsSeen` and `TotalEventsSent` |
| `Supportability/Events/TransactionEvent/Seen` | Total transaction events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/TransactionEvent/Sent` | Total transaction events transmitted | Should be close to `Seen` |
| `Supportability/Events/TransactionError/Seen` | Total error events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/TransactionError/Sent` | Total error events transmitted | Should be close to `Seen` |
| `Supportability/Events/Customer/Seen` | Total custom events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/Customer/Sent` | Total custom events transmitted | Should be close to `Seen` |
| `Supportability/SpanEvent/TotalEventsSeen` | Total span events collected | Compare with `TotalEventsSent` to check for data loss |
| `Supportability/SpanEvent/TotalEventsSent` | Total span events transmitted | Should be close to `TotalEventsSeen` |
| `Supportability/SpanEvent/Discarded` | Span events discarded before harvest | Non-zero values indicate reservoir limits are being hit |
| `Supportability/SpanEvents` | Span events (distributed tracing) are enabled | Confirms the feature is active |
| `Supportability/EventHarvest/LogEventData/HarvestLimit` | Configured reservoir limit for log events | Compare against `Supportability/Logging/Forwarding/Seen` and `/Sent` |
| `Supportability/EventHarvest/LogEventData/ReportPeriod` | How often log events are reported to New Relic | Validate against your configured harvest cycle |

<CollapserGroup>
  <Collapser
    id="example-data-loss"
    title="Example: Detecting data loss"
  >
    If you see these values in your metrics:

    * `Supportability/Events/TransactionEvent/Seen`: 10,000
    * `Supportability/Events/TransactionEvent/Sent`: 2,000

    This indicates your agent collected 10,000 transaction events but only sent 2,000 to New Relic. The remaining 8,000 events were dropped due to reservoir size limits. Consider increasing your `transaction_events.max_samples_stored` configuration.
  </Collapser>
</CollapserGroup>

## Transaction lifecycle metrics [#transaction-metrics]

These metrics track how transactions move through the agent, which can help identify dropped or cancelled transactions.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/Transaction/StartedCount` | Number of transactions started | Baseline for comparing finished/cancelled counts |
| `Supportability/Transaction/FinishedCount` | Number of transactions finished normally | Should closely track `StartedCount` |
| `Supportability/Transaction/CancelledCount` | Number of transactions cancelled before completion | High values may indicate instrumentation issues or timeouts |
| `Supportability/TransactionSize` | Size of transaction trace data | Unusually large values can increase agent overhead |
| `Supportability/TransactionSizeClamp` | A transaction trace was clamped because it exceeded the size limit | Non-zero values indicate very large or deeply nested transactions |
| `Supportability/TransactionSegmentClamp` | A transaction trace was clamped because it exceeded the segment limit | Non-zero values may indicate excessive instrumentation depth |
| `Supportability/Timeout/finishSegmentNotCalled` | A segment timed out because it was never explicitly finished | Indicates custom instrumentation that isn't closing segments properly |

| Metric name | Description | What to monitor |
|-------------|-------------|-----------------|
| `Supportability/WeaveInstrumentation/Loaded/{module}/{version}` | A weave instrumentation module was successfully loaded | Validates that expected frameworks are being monitored |
| `Supportability/WeaveInstrumentation/Loaded/Custom/{module}/{version}` | A custom weave instrumentation module was successfully loaded | Validates your custom instrumentation modules |
| `Supportability/WeaveInstrumentation/Skipped/{module}/{version}` | A weave instrumentation module was skipped | Non-zero values can indicate version incompatibilities |
| `Supportability/WeaveInstrumentation/Skipped/Custom/{module}/{version}` | A custom weave instrumentation module was skipped | Check your custom instrumentation for compatibility issues |
| `Supportability/PointCutInstrumentation/Loaded/{name}` | A legacy pointcut-based instrumentation module was loaded | Useful when troubleshooting older instrumentation modules |
| `Supportability/LoadedClasses/{language}/{version}/count` | Count of loaded classes by detected source language and version | Helps validate polyglot (for example, Kotlin or Scala) support |

## Logging metrics [#logging-metrics]

| Metric name | Description | What it means |

| `Supportability/Logging/Forwarding/Sent` | Log events successfully forwarded to New Relic | Should closely track `Seen` |
| `Supportability/Logging/Forwarding/Denylist` | A log event matched a configured denylist rule and wasn't forwarded | Expected when you've intentionally filtered certain log messages |
| `Supportability/Logging/Forwarding/Java/enabled` | Log forwarding is enabled | Confirms the feature is active |
| `Supportability/Logging/Forwarding/Java/disabled` | Log forwarding is disabled | Confirms the feature is inactive |
| `Supportability/Logging/Metrics/Java/enabled` | Log metrics (counts of log lines by severity) are enabled | Confirms the feature is active |
| `Supportability/Logging/LocalDecorating/Java/enabled` | Local log decoration is active | Confirms linking metadata is being added to your log files |
| `Supportability/Logging/Labels/Java/enabled` | Log forwarding is configured to include your account's labels | Confirms label-based log filtering/organization is active |
| `Supportability/Logging/Java/Log4j2.6/enabled` | The agent detected and instrumented Log4j 2.x | Confirms which logging framework integration is active; similar metrics exist per framework, such as `Log4j1`, `JavaUtilLogging`, `JBossLogging`, and `LogbackClassic1.2` |
| `Supportability/Logging/Java/OpenTelemetryBridge/enabled` | The agent is bridging logs from the OpenTelemetry SDK | Confirms OpenTelemetry log bridging is active |

## JFR metrics [#jfr-metrics]

These metrics track the Java Flight Recorder (JFR) service, which collects JVM-level telemetry on supported runtimes.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/JfrService/Started/Success` | The JFR service started successfully | Baseline for confirming JFR is active |
| `Supportability/JfrService/Stopped/Success` | The JFR service stopped successfully | Expected during graceful agent shutdown |
| `Supportability/JfrService/IgnoreStart/Disabled` | JFR was not started because it's disabled in configuration | Expected if you've intentionally disabled JFR |
| `Supportability/JfrService/IgnoreStart/ApisMissing` | JFR was not started because required JVM APIs are missing | Indicates an unsupported JVM/JDK version for JFR |
| `Supportability/JfrService/IgnoreStart/ServiceNotStarted` | JFR was not started for another internal reason | Check agent logs for details |
| `Supportability/JfrService/Config/HarvestInterval` | The configured JFR harvest interval | Validate against your configuration |
| `Supportability/JfrService/Config/QueueSize` | The configured JFR event queue size | Validate against your configuration |

## Async and token metrics [#async-metrics]

These metrics track the agent's token-based API for linking asynchronous work back to the originating transaction.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/Async/Token/Create` | A token was created to link async work to a transaction | Baseline for comparing link/timeout counts |
| `Supportability/Async/Token/Link/Success` | A token was successfully used to link async work | Should closely track `Token/Create` |
| `Supportability/Async/Token/Link/Ignore` | A token link attempt was ignored | Non-zero values may indicate tokens being linked after the transaction already finished |
| `Supportability/Async/Token/Timeout` | A token expired before it was used to link async work | High values can indicate async work that's slower than the token timeout, or custom instrumentation that never calls the token |
| `Supportability/Async/Token/Expire` | A token expired | Compare against `Create` to see what fraction of tokens go unused |

## Querying supportability metrics [#querying-metrics]

Use these NRQL queries to analyze your supportability metrics:

<CollapserGroup>
  <Collapser
    id="query-distributed-tracing"
    title="Monitor distributed tracing health"
  >
    ```sql
    SELECT
      sum(`Supportability/TraceContext/Create/Success`) AS 'Successful Outbound Traces',
      sum(`Supportability/TraceContext/Accept/Success`) AS 'Successful Inbound Traces',
      sum(`Supportability/TraceContext/Accept/Exception`) AS 'Failed Inbound Traces'
    FROM Metric
    WHERE metricName LIKE 'Supportability/TraceContext%'
    SINCE 1 hour ago
    TIMESERIES
    ```
  </Collapser>

  <Collapser
    id="query-data-harvest"
    title="Check for transaction event data loss"
  >
    ```sql
    SELECT
      sum(`Supportability/Events/TransactionEvent/Seen`) AS 'Events Collected',
      sum(`Supportability/Events/TransactionEvent/Sent`) AS 'Events Sent'
    FROM Metric
    WHERE metricName LIKE 'Supportability/Events/TransactionEvent%'
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-collector-errors"
    title="Check for collector connectivity issues"
  >
    ```sql
    SELECT count(*)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Agent/Collector/HTTPError%'
    FACET metricName
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-environment-info"
    title="Audit runtime environment"
  >
    ```sql
    SELECT uniques(metricName) AS 'Environment Details'
    FROM Metric
    WHERE metricName LIKE 'Supportability/Jvm%'
       OR metricName LIKE 'Supportability/utilization%'
       OR metricName LIKE 'Supportability/Java/AgentVersion%'
    SINCE 1 day ago
    ```
  </Collapser>
</CollapserGroup>

## Troubleshooting with supportability metrics [#troubleshooting]

| Problem | Metrics to check | Solution |
|---------|------------------|----------|
| Missing distributed traces | `Supportability/TraceContext/Create/Success` and `Accept/Success` | Verify distributed tracing is enabled on all services |
| Transaction events missing | Compare `Events/TransactionEvent/Seen` vs `Sent` | Increase your transaction events reservoir size |
| High agent overhead | `Supportability/TransactionSizeClamp`, `Supportability/TransactionSegmentClamp` | Review custom instrumentation for excessive segment creation |
| Collector connectivity errors | `Supportability/Agent/Collector/HTTPError/*`, `Connect/BackoffAttempts` | Check network/proxy/firewall rules between the host and New Relic |
| Async work not linked to transactions | `Supportability/Async/Token/Timeout` vs `Token/Create` | Review custom async instrumentation for tokens that expire before use |
| Infinite Tracing spans dropped | `Supportability/InfiniteTracing/NotReady`, `Response/Error` | Check connectivity to the configured trace observer |

### Creating alerts for supportability metrics

Monitor critical supportability metrics with [NRQL alert conditions](/docs/alerts/create-alert/create-alert-condition/create-nrql-alert-conditions/):

<CollapserGroup>
  <Collapser
    id="alert-data-loss"
    title="Alert on transaction event data loss"
  >
    **Alert condition**: Data loss detection

    ```sql
    SELECT
      (sum(`Supportability/Events/TransactionEvent/Seen`) - sum(`Supportability/Events/TransactionEvent/Sent`)) / sum(`Supportability/Events/TransactionEvent/Seen`) * 100
    FROM Metric
    WHERE metricName LIKE 'Supportability/Events/TransactionEvent%'
    ```

    **Threshold**: Alert when data loss exceeds 10%
  </Collapser>

  <Collapser
    id="alert-collector-errors"
    title="Alert on collector connection problems"
  >
    **Alert condition**: Collector HTTP errors

    ```sql
    SELECT count(*)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Agent/Collector/HTTPError%'
    ```

    **Threshold**: Alert when errors exceed 5 in 5 minutes
  </Collapser>
</CollapserGroup>
