Supportability metrics help you understand how your Node.js agent is performing and identify potential issues with your application monitoring. These metrics provide valuable insights into agent behavior, feature adoption, and configuration effectiveness.

<Callout variant="important">
  You're charged for supportability metric ingest as part of your New Relic data consumption. These metrics provide valuable troubleshooting and optimization information that can help you resolve issues faster and improve application performance.
</Callout>

## What are supportability metrics? [#what-are-supportability-metrics]

Supportability metrics are specialized metrics that the Node.js agent automatically collects about its own operation. They help you:

* **Troubleshoot monitoring issues**: Identify why certain data isn't appearing in your dashboards
* **Validate configuration**: Confirm that features like distributed tracing or Infinite Tracing are working correctly
* **Monitor agent performance**: Track resource usage and identify modules the agent couldn't instrument
* **Optimize feature usage**: Understand which agent API methods your application is using

All supportability metrics use the `Supportability/` prefix in their metric names, making them easy to identify and query with [NRQL](/docs/nrql/get-started/introduction-nrql-new-relics-query-language/).

## Distributed tracing metrics [#distributed-tracing-metrics]

These metrics help you troubleshoot distributed tracing configuration and connectivity issues between your services.

### New Relic payload metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/DistributedTrace/CreatePayload/Success` | Successfully created a tracing payload for an outbound request | Low values relative to outbound request volume may indicate configuration issues |
| `Supportability/DistributedTrace/AcceptPayload/Success` | Successfully processed an incoming tracing payload | Should track with inbound traced request volume |
| `Supportability/DistributedTrace/AcceptPayload/Exception` | Failed to process an incoming tracing payload | Investigate non-zero values for configuration or version mismatches |
| `Supportability/DistributedTrace/AcceptPayload/ParseException` | A payload couldn't be parsed | Indicates malformed headers from an upstream service |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/Null` | A null payload was passed to the accept API | Check instrumentation or custom code calling the API |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/Multiple` | A payload was ignored because one was already accepted on this transaction | Expected in nested call scenarios; high volumes may indicate unexpected re-entrancy |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/MajorVersion` | A payload was ignored due to an unsupported major version | Indicates an incompatible upstream agent version |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/UntrustedAccount` | A payload was ignored because it came from an untrusted account | Check your distributed tracing trust configuration |

### W3C TraceContext metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/TraceContext/Create/Success` | Created W3C-compliant trace headers | Should match outbound request volume |
| `Supportability/TraceContext/TraceState/Create/Exception` | Failed to create a `tracestate` header | Any non-zero values indicate problems |
| `Supportability/TraceContext/Accept/Success` | Processed incoming W3C trace headers | Should match inbound traced request volume |
| `Supportability/TraceContext/Accept/Ignored/Multiple` | A `traceparent` header was ignored because a trace was already accepted | Expected in nested call scenarios |
| `Supportability/TraceContext/Accept/Ignored/CreateBeforeAccept` | A trace context was ignored because a payload was already created on this transaction | Check for calls that create outbound trace headers before accepting inbound ones |
| `Supportability/TraceContext/TraceState/Accept/Exception` | Failed to accept a `tracestate` header | Non-zero values indicate header format issues |
| `Supportability/TraceContext/TraceState/Parse/Exception` | Failed to parse a `tracestate` header | Check upstream services for malformed headers |
| `Supportability/TraceContext/TraceState/Parse/Exception/ListMember` | Failed to parse an individual member of the `tracestate` list | Check upstream services for malformed `tracestate` entries |
| `Supportability/TraceContext/TraceState/NoNrEntry` | No New Relic entry was found in `tracestate` | Expected when the upstream service isn't a New Relic agent |

<Callout variant="tip">
  Compare `Create/Success` and `Accept/Success` counts with your actual request volume. A low ratio may indicate that not all services in your trace have distributed tracing enabled.
</Callout>

## Data harvest and event metrics [#event-harvest-metrics]

These metrics track how much data the agent collects versus how much is actually sent, which helps identify data loss due to reservoir limits.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/EventHarvest/ReportPeriod` | How often the agent reports data to New Relic | Validate against your configured harvest cycle |
| `Supportability/EventHarvest/AnalyticEventData/HarvestLimit` | Configured reservoir limit for transaction events | Compare against `AnalyticsEvents/TotalEventsSeen`/`TotalEventsSent` to check for data loss |
| `Supportability/EventHarvest/ErrorEventData/HarvestLimit` | Configured reservoir limit for error events | Compare against error event seen/sent counts |
| `Supportability/EventHarvest/CustomEventData/HarvestLimit` | Configured reservoir limit for custom events | Compare against `Supportability/Events/Customer/Seen` and `/Sent` |
| `Supportability/EventHarvest/SpanEventData/HarvestLimit` | Configured reservoir limit for span events | Compare against `Supportability/SpanEvent/TotalEventsSeen` and `TotalEventsSent` |
| `Supportability/EventHarvest/LogEventData/HarvestLimit` | Configured reservoir limit for log events | Compare against log forwarding seen/sent counts if log data looks incomplete |
| `Supportability/AnalyticsEvents/TotalEventsSeen` | Total transaction events collected | Compare with `TotalEventsSent` to check for data loss |
| `Supportability/AnalyticsEvents/TotalEventsSent` | Total transaction events transmitted | Should be close to `TotalEventsSeen` |
| `Supportability/AnalyticsEvents/Discarded` | Transaction events discarded before harvest | Non-zero values indicate reservoir limits are being hit |
| `Supportability/Events/TransactionError/Seen` | Total error events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/TransactionError/Sent` | Total error events transmitted | Should be close to `Seen` |
| `Supportability/Events/TransactionError/Dropped` | Error events dropped before harvest | Non-zero values indicate reservoir limits are being hit |
| `Supportability/Events/Customer/Seen` | Total custom events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/Customer/Sent` | Total custom events transmitted | Should be close to `Seen` |
| `Supportability/Events/Customer/Dropped` | Custom events dropped before harvest | Non-zero values indicate reservoir limits are being hit |
| `Supportability/Events/Customer/TooLarge` | A custom event exceeded the maximum allowed size and was dropped | Check the attributes you're attaching to custom events |
| `Supportability/Events/Customer/FailedToSend` | Custom events failed to send | Non-zero values indicate collector connectivity issues |
| `Supportability/SpanEvent/TotalEventsSeen` | Total span events collected | Compare with `TotalEventsSent` to check for data loss |
| `Supportability/SpanEvent/TotalEventsSent` | Total span events transmitted | Should be close to `TotalEventsSeen` |
| `Supportability/SpanEvent/Discarded` | Span events discarded before harvest | Non-zero values indicate reservoir limits are being hit |

<CollapserGroup>
  <Collapser
    id="example-data-loss"
    title="Example: Detecting data loss"
  >
    If you see these values in your metrics:

    * `Supportability/AnalyticsEvents/TotalEventsSeen`: 10,000
    * `Supportability/AnalyticsEvents/TotalEventsSent`: 2,000

    This indicates your agent collected 10,000 transaction events but only sent 2,000 to New Relic. The remaining 8,000 events were dropped due to reservoir size limits. Consider increasing your `transaction_events.max_samples_stored` configuration.
  </Collapser>
</CollapserGroup>

## Infinite Tracing metrics [#infinite-tracing-metrics]

If you use [Infinite Tracing](/docs/distributed-tracing/infinite-tracing/introduction-infinite-tracing/), these metrics help you monitor the gRPC connection used to stream spans.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/InfiniteTracing/Span/Seen` | Spans seen by the agent and eligible for streaming | Baseline for comparing sent/dropped counts |
| `Supportability/InfiniteTracing/Span/Sent` | Spans successfully streamed to the trace observer | Should closely track `Span/Seen` |
| `Supportability/InfiniteTracing/Span/Dropped` | Spans dropped before they could be streamed | Non-zero values indicate the agent's span queue is full or the connection can't keep up |
| `Supportability/InfiniteTracing/Span/Response/Error` | The trace observer returned an error response | Non-zero values indicate issues with the trace observer connection |
| `Supportability/InfiniteTracing/Span/gRPC/UNIMPLEMENTED` | The trace observer returned a gRPC `UNIMPLEMENTED` status | Indicates a version mismatch between the agent and the trace observer |
| `Supportability/InfiniteTracing/Span/QueueCapacity` | Configured capacity of the agent's internal span queue | Reference value when investigating dropped spans |
| `Supportability/InfiniteTracing/Span/QueueSize` | Current size of the agent's internal span queue | Values consistently near `QueueCapacity` indicate the queue is a bottleneck |
| `Supportability/InfiniteTracing/gRPC/Compression` | Whether gRPC compression is active for the trace observer connection | Validates your Infinite Tracing compression configuration |
| `Supportability/InfiniteTracing/gRPC/Batching` | Whether gRPC batching is active for the trace observer connection | Validates your Infinite Tracing batching configuration |
| `Supportability/InfiniteTracing/Drain/Duration` | Time spent draining buffered spans when closing the gRPC stream | High values can indicate backpressure on the trace observer connection |

## Logging metrics [#logging-metrics]

These metrics confirm which [application logging](/docs/logs/logs-context/configure-logs-context-nodejs/) features and logging libraries are active.

| Metric name | Description | What to monitor |
|-------------|-------------|-----------------|
| `Supportability/Logging/Metrics/Nodejs/enabled` or `disabled` | Whether log metrics (`application_logging.metrics`) are enabled | Validates your application logging configuration |
| `Supportability/Logging/Forwarding/Nodejs/enabled` or `disabled` | Whether log forwarding (`application_logging.forwarding`) is enabled | Validates whether logs should be arriving in New Relic |
| `Supportability/Logging/LocalDecorating/Nodejs/enabled` or `disabled` | Whether local log decorating (`application_logging.local_decorating`) is enabled | Confirms whether linking metadata is being added to local log output |
| `Supportability/Logging/Labels/Nodejs/enabled` or `disabled` | Whether custom labels are added to forwarded logs | Validates your `application_logging.forwarding.labels` configuration |
| `Supportability/Logging/Nodejs/winston/enabled` | The agent detected and instrumented the `winston` logging library | Confirms winston-specific log forwarding/decorating is active |
| `Supportability/Logging/Nodejs/bunyan/enabled` | The agent detected and instrumented the `bunyan` logging library | Confirms bunyan-specific log forwarding/decorating is active |
| `Supportability/Logging/Nodejs/pino/enabled` | The agent detected and instrumented the `pino` logging library | Confirms pino-specific log forwarding/decorating is active |
| `Supportability/Logging/Forwarding/Seen` | Total log lines seen and eligible for forwarding | Compare with `Sent` to check for log data loss |
| `Supportability/Logging/Forwarding/Sent` | Total log lines forwarded to New Relic | Should be close to `Seen` |
| `Supportability/Logging/Forwarding/Dropped` | Log lines dropped before forwarding | Non-zero values indicate forwarding reservoir limits are being hit |

## Instrumentation metrics [#instrumentation-metrics]

These metrics flag modules that your application loaded but that the agent couldn't instrument, and confirm which supported modules and features the agent did detect.

| Metric name | Description | What to monitor |
|-------------|-------------|-----------------|
| `Supportability/Uninstrumented` | Total count of modules loaded without New Relic instrumentation | Baseline count across all uninstrumented modules |
| `Supportability/Uninstrumented/{module}` | A specific module (for example, `redis`) was loaded without instrumentation | Confirms whether a library you expect to be monitored is actually supported |
| `Supportability/Features/Instrumentation/OnRequire/{module}` | The agent detected a `require()` of a supported module (for example, `express` or `kafkajs`) | Confirms the agent saw the module load |
| `Supportability/Features/Instrumentation/OnRequire/{module}/Version/{majorVersion}` | The major version of a required module that the agent detected | Validates the installed version against the agent's supported version range |
| `Supportability/Features/Instrumentation/SubscriberUsed/{module}` | The agent used `node:diagnostics_channel`-based instrumentation for a module (for example, `undici` or `pg`) | Confirms channel-based instrumentation is active for that module |
| `Supportability/Nodejs/Instrumentation/{module}/disabled` | Instrumentation for a specific module was explicitly disabled via configuration | Validates your `instrumentation.{module}.enabled: false` configuration |
| `Supportability/Features/ESM/Loader` | Your application is using the agent's ECMAScript module (ESM) loader | Confirms the agent initialized correctly for ESM-based applications |
| `Supportability/Features/EnableSourceMaps` | Your application has `--enable-source-maps` active | Informational: confirms Node's source map support is enabled |
| `Supportability/InstalledDependencies/NoNativeMetricsModule` | The optional native metrics module isn't installed | Non-zero values mean you're missing GC and event loop metrics; install `@newrelic/native-metrics` |

## Transaction and runtime metrics [#transaction-metrics]

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/Nodejs/Transactions/Segments` | Number of segments recorded per transaction | Unusually high values can increase agent overhead |
| `Supportability/Nodejs/Transactions/Nested` | A transaction was started while another was already active on the same context | Non-zero values can indicate instrumentation conflicts or unexpected async context propagation |
| `Supportability/Agent/DoubleLoad` | The agent module was required more than once in the same process | Non-zero values usually indicate `require('newrelic')` is being called in multiple entry points |

## Querying supportability metrics [#querying-metrics]

Use these NRQL queries to analyze your supportability metrics:

<CollapserGroup>
  <Collapser
    id="query-distributed-tracing"
    title="Monitor distributed tracing health"
  >
    ```sql
    SELECT
      sum(`Supportability/TraceContext/Create/Success`) AS 'Successful Outbound Traces',
      sum(`Supportability/TraceContext/Accept/Success`) AS 'Successful Inbound Traces'
    FROM Metric
    WHERE metricName LIKE 'Supportability/TraceContext%'
    SINCE 1 hour ago
    TIMESERIES
    ```
  </Collapser>

  <Collapser
    id="query-data-harvest"
    title="Check for transaction event data loss"
  >
    ```sql
    SELECT
      sum(`Supportability/AnalyticsEvents/TotalEventsSeen`) AS 'Events Collected',
      sum(`Supportability/AnalyticsEvents/TotalEventsSent`) AS 'Events Sent'
    FROM Metric
    WHERE metricName LIKE 'Supportability/AnalyticsEvents%'
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-uninstrumented-modules"
    title="Find uninstrumented modules"
  >
    ```sql
    SELECT uniques(metricName)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Uninstrumented/%'
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-infinite-tracing"
    title="Monitor Infinite Tracing span delivery"
  >
    ```sql
    SELECT
      sum(`Supportability/InfiniteTracing/Span/Seen`) AS 'Spans Seen',
      sum(`Supportability/InfiniteTracing/Span/Sent`) AS 'Spans Sent',
      sum(`Supportability/InfiniteTracing/Span/Response/Error`) AS 'Response Errors'
    FROM Metric
    WHERE metricName LIKE 'Supportability/InfiniteTracing%'
    SINCE 1 day ago
    TIMESERIES
    ```
  </Collapser>

  <Collapser
    id="query-logging-config"
    title="Audit application logging configuration"
  >
    ```sql
    SELECT uniques(metricName)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Logging/%'
    SINCE 1 day ago
    ```
  </Collapser>
</CollapserGroup>

## Troubleshooting with supportability metrics [#troubleshooting]

| Problem | Metrics to check | Solution |
|---------|------------------|----------|
| Missing distributed traces | `Supportability/TraceContext/Create/Success` and `Accept/Success` | Verify distributed tracing is enabled on all services |
| Transaction events missing | Compare `AnalyticsEvents/TotalEventsSeen` vs `TotalEventsSent` | Increase your transaction events reservoir size |
| A library isn't showing up in breakdowns | `Supportability/Uninstrumented/{module}` | Confirm the module and version are supported, or add [custom instrumentation](/docs/apm/agents/nodejs-agent/extend-your-instrumentation/nodejs-custom-instrumentation) |
| Infinite Tracing spans dropped | `Supportability/InfiniteTracing/Span/Response/Error` | Check connectivity to the configured trace observer |
| Custom events not appearing | `Supportability/Events/Customer/TooLarge`, `FailedToSend` | Reduce custom event attribute size, or check collector connectivity |
| Agent loaded multiple times | `Supportability/Agent/DoubleLoad` | Ensure `require('newrelic')` is only called once, as early as possible in your entry point |
| Logs not appearing in New Relic | `Supportability/Logging/Forwarding/Nodejs/enabled`, `Forwarding/Seen` vs `Sent` | Confirm `application_logging.forwarding.enabled` is `true` and check for a supported logging library |
| A feature flag change isn't taking effect | `Supportability/Nodejs/FeatureFlag/{flag}/enabled` or `disabled` | Confirm the flag name and value in your agent configuration, then restart the application |

### Creating alerts for supportability metrics

Monitor critical supportability metrics with [NRQL alert conditions](/docs/alerts/create-alert/create-alert-condition/create-nrql-alert-conditions/):

<CollapserGroup>
  <Collapser
    id="alert-data-loss"
    title="Alert on transaction event data loss"
  >
    **Alert condition**: Data loss detection

    ```sql
    SELECT
      (sum(`Supportability/AnalyticsEvents/TotalEventsSeen`) - sum(`Supportability/AnalyticsEvents/TotalEventsSent`)) / sum(`Supportability/AnalyticsEvents/TotalEventsSeen`) * 100
    FROM Metric
    WHERE metricName LIKE 'Supportability/AnalyticsEvents%'
    ```

    **Threshold**: Alert when data loss exceeds 10%
  </Collapser>

  <Collapser
    id="alert-infinite-tracing-errors"
    title="Alert on Infinite Tracing response errors"
  >
    **Alert condition**: Trace observer response errors

    ```sql
    SELECT sum(`Supportability/InfiniteTracing/Span/Response/Error`)
    FROM Metric
    WHERE metricName = 'Supportability/InfiniteTracing/Span/Response/Error'
    ```

    **Threshold**: Alert when errors exceed 5 in 5 minutes
  </Collapser>
</CollapserGroup>
