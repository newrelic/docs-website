Supportability metrics help you understand how your Python agent is performing and identify potential issues with your application monitoring. These metrics provide valuable insights into agent behavior, feature adoption, and configuration effectiveness.

<Callout variant="important">
  You're charged for supportability metric ingest as part of your New Relic data consumption. These metrics provide valuable troubleshooting and optimization information that can help you resolve issues faster and improve application performance.
</Callout>

## What are supportability metrics? [#what-are-supportability-metrics]

Supportability metrics are specialized metrics that the Python agent automatically collects about its own operation. They help you:

* **Troubleshoot monitoring issues**: Identify why certain data isn't appearing in your dashboards
* **Validate configuration**: Confirm that features like distributed tracing or Infinite Tracing are working correctly
* **Monitor agent performance**: Track resource usage and identify modules the agent couldn't instrument
* **Optimize feature usage**: Understand which agent API methods your application is using

All supportability metrics use the `Supportability/` prefix in their metric names, making them easy to identify and query with [NRQL](/docs/nrql/get-started/introduction-nrql-new-relics-query-language/).

## Distributed tracing metrics [#distributed-tracing-metrics]

These metrics help you troubleshoot distributed tracing configuration and connectivity issues between your services.

### New Relic payload metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/DistributedTrace/CreatePayload/Success` | Successfully created a tracing payload for an outbound request | Low values relative to outbound request volume may indicate configuration issues |
| `Supportability/DistributedTrace/CreatePayload/Exception` | Failed to create a tracing payload due to an error | Any non-zero values indicate problems |
| `Supportability/DistributedTrace/AcceptPayload/Success` | Successfully processed an incoming tracing payload | Should track with inbound traced request volume |
| `Supportability/DistributedTrace/AcceptPayload/Exception` | Failed to process an incoming tracing payload | Investigate non-zero values for configuration or version mismatches |
| `Supportability/DistributedTrace/AcceptPayload/ParseException` | A payload couldn't be parsed | Indicates malformed headers from an upstream service |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/Null` | A null payload was passed to the accept API | Check instrumentation or custom code calling the API |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/Multiple` | A payload was ignored because one was already accepted on this transaction | Expected in nested call scenarios; high volumes may indicate unexpected re-entrancy |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/CreateBeforeAccept` | A payload was ignored because one was already created on this transaction | Check for calls that create outbound trace headers before accepting inbound ones |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/MajorVersion` | A payload was ignored due to an unsupported major version | Indicates an incompatible upstream agent version |
| `Supportability/DistributedTrace/AcceptPayload/Ignored/UntrustedAccount` | A payload was ignored because it came from an untrusted account | Check your distributed tracing trust configuration |

### W3C TraceContext metrics

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/TraceContext/Create/Success` | Created W3C-compliant trace headers | Should match outbound request volume |
| `Supportability/TraceContext/Create/Exception` | Failed to create W3C trace headers | Any non-zero values indicate problems |
| `Supportability/TraceContext/Accept/Success` | Processed incoming W3C trace headers | Should match inbound traced request volume |
| `Supportability/TraceContext/TraceParent/Accept/Success` | Successfully decoded a `traceparent` header | Baseline for comparing against `TraceParent/Parse/Exception` |
| `Supportability/TraceContext/TraceParent/Parse/Exception` | Failed to parse a `traceparent` header | Check upstream services for malformed headers |
| `Supportability/TraceContext/TraceState/Parse/Exception` | Failed to parse a `tracestate` header | Check upstream services for malformed headers |
| `Supportability/TraceContext/TraceState/InvalidNrEntry` | The New Relic entry in `tracestate` was invalid | Check for version mismatches between agents |
| `Supportability/TraceContext/TraceState/NoNrEntry` | No New Relic entry was found in `tracestate` | Expected when the upstream service isn't a New Relic agent |

<Callout variant="tip">
  Compare `Create/Success` and `Accept/Success` counts with your actual request volume. A low ratio may indicate that not all services in your trace have distributed tracing enabled.
</Callout>

## Data harvest and event metrics [#event-harvest-metrics]

These metrics track how much data the agent collects versus how much is actually sent, which helps identify data loss due to reservoir limits.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/Python/RequestSampler/requests` | Total transaction events seen by the reservoir sampler | Compare with `RequestSampler/samples` to check for data loss |
| `Supportability/Python/RequestSampler/samples` | Total transaction events actually sampled and sent | Should be close to `RequestSampler/requests` |
| `Supportability/SpanEvent/TotalEventsSeen` | Total span events collected | Compare with `TotalEventsSent` to check for data loss |
| `Supportability/SpanEvent/TotalEventsSent` | Total span events transmitted | Should be close to `TotalEventsSeen` |
| `Supportability/Events/TransactionError/Seen` | Total error events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/TransactionError/Sent` | Total error events transmitted | Should be close to `Seen` |
| `Supportability/Events/Customer/Seen` | Total custom events collected | Compare with `Sent` to check for data loss |
| `Supportability/Events/Customer/Sent` | Total custom events transmitted | Should be close to `Seen` |

<CollapserGroup>
  <Collapser
    id="example-data-loss"
    title="Example: Detecting data loss"
  >
    If you see these values in your metrics:

    * `Supportability/Python/RequestSampler/requests`: 10,000
    * `Supportability/Python/RequestSampler/samples`: 2,000

    This indicates your agent collected 10,000 transaction events but only sampled and sent 2,000 to New Relic. The remaining 8,000 events were dropped due to reservoir size limits. Consider increasing your `transaction_events.max_samples_stored` configuration.
  </Collapser>
</CollapserGroup>

## Logging metrics [#logging-metrics]

These metrics report which [application logging](/docs/logs/logs-context/configure-logs-context-python/) features are enabled, and track log event harvest volume.

| Metric name | Description | What it means |
|-------------|-------------|---------------|
| `Supportability/Logging/Forwarding/Python/enabled` or `/disabled` | Whether log forwarding to New Relic is enabled | Confirms whether your application's logs are being sent to New Relic |
| `Supportability/Logging/LocalDecorating/Python/enabled` or `/disabled` | Whether local log decoration is enabled | Confirms whether linking metadata is being added to your local log output |
| `Supportability/Logging/Metrics/Python/enabled` or `/disabled` | Whether log-derived metrics are enabled | Confirms whether the agent generates metrics from your log volume |
| `Supportability/Logging/Labels/Python/enabled` or `/disabled` | Whether custom labels are attached to forwarded log events | Validates your log forwarding label configuration |
| `Supportability/Logging/Forwarding/Seen` | Total log events seen by the agent and eligible for forwarding | Compare with `Forwarding/Sent` to check for log data loss |
| `Supportability/Logging/Forwarding/Sent` | Total log events transmitted to New Relic | Should be close to `Forwarding/Seen` |

## Infinite Tracing metrics [#infinite-tracing-metrics]

If you use [Infinite Tracing](/docs/distributed-tracing/infinite-tracing/introduction-infinite-tracing/), these metrics help you monitor the gRPC connection used to stream spans.

| Metric name | Description | When to investigate |
|-------------|-------------|---------------------|
| `Supportability/InfiniteTracing/Span/Seen` | Spans seen by the agent and eligible for streaming | Baseline for comparing sent/error counts |
| `Supportability/InfiniteTracing/Span/Sent` | Spans successfully streamed to the trace observer | Should closely track `Span/Seen` |
| `Supportability/InfiniteTracing/Span/Response/Error` | The trace observer returned an error response | Non-zero values indicate issues with the trace observer connection |
| `Supportability/InfiniteTracing/Span/gRPC/{status code}` | The trace observer returned a specific gRPC status code | Non-`OK` status codes indicate connection or compatibility issues |
| `Supportability/InfiniteTracing/gRPC/Batching/enabled` or `/disabled` | Whether gRPC batching is enabled for Infinite Tracing | Validates your Infinite Tracing batching configuration |
| `Supportability/InfiniteTracing/gRPC/Compression/enabled` or `/disabled` | Whether gRPC compression is enabled for Infinite Tracing | Validates your Infinite Tracing compression configuration |

## Agent collector communication metrics [#collector-metrics]

These metrics monitor communication between your agent and New Relic's data collection service.

| Metric name | Description | What it means |
|-------------|-------------|---------------|
| `Supportability/Python/Collector/{endpoint method}/Output/Bytes` | Bytes sent to the collector for a given endpoint (for example, `metric_data`) | Monitor for data usage tracking |
| `Supportability/Python/Collector/Output/Bytes` | Total bytes sent to the collector across all endpoints | Baseline for overall data usage |
| `Supportability/Python/Collector/{endpoint method}/ZLIB/Bytes` | Uncompressed payload size before compression for a given endpoint | Compare with `ZLIB/Compress` to check compression ratio |
| `Supportability/Python/Collector/{endpoint method}/ZLIB/Compress` | Time spent compressing a payload for a given endpoint | High values can increase harvest latency on large payloads |
| `Supportability/Python/Collector/MaxPayloadSizeLimit/{method}` | A payload exceeded the maximum size limit and was dropped | Indicates data loss; consider reducing harvest limits for that data type |
| `Supportability/Python/Collector/Failures` | Total failed requests to the collector | Baseline for comparing against specific failure types |
| `Supportability/Python/Collector/Failures/{connection}` | Failed requests broken down by connection type (for example, `direct` or `proxy`) | Helps isolate whether failures are proxy-related |
| `Supportability/Python/Collector/HTTPError/{status code}` | An HTTP error was returned by the collector | Non-200-series values indicate connectivity, proxy, or authentication issues |
| `Supportability/Python/Collector/Exception/{exception class}` | A specific exception type (for example, a connection or timeout error) occurred while talking to the collector | Identifies the root cause behind collector `Failures` |
| `Supportability/Python/Certificate/BundleRequired` | The agent needed to supply its own CA certificate bundle | Indicates the host's system certificate store couldn't validate the connection |

## Instrumentation metrics [#instrumentation-metrics]

These metrics flag modules that your application loaded but that the agent couldn't instrument, often due to import order.

| Metric name | Description | What to monitor |
|-------------|-------------|-----------------|
| `Supportability/Python/Uninstrumented` | Total count of modules loaded without New Relic instrumentation | Baseline count across all uninstrumented modules |
| `Supportability/Uninstrumented/{module}` | A specific module (for example, `django.core.handlers.wsgi` or `aiohttp.client`) was loaded without instrumentation | Confirms whether a library you expect to be monitored is actually supported, and whether `newrelic-admin` or the agent import happened early enough |

| Metric name | Description | Use case |
|-------------|-------------|----------|
| `Supportability/utilization/aws/error` | Error gathering AWS utilization data | Non-zero values indicate the agent couldn't reach the AWS metadata endpoint |
| `Supportability/utilization/azure/error` | Error gathering Azure utilization data | Non-zero values indicate the agent couldn't reach the Azure metadata endpoint |
| `Supportability/utilization/gcp/error` | Error gathering GCP utilization data | Non-zero values indicate the agent couldn't reach the GCP metadata endpoint |

## Querying supportability metrics [#querying-metrics]

Use these NRQL queries to analyze your supportability metrics:

<CollapserGroup>
  <Collapser
    id="query-distributed-tracing"
    title="Monitor distributed tracing health"
  >
    ```sql
    SELECT
      sum(`Supportability/TraceContext/Create/Success`) AS 'Successful Outbound Traces',
      sum(`Supportability/TraceContext/Accept/Success`) AS 'Successful Inbound Traces'
    FROM Metric
    WHERE metricName LIKE 'Supportability/TraceContext%'
    SINCE 1 hour ago
    TIMESERIES
    ```
  </Collapser>

  <Collapser
    id="query-data-harvest"
    title="Check for transaction event data loss"
  >
    ```sql
    SELECT
      sum(`Supportability/Python/RequestSampler/requests`) AS 'Events Collected',
      sum(`Supportability/Python/RequestSampler/samples`) AS 'Events Sent'
    FROM Metric
    WHERE metricName LIKE 'Supportability/Python/RequestSampler%'
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-uninstrumented-modules"
    title="Find uninstrumented modules"
  >
    ```sql
    SELECT uniques(metricName)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Uninstrumented/%'
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-collector-errors"
    title="Check for collector connectivity issues"
  >
    ```sql
    SELECT count(*)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Python/Collector/HTTPError%'
    FACET metricName
    SINCE 1 day ago
    ```
  </Collapser>

  <Collapser
    id="query-logging-features"
    title="Check which logging features are enabled"
  >
    ```sql
    SELECT latest(metricName)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Logging/%/Python/%'
    FACET metricName
    SINCE 1 day ago
    ```
  </Collapser>
</CollapserGroup>

## Troubleshooting with supportability metrics [#troubleshooting]

| Problem | Metrics to check | Solution |
|---------|------------------|----------|
| Missing distributed traces | `Supportability/TraceContext/Create/Success` and `Accept/Success` | Verify distributed tracing is enabled on all services |
| Transaction events missing | Compare `Python/RequestSampler/requests` vs `samples` | Increase your transaction events reservoir size |
| A library isn't showing up in breakdowns | `Supportability/Uninstrumented/{module}` | Confirm `newrelic-admin run-program` or `import newrelic.agent` happens before the library is imported |
| Collector connectivity errors | `Supportability/Python/Collector/HTTPError/*`, `Failures`, `Collector/Exception/*` | Check network/proxy/firewall rules between the host and New Relic |
| TLS/connection errors to New Relic | `Supportability/Python/Certificate/BundleRequired` | Check the host's CA certificate bundle configuration |
| Infinite Tracing spans dropped | `Supportability/InfiniteTracing/Span/Response/Error`, `Span/gRPC/*` | Check connectivity to the configured trace observer |
| Logs not appearing in New Relic | `Supportability/Logging/Forwarding/Python/enabled`, `Logging/Forwarding/Seen` vs `Sent` | Confirm `application_logging.forwarding.enabled` is set and check for data loss between `Seen` and `Sent` |

### Creating alerts for supportability metrics

Monitor critical supportability metrics with [NRQL alert conditions](/docs/alerts/create-alert/create-alert-condition/create-nrql-alert-conditions/):

<CollapserGroup>
  <Collapser
    id="alert-data-loss"
    title="Alert on transaction event data loss"
  >
    **Alert condition**: Data loss detection

    ```sql
    SELECT
      (sum(`Supportability/Python/RequestSampler/requests`) - sum(`Supportability/Python/RequestSampler/samples`)) / sum(`Supportability/Python/RequestSampler/requests`) * 100
    FROM Metric
    WHERE metricName LIKE 'Supportability/Python/RequestSampler%'
    ```

    **Threshold**: Alert when data loss exceeds 10%
  </Collapser>

  <Collapser
    id="alert-collector-errors"
    title="Alert on collector connection problems"
  >
    **Alert condition**: Collector HTTP errors

    ```sql
    SELECT count(*)
    FROM Metric
    WHERE metricName LIKE 'Supportability/Python/Collector/HTTPError%'
    ```

    **Threshold**: Alert when errors exceed 5 in 5 minutes
  </Collapser>
</CollapserGroup>
