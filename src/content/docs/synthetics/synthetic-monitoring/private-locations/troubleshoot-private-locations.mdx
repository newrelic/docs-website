If you encounter problems while setting up [private locations](/docs/synthetics/new-relic-synthetics/private-locations/private-locations-overview-monitor-internal-sites-add-new-locations) for synthetic monitoring of New Relic, try these troubleshooting tips to identify common Synthetics Job Manager problems.

## Job demand and consumption [#job-demand]

Identify your current throughput and assess whether your job manager is able to keep up with the job load.

* Jobs demand throughput per minute:

  ```sql
  SELECT rate(uniqueCount(jobId), 1 minute) FROM SyntheticRequest 
  WHERE type != 'SIMPLE' FACET location SINCE 2 days ago
  ```
* Jobs per minute over time:

  ```sql
  SELECT rate(uniqueCount(jobId), 1 minute) FROM SyntheticRequest 
  WHERE type != 'SIMPLE' FACET location SINCE 2 weeks ago TIMESERIES
  ```
* Identify queue growth:

  ```sql
  SELECT derivative(checksPending, 1 minute) AS 'queue growth rate (per minute)' 
  FROM SyntheticsPrivateLocationStatus WHERE name = 'YOUR_PRIVATE_LOCATION' SINCE 2 days ago TIMESERIES
  ```
* Consumption rate:

  ```sql
  SELECT rate(uniqueCount(jobId), 1 minute) FROM SyntheticRequest 
  WHERE type != 'SIMPLE' FACET location SINCE 2 weeks ago TIMESERIES
  ```
* Clean up failing monitors that are consuming resources:

  ```sql
  SELECT 100*latest(minionJobsFailed)/latest(minionJobsReceived) AS 'job failure rate (%)' 
  FROM SyntheticsPrivateMinion FACET minionLocation SINCE 2 weeks ago TIMESERIES MAX
  ```

## Memory usage troubleshooting [#memory]

Recommended memory allocation per synthetics job manager:

* Docker: 3.256 GiB per cpu core for Docker synthetics job manager
* Kubernetes synthetics job manager (values are configurable):

  * 1.6 GiB for job manager pod
  * 1.0 GiB for ping runtime pod
  * 2 GiB per Node.js API runtime pod
  * 3 GiB per Node.js browser runtime pod
* Target 60% max memory utilization

Helpful queries to identify current usage:

* Memory usage per location:

  ```sql
  SELECT latest(minionPhysicalMemoryUsedPercentage) FROM SyntheticsPrivateMinion
  FACET minionLocation SINCE 2 weeks ago TIMESERIES MAX
  ```
* Memory usage per hostname:

  ```sql
  SELECT latest(minionPhysicalMemoryUsedPercentage) FROM SyntheticsPrivateMinion 
  WHERE minionLocation = 'YOUR_PRIVATE_LOCATION' FACET minionHostname SINCE 2 weeks ago TIMESERIES MAX
  ```

## Browser monitors crash due to shared memory sizing on Podman [#shm]

Browser monitors running on a Podman-based private location might fail intermittently with an error like this:

```log
NoSuchSessionError: invalid session id: session deleted as the browser has closed the connection, disconnected: Unable to receive message from renderer
```

This is typically a Chrome renderer process crash caused by insufficient shared memory (`/dev/shm`), not a scripting or network issue. Chrome relies heavily on shared memory for rendering and tends to exhaust it faster than Firefox, especially on pages that redirect across origins during login flows—each new origin spins up additional renderer processes that draw from the same `/dev/shm` pool.

### How Podman pods allocate shared memory

When synthetics job manager runs in Podman with `--pod`, every container joined to that pod shares a single IPC namespace. The pod itself mounts `/dev/shm` once, at the size you created the pod with (64 MiB by default). You set that size at `podman pod create` time, and an individual container can't change or override it afterward.

This means the following common attempts to fix shared memory issues **don't work** once a container has joined a pod, because the pod's `/dev/shm` mount takes precedence over per-container settings:

* Setting `-e MOUNT_DEV_SHM=true` on `podman run`
* Passing `--shm-size` on `podman run` instead of `podman pod create`
* Bind-mounting with `-v /dev/shm:/dev/shm` on `podman run`

This differs from standalone Docker containers, where a per-container `--shm-size` works because each Docker container gets its own private IPC namespace rather than sharing one with a pod.

### Diagnose

Before you change anything, run these checks to confirm the cause:

1. Check the pod's actual configured shared memory size:

   ```shell
   podman pod inspect YOUR_POD_NAME
   ```

   If you didn't fully remove a previous pod with the same name before you recreated it, or didn't restart a container in the pod afterward, you might still be running on the original 64 MiB pod without realizing it.
2. Check the shared memory actually available inside the browser runtime container, ideally captured during or immediately before a failing run:

   ```shell
   podman exec YOUR_BROWSER_RUNTIME_CONTAINER_ID df -h /dev/shm
   ```

   Compare the output to the size you configured:

   * If this still shows `64M`, the resize never took effect—recreate the pod as described in the next section.
   * If this shows your configured size (for example, `2.0G` for a pod created with `--shm-size=2g`) and monitors are still crashing, the resize did take effect, but that size is a shared pool across every container currently running in the pod, not a per-browser-instance allocation. If multiple monitors run concurrently on the same private location, they all draw from that pool. Increase `--shm-size` further, or reduce the number of monitors that run concurrently.

### Fix

Recreate the pod with a larger `--shm-size`, then restart synthetics job manager so it rejoins the new pod:

```shell
podman pod create --network slirp4netns --name YOUR_POD_NAME --add-host=podman.service:HOST_IP_ADDRESS --shm-size=2g
```

See the [Podman start procedure](/docs/synthetics/synthetic-monitoring/private-locations/install-job-manager/#podman-update) for the full pod creation and start steps.

## CPU usage troubleshooting [#cpu-usage]

Identify potential periods of high cpu demand:

* Overall CPU usage:

  ```sql
  SELECT latest(minionProcessorsUsagePercentage) FROM SyntheticsPrivateMinion 
  FACET minionLocation SINCE 2 weeks ago TIMESERIES MAX
  ```
* CPU usage for a specified location:

  ```sql
  SELECT latest(minionProcessorsUsagePercentage) FROM SyntheticsPrivateMinion 
  WHERE minionLocation = 'YOUR_PRIVATE_LOCATION' FACET minionHostname SINCE 2 weeks ago TIMESERIES MAX
  ```

## Network troubleshooting [#network]

<DNT>
  **Network access is red:**
</DNT>

The Synthetics Job Manager makes a check to New Relic to verify public network access. If public network access is not available, the <DNT>**Network Access**</DNT> icon on the [Synthetics Job Manager's <DNT>**Overview**</DNT> page](/docs/synthetics/new-relic-synthetics/pages/synthetics-overview-page-view-monitors-performance) will turn red, but the Synthetics Job Manager will otherwise be fully functional. If this is the expected behavior, you can safely ignore this error.

You may also see log entries like this:

```log
2016-01-21 21:47:09,401 [dw-22 - GET /private-location/status] c.n.s.m.util.PrivateMinionUtils WARN Unable to detect Public Network Access trying to fetch https://newrelic.com/synthetics: java.net.ConnectException: Connection refused
```

<DNT>
  **New Relic access is red:**
</DNT>

The Synthetics Job Manager must have access to `https://synthetics-horde.nr-data.net` in order to retrieve the list of jobs to run and publish results that you can view in your New Relic user interface. If your firewall rules don't permit direct access, you can [configure proxy access](/docs/synthetics/synthetic-monitoring/private-locations/job-manager-configuration/#environment-variables). If necessary, add the DNS endpoint `synthetics-horde.nr-data.net` to your allow list.

## Port conflicts running Docker containers on the host [#port-conflicts-docker]

If you're running multiple job manager containers on the same host, you'll have port conflicts and resource contention. To avoid this, make sure to run each job manager on a separate host.
