Scripted synthetic monitors are just JavaScript — so the most powerful thing you can do is bring your *own* code to them. On New Relic **private locations**, you can bundle any npm package or internal module into the runtime that executes your monitors and `require()` it straight from your scripts. There's no reinventing logic your applications already have, and no waiting on a vendor to add a library.

## Why this matters [#why]

Most synthetic tools lock your scripts to a fixed set of built-in libraries. New Relic private locations don't: the synthetics job manager installs the dependencies you provide and makes them available to every scripted API and scripted browser monitor it runs. Because private locations run inside your own infrastructure, those packages install from **your** registry and never leave your network.

The result: your monitors can act like first-class clients of your services, using the same SDKs, auth flows, and data formats your production code already uses.

## What you can do with it [#use-cases]

* **Reuse your internal SDKs and helpers.** Point a monitor at the same client library your app uses instead of re-implementing requests, retries, or pagination by hand.
* **Handle complex authentication.** Sign JWTs, build OAuth or HMAC signatures, or generate one-time tokens with proven libraries — so you can monitor endpoints that a simple username and password can't reach.
* **Work with proprietary or binary formats.** Encode and decode protobuf, Avro, MessagePack, or your own wire format to exercise internal APIs end to end.
* **Write richer checks and realistic test data.** Bring assertion libraries, data generators, or date and time helpers to make monitors both stricter and easier to maintain.
* **Standardize across your team.** Ship one shared module and reuse it across many monitors, so a single change to your auth or client logic updates every monitor at once.

## How it works [#how-it-works]

You don't just script against the runtime — you shape it:

1. Create a directory with a `package.json` that lists your dependencies (public npm packages, private-registry packages, or local modules in the same tree).
2. Mount that directory into the synthetics job manager. On startup it runs `npm install` and makes the modules available to the runtimes it spawns.
3. In a scripted monitor, `require()` your module like any other Node.js code.

```javascript
// Scripted API monitor: sign a request with your own library, then assert on the response
const jwt = require('jsonwebtoken');

const token = jwt.sign({ svc: 'synthetics' }, $secure.SIGNING_KEY, { expiresIn: '5m' });

$http.get(
  {
    url: 'https://internal.api.example.com/health',
    headers: { Authorization: `Bearer ${token}` },
  },
  function (err, response, body) {
    assert.equal(response.statusCode, 200, 'Health endpoint should return 200');
  }
);
```

For the exact mount paths, Helm values, and container setup, see [Custom node modules](/docs/synthetics/synthetic-monitoring/private-locations/job-manager-configuration/#custom-modules) and [Import Node.js modules](/docs/synthetics/synthetic-monitoring/scripting-monitors/import-nodejs-modules/).

<Callout variant="tip">
  Keep secrets out of your code and modules. Store credentials as [secure credentials](/docs/synthetics/synthetic-monitoring/using-monitors/store-secure-credentials-scripted-browsers-api-tests/) and reference them with `$secure`, as in the example above.
</Callout>

## Monitor your Gen AI applications [#genai]

Gen AI features fail in ways traditional uptime checks miss: a model provider slows down or throttles you, a new model version quietly changes output quality, a retrieval index goes stale, or a safety guardrail regresses after a prompt change. Because scripted monitors run real requests on a schedule — and, with custom modules, can call your models using the same SDKs your applications use — they give enterprises a proactive, outside-in signal on the AI stack before customers feel a problem. On **private locations**, you can do this for internal or self-hosted models **without exposing them outside your network**.

Representative use cases:

* **Model and gateway availability and latency canaries.** Call your LLM endpoint or internal model gateway with a fixed "golden" prompt and assert on status, latency, and that a usable response returned. Surfaces provider outages, rate-limit throttling (HTTP 429), and regional latency regressions before users hit them. *Enabled by* the provider SDK (for example `openai`, `@anthropic-ai/sdk`, or `@aws-sdk/client-bedrock-runtime`) or your own gateway client.
* **Structured-output and quality-regression checks.** For JSON-mode or function-calling features, send a known prompt and validate the response against a schema — valid JSON, required fields, allowed values — plus expected content and length. Catches silent breakage when a model version, prompt template, or parameter changes. *Enabled by* a schema validator such as `ajv`, `chai` assertions, and a tokenizer such as `gpt-tokenizer` for token-budget checks.
* **RAG grounding and retrieval validation.** Ask a question whose correct answer depends on a specific source document, then assert the answer contains the grounded fact and the expected citations. Detects broken retrieval, stale or unindexed content, and vector-store issues that make answers confidently wrong. *Enabled by* your RAG or gateway client, with an optional similarity helper for fuzzy matching.
* **Guardrail and safety regression testing.** Replay a curated set of adversarial inputs — prompt-injection attempts and requests for restricted or PII content — and assert that the guardrail refuses or that the output is properly redacted. This turns your safety requirements into continuously verified tests, so a prompt or policy change can't silently weaken them. *Enabled by* custom assertion helpers and your policy or guardrail client.
* **End-to-end experience and agent-workflow validation.** Use a scripted browser monitor to drive the real copilot or chat UI — submit a prompt, wait for the completed response, and assert on what's rendered — validating the whole path: frontend, gateway, model, and tools. For agents, a scripted API monitor can exercise a multi-step tool-calling flow and assert each step. Catches integration breakage that no single-component check would.

<Callout variant="tip">
  Synthetic monitors are proactive **canaries**: they exercise a curated set of prompts and journeys on a schedule, so they catch regressions early — they complement, rather than replace, [New Relic AI monitoring](/docs/ai-monitoring/intro-to-ai-monitoring/), which observes your real production AI traffic. Keep test cases deterministic where you can, store API keys as [secure credentials](/docs/synthetics/synthetic-monitoring/using-monitors/store-secure-credentials-scripted-browsers-api-tests/), and allow for slow generations within the monitor's check timeout (up to 15 minutes).
</Callout>

## What you need [#requirements]

* **Private locations.** Custom modules run on the synthetics job manager, so this applies to monitors assigned to a private location (not public locations).
* **Scripted monitors.** Available to scripted API and scripted browser monitors — ping monitors don't run scripts.
* **A place to install.** The job manager needs persistent storage for the module directory and runs `npm install` at startup, so restart it to pick up dependency changes.
* **Ownership of your dependencies.** You control the packages, so pin versions and keep them patched, just as you would for application code.
