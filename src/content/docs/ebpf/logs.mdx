The New Relic eBPF agent can now collect your application logs and automatically correlate them with the same APM service entities it already discovers, so when you open a service in New Relic, its logs, metrics, and traces show up together with no extra setup. This turns the eBPF agent into a complete MELT (metrics, events, logs, and traces) engine, removing the need to deploy and maintain a separate log forwarder alongside it.

## Why use eBPF logs [#why-ebpf-logs]

Instead of "tailing" log files like a traditional forwarder, eBPF logs uses kernel-level visibility to capture log data directly from write-related system calls. This gives you:

* **Logs-in-Context by default**: Links captured logs to the correct APM service entity using the eBPF agent's existing entity-synthesis rules, with no customer configuration required.
* **One fewer agent to manage**: Eliminates the resource contention, correlation gaps, and maintenance overhead of running a dedicated log forwarder (such as Fluent Bit) next to the eBPF agent.
* **A smaller attack surface**: Removes the plugin-based logging middleware that a separate forwarder depends on, along with the CVE exposure that comes with it.

## Set up eBPF logs [#setup]

<Callout variant="important" title="Important">

eBPF logs is available as a self-service Public Preview. All logs ingested through eBPF logs are billable according to your applicable order.

Data obfuscation and dropping for sensitive information is only available through the [Pipeline Control Gateway (PCG)](/docs/new-relic-control/pipeline-control/overview) using OpenTelemetry Transformation Language (OTTL). The direct eBPF-to-New Relic data flow doesn't include built-in obfuscation. Contact your account representative to add PCG to your Order. If your logs may contain sensitive data, configure PCG routing to redact it before ingestion.

</Callout>

Turn on eBPF logs by completing these steps:

1. Update your eBPF agent to version 1.4.4 or later, which New Relic recommends for log reporting.
    * For Kubernetes, refer to [Upgrade the eBPF agent](/docs/ebpf/k8s-installation/#upgrade).
    * For Linux hosts, refer to [Upgrade the eBPF agent](/docs/ebpf/linux-installation/#upgrade).
2. Set the following parameters:
    * `reportLogs`: set to `"auto"` or `"true"` to turn on log collection (see [Automatic detection and backoff](#automatic-backoff) below for what each value does).
    * `logDataFilters.applicationLogReporting.enabled`: confirm this is `true` (its default value), or set it explicitly if you've customized your configuration.

    For the full list of log-related parameters, refer to the Configuration parameters section of the [Linux installation](/docs/ebpf/linux-installation/#config-params) or [Kubernetes installation](/docs/ebpf/k8s-installation/#config-params) guide.
3. Restart the eBPF agent.

## Automatic detection and backoff [#automatic-backoff]

To avoid sending duplicate telemetry, the eBPF agent can automatically detect whether another agent is already reporting logs for an entity and back off accordingly. This is the same pattern it already uses for APM data and network metrics.

The `reportLogs` parameter accepts:

* `"auto"`: the eBPF agent collects and reports logs for an entity only when neither a New Relic APM agent nor an OpenTelemetry agent is attached to it. If the agent detects either, it suppresses its own log collection for that entity to avoid duplication.
* `"true"`: the eBPF agent always collects and reports logs, regardless of other agents present.
* `"false"` (default): the eBPF agent never collects or reports logs.

This mirrors how `reportApmData` and `reportNetworkMetrics` behave for eBPF APM and network metrics. For the equivalent pattern applied to network metrics, refer to [Enable network metrics-only mode](/docs/ebpf/network-metrics/#network-only-mode).

## Use cases [#use-cases]

eBPF logs can help with the following objectives:

* **Unified troubleshooting with Logs-in-Context**: Access complete MELT telemetry from a single collection and correlation point, with logs automatically linked to the APM entities they belong to.
* **Fewer agents to manage**: Move from managing multiple agent lifecycles to just one.
* **Security hardening**: Consolidate telemetry collection into a single, kernel-level agent to help minimize attack surface and reduce dependencies on third-party log forwarding plugins.

This approach is particularly valuable for organizations managing containerized applications, microservices architectures, or environments where operational simplicity is a priority.

## View your eBPF logs data [#view-data]

You can view eBPF logs in the New Relic UI:

1. Go to **[one.newrelic.com](https://one.newrelic.com) > APM & Services**.
2. Select the entity whose logs you want to view.
3. Click the **Logs** tab.

<Callout variant="tip">

The eBPF agent automatically generates entity names based on your environment:

* **In hosts or Docker**: names combine process name, directory path or container ID, and listening port. For example, `ruby:/home/ubuntu/app:[5678]` or `java:f4aead533895:[8080]`.
* **In Kubernetes**: names are derived from the service name, for example `mysql-database-service`.

</Callout>

eBPF logs currently captures **application logs only**. This capability doesn't collect infrastructure logs.
