New Relic <DNT>Autopilot</DNT> compute limits provides a level of budget governance to help better manage enterprise budgets. High-frequency observability events—such as incident alert storms or cascading condition failures—can trigger bursts of investigation prompts or analyses that can drive up costs for Large Language Model (LLM) compute resources, potentially leading to invoice surprises. New Relic <DNT>Autopilot</DNT> compute limits helps to provide proactive, policy-based budgeting that allows you to implement certain operational boundaries for costs surrounding <DNT>Autopilot</DNT> runs.

Enterprise compute allocations are configured by Organization Managers and Billing Admins as daily and monthly budgets denominated in Advanced Compute Capacity Units (aCCUs). These roles can now create sub-budgets for System Identity (SI) workflows pertaining to New Relic <DNT>Autopilot</DNT>. Background alert investigations also contain their own dedicated allocation. Setting budgets for these actions help you better manage compute quota used during active incident investigations using <DNT>Autopilot</DNT>.

## User roles and governance capabilities [#permissions]

Access control for <DNT>Autopilot</DNT> compute limits follows New Relic's Role-Based Access Control (RBAC) framework. The matrix below defines administrative authorities compared to read-only operational capabilities across platform workflows:

| Capability | Underlying RBAC capability (batches.yaml) | Organization managers | Read-only users / engineers |
| --- | --- | --- | --- |
| Manage compute budget policies (create, edit, or delete global and sub-budgets) | `sre_agent.manage.compute_limits` | ✅ | ❌ |
| View real-time quota and budget pills | `sre_agent.read.compute_limits` | ✅ | ✅ |
| Inspect audit logs (`NrAuditEvent`) | None (governed by reporting account access) | Reporting account access required | Reporting account access required |

The following section details the administrative workflows and procedures required to configure compute limits within the New Relic platform.

## Configure compute budgets (admin workflow) [#configure]

[Compute budgets](/docs/accounts/accounts-billing/new-relic-one-pricing-billing/compute-budgets/overview/) allow managers to help enforce financial policies or budget policies with configurable, in-UI constraints. Using the New Relic user interface, administrators establish organizational limits that dynamically enforce desired limits on system execution across interactive sessions and background automation.

### UI navigation and configurable parameters [#parameters]

To configure compute budgets, navigate to **<DNT>Autopilot</DNT> Configuration Modal / Onboarding Panel > Compute Limits & Budgeting**.

Administrators can define four core parameters within the configuration interface:

* **Total Daily <DNT>Autopilot</DNT> Cap (aCCUs/day)**: Sets the enterprise-wide expenditure ceiling for all combined interactive user sessions and automated workflows per calendar day (evaluated in the organization's timezone).
* **Automated and Async Daily Sub-Cap (aCCUs/day)**: Allocates a dedicated daily sub-quota strictly for System Identity (SI) workflows, such as alert webhooks and workflow notifications.
* **Total Monthly <DNT>Autopilot</DNT> Cap (aCCUs/month)**: Establishes the macro-level monthly compute budget ceiling across all <DNT>Autopilot</DNT> executions.
* **Automated and Async Monthly Sub-Cap (aCCUs/month)**: Defines a dedicated monthly sub-allocation exclusively reserved for autonomous background investigations.

### Parameter validation rules and backend conversion mechanics [#validation]

The platform UI enforces input validation rules at the configuration entry gate to prevent invalid or conflicting policy states:

* **Rule 1 (Sub-Cap hierarchy)**: Automated sub-caps must be strictly less than their corresponding total cap (`Automated Sub-Cap < Total Cap`).
* **Rule 2 (Temporal multiplier)**: When both daily and monthly caps are configured, the monthly cap must not exceed 30 times the daily cap (`Monthly Cap <= 30 * Daily Cap`).
* **Policy flexibility**: All limit parameters are optional. Organizations can configure partial policies (such as enforcing a daily total cap without a monthly cap) based on specific operational needs.

Admins set budget limits using a single metric (aCCUs), creating an exact, non-negotiable spend limit that automatically blocks an AI from running up huge unexpected bills when doing fast, complex tasks.

### Audit change log specification [#audit-log]

Every configuration change is tracked in `NrAuditEvent` as follows:

| Field name | Data type | Description | Strategic value |
| --- | --- | --- | --- |
| Timestamp | ISO 8601 UTC | Exact time of configuration mutation | Establishes chronological baseline for billing |
| Admin ID | String (userId) | Identity of modifying manager | Ensures administrative accountability |
| Cap Delta | String | Prior value vs. updated value (old cap -> new cap) | Quantifies threshold shifts |
| Change Reason | Text string | Mandatory text field entered during UI save | Resolves intra-organization billing disputes |

Once administrative policies are saved and validated, the platform dynamically evaluates budget thresholds to enforce deterministic execution states for all users.

## User experience and budget thresholds [#thresholds]

<DNT>Autopilot</DNT> operates deterministically: requests execute with full multi-step model reasoning or are blocked at entry once caps are reached.

### State machine and execution behaviors [#state-machine]

The system evaluates compute consumption across three operational tiers based on total spend against the configured budget:

<Callout variant="note" title="Nominal state (0% – 75% budget consumption)">
  * **Execution profile**: Unrestricted AI execution with full multi-step model reasoning and complete RAG knowledge base retrieval (`query_knowledge_base`).
  * **UI visibility**: A non-intrusive, read-only status pill is displayed in the context bar of the chat interface, indicating normal operational state.
</Callout>

<Callout variant="important" title="Warning state (75% – 100% budget consumption)">
  * **Execution profile**: Full reasoning capabilities and standard multi-step executions continue without model degradation or performance changes.
  * **UI visibility**: A contextual warning banner is appended to system responses, informing users that the organization is approaching its daily or monthly compute ceiling.
</Callout>

<Callout variant="caution" title="Hard stop state (100% budget consumption exhausted)">
  * **Execution profile**: Immediate execution block enforced at the orchestration entry gate (`api/orchestration.py`). No downstream LLM calls or subagent tasks are initiated.
  * **UI visibility**: A prominent inline error card replaces the prompt input, instructing users to contact their Billing Admin or wait for the daily quota reset.
</Callout>

### UI error card display format [#error-card]

When an organization reaches 100% of its compute allocation, interactive chat sessions present the following standard error card:

> ⚠️ **<DNT>Autopilot</DNT> Daily Compute Limit Reached**
>
> Your organization has consumed 100% of its daily allocated compute budget (aCCU Limit Exceeded). Interactive reasoning and automated investigations are temporarily paused.
>
> **Next steps**: Contact your New Relic Organization Manager to increase your budget, or retry after the midnight reset (00:00 UTC).

While interactive user sessions provide visual indicators and immediate error card feedback, automated background operations require dedicated processing lifecycles.

### Real-time metric fetch failure and unavailable state [#unavailable]

When the platform UI is unable to fetch real-time usage metrics from the backend telemetry cache, the system transitions to a non-blocking degraded visual state. Backend budget enforcement remains continuously active regardless of UI data availability.

* **Status pill badge text**: Displays `Daily Usage: Unavailable ⚠` in the context bar.
* **Contextual tooltip**: On hover over the unavailable pill, displays: "Unable to fetch real-time usage metrics. Your backend budget enforcement remains active. [Retry]"

<Callout variant="important" title="Usage data temporarily unavailable">
  If an administrator opens the <DNT>Autopilot</DNT> Configuration Modal while usage data is unreachable, an inline top-level alert banner appears at the head of the modal container: "We couldn't load your current usage metrics. Any previously configured limits are still being enforced in the backend. Please try refreshing."
</Callout>

## Automated alert triage and async System Identity (SI) workflows [#si-workflows]

Automated incident triage relies on System Identity (SI) workflows that process incoming alerts asynchronously. During major system outages, alert storms ("thunderstorms") can fire dozens of concurrent webhooks simultaneously. Dedicated SI sub-caps insulate the background intake engine, ensuring automated alert bursts do not impact interactive human investigation budgets.

### System Identity execution lifecycle [#si-lifecycle]

When an automated trigger occurs (for example, `alert_webhook` or `workflow_notification`), the execution path varies based on current sub-cap consumption:

| Sub-Cap state | Webhook intake handling | New Relic issue page experience | Fallback mechanism |
| --- | --- | --- | --- |
| Nominal (&lt;100% SI quota) | HTTP 200 Accepted; automated AI investigation runs asynchronously. | Issue page chat panel is pre-filled with complete automated root-cause analysis. | N/A (standard execution) |
| Hard stop (100% SI quota exhausted) | HTTP 429 Rejected with error code `ADVANCED_DAILY_SI_LIMIT_EXCEEDED`. | Issue page loads normally; pre-filled chat panel is suppressed and replaced with an inline error card. | Manual fallback button enabled: user can manually trigger investigation if interactive budget remains. |

### Error message and response payload [#payload]

When an automated caller triggers an execution after the SI sub-cap is exhausted, the orchestration API sheds the request with an HTTP 429 status code and a structured JSON rejection payload. The response header explicitly includes `Retry-After: 14400` (4 hours), which upstream dispatchers and automated workflow orchestrators (such as New Relic Workflows) must respect by executing exponential backoff rather than immediate retries.

```json
{
  "error": {
    "code": "ADVANCED_DAILY_SI_LIMIT_EXCEEDED",
    "message": "Automated and asynchronous Autopilot compute daily sub-cap reached for organization.",
    "status": 429,
    "retry_after_seconds": 14400
  }
}
```

Managing asynchronous automated bursts effectively requires underlying system safeguards and real-time concurrency controls.

## Edge scenarios, concurrency caps, and safeguards [#safeguards]

Daily and monthly token caps evaluate total cumulative spend, but they cannot prevent sudden event bursts where hundreds of incoming webhooks fire concurrently before token usage can be processed and written to telemetry storage. To handle these edge scenarios, the platform employs defense-in-depth safeguards at the entry gate.

### Alert storm mitigation architecture [#alert-storm]

To maintain platform stability and protect organization budgets during sudden alert spikes, two concurrent protection mechanisms operate at the entry gate:

* **Per-org automated concurrency cap**: Imposes a strict ceiling of maximum 10 simultaneous active automated runs per organization. Requests arriving while 10 automated runs are in-flight are shed immediately with HTTP 429 backpressure and standard `Retry-After` response headers, preventing unmonitored execution queues.
* **Atomic Valkey reservations**: Prior to spawning an asynchronous execution task (`asyncio.create_task`), the entry gate atomically increments high-speed Valkey counters by a conservative estimated token cost—specifically 50,000 tokens for automated runs and 200,000 tokens for interactive human sessions. Upon run completion, the orchestration engine reconciles the reservation against actual consumed token spend. If an initial reservation causes the organization's counter to exceed its configured limit, the transaction rolls back, and the request is rejected immediately.

### High availability and disaster recovery: Valkey outage fallback policy [#valkey-fallback]

During local cache or Valkey infrastructure outages, the orchestration engine applies a tiered operational fallback policy:

<Callout variant="caution" title="Infrastructure outage operational mode">
  * **Automated / SI workflows (fail-closed)**: All automated trigger requests are blocked (HTTP 429) during cache dark periods to prevent unmonitored spend spikes.
  * **Interactive user workflows (fail-open)**: Human interactive chat sessions remain available to preserve engineer operational capabilities during active incident response.
</Callout>

Beyond backend concurrency safeguards, complete administrative operational control relies on continuous telemetry and analytics driven by NRQL.

## Track usage and telemetry with NRQL [#nrql]

All compute limit evaluations, budget transitions, and rejection events emit real-time telemetry to the New Relic Telemetry Data Platform (NRDB). System administrators and engineers can query these events to monitor resource consumption and audit access patterns.

### The SreComputeLimitEvent schema [#schema]

Compute limit evaluation events are emitted to NRDB under the `SreComputeLimitEvent` custom event type. Key schema attributes include:

* `organizationId`: The target New Relic organization account ID.
* `userId`: The specific user ID (populated for interactive requests; NULL for System Identity runs).
* `principalType`: The category of caller (`USER` vs. `SYSTEM_IDENTITY`).
* `limitName`: The policy evaluated (for example, `Autopilot Feature Daily Token Limit`).
* `currentValue`: Cumulative token or compute count at evaluation time.
* `limitValue`: Configured budget ceiling.
* `verdict`: The outcome of the policy evaluation (`PASS`, `WARN`, `REJECT`, or `CONCURRENCY_LIMIT_EXCEEDED`).

<Callout variant="note" title="Granular troubleshooting">
  While `SreComputeLimitEvent` records rolled-up policy evaluation decisions and gating verdicts, individual LLM calls and step executions continue to write granular telemetry to `SreAgentTokens` tagged with `run_id` and `agent_id` for deep, call-level troubleshooting.
</Callout>

### Standard analytical queries [#queries]

Administrators can run the following NRQL queries in the New Relic query builder to analyze consumption.

**Daily consumption trend vs. configured cap**

```sql
SELECT sum(currentValue) AS 'Total Tokens Consumed', max(limitValue) AS 'Daily Cap'
FROM SreComputeLimitEvent
WHERE limitName = 'Autopilot Feature Daily Token Limit'
TIMESERIES 1 hour SINCE 1 day AGO
```

**Rejection audit for automated SI workflows**

```sql
SELECT count(*)
FROM SreComputeLimitEvent
WHERE principalType = 'SYSTEM_IDENTITY' AND verdict = 'REJECT'
FACET organizationId, limitName
SINCE 7 days AGO
```

**Top interactive users by compute volume**

```sql
SELECT sum(currentValue) AS 'Token Consumption'
FROM SreComputeLimitEvent
WHERE principalType = 'USER'
FACET userId
SINCE 30 days AGO
```

**Concurrency cap rejection events**

```sql
SELECT count(*)
FROM SreComputeLimitEvent
WHERE verdict = 'CONCURRENCY_LIMIT_EXCEEDED'
FACET organizationId
TIMESERIES SINCE 24 hours AGO
```

To complement real-time analytics, understanding the architectural relationship between enforcement mechanisms and billing reporting is critical for long-term governance.

## Billing reconciliation, data lag, and disclaimers [#billing]

Distributed system architectures maintain a structural separation between real-time entry gating and asynchronous billing metrics processing.

### Counter architecture and pipeline skew reconciliation [#counters]

The platform uses a dual-store model to balance low-latency enforcement with accounting accuracy:

* **Real-time enforcement layer**: Sub-millisecond Valkey token counters evaluate entry gates to block over-budget runs instantly.
* **Billing and reporting pipeline**: Historical NRDB metric pipelines (`resourceConsumption`) aggregate data asynchronously, with an expected 2-hour processing lag.
* **Margin of error absorption**: Due to high-frequency execution concurrency, minor counter skew may create a temporary overshoot variance of 5% to 10%. New Relic absorbs all overshoot costs internally; customer accounts are never billed for token usage that exceeds their explicitly configured hard cap.

### Important callouts and limitations [#limitations]

<Callout variant="important" title="Admin UI configuration">
  Budget limits configured in the <DNT>Autopilot</DNT> Admin Portal represent target thresholds. While real-time enforcement gates halt execution immediately upon limit detection, processing delays in telemetry rollups may result in minor consumption variances.
</Callout>

<Callout variant="important" title="Real-time user interface notice">
  Compute limit status indicators ("budget pills") reflect near-real-time Valkey counter state. If your organization reaches its daily or monthly cap, active chat sessions will terminate further execution immediately without loss of historical chat data.
</Callout>

<Callout variant="note" title="Monthly billing statement reconciliation">
  Official invoice line items for Advanced Compute Units (aCCUs) are derived exclusively from processed NRDB billing pipeline metrics. In the event of any discrepancy between real-time UI counters and monthly billing statements, the final audited NRDB pipeline metric governs, capped at your explicitly configured policy limit.
</Callout>
