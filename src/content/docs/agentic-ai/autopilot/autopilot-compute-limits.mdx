New Relic <DNT>Autopilot</DNT> compute limits provides a level of budget governance to help better manage enterprise budgets. High-frequency observability events—such as incident alert storms or cascading condition failures—can trigger bursts of investigation prompts or analyses that can drive up costs for Large Language Model (LLM) compute resources, potentially leading to invoice surprises. New Relic <DNT>Autopilot</DNT> Compute Limits helps to provide proactive, policy-based budgeting that allows you to implement certain operational boundaries for costs surrounding <DNT>Autopilot</DNT> runs.

Enterprise compute allocations are configured by Organization Managers and Billing Admins as daily and monthly budgets denominated in aCCUs (advanced Compute Units).  These roles can now create sub-budgets for System Identity (SI) workflows pertaining to New Relic Autopilot. Background alert investigations also contain their own dedicated allocation. Setting budgets for these actions help you better manage compute quota used during active incident investigations using Autopilot.

With compute limits, you can:

* Set daily and monthly budgets for all <DNT>Autopilot</DNT> activity.
* Reserve a separate sub-budget for automated work such as alert triage and workflow notifications.
* Track consumption and rejected requests with NRQL.

### UI navigation and configurable parameters [#parameters]

To configure compute budgets, navigate to <DNT>Autopilot</DNT> Configuration Modal / Onboarding Panel > 'Compute Limits & Budgeting'.

Administrators can define four core parameters within the configuration interface:

* **Total Daily <DNT>Autopilot</DNT> Budget (aCCUs/day)**: Sets the enterprise-wide expenditure ceiling for all combined interactive user sessions and automated workflows per calendar day (evaluated in the organization's timezone).
* **Automated & Async Daily Sub-Budget (aCCUs/day)**: Allocates a dedicated daily sub-quota strictly for System Identity (SI) workflows, such as alert webhooks and workflow notifications.
* **Total Monthly <DNT>Autopilot</DNT> Budget (aCCUs/month)**: Establishes the macro-level monthly compute budget ceiling across all <DNT>Autopilot</DNT> executions.
* **Automated & Async Monthly Sub-Budget (aCCUs/month)**: Defines a dedicated monthly sub-allocation exclusively reserved for autonomous background investigations.

### Parameter validation rules and backend conversion mechanics [#validation]

The platform UI enforces input validation rules at the configuration entry gate to prevent invalid or conflicting policy states:

* **Rule 1 (Sub-Budget Hierarchy)**: Automated Sub-Caps must be strictly less than their corresponding Total Budget (`Automated Sub-Budget < Total Cap`).
* **Rule 2 (Temporal Multiplier)**: When both Daily and Monthly budgets are configured, the Monthly Budget must not exceed 30 times the Daily Budget (`Monthly Budget <= 30 * Daily Cap`).
* **Policy Flexibility**: All limit parameters are optional. Organizations can configure partial policies (such as enforcing a Daily Total Budget without a Monthly Cap) based on specific operational needs.

While administrators configure budgets in aCCUs, the underlying orchestration layer translates consumption into token units at execution using a conversion ratio of 1 aCCU = 20,000 LLM tokens. In the current MVP baseline, the token calculation aggregates raw unweighted input tokens, output tokens, and cache read tokens (`input_tokens + output_tokens + cache_read_tokens`). Although provider-level cache reads are often discounted in post-processed billing models, aggregating raw unweighted tokens at the entry gate establishes a simple, deterministic spend ceiling that prevents unexpected overruns during rapid reasoning chains.

## User experience and budget thresholds [#thresholds]

<DNT>Autopilot</DNT> operates deterministically: requests execute with full multi-step model reasoning or are blocked at entry once caps are reached.

### State machine and execution behaviors [#states]

The system evaluates compute consumption across three operational tiers based on total spend against the configured budget:

<Callout variant="tip" title="Nominal state (0% – 75% budget consumption)">
  * **Execution profile**: Unrestricted AI execution with full multi-step model reasoning and complete RAG knowledge base retrieval (`query_knowledge_base`).
  * **UI visibility**: A non-intrusive, read-only status pill is displayed in the context bar of the chat interface, indicating normal operational state.
</Callout>

<Callout variant="caution" title="Warning state (75% – 100% budget consumption)">
  * **Execution profile**: Full reasoning capabilities and standard multi-step executions continue without model degradation or performance changes.
  * **UI visibility**: A contextual warning banner is appended to system responses, informing users that the organization is approaching its daily or monthly compute ceiling.
</Callout>

<Callout variant="important" title="Hard stop state (100% budget consumption exhausted)">
  * **Execution profile**: Immediate execution block enforced at the orchestration entry gate (`api/orchestration.py`). No downstream LLM calls or subagent tasks are initiated.
  * **UI visibility**: A prominent inline error card replaces the prompt input, instructing users to contact their Billing Admin or wait for the daily quota reset.
</Callout>

{/* If a limit is crossed while a request is already running, <DNT>Autopilot</DNT> finishes the current step, skips the remaining steps, and returns a best-effort answer from the information it has already collected. */}

## Automated alert triage and async System Identity (SI) workflows [#alert-triage]

Automated incident triage relies on System Identity (SI) workflows that process incoming alerts asynchronously. During major system outages, alert storms ("thunderstorms") can fire dozens of concurrent webhooks simultaneously. Dedicated SI sub-caps insulate the background intake engine, ensuring automated alert bursts do not impact interactive human investigation budgets.

### System Identity Execution Lifecycle

When an automated trigger occurs (e.g., `alert_webhook` or `workflow_notification`), the execution path varies based on current sub-budget consumption:

| Sub-Budget State | Webhook Intake Handling | New Relic Issue Page Experience | Fallback Mechanism |
| --- | --- | --- | --- |
| Nominal (under 100% SI Quota) | HTTP 200 Accepted; automated AI investigation runs asynchronously. | Issue page chat panel is pre-filled with complete automated root-cause analysis. | N/A (Standard Execution) |
| Hard Stop (100% SI Quota Exhausted) | HTTP 429 Rejected with error code ADVANCED_DAILY_SI_LIMIT_EXCEEDED. | Issue page loads normally; pre-filled chat panel is suppressed and replaced with an inline error card. | Manual fallback button enabled: user can manually trigger investigation if interactive budget remains. |

### Error Message & Response Payload Callout

When an automated caller triggers an execution after the SI sub-budget is exhausted, the orchestration API sheds the request with an HTTP 429 status code and a structured JSON rejection payload. The response header explicitly includes `Retry-After: 14400` (4 hours), which upstream dispatchers and automated workflow orchestrators (such as New Relic Workflows) must respect by executing exponential backoff rather than immediate retries.

```json
{
  "error": {
    "code": "ADVANCED_DAILY_SI_LIMIT_EXCEEDED",
    "message": "Automated and asynchronous Autopilot compute daily sub-budget reached for organization.",
    "status": 429,
    "retry_after_seconds": 14400
  }
}
```

Managing asynchronous automated bursts effectively requires underlying system safeguards and real-time concurrency controls.

## Edge Scenarios, Concurrency Caps & Safeguards [#edge-cases]

Daily and monthly token caps evaluate total cumulative spend, but they cannot prevent sudden event bursts where hundreds of incoming webhooks fire concurrently before token usage can be processed and written to telemetry storage. To handle these edge scenarios, the platform employs defense-in-depth safeguards at the entry gate.

### Alert Storm Mitigation Architecture

To maintain platform stability and protect organization budgets during sudden alert spikes, two concurrent protection mechanisms operate at the entry gate:

* **Per-Org Automated Concurrency Cap**: Imposes a strict ceiling of maximum 10 simultaneous active automated runs per organization. Requests arriving while 10 automated runs are in-flight are shed immediately with HTTP 429 backpressure and standard `Retry-After` response headers, preventing unmonitored execution queues.
* **Atomic Valkey Reservations**: Prior to spawning an asynchronous execution task (`asyncio.create_task`), the entry gate atomically increments high-speed Valkey counters by a conservative estimated token cost—specifically 50,000 tokens for automated runs and 200,000 tokens for interactive human sessions. Upon run completion, the orchestration engine reconciles the reservation against actual consumed token spend. If an initial reservation causes the organization's counter to exceed its configured limit, the transaction rolls back, and the request is rejected immediately.

### High-Availability & Disaster Recovery: Valkey Outage Fallback Policy

During local cache or Valkey infrastructure outages, the orchestration engine applies a tiered operational fallback policy:

<Callout variant="caution" title="Infrastructure Outage Operational Mode">
  * **Automated / SI Workflows (Fail-Closed)**: All automated trigger requests are blocked (HTTP 429) during cache dark periods to prevent unmonitored spend spikes.
  * **Interactive User Workflows (Fail-Open)**: Human interactive chat sessions remain available to preserve engineer operational capabilities during active incident response.
</Callout>

Beyond backend concurrency safeguards, complete administrative operational control relies on continuous telemetry and analytics driven by NRQL.

## Track usage and telemetry with NRQL [#nrql]

All compute limit evaluations, budget transitions, and rejection events emit real-time telemetry to the New Relic Telemetry Data Platform (NRDB). System administrators and engineers can query these events to monitor resource consumption and audit access patterns.

### The SreComputeLimitEvent schema [#schema]

Compute limit evaluation events are emitted to NRDB under the `SreComputeLimitEvent` custom event type. Key schema attributes include:

* `organizationId`: The target New Relic organization account ID.
* `userId`: The specific user ID (populated for interactive requests; NULL for System Identity runs).
* `principalType`: The category of caller (USER vs. SYSTEM_IDENTITY).
* `limitName`: The policy evaluated (e.g., <DNT>Autopilot</DNT> Feature Daily Token Limit).
* `currentValue`: Cumulative token or compute count at evaluation time.
* `limitValue`: Configured budget ceiling.
* `verdict`: The outcome of the policy evaluation (PASS, WARN, REJECT, or CONCURRENCY_LIMIT_EXCEEDED).

**Note on granular troubleshooting:** While `SreComputeLimitEvent` records rolled-up policy evaluation decisions and gating verdicts, individual LLM calls and step executions continue to write granular telemetry to `SreAgentTokens` tagged with `run_id` and `agent_id` for deep, call-level troubleshooting.

Administrators can execute the following NRQL queries in the New Relic Query Builder to analyze consumption:

To complement real-time analytics, understanding the architectural relationship between enforcement mechanisms and billing reporting is critical for long-term governance.

## Billing reconciliation, data lag, and disclaimers [#billing]

Distributed system architectures maintain a structural separation between real-time entry gating and asynchronous billing metrics processing.

### Counter Architecture & Pipeline Skew Reconciliation

The platform uses a dual-store model to balance low-latency enforcement with accounting accuracy:

* **Real-Time Enforcement Layer**: Sub-millisecond Valkey token counters evaluate entry gates to block over-budget runs instantly.
* **Billing & Reporting Pipeline**: Historical NRDB metric pipelines (`resourceConsumption`) aggregate data asynchronously, with an expected 2-hour processing lag.
* **Margin of Error Absorption**: Due to high-frequency execution concurrency, minor counter skew may create a temporary overshoot variance of 5% to 10%. New Relic absorbs all overshoot costs internally; customer accounts are never billed for token usage that exceeds their explicitly configured hard cap.

### Important Callouts and Limitations

<Callout variant="important" title="Admin UI Configuration">
  Budget limits configured in the Autopilot Admin Portal represent target thresholds. While real-time enforcement gates halt execution immediately upon limit detection, processing delays in telemetry rollups may result in minor consumption variances.
</Callout>

<Callout variant="caution" title="Real-Time User Interface Notice">
  Compute limit status indicators ("budget pills") reflect near-real-time Valkey counter state. If your organization reaches its daily or monthly cap, active chat sessions will terminate further execution immediately without loss of historical chat data.
</Callout>

<Callout variant="tip" title="Monthly Billing Statement Reconciliation">
  Official invoice line items for Advanced Compute Units (aCCUs) are derived exclusively from processed NRDB billing pipeline metrics. In the event of any discrepancy between real-time UI counters and monthly billing statements, the final audited NRDB pipeline metric governs, capped at your explicitly configured policy limit.
</Callout>
