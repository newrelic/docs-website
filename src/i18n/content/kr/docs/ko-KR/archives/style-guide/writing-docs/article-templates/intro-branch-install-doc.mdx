문서 사이트의 분기형 설치 구성 요소를 통해 사용자는 하나 이상의 옵션을 선택할 수 있으며, 선택한 옵션에 따라 콘텐츠가 표시됩니다.

## 생성 프로세스 개요 [#overview]

브랜치 설치 구성 요소로 작업을 시작하기 전에 고려해야 할 사항:

* 분기형 설치를 확실히 사용하고자 하는지 확인하십시오. 다른 솔루션(예: [탭 구성 요소](/docs/style-guide/structure/intro-to-components))으로 문제를 해결할 수 있는지 고려해 보십시오.
* [당사가 작성한 분기형 설치 문서](#uses)를 살펴보고 어떤 것이 가능한지 확인하십시오. 템플릿으로 사용하기 위해 복제할 항목을 선택하십시오.
* 옵션과 표시될 콘텐츠의 논리적 흐름을 확정하십시오. 이상적으로는 브랜치를 생성하기 전에 콘텐츠 계획이 거의 최종 단계에 있어야 합니다. 이러한 이유로 작업을 두 개 이상의 Jira로 나눌 수 있습니다.

분기된 설치 구성 요소를 여러 가지 방법으로 빌드할 수 있으며, 특히 구조가 복잡할수록 제대로 작동하게 하는 데 많은 노력이 필요할 수 있습니다. 하지만 그렇다 하더라도, 생성 프로세스가 일반적으로 어떤 모습인지에 대한 전반적인 개요는 다음과 같습니다:

1. 분기된 설치 문서, 특히 [예제 YAML 파일](#yaml-examples)을 검토하십시오. 이 구성 요소의 구조와 논리를 알아보십시오.
2. 시작할 준비가 되면 에뮬레이션하려는 설치 구성 요소의 YAML 파일과 관련 폴더를 복사하여 프로젝트의 기반으로 사용하십시오.
3. 프로젝트와 일치하도록 최상위 폴더 이름을 변경하고, YAML 파일의 `agentName`도 일치하도록 변경하십시오. `agentName`은(는) YAML 파일에 어느 폴더에서 콘텐츠를 가져올지 알려줍니다. ([예제 YAML 파일](#yaml-examples)을 참조하십시오.)
4. 제대로 작동하는지 확인하려면 로컬 빌드를 수행하십시오.
5. .mdx 파일을 추가하고 yaml 파일을 편집하기 시작하십시오. 계획이 기존 로직과 얼마나 일치하는지에 따라 YAML 파일에서 대부분의 콘텐츠를 제거하고 한 번에 조금씩 추가하는 것이 더 쉬울 수 있습니다.
6. 작업하는 동안 자주 빌드하여 제대로 작동하는지 테스트하십시오. 작업을 작은 단위로 수행한 다음 빌드되는지 확인하면 문제 진단, 해결에 낭비되는 시간을 피할 수 있습니다. 오류를 확인하려면 [YAML 확인 스크립트](/docs/style-guide/writing-docs/article-templates/branch-install-doc-reference#verify-yaml)를 사용하십시오.

진행이 막히는 경우, 이를 구축해 본 사람에게 도움을 요청하십시오.

## 중요한 의사 결정 지점 [#decision-points]

분기된 설치에서 취할 수 있는 몇 가지 다른 접근 방식이 있습니다. 주요 결정 사항은 다음과 같습니다:

<CollapserGroup>
  <Collapser id="default-content-decision" title="옵션을 선택하기 전에 콘텐츠를 표시해야 합니까?">
    이 결정은 다음과 관련이 있습니다: 고객이 문서에 처음 방문했을 때 무엇을 보게 됩니까? 옵션을 선택하기도 전에 지침을 보여주는 것이 합리적입니까? 대다수의 고객이 선택할 단일 경로가 있는 경우, 옵션 선택에 따라 조정되고 변경되는 콘텐츠를 보여주는 것이 합리적일 수 있습니다. 이에 대한 세부 정보:

    * &quot;기본 콘텐츠&quot; 접근 방식은 `override` 및 `skip` 구성 요소를 사용하는 데 의존합니다. 파일을 표시한 다음 다음과 같이 안내합니다: x 옵션이 선택되면 이 파일을 건너뛰거나 덮어씁니다. (이를 사용하는 설치 문서: [자바 설치](/install/java).)
    * 옵션을 선택하기 전에 콘텐츠를 표시하지 않으려면 `isCondition=true` 접근 방식을 사용합니다. 해당 구성 요소는 단순히 &quot;이러한 옵션이 선택된 경우 이 파일을 표시합니다.&quot;를 의미합니다. (이를 사용하는 설치 문서: [.NET 설치](/install/dotnet).)
  </Collapser>

  <Collapser id="display-all-options-decision" title="모든 옵션을 표시해야 합니까? 아니면 중첩해야 합니까?">
    이 결정은 처음에 모든 옵션 선택 항목을 표시할지, 아니면 중첩할지(예: 한 옵션을 선택하면 다른 옵션 선택 상자가 나타남)에 대한 것입니다.

    옵션 선택 논리가 상당히 단순한 경우 모든 옵션을 고객에게 한 번에 노출하는 것이 합리적일 수 있습니다. 그러나 옵션 선택 논리가 다소 복잡한 경우(예: 3개 이상의 선택 항목이 있고 일부 선택 항목이 이후 선택 항목에 영향을 미치는 경우) 이를 중첩하는 것이 합리적일 수 있습니다.

    완전히 노출된 옵션 선택 상자 세트의 예는 \[Network security prerequisites doc]을 참조하십시오. 중첩된 선택 상자 세트의 예는 \[the .NET install]을 참조하십시오.
  </Collapser>

  <Collapser id="guided-install-decision" title="안내 설치가 필요합니까?">
    이 결정 사항은 안내 설치 경로에 대한 정보를 표시해야 하는지 여부에 관한 것입니다. 일부 에이전트의 경우 안내 설치 경로에 대한 일부 콘텐츠를 표시하고자 합니다(예: &quot;앱 서버&quot; 및 &quot;Jetty&quot;를 선택하면 [자바 에이전트 설치](/install/java)에서 안내 설치 콘텐츠를 볼 수 있습니다).

    안내 설치 콘텐츠를 추가하기 위한 몇 가지 옵션이 있습니다:

    * 안내 설치 콘텐츠를 표시할 특정 옵션에 배치할 수 있는 `recommendedGuided: true` 구성 요소가 있습니다. 이것이 기본적으로 수행하는 작업은 해당 옵션 선택 상자가 포함된 .mdx 파일의 콘텐츠를 표시하는 것입니다. 자바 설치에서 이에 대한 예제를 볼 수 있으며, 여기서 안내 설치 콘텐츠는 `appInfo-2` 파일에 있습니다. 이 구현은 실제로 안내 설치 콘텐츠에만 국한되지 않습니다. 이 로직을 사용하여 원하는 임의의 콘텐츠를 표시할 수 있습니다.
    * 또는 안내 설치를 일반적인 .mdx 파일로 추가하고 다른 파일과 마찬가지로 표시할 수 있습니다. .NET 설치에서 이 방식을 사용합니다. 이 방식을 사용하면 다른 파일과 마찬가지로 번호가 매겨진 단계로 표시됩니다.
  </Collapser>

  <Collapser id="config-file-decision" title="구성(config) 파일이 필요합니까?">
    일부 에이전트는 사용자가 설치 문서에서 직접 사용자별 값을 입력할 수 있도록 하는 구성 파일 구성 요소를 사용합니다. 이에 대한 예는 [자바 설치 문서](/install/java)를 참조하십시오.

    이 파일을 사용할 필요는 없습니다. 이것의 사용은 특정 설치 워크플로우에 따라 달라집니다. (예를 들어 .NET 설치 문서에서는 이를 사용하지 않습니다.)
  </Collapser>
</CollapserGroup>

## 당사의 분기 설치는 다음을 사용합니다. [#uses]

다음은 분기된 설치의 구현과 이에 대해 선택한 사항의 요약입니다. 취하고자 하는 접근 방식과 일치하는 것을 선택하여 필요에 따라 조정하는 것을 권장합니다. 새로운 용도를 추가할 때 이 목록을 최신 상태로 유지해 주십시오.

* 취약점 관리: [dependabot 데이터 가져오기](/install/vm/). [이 YAML 파일의 레이블이 지정된 이미지를 참조하십시오](#simple-yaml-example). 세부사항:

  * 매우 간단한 구현입니다. 두 파일 중 하나를 선택할 수 있는 단일 옵션 선택 상자입니다.
  * 기본적으로 표시되는 콘텐츠가 없습니다.
  * 이것은 매우 간단하므로 탭 구성 요소가 더 나은 선택이었을 수 있다는 점에 유의하십시오.

* [MySQL 통합 설치](/install/mysql). 세부사항:

  * 단일 옵션 선택 상자만 있는 간단한 구현입니다.
  * 기본 콘텐츠 표시 방식을 취합니다.

* [자바 설치](/install/java). 세부사항:

  * [기본 콘텐츠 접근 방식](#default-content-decision)을 취합니다. 대부분의 고객이 선택하는 설치 경로가 하나이기 때문입니다.
  * 두 개의 옵션 선택 섹션만 있습니다: 첫 번째 옵션에서 선택한 항목에 따라, 두 번째 옵션 상자가 표시됩니다.
  * `recommendedGuided` 구성 요소를 사용하여 안내 설치(`appInfo-2` 파일에 포함됨)를 표시합니다.
  * 구성 파일 구성 요소를 사용합니다.

* [.NET 설치](/install/dotnet). [이 YAML 파일의 레이블이 지정된 이미지를 확인하십시오](#complex-yaml-example). 세부사항:

  * 기본 콘텐츠는 표시되지 않습니다. 전적으로 [`isConditionalStep: true`](#default-content-decision) 접근 방식에 의존합니다. 이는 경로가 꽤 많고 대다수의 고객이 택하는 단일 경로가 없기 때문입니다(이론적으로 하나를 선택할 수는 있었지만).
  * 여기에는 두 개의 옵션 선택 섹션만 있습니다. 첫 번째 옵션에서 선택한 항목에 따라 두 번째 옵션 상자가 표시됩니다.
  * (`appInfo-2` 파일에 포함된) `recommendedGuided` 구성 요소를 사용합니다.
  * 설정 파일 구성 요소를 사용하지 않습니다: 이는 대부분의 고객이 파일을 직접 사용하지 않고 환경 변수나 기타 옵션을 통해 설정을 편집하기 때문입니다.

* [파이썬 설치](/install/python). 세부사항:

  * 기본 콘텐츠를 표시하지 않습니다. 전적으로 [`isConditionalStep: true` 접근 방식](#default-content-decision)에 의존합니다. 이는 하나의 주요 경로가 없기 때문입니다.
  * 여기에는 선택한 항목에 따라 최대 4개까지 꽤 많은 옵션 선택 상자가 있습니다.
  * 구성 파일 구성 요소를 사용하지 않습니다.
  * 주석을 사용하여 코드에 대한 이해를 돕고 유지 관리를 개선합니다.

* [네트워크 모니터링 엔드포인트](/install/npm). 세부사항:
  * 꽤 간단한 구현입니다. 여러 테이블 중 어떤 테이블을 표시할지 제어하는 세 개의 옵션 선택 상자입니다. 어떤 테이블을 표시할지 결정하는 대체 재정의가 포함된 기본 표시 파일입니다.
