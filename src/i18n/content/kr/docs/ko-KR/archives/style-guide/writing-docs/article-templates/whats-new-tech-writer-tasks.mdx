테크니컬 라이터는 &quot;What&apos;s new&quot; 게시물을 게시하는 데 중요한 역할을 합니다. 기여자가 [What&apos;s New 게시물 작성 지침](/docs/style-guide/writing-docs/article-templates/whats-new-template/)을 따르는 동안, 기여자가 작업을 마무리할 수 있도록 몇 가지 추가 단계를 수행해야 합니다.

## 프로세스 개요 [#overall-process]

`What's new` 프로세스의 전체적인 모습은 다음과 같습니다:

1. 회사 내 누구나 문서 웹사이트에 `What's new` pull 요청(PR)을 제출할 수 있습니다.
2. 다수의 제품 마케팅 관리자가 교대로 게시물을 검토하고 제안을 합니다.
3. 제품 마케팅 관리자가 게시물 검토를 마치면, 기술 문서 팀에 추가 검토를 요청하는 PR 댓글을 남깁니다.
4. 테크니컬 라이터는 검토를 완료하고 게시물을 게시하거나, 특정 날짜 및 시간대에 게시할 준비가 되었음을 확인하는 댓글을 PR에 남깁니다.

## 게시물에 대한 특정 테크니컬 라이터 작업 [#specific-writing-tasks]

일일 영웅은 매일 다음과 같은 책임이 있습니다:

* **예약된 게시물 병합:** Github 보드의 `Scheduled work` 열에서 이미 승인되어 당일 병합되도록 예약된 `What's new` 게시물이 있는지 확인하십시오. 예를 들어, 월요일의 히어로가 수요일 히어로 교대 근무 시간에 게시되도록 예약된 게시물을 검토하고 승인한 경우 해당 PR을 병합해야 합니다.
* **수신되는 모든 게시물 검토:** 수신되는 모든 `What's new` 게시물은 히어로 교대 근무 중에 검토하고 승인해야 합니다. 여기에는 기본 사본 편집, 올바른 이미지 형식 확인, 성공적인 미리 보기 빌드 확인이 포함됩니다. 게시해야 하는 날짜로 제목을 편집한 다음 PR을 `Scheduled work` 열로 이동하십시오. PR이 도착하는 대로 검토하면 병합할 준비가 되었을 때 원활하게 릴리스할 수 있습니다.

더 자세한 지침은 문서의 나머지 부분을 참조하십시오.

<Callout variant="tip">
  작성 검토를 시작하기 전에, 게시물이 해당 부서 외부에서 작성된 경우 프로덕트 마케팅 매니저가 검토했는지 확인하십시오. 예를 들어, 개발자 또는 프로덕트 매니저가 게시물을 제출하는 경우, 먼저 프로덕트 마케팅 매니저([CODEOWNERS 파일](.github/CODEOWNERS)에 나열된 사람)가 검토해야 합니다. 프로덕트 마케팅 매니저가 게시물을 검토하고 히어로에게 전달한 후, 아래 섹션의 단계를 완료하십시오.
</Callout>

### GitHub 보드 관리 [#the-board]

1. GitHub 프로젝트 보드에서 게시물을 분류 열에서 **Scheduled work** 열로 이동하십시오. 게시물은 실제로 게시될 때까지 해당 위치에 유지됩니다.
2. 쉽게 알아볼 수 있도록 PR 제목에 게시 날짜와 시간대를 삽입하십시오. 당사의 [지침](/docs/style-guide/writing-docs/article-templates/whats-new-template/)은 기여자에게 아침, 정오 또는 저녁과 같은 게시 시간대를 제공한다고 알려줍니다. 제시간에 사용할 수 있도록 일찍 게시하기를 원하는지 물어봐야 할 수도 있습니다.

### 게시물을 검토합니다 [#the-review]

1. 기본 스타일 가이드 규칙을 사용하여 문서를 검토하십시오. 주요 문제를 발견한 경우 기여자(또는 제품 마케팅 검토자)와 협력하고, 그렇지 않으면 직접 변경할 수 있습니다.

2. 문서 사이트의 URL이 절대 경로인지 확인해 주십시오. 상대 경로는 제품 UI에서 해석되지 않으므로 게시물에 절대 경로를 사용해야 합니다.

   ```md
   * Absolute path (GOOD): [**Billing user role**](https://docs.newrelic.com/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#roles)
   * Relative path (BAD): [**Billing user role**](/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#roles)
   ```

3. 게시물에서 이미지를 참조하는 경우, 다른 사이트에서 호스팅되는 이미지에 대한 링크가 아닌지 확인하십시오. 이미지 파일은 당사의 저장소에 있어야 합니다.

4. 게시물의 프런트 매터에 `isFeatured: true`이(가) 있는지 확인하십시오. 그렇다면 이는 게시물이 제품 UI 상단에 고정된다는 의미입니다. 단 하나의 게시물만 주요 게시물로 표시되도록 이전에 주요 게시물로 표시된 게시물에서 해당 플래그를 제거해야 합니다.

<Callout variant="tip">
  히어로 교대 근무 중에 &quot;새로운 기능&quot; 게시물 검토를 완료할 수 없는 경우, 다음 교대 근무를 맡은 히어로에게 공지하여 완료할 수 있도록 하십시오.
</Callout>

### 게시물을 게시하십시오. [#publish-the-post]

<Callout variant="caution">
  두 번째 브랜치를 생성하여 `main`에 병합하기 전에 [ID를 생성하는 GitHub 작업](https://github.com/newrelic/docs-website/actions/workflows/update-whats-new-ids.yml)이 완료되는지 확인하십시오.
</Callout>

&quot;새로운 기능&quot; 게시물을 게시하는 데는 `main`에 대한 두 번의 병합이 포함됩니다.

1. 일일 릴리스 브랜치를 생성하고 평소와 같이 `main`에 병합하십시오.
2. `main`에 병합한 후, `develop`을(를) 기반으로 두 번째 릴리스 브랜치를 생성하십시오. 이 두 번째 브랜치에는 &apos;Whats new?&apos; ID가 포함됩니다.
3. 이 두 번째 브랜치를 `main`에 병합하십시오. 이 두 번째 병합은 UI에 &apos;What&apos;s new?&apos; 게시물을 표시합니다. (궁금한 분들을 위해 설명하자면: 두 번째 브랜치에는 문서 사이트의 게시물을 UI에 연결하는 &apos;Whats new?&apos; ID가 포함되어 있습니다. 두 번째 병합은 두 번째 위치를 설명합니다.)
4. 후속 조치를 취하고 게시물이 문서 사이트뿐만 아니라 UI에도 표시되는지 확인하십시오.

### 향후 게시물 계획 [#future-posts]

향후 게시될 게시물의 경우:

* 일반적으로 당직 히어로가 게시되어야 하는 당일의 게시물을 책임집니다.
* 게시물이 일반적인 오전 8시 또는 9시 (미국 태평양 표준시) 병합보다 일찍 배포되어야 하는 경우, 초기에 이 작업을 수행한 담당자가 게시되도록 조치해야 합니다.
* 가시성이 높은 특정 릴리스와 같은 일부 경우에는 테크니컬 라이터가 PR에 자신을 할당하여 게시물에 대한 소유권을 가질 수 있으므로, 모든 사람이 해당 게시물에 대한 책임이 히어로에게 있지 않음을 알 수 있습니다.
