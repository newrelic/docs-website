기술 문서 작성자(TW)는 문서를 담당합니다. 우리는 [문서를 작성 및 편집](/docs/style-guide/writer-workflow/tech-writer-workflow/) 하고 [동료 편집을 교환](/docs/style-guide/writer-workflow/peer-editor-workflow/)하며, 백로그를 유지 관리하고, 히어로 역할을 합니다. 이 모든 것을 실현하기 위해 [문서 팀 GitHub 보드](https://github.com/newrelic/docs-website)를 사용하여 제출된 이슈와 pull 요청(PR)을 관리합니다.

## 이슈 또는 PR의 관계자 [#who]

GitHub는 작업을 진행하는 사람들을 포함하여 이슈 또는 pull 요청의 수명주기의 모든 단계를 추적합니다.

문서 팀은 누구나 GitHub를 통해 문제를 제기하거나 pull 요청을 생성하도록 초대하므로, 제출자와 뉴렐릭 GitHub 조직의 관계를 확인하는 것을 강력히 권장합니다. 기여자가 Relic인지 확실하지 않은 경우, 뉴렐릭 GitHub 조직의 구성원인지 확인하는 것이 좋은 방법입니다. 일반적으로 달리 입증될 때까지 제출자가 외부인이라고 가정하는 것을 권장합니다.

* **생성자**: 이슈 또는 PR을 여는 사람입니다. 생성자는 문서 팀의 누군가, 다른 뉴렐릭 직원 또는 외부 사용자일 수 있습니다. 누가 생성했는지에 따라 이슈 또는 PR에 다르게 레이블을 지정합니다.
* **담당자**: 이슈 또는 PR에 대한 책임을 지고 게시될 때까지 관리하는 사람입니다. Hero는 TW가 아닌 이슈 및 PR을 자신에게 할당하거나 다른 작성자로부터 이슈 또는 PR을 인계받을 수 있습니다.
* **리뷰어**: 코드나 문서의 동료 편집을 제공하고 변경 사항을 승인하는 사람입니다. 이 사람이 반드시 해당 영역을 담당하거나 커밋 병합을 담당하는 사람일 필요는 없습니다. 특정 이슈에 최대 100명의 리뷰어를 할당할 수 있습니다.

**Hero**로서, 하루 종일 다음 사항에 주의를 기울이십시오:

* 하루를 시작할 때(특히 한 주가 시작되는 월요일에) 이전 Hero와 확인하십시오. 필요한 경우 BCN Hero와 동기화하는 것을 잊지 마십시오.
* \#docs\_deploys에서 들어오는 PR을 주시하고 **Needs triage** 열의 모든 항목을 확인하십시오. 해당 열에서 적절한 열로 카드를 드래그하십시오.

**팀의 모든 사람**이 일이 계속 진행되도록 돕습니다:

* 모든 작성자는 **Needs review** 열을 주시해야 합니다. PR에 리뷰어가 없는 경우 직접 맡을 수 있습니다.
* 모든 유형의 검토(단순 또는 복잡)가 준비되면 PR을 **검토 필요**로 이동하십시오.
* SME에 의해 차단된 PR은 반드시 **Waiting on SME/Blocked**로 이동하십시오.
* PR 피드백이 완료되었는지 확인하려면 **TW의 병합 대기 중**을 확인하십시오.
* 동료 피드백을 반영한 후 PR을 병합하고 보드에서 제거하십시오.

## GitHub(및 스타일 가이드)의 참조 처리 [#references]

* 공개된 장소에서 비공개 항목으로 링크하지 마십시오.
* Jira 지원 티켓을 참조할 수 있지만, 링크(`https://newrelic.atlassian.net/browse/DOC-1234`은 불가)가 아닌 이슈 키(`DOC-1234`은 가능)로 지원 티켓을 참조하십시오.
* 트래픽이나 사용량 수치를 공개적으로 언급하지 마십시오.
* 내부 사람을 이름으로 참조하지 마십시오. GH 계정이 있는 경우 GH 핸들을 @멘션하십시오. 그렇지 않은 경우 사람보다는 팀(&quot;브라우저 팀 엔지니어에게 문의&quot; 또는 &quot;지원 엔지니어&quot;)에 대해 이야기하십시오.
* \#help-documentation 채널과 히어로를 언급할 수 있습니다.

## 메인 작업에 릴리스 병합(또는 언제 게시합니까?) [#merging-main]

히어로는 현재 태평양 표준시 기준 오전 9시(아침), 오후 12시(정오) 및 오후 3시(저녁)에 병합합니다. 릴리스 중에 누군가 develop에 병합할 때 중단이 발생하지 않도록 릴리스 브랜치를 main에 병합합니다. 이 워크플로우에 대해 자세히 알아보려면 [Atlassian의 gitflow 문서](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow)를 참조하십시오.

develop 브랜치에서 새 릴리스 브랜치를 생성하는 것이 중요합니다. 새 브랜치를 생성하기 전에 develop 브랜치에 있는지 확인하십시오.

릴리스를 시작하려면:

1. 상단 헤더에서 **Current Branch**를 클릭하고 드롭다운 메뉴에서 **New Branch**를 클릭한 다음 **Develop**을 선택하여 Github Desktop을 사용하여 `develop`의 브랜치를 생성하십시오.
2. 이 패턴으로 브랜치 이름을 지정하십시오: `daily-release/mm-dd-yy-morning/noon/evening`. 예를 들어 2021년 10월 27일 오전 9시에 발생하는 일일 릴리스는 다음 스타일을 따릅니다: `daily-release/10-27-21-morning`.
3. 변경 사항을 푸시하려면 GitHub Desktop에서 **Push Origin**을 클릭하십시오.
4. **Create Pull Request**를 클릭하여 새로운 일일 릴리스 브랜치에서 main으로 pull 요청을 생성하십시오. 그러면 [github.com](github.com)에서 pull 요청 화면이 열립니다. pull 요청은 기본적으로 develop에 병합되므로 페이지 왼쪽에서 `base` 브랜치로 main을 선택한 다음 `Submit Pull Request`을(를) 클릭하십시오.
5. 모든 검사가 완료될 때까지 기다린 다음 pull 요청을 병합하십시오.

`daily-release/mm-dd-yy-morning` 패턴을 따르는 모든 브랜치는 [보호된 브랜치](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/about-protected-branches)입니다. 관리자만 삭제할 수 있습니다.

## GitHub 레이블 [#labels]

백로그의 상태를 더 잘 분류하고 추적할 수 있도록 이슈에 레이블을 적용합니다:

* `content`: 모든 이슈는 이 레이블을 사용합니다. `content`은(는) 이슈가 디자인이나 엔지니어링 이슈가 아니라 콘텐츠 관련 이슈임을 나타냅니다.

* `pg_*`: 문서 팀은 제품 그룹을 나타내기 위해 항상 이 레이블을 사용합니다. 전체 정의는 내부 팀 Google Drive의 &quot;Doc Jira and GitHub fields&quot; 문서를 참조하십시오.

* 문제를 생성한 사람을 나타냅니다:

  * `from_internal`: Relic이 만들었습니다.
  * `from_external`: 뉴렐릭 직원이 아닌 사람이 리포지터리에서 이슈를 열었거나 #customer-feedback 프로세스를 통해 이슈가 접수되었습니다.
  * `from_tw`: 우리 중 한 명이 만들었습니다(#customer-feedback을 전달하는 경우가 아니라면).

* 선택 사항:

  * `docs-issue-candidate`: 제품 팀의 전문 지식 없이 문서 팀이 처리하기에는 범위가 너무 큰 문제입니다. 이 레이블은 문서 문제 팀에 이러한 문제를 고객 피드백 채널로 마이그레이션하도록 알림을 보내며, 여기서 문제를 분류하여 제품 팀으로 보냅니다.
  * `Jira’d`: 해당하는 Jira 지원 티켓이 있는 이슈입니다. 이슈의 댓글에 Jira 번호(예: DOC-1234)를 남겨 두십시오.

기여가 어디서 오는지 확인할 수 있도록 모든 pull 요청에는 다음 레이블이 필요합니다:

* `content`: 항상 추가하십시오. 이는 PR이 디자인이나 엔지니어링이 아닌 콘텐츠와 관련되어 있음을 나타냅니다.

* pull 요청을 생성한 사람을 표시하십시오:

  * `from_internal`: Relic이 만들었습니다.
  * `from_external`: 사용자가 리포지터리에서 열었거나 #customer-feedback 프로세스를 통해 들어왔습니다.
  * `from_tw`: 우리 중 한 명이 생성했습니다(#customer-feedback을 전달하는 경우는 제외). PR이 외부 이슈를 수정하는 경우, 기술 작성자가 작업을 수행했으므로 `from_tw` (으)로 레이블을 지정하십시오.

## 문서 문제 [#docs-issues]

문서 이슈에 적합한 후보를 선택하는 데 엄격하고 빠른 규칙은 없습니다. 문서 담당자가 추적하기 너무 어렵거나 깊은 엔지니어링 전문 지식이 도움이 될 수 있는 모든 것이 될 수 있습니다. 몇 가지 예로는 코드 예제, 요구 사항 섹션 및 NRQL 쿼리가 있습니다.

궁극적으로 문서 문제는 문서 팀이 제품 팀과 협력하여 문서 및 제품 문제를 해결하는 데 도움이 됩니다. 이를 통해 제품 팀의 전문 지식을 활용하여 문제를 제기한 사람에 관계없이 가능한 한 많은 문제를 해결할 수 있습니다.

실행 가능한 이슈 후보의 수명주기는 다음과 같은 형식을 띌 수 있습니다:

1. 누군가 GitHub를 통해 이슈를 제출하면 GitHub 히어로가 이를 잠재적 후보로 평가합니다.
2. 히어로가 `docs-issue-candidate` 레이블을 추가합니다. 이후, 히어로가 이슈를 보관합니다.
3. 매주 지정된 문서 팀 구성원이 `docs-issue-candidate` 레이블이 있는 모든 이슈를 평가합니다.
4. 승인되면 `docs-issue-candidate` 레이블이 `docs-issue` 레이블로 변경됩니다. 그런 다음 이슈를 고객 피드백 Jira 프로젝트로 마이그레이션합니다.
5. 새로운 Jira는 PM에 의해 분류된 다음 올바른 프로젝트 팀으로 퍼널링됩니다.
6. PM은 담당자에게 지원 티켓을 할당하며, 담당자는 완료 시 이를 닫습니다.

## 커밋을 확인하십시오. [#verified-commits]

<img title="verified commit" alt="A screenshot of a verified commit in github" src="/images/verified-commits.webp" />

확인된 커밋을 설정하면 프로세스에 약간의 보안이 추가됩니다. 이를 통해 커밋이 다른 누군가가 원격으로 사용자인 것처럼 가장하여 커밋한 것이 아니라 사용자의 컴퓨터에서 온 것임을 보장합니다. 누군가의 커밋이 확인되면 그 옆에 레이블이 표시됩니다.

먼저 GPG라는 것을 설치해야 합니다. Homebrew를 사용하여 이 작업을 수행할 수 있습니다:

```bash
brew install gpg
```

설치가 완료되면 다음 명령을 실행하여 키를 생성하는 데 사용할 수 있습니다:

```bash
gpg --full-generate-key
```

이렇게 하면 다음과 같이 대답할 수 있는 일련의 프롬프트가 트리거됩니다:

* 선택 사항은 무엇입니까? **1**
* 원하는 키 크기는 무엇입니까? (3072) **4096**
* 키가 유효한 대상은? (0) **0**
* 키가 전혀 만료되지 않습니다\
  맞습니까? (y/N) **y**


이제 `YOUR_KEY_ID`을(를) 이전의 키로 대체하여 다음 명령을 실행함으로써 git의 일부 설정을 조정합니다:

```bash
git config --global user.signingkey YOUR_KEY_ID
git config --global commit.gpgsign true
```

다음으로 이 명령을 실행하여 bash 또는 zsh 프로필에 추가 정보를 저장합니다. zsh를 사용하는 경우 다음을 실행하십시오:

```shell
if [ -r ~/.zshrc ]; then echo -e '\nexport GPG_TTY=\$(tty)' >> ~/.zshrc; \
else echo -e '\nexport GPG_TTY=\$(tty)' >> ~/.zprofile; fi
```

bash를 사용하는 경우 다음을 실행하십시오:

```bash
if [ -r ~/.bash_profile ]; then echo -e '\nexport GPG_TTY=\$(tty)' >> ~/.bash_profile; \
else echo -e '\nexport GPG_TTY=\$(tty)' >> ~/.profile; fi
```

이제 테스트를 실행하여 어떻게 작동하는지 확인할 수 있습니다. 이전에 gpg로 생성한 비밀번호를 입력해야 할 수도 있습니다.

```bash
echo "test" | gpg --clearsign
```

제대로 작동하지 않으면 다음 명령을 실행해 보십시오.

gpg 클라이언트를 종료하려면 먼저 다음 명령을 실행합니다:

```bash
gpgconf --kill all
gpg-agent --daemon
```

그런 다음 `echo test` 명령을 다시 실행하십시오.

여전히 오류가 발생하는 경우 변수를 사용하도록 프롬프트를 표시하고 비밀번호를 다시 인증해야 할 수 있습니다:

```bash
export GPG_TTY=`tty`
```

그런 다음 이 테스트를 다시 실행하십시오:

```bash
echo "test" | gpg --clearsign
```
