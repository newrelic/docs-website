## 0. 로컬 환경 설정 [#set-local]

로컬 환경은 한 번만 설정하면 됩니다. 이미 이 작업을 수행한 경우 이 단계를 건너뛸 수 있습니다.

[로컬 빌드 환경을 설정](/docs/style-guide/writing-docs/writer-workflow/set-up-local)하는 방법에 대한 자세한 지침은 여기를 참조하십시오.

## 1. 브랜치 생성 및 문서 수정 [#edit-doc]

GitHub Desktop에는 **Current Repository**(현재 저장소), **Current Branch**(현재 브랜치) 및 **Fetch origin**(원본 가져오기)이라는 세 개의 탭이 표시됩니다. 기본 브랜치는 **Develop**이므로 브랜치를 생성할 차례입니다.

1. **Current Branch**를 클릭하고 **New Branch**를 선택합니다.
2. 편집할 문서를 찾으십시오.
   * 파일 경로와 함께 Finder 또는 파일 탐색기를 사용하십시오. 예를 들어 파이썬 에이전트 문서를 편집하려면 다음으로 이동하십시오: `~/Documents/github/docs-website/src/content/docs/agents/python-agent/hosting-services/python-agent-stackato.mdx`
3. 원하는 텍스트 편집기에서 [문서를 편집](https://docs.newrelic.com/docs/style-guide/writing-docs/processes-procedures/create-edit-content) 하십시오. [마크다운 언어](https://www.markdownguide.org/basic-syntax)로 문서를 작성해야 합니다.
4. 편집한 파일을 저장하십시오.

작성 가이드라인에 대한 질문이 있는 경우 [스타일 가이드](https://docs.newrelic.com/docs/style-guide/writing-strategies/introduction-style-guide/)의 나머지 부분을 확인하십시오.

## 2. 변경 사항을 커밋합니다. [#commit-changes]

편집 내용을 저장했더라도 여전히 커밋을 해야 합니다. 커밋은 워크플로우의 체크포인트라고 생각할 수 있습니다. 커밋 프로세스는 스테이징으로 시작하여 변경 사항을 GitHub에 푸시할 때 끝납니다.

1. GitHub Desktop으로 다시 이동하여 왼쪽 열을 확인하십시오. Github Desktop의 왼쪽 열에는 다음이 표시됩니다:

   * 모든 문서에 적용된 모든 새 편집 기록
   * **Commit to \[your-branch-name]**이라고 표시된 파란색 버튼

2. 커밋 이름을 지정하고 설명을 추가합니다.

3. **Commit to \[yourbranchname]**을 클릭하십시오.
   * 커밋 이름과 설명은 다음과 같을 수 있습니다. `feat(PythonAgent): Renamed the section heading`

## 3. 로컬에서 사이트 실행 [#run-site]

터미널을 사용하여 로컬에서 사이트를 빌드하십시오. 이 단계는 선택 사항이지만, pull 요청을 열기 전에 로컬에서 사이트를 빌드하고 변경 사항을 미리 보는 것을 **강력히** 권장합니다.

매번 저장하거나 커밋한 후가 아니라 로컬 사이트가 충돌할 때만 로컬 사이트를 다시 빌드하면 됩니다.

1. 터미널에서 복제된 리포지터리인 **docs-website**로 이동하십시오. 예:
   * `cd ~/Documents/github/docs-website`
2. 다음 명령을 사용하여 yarn을 실행합니다: `yarn && yarn start`
3. 사이트를 빌드하는 데 몇 분 정도 걸립니다. 차나 커피를 준비하십시오.
4. 빌드되면 [http://localhost:8000/](http://localhost:8000/)으로 이동하여 브라우저에서 사이트를 미리 보십시오.

## 4. 커밋 게시 [#publish-commits]

변경 사항에 만족하면 커밋을 GitHub에 푸시하십시오. 이렇게 하면 GitHub 저장소의 다른 모든 사람이 사용할 수 있습니다.

1. GitHub 데스크톱에서 파란색 **Publish Branch** 버튼이 있으면 클릭하십시오.
2. Publish Branch가 표시되지 않으면 파란색 **Push Origin** 버튼을 클릭하십시오.

## 5. pull 요청을 엽니다. [#open-pr]

모든 사람이 커밋을 볼 수 있지만, 다른 작성자가 검토할 때까지 수정 사항이 `develop `브랜치에 병합되지 않습니다.

이를 수행하려면 pull 요청(PR)을 여십시오:

1. GitHub Desktop에서 파란색 **Create Pull Request button** \[pull 요청 생성 버튼]을 클릭하십시오.

2. 그러면 브라우저에서 GitHub가 열리고 pull 요청을 작성하라는 프롬프트가 표시됩니다.

   * 브랜치에서 `develop` 브랜치로 병합하고 있는지 확인하십시오.
   * 아래로 스크롤하여 모든 커밋을 검토하십시오.

3. 커밋 설명과 마찬가지로 pull 요청 설명도 상세해야 하며 변경 사항의 전체 컨텍스트를 제공해야 합니다.

   * 여기에 추가 컨텍스트(GitHub 이슈 링크 또는 Jira 이슈 ID, SME 등)를 자유롭게 추가하십시오.
   * PR을 열고 **Conversation** 섹션으로 이동한 다음 **Reviewer** 섹션에 리뷰어의 이름을 입력하여 다른 테크니컬 라이터에게 리뷰를 요청하십시오.

4. PR에 `from_tw` 레이블과 기타 [관련 레이블](/docs/style-guide/writer-workflow/github-intro)을 추가하십시오.
   * `from_tw`을(를) 추가하지 않으면 PR이 검토를 위해 다른 작성자에게 자동으로 할당되지 않습니다.

5. PR에 만족하시면 녹색 **Create pull request button** \[pull 요청 생성 버튼]을 클릭하십시오.

6. 직접 pull 요청을 승인하여 변경 사항을 직접 게시하거나, 다른 기술 작성자에게 동료 편집을 요청할 수 있습니다.

7. pull 요청 페이지 하단에 **Checks** 섹션이 표시됩니다. 이러한 검사는 PR이 사이트의 빌드 프로세스를 중단시키지 않도록 보장합니다. 병합하기 전에 `required` (으)로 표시된 모든 검사를 통과했는지 확인하십시오.

8. pull 요청이 검사를 통과하고 다른 기술 작성자가 승인한 후(또는 변경 사항을 게시할 준비가 되었다고 확신하는 경우) 녹색 **Merge pull request** \[pull 요청 병합] 버튼을 클릭하십시오. 이렇게 하면 브랜치와 커밋이 저장소에 병합되고 빌드 프로세스가 시작됩니다.

<Callout variant="important">
  PR을 처음 생성할 때 `from_tw` 레이블을 추가하지 않으면 리뷰어가 자동으로 할당되지 않습니다. PR을 열기 전에 레이블을 추가하는 것을 잊은 경우:

  1. `from_tw` 레이블을 추가하십시오.
  2. PR을 초안 PR로 전환합니다.
  3. PR을 다시 열려면 페이지 하단의 `PR is ready for review button`을(를) 선택하십시오. 이제 PR에 검토자가 지정되어야 합니다.
</Callout>

## 문서 미리보기 [#preview-doc]

이미 게시하고 커밋을 실행한 브랜치를 미리 보는 데는 두 가지 주요 방법이 있습니다:

* **로컬**: 더 빠르지만, 꽤 많은 설정과 터미널에 대한 숙련도가 필요합니다.
* **Netlify Cloud**: 오버헤드 없이 라이브 사이트의 전체 미리 보기를 제공하며, 초안의 미리 보기를 SME와 공유할 수 있는 매우 편리한 방법입니다. 빌드가 준비되면 Netlify Cloud에서 사이트의 미리 보기 버전 링크와 함께 PR에 댓글을 남깁니다. 사이트를 빌드하는 데 일반적으로 약 15분이 걸리지만, 변경 사항이 많은 경우 때때로 더 오래 걸릴 수 있습니다.

## 문서 수정 및 게시 [#revise-doc]

리뷰어가 파일에 대한 리뷰를 제출했다는 알림을 받으면 PR로 이동하여 변경 사항을 검토합니다. 주석이 있는 리뷰의 일부인 경우 다른 뷰에서 볼 수 있으며, 그렇지 않은 경우 파일에서 사본 편집으로 나타날 수 있습니다.

1. 파일의 모든 댓글에 응답하십시오. 후속 논의로 답장하거나 **Resolve conversation** \[대화 해결]을 클릭하십시오.
2. 모든 주석을 해결하고 모든 자동 검사를 통과하면 pull 요청을 병합할 수 있습니다. pull 요청을 병합하면 자동화된 빌드 프로세스가 시작되고 변경 사항이 곧 게시됩니다.

<Callout variant="tip">
  **Merge pull 요청** 버튼이 녹색일 때만 병합할 수 있습니다. 녹색이 아닌 경우, 놓친 코멘트나 GitHub에서 병합을 차단하는 이유를 나타내는 기타 메시지가 있는지 검토하십시오.
</Callout>

## 병합 되돌리기 [#revert]

거의 항상 작업을 실행 취소할 수 있다는 점을 기억하십시오. PR을 병합한 후 병합하지 말았어야 했다는 것을 알게 된 경우, **되돌리기** 버튼을 사용하여 병합을 해제할 수 있습니다.

1. GitHub의 pull 요청 탭에서 집계 표시줄의 **Closed**를 클릭하여 이미 병합된 모든 이슈와 PR을 확인하십시오.
2. 병합한 PR을 찾고, Revert 버튼을 찾으십시오.
3. Revert를 클릭합니다. 그러면 병합해야 하는 새 PR이 생성됩니다. 다시 열려면 원래 PR로 돌아가는 링크를 따라가서 되돌리거나 다시 열어야 합니다.

## 작성자 전용: 포크가 아닌 브랜치에서 작업하십시오 [#branch-fork]

일부 팀은 브랜치에서 작업하고 일부 팀은 포크에서 작업합니다, **문서 팀은 브랜치에서 작업합니다**. 브랜치가 업스트림으로 푸시되는 한, 이를 통해 협업할 수 있으며 누군가 휴가를 가더라도 작업이 손실되지 않도록 할 수 있습니다.

docs-website 리포지터리에 브랜치를 생성하려면:

1. GitHub Desktop을 여십시오.
2. **Current branch: xxx**를 클릭하십시오.
3. **New Branch**를 클릭합니다.
4. 새 브랜치의 이름을 지정하라는 프롬프트가 표시됩니다. 기술적인 이름이 가장 좋습니다. 사람들이 작업 내용이 무엇인지 빠르게 이해할 수 있도록 하는 좋은 방법입니다. 예를 들어, What’s New 페이지에서 작업하는 경우 브랜치 이름을 **Whats-new-updates**로 지정할 수 있습니다.

새 브랜치를 생성할 때 브랜치 이름과 PR 제목에 Jira 이슈 ID(DOC-1234)를 추가하는 것을 잊지 마십시오.

## GitHub 권한에 대한 참고 사항 [#permissions]

문서 팀의 작성자는 브랜치에서 작업하지만 문서 팀 외부의 기여자는 포크를 사용합니다. 이는 또한 문서 팀 소속이 아닌 기여자가 브랜치의 콘텐츠를 직접 편집할 수 없음을 의미하며, 이로 인해 협업이 까다로워질 수 있습니다.

GitHub 권한은 브랜치에서 작업할 수 있는 사람과 포크에서 작업할 수 있는 사람을 결정하는 데 사용됩니다. GitHub에서 액세스는 팀 및 멤버 역할에 따라 결정됩니다. 누구나 공개 저장소에 기여할 수 있지만, 추가 액세스는 `Write` 및 `Admin` 역할을 통해 부여됩니다. (자주 사용되지 않는 다른 정의된 역할도 있습니다.)

Docs 팀의 모든 구성원에게는 저장소에 대한 풀 액세스 권한을 부여하는 `Admin` 역할이 부여됩니다. 다른 뉴렐릭 기여자에게는 사용자 할당 및 pull 요청 열기와 닫기를 허용하는 `Write` 역할이 부여됩니다.

현재 액세스 설정을 검토하려면 `docs-website` 리포지터리로 이동한 다음 **Settings &gt; Collaborators and teams** 또는 **Team and member roles**로 이동하십시오.
