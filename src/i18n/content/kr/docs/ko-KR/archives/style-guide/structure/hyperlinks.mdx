가능한 한 텍스트 자체의 관련 있는 곳에 하이퍼링크를 포함하십시오. 미래의 작성자가 그 중요성을 파악하기 어렵기 때문에 **For more help** 섹션에 문서 링크 목록을 만들지 마십시오.

<Callout variant="tip">
  제품에 연결하는 경우 [UI 경로](/docs/style-guide/quick-reference/ui-paths)에 대한 스타일 가이드 페이지를 참조하십시오.
</Callout>

## 링크 구문 [#link-syntax]

문서 사이트에서는 마크다운 인라인 링크 구문을 사용합니다:

```markdown
[link text](https://example.com)
```

문서 사이트의 다른 페이지로 링크하는 경우 &quot;상대&quot; 링크를 사용해야 합니다(문서 사이트의 `https://docs.newrelic.com` 루트 URL 생략):

```markdown
[link text](/docs/category-path/doc-path/)
```

<Callout variant="tip">
  마크다운은 대상 URL이 문서 끝에 나열되는 [&quot;참조&quot; 스타일 링크도 지원합니다](https://daringfireball.net/projects/markdown/syntax#link). 정상적으로 작동하고 올바르게 렌더링되지만, 몇 가지 이유로 이 링크 스타일의 사용을 피합니다:

  * 이는 덜 일반적인 스타일이며, 기여자에게 혼란을 줄 수 있습니다.
  * 우리 문서는 매우 길기 때문에 기여자가 링크를 대상에 연결하기가 까다로울 수 있습니다.
</Callout>

## 링크 텍스트 [#hyperlinks-linktext]

하이퍼링크 텍스트를 작성할 때 다음 가이드라인을 따르십시오:

* **레이블:** 문서의 각 링크에 고유하고 의미 있는 텍스트 레이블이 있는지 확인하십시오. 다른 링크에 레이블을 지정할 때 동일한 텍스트 문자열을 사용하지 마십시오.
* **위치:** 링크가 이동하는 위치를 식별할 수 있도록 명확하고 간결한 텍스트 레이블을 포함하십시오. 외부 사이트로 연결되는 링크인 경우 추가 컨텍스트를 제공하십시오. 사용자를 해당 위치로 보내는 이유는 무엇입니까?
* **여기를 클릭하십시오:** &quot;여기를 클릭하십시오&quot; 또는 기타 의미 없는 링크 레이블을 사용하지 마십시오.
* **&quot;링크 테스트:&quot;** 주변 텍스트 없이 링크만 읽어 보십시오. 사용자가 페이지에서 링크만 볼 경우, 각 링크가 어디로 연결되는지에 대한 명확한 설명으로 독립적으로 기능할 수 있습니까?
* **URL 접두사 피하기:** URL을 링크 텍스트로 사용하려는 주소로 사용자를 보내는 경우 링크 텍스트에서 `https:` 및 `www.` 접두사를 삭제하십시오. 예를 들어 `[https://github.com/](https://github.com)`이(가) 아니라 `[github.com](https://github.com)` 입니다. 또는 `[https://github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)`이(가) 아니라 `[github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)` 입니다.

이 세 가지 예에 대해 링크 테스트를 수행해 보십시오. 마지막 항목은 PHP 구성에 대한 정보를 찾는 독자에게 가장 좋습니다. 페이지의 다른 내용을 읽을 필요 없이 링크에서 명확하게 식별할 수 있기 때문입니다.

## 지원 링크 [#support-link]

**지원 이메일 주소에 대한 하이퍼링크를 포함하지 마십시오.** 이는 스팸을 방지하고 고객이 지원 티켓 제출 양식을 사용하여 지원 티켓을 생성하도록 하여 올바른 지원 우선순위를 받을 수 있도록 합니다. 고객에게 지원팀에 문의하라고 안내해야 하는 경우 대신 다음을 사용하십시오:

```md
Get support at [support.newrelic.com](support.newrelic.com).
```

## 앵커 링크 [#hyperlinks-anchor]

링크에 앵커(예: `#inivar-scope`)가 포함된 경우, 해당 링크가 사용하는 완전한 **현재** 문서 경로를 사용하십시오. 일부 브라우저는 리디렉션 시 앵커를 유지하지 않습니다.

앵커 링크에 대한 HTML `id`을(를) 생성하거나 편집할 때 다음 가이드라인을 따르십시오:

* 새로운 ID를 생성할 때는 소문자만 사용하십시오.
* 단어를 구분하려면 하이픈 `-`을 사용하십시오. 밑줄 `_`을 사용하지 마십시오.
* 문서를 재구성할 때 가능한 한 수신 앵커 링크를 유지하도록 노력하십시오. 레벨 2 제목 `##`을(를) 삭제하면 해당 제목에 대한 모든 링크가 끊어지므로 주의하십시오.
* 내부 뉴렐릭 계정에서 해당 앵커 ID로의 트래픽을 모니터링하고 있을 수 있으므로 기존 앵커 ID를 변경하지 마십시오.

## 제품으로의 딥 링크 [#deep-links]

사용자를 제품의 특정 부분으로 안내할 때는 가능한 한 딥 링크를 사용하십시오. 딥 링크는 사용자가 제품으로 이동하도록 유도하며, 아직 계정을 만들지 않은 경우 가입하라는 프롬프트를 표시합니다. 이는 단순히 가입 페이지로 링크하는 것보다 더 효과적입니다. 그러나 UI로의 딥 링크는 때때로만 작동하며 좋은 영구 링크를 찾으려면 약간의 실험이 필요합니다.

다음은 로그 UI를 사용하는 워크플로우의 예입니다:

1. 업무용 계정에서 링크하려는 UI 부분으로 이동하십시오. 자연스럽게 표시되는 전체 URL을 가져오십시오.
2. 시크릿 창을 열고 URL을 붙여넣으십시오.
3. URL을 더 깔끔한 상태로 편집하십시오. 가능한 한 단순한 URL을 원합니다. 로그의 경우 다음과 같습니다: `https://one.newrelic.com/logger`.
4. 뉴렐릭에서 로그인하라는 프롬프트를 표시하므로 업무용이 아닌 이메일로 로그인하십시오.

이 URL은 사용자를 로그 페이지로 보내고 계정 ID 식별 정보를 자동 완성합니다. 해당 페이지는 딥 링크가 가능합니다.

단순 URL이 작동하지 않는 경우 두 가지 추가 단계가 있습니다. 다음은 단순 URL이 작동하지 않는 예시 워크플로우입니다. 다음 URL을 기반으로 작업합니다:

```
https://one.newrelic.com/marketplace/install-data-source?account=[ACCOUNT_ID_HERE]&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
```

1. URL을 찾은 후 시크릿 창을 열고 간단한 URL을 붙여넣으십시오: `https://one.newrelic.com/marketplace/install-data-source`이 페이지는 단순화된 URL로 로드되지 않습니다.

2. 슬러그의 `account=[ACCOUNT_ID_HERE]` 부분을 제거하여 이 URL을 테스트하십시오. 새 URL은 다음과 같습니다:

   ```
   https://one.newrelic.com/marketplace/install-data-source?&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
   ```

3. 새 시크릿 창에 해당 URL을 붙여넣으십시오. 고유한 계정 ID가 채워진 올바른 페이지로 이동합니다.

4. 계정 ID 번호가 제거된 URL을 열도록 하여 이 URL이 작동하는지 다른 작성자와 확인하십시오. 업무용이 아닌 이메일을 사용해야 합니다.

두 경우 모두 URL이 실패하면 제품 UI의 해당 부분은 딥 링크가 불가능할 가능성이 높습니다. 이 경우 `one.newrelic.com`을(를) **모든 기능** 페이지에 링크한 다음 [경로 지정 가이드라인](/docs/style-guide/formatting/ui-paths)에 따라 경로를 설명하십시오.

## 외부 링크 [#hyperlinks-external]

`docs.newrelic.com` 하위 도메인 외부의 웹사이트(`newrelic.com`, `one.newrelic.com`, `discuss.newrelic.com` 포함)에 대한 링크를 생성할 때 문서 사이트는 새 탭에서 링크를 여는 코드를 자동으로 포함합니다.

이 문서의 링크 텍스트 가이드라인 외에도 외부 사이트에 링크할 때 염두에 두어야 할 몇 가지 다른 사항은 다음과 같습니다.

* 링크의 미래를 대비하는 가장 좋은 방법에 대해 생각해 보십시오. 가능한 경우 최상위 도메인을 가리키도록 하되, 링크의 유용성을 떨어뜨리는 경우에는 그렇게 하지 마십시오. 링크하려는 콘텐츠는 얼마나 안정적입니까? URL이 변경될 가능성이 있습니까?
* 링크를 최대한 유용하게 만드십시오. 문서에 어떤 가치를 추가하고자 하십니까? 해당 정보를 다른 방식으로 공유할 수 있습니까?
* 독자가 이 외부 소스에 링크하는 이유를 이해할 수 있도록 도와주십시오. 시간대 목록과 같은 유용한 참조 자료입니까? 찾기 어려운 파일에 직접 링크하는 등 누군가의 시간을 절약할 수 있는 방법입니까?
* 링크에 일반적으로 액세스할 수 있는지 확인하십시오. 비공개 GitHub 리포지터리와 같이 인증이 필요한 외부 사이트로 연결하고 있습니까?
