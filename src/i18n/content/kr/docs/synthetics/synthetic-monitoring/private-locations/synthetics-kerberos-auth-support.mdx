## 요구 사항 및 호환성 [#requirements]

Kerberos 인증은 KDC(Key Distribution Center)에 대한 직접적인 네트워크 액세스, 내부 DNS 확인 및 긴밀하게 동기화된 시계에 의존합니다. 이러한 제약 조건은 실행할 수 있는 위치를 제한하므로 시작하기 전에 다음 요구 사항을 검토하십시오.

다음 환경에서는 Kerberos 인증을 지원합니다:

* 도커 컨테이너 환경에서 신세틱스 작업 관리자를 실행하는 프라이빗 로케이션
* Podman 컨테이너 환경에서 신세틱스 작업 관리자를 실행하는 프라이빗 로케이션

다음 환경에서는 Kerberos 인증을 지원하지 않습니다:

* 내부 KDC로의 네트워크 경로가 없는 공개 위치
* Kubernetes 및 OpenShift 작업 관리자 환경

작업 관리자는 브라우저 모니터 작업에만 Kerberos 자격 증명을 제공합니다. 스크립팅된 API 모니터 및 핑 모니터는 Kerberos 인증 없이 실행됩니다.

각 브라우저 런타임 컨테이너는 자체 Kerberos 지원 티켓을 획득하므로(`kinit`을(를) 통해, Chrome이 출시되기 전에), 프라이빗 로케이션도 다음 요구 사항을 충족해야 합니다:

* 런타임 컨테이너 내부에서 TCP 및 UDP 포트 88을 통해 KDC에 연결하십시오.
* 런타임 컨테이너 내부에서 KDC 및 타겟 애플리케이션 호스트명을 확인하십시오. 도커 배포에서 내부 DNS가 이를 확인하지 못하는 경우, [`RUNTIME_EXTRA_HOSTS`](/docs/synthetics/synthetic-monitoring/private-locations/job-manager-configuration#mtls-docker) (으)로 매핑하십시오 ― 이 변수는 도커 전용입니다. Podman 배포는 내부 DNS에 의존합니다.
* `chrony`과(와) 같은 서비스를 사용하여 프라이빗 로케이션 호스트의 시계를 KDC 시계와 5분 이내로 유지하십시오. 런타임 컨테이너는 호스트의 커널 시계를 공유하므로 호스트를 동기화하는 것으로 충분합니다.

## 1부: Kerberos 테스트 랩 설정(선택 사항) [#host-setup]

<Callout variant="tip">
  1부에서는 작업 관리자 설정을 처음부터 끝까지 검증할 수 있도록 독립적인 Kerberos 영역과 보호된 테스트 애플리케이션을 구축합니다. 이는 프로덕션 경로가 아니며, 뉴렐릭은 사용자의 KDC를 관리하지 않습니다. 이미 Kerberos KDC 또는 Active Directory 도메인을 실행 중인 경우, 관리자로부터 영역 이름, KDC 주소 및 클라이언트 키탭을 가져온 다음 [2부](#sjm-configuration)로 건너뛰십시오.
</Callout>

<CollapserGroup>
  <Collapser id="install-packages" title="1단계: Kerberos 패키지 설치">
    호스트 EC2 인스턴스에 Kerberos KDC 서버 및 관리 도구를 설치하십시오:

    ```bash
    sudo dnf install -y krb5-server krb5-workstation
    ```
  </Collapser>

  <Collapser
    id="system-config"
    title={<>2단계: 시스템 Kerberos 구성(<InlineCode>/etc/krb5.conf</InlineCode>)</>
    }
  >
    realm requests를 KDC로 전달하도록 `/etc/krb5.conf`을(를) 구성하십시오:

    ```bash
    sudo tee /etc/krb5.conf > /dev/null <<'EOF'
    [libdefaults]
        default_realm = <REALM_NAME>
        dns_lookup_realm = false
        dns_lookup_kdc = false
        rdns = false

    [realms]
        <REALM_NAME> = {
            kdc = <EC2_PRIVATE_IP>
            admin_server = <EC2_PRIVATE_IP>
        }

    [domain_realm]
        <EC2_INTERNAL_HOSTNAME> = <REALM_NAME>
    EOF
    ```
  </Collapser>

  <Collapser
    id="kdc-config"
    title={<>3단계: KDC 데몬 구성(<InlineCode>kdc.conf</InlineCode>)</>
    }
  >
    KDC 서비스의 포트 및 암호화 규칙을 정의하십시오:

    ```bash
    sudo tee /var/kerberos/krb5kdc/kdc.conf > /dev/null <<'EOF'
    [kdcdefaults]
        kdc_ports = 88
        kdc_tcp_ports = 88

    [realms]
        <REALM_NAME> = {
            acl_file = /var/kerberos/krb5kdc/kadm5.acl
            dict_file = /usr/share/dict/words
            admin_keytab = /var/kerberos/krb5kdc/kadm5.keytab
            supported_enctypes = aes256-cts-hmac-sha1-96:normal aes128-cts-hmac-sha1-96:normal
        }
    EOF
    ```
  </Collapser>

  <Collapser id="init-db" title="4단계: 마스터 데이터베이스 및 KDC 데몬 초기화">
    데이터베이스를 생성하고 KDC 백그라운드 서비스를 시작하십시오:

    ```bash
    # Create the Kerberos database (assign a master password when prompted)
    sudo kdb5_util create -r <REALM_NAME> -s

    # Grant admin permissions and enable KDC services on system boot
    echo "*/admin@<REALM_NAME> *" | sudo tee /var/kerberos/krb5kdc/kadm5.acl
    sudo systemctl enable --now krb5kdc kadmin
    ```
  </Collapser>

  <Collapser id="keytab-generation" title="5단계: 클라이언트 및 서버 키탭 생성">
    클라이언트(신세틱스 워커)와 타겟 웹 서버 서비스 주체 이름(SPN) 모두에 대한 비대화형 자격 증명을 포함하는 키탭 파일을 생성하십시오:

    ```bash
    mkdir -p /home/ec2-user/kerb-test

    # 1. Create client principal & keytab for synthetics runners
    sudo kadmin.local -q "addprinc -randkey <CLIENT_PRINCIPAL>@<REALM_NAME>"
    sudo kadmin.local -q "ktadd -k <CLIENT_KEYTAB_PATH> <CLIENT_PRINCIPAL>@<REALM_NAME>"
    sudo chmod 644 <CLIENT_KEYTAB_PATH>

    # 2. Create HTTP service principal name (SPN) keytab for the web server
    sudo kadmin.local -q "addprinc -randkey HTTP/<EC2_INTERNAL_HOSTNAME>@<REALM_NAME>"
    sudo kadmin.local -q "ktadd -k /home/ec2-user/kerb-test/http.keytab HTTP/<EC2_INTERNAL_HOSTNAME>@<REALM_NAME>"
    sudo chown 33:33 /home/ec2-user/kerb-test/http.keytab
    sudo chmod 644 /home/ec2-user/kerb-test/http.keytab
    ```

    <Callout variant="important">
      클라이언트 키탭의 파일 모드는 보기보다 덜 중요합니다: 여기서 주요 신뢰 경계는 도커 소켓 액세스입니다 ― SJM 자체는 `-v /var/run/docker.sock:/var/run/docker.sock:rw`을(를) 요구하며, 해당 액세스 권한이 있는 사람은 권한 비트와 관계없이 이미 호스트의 모든 파일을 루트로 읽을 수 있습니다. 위에서 생성한 대로 클라이언트 키탭을 루트 소유로 유지하고 권한을 `644` (으)로 설정하십시오 ― 이는 그룹 읽기 비트를 통해 브라우저 런타임 컨테이너의 실행 ID(UID 2000, GID 0)와 일치합니다. 다른 사용자로 chown하지 마십시오. 그렇게 하면 해당 그룹 일치가 깨지고 액세스가 전적으로 전체 읽기 비트에 의존하게 될 수 있습니다. HTTP 서비스 키탭은 테스트 웹 서버 자체의 ID입니다: 6단계의 컨테이너 내부에서 아파치가 실행되는 UID 및 GID를 부여하고 ― Debian의 `www-data` 사용자인 `33` ― 권한도 `644` (으)로 유지하십시오. 작업 관리자를 설정하는 데 HTTP 키탭은 필요하지 않습니다.
    </Callout>
  </Collapser>

  <Collapser id="deploy-test-container" title="(선택 사항) 6단계: 테스트 웹 컨테이너 배포">
    <Callout variant="tip">
      설정을 검증하기 위해 동일한 호스트에서 테스트 웹 서버를 실행하려는 경우에만 이 단계가 필요합니다. SJM을 구성하는 데는 필요하지 않습니다.
    </Callout>

    `mod_auth_gssapi`(으)로 구성된 아파치 컨테이너를 배포하십시오:

    ```bash
    mkdir -p ~/kerb-test/httpd-image && cd ~/kerb-test/httpd-image

    cat > kerb-test.conf <<'EOF'
    <Location /kerb-test>
        AuthType GSSAPI
        AuthName "Kerberos Login"
        GssapiCredStore keytab:/etc/krb5-http.keytab
        Require valid-user
    </Location>
    EOF

    cat > Dockerfile <<'EOF'
    FROM debian:bookworm-slim
    RUN apt-get update && \
        apt-get install -y --no-install-recommends apache2 libapache2-mod-auth-gssapi krb5-user && \
        a2enmod auth_gssapi && \
        mkdir -p /var/www/html/kerb-test && \
        echo '<h1>Kerberos SSO worked</h1>' > /var/www/html/kerb-test/index.html && \
        rm -rf /var/lib/apt/lists/*
    COPY kerb-test.conf /etc/apache2/conf-enabled/kerb-test.conf
    EXPOSE 80
    CMD ["apache2ctl", "-D", "FOREGROUND"]
    EOF

    docker build -t kerb-test-httpd .

    docker run -d --name kerb-test-httpd \
      -p 8080:80 \
      -v /etc/krb5.conf:/etc/krb5.conf:ro \
      -v /home/ec2-user/kerb-test/http.keytab:/etc/krb5-http.keytab:ro \
      kerb-test-httpd
    ```
  </Collapser>

  <Collapser id="verify-handshake" title="7단계: 로컬 DNS 및 Kerberos 핸드셰이크 확인">
    내부 도메인이 호스트에서 로컬로 해석되는지 확인하고, Kerberos 인증이 성공적으로 완료되는지 확인하십시오:

    ```bash
    # 1. Map internal hostname in /etc/hosts
    echo "<EC2_PRIVATE_IP> <EC2_INTERNAL_HOSTNAME>" | sudo tee -a /etc/hosts

    # 2. Verify unauthenticated challenge returns 401 Unauthorized
    curl -i http://<EC2_INTERNAL_HOSTNAME>:8080/kerb-test/

    # 3. Test ticket acquisition and end-to-end Kerberos SSO
    kinit -kt <CLIENT_KEYTAB_PATH> <CLIENT_PRINCIPAL>@<REALM_NAME>
    curl --negotiate -u : -i http://<EC2_INTERNAL_HOSTNAME>:8080/kerb-test/
    ```

    테스트에 성공하면 `HTTP/1.1 200 OK` (으)로 응답하고 보호된 웹 페이지 콘텐츠를 표시합니다.
  </Collapser>
</CollapserGroup>

## 파트 2: Kerberos용 신세틱스 작업 관리자 구성 [#sjm-configuration]

신세틱스 브라우저 러너 컨테이너가 자동으로 KDC를 확인하고, Kerberos 지원 티켓을 획득하며, 보호된 엔드포인트에 대해 인증할 수 있도록 하려면 작업 관리자를 시작하는 명령에 다음 Kerberos 환경 변수 및 keytab 볼륨 마운트를 추가하십시오.

<Callout variant="caution">
  프라이빗 로케이션에서 Kerberos를 활성화하면 해당 위치의 모든 브라우저 모니터 작업이 키탭 마운트 및 Kerberos 환경 변수를 수신합니다. 작업 관리자는 모니터 또는 URL별로 자격 증명을 필터링하지 않습니다. Chrome은 `KERBEROS_HOST_ALLOWLIST`에만 기반하여 Kerberos 지원 티켓을 수신할 호스트를 결정하므로 해당 허용 목록을 가능한 한 좁게 유지하십시오.
</Callout>

<Callout variant="important">
  4개의 `KERBEROS_*` 변수를 모두 설정하거나 아무것도 설정하지 마십시오. 일부만 설정하면 신세틱스 작업 관리자가 시작되지 않고 불완전한 Kerberos 설정 오류를 로그에 기록합니다.
</Callout>

### 표준 명령(Kerberos 제외) [#standard-sjm-command]

```bash
docker run -e PRIVATE_LOCATION_KEY=<PRIVATE_LOCATION_KEY> \
  -d --restart unless-stopped \
  -v /var/run/docker.sock:/var/run/docker.sock:rw \
  newrelic/synthetics-job-manager
```

### 필수 명령(Kerberos 지원 활성화됨) [#kerberos-sjm-command]

작업 관리자를 시작하기 위해 이미 사용하는 명령에 4개의 `KERBEROS_*` 환경 변수(`-e`) 및 키탭 볼륨 마운트(`-v`)를 추가하십시오.

<CollapserGroup>
  <Collapser id="kerberos-sjm-docker" title="도커">
    ```bash
    docker run -d \
      --name sjm-container \
      --restart unless-stopped \
      -e PRIVATE_LOCATION_KEY=<PRIVATE_LOCATION_KEY> \
      -e KERBEROS_REALM=<REALM_NAME> \
      -e KERBEROS_KDC=<EC2_PRIVATE_IP> \
      -e KERBEROS_HOST_ALLOWLIST=<EC2_INTERNAL_HOSTNAME> \
      -e KERBEROS_KEYTAB_HOST_PATH=<CLIENT_KEYTAB_PATH> \
      -e RUNTIME_EXTRA_HOSTS=<EC2_INTERNAL_HOSTNAME>:<EC2_PRIVATE_IP> \
      -v /var/run/docker.sock:/var/run/docker.sock:rw \
      -v <CLIENT_KEYTAB_PATH>:<CLIENT_KEYTAB_PATH>:ro \
      newrelic/synthetics-job-manager
    ```
  </Collapser>

  <Collapser id="kerberos-sjm-podman" title="포드만">
    [작업 관리자 설치](/docs/synthetics/synthetic-monitoring/private-locations/install-job-manager)의 `podman run` 명령에 동일한 Kerberos 변수 및 keytab 마운트를 추가하십시오. Podman은 도커 소켓을 마운트하는 대신 파드에서 작업 관리자를 실행하므로 기존 `CONTAINER_ENGINE`, `PODMAN_API_SERVICE_PORT` 및 `PODMAN_POD_NAME` 설정을 유지하십시오.

    ```bash
    podman run -d \
      --pod SYNTHETICS \
      --restart unless-stopped \
      -e PRIVATE_LOCATION_KEY=<PRIVATE_LOCATION_KEY> \
      -e CONTAINER_ENGINE=PODMAN \
      -e PODMAN_API_SERVICE_PORT=8000 \
      -e PODMAN_POD_NAME=SYNTHETICS \
      -e KERBEROS_REALM=<REALM_NAME> \
      -e KERBEROS_KDC=<EC2_PRIVATE_IP> \
      -e KERBEROS_HOST_ALLOWLIST=<EC2_INTERNAL_HOSTNAME> \
      -e KERBEROS_KEYTAB_HOST_PATH=<CLIENT_KEYTAB_PATH> \
      -v <CLIENT_KEYTAB_PATH>:<CLIENT_KEYTAB_PATH>:ro,Z \
      newrelic/synthetics-job-manager
    ```

    <Callout variant="tip">
      SELinux 호스트에서 컨테이너가 키탭을 읽을 수 있도록 레이블 재지정 플래그를 추가하십시오. 작업 관리자와 작업 관리자가 출시하는 모든 브라우저 런타임 컨테이너는 동일한 파드(`PODMAN_POD_NAME`) 내에서 실행되며, Podman은 파드의 모든 컨테이너에서 하나의 SELinux 레이블을 공유합니다 ― 따라서 여러 컨테이너가 키탭을 읽더라도 여기서는 `:ro,Z`이(가) 작동합니다. 키탭을 이 파드 외부의 컨테이너와 공유할 필요가 없으므로 `:ro,Z` 대신 `:Z`을(를) 사용하십시오. 자세한 내용은 [Podman 볼륨 문서](https://docs.podman.io/en/latest/markdown/podman-run.1.html#volume-v-source-volume-host-dir-container-dir-options)를 참조하십시오.
    </Callout>
  </Collapser>
</CollapserGroup>

## 3부: Kerberos 인증 문제 해결 [#troubleshooting]

런타임 컨테이너 내부에서 Kerberos 초기화가 실패하더라도, 컨테이너의 시작 파이프라인은 여전히 브라우저를 출시하고 모니터를 실행합니다. 그런 다음 모니터는 HTTP 401 챌린지 또는 탐색 시간 초과와 함께 보호된 엔드포인트에 대해 실패하며, 결과에 `KerberosInitWarning` 근본 원인으로 태그를 지정합니다. 실패가 일반적인 시간 초과처럼 보이기 때문에, 모니터 스크립트를 조사하기 전에 작업 로그에서 다음 오류 코드를 확인하십시오.

이 코드는 [2부](#sjm-configuration)의 시작 유효성 검사와 별개입니다 ― `KERBEROS_*` 변수 중 일부만 설정하면 작업 관리자가 아예 시작되지 않으며, 이러한 코드는 작업의 로그에 전혀 나타나지 않습니다.
