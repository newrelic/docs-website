<Callout variant="important" title="청구">
  Collector 옵저버빌리티 사용은 귀하의 계정에 연결된 가격 모델 및 아래에 정의된 내용에 따라 주문에 의거하여 미리보기 기간 동안 요금이 부과됩니다.

  이 기능과 관련된 비용은 귀하의 계정에 적용된 가격 모델에 따라 다음과 같은 요소에 의해 결정됩니다.

  **코어 컴퓨트**: 코어 CCU로 측정되는 요약 페이지는 프리뷰 기간 동안 요금이 청구됩니다.

  **데이터 수집**: 내부 텔레메트리에서 추가되는 데이터(GB 단위)는 미리 보기 기간 동안 요금이 부과됩니다.

  이 기능이 일반 사용자에게 제공될 경우, 사용료는 주문 내용에 따라 청구됩니다.
</Callout>

## 단계별 설정

<Steps>
  <Step>
    ### 설정 파일 다운로드 [#download-config]

    기본적으로 수집기는 [내부 텔레메트리를](https://opentelemetry.io/docs/collector/internal-telemetry/) 내보내지 않으므로 먼저 활성화해야 합니다.

    ```bash
    curl 'https://raw.githubusercontent.com/newrelic/nrdot-collector-releases/refs/heads/main/examples/internal-telemetry-config.yaml' \
      --silent --output internal-telemetry-config.yaml
    ```
  </Step>

  <Step>
    ### 환경 변수 설정 [#set-env-vars]

    * <DNT>`INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY`</DNT>: 내부 텔메트리 계정에 대한 Ingest 키가 전송되어야 합니다. 이 키는 수집기가 뉴렐릭에게 일반 데이터를 보낼 때 사용하는 키(예: 아래 예시의 <DNT>`NEW_RELIC_LICENSE_KEY`</DNT> 와 다를 수 있습니다.
    * <DNT>`INTERNAL_TELEMETRY_SERVICE_NAME`</DNT>: 기본값은 `otel-collector` 이며, 편집 이름을 뉴렐릭으로 결정합니다.
    * <DNT>`INTERNAL_TELEMETRY_OTLP_ENDPOINT`</DNT>: US `https://otlp.nr-data.net`이(가) 기본값입니다, EU에 있는 경우 이를 `https://otlp.eu01.nr-data.net`(으)로 설정하고, JP에 있는 경우 이를 다음으로 설정합니다 `https://otlp.jp.nr-data.net`
  </Step>

  <Step>
    ### 병합된 설정으로 수집기 실행 [#run-collector]

    구성 요소 및 파이프라인에 대한 일반 설정(다음 예 `--config=/etc/nrdot-collector/config.yaml`) 외에도 두 설정을 병합하는 두 번째 인수 `--config` 를 추가합니다.

    ```bash
    docker run \
      -e INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY='...' \
      -e NEW_RELIC_LICENSE_KEY='...' \
      -e INTERNAL_TELEMETRY_SERVICE_NAME='demo-collector' \
      -v './internal-telemetry-config.yaml:/etc/nrdot-collector/config-internal.yaml' \
      newrelic/nrdot-collector:2.5.0 --config=/etc/nrdot-collector/config.yaml \
      --config='/etc/nrdot-collector/config-internal.yaml'
    ```

    <Callout variant="important">
      `service::telemetry` 노드 아래에 기존 설정이 있는 경우 `--config` 인수의 순서가 중요합니다. 수집기는 설정과 구성의 특정 부분(예: 리스트, 리프 노드)는 병합할 수 없으므로 마지막 `--config` 인수로 덮어쓰여집니다.
    </Callout>
  </Step>

  <Step>
    ### 엔티티 태그 추가 [#add-tag]

    태그 <DNT>`newrelic.service.type: otel_collector`</DNT> 은 UI 수준에서 해당 경험에 대한 선택적 참여 역할을 합니다. 다음 옵션 중 하나를 선택하십시오.

    * **옵션 1**: 위에서 제공된 예시 설정(옵션 2의 설정이 포함되어 있음)을 사용합니다.
    * **옵션 2**: 수집기에 인수 <DNT>`--config=yaml:service::telemetry::resource::newrelic.service.type: otel_collector`</DNT> 을 추가합니다. 그러면 속성이 리소스 속성으로 추가되고 뉴렐릭은 수집 시 태그를 수행합니다. 이 옵션을 제거하면 태그가 만료되는 데 하루가 걸립니다.
    * **옵션 3**: APM UI를 통해 태그를 추가합니다(페이지 상단, 엔티티 이름 옆). UI를 통해서도 이 설정을 제거하여 다시 원래대로 되돌릴 수 있습니다.

    태그가 지정되면 [UI에서 수집기 보기](/docs/opentelemetry/collector-observability/collector-observability#view-ui)를 참조하여 수집기의 데이터를 탐색하십시오.
  </Step>

  <Step>
    ### 선택 사항: 설정을 사용자 지정하십시오. [#customize]

    기본 설정에서는 세부 수준 및 샘플링과 같은 일반적인 옵션을 조정하기 위해 `INTERNAL_TELEMETRY_...` 형식의 추가 환경 변수를 노출합니다. 자세한 내용은 [해당 설정 파일](https://github.com/newrelic/nrdot-collector-releases/blob/main/examples/internal-telemetry-config.yaml) 을 참조하십시오.

    수집기를 모니터하기 위해 기본 설정을 사용하는 것을 권장합니다. 하지만 세부 수준, 샘플링 또는 데이터 수집 속도를 줄이는 등 필요에 맞게 예제 설정을 수정할 수 있습니다. 자세한 내용은 [공식 문서](https://opentelemetry.io/docs/collector/internal-telemetry/)를 참조하십시오. 설정을 변경하면 UI의 특정 부분에 데이터가 표시되지 않을 수 있다는 점을 유의하십시오. 또한 [제한 사항](/docs/opentelemetry/collector-observability/collector-observability#limitations)을 참조하십시오. 수집기의 내부 텔레메트리 설정 옵션은 OTel 커뮤니티가 발전함에 따라 변경됩니다. 제공된 기본값 사용 여부를 포함하여 설정을 완벽하게 제어할 수 있습니다.
  </Step>
</Steps>

## 간접비 고려 사항 [#overhead]

모든 텔레메트리와 마찬가지로 수집기의 내부 텔레메트리는 데이터 수집을 증가시킵니다. 오버헤드는 워크로드와 설정에 따라 다릅니다. 고려해야 할 주요 요소는 다음과 같습니다.

**메트릭은** 처리량과 관계없이 수집기 및 모든 활성 구성 요소에 지속적인 오버헤드를 발생시킵니다. 알림은 일정한 간격(기본값 60초)으로 전송됩니다. 모든 구성 요소는 각각의 [메타데이터.yaml](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/filterprocessor/metadata.yaml#L20) 에 표시된 대로 맞춤 지표를 내보낼 수 있습니다. 이는 간접비용을 증가시킬 수 있습니다.

수집기가 방출하는 철의 양을 줄여야 하는 경우 철 레벨을 <DNT>`normal`</DNT> 으로 설정하는 것이 좋습니다. 예를 들어 예제 구성의 환경 변수 <DNT>`INTERNAL_TELEMETRY_METRICS_LEVEL`</DNT> 통해 UI에서 <DNT>`detailed`</DNT> 메트릭의 하위 집합만 사용되며 일반적으로 성능 또는 네트워크 문제를 미세 조정하기 위한 메트릭이므로 필요에 따라 다시 활성화할 수 있습니다.

**로그는** 정상 작동에 미치는 영향이 미미합니다. 오류 로그가 급격히 증가할 경우 오버헤드가 높아질 수 있지만, 기본적으로 로그 샘플링이 이루어지기 때문에 이러한 오버헤드는 줄어듭니다. 샘플링 알고리즘은 정의된 간격마다 일정한 수의 로그를 확보한 후 고정된 속도로 샘플링합니다. [서비스::텔레메트리::로그::샘플링을](https://github.com/newrelic/nrdot-collector-releases/blob/main/examples/internal-telemetry-config.yaml) 참조하십시오.

**트레이는** 기본적으로 비활성화되어 있습니다. 이유는 다음과 같습니다.

* 트레이스의 성숙도가 제한되어 있습니다. 모든 구성 요소가 계측된 것은 아닙니다. 이 [GitHub 이슈를](https://github.com/open-telemetry/opentelemetry-collector/issues/8804) 참조하세요.
* 업스트림 에이전트 및 수집기의 워크로드 및 배치 설정에 따라 달라지는 예측할 수 없는 오버헤드입니다.
* 적응형 샘플링 알고리즘을 사용할 수 없습니다. 이로 인해 특정 사용 사례에서 예상치 못한 비용 발생 위험 없이 보편적인 샘플링 권장 사항을 제시하는 것이 불가능해집니다.

트랜스가 더욱 성숙해지면, 트랜스는 데이터 수집기가 구성 요소 수준에서 데이터를 처리하는 데 얼마나 많은 시간을 소비하는지에 대한 귀중한 정보를 제공할 것입니다. 트레이스가 개발되는 동안 실험하려면 <DNT>`INTERNAL_TELEMETRY_TRACE_LEVEL=info`</DNT> 설정하고 수집량을 모니터링하면서 <DNT>`INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO=0.001`</DNT> (0.1%)과 같은 낮은 샘플링 속도로 시작하세요.

## 설정 예 [#examples]

이 섹션에서는 위의 단계별 가이드가 수집기와 관련된 다양한 사용 사례에 어떻게 적용되는지 예시를 보여줍니다.

### 내부 텔레메트리가 활성화된 단순 수집기

docker Compose를 사용하여 수집기를 실행하는 [최소한의 예제입니다](https://github.com/newrelic/newrelic-opentelemetry-examples/tree/main/other-examples/collector/internal-telemetry).

### 인프라 관계 입력 (선택 사항, 실험적 기능)

[요약 페이지](/docs/opentelemetry/collector-observability/collector-observability#summary-page)에서 언급했듯이, APM은 수집기가 실행 중인 인프라에 대한 인프라 메트릭을 표시할 수 있지만, 이는 인프라가 계측되고 [관계](https://docs.newrelic.com/docs/new-relic-solutions/new-relic-one/core-concepts/what-entity-new-relic/#related-entities)가 형성될 수 있는 경우에만 가능합니다. 이 관계는 수집기의 내부 텔레메트리에 있는 추가 속성에 의해 결정됩니다. 이 주제에 대한 자세한 내용은 [OTel 문서](https://docs.newrelic.com/docs/opentelemetry/best-practices/opentelemetry-best-practices-resources/#service-to-infra-otel-collector)를 확인하십시오. 이를 설정하는 단계는 정확한 인프라에 따라 크게 달라집니다. 일반적으로 선택하는 Kubernetes의 경우,[당사의 Kubernetes용 OTel 솔루션](https://docs.newrelic.com/docs/kubernetes-pixie/k8s-otel/intro/) 을 기반으로 컨테이너-서비스 관계를 형성하는 방법을 [보여주는 예제 를 만들었습니다.](https://github.com/newrelic/newrelic-opentelemetry-examples/tree/main/other-examples/collector/internal-telemetry-k8s-container-relationships)
