NGINX 1.25.3 및 이후 버전에는 웹 서버에 직접 분산 추적 지원을 추가하는 네이티브 OpenTelemetry 모듈인 [`ngx_otel_module`](https://nginx.org/en/docs/ngx_otel_module.html)이(가) 포함되어 있습니다.

`ngx_otel_module`을(를) 계측된 애플리케이션과 결합하면, 뉴렐릭은 트레이스를 엔드투엔드로 연결하고 서비스와 NGINX 엔티티 간에 [서비스 관계](/docs/new-relic-solutions/new-relic-one/ui-data/service-maps/service-maps/)를 생성합니다. 이러한 관계는 [서비스 맵](/docs/new-relic-solutions/new-relic-one/ui-data/service-maps/service-maps/)에 표시되어, 트래픽이 웹 서버 또는 리버스 프록시를 통해 어떻게 흐르는지 파악할 수 있는 가시성을 제공합니다.

## 작동 원리 [#how-it-works]

일반적인 설정에서 트래픽은 다음과 같이 흐릅니다:

```
Instrumented app (client) → NGINX (with ngx_otel_module) → Instrumented app (backend)
```

1. 클라이언트 애플리케이션은 [W3C](https://www.w3.org/TR/trace-context/) `traceparent` 헤더와 함께 요청을 보냅니다.
2. NGINX의 `ngx_otel_module`은(는) 트레이스 컨텍스트를 추출하고, 요청에 대한 스팬을 생성하며, 업스트림 백앤드로 프록시된 요청에 업데이트된 트레이스 컨텍스트를 주입합니다.
3. 백앤드 애플리케이션은 전파된 트레이스 컨텍스트와 함께 요청을 수신하고 트레이스를 계속합니다.
4. 모든 스팬(클라이언트, NGINX 및 백앤드에서 발생)은 OpenTelemetry Collector로 내보내지며, 이 Collector는 NGINX 스팬에 NGINX ID를 추가하여 뉴렐릭으로 전달합니다.

뉴렐릭은 이러한 연결된 스팬을 사용하여 CALLS 관계를 생성합니다:

* **클라이언트 서비스**가 **NGINX 엔티티**를 호출합니다.
* **NGINX 엔티티** 호출 **백앤드 서비스**

수집기가 NGINX 메트릭이 사용하는 것과 동일한 `nginx.deployment.name` 및 `nginx.server.endpoint` ID를 스탬프 처리하므로, NGINX 스팬은 NGINX 메트릭과 **동일한** `NGINXSERVER` 엔티티로 확인됩니다. 이러한 관계는 [서비스 맵](/docs/new-relic-solutions/new-relic-one/ui-data/service-maps/service-maps/) 및 [맵 환경](/docs/service-architecture-intelligence/maps/advanced-maps/)에서 확인할 수 있습니다.

## 호환성 [#compatibility]

`ngx_otel_module` 다음을 포함하여 W3C Trace Context 전파를 지원하는 모든 애플리케이션과 작동합니다:

* **OpenTelemetry SDK**로 계측된 애플리케이션(모든 언어)
* **OpenTelemetry 자동 계측** (자바, .NET, 파이썬, Node.js, Go)
* **뉴렐릭 APM 에이전트** (Go, 자바, .NET, Node.js, 파이썬, 루비, PHP) 중 [분산 추적](/docs/distributed-tracing/enable-configure/overview-enable-distributed-tracing/)이 활성화된 에이전트

계측 방식을 혼합할 수 있습니다. 예를 들어, OTel SDK 클라이언트가 NGINX를 통해 뉴렐릭 APM 에이전트 백앤드를 호출할 수 있으며, 관계 체인이 뉴렐릭에 올바르게 표시됩니다.

## 시작하기 전에 [#prerequisites]

다음 사항을 확인하십시오:

* 유효한 뉴렐릭 [클러스터](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key)
* `ngx_otel_module`을(를) 사용할 수 있는 **NGINX 1.25.3 이상**. 이 모듈은 [공식 NGINX 패키지 저장소](https://nginx.org/en/linux_packages.html)에서 사전 빌드된 동적 모듈(`nginx-module-otel`)로 제공되며, 설치에 대한 자세한 내용은 [`ngx_otel_module` 문서](https://nginx.org/en/docs/ngx_otel_module.html)를 참조하십시오.
* 동일한 호스트에서 실행되거나 NGINX 호스트에서 액세스할 수 있는 **OpenTelemetry Collector** ([NRDOT](https://github.com/newrelic/nrdot-collector-releases) 또는 [OTel Collector Contrib](https://github.com/open-telemetry/opentelemetry-collector-releases/releases/latest))
* 위에 나열된 호환 가능한 계측 접근 방식 중 하나를 사용하여 NGINX를 통해 requests를 보내는 **계측된 애플리케이션**
* 수집기에서 뉴렐릭 [OTLP 엔드포인트](/docs/opentelemetry/best-practices/opentelemetry-otlp/#configure-endpoint-port-protocol)로의 네트워크 액세스

<Callout variant="tip">
  이 가이드는 단일 OTel Collector에서 메트릭 수집과 분산 추적을 모두 설정합니다. 메트릭 전용 설정 또는 Kubernetes 배포의 경우 [자체 호스팅 NGINX 모니터](/docs/opentelemetry/integrations/nginx/nginx-otel-host/) 및 [Kubernetes의 NGINX 모니터](/docs/opentelemetry/integrations/nginx/nginx-otel-kubernetes/)를 참조하십시오.
</Callout>

## 분산 추적 설정 [#setup]

<Callout variant="tip">
  아래의 트레이스 파이프라인은 분산 추적에 참여하는 모든 서비스에 사용할 수 있는 동일한 표준 설정입니다. 수동 관계 설정이 아닙니다. 추적이 활성화되면 뉴렐릭은 연결된 스팬을 자동으로 감지하고 서비스 관계를 생성합니다.
</Callout>

<CollapserGroup>
  <Collapser id="step1-nginx-config" title="1단계: NGINX에서 ngx_otel_module 설정">
    모듈을 로드하고 `nginx.conf`에서 추적을 활성화하십시오. 최상위 수준(기본 컨텍스트)에 `load_module` 지시문을 추가하고 `http` 컨텍스트 내에 OpenTelemetry 지시문을 추가하십시오:

    ```nginx
    # Main context — load the dynamic module
    load_module modules/ngx_otel_module.so;

    http {
        # Export spans to the OpenTelemetry Collector over OTLP/gRPC
        otel_exporter {
            endpoint localhost:4317;
        }

        # A name that identifies this NGINX instance in traces
        otel_service_name nginx-server;

        # Emit a span per request and propagate W3C trace context to upstreams
        otel_trace on;
        otel_trace_context propagate;

        server {
            listen 80;

            location / {
                proxy_pass http://backend_app;
            }
        }
    }
    ```

    이 설정:

    * OpenTelemetry 모듈(`load_module`)을 **로드합니다**.
    * OTLP/gRPC를 통해 `localhost:4317` (`otel_exporter`)에서 수신 대기 중인 수집기로 스팬을 **내보냅니다**.
    * 모든 요청(`otel_trace on`)에 대해 **스팬을 생성합니다**. 처리량이 많은 환경에서 트래픽의 하위 집합을 트레이스하려면 `on` 대신 `otel_trace`을(를) 변수(예: [`split_clients`](https://nginx.org/en/docs/http/ngx_http_split_clients_module.html)에 의해 구동됨)로 설정하십시오.
    * **전파** 트레이스 컨텍스트(`otel_trace_context propagate`): 이는 수신되는 `traceparent` 헤더를 *추출* (NGINX 스팬을 호출 서비스에 연결)하고 업데이트된 컨텍스트를 업스트림으로 전송된 requests에 *주입* (다운스트림 서비스가 트레이스를 계속할 수 있도록 함)합니다.

    특정 가상 호스트나 라우트만 트레이스하려는 경우 `otel_trace on` 및 `otel_trace_context` 지시문을 `server` 또는 `location` 블록별로 설정할 수도 있습니다.

    전체 지시문 참조는 [`ngx_otel_module` 문서](https://nginx.org/en/docs/ngx_otel_module.html)를 참조하십시오.
  </Collapser>

  <Collapser id="step2-collector" title="2단계: OTel Collector 설정">
    `ngx_otel_module`에서 트레이스를 수신하고 NGINX 스텁 상태 엔드포인트에서 메트릭을 수신하도록 OTel Collector를 설정하고, 두 가지 모두 NGINX ID로 보강하여 뉴렐릭으로 전달하십시오.

    ```yaml
    receivers:
      # Receives spans from ngx_otel_module (NGINX → localhost:4317)
      otlp:
        protocols:
          grpc:
            endpoint: "0.0.0.0:4317"
          http:
            endpoint: "0.0.0.0:4318"
      # Collects NGINX metrics from the stub status endpoint
      nginx:
        endpoint: <YOUR_STUB_STATUS_ENDPOINT>  # e.g. http://127.0.0.1/status
        collection_interval: 30s

    processors:
      resourcedetection:
        detectors: [system]
        system:
          resource_attributes:
            host.id:
              enabled: true

      # Adds the NGINX identity so spans and metrics resolve to the SAME NGINXSERVER entity
      resource/nginx:
        attributes:
          - key: nginx.server.endpoint
            value: "<YOUR_STUB_STATUS_ENDPOINT>"  # must match the nginx receiver endpoint
            action: upsert
          - key: nginx.deployment.name
            value: "<YOUR_DEPLOYMENT_NAME>"        # a stable name for this NGINX deployment
            action: upsert

      # Sets nginx.display.name for the metrics pipeline
      transform/nginx_metrics:
        metric_statements:
          - context: resource
            statements:
              - set(attributes["nginx.display.name"], Concat(["server", attributes["nginx.deployment.name"]], ":"))

      # Same display-name stamp for the traces pipeline — ngx_otel_module spans carry no
      # NGINX identity by default; resource/nginx adds the endpoint + deployment name, and
      # this adds nginx.display.name, so the spans resolve to the NGINXSERVER entity.
      transform/nginx_traces:
        trace_statements:
          - context: resource
            statements:
              - set(attributes["nginx.display.name"], Concat(["server", attributes["nginx.deployment.name"]], ":"))

      batch:

    exporters:
      otlp_http:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          api-key: ${env:NEW_RELIC_LICENSE_KEY}

    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [resourcedetection, resource/nginx, transform/nginx_traces, batch]
          exporters: [otlp_http]
        metrics/nginx:
          receivers: [nginx]
          processors: [resourcedetection, resource/nginx, transform/nginx_metrics, batch]
          exporters: [otlp_http]
    ```

    이 수집기 설정에는 두 개의 파이프라인이 포함됩니다:

    * **트레이스 파이프라인**: gRPC(포트 4317) 또는 HTTP(포트 4318)를 통해 `ngx_otel_module` 및 계측된 애플리케이션에서 OTLP 트레이스 데이터를 수신합니다. 이는 OTLP 데이터를 뉴렐릭으로 전송하는 모든 서비스에 사용하는 것과 동일한 표준 트레이스 파이프라인입니다.
    * **메트릭 파이프라인**: [`nginxreceiver`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/nginxreceiver)을(를) 사용하여 NGINX 스텁 상태 엔드포인트에서 성능 메트릭(연결, requests)을 수집합니다. 이러한 메트릭은 골든 메트릭과 함께 뉴렐릭에 NGINX 엔티티를 생성합니다.

    두 파이프라인 모두 다음 프로세서를 공유합니다:

    * **`resourcedetection`**: OpenTelemetry 에코시스템 전반에서 호스트를 식별하는 데 사용되는 표준 리소스 속성인 `host.id`을(를) 추가합니다.
    * **`resource/nginx`**: `nginx.server.endpoint` 및 `nginx.deployment.name`를 추가합니다. 이 두 속성은 NGINX 엔티티의 식별자를 형성합니다. 이를 두 파이프라인 모두에 적용하면 NGINX 스팬과 메트릭이 중복 서비스 엔티티 대신 동일한 `NGINXSERVER` 엔티티로 확인됩니다.
    * **`transform/nginx_*`**: 친숙한 엔티티 이름을 위해 `nginx.display.name`을(를) 추가합니다.

    <Callout variant="important">
      `resource/nginx`의 `nginx.server.endpoint` 값과 `nginx` 수신기 `endpoint`은(는) 동일해야 합니다. `nginx.deployment.name`와(과) 함께 `NGINXSERVER` 엔티티의 ID를 형성합니다. 이는 NGINX 인스턴스당 일회성 정적 값입니다. 백앤드 및 클라이언트 애플리케이션을 추가하거나 제거할 때 수집기 설정을 변경할 필요가 없습니다. 트레이스 컨텍스트 전파를 통해 관계가 자동으로 형성됩니다.
    </Callout>

    필요한 환경 변수를 설정하고 수집기를 시작(또는 다시 시작)하십시오:

    ```bash
    export NEW_RELIC_LICENSE_KEY="<YOUR_LICENSE_KEY>"
    export OTEL_EXPORTER_OTLP_ENDPOINT="<YOUR_NEWRELIC_OTLP_ENDPOINT>"

    sudo systemctl restart nrdot-collector
    ```

    `<YOUR_LICENSE_KEY>`을(를) <InlinePopover type="licenseKey" />(으)로 교체합니다. OTLP 엔드포인트의 경우 [뉴렐릭 OTLP 엔드포인트 설정](/docs/opentelemetry/best-practices/opentelemetry-otlp/#configure-endpoint-port-protocol)을 참조하십시오.
  </Collapser>

  <Collapser id="step3-restart" title="3단계: NGINX 다시 로드 및 확인">
    설정을 테스트하고 NGINX를 다시 로드하여 OpenTelemetry 모듈을 로드하십시오:

    ```bash
    sudo nginx -t
    sudo systemctl reload nginx
    ```

    <Callout variant="important">
      `load_module` 지시문은 `ngx_otel_module.so` 파일이 지정된 경로에 존재하고 NGINX 버전과 일치해야 합니다. `unknown directive "otel_exporter"` 또는 모듈 로드 오류가 표시되면 모듈이 설치되지 않았거나 로드되지 않은 것입니다. NGINX 버전에 맞는 `nginx-module-otel` 패키지를 설치하고 `load_module` 경로를 확인하십시오.
    </Callout>

    NGINX와 수집기가 실행되면 계측된 애플리케이션을 통해 트래픽을 생성하십시오. 몇 분 후 뉴렐릭에 데이터가 도착하는지 확인하십시오:

    ```sql
    -- Verify NGINX trace spans
    FROM Span SELECT count(*)
    WHERE nginx.deployment.name = '<YOUR_DEPLOYMENT_NAME>'
    SINCE 10 minutes ago

    -- Verify NGINX metrics
    FROM Metric SELECT count(*)
    WHERE metricName LIKE 'nginx.%'
    SINCE 10 minutes ago
    ```
  </Collapser>

  <Collapser id="step4-relationships" title="4단계: 서비스 관계 보기">
    트레이스 데이터가 흐르기 시작하면 뉴렐릭은 서비스와 NGINX 엔티티 간에 CALLS 관계를 자동으로 생성합니다. 관계가 나타나려면 최대 10분이 걸릴 수 있습니다.

    관계를 보려면 다음을 수행하십시오:

    1. <DNT>**[one.newrelic.com &gt; All capabilities](https://one.newrelic.com/all-capabilities) &gt; All entities**</DNT> 으)로 이동합니다.
    2. NGINX 엔티티 또는 계측된 서비스 중 하나를 검색하십시오.
    3. 엔티티를 선택하여 요약 페이지를 여십시오.
    4. 엔티티 관계 그래프를 보려면 <DNT>**Service map**</DNT>을(를) 클릭하십시오.

    클라이언트 서비스가 NGINX에 연결되고 NGINX가 백앤드 서비스에 연결된 것을 볼 수 있습니다:

    ```
    [Client app] → CALLS → [NGINX] → CALLS → [Backend app]
    ```

    또한 NRQL로 관계를 쿼리할 수 있습니다:

    ```sql
    FROM Relationship SELECT *
    WHERE source.entityName = '<YOUR_NGINX_DISPLAY_NAME>'
      OR target.entityName = '<YOUR_NGINX_DISPLAY_NAME>'
    SINCE 1 day ago
    ```
  </Collapser>
</CollapserGroup>

## 문제점 해결 [#troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-no-spans" title="뉴렐릭에 NGINX 스팬이 나타나지 않습니다.">
    * NGINX가 오류 없이 다시 로드되었는지 확인하십시오: `sudo nginx -t` 및 `sudo journalctl -u nginx -n 50 --no-pager`
    * `ngx_otel_module`이(가) 로드되었는지 확인하십시오. `unknown directive "otel_exporter"` 오류는 모듈이 로드되지 않았음을 의미합니다. `load_module` 경로를 확인하고 NGINX 버전에 맞는 `nginx-module-otel`이(가) 설치되어 있는지 확인하십시오.
    * OTel Collector가 실행 중이고 `otel_exporter`의 포트에서 수신 대기 중인지 확인하십시오: `sudo ss -tlnp | grep 4317`
    * 수집기 로그에서 오류 확인: `sudo journalctl -u nrdot-collector -n 50 --no-pager`
    * `otel_exporter` 엔드포인트가 수집기의 gRPC 리스너 주소와 일치하는지 확인하십시오.
  </Collapser>

  <Collapser id="troubleshoot-no-relationships" title="스팬은 나타나지만 관계가 형성되지 않습니다">
    * 첫 번째 스팬이 도착한 후 관계가 나타나려면 최대 10분이 걸립니다.

    * 계측된 애플리케이션이 수집기를 통해 트레이스를 전송하고 있는지 확인하십시오. 관계가 형성되려면 NGINX 스팬과 애플리케이션 스팬이 모두 뉴렐릭에 도달해야 합니다.

    * 클라이언트 애플리케이션이 W3C `traceparent` 헤더를 전파하는지 확인하십시오. 트레이스 컨텍스트 전파가 없으면 NGINX 스팬이 호출 서비스에 연결되지 않습니다.

    * `resourcedetection` 및 `resource/nginx` 프로세서가 모두 수집기 트레이스 파이프라인에 포함되어 있는지 확인하십시오. NGINX 스팬이 NGINXSERVER 엔티티로 확인되려면 `nginx.server.endpoint` 및 `nginx.deployment.name` 속성이 필요합니다.

    * `otel_trace_context propagate`이(가) 설정되어 있는지 확인하십시오(`extract` 또는 `inject`만 설정된 것이 아님). NGINX를 통한 엔드투엔드 컨텍스트 흐름에는 `propagate`이(가) 필요합니다.

    * NGINX와 애플리케이션 스팬이 모두 트레이스 ID를 공유하는지 확인하기 위한 쿼리:

      ```sql
      FROM Span SELECT uniques(service.name)
      WHERE trace.id IN (
        SELECT uniques(trace.id) FROM Span
        WHERE nginx.deployment.name = '<YOUR_DEPLOYMENT_NAME>'
        SINCE 10 minutes ago LIMIT 5
      )
      SINCE 10 minutes ago
      ```

      애플리케이션 서비스 이름과 함께 NGINX 서비스가 표시되어야 합니다.
  </Collapser>

  <Collapser id="troubleshoot-duplicate-entity" title="NGINX는 NGINXSERVER 엔티티 대신 별도의 서비스로 나타납니다">
    * `resource/nginx` 프로세서가 **트레이스** 파이프라인(메트릭 파이프라인뿐만 아니라)에서 실행되는지 확인하십시오. 이것이 없으면 NGINX 스팬에 `nginx.deployment.name` / `nginx.server.endpoint`이(가) 부족하여 NGINXSERVER 엔티티로 확인되지 않고 일반 서비스로 합성됩니다.
    * `nginx` 수신기와 `resource/nginx` 프로세서에서 `nginx.server.endpoint` 값이 **동일한지** 확인하고, `nginx.deployment.name`이(가) NGINX 메트릭에서 사용되는 값과 일치하는지 확인하십시오. 엔티티 식별자는 이 두 값의 조합입니다. 일치하지 않으면 다른 엔티티가 생성됩니다.
    * 메트릭 파이프라인도 실행하십시오. NGINXSERVER 엔티티의 골든 메트릭은 `nginxreceiver`에서 가져오며, 이 항목이 없으면 NGINX는 여전히 트레이스를 통해 나타나지만 메트릭은 없습니다.
  </Collapser>

  <Collapser id="troubleshoot-partial-relationships" title="일부 관계는 나타나지만 전부는 아님">
    * 모든 서비스의 스팬 데이터가 동일한 계정에 도달하도록 각 계측된 애플리케이션은 동일한 OTel Collector를 통해(또는 뉴렐릭으로 직접) 트레이스를 전송해야 합니다.
    * 뉴렐릭 APM 에이전트를 사용하는 애플리케이션의 경우 [분산 추적](/docs/distributed-tracing/enable-configure/overview-enable-distributed-tracing/)이 활성화되어 있고 에이전트가 연결되어 있는지 확인하십시오.
    * OTel SDK 애플리케이션의 경우 OTLP 익스포터가 수집기로 전송하도록 설정되어 있는지 확인하십시오.
    * 추가 시간을 두십시오. 트래픽 양이 적은 서비스의 관계는 나타나는 데 시간이 더 오래 걸릴 수 있습니다.
  </Collapser>
</CollapserGroup>
