## 쓰기 문에 대한 쿼리 계획 [#query]

`explain_mode`을(를) `procedure` (으)로 설정하면 모니터링 사용자에게 DML 권한을 부여하지 않고도 NRDOT Collector가 쓰기 문에 대한 `EXPLAIN` 계획을 수집할 수 있습니다. 설정 시 수신기는 이름이 `<schema>.explain_statement`인 `SQL SECURITY DEFINER` 프로시저를 검색합니다. 해당 프로시저가 존재하지 않거나 모니터링 사용자에게 실행 권한이 없는 경우 수신기는 `inline` 모드로 대체됩니다. 이 상태에서는 쓰기 문이 쿼리 계획을 수집하지 못하며, 수집기 로그에 다음 경고가 표시됩니다: `unable to execute explain statement`.

`explain_mode`을(를) `procedure`(으)로 설정하려면, 스키마당 한 번씩 권한이 있는 계정(예: `root`)으로 다음을 실행하십시오:

```sql
DELIMITER //
CREATE DEFINER = 'root'@'%' PROCEDURE <YOUR_SCHEMA>.explain_statement(IN q TEXT)
SQL SECURITY DEFINER
BEGIN
  SET @nr_explain_sql = CONCAT('EXPLAIN FORMAT=JSON ', q);
  PREPARE nr_explain_stmt FROM @nr_explain_sql;
  EXECUTE nr_explain_stmt;
  DEALLOCATE PREPARE nr_explain_stmt;
END//
DELIMITER ;
GRANT EXECUTE ON PROCEDURE <YOUR_SCHEMA>.explain_statement TO '<YOUR_DB_USERNAME>'@'%';
```

`GRANT EXECUTE` 단계는 `CALL` 문을 실행하는 것 이상을 위해 필요합니다. 이 권한이 없으면 모니터링 사용자는 수신자가 존재 여부를 확인하는 데 사용하는 `information_schema.ROUTINES`의 프로시저를 볼 수 없습니다. `GRANT EXECUTE`을(를) 생략하면 프로시저가 누락된 것과 동일한 결과가 발생하며, 두 경우 모두 수신자가 `inline` 모드로 폴백하게 됩니다.

<Callout variant="tip">
  이 설정은 스키마별로 상태를 유지합니다. 데이터베이스를 생성 또는 복원하거나 프로시저를 삭제하면 해당 스키마에 대한 쓰기 문 계획 수집이 알림 없이 비활성화되고 `inline` 모드로의 폴백이 트리거됩니다. `SQL SECURITY DEFINER` 저장 루틴은 그 안에서 `PREPARE`/`EXECUTE` 문을 통해 실행되는 동적 SQL에 정의자의 권한을 적용합니다. 이를 통해 `SELECT`전용 모니터링 사용자는 직접 실행 권한이 없는 문에 대한 계획을 검색할 수 있습니다.
</Callout>
