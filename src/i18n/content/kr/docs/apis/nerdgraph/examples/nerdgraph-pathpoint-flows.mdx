UI에서 빌드하는 대신 [NerdGraph API](/docs/apis/nerdgraph/get-started/introduction-new-relic-nerdgraph)를 사용하여 프로그래밍 방식으로 Pathpoint 플로우를 생성하고 관리할 수 있습니다.

플로우는 결제, 인증 또는 온보딩과 같은 하나의 비즈니스 여정을 나타냅니다. API를 통해 생성하고 관리하는 단위입니다. 플로우는 [엔티티](/docs/new-relic-solutions/new-relic-one/core-concepts/what-entity-new-relic)이므로, 각각에는 읽기, 업데이트 또는 삭제하는 데 사용하는 엔티티 <DNT>GUID</DNT>이(가) 있습니다.

모든 플로우는 4개 티어 계층 구조를 따르며, KPI는 플로우 레벨, 스테이지 레벨 또는 둘 다에 연결됩니다:

```
Flow
├── Flow KPIs
└── Stages
    ├── Stage KPIs
    └── Levels
        └── Steps
            └── Signals (entity GUIDs, alert condition GUIDs, or a dynamic query)
```

Pathpoint 자체에 대한 소개는 [Pathpoint 시작하기](/docs/pathpoint/get-started-pathpoint)를 참조하십시오.

## 시작하기 전에 [#requirements]

필요한 것:

* 계정에서 Pathpoint가 활성화되었습니다.
* requests를 인증하기 위한 뉴렐릭<InlinePopover type="userKey" />
* 귀하의 [계정 ID](/docs/accounts/accounts-billing/account-structure/account-id).

## 플로우 작업 [#crud-operations]

이러한 예제를 대화형으로 실행하려면 [NerdGraph GraphiQL 탐색기](https://api.newrelic.com/graphiql)를 열고 스키마에서 `pathPoint`을(를) 검색하십시오. 예제를 실행하기 전에 플레이스홀더를 자체 값: `YOUR_ACCOUNT_ID`, `TARGET_ACCOUNT_ID`, `FLOW_GUID`, `SOURCE_FLOW_GUID`, `ENTITY_GUID`, `ANOTHER_ENTITY_GUID`, `ENTITY_NAME`, `ALERT_CONDITION_GUID` 및 스테이지, 레벨, 스텝 ID로 교체하십시오.

    최상위 레벨의 KPI는 전체 플로우에 적용됩니다. 스테이지(`stageKpis`) 내부의 KPI는 해당 스테이지에만 적용됩니다. 둘 다 동일한 스키마를 사용합니다.

    각 KPI의 `timeWindow`은(는) 고정된 기간으로 빌드된 `relativeRange` 또는 원시 NRQL 시간 표현식을 포함하는 `customRange` 중 하나를 사용하며, 둘 다 사용할 수는 없습니다.

    ```graphql
    mutation {
      pathPointCreate(
        scope: { id: YOUR_ACCOUNT_ID, type: ACCOUNT }
        pathpoint: {
          name: "Checkout flow"
          refreshInterval: FIVE_MINUTES
          kpis: [
            {
              name: "Order success rate"
              category: "Revenue"
              description: "Orders completed successfully"
              query: {
                from: "Transaction"
                where: "transactionType = 'Web' AND name = 'checkout'"
                select: { aggregationType: COUNT, alias: "orders" }
                timeWindow: {
                  relativeRange: { since: TWENTY_FOUR_HOURS, compareAgainst: SEVEN_DAYS }
                }
              }
            }
          ]
          stages: [
            {
              name: "Payment"
              stageKpis: [
                {
                  name: "Payment errors"
                  category: "Reliability"
                  query: {
                    from: "TransactionError"
                    select: { aggregationType: COUNT, alias: "errors" }
                    timeWindow: { customRange: "SINCE 30 minutes ago" }
                  }
                }
              ]
              levels: [
                {
                  steps: [
                    {
                      name: "Payment gateway"
                      config: {
                        healthRollup: WORST_STATUS_WINS
                        thresholdType: FIXED
                        thresholdValue: 1
                      }
                      entitySearchQuery: {
                        query: "domain = 'APM' AND name = 'PaymentGateway'"
                      }
                    }
                  ]
                }
              ]
            }
          ]
        }
      ) {
        guid
        name
        version
        excludedKpis
        kpis {
          id
          name
          category
          query {
            from
            where
            select {
              aggregationType
              attribute
              alias
            }
            timeWindow {
              customRange
              relativeRange {
                since
                compareAgainst
              }
            }
          }
        }
      }
    }
    ```

  <Collapser id="mutation-create-flow-health-rollup" title="상태 롤업 계산">
    플로우와 각 스테이지는 두 가지 방법 중 하나로 상태를 계산하며, 해당 레벨의 `healthRollup` 필드를 사용하여 설정합니다.

    플로우 레벨에서 `healthRollup`은(는) 플로우의 전반적인 상태가 도출되는 방식을 제어합니다:

    * <DNT>**Automatic rollup**</DNT> (`AUTOMATIC_ROLL_UP`, 기본값): 상태는 플로우의 스테이지에서 자동으로 롤업됩니다. 플로우의 전체 상태에서 제외하려면 스테이지에 `isExcluded: true`을(를) 설정하십시오. 해당 스테이지 자체의 레벨, 단계 및 신호는 여전히 평가되며 UI에 계속 표시됩니다. 스테이지는 플로우의 상태에 영향을 미치지 않게 되며, 이는 구축 중이거나 일시적으로 범위를 벗어난 스테이지에 유용합니다. 기본값인 `isExcluded: false`은(는) 스테이지가 정상적으로 참여함을 의미합니다.
    * <DNT>**Alert conditions**</DNT> (`ALERT_CONDITIONS`): 상태는 스테이지 롤업 대신 플로우의 KPI에 대한 공지 조건에서 가져옵니다. 플로우 레벨 `kpis`과(와) 페어링하십시오.

    동일한 두 가지 방법이 스테이지 수준에 적용되며, 스테이지 자체의 `healthRollup` 필드로 설정됩니다. `AUTOMATIC_ROLL_UP`은(는) 해당 스테이지의 수준에서 단계와 신호를 통해 롤업됩니다. 해당 계산에서 제외하려면 단계, 신호 또는 `entitySearchQuery`에 `isExcluded: true`을(를) 설정하십시오. 대신 `ALERT_CONDITIONS`은(는) 스테이지의 상태를 자체 KPI(`stageKpis`) 중 하나에 연결합니다. 이는 마케팅 캠페인 스테이지의 이메일 오픈율 KPI와 같이 단계 및 신호 텔레메트리보다 비즈니스 성과를 반영해야 하는 상태를 가진 스테이지에 적합합니다.

    플로우 레벨 및 스테이지 레벨 설정은 독립적이므로, 플로우는 한 가지 방법을 사용하고 스테이지는 다른 방법을 사용할 수 있습니다.

    이 예제는 두 개의 스테이지를 가지며 자체적인 전반적인 상태를 위해 `AUTOMATIC_ROLL_UP`을(를) 사용하는 &quot;Checkout flow&quot;를 생성합니다. &quot;Revenue&quot;는 &quot;Payment errors&quot; KPI에 연결된 `ALERT_CONDITIONS`을(를) 사용하고, &quot;Frontend&quot;는 상태에서 하나의 신호를 제외하면서 `AUTOMATIC_ROLL_UP`을(를) 사용합니다.

    ```graphql
    mutation {
      pathPointCreate(
        scope: { id: YOUR_ACCOUNT_ID, type: ACCOUNT }
        pathpoint: {
          name: "Checkout flow"
          description: "End-to-end checkout pipeline"
          refreshInterval: FIVE_MINUTES
          healthRollup: AUTOMATIC_ROLL_UP
          stages: [
            {
              name: "Revenue"
              healthRollup: ALERT_CONDITIONS
              related: { source: false, target: true }
              stageKpis: [
                {
                  name: "Payment errors"
                  category: "Reliability"
                  query: {
                    from: "TransactionError"
                    select: { aggregationType: COUNT, alias: "errors" }
                  }
                }
              ]
              levels: [
                {
                  steps: [
                    {
                      name: "Order service"
                      config: { healthRollup: WORST_STATUS_WINS }
                      entitySearchQuery: {
                        query: "domain = 'APM' AND name = 'OrderService'"
                      }
                    }
                  ]
                }
              ]
            }
            {
              name: "Frontend"
              healthRollup: AUTOMATIC_ROLL_UP
              related: { source: true, target: false }
              levels: [
                {
                  steps: [
                    {
                      name: "Login page"
                      config: {
                        healthRollup: WORST_STATUS_WINS
                        thresholdType: FIXED
                        thresholdValue: 1
                      }
                      entitySearchQuery: {
                        query: "domain = 'BROWSER' AND name = 'Login'"
                      }
                      signals: [
                        {
                          guid: "ENTITY_GUID"
                          name: "ENTITY_NAME"
                          type: ENTITY
                          isExcluded: true
                        }
                      ]
                    }
                  ]
                }
              ]
            }
          ]
        }
      ) {
        guid
        name
        message
      }
    }
    ```
  </Collapser>
</CollapserGroup>

`pathPointCreate` 계정 `scope`이(가) 필요합니다. 페이로드 내에서는 `name`만 필요합니다. `stages`을(를) 포함한 다른 모든 것은 선택 사항입니다. 단계는 세 가지 방법 중 하나로 신호를 가져오며, 이를 결합할 수 있습니다:

* <DNT>**A dynamic query**</DNT> (`entitySearchQuery`): 쿼리와 일치하는 모든 엔티티이며, 새로 고칠 때마다 다시 평가됩니다.
* <DNT>**A pinned entity**</DNT> (`type: ENTITY`): GUID로 식별되는 하나의 특정 엔티티입니다.
* <DNT>**A pinned alert condition**</DNT> (`type: ALERT`): GUID로 식별되는 하나의 공지 조건입니다.

`type` 필드는 선택 사항입니다. GUID만으로도 신호를 식별하기에 충분합니다.

스테이지는 또한 상태 롤업과 독립적으로 UI가 스테이지 사이의 커넥터 화살표를 그리는 방법을 제어하는 선택적 `related` 블록을 사용합니다. 스테이지가 이전 스테이지에서 들어오는 화살표를 표시해야 하는 경우 `source: true`을(를) 설정하고, 다음 스테이지로 나가는 화살표를 표시해야 하는 경우 `target: true`을(를) 설정하십시오. 모든 스테이지가 순서대로 다음 스테이지에 연결되는 플로우에서 첫 번째 스테이지는 `source: false, target: true`이고 마지막 스테이지는 `source: true, target: false`이며, 그 사이의 모든 스테이지는 둘 다에 대해 `true` 입니다.

<Callout variant="important">
  KPI의 `accountId`은(는) 기본적으로 플로우의 계정으로 설정됩니다. 다른 계정으로 설정하면 KPI가 생성되지 않으며 오류도 반환되지 않습니다. 응답의 `excludedKpis` 필드를 확인하여 뮤테이션이 건너뛴 KPI를 확인하십시오.
</Callout>

### 플로우 읽기 [#read-flow]

엔티티 GUID로 플로우를 읽어 전체 설정과 플로우, 각 스테이지, 각 레벨 및 각 스텝의 현재 상태를 가져옵니다. `healthStatus`은(는) 읽기에만 나타납니다.

```graphql
                threshold

                  since
                  compareAgainst

              }
            }
            metricQuery
          }
          stages {
            totalCount
            nextCursor
            items {
              id
              name
              link
              healthRollup
              healthStatus
              isExcluded
              related {
                source
                target
              }
              levels {
                totalCount

                items {

                    totalCount
                    nextCursor
                    items {
                      id
```

전체 트리가 필요하지 않은 경우 더 적은 필드를 요청하십시오. 예를 들어 `name` 및 `healthStatus`만 읽어도 플로우의 상태를 폴링하기에 충분합니다.

### 플로우 업데이트 [#update-flow]

`pathPointUpdate` diff 기반 작업입니다. 전송한 페이로드를 플로우의 현재 상태와 비교하고 ID 포함 여부에 따라 각 스테이지, 레벨, 단계 및 KPI에 대해 작동합니다:

* <DNT>**ID included**</DNT>: 기존 객체를 업데이트합니다.
* <DNT>**ID omitted**</DNT>: 새 객체를 생성합니다.
* <DNT>**Object left out of the payload entirely**</DNT>: 플로우에서 삭제합니다.

<Callout variant="caution">
  생략은 삭제를 의미하므로, 항상 먼저 [플로우를 읽고](#read-flow), 반환된 페이로드를 수정한 다음, 의도한 전체 상태를 전송하십시오. 부분적인 페이로드를 전송하면 누락된 모든 항목이 삭제됩니다.

  `version` 필드도 필요합니다. 낙관적 동시성 제어에 사용되는 에포크 밀리초 단위의 플로우의 마지막 업데이트 타임스탬프입니다. 이를 생략하거나 오래된 값을 보내면 업데이트가 실패합니다.
</Callout>

### 플로우 복제 [#duplicate-flow]

구조만 복제하거나 전체 플로우를 복제할 수 있습니다:

* `STRUCTURE`: 시그널이나 KPI 없이 스테이지, 레벨 및 단계만 복사합니다.
* `WHOLE_FLOW`: 신호 및 KPI와 함께 구조를 복사합니다.

입력에 설정한 모든 속성은 소스 플로우의 값을 재정의합니다. 속성을 상속하려면 해당 속성을 생략하십시오.

<CollapserGroup>
  <Collapser id="mutation-duplicate-flow" title="동일한 계정에서 전체 플로우 복제">
    동일한 계정 내에서 복제하려면 `scope` 인수가 필요하지 않습니다. `duplicateType: WHOLE_FLOW`을(를) 설정하십시오.

    ```graphql
    mutation {
      pathPointDuplicate(
        sourceGuid: "SOURCE_FLOW_GUID"
        pathpoint: {
          name: "Checkout flow (copy)"
          category: "E-Commerce"
          refreshInterval: TEN_MINUTES
          duplicateType: WHOLE_FLOW
        }
      ) {
        guid
        name
      }
    }
    ```
  </Collapser>

  <Collapser id="mutation-duplicate-flow-cross-account" title="전체 플로우를 다른 계정으로 복제">
    플로우를 다른 계정으로 복사하려면 `scope`을(를) 추가하고 해당 `id`을(를) 타겟 계정으로 설정하십시오. 소스 계정 내에서 복제하려면 `scope`을(를) 생략하십시오.

    다른 계정으로 복제하면 KPI가 아닌 스테이지, 레벨, 단계 및 신호만 복사됩니다.

    ```graphql
    mutation {
      pathPointDuplicate(
        sourceGuid: "SOURCE_FLOW_GUID"
        scope: { id: TARGET_ACCOUNT_ID, type: ACCOUNT }
        pathpoint: { name: "Checkout flow", duplicateType: WHOLE_FLOW }
      ) {
        guid
        name
      }
    }
    ```
  </Collapser>

  <Collapser id="mutation-duplicate-flow-structure" title="플로우의 구조 복제">
    신호나 KPI 없이 플로우의 형태만 복사하려면 `duplicateType: STRUCTURE`을(를) 설정하십시오.

    ```graphql
    mutation {
      pathPointDuplicate(
        sourceGuid: "SOURCE_FLOW_GUID"
        pathpoint: {
          name: "Checkout flow (copy)"
          category: "E-Commerce"
          refreshInterval: TEN_MINUTES
          duplicateType: STRUCTURE
        }
      ) {
        guid
        name
      }
    }
    ```
  </Collapser>
</CollapserGroup>

### 플로우 삭제 [#delete-flow]

플로우 삭제는 연쇄적으로 작용합니다: 모든 스테이지, 레벨, 단계 및 KPI와 함께 플로우를 제거합니다. 시그널 자체, 플로우가 가리키는 엔티티 및 공지 조건은 계정에 유지됩니다.

<Callout variant="caution">
  플로우 삭제는 영구적입니다.
</Callout>

```graphql
mutation {
  pathPointDelete(guid: "FLOW_GUID") {
    guid
    name
  }
}
```

## 부분 실패 [#partial-failures]

개별 객체가 실패하더라도 전체적인 생성 또는 업데이트는 성공할 수 있습니다. 응답의 두 필드는 이러한 상황이 발생한 시기를 알려줍니다:

* `message`: 실패한 스테이지, 레벨 또는 단계의 세부 정보입니다. 모든 것이 성공하면 `null` 입니다.
* `excludedKpis`: 생성되지 않은 KPI의 이름으로, 가장 일반적인 이유는 KPI의 `accountId`이(가) 플로우의 계정과 일치하지 않기 때문입니다.

부분적인 성공을 완전한 성공으로 취급하지 않도록 뮤테이션에서 두 필드를 모두 요청하십시오.
