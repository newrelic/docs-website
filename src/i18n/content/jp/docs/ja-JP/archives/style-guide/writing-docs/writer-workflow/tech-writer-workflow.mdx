## 0. ローカル環境のセットアップ [#set-local]

ローカル環境をセットアップする必要があるのは1回だけです。すでにこれを行っている場合は、この手順をスキップできます。

[ローカルビルド環境のセットアップ](/docs/style-guide/writing-docs/writer-workflow/set-up-local)に関する詳細な手順については、こちらをご覧ください。

## 1. ブランチを作成してドキュメントを編集します [#edit-doc]

GitHub Desktopには、**Current Repository**、**Current Branch**、および**Fetch origin**というラベルの付いた3つのタブが表示されます。デフォルトのブランチは**Develop**であるため、ブランチを作成します。

1. **Current Branch**をクリックし、**New Branch**を選択します。
2. 編集するドキュメントを見つけます。
   * Finderまたはエクスプローラーでファイルパスを使用します。たとえば、Pythonエージェントのドキュメントを編集する場合は、次のように移動します： `~/Documents/github/docs-website/src/content/docs/agents/python-agent/hosting-services/python-agent-stackato.mdx`
3. 任意のテキストエディタで[ドキュメントを編集](https://docs.newrelic.com/docs/style-guide/writing-docs/processes-procedures/create-edit-content)します。ドキュメントは[Markdown言語](https://www.markdownguide.org/basic-syntax)で記述する必要があります。
4. 編集したファイルを保存してください。

執筆ガイドラインに関するご質問については、[スタイルガイド](https://docs.newrelic.com/docs/style-guide/writing-strategies/introduction-style-guide/)の残りの部分をご覧ください。

## 2. 変更内容をコミットします [#commit-changes]

編集内容を保存しても、コミットを行う必要があります。コミットは、ワークフローのチェックポイントのように考えることができます。コミットプロセスはステージングから始まり、変更をGitHubにプッシュしたときに終了します。

1. GitHub Desktopに戻り、左側の列を確認してください。Github Desktopの左側の列には次のように表示されます：

   * 任意のドキュメントに加えられたすべての新しい編集の記録
   * **Commit to \[your-branch-name]**と書かれた青いボタン

2. コミットに名前を付け、説明を追加します。

3. **Commit to \[yourbranchname]**をクリックします。
   * コミット名と説明は次のようになります `feat(PythonAgent): Renamed the section heading`

## 3. サイトをローカルで実行します [#run-site]

ターミナルを使用してサイトをローカルでビルドします。この手順はオプションですが、プルリクエストを開く前に、サイトをローカルでビルドして変更をプレビューすることを**強く**お勧めします。

ローカルサイトを再ビルドする必要があるのはクラッシュしたときだけであり、保存やコミットのたびに行う必要はありません。

1. ターミナルで、クローンしたリポジトリである**docs-website**に移動します。例を以下に示します。
   * `cd ~/Documents/github/docs-website`
2. 次のコマンドを使用してyarnを実行します： `yarn && yarn start`
3. サイトのビルドには数分かかります。お茶やコーヒーを淹れてお待ちください。
4. ビルドが完了したら、[http://localhost:8000/](http://localhost:8000/)に移動して、ブラウザでサイトをプレビューします。

## 4. コミットの公開 [#publish-commits]

変更に満足したら、コミットをGitHubにプッシュします。これにより、GitHubリポジトリ内の他のすべてのユーザーが利用できるようになります。

1. GitHub Desktopで、利用可能な場合は青色の**Publish Branch**ボタンをクリックします。
2. Publish Branchが表示されない場合は、青い**Push Origin**ボタンをクリックします。

## 5. プルリクエストを開きます [#open-pr]

コミットは誰でも表示できますが、別のライターがレビューするまで、編集内容は`develop `ブランチにマージされません。

これを行うには、プルリクエスト（PR）を開きます：

1. GitHub Desktopで、青い**Create Pull Request button** \[プルリクエストの作成ボタン]をクリックします。

2. これによりブラウザでGitHubが開き、プルリクエストに入力するようプロンプトが表示されます。

   * ブランチから`develop`ブランチにマージしていることを確認してください。
   * 下にスクロールして、すべてのコミットを確認します。

3. コミットの説明と同様に、プルリクエストの説明も詳細に記述し、変更の完全なコンテキストを提供する必要があります。

   * ここに追加のコンテキスト（GitHubのissueリンクやJiraのissue ID、SMEなど）を自由に追加してください。
   * PRを開き、**Conversation**セクションに移動して、**Reviewer**セクションにレビュー担当者の名前を入力することで、別のテクニカルライターにレビューをリクエストします。

4. PRに`from_tw`ラベルとその他の[関連するラベル](/docs/style-guide/writer-workflow/github-intro)を追加します。
   * `from_tw`を追加しないと、PRはレビューのために別のライターに自動的に割り当てられません。

5. PRに満足したら、緑色の**Create pull request button** \[プルリクエストの作成ボタン]をクリックします。

6. 自分でプルリクエストを承認して変更を直接公開するか、別のテクニカルライターにピア編集をリクエストすることができます。

7. プルリクエストページの下部に、**Checks**セクションが表示されます。これらのチェックにより、PRがサイトのビルドプロセスを中断しないことが保証されます。マージする前に、`required`とマークされたすべてのチェックに合格していることを確認してください。

8. プルリクエストがチェックに合格し、別のテクニカルライターによって承認されたら（または変更を公開する準備ができていると確信している場合）、緑色の**Merge pull request**ボタンをクリックします。これにより、ブランチとコミットがリポジトリにマージされ、ビルドプロセスが開始されます。

<Callout variant="important">
  PRを最初に作成するときに`from_tw`ラベルを追加しないと、レビュー担当者が自動的に割り当てられません。PRを開く前にラベルを追加するのを忘れた場合：

  1. `from_tw`ラベルを追加します。
  2. PRをドラフトPRに変更します。
  3. PRを再度開くには、ページの下部にある`PR is ready for review button`を選択してください。これで、PRにレビュー担当者が設定されたはずです。
</Callout>

## ドキュメントをプレビューする [#preview-doc]

すでに公開し、コミットを実行したブランチをプレビューするには、主に2つの方法があります：

* **ローカル**: より高速ですが、ある程度のセットアップとターミナルに関する知識が必要です。
* **Netlify Cloud**: オーバーヘッドなしでライブサイトの完全なプレビューが可能であり、SMEと下書きのプレビューを共有するための非常に便利な方法です。ビルドの準備ができると、Netlify CloudはサイトのプレビューバージョンへのリンクをPRにコメントします。サイトのビルドには通常約15分かかりますが、変更が多い場合はさらに時間がかかることがあります。

## ドキュメントの改訂と公開 [#revise-doc]

レビュアーがファイルにレビューを送信したことが通知されたら、PRに移動して変更を確認します。コメント付きのレビューの一部である場合は、差分表示で確認できる場合があります。それ以外の場合は、ファイル内のコピー編集として表示される場合があります。

1. ファイル内のコメントに返信します。フォローアップのディスカッションで返信するか、**Resolve conversation** \[会話を解決]をクリックします。
2. すべてのコメントを解決し、すべての自動チェックに合格したら、プルリクエストをマージできます。プルリクエストをマージすると、自動ビルドプロセスが開始され、変更はまもなく公開されます。

<Callout variant="tip">
  **プルリクエストをマージ**ボタンが緑色の場合にのみ、マージできます。緑色ではない場合は、見落としているコメントや、GitHubがマージをブロックしている理由を示すその他のメッセージがないか確認してください。
</Callout>

## マージを元に戻す [#revert]

ほとんどの場合、元に戻すことができることを覚えておいてください。PRをマージした後に、マージすべきではなかったことに気付いた場合は、**Revert**ボタンを使用してマージを解除できます。

1. GitHubのプルリクエストタブで、集計バーの**Closed**をクリックして、すでにマージされているすべてのIssueとPRを表示します。
2. マージしたPRを見つけ、Revertボタンを見つけます。
3. \[Revert] をクリックします。これにより新しいPRが作成されますが、これはマージする必要があります。再度開く場合は、リンクをたどって元のPRに戻り、それをリバートするか再度開く必要があります。

## ライターのみ：フォークではなく、ブランチで作業します。 [#branch-fork]

ブランチで作業するチームもあれば、フォークで作業するチームもあります；**Docsチームはブランチで作業します**。ブランチがアップストリームにプッシュされている限り、これにより共同作業が可能になり、誰かが休暇を取っても作業が失われることはありません。

docs-websiteリポジトリにブランチを作成するには：

1. GitHub Desktopを開きます。
2. **Current branch: xxx**をクリックします。
3. **New Branch**をクリックします
4. 新しいブランチに名前を付けるようプロンプトが表示されます。分かりやすい名前が最適です。これは、自分の作業内容を他の人にすばやく理解してもらうための優れた方法です。たとえば、What’s Newページで作業している場合、ブランチに**Whats-new-updates**という名前を付けることができます。

新しいブランチを作成するときは、ブランチ名とPRのタイトルにJiraのIssue ID(DOC-1234)を追加することを忘れないでください。

## GitHubの権限に関する注意事項 [#permissions]

Docsチームのライターはブランチで作業しますが、Docsチーム以外のコントリビューターはフォークを使用します。これは、Docs以外のコントリビューターがブランチ上のコンテンツを直接編集できないことも意味し、コラボレーションが難しくなる可能性があります。

GitHubの権限は、誰がブランチで作業でき、誰がフォークで作業できるかを決定するために使用されます。GitHubでは、アクセスはチームとメンバーのロールによって決定されます。誰でもパブリックリポジトリに貢献できますが、追加のアクセス権は`Write`および`Admin`のロールを通じて付与されます。（あまり使用されない他の定義済みロールもあります）。

Docsチームのすべてのメンバーには`Admin`ロールが付与され、リポジトリへのフルアクセスが許可されます。他のNew Relicコントリビューターには`Write`ロールが付与され、ユーザーの割り当て、およびプルリクエストのオープンとクローズが許可されます。

現在のアクセス設定を確認するには、`docs-website`リポジトリに移動し、**Settings &gt; Collaborators and teams**または**Team and member roles**に移動します。
