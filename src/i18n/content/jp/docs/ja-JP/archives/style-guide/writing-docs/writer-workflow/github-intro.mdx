テクニカルドキュメントライター（TW）はドキュメントを担当します。私たちは[ドキュメントの執筆と編集](/docs/style-guide/writer-workflow/tech-writer-workflow/)、[ピアエディットの交換](/docs/style-guide/writer-workflow/peer-editor-workflow/)、バックログの維持、およびヒーロー業務を行います。これらすべてを実現するために、[DocsチームのGitHubボード](https://github.com/newrelic/docs-website)を使用して、提出されたIssueとプルリクエスト（PR）を管理します。

## IssueまたはPRの関係者 [#who]

GitHubは、作業を進める人々を含め、Issueまたはプルリクエストのライフサイクルのすべての段階を追跡します。

DocsチームはGitHubを通じて誰でもissueを提出したりプルリクエストを作成したりできるようにしているため、提出者とNew Relic GitHub組織との関係を確認することを強くお勧めします。貢献者がRelicかどうか不確かな場合は、New Relic GitHub組織のメンバーであるかどうかを確認するのが良い方法です。一般的に、そうでないと証明されるまでは、提出者は外部の人間であると想定することをお勧めします。

* **作成者**: issueまたはPRを開く人です。作成者は、Docsチームのメンバー、他のRelic、または外部ユーザーのいずれかです。誰が作成したかに応じて、IssueまたはPRに異なるラベルを付けます。
* **担当者**：IssueまたはPRの責任を持ち、公開まで見届ける人のことです。Heroは、TW以外のIssueやPRを自分自身に割り当てるか、他のライターからIssueやPRを引き継ぐことができます。
* **レビュアー**：これは、コードやドキュメントのピア編集を提供し、変更を承認する人のことです。これは必ずしも、その領域の責任者やコミットのマージの責任者であるとは限りません。特定のissueには最大100人のレビュアーを割り当てることができます。

**Hero**として、1日を通して以下のことに注意してください：

* 1日の始まり（特に週の初めの月曜日）に、前のHeroに状況を確認してください。必要に応じて、BCNのHeroと同期することを忘れないでください。
* \#docs\_deploysで受信したPRを監視し、**Needs triage**列のすべてを確認します。その列から適切な列にカードをドラッグします。

**チームの全員**が物事を進めるのに役立ちます：

* すべてのライターは**Needs review**列に注意を払う必要があります。PRにレビュアーがいない場合は、担当することができます。
* レビュー（単純または複雑）の準備ができたら、PRを**Needs review**に移動します。
* SMEによってブロックされているPRは、必ず**Waiting on SME/Blocked**に移動してください。
* PRのフィードバックが完了しているかどうかを確認するには、**Waiting on TW to merge**を確認してください。
* ピアフィードバックを取り入れた後、PRをマージし、ボードから削除してください。

## GitHub（およびスタイルガイド）での参照の処理 [#references]

* 公開されている場所から非公開のものにリンクしないでください。
* Jiraチケットを参照できますが、リンク（`https://newrelic.atlassian.net/browse/DOC-1234`は不可）ではなく、課題キー（`DOC-1234`は可）でチケットを参照してください。
* トラフィックや使用量の数値を公に言及しないでください。
* 内部の人物を名前で参照しないでください。GHアカウントを持っている場合は、そのGHハンドルを@メンションしてください。持っていない場合は、個人ではなくチーム（「ブラウザチームのエンジニアに相談する」や「サポートエンジニア」など）について話してください。
* \#help-documentationチャネルとヒーローに言及することができます。

## リリースをメインの作業にマージします（または、いつ公開しますか？）。 [#merging-main]

Heroは現在、太平洋時間の午前9時（朝）、午後12時（正午）、および午後3時（夕方）にマージされます。リリース中に誰かがdevelopにマージしたときの中断を避けるため、リリースブランチをmainにマージします。このワークフローの詳細については、[Atlassianのgitflowドキュメント](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow)を参照してください。

developブランチから新しいリリースブランチを作成することが重要です。新しいブランチを作成する前に、developにいることを確認してください。

リリースを開始するには：

1. トップヘッダーの**Current Branch**、ドロップダウンの**New Branch**をクリックし、次に**Develop**を選択して、Github Desktopを使用して`develop`のブランチを作成します。
2. 次のパターンでブランチに名前を付けます：`daily-release/mm-dd-yy-morning/noon/evening`。たとえば、2021年10月27日午前9時に行われる毎日のリリースは、次のスタイルに従います：`daily-release/10-27-21-morning`。
3. 変更をプッシュするには、GitHub Desktopで**Push Origin**をクリックします。
4. **Create Pull Request**をクリックして、新しい日次リリースブランチからmainへのプルリクエストを作成します。これにより、[github.com](github.com)でプルリクエスト画面が開きます。プルリクエストはデフォルトでdevelopにマージされるため、ページの左側で`base`ブランチとしてmainを選択し、`Submit Pull Request`をクリックします。
5. すべてのチェックが完了するまで待ってから、プルリクエストをマージします。

`daily-release/mm-dd-yy-morning`パターンに従うすべてのブランチは、[保護されたブランチ](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/about-protected-branches)です。管理者のみがこれらを削除できます。

## GitHubラベル [#labels]

バックログのトリアージと健全性の追跡を改善するために、Issueにラベルを適用します：

* `content`：すべての課題でこのラベルを使用します。`content`は、課題がデザインやエンジニアリングの課題ではなく、コンテンツに関連するものであることを示します。

* `pg_*`: Docsチームは、製品グループを示すために常にこのラベルを使用します。完全な定義については、社内チームのGoogleドライブにある「Doc Jira and GitHub fields」ドキュメントをご覧ください。

* issueを作成したユーザーを示します：

  * `from_internal`：Relicが作成しました。
  * `from_external`：New Relic以外のユーザーがリポジトリでIssueを作成したか、またはIssueが#顧客フィードバックプロセスを通じて寄せられました。
  * `from_tw`：私たちの誰かが作成しました（#顧客フィードバックを転送していた場合を除きます）。

* オプション：

  * `docs-issue-candidate`：製品チームの専門知識なしではDocsチームが処理するには範囲が広すぎるissue。このラベルは、これらのissueを顧客フィードバックチャネルに移行するようにDocs issueチームにアラートを出します。顧客フィードバックチャネルでは、トリアージされて製品チームに送信されます。
  * `Jira’d`：対応するJiraチケットがあるissue。issueのコメントにJira番号を残すようにしてください（たとえば、DOC-1234）。

貢献がどこから来たのかを確認できるように、すべてのプルリクエストにはこれらのラベルが必要です：

* `content`: 常に追加します。これは、PRがデザインやエンジニアリングではなく、コンテンツに関連していることを示します。

* 誰がプルリクエストを作成したかを示します：

  * `from_internal`：Relicが作成しました。
  * `from_external`：ユーザーがリポジトリで開いたか、#顧客フィードバックプロセスを通じて寄せられたものです。
  * `from_tw`：私たちの誰かが作成しました（#customer-feedbackを伝達する場合を除きます）。PRが外部の問題を修正する場合は、作業がテクニカルライターによって行われたため、`from_tw`としてラベル付けしてください。

## ドキュメントの問題 [#docs-issues]

ドキュメントの課題の適切な候補を選択するための厳格なルールはありません。ドキュメントヒーローが追跡するには難しすぎるものや、深いエンジニアリングの専門知識が役立つ可能性のあるものが考えられます。いくつかの例として、コード例、要件セクション、およびNRQLクエリがあります。

最終的に、ドキュメントの課題は、ドキュメントチームが製品チームと協力してドキュメントおよび製品の課題を解決するのに役立ちます。これにより、誰が提出したかにかかわらず、製品チームの専門知識を活用して、できるだけ多くの課題を解決できます。

実行可能な問題候補のライフサイクルは、次のようになります。

1. GitHubヒーローが潜在的な候補として評価できるように、誰かがGitHubを通じてIssueを提出します。
2. ヒーローは`docs-issue-candidate`ラベルを追加します。その後、ヒーローは課題をアーカイブします。
3. 毎週、指定されたドキュメントチームのメンバーが、`docs-issue-candidate`ラベルの付いたすべての問題を評価します。
4. 承認されると、`docs-issue-candidate`ラベルは`docs-issue`ラベルに変更されます。その後、Issueを顧客フィードバックのJiraプロジェクトに移行します。
5. 新しいJiraはPMによってトリアージされ、適切なプロジェクトチームにファネルされます。
6. PMはチケットを担当者に渡し、担当者は完了後にそれを閉じます。

## コミットを検証します [#verified-commits]

<img title="verified commit" alt="A screenshot of a verified commit in github" src="/images/verified-commits.webp" />

検証済みコミットを設定することで、プロセスに少しセキュリティが追加されます。これにより、コミットがあなたのマシンからのものであり、他の誰かがリモートであなたになりすましてコミットしたものではないことが保証されます。誰かのコミットが検証されると、その横にラベルが表示されます。

まず、GPGと呼ばれるものをインストールする必要があります。これはhomebrewを使用して行うことができます：

```bash
brew install gpg
```

インストールが完了したら、次のコマンドを実行してキーを作成できます：

```bash
gpg --full-generate-key
```

これにより、次のように回答できる一連のプロンプトがトリガーされます：

* 選択内容は？**1**
* どのキーサイズをご希望ですか？（3072）**4096**
* キーの有効期間は？（0） **0**
* キーの有効期限はまったく切れません\
  これで正しいですか？(y/N) **y**

名前とメールアドレス（githubで使用しているもの）、および&quot;コメント&quot;も求められます。コメントを空白のままにしてEnterキーを押すことができます。

次に、`YOUR_KEY_ID`を先ほどのキーに置き換えてこれらのコマンドを実行し、gitのいくつかの設定を調整します：

```bash
git config --global user.signingkey YOUR_KEY_ID
git config --global commit.gpgsign true
```

次に、このコマンドを実行して、bashまたはzshプロファイルに追加情報を保存します。zshを使用している場合は、次を実行します：

```shell
if [ -r ~/.zshrc ]; then echo -e '\nexport GPG_TTY=\$(tty)' >> ~/.zshrc; \
else echo -e '\nexport GPG_TTY=\$(tty)' >> ~/.zprofile; fi
```

bashを使用する場合は、次を実行します：

```bash
if [ -r ~/.bash_profile ]; then echo -e '\nexport GPG_TTY=\$(tty)' >> ~/.bash_profile; \
else echo -e '\nexport GPG_TTY=\$(tty)' >> ~/.profile; fi
```

これで、テストを実行して動作を確認できます。以前にgpgで作成したパスワードを入力する必要がある場合があります。

```bash
echo "test" | gpg --clearsign
```

うまく機能しない場合は、次のコマンドを実行してみてください。

まずこのコマンドを実行して、gpgクライアントを終了します：

```bash
gpgconf --kill all
gpg-agent --daemon
```

次に、コマンド`echo test`を再度実行します。

それでもエラーが発生する場合は、変数を使用するようにプロンプトで指示し、パスワードを再認証する必要がある場合があります：

```bash
export GPG_TTY=`tty`
```

次に、このテストを再度実行します：

```bash
echo "test" | gpg --clearsign
```

最後に、コミットを試してみてください！github desktopを使用している場合は、コミットする前にアプリを終了/再起動することをお勧めします。エラーが発生した場合は、#doc\_eng\_helpにお問い合わせください。
