ドキュメントサイトの分岐インストールコンポーネントを使用すると、ユーザーは1つ以上のオプションを選択でき、その選択に基づいてコンテンツが表示されます。

## 作成プロセスの概要 [#overview]

ブランチインストールコンポーネントの作業を開始する前に、考慮すべき事項は次のとおりです。

* 分岐インストールを確実に使用したいことを確認してください。問題が別のソリューション（たとえば、[タブコンポーネント](/docs/style-guide/structure/intro-to-components)）で解決できるかどうかを検討してください。
* [作成したブランチのインストールに関するドキュメント](#uses)を参照して、何が可能かを確認してください。テンプレートとして使用するためにクローンするものを1つ選択してください。
* オプションがどうなるか、どのようなコンテンツが表示されるかの論理的なフローを確定します。理想的には、ブランチを作成する前にコンテンツ計画をほぼ最終的な状態にしておく必要があります。このため、作業を2つ以上のJiraに分割する場合があります。

ブランチインストールコンポーネントはさまざまな方法で構築できますが、特に構造が複雑な場合は、機能させるために多大な労力が必要になることがあります。とはいえ、作成プロセスがどのようになるかについての概要は次のとおりです。

1. 分岐したインストールドキュメント、特に当社の[YAMLファイル例](#yaml-examples)を確認してください。このコンポーネントの構造とロジックを理解してください。
2. 開始する準備ができたら、エミュレートするインストールコンポーネントのYAMLファイルと関連フォルダーをコピーし、それらをプロジェクトのベースとして使用します。
3. プロジェクトに合わせて最上位のフォルダー名を変更し、それに合わせてYAMLファイルの`agentName`を変更してください。`agentName`は、YAMLファイルにコンテンツを取得するフォルダーを指示するものです。（[YAMLファイル例](#yaml-examples)を参照してください）。
4. 正しく機能していることを確認するには、ローカルビルドを実行します。
5. .mdx ファイルの追加と YAML ファイルの編集を開始します。作成する計画が既存のロジックとどの程度一致するかによって、YAML ファイルから大部分のコンテンツを削除し、一度に少しずつ追加していく方が簡単な場合があります。
6. 作業中は、頻繁にビルドして、正常に機能しているかどうかをテストしてください。小さな作業の塊をこなし、ビルドされているかどうかを確認することで、トラブルシューティングに無駄な時間を費やすのを避けることができます。エラーを確認するには、[YAML検証スクリプト](/docs/style-guide/writing-docs/article-templates/branch-install-doc-reference#verify-yaml)を使用してください。

問題が発生して解決できない場合は、これまでに作成経験があるメンバーにサポートを依頼してください。

## 重要な決定事項 [#decision-points]

ブランチインストールには、いくつかのアプローチがあります。主な決定事項は次のとおりです。

<CollapserGroup>
  <Collapser id="default-content-decision" title="オプションが選択される前にコンテンツを表示する必要がありますか？">
    この決定は次のことに関するものです：顧客が最初にドキュメントにアクセスしたときに何が表示されるか？オプションを選択する前であっても、いくつかの手順を表示することは理にかなっていますか？大多数の顧客がたどる単一のパスがある場合、オプションの選択に応じて調整および変更されるコンテンツを表示することは理にかなっています。これに関する詳細：

    * &quot;デフォルトコンテンツ&quot;アプローチは、`override`および`skip`コンポーネントの使用に依存しています。ファイルを表示し、「xオプションが選択された場合はこのファイルをスキップまたは上書きする」と表示します。（これを使用するインストールドキュメント：[Javaインストール](/install/java)）。
    * オプションが選択されるまでコンテンツを表示したくない場合は、`isCondition=true` の方法を使用します。このコンポーネントは、単純に「これらのオプションが選択された場合に、このファイルを表示する」という動作を指定するものです。（これを使用しているインストール手順ドキュメント：[.NET のインストール手順](/install/dotnet)）
  </Collapser>

  <Collapser id="display-all-options-decision" title="すべてのオプションを表示する必要がありますか？それともネストしますか？">
    この決定は、すべてのオプションの選択肢を最初に表示するか、それともネストするか（たとえば、1つのオプションを選択すると別のオプション選択ボックスが表示されるなど）に関するものです。

    オプションの選択ロジックが比較的シンプルな場合は、すべてのオプションを一度にユーザーに提示するのが合理的です。しかし、選択ロジックがかなり複雑な場合（例：3つ以上の選択肢があり、一部の選択内容が後続の選択肢に影響を与えるなど）、それらをネスト構造にするのが合理的です。

    完全に展開されたオプション選択ボックスのセットの例については、\[Network security prerequisites doc]をご覧ください。ネストされた選択ボックスのセットの例については、\[the .NET install]をご覧ください。
  </Collapser>

  <Collapser id="guided-install-decision" title="ガイド付きインストールは必要ですか？">
    この決定ポイントは、ガイド付きインストールパスに関する情報を表示する必要があるかどうかに関するものです。一部のエージェントでは、ガイド付きインストールパスに関するコンテンツを表示したい場合があります（たとえば、「app server」と「Jetty」を選択すると、[Javaエージェントインストール](/install/java)でガイド付きインストールコンテンツを確認できます）。

    ガイド付きインストールコンテンツを追加するためのいくつかのオプションがあります：

    * ガイド付きインストールコンテンツを表示したい特定のオプションに配置できる `recommendedGuided: true`コンポーネントを用意しています。これは基本的に、該当するオプション選択ボックスを含む .mdx ファイルのコンテンツを表示する仕組みです。この例は Java のインストール手順で確認できます。この手順では、ガイド付きインストールコンテンツが `appInfo-2` ファイル内に配置されています。この実装はガイド付きインストールコンテンツ専用のものではありません。このロジックを使用すれば、任意のコンテンツを自由に表示することができます。
    * または、ガイド付きインストールを通常の.mdxファイルとして追加し、他のファイルと同じように表示することもできます。.NETのインストールでは、このアプローチを採用しています。このアプローチでは、他のファイルと同様に番号付きのステップとして表示されます。
  </Collapser>

  <Collapser id="config-file-decision" title="設定ファイルは必要ですか？">
    一部のエージェントは、ユーザーがインストールドキュメントから直接ユーザー固有の値を入力できる設定ファイルコンポーネントを利用します。この例については、[Javaインストールドキュメント](/install/java)を参照してください。

    このファイルを使用する必要はありません。これを使用するかどうかは、特定のインストールワークフローによって異なります。（たとえば、.NETのインストール手順ではこれは使用されません）。
  </Collapser>
</CollapserGroup>

## 分岐インストールでは次を使用します [#uses]

以下は、ブランチ（分岐）型インストールの実装例と、それぞれの設計上の選択理由の要約です。作成したいアプローチに最も近いものを1つ選択し、必要に応じて調整することをお勧めします。今後新しい用途が追加された際は、このリストを最新の状態に維持するよう努めてください。

* Vulnerability Management（脆弱性管理）：[dependabotデータのインポート](/install/vm/)。[このYAMLファイルのラベル付き画像を参照してください](#simple-yaml-example)。詳細:

  * 非常にシンプルな実装です。2つのファイルから選択できる単一のオプション選択ボックスです。
  * デフォルトで表示されるコンテンツはありません。
  * これは非常にシンプルであるため、タブコンポーネントの方が適した選択肢であった可能性があることにご注意ください。

* [MySQL 統合機能のインストール手順](/install/mysql)。詳細：

  * 選択ボックスを1つだけ使用するシンプルな実装例。
  * デフォルトのコンテンツが表示されるアプローチを採用しています。

* [Javaインストール](/install/java)。詳細:

  * [デフォルトコンテンツのアプローチ](#default-content-decision)を採用しています。これは、ほとんどの顧客がたどるインストールパスが1つあるためです。
  * オプション選択セクションは2つだけです：最初のオプションで選択された内容に応じて、2番目のオプションボックスが表示されます。
  * `recommendedGuided`コンポーネントを使用して、（`appInfo-2`ファイルに含まれる）ガイド付きインストールを表示します。
  * 設定ファイルコンポーネントを使用します。

* [.NETインストール](/install/dotnet)。[このYAMLファイルのラベル付き画像を参照してください](#complex-yaml-example)。詳細:

  * この構成では、デフォルトのコンテンツは一切表示されません。これは完全に [`isConditionalStep: true`](#default-content-decision) の手法に依存しています。その理由は、選択可能なパスが非常に多く、大半のユーザーが選択する特定のパスが存在しないためです（理論上は、どれか1つをデフォルトとして選択することも可能でした）。
  * これには2つのオプション選択セクションしかありません：最初のオプションで選択された内容に応じて、2番目のオプションボックスが表示されます。
  * `appInfo-2`ファイルに含まれる`recommendedGuided`コンポーネントを使用します。
  * 設定ファイルコンポーネントは使用しません：これは、ほとんどの顧客がファイルを直接使用するのではなく、環境変数やその他のオプションを介して設定を編集するためです。

* [Pythonのインストール](/install/python)。詳細:

  * デフォルトのコンテンツは表示されません。これは完全に[`isConditionalStep: true`アプローチ](#default-content-decision)に依存しています。これは、主要なパスが1つではないためです。
  * これにはかなり多くのオプション選択ボックスがあります：選択されたものに応じて最大4つです。
  * 構成ファイルコンポーネントは使用しません。
  * コメントを利用しており、コードの理解とメンテナンスの向上に役立ちます。

* [ネットワーク監視エンドポイント](/install/npm)。詳細:
  * 非常にシンプルな実装です。表示するテーブルを制御する3つのオプション選択ボックス。表示するテーブルを決定する置換オーバーライドを備えた、デフォルトで表示されるファイル。
