テクニカルライターは、&quot;What&apos;s new&quot;の投稿を公開する上で重要な役割を果たします。コントリビューターは[What&apos;s New投稿の作成手順](/docs/style-guide/writing-docs/article-templates/whats-new-template/)に従いますが、コントリビューターが作業を完了できるよう、いくつかの追加手順を実行します。

## プロセスの概要 [#overall-process]

`What's new`プロセスの全体像は次のようになります：

1. 社内の誰もが、ドキュメントWebサイトに`What's new`プルリクエスト（PR）を送信できます。
2. 複数のプロダクトマーケティングマネージャーが交代で投稿をレビューし、提案を行います。
3. プロダクトマーケティングマネージャーは、投稿のレビューを完了すると、技術ドキュメントチームに再レビューを依頼するPRコメントを挿入します。
4. テクニカルライターはレビューを完了し、投稿を公開するか、特定の日時の枠で投稿する準備ができていることを確認するコメントをPRに記載します。

## 投稿に関する特定のテクニカルライターのタスク [#specific-writing-tasks]

毎日のヒーローには、毎日次の責任があります：

* **スケジュールされた投稿のマージ:** Githubボードの`Scheduled work`列を確認し、すでに承認され、その日にマージされる予定の`What's new`の投稿がないか確認します。たとえば、月曜日のヒーローがレビューして承認した投稿が、水曜日のヒーローシフトで公開される予定の場合、そのPRをマージする必要があります。
* **受信した投稿を確認する:** 受信した`What's new`の投稿はすべて、ヒーローシフト中に確認して承認する必要があります。これには、基本的なコピー編集、正しい画像フォーマットの確保、およびプレビュービルドの成功の確認が含まれます。タイトルを公開する日に編集し、その後、PRを`Scheduled work`列に移動します。PRが届き次第レビューすることで、マージの準備が整った際にスムーズなリリースを確実に行うことができます。

より詳細な手順については、ドキュメントの残りの部分を参照してください。

<Callout variant="tip">
  執筆のレビューを開始する前に、投稿がその部門外からのものである場合は、プロダクトマーケティングマネージャーによってレビューされていることを確認してください。たとえば、開発者またはプロダクトマネージャーが投稿を送信した場合、最初にプロダクトマーケティングマネージャー（[CODEOWNERSファイル](.github/CODEOWNERS)にリストされている人）によってレビューされる必要があります。プロダクトマーケティングマネージャーが投稿をレビューしてヒーローに渡した後、以下のセクションの手順を完了していることを確認してください。
</Callout>

### GitHubボードの管理 [#the-board]

1. GitHubプロジェクトボードで、投稿をトリアージ列から**Scheduled work**列に移動します。投稿は、実際に公開されるまでそこに残ります。
2. 認識しやすいように、公開日と時間枠をプルリクエストのタイトルに挿入します。当社の[手順](/docs/style-guide/writing-docs/article-templates/whats-new-template/)では、コントリビューターに次の公開枠を提供していることを伝えています：午前、正午、または夕方。時間どおりに利用できるように、これを早めに投稿するかどうかを尋ねる必要がある場合があります。

### 投稿をレビューします。 [#the-review]

1. メインのスタイルガイドのルールを使用して、ドキュメントをレビューしてください。大きな問題が見つかった場合は、コントリビューター（またはプロダクトマーケティングのレビュアー）と協力してください；それ以外の場合は、ご自身で変更を加えることができます。

2. ドキュメントサイトへのURLが絶対パスであることを確認してください。相対パスは製品UIで解決されないため、投稿では絶対パスを使用する必要があります。

   ```md
   * Absolute path (GOOD): [**Billing user role**](https://docs.newrelic.com/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#roles)
   * Relative path (BAD): [**Billing user role**](/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#roles)
   ```

3. 投稿で画像を参照している場合は、他のサイトでホストされている画像へのリンクではないことを確認してください。画像ファイルは当社のリポジトリに配置する必要があります。

4. 投稿のフロントマターに`isFeatured: true`があるかどうかを確認します。その場合、投稿が製品UIの上部に固定されることを意味します。1つの投稿のみがフィーチャーされるように、以前にフィーチャーされた投稿の対応するフラグを削除する必要があります。

<Callout variant="tip">
  ヒーローシフト中に&quot;What&apos;s new&quot;の投稿レビューを完了できない場合は、次のシフトを担当するヒーローが完了できるように集計してください。
</Callout>

### 投稿を公開する [#publish-the-post]

<Callout variant="caution">
  2番目のブランチを作成して`main`にマージする前に、[IDを生成するGitHubアクション](https://github.com/newrelic/docs-website/actions/workflows/update-whats-new-ids.yml)が完了していることを確認してください。
</Callout>

「What&apos;s new?」の投稿を公開するには、`main`へのマージが2回必要です。

1. 通常どおり、日次リリースブランチを作成して`main`にマージします。
2. `main`にマージした後、`develop`に基づいて2番目のリリースブランチを作成します。この2番目のブランチには、「Whats new?」IDが含まれます。
3. この2番目のブランチを`main`にマージします。この2番目のマージにより、UIに「What&apos;s new？」の投稿が表示されます。（好奇心旺盛な方へ：2番目のブランチには、ドキュメントサイトの投稿をUIに接続する「Whats new？」IDが含まれています。2番目のマージは、2番目のロケーションに対応しています）。
4. フォローアップして、投稿がドキュメントサイトだけでなくUIにも表示されていることを確認します。

### 将来の投稿を計画する [#future-posts]

将来公開される予定の投稿の場合：

* 一般的に、当番のヒーローは、公開する必要がある日に投稿の責任を負います。
* 投稿を通常の午前8時または9時よりも早く公開する必要がある場合。（米国太平洋標準時）のマージでは、最初に取り組んだ担当者が投稿を手配する必要があります。
* 特定の注目度の高いリリースなど、場合によっては、テクニカルライターが自分自身をPRに割り当てることで投稿の所有権を取得し、ヒーローがその投稿の責任者ではないことを全員が確認できるようにすることがあります。
