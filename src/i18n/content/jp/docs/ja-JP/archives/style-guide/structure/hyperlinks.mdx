可能な限り、テキスト内の関連する箇所にハイパーリンクを含めてください。**For more help**セクションにドキュメントリンクのリストを作成することは避けてください。将来のライターがその重要性を判断するのが難しくなるためです。

<Callout variant="tip">
  製品にリンクする場合は、[UIパス](/docs/style-guide/quick-reference/ui-paths)に関するスタイルガイドのページをご覧ください。
</Callout>

## リンク構文 [#link-syntax]

ドキュメントサイトでは、Markdownのインラインリンク構文を使用します：

```markdown
[link text](https://example.com)
```

ドキュメントサイトの別のページにリンクする場合は、「相対」リンクを使用する必要があります（ドキュメントサイトの`https://docs.newrelic.com`ルートURLを省略します）：

```markdown
[link text](/docs/category-path/doc-path/)
```

<Callout variant="tip">
  Markdownは、ドキュメントの最後に宛先URLがリストされる[&quot;参照&quot;スタイルのリンクもサポートしています](https://daringfireball.net/projects/markdown/syntax#link)。これらは機能し、正しくレンダリングされますが、いくつかの理由からこのリンクスタイルの使用を避けています：

  * これはあまり一般的ではないスタイルであり、コントリビューターの混乱を招く可能性があります。
  * ドキュメントは非常に長いため、コントリビューターにとってリンクをその宛先に接続するのが扱いにくくなる可能性があります。
</Callout>

## リンクテキスト [#hyperlinks-linktext]

ハイパーリンクのテキストを記述する際は、次のガイドラインに従ってください。

* **ラベル:** ドキュメント内の各リンクに、一意で意味のあるテキストラベルがあることを確認してください。異なるリンクのラベルに同じテキスト文字列を使用しないでください。
* **場所:** リンク先を識別するための明確で簡潔なテキストラベルを含めます。外部サイトにリンクする場合は、追加のコンテキストを提供してください。なぜそこにユーザーを誘導するのですか？
* **ここをクリック:** 「ここをクリック」などの意味のないリンクラベルは使用しないでください。
* **&quot;リンクテスト：&quot;** 周囲のテキストなしで、リンクのみを読んでください。ユーザーがページ上でそれだけを見た場合、それぞれがリンク先を明確に説明するものとして独立して成立していますか？
* **URLプレフィックスの回避：** URLをリンクテキストとして使用したいアドレスにユーザーを誘導する場合は、リンクテキストから`https:`および`www.`プレフィックスを削除してください。例：`[https://github.com/](https://github.com)`ではなく`[github.com](https://github.com)`。または、`[https://github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)`ではなく`[github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)`。

これら3つの例についてリンクテストを実施します。最後の例は、ページ上の他の内容を読まなくてもリンクで明確に識別できるため、PHPの設定に関する情報を探している読者にとって最適です。

## サポートリンク [#support-link]

**サポートのメールアドレスへのハイパーリンクは絶対に含めないでください。**これにより、スパムが防止され、顧客がチケット送信フォームを使用してチケットを作成し、適切なサポートの優先度を受け取ることができるようになります。顧客にサポートへの連絡を指示する必要がある場合は、代わりに次を使用してください：

```md
Get support at [support.newrelic.com](support.newrelic.com).
```

## アンカーリンク [#hyperlinks-anchor]

リンクにアンカーが含まれている場合（例：`#inivar-scope`）、それが使用する完全で**現在**のドキュメントパスを使用してください。一部のブラウザでは、リダイレクト時にアンカーが保持されません。

アンカーリンクのHTML `id`を作成または編集する場合は、以下のガイドラインに従ってください：

* 新しいIDを作成する場合は、小文字のみを使用してください。
* 単語を区切るにはハイフン`-`を使用します。アンダースコア`_`は使用しないでください。
* ドキュメントを再編成する際は、可能な限り受信アンカーリンクを保持するようにしてください。レベル2の見出し`##`を削除すると、その見出しへのリンクが切断されることに注意してください。
* 内部のNew Relicアカウントからそのトラフィックを監視している可能性があるため、既存のアンカーIDを変更しないでください。

## 製品へのディープリンク [#deep-links]

ユーザーを製品の一部に誘導する場合は、可能な限りディープリンクを使用することをお勧めします。ディープリンクは、ユーザーが製品にアクセスすることを促し、アカウントをまだ作成していない場合は、サインアップするようにプロンプトを出します。これは、単にサインアップページにリンクするよりも効果的です。ただし、UIへのディープリンクは機能しない場合もあり、適切なパーマリンクを見つけるにはいくつかの実験が必要です。

ログUIを使用したワークフローの例は次のとおりです：

1. 職場のアカウントから、リンクするUIの部分に移動します。自然に表示される完全なURLを取得します。
2. シークレットウィンドウを開き、URLを貼り付けます。
3. URLをよりクリーンな状態に編集してください。可能な場合はシンプルなURLを使用してください。ログの場合、これは次のようになります：`https://one.newrelic.com/logger`。
4. New Relicはサインインするようにプロンプトを出すため、職場以外のメールアドレスでサインインしてください。

URLはログページに移動し、アカウントIDの識別情報を自動補完します。そのページはディープリンク可能です。

シンプルなURLが機能しない場合は、2つの追加手順があります。シンプルなURLが機能しないワークフローの例を次に示します。このURLをベースとして使用します：

```
https://one.newrelic.com/marketplace/install-data-source?account=[ACCOUNT_ID_HERE]&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
```

1. URLを見つけたら、シークレットウィンドウを開き、シンプルなURLを貼り付けます：`https://one.newrelic.com/marketplace/install-data-source`このページは簡略化されたURLでは読み込まれません。

2. スラッグの`account=[ACCOUNT_ID_HERE]`部分を削除して、このURLをテストします。新しいURLは次のようになります。

   ```
   https://one.newrelic.com/marketplace/install-data-source?&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
   ```

3. そのURLを新しいシークレットウィンドウに貼り付けます。固有のアカウントIDが入力された正しいページに移動します。

4. アカウントID番号を削除した状態でURLを開いてもらい、このURLが機能することを別のライターに確認してください。仕事用以外のメールアドレスを使用する必要があります。

どちらの場合もURLが機能しない場合は、製品UIのその部分がディープリンク可能ではない可能性があります。その場合は、`one.newrelic.com`を**All capabilities**ページにリンクし、[パスのガイドライン](/docs/style-guide/formatting/ui-paths)に従ってパスを説明してください。

## 外部リンク [#hyperlinks-external]

`docs.newrelic.com`サブドメイン外のWebサイト（`newrelic.com`、`one.newrelic.com`、`discuss.newrelic.com`を含む）へのリンクを作成する場合、ドキュメントサイトはリンクを新しいタブで開くコードを自動的に含めます。

このドキュメントのリンクテキストのガイドラインに加えて、外部サイトにリンクする際に留意すべきその他の事項を以下に示します：

* リンクを将来にわたって有効に保つための最善の方法を検討してください。可能であればトップレベルドメインを指すようにしますが、リンクの有用性が低下する場合はこの限りではありません。リンク先のコンテンツはどの程度安定していますか？URLが変更される可能性はありますか？
* リンクが可能な限り役立つものであることを確認してください。ドキュメントにどのような価値を追加しようとしていますか？その情報は別の方法で共有できますか？
* この外部ソースにリンクしている理由を読者が理解できるようにしてください。タイムゾーンのリストなど、役立つリファレンスですか？見つけにくいファイルに直接リンクするなど、時間を節約する方法ですか？
* リンクが一般にアクセス可能であることを確認してください。プライベートなGitHubリポジトリなど、認証が必要な外部サイトにリンクしていますか？
