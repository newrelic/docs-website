New Relicコンテンツ全体で一貫性を保つため、一般的な単語の使用ガイドラインを以下に示します：

* 一般的に、Chicago Manual of Styleに基づく[Microsoft Style Guide](https://docs.microsoft.com/en-us/style-guide/welcome/)に従います。
* イギリス英語ではなく、アメリカ英語の規則に従います。
* 製品への言及については、公式の製品名に従います。（たとえば、Amazon Web Services (AWS)については、[aws.amazon.com/products](https://aws.amazon.com/products/)をご覧ください。）
* New Relic固有の用語については、[製品用語集](/docs/using-new-relic/welcome-new-relic/getting-started/glossary)を使用します。

<CollapserGroup>
  <Collapser id="account" title="アカウント">
    New Relicにサインアップすると、New Relic組織（組織IDで表されます）が提供されます。その組織には、1つ以上のアカウント（各アカウントにはアカウントIDがあります）を含めることができます。`organization`と`account,`の違いの詳細については、[組織とアカウント構造](/docs/accounts/accounts-billing/account-structure/new-relic-account-structure)を参照してください。

    New Relic以外の一般的な使用法では、`account`はより広い意味でよく使用されます。たとえば、私たちが`organization,`を使用するのと同じ方法で使用されたり、誰かのユーザーレコードを指すために使用されたりする場合があります。これらの用語を使用する際は、できるだけ正確になるように努める必要があります。これは、New Relic組織ではなく、New Relicアカウントにのみ適用される側面（たとえば、アカウントレベルのデータやクエリの制限）を文書化する場合に特に当てはまります。

    とはいえ、使用法が一般的であればあるほど、`organization`の同義語として`account`を使用することが許容されます。たとえば、New Relicでは「New Relicアカウントにサインアップする」のようなフレーズを使用することがあります。`organization`の代わりに`account`を使用することは、`account`の一般的な使用法と一致しており、`account`の定義に固有のものを参照しているわけではないため、問題ありません。
  </Collapser>

  <Collapser id="account-id" title="アカウントID">
    [特定のNew Relicアカウントを識別する](/docs/accounts-partnerships/accounts/account-setup/account-id)一意の番号。`account number`は使用しないでください。
  </Collapser>

  <Collapser id="agent" title="エージェント">
    New Relicエージェントは、インストール可能なソフトウェアであり、さまざまな種類のテクノロジー（ウェブフレームワーク、OS、データベースのタイプなど）と統合し、通常は特定の頻度でNew Relicにデータを報告します。すべてのエージェントはインテグレーションですが、すべてのインテグレーションがエージェントであるとは限りません。多くのエージェントは複数のインテグレーションをサポートしています；たとえば、JavaエージェントはさまざまなJavaフレームワークやテクノロジーからデータを収集し、infrastructureエージェントはオンホストのCassandraインテグレーションを有効にします。

    New Relicエージェントと見なされるもののリストは次のとおりです：

    * APM：

      * Goエージェント
      * Javaエージェント
      * .NETエージェント
      * Node.jsエージェント
      * PHPエージェント
      * Pythonエージェント
      * Rubyエージェント

    * インフラストラクチャ：

      * インフラストラクチャー・エージェント
      * Linuxエージェント
      * MacOSエージェント
      * Unixエージェント
      * Windowsエージェント

    * Browserエージェント

    * モバイル：

      * Androidエージェント
      * iOSエージェント
      * ハイブリッドエージェント（Capacitor、Flutterなど）

    * ネットワーク：

      * ktranslateエージェント
      * ネットワークフローエージェント

    * SNMPエージェント

      * Syslogエージェント

    * Roku

    * Elixir

      インテグレーションと見なされるもののリストについては、[インテグレーション](#integration)の定義を参照してください。
  </Collapser>

  <Collapser id="AIOps" title="AIOps">
    ITオペレーション向け人工知能の略です。
  </Collapser>

  <Collapser id="ampm" title="午前と午後">
    * 12時間表記を使用し、その後に（小文字の）期間amまたはpmを続けます。

    * タイムスタンプの最後の数字の後にスペースを入れないでください（12:00 amではなく、12:00am）。

    * 時間が10未満の場合、先頭に0を含めないでください。

      ```
      9:30am, 12:30pm, 8:30pm
      ```
  </Collapser>

  <Collapser id="aws" title="Amazon Web Services (AWS)の製品名">
    * 会話では一般的に`AWS`と呼ばれます。最初のインスタンスでは`Amazon Web Services`を参照し、その後は`AWS`を使用できます。
    * Amazonには、[Amazon EC2](https://aws.amazon.com/documentation-overview/ec2/)や[Amazon S3](https://aws.amazon.com/documentation-overview/s3/)など、正式名称ではなく略称で呼ばれることがほとんどである製品が多数あります。Amazonが略称を使用している場合は、最初のインスタンスで略称を使用できます。
    * 一部のAmazon製品はプレフィックスとして`Amazon`を使用し（`Amazon EC2`のように）、他の製品は`AWS`を使用します（`AWS Amplify`のように）。[AWSドキュメントサイト](https://aws.amazon.com/documentation)に合わせてください。
    * 一部のAmazon製品名は、データや設定オプションを参照するために、より非公式な方法で使用されることもあります。たとえば、[AWSメトリクスストリーム](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Metric-Streams.html)の場合、AWSは製品を参照する際にはその名前をタイトルケースでフォーマットしますが、生成されたデータを参照する際には非公式に参照します（たとえば、`metric stream data`や`metric streams`として）。一般的に、AWSが行っていることに従う必要があります。
  </Collapser>

  <Collapser id="ampersand-details" title="アンパサンド（&）">
    会社名やブランド名の一部である場合を除き、文や見出しにアンパサンドを使用しないでください。例外：スペースが限られている場合（つまり、「and」が収まらない場合）、アンパサンドを使用してもかまいません。
  </Collapser>

  <Collapser id="app-name" title="アプリ名対アプリエイリアス">
    Collectorがアプリを一意に識別するために使用する&quot;マシン名&quot;は、その`app name`です。一意の識別子を変更せずにアプリの表示される&quot;名前&quot;を変更するサーバーサイドコンフィグレーション設定は、その`app alias`です。
  </Collapser>

  <Collapser id="Azure naming conventions" title="Azure命名規則">
    Microsoftが規定するMicrosoft Azure cloudコンピューティングプラットフォームの命名規則を使用してください；これは顧客が理解し認識しているものです。たとえば、Azure Native New Relic Serviceです。
  </Collapser>

  <Collapser id="backend" title="バックエンド">
    形容詞として使用される場合でも名詞として使用される場合でも、これは1つの単語です。[`frontend`](#frontend)も参照してください。
  </Collapser>

    使用しないでください。代わりに`deny list`と`allow list`を使用してください；たとえば、「拒否リストにホスト名を追加します。」

  <Collapser id="call-called" title="呼び出し、呼び出し元、および呼び出し先">
    あるエンティティが別のエンティティとどのように通信するか、または接続されるかを説明する場合は、呼び出しと、それらがどの方向に進んでいるかに焦点を当てます。これらのインタラクションを説明するために`upstream`や`downstream`を使用することは避けてください。たとえば、`service A calls service B`、`called services`、`calling services`。
  </Collapser>

  <Collapser id="child-account" title="子アカウント">
    [親アカウント](#parent-account)には、1つ以上の子アカウントが含まれます。子アカウントは、以前は「サブアカウント」と呼ばれていました。

  <Collapser id="click" title="クリック">
    一般に、あいまいな`select`ではなく`click`を使用します。たとえば、UIで何かをクリックしてから、リストから何かを選択する場合があります。

    マウスでのみ意味を持つアクションを説明するために`click`を使用する場合は、特に注意してください；たとえば、`right click`や`click and drag`を使用する場合などです。また、ユーザーが選択できないオブジェクト（`to save your changes, click anywhere outside the dialog box`）をクリックする必要がある場合は、`click`を使用します。[mouse over](#mouse-over)も参照してください。
  </Collapser>

  <Collapser id="collector" title="コレクターとNew Relicへの接続">
    New Relicサーバーと通信するエージェントに言及する場合は、これを[New Relicコレクター](/docs/accounts-partnerships/education/getting-started-new-relic/glossary#collector)として説明してください。内部的には`collector`は当社のアーキテクチャーの特定の部分のみを指しますが、ドキュメントではより広く、&quot;顧客が任意の製品のデータを報告するために接続する必要がある任意のエンドポイント&quot;を意味するために使用します。&quot;New Relicに接続する&quot;は避け、&quot;New Relic UIに接続する&quot;は使用しないでください。
  </Collapser>

  <Collapser id="contractions" title="縮小">
    明確さ、簡潔さ、トーンとボイスのために意味がある場合は、短縮形を使用してください。文章をより自然な話し言葉のように聞こえさせ、専門知識や権威を犠牲にすることなく明確さとアクセシビリティを向上させる場所で、それらを使用してください。

    どの短縮形が許容されるか、または許容されないかについての厳密なルールはありませんが、複雑でまれなものよりも、シンプルで一般的なものが推奨されます。たとえば、`it is`の代わりに`it's`を使用するのは問題ありませんが、`mustn't`や`wouldn't've`のようなあまり一般的ではない構成は避けるのが最善です。

    また：

    * 否定の短縮形（`don't`、`can't`、`won't`）を使用する場合は、何をすべきか、何ができるかについて追加情報を提供するようにしてください。（詳細については、[スタイルガイドの概要](/docs/new-relic-only/basic-style-guide/writing-guidelines/introduction-style-guide#tone)を参照してください。）
    * ドキュメントの中には — たとえば、メモや警告など — 回避すべきアクションやブロックを強調するために、短縮形よりも`do not`、`cannot`、または`will not`をスペルアウトする方が好ましい場合があります。
  </Collapser>

  <Collapser id="customer-vs-user" title="顧客とユーザー">
    可能な場合は、読者とのつながりを感じさせるために、二人称の`you`を使用します。分かりやすい三人称名詞が必要な場合は、次のガイドラインに留意してください：

    * `customer` および`user`は、コンテキストに応じてどちらも適切です。
    * `customer` 請求、または人々のグループやビジネスエンティティについて話す場合により意味をなします。たとえば、1人の顧客には、顧客のアカウントを通じてNew Relicとやり取りする1人以上の個別のユーザーがいる場合があります。
    * `user` 個々のユーザーの一般的な用語として、またはアカウントモデルのオブジェクトとしてユーザーについて話す場合により意味があります。たとえば、アカウントモデルについて議論する場合、システム内で単一の個人のアイデンティティを構成するものを明確にすることが重要です。
  </Collapser>

  <Collapser id="cyber words" title="サイバー用語">
    `cyber`で始まる単語（`cyberattack`、`cybersecurity`、`cyberspace`、`cyberthreat`など）を区切ったりハイフンで繋いだりしないでください。
  </Collapser>

  <Collapser id="dashboard" title="ダッシュボード">
    一般的な業界の観点から見ると、通常、`dashboard`は画面上の1つ以上のチャートまたはその他のウィジェットを指します。この一般的な定義は、[ダッシュボードのWikipediaエントリ](https://en.wikipedia.org/wiki/Dashboard_\(business\))で確認できます。

    New Relicでは、`dashboard`という用語をいくつかの異なる方法で使用しています：

    * Dashboardsは、[機能ページ](https://newrelic.com/platform/dashboards)にあるように、`New Relic dashboards`と呼ばれるNew Relicの機能を指します。このコンテキストでは、`New Relic dashboards`は、コアプラットフォームエクスペリエンス（たとえば、APM、ブラウザ監視、OpenTelemetryなどのUI）に組み込まれていないカスタマイズされたビューを作成および使用する機能を指します。これらのカスタムダッシュボードは、**Dashboards** UIページにあります。
    * Dashboardsは、キュレートされたダッシュボードを指すこともあります。これらのダッシュボードは、顧客が当社のコアプラットフォームソリューション（たとえば、APM、インフラストラクチャ、およびブラウザ監視のUIエクスペリエンス）を使用する際に得られるデフォルトのビューです。

    カスタマイズされたダッシュボードには、[New Relicアプリ](https://opensource.newrelic.com/nerdpacks/)にあるダッシュボードや、[Instant Observabilityページ](https://newrelic.com/instant-observability)のクイックスタートにあるダッシュボードが含まれます。たとえば、[.NETクイックスタート](https://newrelic.com/instant-observability/dotnet)を見ると、厳選されたエクスペリエンスの一部ではない追加のダッシュボードが1つ付属していることがわかります。

    一般的な用語である「ダッシュボード」を使用する際に曖昧さがあると思われる場合は、次の使用方法をお勧めします：

    * Nerdpack、クイックスタート、または顧客やそのチームによって作成されたダッシュボードにあるカスタムエクスペリエンスを指すには、`custom dashboards`、`customizable dashboards`、または`quickstart dashboards`を使用します。
    * よりキュレートされたビューを指すには、`curated views`、`curated dashboards`、`New Relic-built dashboards`、`APM dashboards`、`APM views`を使用します（いくつか例を挙げると）。

    コンテキストを確立するために、できるだけ具体的にすることをお勧めします。文章でそのコンテキストが一度確立されている場合は、一般的な`dashboard`を自由に使用してください。
  </Collapser>

  <Collapser id="data-center" title="データセンター">
    [1語とするMicrosoftのガイダンス](https://learn.microsoft.com/en-us/style-guide/a-z-word-list-term-collections/d/datacenter)から逸脱し、1語（`datacenter`）ではなく2語（`data center`）とします。これは、契約との一貫性を保つためです。
  </Collapser>

  <Collapser id="data-sheet" title="データシート">
    データシートに言及する場合は、`datasheet`ではなく`data sheet`となるように2つの単語に分けてください。
  </Collapser>

  <Collapser id="DevOps" title="DevOps">
    ソフトウェア開発者と運用の略です。
  </Collapser>

  <Collapser id="document" title="doc、document、documentation、docs site">
    ドキュメント自体を参照する必要がある場合—参照しないでください。一般的に、参照しているドキュメントに直接リンクし、ドキュメントのタイトルをリンクテキストとして使用することをお勧めします。たとえば、`See our [.NET agent install docs](URL)`ではなく`See [Install the .NET agent](URL)`です。

    適切な代替案がない場合、一般的に`doc`は`document`や`documentation`よりも自然に聞こえます。長い形式を使用したい場合は、声に出して読んでみて、どれが最も読みやすいかを確認してください。

    サイト全体を指す必要がある場合は、`Docs site`や`documentation site`ではなく`docs site`と呼びます。内部的には、内部プラットフォームドキュメントやAPIエクスプローラードキュメントなどの他のドキュメントソースとの曖昧さを避けるために、URL全体`docs.newrelic.com`を参照することもできます。[当社のドキュメントのGitHubリポジトリ](https://github.com/newrelic/docs-website)を指すには、リポジトリ名`docs-website`またはリポジトリパス`newrelic/docs-website`を使用します。
  </Collapser>

  <Collapser id="downstream-upstream" title="ダウンストリームとアップストリーム">
    エンティティが互いにどのように関連しているかを説明するためには使用しないでください。ダウンストリームとアップストリームの解釈は人によって大きく異なるため、関連するエンティティ要素で行っているように、特定の種類の接続に焦点を当てます：呼び出し、作成、ホスト、保守など。

    例えば：

    * `[Service A] calls [service B]`
    * `Called services`
    * `Calling services`
    * `maintained by [repository name]`
  </Collapser>

  <Collapser id="dropdown" title="ドロップダウン">
    `drop-down`や`drop down`の代わりに`dropdown`を使用します。

    一般的な用法ではありませんが、`dropdown menu`や`dropdown list`と言う必要なく、`dropdown`を独立して名詞として使用できます。たとえば、`select a date from the **Date** dropdown`。
  </Collapser>

  <Collapser id="eg" title="e.g.とi.e.">
    これらのラテン語の略語は避けてください。

    `e.g.`の代わりに、`for example`または`such as`を使用してください。`i.e.`の代用はより複雑です。なぜなら、`that is`を意味するために使用されることもあれば、`for example`を意味するために誤用されることもあるためです。コンテキストを読んで明確にしてください。ただし、通常は、説明テキストを必要とせずに説明が明確になるように書き直すことが最善の解決策です。
  </Collapser>

  <Collapser id="ellipses" title="省略記号">

  <Collapser id="event" title="イベント">
    イベントについて最適に記述する方法を理解するには、以下を読むことをお勧めします：

    * [データ型ドキュメントのイベントセクション](/docs/data-apis/understand-data/new-relic-data-types/#event-data)

    * [&quot;イベント&quot;の用語集エントリ](/docs/glossary/glossary/#event)

      イベントについて記述する際の言語に関するいくつかの考慮事項は次のとおりです。

    * 私たちが時々「イベント」という言葉をどのように使用するかについての曖昧さと歴史を理解することが重要です。`Metric`、`Log`、および`Span`という他の3つのコアデータ型が展開される前は、New RelicではNRDBに保存されたすべてのオブジェクトを「イベント」と呼んでいました。このため、社内や時には社外でも、すべてのNRDBオブジェクトを「イベント」と呼ぶことがまだあります。（たとえば、[クエリUI](/docs/query-your-data/nrql-new-relic-query-language/get-started/rate-limits-nrql-queries/#inspected-count-limits)では、現在でも「検査されたイベント」を使用しており、これはすべてのNRDBデータ型を指します）。ただし、一般向けの公開リソースでは、`Metric`、`Log`、または`Span`のデータ型**ではない**NRDBに保存されたデータを指すために「イベント」を使用するように努める必要があります。

    * 「イベント」の概念が「メトリクス」の概念とどのように重なるかを理解することが重要です。どちらも幅広い一般的な用語であるため、意味に多少の重複が生じる可能性があります。メトリクスは単なる測定値であるため、すべてのNew Relicデータ（イベント、スパン、ログ）はメトリクスである、またはメトリクスを含んでいると言えます。例：当社のinfrastructureモニタリングによって報告されるイベントにはさまざまなメトリクスが含まれていますが、これらは単なるさまざまな種類の数値測定値です（[メトリクスを含むインフラストラクチャイベントの詳細を読む](/docs/data-apis/understand-data/new-relic-data-types/#metric-event-attributes)）。
  </Collapser>

  <Collapser id="metric" title="メトリック">
    業界での`metric`という単語の使用方法とNew Relicでの使用方法の説明については、[データ型](/docs/data-apis/understand-data/new-relic-data-types/#metrics)をご覧ください。

    * &quot;メトリクス&quot;という言葉は幅広く一般的な概念であり、New Relicには[&quot;メトリクス&quot;と呼ばれる多数のデータ型とデータレポートメソッド](/docs/data-apis/understand-data/new-relic-data-types/#metrics-new-relic)があることに注意してください。

    * 最適なメトリクスデータ形式は、次元メトリクスデータ、別名`Metric`データ型です。そのデータはメトリクスAPIを介してレポートされます。これは、4つのコア「MELT」データ型（メトリクス、イベント、ログ、およびトレース）の「メトリクス」について話すときに、私たちが主に指している「メトリクス」データです。

    * 当社の元のメトリクスデータ形式は、メトリックタイムスライスデータと呼ばれます。これは現在でも、APM、ブラウザ監視、およびモバイル監視によって報告されます。これは非常にシンプルな形式のメトリクスデータであり、NRDBに保存されていなかったため、NRQLでクエリを行うことはできませんでした。現在、APMのメトリックタイムスライスデータはNRDBにミラーリングされているため、[NRQLを介してクエリを行えます](/docs/data-apis/understand-data/metric-data/query-apm-metric-timeslice-data-nrql)。

      スタイルに関するいくつかの推奨事項：

    * **データ構造やレポートプロセスについて詳しく説明するのではなく、一般的に「メトリクス」について話すようにしてください**。一般的に、ディメンショナルメトリクス（`Metric`データ型）、メトリックタイムスライスデータ、またはインフラストラクチャイベント属性として報告されるメトリクスのいずれについて話す場合でも、単に「メトリクス」または「メトリックデータ」を使用できます。ドキュメントやUIのほとんどのケースでは、顧客がデータの種類を正確に知る必要はあまりないと考えられています。ただし、データの種類を知ることが役立つと思われる場合（たとえば、そのデータのクエリ方法について話す場合など）は、データの種類についてさらに詳しく説明できます。

    * メトリクスデータのタイプを簡単な方法で明確にしたい場合は、[このセクション](/docs/data-apis/understand-data/new-relic-data-types/#metrics-new-relic)の特定のメトリクスデータタイプのコラプサーにリンクできます。たとえば、次のようにすることができます：「このインテグレーションは[メトリクスデータ](/docs/data-apis/understand-data/new-relic-data-types/#dimensional-metrics)を報告します。」
  </Collapser>

  </Collapser>

  <Collapser id="original" title="オリジナル">
    まだ使用されている可能性のある製品、機能、およびケイパビリティの最初または以前のバージョンを指す場合は、&quot;レガシー&quot;の代わりに使用します。&quot;Original&quot;は機能の有効性と継続的なサポートを伝えますが、&quot;レガシー&quot;という言葉は機能がサポートされなくなったと誤って伝える可能性があります。
  </Collapser>

  <Collapser id="pages" title="ページ">

  </Collapser>

    親アカウントは以前に[マスターアカウント](#master-account)と呼ばれており、コードベースにはまだこの使用例がいくつか残っています。

  <Collapser id="quickstart" title="クイックスタート">
    [クイックスタートの用語集の項目](/docs/new-relic-solutions/get-started/glossary)を参照してください。提供しているすべてのものがクイックスタートであるとは限らないことに注意してください。`quickstart`という用語は、Instant Observabilityページエントリの`Install now`インストールルート用に予約する必要があり、そのクイックスタートルートに従わないエージェントやインテグレーションのインストレーションやセットアップを指すために使用しないでください。

  <Collapser id="real-user-monitoring" title="リアルユーザー監視（RUM）">
    これをブラウザ監視のドキュメント以外で使用しないでください。RUMと略されることが多いですが、これはブラウザ監視を表す一般的な業界用語です。New Relicでは、通常これを`page load timing`または`browser monitoring`と呼びます。この用語はSEOまたは明確化の目的でのみ使用し、実際の機能を参照するためには使用しないでください。
  </Collapser>

  <Collapser id="record" title="record vs. report vs. collect">
    「ホストがNew Relicにデータを報告する」など、New Relicに送信されるデータについて説明する場合は、`report`を使用します。

    名詞として「report」を使用することは避けてください。代わりに「the reported metrics」または「the collected data」を使用してください。

    &quot;report&quot;という表現が不自然に聞こえる場合は、New Relicが収集しているものがセキュリティ上機密であるように聞こえない限り、`collect`を使用することもできます。
  </Collapser>

  <Collapser id="update" title="updateとupgradeの比較">
    ユーザーが使用しているもののバージョンを変更する必要がある場合は、`update`を使用します。アップデートに金銭や支払いは必要ありません。

    製品のProバージョンへのアップグレードなど、金銭や支払いが関係する可能性がある場合は常に`upgrade`を使用してください。新しい価格モデルでは、これを使用する必要がある可能性は低いです。
  </Collapser>

    ユーザーロールやグループなどに関連するスタイルと形式については、[ユーザー関連のスタイル](/docs/style-guide/word-choice/user-related-language-guidelines/)を参照してください。
  </Collapser>

  <Collapser id="username" title="user nameではなくusername">
    2語ではなく、1語（`username`）です。[これが最も一般的な使用法](https://trends.google.com/trends/explore?geo=US&q=%22user%20name%22,%22username%22)であり、MicrosoftおよびGoogleのスタイルガイドで推奨されています。
  </Collapser>

  <Collapser id="version" title="バージョン番号の参照">
    複数のバージョン番号を参照する場合は、`or higher`または`or lower`を使用します。`and higher`（`or`よりも曖昧です）、または`greater`や`later`という単語は使用しないでください。また、`version 1.2+`や`<version 1.2`のように句読点を使用しないでください。`1.2.X`スタイルの参照は避け、代わりに正確なバージョン番号を使用してください。例を以下に示します。

    ```
    Foo requires Ruby agent version 1.2.3 or higher
    ```

    ```
    Bar is compatible with ActiveMerchant version 4.5.6 or lower
    ```

    コンテキストによっては、`version`と`versions`の両方が機能することがわかります；確信が持てない場合は、声に出して読んでみてください。

    その他の使用上の注意：

    * ユーザーには、`up-to-date`や`current`のバージョンではなく、`latest version`を使用するように伝えてください。
    * `version`という単語を省略するには、数字の前にスペースを入れずに小文字の`v`を使用します。たとえば、`v2`や`v1.2.3`などです。
    * 「最新バージョンに更新するには...」のように、エージェントのバージョンについて話すときは、`upgrade`ではなく`update`を使用してください。
    * バージョンをより曖昧に参照する場合は、`in earlier agent versions`の使用を検討してください。
  </Collapser>

  <Collapser id="we" title="私たち">
    文章の流れに合う場合は、`we`および`our`と記述します。段落に`New Relic`の言及を詰め込みすぎないようにするか、New Relicではなくユーザーに焦点が当たるように言い換えてください。たとえば、次のような記述は避けてください：

    ```
    New Relic recommends setting a startup timeout.
    ```

    代わりに、次のように記述します：

    ```
    Recommendation: To help with troubleshooting, include a startup timeout in your configuration.
    ```

    また

    ```
    We recommend setting a startup timeout.
    ```
  </Collapser>
