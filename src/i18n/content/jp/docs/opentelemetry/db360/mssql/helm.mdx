`mssql-otel` Helmチャートを使用して、Kubernetes上にSQL Serverの監視をインストールおよび構成できます。オプションとして、チャートは監視用のログインを作成するセットアップジョブを実行することもできます。

<Callout variant="tip" title="ガイド付きインストレーション">
  代わりにNew Relic UIからこれをインストールするには、<DNT>**[one.newrelic.com &gt; Integrations &amp; Agents &gt; Microsoft SQL Server (Database 360)](https://onenr.io/00jlEJX6EQW)** </DNT>に移動してください。画面上の指示に従って、インテグレーションをセットアップします。このページでは、手動インストレーションについてのみ説明します。
</Callout>

<Callout variant="important">
  このチャートは、SQL Server認証（ユーザー名/パスワード）のみをサポートします。Windows認証、Windowsドメイン認証、またはgMSAはサポートしていません。コレクターは、LinuxまたはWindows、セルフホストまたはRDSのいずれで実行されているかにかかわらず、常にネットワーク経由でリモートからSQL Serverにアクセスします。そのため、SQL認証はすべての場合において同じように機能します。また、コレクターはSQL Serverホスト自体ではなく、Kubernetesデプロイメントとして実行されるため、SQL Serverのメトリクスのみを報告します（ホスト/インフラストラクチャのメトリクスはありません）。
</Callout>

<Steps>
  <Step>
    ## 前提条件 [#helm-prerequisites]

    * 有効なNew Relicの[ライセンスキー](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key)。

    * Helm 3.0以降、およびKubernetesクラスタにアクセスするように設定された`kubectl`。

    * KubernetesクラスタからSQL Serverホスト（またはRDSエンドポイント）およびポートへのネットワーク接続：

      * セルフホスト：SQL Serverホストへのルーティングされたパス（VPN、ピアリング、または共有ネットワーク）が必要であり、SQL Server側のファイアウォールは接続の送信元IPを許可する必要があります。
      * AWS RDS：RDSインスタンスとのVPCピアリング、トランジットゲートウェイ、または共有VPCへの配置が必要であり、RDSセキュリティグループでクラスタのエグレスソースからのSQL Serverポート（デフォルトでは`1433`）を許可する必要があります。

    * すでに作成済みの監視ログイン、またはチャートのセットアップジョブが監視ログインを作成できるようにするためのSQL Server管理者認証情報（`sa`やRDSマスターユーザーなどの`sysadmin`ロールのログイン）のいずれかが必要です。以下の[監視認証情報の設定](#helm-credentials)を参照してください。
  </Step>

  <Step>
    ## ネームスペースを作成 [#helm-namespace]

    インストール先のネームスペースを作成します。`helm install --create-namespace`は最後のインストール手順でのみネームスペースを作成するため、次の手順でシークレットを作成する前に、ネームスペースが存在している必要があります：

    ```bash
    kubectl create namespace newrelic
    ```

    <Callout variant="tip">
      以下のすべてのコマンドで`-n`を渡す必要がないように、現在の`kubectl`コンテキストのデフォルトのネームスペースとして設定します：

      ```bash
      kubectl config set-context --current --namespace=newrelic
      ```
    </Callout>
  </Step>

  <Step>
    ## 監視資格情報の設定 [#helm-credentials]

    チャートのセットアップジョブにSQL Serverの監視ログインを作成させるかどうかを決定し、作成させない場合は、その資格情報をどのように提供するかを決定してください：

    <CollapserGroup>
      <Collapser id="helm-creds-inline" title="セットアップジョブなし：プレーンなユーザー名とパスワード">
        この方法ではセットアップジョブがないため、ここで監視ログインが作成されることはありません。このチャートはSQL Server認証のみをサポートしているため、インストールする前に、環境に応じて[ Linuxセルフホスト](/docs/opentelemetry/db360/mssql/linux-hosted/#user) 、[ Windowsセルフホスト](/docs/opentelemetry/db360/mssql/windows-hosted-sql/#user-sql) 、[ Linux RDS](/docs/opentelemetry/db360/mssql/linux-rds/#user) 、または[ Windows RDS](/docs/opentelemetry/db360/mssql/windows-rds-sql/#user-sql)** のSQL Server認証の 監視ユーザーの作成** ステップを使用して、ご自身で監視ログインを作成してください。

        次のステップで、監視用のユーザー名とパスワードを直接`values.yaml`に設定します。
      </Collapser>

      <Collapser id="helm-creds-secret-nojob" title="セットアップジョブなし：シークレットベースの認証情報">
        この方法でも、セットアップジョブはありません。まず、上記の plain-credentials メソッドとまったく同じように、ご自身で監視ログインを作成してください。唯一の違いは、資格情報の保存場所です：`values.yaml`にプレーンテキストで保存する代わりに、Kubernetesシークレットに保存します：

        ```bash
        kubectl create secret generic mssql-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        ```
      </Collapser>

      <Collapser id="helm-creds-setupjob" title="自動セットアップジョブ">
        この方法では、チャートのセットアップジョブが、SQL Serverの管理者資格情報を使用して監視ログインを作成します。監視と管理者の両方の資格情報は、Kubernetesシークレットとして提供する必要があります：セットアップジョブはプレーンテキストの管理者資格情報を受け入れることはなく、セットアップジョブを有効にするにはシークレットベースの監視資格情報も必要になります。

        1. 監視のユーザー名とパスワードを使用してシークレットを作成します。これは、セットアップジョブが作成し、コレクターが接続に使用するIDです：

           ```bash
           kubectl create secret generic mssql-monitor-creds \
             --from-literal=username=<MONITORING_USERNAME> \
             --from-literal=password='<MONITORING_PASSWORD>' \
             -n newrelic
           ```

        2. セットアップジョブは、Kubernetesシークレット経由でのみ管理者資格情報を受け入れます（`values.yaml`にプレーンテキストのユーザー名/パスワードを含めることはできません）。この資格情報はログインを作成し、幅広い`VIEW`アクセスを付与できるため、独自のシークレットとして作成してください。セルフホスト型のSQL Serverには`sysadmin`ロール（または同等のもの）のログインを使用し、AWS RDS上のSQL ServerにはRDSマスターユーザーを使用してください：

           ```bash
           kubectl create secret generic mssql-admin-creds \
             --from-literal=username=<ADMIN_USERNAME> \
             --from-literal=password='<ADMIN_PASSWORD>' \
             -n newrelic
           ```
      </Collapser>
    </CollapserGroup>
  </Step>

    <CollapserGroup>
      <Collapser id="helm-values-inline" title="セットアップジョブなし：プレーンなユーザー名とパスワード">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: https://otlp.nr-data.net:4318

        mssql:
          topology: <self-hosted|rds>
          server: <YOUR_DB_HOST>
          port: <YOUR_DB_PORT>

          password: <YOUR_MONITORING_PASSWORD>

        # before installing the chart.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-values-secret-nojob" title="セットアップジョブなし：シークレットベースの認証情報">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: https://otlp.nr-data.net:4318

        mssql:
          topology: <self-hosted|rds>
          server: <YOUR_DB_HOST>
          port: <YOUR_DB_PORT>
          existingSecret: mssql-monitor-creds

        # No setup job runs, so the monitoring login referenced by
        # this secret must already exist - create it yourself
        # before installing the chart.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-values-setupjob" title="自動セットアップジョブ">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: https://otlp.nr-data.net:4318

        mssql:
          topology: <self-hosted|rds>
          server: <YOUR_DB_HOST>
          port: <YOUR_DB_PORT>
          existingSecret: mssql-monitor-creds

        setupJob:
          enabled: true
          image:
            # -- sqlcmd image. No default: see the chart's README for why
            # (mcr.microsoft.com/mssql-tools:latest is freely pullable but
            # stale and unmaintained).
            repository: ""
            tag: ""
            pullPolicy: IfNotPresent
          sqlAdmin:
            existingSecret: mssql-admin-creds
        ```
      </Collapser>

  <Step>
    ## (オプション) 1つのリリースから複数のインスタンスをモニターする [#helm-multi]

    1つのリリースで単一のコレクターポッドから複数のSQL Serverインスタンス（セルフホスト型またはRDS）をモニターするには、`mssql.*`の代わりに`mssqlMulti.enabled: true`を設定します。2つのモードは相互に排他的です：同じリリースで`mssql.server`と`mssqlMulti.enabled: true`を設定しないでください。

    マルチインスタンスモードには、プレーンなユーザー名/パスワードのパスはありません：各インスタンスには、監視資格情報を含む独自のKubernetesシークレットが必要です。セットアップジョブで各監視ログインも作成するかどうかを決定します：

    <CollapserGroup>
      <Collapser id="helm-multi-nojob" title="セットアップジョブなし">
        インストールする前に、各インスタンスの監視ログインシークレットをご自身で作成してください（`values.yaml` で指定する `name` に合わせて、インスタンスごとに繰り返します）：

        ```bash
        kubectl create secret generic db1-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        # Repeat for every instance (db2-monitor-creds, ...)
        ```

        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: https://otlp.nr-data.net:4318

        # EDIT the two example entries below (or add more) to match
        # your real instances - each `name` must be unique within
        # this release and match the Secret you created for it.
        mssqlMulti:
          enabled: true
          topology: <self-hosted|rds>
          databases:
            - name: db1
              server: <YOUR_DB_1_HOST>
              existingSecret: db1-monitor-creds
            - name: db2
              server: <YOUR_DB_2_HOST>
              existingSecret: db2-monitor-creds

        # No admin credential is configured here since the setup
        # job is disabled - create each instance's monitoring login
        # yourself first.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-multi-setupjob" title="自動セットアップジョブ">
        各インスタンスには、独自の監視ログインシークレットと独自の管理者資格情報シークレットの両方が必要です（インスタンスごとに繰り返します）：

        ```bash
        kubectl create secret generic db1-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        kubectl create secret generic db1-admin-creds \
          --from-literal=username=<ADMIN_USERNAME> \
          --from-literal=password='<ADMIN_PASSWORD>' \
          -n newrelic
        # Repeat for every instance (db2-monitor-creds, db2-admin-creds, ...)
        ```

        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: https://otlp.nr-data.net:4318

        # EDIT the two example entries below (or add more) to match
        # your real instances - each `name` must be unique within
        # this release and match the Secrets you created for it.
        mssqlMulti:
          enabled: true
          topology: <self-hosted|rds>
          databases:
            - name: db1
              server: <YOUR_DB_1_HOST>
              existingSecret: db1-monitor-creds
              sqlAdmin:
                existingSecret: db1-admin-creds
            - name: db2
              server: <YOUR_DB_2_HOST>
              existingSecret: db2-monitor-creds
              sqlAdmin:
                existingSecret: db2-admin-creds

        setupJob:
          enabled: true
          image:
            repository: ""
            tag: ""
        ```
      </Collapser>
    </CollapserGroup>

      スクレイプ設定（収集間隔、TLS、メトリクス）は、`mssqlMulti.databases`のすべてのインスタンスに同一に適用されます。インスタンスごとのオーバーライドはありません。異なる必要があるものには`additionalReceiverConfig`を使用します。セットアップジョブは、リリースごとに1回ではなく、インスタンス（`<release>-setup-<name>`）ごとに1回実行されます。

  <Step>
    ## Helmチャートをインストールする [#helm-install]

    1. New Relic Helm リポジトリを追加します。

       ```bash
       helm repo add newrelic https://helm-charts.newrelic.com
       helm repo update
       ```

    2. `values.yaml`ファイルを使用してチャートをインストールします：

       ```bash
       helm upgrade --install mssql-otel newrelic/mssql-otel \
         -n newrelic \
         --create-namespace \
         -f values.yaml
       ```
  </Step>

  <Step>
    ## インストレーションを確認する [#helm-verify]

    1. セットアップジョブが完了し（有効な場合）、コレクターポッドが実行されていることを確認します：

       ```bash
       kubectl get jobs,pods -n newrelic --watch
       ```

    2. データが到着していることを確認するには、[クエリビルダー](/docs/query-your-data/explore-query-data/query-builder/introduction-query-builder/)でこのクエリを実行してください：

       ```sql
       SELECT count(*) FROM Metric
       WHERE metricName LIKE 'sqlserver.%'
       AND instrumentation.provider = 'opentelemetry'
       SINCE 10 minutes ago
       ```
  </Step>

  <Step>
    ## データを探す、使う [#find]

    データの収集が開始されると、New Relic UIを通じて包括的なSQL Serverデータベース監視にアクセスできます。

    New Relic で SQL Server データベース エンティティを見つけるには:

    1. <DNT>**[one.newrelic.com](https://one.newrelic.com) &gt; All capabilities &gt; Databases**</DNT>に移動します。

    2. **<DNT>Entity type</DNT>**ドロップダウンから<DNT>**MSSQL instance**</DNT>を選択し、<DNT>**Apply**</DNT>をクリックします。

    3. エンティティのリストから SQL Server データベースを選択します。

       NRDOTを使用してSQL Serverの監視をセットアップした後、次のことができます：

       * データベースのメトリクスを視覚化する[カスタムダッシュボードを作成する](/docs/query-your-data/explore-query-data/dashboards/introduction-dashboards/)
       * クリティカルデータベースパフォーマンス閾値の[アラートを設定する](/docs/alerts/create-alert/create-alert-condition/alert-conditions/)
       * New Relicのクエリ機能を使用して、[データを探索](/docs/query-your-data/explore-query-data/browse-data/introduction-data-explorer/)します
  </Step>
</Steps>
