[Collectorオブザーバビリティの概要ページ](/docs/opentelemetry/collector-observability/collector-observability#summary-page)を開くと、コレクターの健全性を一目で確認できる6つのKPI（主要パフォーマンス指標）タイルが表示されます。いずれかのタイルをクリックすると詳細ビューが開き、基となるチャートに加えて、KPIの予期せぬ変化を調査するのに役立つ関連するテレメトリーチャートのセットが表示されます。ほとんどの場合、特定のシグナルタイプを選択すると、関連するテレメトリーをシグナルタイプまたはコンポーネント（エクスポーター/プロセッサー/レシーバー）ごとにファセット化できます。このページでは、各KPIの意味と、関連する各テレメトリーチャートが存在する理由について説明します。

## 受信したアイテム [#items-received]

レシーバー経由でコレクターに流入するテレメトリーの量。予期せぬ変化の一般的な原因は、アップストリームのクライアントの問題 — データを送信するインストゥルメントされたアプリケーションの増減 — または、レシーバーが、プルするように設定されたデータのスクレイピングに失敗していることです。

関連するテレメトリー：

* <DNT>**Receiver accepted**</DNT>: 合計をシグナルまたはレシーバーごとに分類するため、変更が正確にどこから発生しているかを把握できます。
* <DNT>**Receiver refused**</DNT>：ドロップの一部が、アップストリームトラフィックのドロップではなく、拒否されたテレメトリー（[Receiver refused](#receiver-refused)も参照）によるものかどうかを示します。
* <DNT>**Memory limiter drop ratio**</DNT>: レシーバーがデータを拒否するのは、最終的に[memorylimiter](https://github.com/open-telemetry/opentelemetry-collector/tree/v0.161.0/processor/memorylimiterprocessor)のブロックが原因である可能性があります。

## 送信したアイテム [#items-sent]

コレクターのエクスポーターによってダウンストリームの宛先に正常に送信されたテレメトリーです。予期しない変化の一般的な原因は、アップストリームの問題（プロセッサーによるデータのドロップ、レシーバーによるデータの拒否、またはクライアントからコレクターに送信されるデータの減少）、あるいはエクスポーターの障害です。

関連するテレメトリー：

* <DNT>**Exporter sent**</DNT>：合計をシグナルまたはエクスポーターごとに分類し、変更が正確にどこから発生しているかを把握できるようにします。
* <DNT>**Exporter failures**</DNT>：送信されるアイテムが少なくなる原因として、エクスポーターの失敗（[エクスポート失敗率](#export-failure-rate)を参照）を明らかにします。
* <DNT>**Exporter queue saturation**</DNT>：飽和状態の送信キュー（[キューの飽和](#queue-saturation)を参照）がアイテムの送信を保留しているかどうかを示します。

## キューの飽和 [#queue-saturation]

各エクスポーターの送信キューがどの程度満杯であるか；キューが満杯になるとデータ損失につながります。サチュレーションの急増の一般的な原因は、エクスポーターの障害によるキューの滞留、またはサイズが不十分なキューへのトラフィックの急増です。

関連するテレメトリー：

* <DNT>**Exporter send failures**</DNT>：失敗したエクスポートは時間がかかることがよくあります（例：タイムアウト）。これらは再試行につながり、キューの滞留を引き起こします。
* <DNT>**Exporter queue size vs. capacity**</DNT>: 設定された容量に対する実際のキューサイズを表示するため、飽和の原因がトラフィックの急増によるものか、単にキューのサイズが小さすぎるためかを判断できます。

## レシーバー拒否 [#receiver-refused]

レシーバーが積極的に拒否しているアップストリームのテレメトリーです。これは通常ゼロになります；継続的なレートは、ログを通じて診断すべき異常です。

関連するテレメトリー：

* <DNT>**Memory limiter drop ratio**</DNT>：[memorylimiter](https://github.com/open-telemetry/opentelemetry-collector/tree/v0.161.0/processor/memorylimiterprocessor)プロセッサーがブロックすると、レシーバーはテレメトリーの拒否を開始しますが、これが実際の根本原因となります。
* <DNT>**Process memory RSS**</DNT>: コレクターのメモリ使用量を表示することで、memorylimiterのメトリクスにコンテキストを提供します。
* <DNT>**Process runtime heap allocated**</DNT>：Goヒープの増加は不健全なガベージコレクションを引き起こす可能性があり、それが結果としてコレクターのスループットを低下させる可能性があります。

## エクスポート失敗率 [#export-failure-rate]

設定されている場合、失敗して再試行されるエクスポーターのrequestsの割合です。一般的な原因は、ネットワークの問題、またはエクスポーターや宛先の設定ミスです。

関連するテレメトリー：

* <DNT>**Exporter failures**</DNT>：シグナルまたはエクスポーターごとの失敗の絶対数（分子）を示し、失敗が正確にどこで発生しているかを把握できるようにします。
* <DNT>**Exporter sent**</DNT>: エクスポートの絶対数（分母）を表示することで、失敗とレートの全体像を把握できるようにします。

## キュードロップ [#queue-drops]

キューがいっぱいだったため、コレクターがエクスポート用にキューに入れることができなかったテレメトリー。キューに入れられなかったデータは破棄されます。つまり、データ損失が確定します。

関連するテレメトリー：

* <DNT>**Exporter enqueue failures**</DNT>：確認されたデータ損失のシグナルまたはエクスポーター別の内訳を示します。
* <DNT>**Exporter queue size vs. capacity**</DNT>：キューが急速にいっぱいになったか（例：トラフィックのスパイク）、または徐々にいっぱいになったか（例：コレクターのサイズ不足、キューのサイズ不足、または継続的な障害の蓄積）を示します。
* <DNT>**Exporter failures**</DNT>：エクスポートの失敗は多くの場合、満杯になるまでキューを滞留させるため、これが根本原因であるかどうかを確認するのに役立ちます。
