## ステップごとの設定

<Steps>
<Step>
### 設定ファイルをダウンロードする [#download-config]

デフォルトでは、コレクターは[内部テレメトリー](https://opentelemetry.io/docs/collector/internal-telemetry/)を出力しないため、最初にそれを有効にする必要があります。

```bash
curl 'https://raw.githubusercontent.com/newrelic/nrdot-collector-releases/refs/heads/main/examples/internal-telemetry-config.yaml' \
  --silent --output internal-telemetry-config.yaml
```
</Step>

<Step>
### 環境変数の設定 [#set-env-vars]

* <DNT>`INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY`</DNT>: 内部テレメトリーの送信先アカウントのライセンスキーを取り込みます。 このキーは、コレクターが New Relic に通常のデータを送信するために使用するキー (以下の例では<DNT>`NEW_RELIC_LICENSE_KEY`</DNT>とは異なる場合があります。
* <DNT>`INTERNAL_TELEMETRY_SERVICE_NAME`</DNT>: デフォルトは`otel-collector`で、New Relic のエンティティ名を決定します
* <DNT>`INTERNAL_TELEMETRY_OTLP_ENDPOINT`</DNT>：デフォルトはUS `https://otlp.nr-data.net`です；EUの場合は、これを`https://otlp.eu01.nr-data.net`に設定してください；JPの場合は、これを次に設定してください `https://otlp.jp.nr-data.net`
</Step>

<Step>
### マージされた設定でコレクターを実行する [#run-collector]

コンポーネントとパイプラインの通常の設定 (次の例では`--config=/etc/nrdot-collector/config.yaml`) に加えて、両方の設定をマージする 2 番目の`--config`引数を追加します。

```bash
docker run \
  -e INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY='...' \
  -e NEW_RELIC_LICENSE_KEY='...' \
  -e INTERNAL_TELEMETRY_SERVICE_NAME='demo-collector' \
  -v './internal-telemetry-config.yaml:/etc/nrdot-collector/config-internal.yaml' \
  newrelic/nrdot-collector:2.5.0 --config=/etc/nrdot-collector/config.yaml \
  --config='/etc/nrdot-collector/config-internal.yaml'
```

<Callout variant="important">
`service::telemetry`ノードの下に既存の設定がある場合、 `--config`引数の順序は重要になります。 コレクターは、設定と構成の特定の部分（例: リスト、リーフノードなど)はマージできないため、最後の`--config`引数によって上書きされます。
</Callout>
</Step>

<Step>
### エンティティタグを追加する [#add-tag]

タグ<DNT>`newrelic.service.type: otel_collector`</DNT>は、UI レベルでのエクスペリエンスへのオプトインとして機能します。次のいずれかのオプションを選択します。

* **オプション 1** : オプション 2 の設定を含む上記の設定例を使用します。
* **オプション 2** : コレクターに引数<DNT>`--config=yaml:service::telemetry::resource::newrelic.service.type: otel_collector`</DNT>を追加します。これにより、属性がリソース属性として追加され、New Relic が取り込み時にタグ付けを実行します。このオプションを削除すると、タグの有効期限が切れるまでに 1 日かかります。
* **オプション 3** : APM UI (ページ上部、エンティティ名の横) からタグを追加します。UI 経由でこれを削除したり、元に戻したりすることもできます。

タグ付けしたら、コレクターのデータを探索するために、[UIでコレクターを表示する](/docs/opentelemetry/collector-observability/collector-observability#view-ui)をご覧ください。
</Step>

<Step>
### オプション：設定をカスタマイズする [#customize]

デフォルトの設定では、詳細レベルやサンプリングなどの一般的なオプションを微調整するための形式`INTERNAL_TELEMETRY_...`の追加の環境変数が公開されます。 詳細については[設定自体](https://github.com/newrelic/nrdot-collector-releases/blob/main/examples/internal-telemetry-config.yaml)を参照してください。

コレクターをモニターするには、デフォルトの設定を使用することをお勧めします。ただし、詳細レベル、サンプリング、またはデータ収集率を下げるなど、ニーズに合わせてサンプルの設定を変更できます。詳細については、[公式ドキュメント](https://opentelemetry.io/docs/collector/internal-telemetry/)を参照してください。設定を変更すると、UIの一部でデータが表示されなくなる場合がありますのでご注意ください。[「制限事項」](/docs/opentelemetry/collector-observability/collector-observability#limitations)もご覧ください。OTelコミュニティの発展に伴い、コレクターの内部テレメトリー設定オプションは変更されます。提供されているデフォルトを使用するかどうかを含め、設定を完全に制御できます。
</Step>
</Steps>

## オーバーヘッドの考慮 [#overhead]

すべてのテレメトリーと同様、コレクターの内部テレメトリーによりデータの取り込みが増加します。 オーバーヘッドはワークロードと設定によって異なります。 考慮すべき重要な要素は次のとおりです。

**メトリクスは**、スループットに関係なく、コレクターとすべてのアクティブなコンポーネントに対して一定のオーバーヘッドを作成します。メトリクスは一定の間隔 (デフォルトでは 60 秒) で放射されます。 それぞれの[メタデータ.yaml](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/filterprocessor/metadata.yaml#L20)で示されているように、どのコンポーネントでもカスタムメトリックを発行できます。 これによりオーバーヘッドが増加する可能性があります。

コレクターが送信するメトリクスの量を減らす必要がある場合は、メトリクスレベルを<DNT>`normal`</DNT>に設定することをお勧めします。たとえば、サンプル設定の環境変数<DNT>`INTERNAL_TELEMETRY_METRICS_LEVEL`</DNT>を使用します。UIで使用される<DNT>`detailed`</DNT>メトリクスは一部のみであり、通常はパフォーマンスやネットワークの問題を微調整するためのメトリクスであるため、必要に応じて再度有効にすることができます。

**ログ**通常の操作中は影響は最小限です。エラー ログが急増するとオーバーヘッドが大きくなる可能性がありますが、ログはデフォルトでサンプリングされるため、オーバーヘッドは軽減されます。サンプリング アルゴリズムでは、定義された間隔ごとに一定数のログが許可され、その後、静的なレートでサンプリングが行われます。[service::テレメトリー::ログ::sampling](https://github.com/newrelic/nrdot-collector-releases/blob/main/examples/internal-telemetry-config.yaml)を参照してください。

**トレースは**デフォルトで無効になっています。理由:

* トレースの成熟度は限られています。 すべてのコンポーネントがインストゥルメント化されているわけではありません。この[github issue を](https://github.com/open-telemetry/opentelemetry-collector/issues/8804)参照してください。
* 上流エージェントやコレクターからのワークロードやバッチ設定によって異なる、予測できないオーバーヘッド。
* 適応サンプリング アルゴリズムは使用できません。このため、特定のユースケースで予期しないコストが発生するリスクがない、普遍的なサンプリング推奨事項を提供することは不可能になります。

トレースがさらに成熟すると、コレクターがコンポーネント レベルでのデータ処理にどれだけの時間を費やしたかについて貴重なインサイトを提供するようになるでしょう。 トレースの作成中に実験するには、 <DNT>`INTERNAL_TELEMETRY_TRACE_LEVEL=basic`</DNT>を設定し、 <DNT>`INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO=0.001`</DNT> (0.1%) などの低いサンプリング レートから開始して、取り込みボリュームを監視し、必要に応じて調整します。

### インフラストラクチャ関係を設定する（オプション、実験的）

[「概要」ページ](/docs/opentelemetry/collector-observability/collector-observability#summary-page)で説明しているように、APMはコレクターが実行されているインフラストラクチャのインフラストラクチャメトリクスを表示できますが、これはインフラストラクチャがインストゥルメントされた状態であり、[関係](https://docs.newrelic.com/docs/new-relic-solutions/new-relic-one/core-concepts/what-entity-new-relic/#related-entities)を形成できる場合に限られます。この関係は、コレクターの内部テレメトリーの追加属性によって決定されます。このトピックの詳細については、[OTelのドキュメント](https://docs.newrelic.com/docs/opentelemetry/best-practices/opentelemetry-best-practices-resources/#service-to-infra-otel-collector)を参照してください。これを設定する手順は、実際のインフラストラクチャに大きく依存します。一般的な選択肢であるKubernetesについては、[ OTel for Kubernetesソリューション](https://docs.newrelic.com/docs/kubernetes-pixie/k8s-otel/intro/) に基づいてコンテナとサービスの関係を実現する方法を示す[ 例](https://github.com/newrelic/newrelic-opentelemetry-examples/tree/main/other-examples/collector/internal-telemetry-k8s-container-relationships) を作成しました。
