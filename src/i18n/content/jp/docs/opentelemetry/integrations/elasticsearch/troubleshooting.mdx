[Elasticsearch OpenTelemetryインテグレーションのインストレーション](/docs/opentelemetry/integrations/elasticsearch/elasticsearch-otel-integration-install)または[Kubernetesインストレーション](/docs/opentelemetry/integrations/elasticsearch/elasticsearch-otel-integration-k8-install)を完了したにもかかわらず、New Relicにデータが表示されない場合は、以下の問題を確認し、解決手順に従ってください。

## ホストベースのデプロイメント [#host-troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-collector-stopped" title="Collectorサービスが停止または失敗しました">
    <strong>確認方法</strong>

    ```bash
    sudo systemctl status otelcol-contrib
    ```

    <strong>解像度</strong>

    * サービスが非アクティブの場合は、開始します。
      <InlineCode>
        sudo systemctl start otelcol-contrib
      </InlineCode>
    * サービスが失敗した場合は、設定エラーを修正して再起動してください。
      <InlineCode>
        sudo systemctl restart otelcol-contrib
      </InlineCode>
  </Collapser>

  <Collapser id="troubleshoot-collector-logs-errors" title="Collectorレポートのスクレイピングまたはエクスポート エラー">
    <strong>確認方法</strong>

    ```bash
    sudo journalctl -u otelcol-contrib.service -f
    ```

    <strong>解像度</strong>

    ログ出力を確認し、根本原因（接続の問題、認証の失敗、権限の問題など）を解決します。
  </Collapser>

  <Collapser id="troubleshoot-connection-refused" title="Elasticsearch を呼び出すときに接続が拒否されました">
    <strong>エラーサンプル</strong>: <InlineCode>
      dial tcp \[::1]:9200: connect: connection refused
    </InlineCode>

    <strong>解像度</strong>

    * <InlineCode>
        config.yaml
      </InlineCode>
      の
      <InlineCode>
        endpoint
      </InlineCode>
      が Elasticsearch のホストとポートと一致していることを確認します。
    * Elasticsearch が実行中であり、コレクター ホストからアクセスできることを確認します。
  </Collapser>

  <Collapser id="troubleshoot-403" title="New Relicへのエクスポート時に403 Forbiddenが発生する">
    <strong>エラーサンプル</strong>: <InlineCode>
      permanent error: 403 Forbidden
    </InlineCode>

    <strong>解像度</strong>

    1. <InlineCode>
         /etc/systemd/system/otelcol-contrib.service.d/environment.conf
       </InlineCode>の<InlineCode>
         NEWRELIC\_LICENSE\_KEY
       </InlineCode>を確認してください。

    2. systemd をリロードし、コレクターを再起動します。

       ```bash
       sudo systemctl daemon-reload
       sudo systemctl restart otelcol-contrib
       ```
  </Collapser>

  <Collapser id="troubleshoot-permission-denied" title="ログ収集時にアクセスが拒否されました">
    <strong>エラーサンプル</strong>: <InlineCode>
      permission denied
    </InlineCode>または <InlineCode>
      cannot open file
    </InlineCode>

    <strong>解像度</strong>

    1. コレクター ユーザーを Elasticsearch グループに追加します。
       ```bash
       sudo usermod -a -G elasticsearch otelcol-contrib
       ```
    2. コレクターを再起動します。
       <InlineCode>
         sudo systemctl restart otelcol-contrib
       </InlineCode>
  </Collapser>

  <Collapser id="troubleshoot-api-reachability" title="コレクターからElasticsearch APIにアクセスできません">
    <strong>確認方法</strong>

    ```bash
    # Unsecured cluster
    curl -I http://localhost:9200

    # With authentication
    curl -u username:password -k https://localhost:9200
    ```

    <strong>解像度</strong>

    クラスターが正常であること、資格情報が有効であること、ファイアウォールまたはセキュリティ設定でアクセスが許可されていることを確認します。
  </Collapser>

  <Collapser id="troubleshoot-missing-entity" title="New Relic UI に Elasticsearch エンティティが見つかりません">
    <strong>解像度</strong>

    * <InlineCode>
        resourcedetection
      </InlineCode>
      プロセッサがすべてのメトリクス パイプラインに含まれていることを確認してください。
    * <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      が
      <InlineCode>
        resource/cluster_name_override
      </InlineCode>
      プロセッサ経由で設定されていることを確認します。
  </Collapser>

  <Collapser id="troubleshoot-logs-missing" title="メトリクスは存在するがログがない">
    <strong>解像度</strong>

    * <InlineCode>
        filelog
      </InlineCode>
      受信パスが正しく絶対的であることを確認してください。
    * ログ パイプラインに
      <InlineCode>
        filelog
      </InlineCode>
      レシーバーと
      <InlineCode>
        otlphttp
      </InlineCode>
      エクスポーターの両方が含まれていることを確認します。
  </Collapser>
</CollapserGroup>

## Kubernetesのデプロイメント [#kubernetes-troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-k8s-no-pods-discovered" title="Elasticsearchポッドが検出されませんでした - ラベルが欠落しています">
    <strong>確認方法</strong>

    ```bash
    # Verify your Elasticsearch pods have the required label
    kubectl get pods -n <namespace> -l app=elasticsearch --show-labels
    ```

    <strong>解像度</strong>

    ポッドが返されない場合、Elasticsearchポッドに必要な<InlineCode>
      app=elasticsearch
    </InlineCode>ラベルが欠落しています。receiver\_creatorは、一致するラベルがないとポッドを発見できません。

    * StatefulSet/デプロイメントの場合、ポッドテンプレートにラベルを追加します：
      ```yaml
      spec:
        template:
          metadata:
            labels:
              app: elasticsearch
      ```
    * 既存のポッドの場合は、ラベルを追加して再起動します：
      ```bash
      kubectl label pods -l <your-selector> app=elasticsearch -n <namespace>
      kubectl rollout restart statefulset/elasticsearch -n <namespace>
      ```
    * カスタムラベルを使用する場合は、ラベルに一致するように values.yaml の receiver ルールを更新してください：
      ```yaml
      rule: type == "pod" && labels["app"] == "your-custom-label"
      ```
  </Collapser>

  <Collapser id="troubleshoot-k8s-collector-not-running" title="Collectorポッドが実行されていないか、クラッシュしている">
    <strong>確認方法</strong>

    ```bash
    kubectl get pods -n newrelic
    kubectl describe pod <collector-pod-name> -n newrelic
    ```

    <strong>解像度</strong>

    * ポッドのイベントでエラーを確認します：
      <InlineCode>
        kubectl describe pod
      </InlineCode>

    * コレクターログを確認します：

      ```bash
      kubectl logs -n newrelic -l app.kubernetes.io/name=opentelemetry-collector
      ```

    * シークレットが存在することを確認します：

      ```bash
      kubectl get secret newrelic-licenses -n newrelic
      ```

    * リソース制限が低すぎないか確認してください。
  </Collapser>

  <Collapser id="troubleshoot-k8s-discovery-errors" title="Receiver creatorがポッドを検出できない">
    <strong>確認方法</strong>

    ```bash
    # Check collector logs for discovery errors
    kubectl logs -n newrelic -l app.kubernetes.io/name=opentelemetry-collector | grep "receiver_creator"
    ```

    <strong>解像度</strong>

    * RBACアクセス権限が正しく設定されていることを確認します：

      ```bash
      kubectl get clusterrole | grep opentelemetry
      kubectl describe clusterrole <role-name>
      ```

    * コレクターにポッド、ノード、およびエンドポイントを監視する権限があることを確認します。

    * 設定でk8s\_observer拡張機能が有効になっていることを確認します。
  </Collapser>

  <Collapser id="troubleshoot-k8s-network-connectivity" title="Collector は Elasticsearch ポッドに接続できません">
    <strong>確認方法</strong>

    ```bash
    # Check network policies
    kubectl get networkpolicies -n <namespace>

    # Test connectivity from collector to Elasticsearch
    kubectl exec -n newrelic <collector-pod> -- curl http://<es-pod-ip>:9200
    ```

    <strong>解像度</strong>

    * ネットワークポリシーで、newrelicネームスペースからElasticsearchネームスペースへのトラフィックが許可されていることを確認します。
    * Elasticsearchポッドが正しいポート（デフォルト：9200）を公開しているか確認します。
    * ファイアウォールルールがポッド間通信をブロックしないことを確認してください。
  </Collapser>

  <Collapser id="troubleshoot-k8s-wrong-endpoint" title="Kubernetesでの403 Forbiddenまたは認証エラー">
    <strong>エラーサンプル</strong>: <InlineCode>
      permanent error: 403 Forbidden
    </InlineCode>

    <strong>解像度</strong>

    * シークレットに正しいライセンスキーが含まれていることを確認します：

      ```bash
      kubectl get secret newrelic-licenses -n newrelic -o jsonpath='{.data.NEWRELIC_LICENSE_KEY}' | base64 -d
      ```

    * OTLPエンドポイントがご利用の地域に対して正しいことを確認してください。

    * シークレットがコレクターポッドにマウントされていることを確認します：

      ```bash
      kubectl describe pod <collector-pod> -n newrelic | grep -A5 "Environment"
      ```
  </Collapser>

  <Collapser id="troubleshoot-k8s-logs-not-collected" title="Kubernetesでログが収集されない">
    <strong>解像度</strong>

    * <InlineCode>
        mode: daemonset
      </InlineCode>
      を使用していることを確認してください（デプロイメントモードではノードログにアクセスできません）

    * ボリュームマウントが正しく設定されていることを確認します：

      ```bash
      kubectl describe pod <collector-pod> -n newrelic | grep -A10 "Mounts"
      ```

    * filelogレシーバーのパスがElasticsearchポッドのログと一致することを確認します：

      ```bash
      kubectl exec -n newrelic <collector-pod> -- ls /var/log/pods/*/elasticsearch*/*.log
      ```

    * コレクターにホストのログディレクトリに対する読み取り権限があることを確認してください。
  </Collapser>

  <Collapser id="troubleshoot-k8s-cluster-name-missing" title="k8s.cluster.name属性が欠損しているメトリクス">
    <strong>解像度</strong>

    * values.yamlに環境変数
      <InlineCode>
        K8S_CLUSTER_NAME
      </InlineCode>
      が設定されていることを確認します

    * <InlineCode>
        resource/cluster
      </InlineCode>
      プロセッサがメトリクスパイプラインにあることを確認してください

    * 確認するクエリ：

      ```sql
      FROM Metric SELECT * WHERE metricName LIKE 'elasticsearch.%' LIMIT 1
      ```

      <InlineCode>
        k8s.cluster.name
      </InlineCode>属性が存在するか確認します
  </Collapser>
</CollapserGroup>

## APMの相関とディストリビューティッド（分散）トレーシング [#correlation-troubleshooting]

これらの問題は、[ディストリビューティッド（分散）トレーシングとのAPM相関](/docs/opentelemetry/integrations/elasticsearch/distributed-tracing)を設定した場合に適用されます。

<CollapserGroup>
  <Collapser id="troubleshoot-no-es-spans" title="New RelicにElasticsearchのスパンが表示されない">
    <strong>確認方法</strong>

    ```sql
    FROM Span SELECT count(*) WHERE es.cluster.name = '<elasticsearch-cluster-name>' SINCE 30 minutes ago
    ```

    <strong>解像度</strong>

    * ネイティブOTLPトレースのエクスポートには、<strong>Elasticsearch 9.4以降</strong>が必要です。
      <InlineCode>
        curl http://localhost:9200
      </InlineCode>
      でバージョンを確認してください。
    * <InlineCode>
        elasticsearch.yml
      </InlineCode>
      に3つの設定すべてが存在することを確認してください：
      <InlineCode>
        telemetry.tracing.enabled: true
      </InlineCode>
      、
      <InlineCode>
        telemetry.export.endpoint
      </InlineCode>
      、および
      <InlineCode>
        telemetry.tracing.sample_rate
      </InlineCode>
      。
    * JVMシステムプロパティ
      <InlineCode>
        -Dtelemetry.otel.traces.enabled=true
      </InlineCode>
      が（
      <InlineCode>
        jvm.options
      </InlineCode>
      または
      <InlineCode>
        ES_JAVA_OPTS
      </InlineCode>
      で）設定されていることを確認し、Elasticsearchを再起動してください。
    * デフォルトの
      <InlineCode>
        telemetry.tracing.sample_rate
      </InlineCode>
      は
      <InlineCode>
        0.001
      </InlineCode>
      （0.1％）です。スパンがすぐに表示されるように、検証中に値を上げてください。
  </Collapser>

  <Collapser id="troubleshoot-traces-pipeline" title="Elasticsearch はスパンをエクスポートしていますが、New Relic に到達しません。">
    <strong>解像度</strong>

    * コレクターに
      <InlineCode>
        0.0.0.0:4317
      </InlineCode>
      でgRPCプロトコルが有効になっている
      <InlineCode>
        otlp
      </InlineCode>
      レシーバーがあること、およびElasticsearchノードからエンドポイントに到達可能であることを確認してください。
    * <InlineCode>
        traces
      </InlineCode>
      パイプラインが存在し、
      <InlineCode>
        otlp
      </InlineCode>
      レシーバーと
      <InlineCode>
        otlphttp
      </InlineCode>
      エクスポーターが含まれていることを確認してください。
    * コレクターのログでOTLPレシーバーまたはエクスポートのエラーを確認してください。
  </Collapser>

  <Collapser id="troubleshoot-cluster-self-loop" title="クラスタは自身への関係を示します（自身を呼び出します）。">
    <strong>原因</strong>

    呼び出し元のアプリケーションに属性付けできないElasticsearchのスパンがNew Relicに到達すると、セルフループが表示されます。一般的な原因は2つあります：

    * <strong>親のない（ルート）Elasticsearchスパン</strong> — KubernetesのヘルスプローブやElasticsearchメトリクスレシーバー自体のスクレイプ呼び出し（
      <InlineCode>
        \_nodes/stats
      </InlineCode>
      、
      <InlineCode>
        \_cluster/health
      </InlineCode>
      など）のような、親アプリケーションスパンを持たないスパン。これらはアプリケーションのトレースの一部ではないため、New Relicには呼び出し元のサービスがなく、クラスタ自体に関係を描画します。
    * <strong>ノード自身のアドレス</strong> — Elasticsearchサーバーのスパンには
      <InlineCode>
        http.request.headers.host
      </InlineCode>
      （および
      <InlineCode>
        server.address
      </InlineCode>
      ）が含まれており、New Relicはこれをクラスタに解決します。

    <strong>解像度</strong>

    両方のプロセッサを<InlineCode>
      traces
    </InlineCode>パイプラインに追加し、コレクターを再起動してください。<InlineCode>
      filter/drop\_rootless\_es
    </InlineCode>は親のないElasticsearchスパンをドロップし（アプリケーション駆動のスパンには常に親があるため保持されます）、<InlineCode>
      transform/strip\_es\_host
    </InlineCode>はアドレス属性を削除します：

    ```yaml
    processors:
      filter/drop_rootless_es:
        error_mode: ignore
        traces:
          span:
            - 'instrumentation_scope.name == "elasticsearch" and IsRootSpan()'
      transform/strip_es_host:
        error_mode: ignore
        trace_statements:
          - context: span
            statements:
              - delete_key(attributes, "http.request.headers.host") where instrumentation_scope.name == "elasticsearch"
              - delete_key(attributes, "server.address") where instrumentation_scope.name == "elasticsearch"
    # traces pipeline: processors: [filter/drop_rootless_es, transform/strip_es_host, batch]
    ```

    修正されたスパンが到着し、以前の関係の有効期限が切れると、既存のセルフループは自然にクリアされます（これには最大約75分かかる場合があります）。
  </Collapser>

  <Collapser id="troubleshoot-app-not-linked" title="Elasticsearchのスパンは届きますが、アプリケーションがクラスタにリンクされていません">
    <strong>解像度</strong>

    * アプリケーションがインストゥルメントされた状態であり、Elasticsearchの呼び出しでW3C
      <InlineCode>
        traceparent
      </InlineCode>
      ヘッダーを伝播することを確認してください。アプリケーションがOpenTelemetryでインストゥルメントされた場合、最新のElasticsearchクライアントのほとんどはこれを自動的に行います。
    * Elasticsearchの呼び出しを含むディストリビューティッド（分散）トレーシングを開き、アプリケーションのスパンとElasticsearchのスパンが同じトレースを共有していることを確認してください。
    * 関係が構築されるまで数分お待ちください。New Relicはエンティティの関係を定期的に再評価します。
  </Collapser>

  <Collapser id="troubleshoot-name-mismatch" title="トレースとメトリクスが異なるクラスタエンティティに解決される">
    <strong>解像度</strong>

    * トレースのパスは
      <InlineCode>
        es.cluster.name
      </InlineCode>
      （Elasticsearchによってスパンにスタンプされます）をキーとし、メトリクスのパスは
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      をキーとします。
      <InlineCode>
        elasticsearchreceiver
      </InlineCode>
      はElasticsearchが返す値から自動的に
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      を報告するため、両方とも同じ
      <InlineCode>
        cluster.name
      </InlineCode>
      から派生し、1つのエンティティに解決されます — 追加のコレクター設定は必要ありません。
    * メトリクスのクラスタ名を固定値に強制しないでください。コレクター設定で
      <InlineCode>
        resource
      </InlineCode>
      プロセッサ（たとえば、名前をハードコードする
      <InlineCode>
        resource/cluster_name_override
      </InlineCode>
      ）を使用して設定している場合は、その上書きを削除してください — そうしないと、メトリクスとトレースが2つの異なるエンティティに解決され、相関するエンティティにメトリクスデータが表示されません。
    * 単一の明確なエンティティにマッピングされるように、Elasticsearchの
      <InlineCode>
        cluster.name
      </InlineCode>
      がNew Relicアカウント内で一意であることを確認してください。
  </Collapser>
</CollapserGroup>
