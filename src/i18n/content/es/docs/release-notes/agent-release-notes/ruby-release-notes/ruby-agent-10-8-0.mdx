## v10.8.0

* **Característica: reportar un nombre de host único para Worker Pools y Jobs de Google Cloud Run**

  El soporte para el nombre de host de Cloud Run, agregado en el [PR#3609](https://github.com/newrelic/newrelic-ruby-agent/pull/3609/), detectaba Cloud Run solo a través de `K_REVISION`, la variable de entorno establecida por los **Services** de Cloud Run. El agente ahora también reconoce [`CLOUD_RUN_REVISION`](https://docs.cloud.google.com/run/docs/container-contract#env-vars) (Worker Pools) y `CLOUD_RUN_EXECUTION` (Jobs), por lo que `utilization.gcp_cloud_run.use_instance_as_host` ahora se aplica a los tres tipos de recursos. Cuando `utilization.gcp_cloud_run.include_revision_in_host` es `true`, el nombre de host se crea a partir de cualquiera de estas variables que esté presente —por ejemplo, `{CLOUD_RUN_EXECUTION}-{instance id}` para un Job. [Issue#3651](https://github.com/newrelic/newrelic-ruby-agent/issues/3651) [PR#3652](https://github.com/newrelic/newrelic-ruby-agent/pull/3652)

* **Característica: agregar opción de configuración `browser_monitoring.version`**

  Los clientes ahora pueden fijar la versión exacta del cargador del agente del browser que inyecta New Relic al establecer la nueva opción de configuración `browser_monitoring.version`. Consulte la [política de EOL del agente del browser](https://docs.newrelic.com/docs/browser/browser-monitoring/getting-started/browser-agent-eol-policy/) para saber qué versiones están disponibles y son compatibles actualmente. [PR#3663](https://github.com/newrelic/newrelic-ruby-agent/pull/3663)

* **Característica: agregar span.kind a las bibliotecas de trabajos en segundo plano**

  Ahora, el atributo `span.kind` se agregará a las operaciones `produce` y `consume` de las bibliotecas de trabajos en segundo plano. Esto incluye ActiveJob, Sidekiq, Resque y DelayedJob. [PR#3636](https://github.com/newrelic/newrelic-ruby-agent/pull/3636)

* **Corrección de errores: la instrumentación de DelayedJob ya no se reinstala en cada trabajador en el modo prepend**

  Cuando la instrumentación de DelayedJob se instala mediante prepend (el valor predeterminado), crear más de un `Delayed::Worker` en el mismo proceso provocaba que el agente registrara “Installing DelayedJob instrumentation” y reinicializara el plug-in de nuevo para cada worker adicional. Esto era inofensivo pero ruidoso; ahora solo se realiza una vez por proceso, lo que coincide con el comportamiento de instrumentación de cadena existente. [PR#3654](https://github.com/newrelic/newrelic-ruby-agent/pull/3654)

* **Corrección de errores: los valores de configuración de la lista de permitidos ya no distinguen entre mayúsculas y minúsculas**

  Anteriormente, las opciones de configuración en la lista de permitidos requerían una coincidencia exacta de mayúsculas y minúsculas, por lo que un valor con un uso de mayúsculas y minúsculas inesperado —como `OBFUSCATED` o `ObFuScAtEd` para `slow_sql.record_sql` — volvía silenciosamente al valor predeterminado. Las opciones de configuración que se validan con una lista de permitidos ahora coinciden con los valores independientemente de las mayúsculas y minúsculas, por lo que ambos se tratan igual que `obfuscated`. [Issue#3613](https://github.com/newrelic/newrelic-ruby-agent/issues/3613) [PR#3645](https://github.com/newrelic/newrelic-ruby-agent/pull/3645)

* **Corrección de error: la instrumentación de Puma funciona cuando Puma se carga de forma diferida**

  Con `gem "puma", require: false`, Puma aún no estaba cargado cuando se ejecutó la comprobación de dependencia del agente, por lo que la instrumentación de Puma fallaba al instalarse. El agente ahora reconoce `Puma::RackHandler` como evidencia de que Puma está presente, lo que soluciona este problema. [Problema#3641](https://github.com/newrelic/newrelic-ruby-agent/issues/3641) [PR#3650](https://github.com/newrelic/newrelic-ruby-agent/pull/3650)
