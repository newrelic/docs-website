## v10.7.0

* **Característica: agregar transaction\_tracer.cap\_segment\_artifacts opción de configuración**

  Las transacciones de larga duración con muchos segmentos pueden causar un uso de memoria en continuo aumento durante la vida útil de la transacción. El agente ahora ofrece una opción de configuración `transaction_tracer.cap_segment_artifacts` opcional (el valor predeterminado es `false`). Cuando está habilitado, una vez que se alcanza [`transaction_tracer.limit_segments`](https://docs.newrelic.com/docs/apm/agents/ruby-agent/configuration/ruby-agent-configuration/#transaction_tracer-limit_segments), el agente también deja de registrar el tiempo exclusivo para cualquier segmento creado posteriormente en esa transacción, lo que reduce el uso de memoria a costa de datos de tiempo menos precisos para la transacción. [PR#3615](https://github.com/newrelic/newrelic-ruby-agent/pull/3615)

* **Característica: agregar instrumentación de server-statistics de Puma**

  El agente ahora realiza un muestreo de las estadísticas del servidor de todo el clúster de Puma y las reporta como métricas de intervalo de tiempo `Ruby/Puma/*`, incluyendo `backlog`, `running`, `pool_capacity`, `max_threads` y `requests_count`. Las estadísticas se muestrean en modo único y en modo agrupado cuando `preload_app!` está habilitado. Esta instrumentación está deshabilitada de forma predeterminada. Habilítela configurando `disable_puma_instrumentation` en `false`. Cuando está habilitado, el agente inicia un hilo de informes en el proceso maestro de Puma para entregar estas métricas, lo que ejecuta una conexión de agente adicional junto con los trabajadores de Puma. El intervalo de muestreo es configurable a través de la nueva configuración `puma.sample_rate` (60 segundos de forma predeterminada). Requiere Puma 6.6 o posterior. Consulte [nuestros documentos](https://docs.newrelic.com/docs/apm/agents/ruby-agent/instrumented-gems/puma-instrumentation/) para obtener más información. [PR#3578](https://github.com/newrelic/newrelic-ruby-agent/pull/3578)

* **Característica: reportar un nombre de host único para las instancias de Google Cloud Run**

  El agente ahora detecta Cloud Run y reporta el ID de la instancia de GCP como el nombre de host para que se puedan distinguir las instancias individuales. Antes de este cambio, todos los nombres de host de Google Cloud Run eran `localhost`. Esta característica está controlada por la nueva opción de configuración `utilization.gcp_cloud_run.use_instance_as_host` (`true` de forma predeterminada). Establezca `utilization.gcp_cloud_run.include_revision_in_host` (`false` de forma predeterminada) en `true` para reportar el nombre de host como `{K_REVISION}-{instance id}` en su lugar, donde [`K_REVISION`](https://docs.cloud.google.com/run/docs/container-contract#env-vars) es el nombre de revisión de Cloud Run. [Issue#3295](https://github.com/newrelic/newrelic-ruby-agent/issues/3295) [PR#3609](https://github.com/newrelic/newrelic-ruby-agent/pull/3609)

* **Corrección de errores: el SQL lento ya no se registra después de transaction\_tracer.limit\_segments excedido**

  Una vez que una transacción excedía [`transaction_tracer.limit_segments`](https://docs.newrelic.com/docs/apm/agents/ruby-agent/configuration/ruby-agent-configuration/#transaction_tracer-limit_segments), los segmentos de almacenamiento de datos creados posteriormente aún podían tener su SQL lento registrado. El agente ahora deja de registrar SQL lento para cualquier segmento creado después de que se alcanza el límite. [PR#3615](https://github.com/newrelic/newrelic-ruby-agent/pull/3615)

* **Corrección de errores: los planes de explicación podían apuntar a la base de datos incorrecta en aplicaciones Rails de múltiples bases de datos (Rails &gt;= 7.2)**

  En Rails 7.2+, el agente recopiló planes de explicación utilizando una conexión del grupo predeterminado/compartido de la aplicación en lugar de una dedicada. Esto afectó principalmente a las aplicaciones de múltiples bases de datos. Los planes de explicación podrían generarse en la base de datos incorrecta, y una explicación fallida podría dejar una conexión compartida en mal estado, afectando a requests no relacionadas. El agente ahora usa su propia conexión dedicada para los planes de explicación, como lo hacía antes de Rails 7.2, y restablece o descarta esa conexión cada vez que falla un intento de explicación, por lo que nunca se reutiliza una mala conexión. [Issue#3610](https://github.com/newrelic/newrelic-ruby-agent/issues/3610) [PR#3612](https://github.com/newrelic/newrelic-ruby-agent/pull/3612)

* **Corrección de errores: la instrumentación de monitoreo de browser ya no falla con `FrozenError`**

  Cuando el primer fragmento del cuerpo de una respuesta era un `String` congelado y había múltiples fragmentos, la instrumentación del navegador se encontraba con un `FrozenError` y el encabezado de tiempos del navegador nunca se inyectaba. Esto comenzó a aparecer con `ERB` 6.0.3+, que empezó a congelar más de sus cadenas compiladas. Este problema ya fue solucionado. [Issue#3624](https://github.com/newrelic/newrelic-ruby-agent/issues/3624) [PR#3625](https://github.com/newrelic/newrelic-ruby-agent/pull/3625)

* **Corrección de errores: normalizar los valores de configuración booleanos para permitir cualquier uso de mayúsculas y minúsculas**

  En la versión 9.x, el agente aceptaba valores booleanos en mayúsculas, como &quot;FALSE&quot;, y valores con mayúsculas y minúsculas como &quot;True&quot;. La versión 10.0.0 incluyó el [PR#3341](https://github.com/newrelic/newrelic-ruby-agent/pull/3341), que eliminó involuntariamente el requisito de no distinguir entre mayúsculas y minúsculas. Esto provocó que las opciones de configuración de los usuarios que tenían cualquier uso de mayúsculas y minúsculas además de todo en minúsculas volvieran a los valores predeterminados. Ahora, el agente vuelve a utilizar comprobaciones que no distinguen entre mayúsculas y minúsculas. [Issue#3632](https://github.com/newrelic/newrelic-ruby-agent/issues/3632) [PR#3633](https://github.com/newrelic/newrelic-ruby-agent/pull/3633)
