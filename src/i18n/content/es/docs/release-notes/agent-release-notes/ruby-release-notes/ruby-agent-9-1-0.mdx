## v9.1.0

La versión 9.1.0 del agente ofrece soporte para dos nuevas características de [Errors Inbox](https://docs.newrelic.com/docs/triage-inbox/errors-inbox/): huellas dactilares de errores y seguimiento de usuarios, identifica el almacén de datos de Amazon Timestream, elimina las advertencias de rastreo distribuido de los logs del agente al usar Sidekiq, corrige errores y se prueba con el JRuby 9.4.2.0 lanzado recientemente.

* **Característica: huellas dactilares de error: proporcione sus propios nombres de grupo de Errors Inbox**

  ¿Sus ocurrencias de errores están mal agrupadas? Configure su propia huella de error mediante una función de devolución de llamada. Se ha agregado un nuevo método de API pública `set_error_group_callback` que aceptará un proc definido por el usuario. El procedimiento se invocará para cada error detectado y, siempre que devuelva una cadena, esa cadena se utilizará como el nombre del grupo de errores para el error y tendrá prioridad sobre cualquier agrupación del lado del servidor que se realice con Errors Inbox de New Relic. Esto brinda a los usuarios un control mucho mayor sobre la agrupación de sus errores.

  Se espera que el proc definido por los clientes reciba exactamente un argumento de entrada, un hash. El hash contiene lo siguiente:

  | Llave                | Valor                                                                                 |
  | -------------------- | ------------------------------------------------------------------------------------- |
  | `:error`             | La instancia de clase de error de Ruby. Ofertas `#class`, `#message` y `#backtrace`   |
  | `:customAttributes`  | Cualquier atributo personalizado definido por los clientes para la transacción actual |
  | `:'request.uri'`     | El URI de solicitud actual si está disponible                                         |
  | `:'http.statusCode'` | El código de estado HTTP (200, 404, etc.) si está disponible                          |
  | `:'http.method'`     | El método HTTP (GET, PUT, etc.) si está disponible                                    |
  | `:'error.expected'`  | Si (verdadero) o no (falso) se esperaba el error                                      |
  | `:'options'`         | El hash de opciones pasó a `NewRelic::Agent.notice_error`                             |

  La devolución de llamada solo debe configurarse una vez por inicialización del agente de New Relic.

  Ejemplo de uso:

  ```
  proc = proc { |hash| "Access" if hash[:'http.statusCode'] == 401 }
  NewRelic::Agent.set_error_group_callback(proc)
  ```

* **Característica: seguimiento de usuarios - asociar errores con un ID de usuario**

  Ahora puede ver la cantidad de usuarios afectados por un grupo de errores. Identifique al usuario final con un nuevo método de API pública `set_user_id` que aceptará una representación de cadena de un ID de usuario y asociará ese ID de usuario con la transacción actual. Las transacciones y los errores tendrán entonces un nuevo atributo de agente `enduser.id` asociado a ellos. Esto permitirá a los usuarios del agente etiquetar transacciones y errores como pertenecientes a ID de usuario determinados para admitir mayores capacidades de filtrado y alerta.

* **Identificar Amazon Timestream cuando se usa el adaptador AR amazon\_timestream**

  Cuando el agente detecte que se está utilizando la gema [activerecord-amazon-timestream-adapter](https://rubygems.org/gems/activerecord-amazon-timestream-adapter), ahora identificará el almacén de datos como “Timestream”. ¡Muchas gracias a [@wagner](https://github.com/wagner) por contribuir con esta mejora! [PR#1872](https://github.com/newrelic/newrelic-ruby-agent/pull/1872)

* **Corrección de errores: elimina las advertencias relacionadas con el rastreo distribuido de los logs del agente cuando los encabezados no están presentes en Sidekiq**

  Anteriormente, el agente registraba una advertencia en `newrelic_agent.log` cada vez que intentaba aceptar encabezados de rastreo distribuido vacíos de los trabajos de Sidekiq, lo que podía resultar en un número excesivo de advertencias. Ahora el agente ya no creará estas advertencias al usar Sidekiq. [PR#1834](https://github.com/newrelic/newrelic-ruby-agent/pull/1834)

* **Corrección de error: registrar los encabezados de solicitud en logs de nivel de depuración en lugar de Objetos legibles por humanos**

  Anteriormente, el agente a veces recibía hijos de la clase `NewRelic::Agent::HTTPClients::AbstractRequest` como argumento cuando se llamaba a `NewRelic::Agent::Transaction::DistributedTracers#log_request_headers`. Esto causaba que los mensajes de log de nivel de depuración que imprimen los encabezados de la solicitud mostraran Objetos legibles por humanos (p. ej., `#<NewRelic::Agent::HTTPClients::HTTPClientRequest:0x00007fd0dda983e0>`) en lugar de los encabezados de la solicitud. Ahora, el hash de los encabezados de la solicitud siempre debe registrarse. [PR#1839](https://github.com/newrelic/newrelic-ruby-agent/pull/1839)

* **Corrección de error: se corrigió el método no definido `controller_path` registrado en la instrumentación de Action Controller**

  Anteriormente, el agente podía registrar un error al intentar determinar el nombre de la métrica en la instrumentación de Action Controller si la clase del controlador no respondía a `controller_path`. Esto se ha resuelto y el agente ya no llamará a este método a menos que la clase responda a él. Gracias a [@gsar](https://github.com/gsar) por informarnos sobre este problema. [PR#1844](https://github.com/newrelic/newrelic-ruby-agent/pull/1844)

* **Corrección de error: solucionar la excepción Transaction#finish y disminuir el nivel de logs para la advertencia relacionada durante las transacciones asíncronas**

  Anteriormente, el agente generaba un error no fatal cuando un segmento sin elemento principal quedaba sin terminar al completarse la transacción. Este error se generaba al construir un mensaje de log de nivel `warn`. Ahora que la instrumentación de Thread está activada por defecto, este mensaje de log se emite con mayor frecuencia y es menos preocupante. En los casos en los que vemos un segmento de Thread, Fiber o concurrent-ruby en una transacción, el mensaje se degradará a un nivel `debug`. Gracias a [@NielsKSchjoedt](https://github.com/NielsKSchjoedt) por crear la incidencia y a [@boomer196](https://github.com/boomer196) por probar las soluciones. [PR#1876](https://github.com/newrelic/newrelic-ruby-agent/pull/1876)

* **CI: objetivo JRuby 9.4.2.0**

  El agente ahora se está probando activamente con JRuby 9.4.2.0. TENGA EN CUENTA que esta versión no contiene ningún cambio no relacionado con CI para JRuby. Se espera que las versiones antiguas del agente sigan funcionando con versiones más recientes de JRuby y que la versión más reciente del agente siga funcionando con versiones más antiguas de JRuby.
