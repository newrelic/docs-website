### Mejoras

* Java 10

El agente de Java de New Relic ahora es totalmente compatible con Java 10. Para obtener más información sobre la versión del JDK y el agente de Java, consulte [este tema en el Explorers Hub](https://support.newrelic.com/s/hubtopic/aAX8W0000008ZWk/jdk-releases-and-the-java-agent).

* No es compatible con Java 6

Para continuar innovando y proporcionar de manera eficiente nuevas capacidades a nuestros clientes que se ejecutan en la JVM, esta y las futuras versiones del agente no son compatibles con Java 6. Si ejecuta Java 6, puede continuar usando el agente de Java 4.3.0 o inferior. Para obtener más detalles, consulte [este tema en el Explorers Hub](https://discuss.newrelic.com/t/with-support-for-java-10-new-relic-deprecates-java-6/57738).

* Akka 2.5 y Akka HTTP 10.1

El agente de Java ahora es compatible con Akka 2.5.x y Akka HTTP 10.1.x. Verá sus llamadas de Akka HTTP como transacciones de New Relic, verá las transferencias entre los actores de Akka y comprenderá las llamadas a otras bases de datos y servicios.

* Solr 7

El agente de Java ahora es compatible con Solr 7.x. El soporte para Solr de New Relic reporta las llamadas a la base de datos a los servidores Solr, además de monitorear el propio servidor Solr.

Problema conocido: la recopilación de estadísticas de JMX para Solr 7 no es compatible a partir de esta versión.

* Fuente de datos de WebLogic

El agente de Java ahora muestra datos de estado sobre la fuente de datos de WebLogic en la pestaña Datasource en la página de la JVM.

### Correcciones

* Se solucionó un problema por el cual el agente de Java 4.3.0 no reportaba datos según la configuración regional de la JVM. Agente de Java 4.3.0 falló al enviar datos de eventos si la configuración regional de la JVM está configurada para usar una coma como decimal. Vería NumberFormatException en el log del agente.
* Se solucionó un problema poco frecuente en el que el agente intentaba incorrectamente volver a transformar las clases de forma continua cuando se utilizaba una extensión con una fecha de modificación en el futuro, lo que causaba un aumento significativo en la carga de la CPU.
* Se corrigió una ConcurrentModificationException causada por la instrumentación de ning que se manifiesta en la instrumentación de Mule que hace que la solicitud a la que afecta se vuelva a intentar y que el agente de Java no informe los datos del encabezado.
* Se solucionó un problema en el que si `enable_auto_app_naming` se establecía en true y `distributed_tracing.enabled` se establecía en true, se muestreaba cada evento de rastreo distribuido. Ahora, si el agente tiene ambas configuraciones habilitadas, no activará el rastreo distribuido.
