## Configuración paso a paso

<Steps>
<Step>
### Cree el archivo de configuración [#create-config]

Habilite la [telemetría interna](https://opentelemetry.io/docs/collector/internal-telemetry/) del recolector guardando la siguiente configuración como `internal-telemetry-config.yaml`:

```yaml
##### Example configuration for internal telemetry
# This configuration is intended to be used in conjunction with a configuration of components and pipelines. The
# collector supports config merging on startup.
##### Requirements
# - nrdot-collector (any distro) >= 1.3.0 or collector core version >= v1.35.0 / v0.129.0
##### Configuration via environment variables
# For official documentation, see: https://opentelemetry.io/docs/collector/internal-telemetry/
## Required
# - INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY
## Optional
# - INTERNAL_TELEMETRY_SERVICE_NAME: defaults to 'otel-collector'; determines entity name in New Relic
# - INTERNAL_TELEMETRY_OTLP_ENDPOINT: defaults to 'https://otlp.nr-data.net'; see https://docs.newrelic.com/docs/opentelemetry/best-practices/opentelemetry-otlp/ and https://docs.newrelic.com/docs/opentelemetry/best-practices/opentelemetry-otlp-troubleshooting/
# - INTERNAL_TELEMETRY_METRICS_LEVEL: defaults to 'detailed'; other values are 'normal', 'basic', 'none'
# - INTERNAL_TELEMETRY_LOG_LEVEL: defaults to INFO; other values are DEBUG, WARN, ERROR
# - INTERNAL_TELEMETRY_TRACE_LEVEL: defaults to 'none' (traces disabled); other value is 'basic'
# - INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO: defaults to 0.01, i.e. 1% sampling; has no effect if TRACE_LEVEL is 'none'
service:
  telemetry:
    metrics:
      level: "${env:INTERNAL_TELEMETRY_METRICS_LEVEL:-detailed}"
      readers:
        - periodic:
            exporter:
              otlp:
                protocol: http/protobuf
                endpoint: "${env:INTERNAL_TELEMETRY_OTLP_ENDPOINT:-https://otlp.nr-data.net}"
                temporality_preference: delta
                headers:
                  - name: api-key
                    value: "${env:INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY}"
    logs:
      level: "${env:INTERNAL_TELEMETRY_LOG_LEVEL:-INFO}"
      # default sampling config for reference to simplify overwrites even if not exposed via env var, e.g. --config=yaml:service::telemetry::logs::sampling::enabled::false
      sampling:
        enabled: true
        # The interval in seconds that the logger applies to each sampling.
        tick: 10s
        # The number of messages logged at the start of each sampling::tick
        initial: 10
        # Sets the sampling policy for subsequent messages after sampling::initial messages are logged. When sampling::thereafter is set to N, every Nth message is logged and all others are dropped. If N is zero, the logger drops all messages after sampling::initial messages are logged.
        thereafter: 100
      processors:
        - batch:
            exporter:
              otlp:
                protocol: http/protobuf
                endpoint: "${env:INTERNAL_TELEMETRY_OTLP_ENDPOINT:-https://otlp.nr-data.net}"
                headers:
                  - name: api-key
                    value: "${env:INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY}"
    traces:
      # traces are disabled by default due to experimental status and lack of default sampling rate that works across use cases
      level: "${env:INTERNAL_TELEMETRY_TRACE_LEVEL:-none}"
      sampler:
        parent_based:
          root:
            trace_id_ratio_based:
              ratio: ${env:INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO:-0.01}
      processors:
        - batch:
            exporter:
              otlp:
                protocol: http/protobuf
                endpoint: "${env:INTERNAL_TELEMETRY_OTLP_ENDPOINT:-https://otlp.nr-data.net}"
                headers:
                  - name: api-key
                    value: "${env:INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY}"
    resource:
      service.name: "${env:INTERNAL_TELEMETRY_SERVICE_NAME:-otel-collector}"
```
</Step>

<Step>
### Establecer variables de entorno [#set-env-vars]

* <DNT>`INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY`</DNT>: Clave de licencia de ingesta para la cuenta a la que se debe enviar la telemetría interna. Esta clave puede ser diferente a la clave que utiliza el colector para enviar datos regulares a New Relic, es decir, <DNT>`NEW_RELIC_LICENSE_KEY`</DNT> en el ejemplo a continuación.
* <DNT>`INTERNAL_TELEMETRY_SERVICE_NAME`</DNT>: El valor predeterminado es `otel-collector`, determina el nombre de la entidad en New Relic
* <DNT>`INTERNAL_TELEMETRY_OTLP_ENDPOINT`</DNT>: el valor predeterminado es EE. UU. `https://otlp.nr-data.net`; si está en la UE, establezca esto en `https://otlp.eu01.nr-data.net`; si está en JP, establezca esto en `https://otlp.jp.nr-data.net`
</Step>

<Step>
### Ejecutar el colector con la configuración fusionada [#run-collector]

Además de la configuración normal para componentes y pipelines (en el siguiente ejemplo `--config=/etc/nrdot-collector/config.yaml`), agregue un segundo argumento `--config` que combinará ambas configuraciones:

```bash
docker run \
  -e INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY='...' \
  -e NEW_RELIC_LICENSE_KEY='...' \
  -e INTERNAL_TELEMETRY_SERVICE_NAME='demo-collector' \
  -v './internal-telemetry-config.yaml:/etc/nrdot-collector/config-internal.yaml' \
  newrelic/nrdot-collector:2.8.1 --config=/etc/nrdot-collector/config.yaml \
  --config='/etc/nrdot-collector/config-internal.yaml'
```

<Callout variant="important">
El orden de los argumentos de `--config` importa si tiene una configuración preexistente bajo el nodo `service::telemetry`. El colector utiliza una estrategia de &apos;el último gana&apos; a nivel de nodo al fusionar configuraciones y ciertas partes de la configuración (p. ej., listas, nodos hoja) no se pueden fusionar, por lo que se sobrescriben con el último argumento `--config`.
</Callout>
</Step>

<Step>
### Espere a que New Relic detecte el recolector [#auto-detection]

No necesita configurar nada más. New Relic detecta el recolector automáticamente y muestra la experiencia del recolector para su entidad.

En segundo plano, la mayoría de las métricas internas del recolector tienen nombres que comienzan con <DNT>`otelcol`</DNT>. Cuando una entidad emite una métrica con este prefijo, New Relic marca la entidad como un recolector agregando la etiqueta de entidad <DNT>`otelCollector: opentelemetry`</DNT>. Esto ocurre en la ingesta, por lo que puede tomar unos minutos después de que lleguen los primeros datos antes de que aparezca la experiencia.

Una vez detectado, consulte [Ver el recolector en la UI](/docs/opentelemetry/collector-observability/collector-observability#view-ui) para explorar los datos del recolector.
</Step>

<Step>
### Opcional: personalizar la configuración [#customize]

La configuración predeterminada expone variables de entorno adicionales de la forma `INTERNAL_TELEMETRY_...` para ajustar opciones comunes, como los niveles de detalle y el muestreo. Consulte la [configuración en sí](#create-config) para obtener más detalles.

Recomendamos utilizar la configuración predeterminada para monitorear el recolector. Sin embargo, puede modificar la configuración de ejemplo, como reducir el nivel de detalle, la tasa de muestreo o la tasa de recolección de datos. Consulte la [documentación oficial](https://opentelemetry.io/docs/collector/internal-telemetry/) para obtener más detalles. Tenga en cuenta que los cambios en la configuración pueden hacer que ciertas partes de la UI no muestren datos. Consulte también [las preguntas frecuentes](/docs/opentelemetry/collector-observability/collector-observability-faq). Las opciones de configuración de la telemetría interna del recolector cambian a medida que la comunidad de OTel evoluciona. Puede usar o modificar los valores predeterminados proporcionados según sea necesario.
</Step>
</Steps>

## Consideraciones de sobrecarga [#overhead]

Al igual que toda telemetría, la telemetría interna del colector aumenta su ingesta de datos. La sobrecarga depende de su carga de trabajo y configuración. Estos son los factores clave a tener en cuenta:

**Métricas** Genera una sobrecarga constante para el recopilador y todos los componentes activos, independientemente del rendimiento. Las métricas se emiten en un intervalo constante (60 segundos por defecto). Cualquier componente puede emitir métricas personalizadas, como lo indica el respectivo [metadata.yaml](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/filterprocessor/metadata.yaml#L20), lo que puede aumentar la sobrecarga.

Si necesita reducir la cantidad de métricas que emite su colector, recomendamos establecer el nivel de métrica en <DNT>`normal`</DNT>, p. ej. a través de la variable de entorno <DNT>`INTERNAL_TELEMETRY_METRICS_LEVEL`</DNT> en la configuración de ejemplo, ya que la interfaz de usuario solo utiliza un subconjunto de las métricas de <DNT>`detailed`</DNT> y suelen ser métricas destinadas a ajustar el rendimiento o a problemas de red, por lo que puede volver a habilitarlas según sea necesario.

**Logs** Los logs tienen un impacto mínimo durante la operación normal. Puede ocurrir una mayor sobrecarga cuando los logs de errores aumentan rápidamente, pero esto se reduce porque los logs se muestrean de forma predeterminada. El algoritmo de muestreo permite un número constante de logs por intervalo definido y luego muestrea a una tasa estática. Consulte <DNT>`service::telemetry::logs::sampling`</DNT> en la [configuración](#create-config).

**Trazas** Deshabilitadas por defecto, consulte [las preguntas frecuentes](/docs/opentelemetry/collector-observability/collector-observability-faq#traces-disabled) para obtener más detalles. Para experimentar con las trazas a medida que se desarrollan, configure <DNT>`INTERNAL_TELEMETRY_TRACE_LEVEL=basic`</DNT> y comience con una tasa de muestreo baja como <DNT>`INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO=0.001`</DNT> (0.1 %) mientras monitorea el volumen de ingesta y ajusta según sea necesario.

### Ejemplo: poblar relaciones de infraestructura (opcional)

Como se mencionó en la [página de resumen](/docs/opentelemetry/collector-observability/collector-observability#summary-page), APM puede mostrar métricas de infraestructura para la infraestructura en la que se ejecuta el recolector, pero solo si la infraestructura está instrumentada y se puede establecer [una relación](https://docs.newrelic.com/docs/new-relic-solutions/new-relic-one/core-concepts/what-entity-new-relic/#related-entities). La relación está determinada por atributos adicionales en la telemetría interna del recolector. Puede leer más sobre este tema en nuestra [documentación de OTel](https://docs.newrelic.com/docs/opentelemetry/best-practices/opentelemetry-best-practices-resources/#service-to-infra-otel-collector). Los pasos para configurar esto dependen en gran medida de la infraestructura exacta. Para la opción común de Kubernetes, creamos [un ejemplo](https://github.com/newrelic/newrelic-opentelemetry-examples/tree/main/other-examples/collector/internal-telemetry-k8s-container-relationships) que muestra cómo lograr relaciones entre contenedores y servicios basado en nuestra [solución de OTel para Kubernetes](https://docs.newrelic.com/docs/kubernetes-pixie/k8s-otel/intro/).
