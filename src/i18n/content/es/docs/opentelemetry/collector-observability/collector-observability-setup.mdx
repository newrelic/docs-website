## Configuración paso a paso

<Steps>
  <Step>
    ### Descargar el archivo de configuración [#download-config]

    De forma predeterminada, el recopilador no emite su [telemetría interna](https://opentelemetry.io/docs/collector/internal-telemetry/), por lo que deberá habilitarla primero.

    ```bash
    curl 'https://raw.githubusercontent.com/newrelic/nrdot-collector-releases/refs/heads/main/examples/internal-telemetry-config.yaml' \
      --silent --output internal-telemetry-config.yaml
    ```
  </Step>

  <Step>
    ### Establecer variables de entorno [#set-env-vars]

    * <DNT>`INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY`</DNT>: Clave de licencia de ingesta para la cuenta a la que se debe enviar la telemetría interna. Esta clave puede ser diferente a la clave que utiliza el colector para enviar datos regulares a New Relic, es decir, <DNT>`NEW_RELIC_LICENSE_KEY`</DNT> en el ejemplo a continuación.
    * <DNT>`INTERNAL_TELEMETRY_SERVICE_NAME`</DNT>: El valor predeterminado es `otel-collector`, determina el nombre de la entidad en New Relic
    * <DNT>`INTERNAL_TELEMETRY_OTLP_ENDPOINT`</DNT>: el valor predeterminado es EE. UU. `https://otlp.nr-data.net`; si está en la UE, establezca esto en `https://otlp.eu01.nr-data.net`; si está en JP, establezca esto en `https://otlp.jp.nr-data.net`
  </Step>

  <Step>
    ### Ejecutar el colector con la configuración fusionada [#run-collector]

    Además de la configuración normal para componentes y pipelines (en el siguiente ejemplo `--config=/etc/nrdot-collector/config.yaml`), agregue un segundo argumento `--config` que combinará ambas configuraciones:

    ```bash
    docker run \
      -e INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY='...' \
      -e NEW_RELIC_LICENSE_KEY='...' \
      -e INTERNAL_TELEMETRY_SERVICE_NAME='demo-collector' \
      -v './internal-telemetry-config.yaml:/etc/nrdot-collector/config-internal.yaml' \
      newrelic/nrdot-collector:2.5.0 --config=/etc/nrdot-collector/config.yaml \
      --config='/etc/nrdot-collector/config-internal.yaml'
    ```

    <Callout variant="important">
      El orden de los argumentos de `--config` importa si tiene una configuración preexistente bajo el nodo `service::telemetry`. El colector utiliza una estrategia de &apos;el último gana&apos; a nivel de nodo al fusionar configuraciones y ciertas partes de la configuración (p. ej., listas, nodos hoja) no se pueden fusionar, por lo que se sobrescriben con el último argumento `--config`.
    </Callout>
  </Step>

  <Step>
    ### Agregar etiqueta de entidad [#add-tag]

    La etiqueta <DNT>`newrelic.service.type: otel_collector`</DNT> actúa como una opción de participación en la experiencia a nivel de la interfaz de usuario. Seleccione una de las siguientes opciones:

    * **Opción 1**: Use la configuración de ejemplo proporcionada arriba que contiene la configuración de la Opción 2.
    * **Opción 2**: Agregue el argumento <DNT>`--config=yaml:service::telemetry::resource::newrelic.service.type: otel_collector`</DNT> al colector. Esto agrega el atributo como un atributo de recurso y New Relic realiza el etiquetado por usted en la ingesta. Si elimina esta opción, la etiqueta tardará un día en expirar.
    * **Opción 3**: Agregar etiqueta mediante la UI de APM (parte superior de la página, junto al nombre de la entidad). También puede eliminar esto a través de la interfaz de usuario para volver a cambiar.

    Una vez etiquetado, consulte [Ver el recolector en la UI](/docs/opentelemetry/collector-observability/collector-observability#view-ui) para explorar los datos del recolector.
  </Step>

  <Step>
    ### Opcional: personalizar la configuración [#customize]

    La configuración predeterminada expone variables de entorno adicionales de la forma `INTERNAL_TELEMETRY_...` para ajustar opciones comunes, como los niveles de detalle y el muestreo. Consulte la [configuración en sí](https://github.com/newrelic/nrdot-collector-releases/blob/main/examples/internal-telemetry-config.yaml) para obtener más detalles.

    Recomendamos utilizar la configuración predeterminada para monitorear el recolector. Sin embargo, puede modificar la configuración de ejemplo para satisfacer sus necesidades, como reducir el nivel de detalle, el muestreo o las tasas de recolección de datos. Consulte la [documentación oficial](https://opentelemetry.io/docs/collector/internal-telemetry/) para obtener más detalles. Tenga en cuenta que los cambios en la configuración pueden provocar que ciertas partes de la UI no muestren datos. Consulte también [Limitaciones](/docs/opentelemetry/collector-observability/collector-observability#limitations). Las opciones de configuración de la telemetría interna del recolector cambian a medida que la comunidad de OTel evoluciona. Tiene control total sobre la configuración, incluido si desea utilizar los valores predeterminados proporcionados.
  </Step>
</Steps>

## Consideraciones de sobrecarga [#overhead]

Al igual que toda telemetría, la telemetría interna del colector aumenta su ingesta de datos. La sobrecarga depende de su carga de trabajo y configuración. Estos son los factores clave a tener en cuenta:

**Métricas** Genera una sobrecarga constante para el recopilador y todos los componentes activos, independientemente del rendimiento. Las métricas se emiten en un intervalo constante (60 segundos por defecto). Cualquier componente puede emitir métricas personalizadas, como lo indica el respectivo [metadata.yaml](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/filterprocessor/metadata.yaml#L20), lo que puede aumentar la sobrecarga.

Si necesita reducir la cantidad de métricas que emite su colector, recomendamos establecer el nivel de métrica en <DNT>`normal`</DNT>, p. ej. a través de la variable de entorno <DNT>`INTERNAL_TELEMETRY_METRICS_LEVEL`</DNT> en la configuración de ejemplo, ya que la interfaz de usuario solo utiliza un subconjunto de las métricas de <DNT>`detailed`</DNT> y suelen ser métricas destinadas a ajustar el rendimiento o a problemas de red, por lo que puede volver a habilitarlas según sea necesario.

**Logs** Tiene un impacto mínimo durante la operación normal. Puede ocurrir una mayor sobrecarga cuando los logs de errores aumentan rápidamente, pero esto se reduce porque los logs se muestrean de forma predeterminada. El algoritmo de muestreo permite un número constante de logs por intervalo definido y luego muestrea a una tasa estática. Consulte [service::telemetry::logs::sampling](https://github.com/newrelic/nrdot-collector-releases/blob/main/examples/internal-telemetry-config.yaml).

**Trazas** Deshabilitado por defecto debido a:

* Madurez limitada de las trazas. No todos los componentes están instrumentados, consulte este [problema de GitHub](https://github.com/open-telemetry/opentelemetry-collector/issues/8804).
* Sobrecarga impredecible que varía con la carga de trabajo y la configuración de lotes de los agentes y recopiladores ascendentes.
* No hay algoritmo de muestreo adaptativo disponible. Esto hace imposible proporcionar una recomendación de muestreo universal que no conlleve el riesgo de costos inesperados para ciertos casos de uso.

Cuando las trazas maduren, proporcionarán información valiosa sobre cuánto tiempo dedica el colector a procesar datos a nivel de componente. Para experimentar con las trazas a medida que se desarrollan, configure <DNT>`INTERNAL_TELEMETRY_TRACE_LEVEL=info`</DNT> y comience con una tasa de muestreo baja como <DNT>`INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO=0.001`</DNT> (0.1%) mientras monitorea su volumen de ingesta y ajusta según sea necesario.

### Poblar relaciones de infraestructura (opcional, experimental)

Como se mencionó en la [página de resumen](/docs/opentelemetry/collector-observability/collector-observability#summary-page), APM puede mostrar métricas de infraestructura para la infraestructura en la que se ejecuta el recolector, pero solo si la infraestructura está instrumentada y se puede establecer [una relación](https://docs.newrelic.com/docs/new-relic-solutions/new-relic-one/core-concepts/what-entity-new-relic/#related-entities). La relación está determinada por atributos adicionales en la telemetría interna del recolector. Puede leer más sobre este tema en nuestra [documentación de OTel](https://docs.newrelic.com/docs/opentelemetry/best-practices/opentelemetry-best-practices-resources/#service-to-infra-otel-collector). Los pasos para configurar esto dependen en gran medida de la infraestructura exacta. Para la opción común de Kubernetes, creamos [un ejemplo](https://github.com/newrelic/newrelic-opentelemetry-examples/tree/main/other-examples/collector/internal-telemetry-k8s-container-relationships) que muestra cómo lograr relaciones entre contenedores y servicios basado en nuestra [solución de OTel para Kubernetes](https://docs.newrelic.com/docs/kubernetes-pixie/k8s-otel/intro/).
