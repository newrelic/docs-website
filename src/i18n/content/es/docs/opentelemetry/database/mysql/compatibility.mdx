Antes de comenzar a monitorear su MySQL con NRDOT, asegúrese de que su entorno cumpla con estos requisitos.

## Requisitos previos [#prereq]

Antes de comenzar, cerciorar de tener lo siguiente:

* [Clave de licencia](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key)de New Relic válida
* Conectividad de red entre el host donde instala el NRDOT Collector y su base de datos MySQL. Si planea instalar el NRDOT Collector en un host diferente al de su base de datos MySQL, consulte los [Requisitos de acceso a la red](#network).
* Conectividad de red a la [documentación de los extremos OTLP de New Relic](/docs/opentelemetry/best-practices/opentelemetry-otlp/)
* Esta integración está disponible como parte del programa de vista previa pública (public preview) de New Relic. Consulte con el Gerente de su organización para activarla desde la página de [Previsualizaciones y pruebas (Previews &amp; Trials)](https://one.newrelic.com/admin-portal/promotion-management/home).

## Requisitos de acceso a la red [#network]

De forma predeterminada, NRDOT se conecta a través de **TCP** (`transport: tcp` en la configuración del receptor, el valor predeterminado). Si el recolector se ejecuta en el mismo host que la base de datos, en su lugar puede configurar `transport: unix` y apuntar `endpoint` al socket de dominio de Unix de la base de datos (por ejemplo, `/var/run/mysqld/mysqld.sock`), lo que evita por completo las comprobaciones de red a continuación. Para cualquier otro despliegue —recolector y base de datos en diferentes hosts, contenedores o VPC— se requiere TCP.

<table>
  <thead>
    <tr>
      <th>
        Despliegue
      </th>

      <th>
        Qué revisar
      </th>
    </tr>
  </thead>

  <tbody>
    <tr>
      <td>
        MySQL autoadministrado en EC2
      </td>

      <td>
        **Grupo de seguridad**

        : agregue una regla de entrada en el puerto de la base de datos (predeterminado 

        `3306`

        ) desde el origen del recolector —su propio ID de grupo de seguridad (misma VPC, preferido sobre una IP sin procesar) si el recolector se ejecuta en una instancia EC2 diferente, o no se necesita ninguna regla si se ejecuta como un sidecar en la misma instancia. También verifique 

        `bind-address`

         en 

        `my.cnf`

        : muchos valores predeterminados de distribución incluyen 

        `bind-address = 127.0.0.1`

        , que rechaza cualquier conexión TCP no local —establézcalo en la IP privada de la instancia o 

        `0.0.0.0`

         antes de que un recolector remoto pueda alcanzarlo.
      </td>
    </tr>

    <tr>
      <td>
        Amazon RDS/Aurora para MySQL
      </td>

      <td>
        **Grupo de seguridad de VPC**

        : agregue una regla de entrada en el puerto de la instancia de RDS (predeterminado 

        `3306`

        ) desde el grupo de seguridad o la IP privada del recolector; RDS no tiene 

        `my.cnf`

         a nivel de sistema operativo para editar, por lo que esta es la única puerta de red. Los 

        **permisos**

         deben provenir del usuario maestro de RDS — RDS no tiene una cuenta 

        `root`

        . 

        **Privilegios restringidos**

        : 

        `SUPER`

         y 

        `FILE`

         están restringidos o no están disponibles según la versión del motor de RDS y el grupo de parámetros. 

        **TLS**

        : las instancias de RDS con la exigencia de &quot;Require SSL/TLS&quot; necesitan que el recolector confíe en la CA de RDS de Amazon — establezca 

        `tls.ca_file`

         (o 

        `tls.ca_pem`

        ) en el 

        [paquete de certificados de Amazon RDS](https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem)

         y deje 

        `tls.insecure`

        /

        `tls.insecure_skip_verify`

         en 

        `false`

        .
      </td>
    </tr>

    <tr>
      <td>
        Cualquier despliegue remoto/entre hosts
      </td>

      <td>
        MySQL trata a 

        `'<user>'@'localhost'`

         y 

        `'<user>'@'%'`

         (o un host/CIDR específico) como 

        **cuentas diferentes**

        , incluso con un nombre de usuario idéntico — la creación del usuario de monitoreo como 

        `'<user>'@'localhost'`

         falla silenciosamente al autenticarse desde un recolector que se ejecuta en cualquier otro lugar, con un error de acceso denegado indistinguible de una contraseña incorrecta. Use 

        `'<user>'@'%'`

         o limítelo a la IP/CIDR privada específica del recolector.
      </td>
    </tr>
  </tbody>
</table>

<Callout variant="important">
  Verificado en una instancia activa de Amazon RDS para MySQL: la familia de grupos de parámetros `mysql8.0` de RDS no expone ningún parámetro `performance_schema_consumer_*` en absoluto —solo los parámetros de tamaño/búfer más `performance_schema`, `slow_query_log` y `long_query_time` se pueden configurar allí. Esto significa que `events_waits_current` (necesario para `mysql.events_waits_current.timer_wait` y los dashboards basados en esperas en general) solo se puede activar en tiempo de ejecución en RDS, y no sobrevive a un reinicio o conmutación por error.
</Callout>

## Configuración del lado del servidor recomendada [#server]

Configure estos parámetros del servidor MySQL para garantizar que el receptor pueda recopilar todas las métricas y planes de consulta disponibles. La siguiente tabla enumera los parámetros y sus valores recomendados:

<table>
  <thead>
    <tr>
      <th>
        Parámetro
      </th>

      <th>
        Valor recomendado
      </th>

      <th>
        Por qué
      </th>
    </tr>
  </thead>

  <tbody>
    <tr>
      <td>
        `performance_schema`
      </td>

      <td>
        Activado
      </td>

      <td>
        Las muestras de consultas, las consultas principales y la detección de bloqueos dependen de ello
      </td>
    </tr>

    <tr>
      <td>
        `max_digest_length`
      </td>

      <td>
        `4096`
      </td>

      <td>
        Texto de resumen más largo antes de que MySQL lo trunque
      </td>
    </tr>

    <tr>
      <td>
        `performance_schema_max_digest_length`
      </td>

      <td>
        `4096`
      </td>

      <td>
        Igual, en la capa del esquema de rendimiento
      </td>
    </tr>

    <tr>
      <td>
        `performance_schema_max_sql_text_length`
      </td>

      <td>
        `4096`
      </td>

      <td>
        Si una sentencia capturada se trunca, el receptor omite 

        `EXPLAIN`

         para ella por completo. Los planes de consulta desaparecen silenciosamente para sentencias largas en el valor predeterminado de 

        `1024`

        bytes
      </td>
    </tr>
  </tbody>
</table>
