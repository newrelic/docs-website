Puede instalar y configurar el monitoreo de SQL Server en Kubernetes usando el chart de Helm `mssql-otel`. Opcionalmente, el chart también puede ejecutar un trabajo de configuración que le crea el inicio de sesión de monitoreo.

<Callout variant="tip" title="Instalación guiada">
Para instalar esto a través de la UI de New Relic en su lugar, vaya a <DNT>**[one.newrelic.com &gt; Integrations &amp; Agents &gt; Microsoft SQL Server (Database 360)](https://onenr.io/00jlEJX6EQW)** </DNT>. Siga las instrucciones en pantalla para configurar la integración. Esta página solo cubre la instalación manual.
</Callout>

<Callout variant="important">
Este chart solo admite la autenticación de SQL Server (nombre de usuario/contraseña). No admite la autenticación de Windows, la autenticación de dominio de Windows ni gMSA. El recolector siempre se conecta a SQL Server de forma remota a través de la red, ya sea que se ejecute en Linux o Windows, de forma autohospedada o en RDS, por lo que la autenticación de SQL funciona de manera idéntica en todos los casos. También informa solo las métricas de SQL Server (sin métricas de host/infraestructura), ya que el recolector se ejecuta como un despliegue de Kubernetes en lugar de en el propio host de SQL Server.
</Callout>

<Steps>
<Step>
## Requisitos previos [#helm-prerequisites]

* [Clave de licencia](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key) de New Relic válida.

* Helm 3.0 o posterior, y `kubectl` configurado para acceder al clúster de Kubernetes.

* Conectividad de red desde el clúster de Kubernetes al host de SQL Server (o extremo de RDS) y puerto:

  * Autohospedado: una ruta enrutada al host de SQL Server (VPN, peering o red compartida), y el firewall del lado de SQL Server debe permitir la IP de origen de la conexión.
  * AWS RDS: interconexión de VPC, una puerta de enlace de tránsito o ubicación de VPC compartida con la instancia de RDS, y el grupo de seguridad de RDS debe permitir el puerto de SQL Server (`1433` de forma predeterminada) desde el origen de salida del clúster.

* Ya sea un inicio de sesión de monitoreo que ya haya creado o credenciales de administrador de SQL Server (un inicio de sesión con rol `sysadmin`, como `sa` o el usuario maestro de RDS) para que el trabajo de configuración del chart pueda crearle uno. Consulte [Configurar las credenciales de monitoreo](#helm-credentials) a continuación.
</Step>

<Step>
## Cree el namespace [#helm-namespace]

Cree el namespace en el que realizará la instalación. Debe existir antes de crear cualquier secreto en el siguiente paso, ya que `helm install --create-namespace` solo crea el namespace durante el paso de instalación final:

```bash
kubectl create namespace newrelic
```

<Callout variant="tip">
Establézcalo como el namespace predeterminado para el contexto `kubectl` actual para que no necesite pasar `-n` en cada comando a continuación:

```bash
kubectl config set-context --current --namespace=newrelic
```
</Callout>
</Step>

<Step>
## Configurar las credenciales de monitoreo [#helm-credentials]

Decida si desea que el trabajo de configuración del chart cree el inicio de sesión de monitoreo de SQL Server y, de no ser así, cómo proporcionará sus credenciales:

<CollapserGroup>
<Collapser id="helm-creds-inline" title="Sin trabajo de configuración: nombre de usuario y contraseña en texto sin formato">
Con este método no hay un trabajo de configuración, por lo que nada aquí crea el inicio de sesión de monitoreo. Este chart solo admite la autenticación de SQL Server, por lo que antes de instalarlo, cree el inicio de sesión de monitoreo utilizando el paso de autenticación de SQL Server **Crear usuario de monitoreo** de [Linux autohospedado](/docs/opentelemetry/db360/mssql/linux-hosted/#user), [Windows autohospedado](/docs/opentelemetry/db360/mssql/windows-hosted-sql/#user-sql), [Linux RDS](/docs/opentelemetry/db360/mssql/linux-rds/#user) o [Windows RDS](/docs/opentelemetry/db360/mssql/windows-rds-sql/#user-sql), según su entorno.

Configurará el nombre de usuario y la contraseña de monitoreo directamente en `values.yaml` en el siguiente paso.
</Collapser>

<Collapser id="helm-creds-secret-nojob" title="Sin trabajo de configuración: credenciales basadas en secretos">
Con este método tampoco hay un trabajo de configuración. Cree primero el inicio de sesión de monitoreo, exactamente como en el método de credenciales en texto sin formato anterior. La única diferencia es dónde residen sus credenciales: en lugar de texto sin formato en `values.yaml`, guárdelas en un secreto de Kubernetes:

```bash
kubectl create secret generic mssql-monitor-creds \
  --from-literal=username=<MONITORING_USERNAME> \
  --from-literal=password='<MONITORING_PASSWORD>' \
  -n newrelic
```
</Collapser>

<Collapser id="helm-creds-setupjob" title="Trabajo de configuración automatizado">
Con este método, el trabajo de configuración del chart crea el inicio de sesión de monitoreo utilizando las credenciales de administrador de SQL Server. Tanto las credenciales de monitoreo como las de administrador deben proporcionarse como secretos de Kubernetes: el trabajo de configuración nunca acepta credenciales de administrador en texto sin formato, y habilitarlo también requiere credenciales de monitoreo basadas en secretos.

1. Cree un secreto con el nombre de usuario y la contraseña de monitoreo. Esta es la identidad que crea el trabajo de configuración y con la que se conecta el recolector:

   ```bash
   kubectl create secret generic mssql-monitor-creds \
     --from-literal=username=<MONITORING_USERNAME> \
     --from-literal=password='<MONITORING_PASSWORD>' \
     -n newrelic
   ```

2. El trabajo de configuración solo acepta credenciales de administrador a través de un secreto de Kubernetes (sin nombre de usuario/contraseña en texto sin formato en `values.yaml`). Dado que esta credencial puede crear inicios de sesión y otorgar un amplio acceso a `VIEW`, créela como su propio secreto. Utilice un inicio de sesión en el rol `sysadmin` (o equivalente) para SQL Server autohospedado, o el usuario maestro de RDS para SQL Server en AWS RDS:

   ```bash
   kubectl create secret generic mssql-admin-creds \
     --from-literal=username=<ADMIN_USERNAME> \
     --from-literal=password='<ADMIN_PASSWORD>' \
     -n newrelic
   ```
</Collapser>
</CollapserGroup>
</Step>

<CollapserGroup>
<Collapser id="helm-values-inline" title="Sin trabajo de configuración: nombre de usuario y contraseña en texto sin formato">
```yaml
licenseKey: <YOUR_LICENSE_KEY>
otlpEndpoint: https://otlp.nr-data.net:4318

mssql:
  topology: <self-hosted|rds>
  server: <YOUR_DB_HOST>
  port: <YOUR_DB_PORT>
  username: <YOUR_MONITORING_USERNAME>
  password: <YOUR_MONITORING_PASSWORD>

# No setup job runs, so create the monitoring login yourself
# before installing the chart.
setupJob:
  enabled: false
```
</Collapser>

```yaml
licenseKey: <YOUR_LICENSE_KEY>

  topology: <self-hosted|rds>
  server: <YOUR_DB_HOST>
  port: <YOUR_DB_PORT>
  existingSecret: mssql-monitor-creds

# No setup job runs, so the monitoring login referenced by
# this secret must already exist - create it yourself
# before installing the chart.
setupJob:
  enabled: false
```
</Collapser>

<Collapser id="helm-values-setupjob" title="Trabajo de configuración automatizado">
```yaml
licenseKey: <YOUR_LICENSE_KEY>
otlpEndpoint: https://otlp.nr-data.net:4318

mssql:
  topology: <self-hosted|rds>
  server: <YOUR_DB_HOST>
  port: <YOUR_DB_PORT>
  existingSecret: mssql-monitor-creds

setupJob:
  enabled: true
  image:
    # -- sqlcmd image. No default: see the chart's README for why
    # (mcr.microsoft.com/mssql-tools:latest is freely pullable but
    # stale and unmaintained).
    repository: ""
    tag: ""
    pullPolicy: IfNotPresent
  sqlAdmin:
    existingSecret: mssql-admin-creds
```
</Collapser>

<Step>
## (Opcional) Monitorear múltiples instancias desde un release [#helm-multi]

En lugar de `mssql.*`, configure `mssqlMulti.enabled: true` para monitorear varias instancias de SQL Server (autohospedadas o RDS) desde un solo pod recolector en un release. Los dos modos son mutuamente excluyentes: no configure `mssql.server` y `mssqlMulti.enabled: true` en el mismo lanzamiento.

El modo de múltiples instancias no tiene una ruta de nombre de usuario/contraseña en texto sin formato: cada instancia necesita su propio secreto de Kubernetes con credenciales de monitoreo. Decida si también desea que el trabajo de configuración le cree cada inicio de sesión de monitoreo:

<CollapserGroup>
<Collapser id="helm-multi-nojob" title="Sin trabajo de configuración">
Cree usted mismo el secreto de inicio de sesión de monitoreo de cada instancia antes de instalar (repita por instancia, haciendo coincidir el `name` que le asigne en `values.yaml`):

```bash
kubectl create secret generic db1-monitor-creds \
  --from-literal=username=<MONITORING_USERNAME> \
  --from-literal=password='<MONITORING_PASSWORD>' \
  -n newrelic
# Repeat for every instance (db2-monitor-creds, ...)
```

```yaml
licenseKey: <YOUR_LICENSE_KEY>
otlpEndpoint: https://otlp.nr-data.net:4318

# EDIT the two example entries below (or add more) to match
# your real instances - each `name` must be unique within
# this release and match the Secret you created for it.
mssqlMulti:
  enabled: true
  topology: <self-hosted|rds>
  databases:
    - name: db1
      server: <YOUR_DB_1_HOST>
      existingSecret: db1-monitor-creds
    - name: db2
      server: <YOUR_DB_2_HOST>
      existingSecret: db2-monitor-creds

# No admin credential is configured here since the setup
# job is disabled - create each instance's monitoring login
# yourself first.
setupJob:
  enabled: false
```
</Collapser>

<Collapser id="helm-multi-setupjob" title="Trabajo de configuración automatizado">
Cada instancia necesita tanto su propio secreto de inicio de sesión de monitoreo como su propio secreto de credenciales de administrador (repita por instancia):

```bash
kubectl create secret generic db1-monitor-creds \
  --from-literal=username=<MONITORING_USERNAME> \
  --from-literal=password='<MONITORING_PASSWORD>' \
  -n newrelic
kubectl create secret generic db1-admin-creds \
  --from-literal=username=<ADMIN_USERNAME> \
  --from-literal=password='<ADMIN_PASSWORD>' \
  -n newrelic
# Repeat for every instance (db2-monitor-creds, db2-admin-creds, ...)
```

```yaml
licenseKey: <YOUR_LICENSE_KEY>
otlpEndpoint: https://otlp.nr-data.net:4318

# EDIT the two example entries below (or add more) to match
# your real instances - each `name` must be unique within
# this release and match the Secrets you created for it.
mssqlMulti:
  enabled: true
  topology: <self-hosted|rds>
  databases:
    - name: db1
      server: <YOUR_DB_1_HOST>
      existingSecret: db1-monitor-creds
      sqlAdmin:
        existingSecret: db1-admin-creds
    - name: db2
      server: <YOUR_DB_2_HOST>
      existingSecret: db2-monitor-creds
      sqlAdmin:
        existingSecret: db2-admin-creds

setupJob:
  enabled: true
  image:
    repository: ""
    tag: ""
```
</Collapser>
</CollapserGroup>

<Callout variant="tip">
Los ajustes de extracción (intervalo de recolección, TLS, métrica) se aplican de manera idéntica a cada instancia en `mssqlMulti.databases`. No hay sobrescritura por instancia. Use `additionalReceiverConfig` para cualquier cosa que deba ser diferente. El trabajo de configuración se ejecuta una vez por instancia (`<release>-setup-<name>`) en lugar de una vez por versión.
</Callout>

<Step>
## Instale el chart de Helm [#helm-install]

1. Agregue el repositorio Helm de New Relic:

   ```bash
   helm repo add newrelic https://helm-charts.newrelic.com
   helm repo update
   ```

2. Instale el chart utilizando su archivo `values.yaml`:

   ```bash
   helm upgrade --install mssql-otel newrelic/mssql-otel \
     -n newrelic \
     --create-namespace \
     -f values.yaml
   ```
</Step>

<Step>
## Verifique la instalación [#helm-verify]

1. Compruebe que el trabajo de configuración se haya completado (si está habilitado) y que el pod del recolector se esté ejecutando:

   ```bash
   kubectl get jobs,pods -n newrelic --watch
   ```

2. Ejecute esta consulta en el [generador de consultas](/docs/query-your-data/explore-query-data/query-builder/introduction-query-builder/) para confirmar que los datos están llegando:

   ```sql
   SELECT count(*) FROM Metric
   WHERE metricName LIKE 'sqlserver.%'
   AND instrumentation.provider = 'opentelemetry'
   SINCE 10 minutes ago
   ```
</Step>

<Step>
## Encuentra y utiliza tus datos [#find]

Una vez que sus datos se estén recopilando, puede acceder al monitoreo integral de bases de datos SQL Server a través de la UI de New Relic.

Para encontrar su entidad de base de datos SQL Server en New Relic:

1. Vaya a <DNT>**[one.newrelic.com](https://one.newrelic.com) &gt; All capabilities &gt; Databases**</DNT>.

2. En el menú desplegable **<DNT>Entity type</DNT>**, seleccione <DNT>**MSSQL instance**</DNT> y luego haga clic en <DNT>**Apply**</DNT>.

3. Seleccione su base de datos SQL Server de la lista de entidades.

   Después de configurar el monitoreo de SQL Server con NRDOT, puede:

   * [Crea dashboards personalizados](/docs/query-your-data/explore-query-data/dashboards/introduction-dashboards/) para visualizar las métricas de tu base de datos
   * [Configura alertas](/docs/alerts/create-alert/create-alert-condition/alert-conditions/) para umbrales críticos de rendimiento de la base de datos
   * [Explore los datos](/docs/query-your-data/explore-query-data/browse-data/introduction-data-explorer/) con las capacidades de consulta de New Relic
</Step>
</Steps>
