Antes de comenzar a monitorear su MySQL con NRDOT, asegúrese de que su entorno cumpla con estos requisitos.

## Requisitos previos [#prereq]

Antes de comenzar, cerciorar de tener lo siguiente:

* Una [clave de licencia](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key)de New Relic válida
* Conectividad de red entre el host donde instala el NRDOT Collector y su base de datos MySQL. Si planea instalar el NRDOT Collector en un host diferente al de su base de datos MySQL, consulte los [Requisitos de acceso a la red](#network).
* Conectividad de red a la [documentación de los extremos OTLP de New Relic](/docs/opentelemetry/best-practices/opentelemetry-otlp/)

## Requisitos de acceso a la red [#network]

Por defecto, NRDOT se conecta a través de **TCP** (`transport: tcp` en la configuración del receptor, el valor por defecto). Si el recolector se ejecuta en el mismo host que la base de datos, en su lugar puede establecer `transport: unix` y apuntar `endpoint` al socket de dominio Unix de la base de datos (por ejemplo, `/var/run/mysqld/mysqld.sock`), lo que evita por completo las comprobaciones de red a continuación. Para cualquier otro despliegue (recolector y base de datos en diferentes hosts, contenedores o VPC), se requiere TCP.

<table>
  <thead>
    <tr>
      <th>
        Despliegue
      </th>

      <th>
        Qué revisar
      </th>
    </tr>
  </thead>

  <tbody>
    <tr>
      <td>
        MySQL autoadministrado en EC2
      </td>

      <td>
        **Grupo de seguridad**

        : agregue una regla de entrada en el puerto de la base de datos (predeterminado 

        `3306`

        ) desde el origen del recolector: su propio ID de grupo de seguridad (misma VPC, preferible a una IP sin procesar) si el recolector se ejecuta en una instancia EC2 diferente, o no se necesita ninguna regla si se ejecuta como sidecar en la misma instancia. Verifique también 

        `bind-address`

         en 

        `my.cnf`

        : muchas distribuciones incluyen por defecto 

        `bind-address = 127.0.0.1`

        , que rechaza cualquier conexión TCP no local. Establézcalo en la IP privada de la instancia o en 

        `0.0.0.0`

         antes de que un recolector remoto pueda acceder a él.
      </td>
    </tr>

    <tr>
      <td>
        Amazon RDS/Aurora para MySQL
      </td>

      <td>
        **Grupo de seguridad de VPC**

        : agregue una regla de entrada en el puerto de la instancia de RDS (predeterminado 

        `3306`

        ) desde el grupo de seguridad del recolector o la IP privada; RDS no tiene 

        `my.cnf`

         a nivel de sistema operativo para editar, por lo que esta es la única puerta de red. Los 

        **permisos**

         deben provenir del usuario maestro de RDS. RDS no tiene una cuenta 

        `root`

        . 

        **Privilegios restringidos**

        : 

        `SUPER`

         y 

        `FILE`

         están restringidos o no están disponibles según la versión del motor de RDS y el grupo de parámetros. 

        **TLS**

        : las instancias de RDS con la imposición de “Require SSL/TLS” necesitan que el recolector confíe en la CA de RDS de Amazon. Establezca 

        `tls.ca_file`

         (o 

        `tls.ca_pem`

        ) en el 

        [paquete de certificados de Amazon RDS](https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem)

         y deje 

        `tls.insecure`

        /

        `tls.insecure_skip_verify`

         en 

        `false`

        .
      </td>
    </tr>

    <tr>
      <td>
        Cualquier despliegue remoto/entre hosts
      </td>

      <td>
        MySQL trata 

        `'<user>'@'localhost'`

         y 

        `'<user>'@'%'`

         (o un host/CIDR específico) como 

        **cuentas diferentes**

        , incluso con un nombre de usuario idéntico. Crear el usuario de monitoreo como 

        `'<user>'@'localhost'`

         falla silenciosamente al autenticar desde un recolector que se ejecuta en cualquier otro lugar, con un error de acceso denegado indistinguible de una contraseña incorrecta. Use 

        `'<user>'@'%'`

         o limítelo a la IP/CIDR privada específica del recolector.
      </td>
    </tr>
  </tbody>
</table>

<Callout variant="important">
  Verificado en una instancia activa de Amazon RDS para MySQL: la familia de grupos de parámetros `mysql8.0` de RDS no expone parámetros `performance_schema_consumer_*` en absoluto; solo los parámetros de tamaño/búfer, además de `performance_schema`, `slow_query_log` y `long_query_time`, se pueden configurar allí. Esto significa que `events_waits_current` (necesario para `mysql.events_waits_current.timer_wait` y para los dashboards basados en esperas en general) solo se puede activar en tiempo de ejecución en RDS, y no sobrevive a un reinicio o conmutación por error.
</Callout>

## Configuración del lado del servidor recomendada [#server]

Configure estos parámetros del servidor MySQL para garantizar que el receptor pueda recopilar todas las métricas y planes de consulta disponibles. La siguiente tabla enumera los parámetros y sus valores recomendados:

    <tr>

      <td>

      </td>

      </td>

        `1024`

        bytes

## Próximos pasos [#next]

Una vez que haya verificado que su entorno cumple con estos requisitos previos:

1. Elija su método de instalación:

* [Configuración autohospedada](/docs/opentelemetry/db360/mysql/hosted)
* [Configuración de AWS RDS](/docs/opentelemetry/db360/mysql/rds)

2. Revise las [métricas disponibles](/docs/opentelemetry/db360/mysql/metrics-reference) que se recopilarán
3. Consulte [Habilitar información valiosa detallada](/docs/opentelemetry/db360/mysql/optional) para conocer características opcionales como los planes de consulta de sentencias de escritura y el seguimiento de la duración de la espera de bloqueo
4. Consulte la [guía de resolución de problemas](/docs/opentelemetry/db360/mysql/troubleshooting) para problemas comunes
