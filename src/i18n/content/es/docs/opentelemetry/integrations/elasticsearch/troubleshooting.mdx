Si ha completado la [instalación de la integración de OpenTelemetry de Elasticsearch](/docs/opentelemetry/integrations/elasticsearch/elasticsearch-otel-integration-install) o la [instalación de Kubernetes](/docs/opentelemetry/integrations/elasticsearch/elasticsearch-otel-integration-k8-install) pero no ve datos en New Relic, busque su problema a continuación y siga los pasos de la solución.

## Implementaciones basadas en host [#host-troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-collector-stopped" title="El servicio de colector se detuvo o falló">
    <strong>Cómo verificar</strong>

    ```bash
    sudo systemctl status otelcol-contrib
    ```

    <strong>Resolución</strong>

    * Si el servicio está inactivo, inícielo:
      <InlineCode>
        sudo systemctl start otelcol-contrib
      </InlineCode>
    * Si el servicio falló, corrija los errores de configuración y reinicie:
      <InlineCode>
        sudo systemctl restart otelcol-contrib
      </InlineCode>
  </Collapser>

  <Collapser id="troubleshoot-collector-logs-errors" title="Los logs del Collector reportan errores de scraping o exportación">
    <strong>Cómo verificar</strong>

    ```bash
    sudo journalctl -u otelcol-contrib.service -f
    ```

    <strong>Resolución</strong>

    Revise la salida del log y resuelva la causa raíz (por ejemplo, problemas de conexión, fallas de autenticación o problemas de permisos).
  </Collapser>

  <Collapser id="troubleshoot-connection-refused" title="Conexión rechazada al llamar a Elasticsearch">
    <strong>Muestra de error</strong>: <InlineCode>
      dial tcp \[::1]:9200: connect: connection refused
    </InlineCode>

    <strong>Resolución</strong>

    * Asegúrese de que el
      <InlineCode>
        endpoint
      </InlineCode>
      en
      <InlineCode>
        config.yaml
      </InlineCode>
      coincida con el host y el puerto de Elasticsearch.
    * Confirme que Elasticsearch se esté ejecutando y sea accesible desde el host del colector.
  </Collapser>

  <Collapser id="troubleshoot-403" title="403 Forbidden al exportar a New Relic">
    <strong>Muestra de error</strong>: <InlineCode>
      permanent error: 403 Forbidden
    </InlineCode>

    <strong>Resolución</strong>

    1. Verifique <InlineCode>
         NEWRELIC\_LICENSE\_KEY
       </InlineCode> en <InlineCode>
         /etc/systemd/system/otelcol-contrib.service.d/environment.conf
       </InlineCode>.

    2. Recargue systemd y reinicie el recopilador:

       ```bash
       sudo systemctl daemon-reload
       sudo systemctl restart otelcol-contrib
       ```
  </Collapser>

  <Collapser id="troubleshoot-permission-denied" title="Permiso denegado al recopilar logs">
    <strong>Muestra de error</strong>: <InlineCode>
      permission denied
    </InlineCode> o <InlineCode>
      cannot open file
    </InlineCode>

    <strong>Resolución</strong>

    1. Agregue el usuario del colector al grupo de Elasticsearch:
       ```bash
       sudo usermod -a -G elasticsearch otelcol-contrib
       ```
    2. Reinicie el colector:
       <InlineCode>
         sudo systemctl restart otelcol-contrib
       </InlineCode>
  </Collapser>

  <Collapser id="troubleshoot-api-reachability" title="No se puede acceder a la API de Elasticsearch desde el colector">
    <strong>Cómo verificar</strong>

    ```bash
    # Unsecured cluster
    curl -I http://localhost:9200

    # With authentication
    curl -u username:password -k https://localhost:9200
    ```

    <strong>Resolución</strong>

    Verifique que el clúster esté en buen estado, que las credenciales sean válidas y que la configuración del firewall o de seguridad permita el acceso.
  </Collapser>

  <Collapser id="troubleshoot-missing-entity" title="Entidad de Elasticsearch faltante en la UI de New Relic">
    <strong>Resolución</strong>

    * Asegúrese de que el procesador
      <InlineCode>
        resourcedetection
      </InlineCode>
      esté incluido en cada pipeline de métricas.
    * Verifique que
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      esté configurado mediante el procesador
      <InlineCode>
        resource/cluster_name_override
      </InlineCode>
      .
  </Collapser>

  <Collapser id="troubleshoot-logs-missing" title="Métricas presentes pero faltan logs">
    <strong>Resolución</strong>

    * Confirme que las rutas del receptor
      <InlineCode>
        filelog
      </InlineCode>
      sean correctas y absolutas.
    * Verifique que el pipeline de logs incluya tanto el receptor
      <InlineCode>
        filelog
      </InlineCode>
      como el exportador
      <InlineCode>
        otlphttp
      </InlineCode>
      .
  </Collapser>
</CollapserGroup>

## Implementaciones de Kubernetes [#kubernetes-troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-k8s-no-pods-discovered" title="No se descubrieron pods de Elasticsearch - faltan etiquetas">
    <strong>Cómo verificar</strong>

    ```bash
    # Verify your Elasticsearch pods have the required label
    kubectl get pods -n <namespace> -l app=elasticsearch --show-labels
    ```

    <strong>Resolución</strong>

    Si no se devuelven pods, a sus pods de Elasticsearch les falta la etiqueta <InlineCode>
      app=elasticsearch
    </InlineCode> requerida. El receiver\_creator no puede descubrir pods sin etiquetas coincidentes.

    * Para StatefulSet/despliegue, agregue la etiqueta en la plantilla del pod:
      ```yaml
      spec:
        template:
          metadata:
            labels:
              app: elasticsearch
      ```
    * Para los pods existentes, agregue la etiqueta y reinicie:
      ```bash
      kubectl label pods -l <your-selector> app=elasticsearch -n <namespace>
      kubectl rollout restart statefulset/elasticsearch -n <namespace>
      ```
    * Si utiliza etiquetas personalizadas, actualice la regla del receptor en values.yaml para que coincida con sus etiquetas:
      ```yaml
      rule: type == "pod" && labels["app"] == "your-custom-label"
      ```
  </Collapser>

  <Collapser id="troubleshoot-k8s-collector-not-running" title="Los pods del Collector no se ejecutan o fallan">
    <strong>Cómo verificar</strong>

    ```bash
    kubectl get pods -n newrelic
    kubectl describe pod <collector-pod-name> -n newrelic
    ```

    <strong>Resolución</strong>

    * Verifique los eventos del pod para detectar errores:
      <InlineCode>
        kubectl describe pod
      </InlineCode>

    * Revisar los logs del recolector:

      ```bash
      kubectl logs -n newrelic -l app.kubernetes.io/name=opentelemetry-collector
      ```

    * Verifique que exista el secreto:

      ```bash
      kubectl get secret newrelic-licenses -n newrelic
      ```

    * Verificar que los límites de recursos no sean demasiado bajos
  </Collapser>

  <Collapser id="troubleshoot-k8s-discovery-errors" title="El creador de receptores no puede descubrir pods">
    <strong>Cómo verificar</strong>

    ```bash
    # Check collector logs for discovery errors
    kubectl logs -n newrelic -l app.kubernetes.io/name=opentelemetry-collector | grep "receiver_creator"
    ```

    <strong>Resolución</strong>

    * Verifique que los permisos RBAC estén configurados correctamente:

      ```bash
      kubectl get clusterrole | grep opentelemetry
      kubectl describe clusterrole <role-name>
      ```

    * Asegúrese de que el recolector tenga permisos para observar pods, nodos y extremos

    * Verifique que la extensión k8s\_observer esté habilitada en la configuración
  </Collapser>

  <Collapser id="troubleshoot-k8s-network-connectivity" title="Collector no puede conectarse a los pods de Elasticsearch">
    <strong>Cómo verificar</strong>

    ```bash
    # Check network policies
    kubectl get networkpolicies -n <namespace>

    # Test connectivity from collector to Elasticsearch
    kubectl exec -n newrelic <collector-pod> -- curl http://<es-pod-ip>:9200
    ```

    <strong>Resolución</strong>

    * Verifique que las políticas de red permitan el tráfico desde el namespace newrelic hacia su namespace de Elasticsearch
    * Verifique si los pods de Elasticsearch están exponiendo el puerto correcto (predeterminado: 9200)
    * Asegúrese de que ninguna regla de firewall bloquee la comunicación entre pods.
  </Collapser>

  <Collapser id="troubleshoot-k8s-wrong-endpoint" title="403 Forbidden o errores de autenticación en Kubernetes">
    <strong>Muestra de error</strong>: <InlineCode>
      permanent error: 403 Forbidden
    </InlineCode>

    <strong>Resolución</strong>

    * Verifique que el secreto contenga la clave de licencia correcta:

      ```bash
      kubectl get secret newrelic-licenses -n newrelic -o jsonpath='{.data.NEWRELIC_LICENSE_KEY}' | base64 -d
      ```

    * Asegúrese de que el extremo OTLP sea correcto para su región

    * Compruebe que el secreto esté montado en el pod recolector:

      ```bash
      kubectl describe pod <collector-pod> -n newrelic | grep -A5 "Environment"
      ```
  </Collapser>

  <Collapser id="troubleshoot-k8s-logs-not-collected" title="Los logs no se están recopilando en Kubernetes">
    <strong>Resolución</strong>

    * Verifique que está usando
      <InlineCode>
        mode: daemonset
      </InlineCode>
      (el modo de despliegue no puede acceder a los logs del nodo)

    * Verifique que los montajes de volumen estén configurados correctamente:

      ```bash
      kubectl describe pod <collector-pod> -n newrelic | grep -A10 "Mounts"
      ```

    * Verifique que la ruta del receptor filelog coincida con los logs de su pod de Elasticsearch:

      ```bash
      kubectl exec -n newrelic <collector-pod> -- ls /var/log/pods/*/elasticsearch*/*.log
      ```

    * Asegúrese de que el recolector tenga permisos de lectura en los directorios de logs del host
  </Collapser>

  <Collapser id="troubleshoot-k8s-cluster-name-missing" title="Métricas sin el atributo k8s.cluster.name">
    <strong>Resolución</strong>

    * Verifique que la variable de entorno
      <InlineCode>
        K8S_CLUSTER_NAME
      </InlineCode>
      esté configurada en values.yaml

    * Verifique que el procesador
      <InlineCode>
        resource/cluster
      </InlineCode>
      esté en el pipeline de métricas

    * Consulta para verificar:

      ```sql
      FROM Metric SELECT * WHERE metricName LIKE 'elasticsearch.%' LIMIT 1
      ```

      Verifique si el atributo <InlineCode>
        k8s.cluster.name
      </InlineCode> está presente
  </Collapser>
</CollapserGroup>

## Correlación de APM y rastreo distribuido [#correlation-troubleshooting]

Estos problemas se aplican cuando ha configurado la [correlación de APM con el rastreo distribuido](/docs/opentelemetry/integrations/elasticsearch/distributed-tracing).

<CollapserGroup>
  <Collapser id="troubleshoot-no-es-spans" title="No aparecen spans de Elasticsearch en New Relic">
    <strong>Cómo verificar</strong>

    ```sql
    FROM Span SELECT count(*) WHERE es.cluster.name = '<elasticsearch-cluster-name>' SINCE 30 minutes ago
    ```

    <strong>Resolución</strong>

    * La exportación nativa de trazas OTLP requiere <strong>Elasticsearch 9.4 o posterior</strong>. Confirme la versión con
      <InlineCode>
        curl http://localhost:9200
      </InlineCode>
      .
    * Verifique que las tres configuraciones estén presentes en
      <InlineCode>
        elasticsearch.yml
      </InlineCode>
      :
      <InlineCode>
        telemetry.tracing.enabled: true
      </InlineCode>
      ,
      <InlineCode>
        telemetry.export.endpoint
      </InlineCode>
      y
      <InlineCode>
        telemetry.tracing.sample_rate
      </InlineCode>
      .
    * Confirme que la propiedad del sistema de la JVM
      <InlineCode>
        -Dtelemetry.otel.traces.enabled=true
      </InlineCode>
      esté configurada (en
      <InlineCode>
        jvm.options
      </InlineCode>
      o
      <InlineCode>
        ES_JAVA_OPTS
      </InlineCode>
      ) y, luego, reinicie Elasticsearch.
    * El valor predeterminado de
      <InlineCode>
        telemetry.tracing.sample_rate
      </InlineCode>
      es
      <InlineCode>
        0.001
      </InlineCode>
      (0.1 %). Auméntelo durante la validación para que los spans aparezcan rápidamente.
  </Collapser>

  <Collapser id="troubleshoot-traces-pipeline" title="Elasticsearch está exportando spans, pero nunca llegan a New Relic.">
    <strong>Resolución</strong>

    * Confirme que el recolector tenga un receptor
      <InlineCode>
        otlp
      </InlineCode>
      con el protocolo gRPC habilitado en
      <InlineCode>
        0.0.0.0:4317
      </InlineCode>
      y que el extremo sea accesible desde los nodos de Elasticsearch.
    * Confirme que exista un pipeline de
      <InlineCode>
        traces
      </InlineCode>
      e incluya el receptor
      <InlineCode>
        otlp
      </InlineCode>
      y el exportador
      <InlineCode>
        otlphttp
      </InlineCode>
      .
    * Verifique los logs del recolector en busca de errores de exportación o del receptor OTLP.
  </Collapser>

  <Collapser id="troubleshoot-cluster-self-loop" title="El clúster muestra una relación consigo mismo (se llama a sí mismo)">
    <strong>Causa</strong>

    Aparece un bucle automático cuando llegan a New Relic spans de Elasticsearch que no se pueden atribuir a una aplicación de llamada. Hay dos fuentes comunes:

    * <strong>Spans de Elasticsearch sin elementos principales (raíz)</strong> —spans sin span de aplicación principal, como los sondeos de estado de Kubernetes o las propias llamadas de extracción del receptor de métricas de Elasticsearch (
      <InlineCode>
        \_nodes/stats
      </InlineCode>
      ,
      <InlineCode>
        \_cluster/health
      </InlineCode>
      y similares). Debido a que no son parte de la traza de una aplicación, New Relic no tiene un servicio de llamada y dibuja la relación en el propio clúster.
    * <strong>La dirección propia del nodo</strong> —los spans del servidor de Elasticsearch contienen
      <InlineCode>
        http.request.headers.host
      </InlineCode>
      (y
      <InlineCode>
        server.address
      </InlineCode>
      ), que New Relic resuelve en el clúster.

    <strong>Resolución</strong>

    Agregue ambos procesadores a la canalización de <InlineCode>
      traces
    </InlineCode> y, a continuación, reinicie el recolector. <InlineCode>
      filter/drop\_rootless\_es
    </InlineCode> descarta los spans de Elasticsearch sin elementos principales (los spans controlados por la aplicación siempre tienen un elemento principal, por lo que se mantienen) y <InlineCode>
      transform/strip\_es\_host
    </InlineCode> elimina los atributos de dirección:

    ```yaml
    processors:
      filter/drop_rootless_es:
        error_mode: ignore
        traces:
          span:
            - 'instrumentation_scope.name == "elasticsearch" and IsRootSpan()'
      transform/strip_es_host:
        error_mode: ignore
        trace_statements:
          - context: span
            statements:
              - delete_key(attributes, "http.request.headers.host") where instrumentation_scope.name == "elasticsearch"
              - delete_key(attributes, "server.address") where instrumentation_scope.name == "elasticsearch"
    # traces pipeline: processors: [filter/drop_rootless_es, transform/strip_es_host, batch]
    ```

    Los autobucles existentes se eliminan por sí solos una vez que llegan los spans corregidos y la relación anterior expira (esto puede tardar hasta unos 75 minutos).
  </Collapser>

  <Collapser id="troubleshoot-app-not-linked" title="Llegan los spans de Elasticsearch, pero las aplicaciones no están vinculadas al clúster">
    <strong>Resolución</strong>

    * Asegúrese de que las aplicaciones estén instrumentadas y propaguen el encabezado
      <InlineCode>
        traceparent
      </InlineCode>
      del W3C en las llamadas a Elasticsearch. La mayoría de los clientes modernos de Elasticsearch hacen esto automáticamente cuando la aplicación está instrumentada con OpenTelemetry.
    * Abra un rastreo distribuido que incluya una llamada a Elasticsearch y confirme que los spans de la aplicación y los spans de Elasticsearch comparten la misma traza.
    * Espere unos minutos para que se establezca la relación. New Relic vuelve a evaluar las relaciones de entidad periódicamente.
  </Collapser>

  <Collapser id="troubleshoot-name-mismatch" title="Las trazas y las métricas se resuelven en diferentes entidades del clúster">
    <strong>Resolución</strong>

    * La ruta de trazas se basa en
      <InlineCode>
        es.cluster.name
      </InlineCode>
      (marcado por Elasticsearch en sus spans) y la ruta de métricas en
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      . El
      <InlineCode>
        elasticsearchreceiver
      </InlineCode>
      informa
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      automáticamente a partir del valor que devuelve Elasticsearch, por lo que ambos derivan del mismo
      <InlineCode>
        cluster.name
      </InlineCode>
      y se resuelven en una entidad —no se necesita configuración adicional del recolector.
    * No fuerce el nombre del clúster de métricas a un valor fijo. Si la configuración del recolector lo establece con un procesador
      <InlineCode>
        resource
      </InlineCode>
      (por ejemplo, un
      <InlineCode>
        resource/cluster_name_override
      </InlineCode>
      que define el nombre de forma rígida), elimine esa sobrescritura —de lo contrario, las métricas y las trazas se resuelven en dos entidades diferentes y la entidad correlacionada no muestra datos de métricas.
    * Asegúrese de que el
      <InlineCode>
        cluster.name
      </InlineCode>
      de Elasticsearch sea único en la cuenta de New Relic para que se asigne a una única entidad inequívoca.
  </Collapser>
</CollapserGroup>
