## 0. Configure su entorno local [#set-local]

Solo necesita configurar su entorno local una vez. Si ya ha hecho esto, puede omitir este paso.

Vaya aquí para obtener instrucciones detalladas sobre cómo [configurar su entorno de compilación local](/docs/style-guide/writing-docs/writer-workflow/set-up-local).

## 1. Cree una rama y edite los documentos [#edit-doc]

En GitHub Desktop, verá tres pestañas con las etiquetas **Repositorio actual**, **Rama actual** y **Obtener origen**. La rama predeterminada es **Develop**, por lo que es hora de crear una rama.

1. Haga clic en **Current Branch** y seleccione **New Branch**.
2. Busque un documento que desea editar.
   * Use Finder o el Explorador de archivos con la ruta del archivo. Por ejemplo, si deseara editar un documento del agente de Python, navegaría a: `~/Documents/github/docs-website/src/content/docs/agents/python-agent/hosting-services/python-agent-stackato.mdx`
3. [Edite el documento](https://docs.newrelic.com/docs/style-guide/writing-docs/processes-procedures/create-edit-content) en su editor de texto preferido. Debe escribir los documentos con [lenguaje markdown](https://www.markdownguide.org/basic-syntax).
4. Guarde el archivo con sus ediciones.

Consulte el resto de nuestra [guía de estilo](https://docs.newrelic.com/docs/style-guide/writing-strategies/introduction-style-guide/) para cualquier pregunta sobre las pautas de escritura.

## 2. Confirme sus cambios [#commit-changes]

Aunque haya guardado sus ediciones, aún debe hacer un commit. Puede pensar en un commit como un punto de control en su flujo de trabajo. El proceso de commit comienza con la fase de prueba y termina cuando envía sus cambios a GitHub.

1. Vuelva a GitHub Desktop y revise la columna izquierda. En Github Desktop la columna izquierda muestra:

   * Un registro de todas las nuevas ediciones realizadas en cualquier documento
   * Un botón azul que dice **Commit to \[your-branch-name]**

2. Asigne un nombre a su commit y agregue una descripción.

3. Haga clic en **Commit to \[yourbranchname]**.
   * El nombre y la descripción del commit podrían verse como `feat(PythonAgent): Renamed the section heading`

## 3. Ejecute el sitio localmente [#run-site]

Compile el sitio localmente usando la terminal. Si bien este paso es opcional, se recomienda **ampliamente** compilar el sitio localmente y previsualizar los cambios antes de abrir un pull request.

Solo necesita reconstruir el sitio local cuando falla, no después de cada guardado o commit.

1. En su terminal, vaya a su repositorio clonado, **docs-website**. Por ejemplo:
   * `cd ~/Documents/github/docs-website`
2. Ejecute yarn con los siguientes comandos: `yarn && yarn start`
3. El sitio tardará unos minutos en compilarse. Prepárese un té o un café.
4. Una vez compilado, obtenga una vista previa del sitio en su navegador navegando a [http://localhost:8000/](http://localhost:8000/)

## 4. Publique sus commits [#publish-commits]

Una vez que esté satisfecho con sus cambios, envíe sus commits a GitHub. Esto los hace disponibles para todos los demás en el respositorio de GitHub.

1. En GitHub Desktop, haga clic en el botón azul **Publish Branch** si está disponible.
2. Si no ve Publish Branch, haga clic en el botón azul **Push Origin**.

## 5. Abra su pull request [#open-pr]

Aunque sus confirmaciones son visibles para todos, sus ediciones no se fusionarán en la rama `develop `hasta que otro escritor las haya revisado.

Para hacer esto, abra un pull request (PR):

1. En GitHub Desktop, haga clic en el botón azul **Crear pull request**.

2. Esto abrirá GitHub en su navegador y le solicitará que complete su pull request.

   * Asegúrese de fusionar desde su rama hacia la rama `develop`.
   * Desplácese hacia abajo para revisar todos sus commits.

3. Al igual que su descripción de commit, su descripción de pull request debe ser detallada y dar el contexto completo de sus cambios.

   * Siéntase libre de agregar cualquier contexto adicional aquí (enlace del problema de GitHub o ID del problema de Jira, expertos en la materia, etc.)
   * Solicite una revisión de otro escritor técnico abriendo el PR, navegando a la sección **Conversación** e ingresando el nombre del revisor en la sección **Revisor**.

4. Agregue la etiqueta `from_tw` y cualquier otra [etiqueta relevante](/docs/style-guide/writer-workflow/github-intro) a su PR.
   * Si no agrega `from_tw`, el PR no se asignará automáticamente a otro escritor para su revisión.

5. Una vez que esté satisfecho con su PR, haga clic en el botón verde **Create pull request**.

6. Puede publicar los cambios directamente al aprobar el pull request, o puede solicitar a otro redactor técnico que lo revise.

7. En la parte inferior de la página del pull request, verá una sección de **Comprobaciones**. Estas comprobaciones aseguran que su pull request no rompa el proceso de compilación del sitio. Asegúrese de que todas las comprobaciones marcadas con `required` pasen antes de fusionar.

8. Una vez que el pull request haya pasado las comprobaciones y haya sido aprobado por otro escritor técnico (o esté seguro de que los cambios están listos para publicarse), haga clic en el botón verde **Merge pull request**. Esto fusionará su rama y commits en el respositorio y comenzará el proceso de compilación.

<Callout variant="important">
  Si no agrega la etiqueta `from_tw` cuando crea un PR por primera vez, no asignará automáticamente un revisor. Si olvida agregar la etiqueta antes de abrir el PR:

  1. Agregue la etiqueta `from_tw`.
  2. Convierta el PR en un PR en borrador.
  3. Seleccione el `PR is ready for review button` en la parte inferior de la página para volver a abrir el PR. El PR ahora debería tener un revisor.
</Callout>

## Previsualizar un documento [#preview-doc]

Hay dos formas principales de obtener una vista previa de las ramas que ya ha publicado y en las que ha ejecutado confirmaciones:

* **Local**: más rápido, pero requiere una cantidad semisustancial de configuración y familiaridad con una terminal.
* **Netlify Cloud**: vista previa completa del sitio en vivo sin sobrecarga y una forma muy conveniente de compartir una vista previa de su borrador con un SME. Netlify Cloud comentará en su PR con un enlace a una versión de vista previa del sitio una vez que la compilación esté lista. La compilación del sitio generalmente toma alrededor de 15 minutos, pero a veces puede demorar más si hay muchos cambios.

## Revisar y publicar un documento [#revise-doc]

Si se le notifica que un revisor ha enviado una revisión a su archivo, vaya a su PR y revise los cambios. Es posible que los vea en la vista de diferencias, si son parte de una revisión con comentarios; de lo contrario, podrían aparecer como ediciones de texto en el archivo.

1. Responda a cualquier comentario en el archivo. O bien responda con una discusión de seguimiento, o haga clic en **Resolve conversation**.
2. Cuando haya resuelto todos los comentarios y hayan pasado todas las comprobaciones automáticas, puede fusionar el pull request. Fusionar el pull request pone en marcha el proceso de compilación automatizado y sus cambios se publicarán en breve.

<Callout variant="tip">
  Solo podrá fusionar cuando el botón **Fusionar pull request** esté verde. Si no está en verde, revise si hay algún comentario que se haya perdido u otros mensajes que indiquen por qué GitHub le impide fusionar.
</Callout>

## Revertir la fusión [#revert]

Recuerde que casi siempre puede deshacer las cosas. Si fusiona un PR y luego descubre que no debería haberlo hecho, puede deshacer la fusión con el botón **Revertir**.

1. En la pestaña de pull request en GitHub, haga clic en **Closed** en la barra de conteo para ver todas las incidencias y PR que ya se han fusionado.
2. Ubique el PR que fusionó y ubique el botón Revertir.
3. Haga clic en Revertir. Eso crea un nuevo PR, que debe fusionarse. Si desea volver a abrirlo, debe seguir el enlace al PR original y revertirlo o volver a abrirlo.

## Solo para escritores: trabaje en una rama, no en una bifurcación [#branch-fork]

Algunos equipos trabajan en ramas, algunos equipos trabajan en bifurcaciones; **el equipo de Docs trabaja en ramas**. Siempre que una rama se haya enviado a upstream, esto nos permite trabajar de forma colaborativa y garantizar que nunca se pierda ningún trabajo cuando alguien se va de vacaciones.

Para crear una rama en el repositorio docs-website:

1. Abra GitHub Desktop
2. Haga clic en **Rama actual: xxx**
3. Haga clic en **New Branch**
4. Se le pedirá en el símbolo que nombre su nueva rama. Los nombres descriptivos son mejores. Es una excelente manera de dar una idea rápida a las personas de qué se trata su trabajo. Por ejemplo, si está trabajando en las páginas de Novedades, podría nombrar la rama **Whats-new-updates**.

Cuando cree una nueva rama, no olvide agregar el ID del problema de Jira (DOC-1234) al nombre de la rama y al título del PR.

## Una nota sobre los permisos de GitHub [#permissions]

Los escritores del equipo de Docs trabajan en ramas, pero los colaboradores externos al equipo de Docs usan bifurcaciones. Esto también significa que los colaboradores que no pertenecen a Docs no pueden editar el contenido en una rama directamente, lo que puede dificultar la colaboración.

Los permisos de GitHub se utilizan para determinar quién puede trabajar en una rama y quién puede trabajar en una bifurcación. En GitHub, el acceso está determinado por los roles de equipo y de miembro. Aunque cualquiera puede contribuir a nuestro repositorio público, se otorga acceso adicional a través de los roles `Write` y `Admin`. (Hay otros roles definidos que no se usan a menudo).

A cada miembro del equipo de Docs se le otorga el rol `Admin`, que otorga acceso completo al respositorio. A otros colaboradores de New Relic se les otorga el rol `Write`, que permite asignar usuarios y abrir y cerrar pull request.

Para revisar la configuración de acceso actual, vaya al repositorio `docs-website`, luego vaya a **Settings &gt; Collaborators and teams** o **Team and member roles**.
