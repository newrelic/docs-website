Siempre que sea posible, incluya hipervínculos donde sea relevante dentro del propio texto. Evite crear listas de enlaces a documentos en la sección **Para obtener más ayuda**, ya que es más difícil para los futuros redactores determinar por qué son importantes.

<Callout variant="tip">
  Si enlaza al producto, consulte nuestra página de la guía de estilo sobre [rutas de la UI](/docs/style-guide/quick-reference/ui-paths).
</Callout>

## Sintaxis de enlaces [#link-syntax]

El sitio de documentación utiliza la sintaxis de enlaces en línea de Markdown:

```markdown
[link text](https://example.com)
```

Si está enlazando a otra página en el sitio de documentos, debe usar enlaces &quot;relativos&quot; (omitiendo la URL raíz `https://docs.newrelic.com` del sitio de documentos):

```markdown
[link text](/docs/category-path/doc-path/)
```

<Callout variant="tip">
  Markdown [también admite enlaces de estilo &quot;referencia&quot;](https://daringfireball.net/projects/markdown/syntax#link), donde la URL de destino se indica al final del documento. Aunque funcionarán y se mostrarán correctamente, evitamos usar este estilo de enlace por algunas razones:

  * Es un estilo menos común y puede resultar confuso para los colaboradores.
  * Nuestros documentos son muy largos, lo que puede hacer que conectar un enlace a su destino sea complicado para los colaboradores.
</Callout>

## Texto de vínculo [#hyperlinks-linktext]

Siga estas directrices al escribir texto para hipervínculos:

* **Etiquetas:** asegúrese de que cada vínculo en el documento tenga una etiqueta de texto única y significativa. No utilice la misma cadena de texto para etiquetar diferentes vínculos.
* **Ubicación:** incluya una etiqueta de texto clara y concisa para identificar a dónde va el enlace. Proporcione contexto adicional si está enlazando a un sitio externo. ¿Por qué está enviando a alguien allí?
* **Haga clic aquí:** no utilice &quot;haga clic aquí&quot; u otras etiquetas de enlace sin sentido.
* **&quot;Prueba de enlace:&quot;** lea solo los enlaces, sin el texto circundante. ¿Puede cada uno valerse por sí mismo como una descripción clara de a dónde va el enlace si eso es todo lo que el usuario mira en la página?
* **Evite los prefijos de URL:** si envía a los usuarios a una dirección en la que desea utilizar la URL como texto de vínculo, elimine los prefijos `https:` y `www.` del texto de vínculo. Por ejemplo, `[github.com](https://github.com)` no `[https://github.com/](https://github.com)`. O `[github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)` no `[https://github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)`.

Realice la prueba de vínculos para estos tres ejemplos. El último es el mejor para los lectores que buscan información sobre la configuración de PHP, porque el vínculo lo identifica claramente, sin tener que leer nada más en la página.

## Vínculos de soporte [#support-link]

**Nunca incluya un hipervínculo a la dirección de correo electrónico de soporte.** Esto evita el spam y garantiza que los clientes utilicen el formulario de envío de ticket para crear ticket, de modo que reciban la prioridad de soporte correcta. Si necesita indicar a los clientes que se comuniquen con soporte, utilice esto en su lugar:

```md
Get support at [support.newrelic.com](support.newrelic.com).
```

## Enlaces de anclaje [#hyperlinks-anchor]

Si su enlace incluye un ancla (por ejemplo, `#inivar-scope`), use la ruta de documento **actual** y completa que utiliza. Algunos navegadores no conservan las anclas con los redireccionamientos.

Al crear o editar un `id` HTML para un vínculo de anclaje, siga estas pautas:

* Solo use minúsculas al crear nuevos ID.
* Utilice guiones `-` para separar las palabras. No utilice `_` guiones bajos.
* Al reorganizar un documento, intente conservar los enlaces de anclaje entrantes siempre que sea posible. Tenga en cuenta que cuando elimine un encabezado de nivel dos `##`, se romperá cualquier enlace a ese encabezado.
* Evite cambiar un ID de anclaje existente, porque podríamos estar monitoreando el tráfico hacia él desde nuestra cuenta interna de New Relic.

## Enlaces profundos al producto [#deep-links]

Al dirigir a los usuarios a partes del producto, es conveniente usar enlaces profundos cuando sea posible. Los enlaces profundos animan a los usuarios a entrar en el producto y, si aún no han creado una cuenta, los invita a registrarse. Esto es más efectivo que simplemente enlazar a una página de registro. Sin embargo, los enlaces profundos en la UI solo funcionan a veces y se necesita algo de experimentación para encontrar un buen vínculo permanente.

Aquí hay un flujo de trabajo de ejemplo usando la UI de Logs:

1. Desde su cuenta de trabajo, vaya a la parte de la UI que desea enlazar. Copie la URL completa tal como aparece naturalmente.
2. Abra una ventana de incógnito y pegue la URL.
3. Edite la URL a un estado más limpio. Queremos URL simples cuando sea posible. Para los logs, esto se ve así: `https://one.newrelic.com/logger`.
4. New Relic le pedirá que inicie sesión, así que inicie sesión con un correo electrónico que no sea del trabajo.

La URL lo envía a la página de logs y autocompleta la información de identificación del ID de la cuenta. Esa página admite enlaces profundos.

Si la URL simple no funciona, tiene dos pasos adicionales. A continuación, se muestra un flujo de trabajo de ejemplo donde la URL simple no funciona. Usaremos esta URL como base:

```
https://one.newrelic.com/marketplace/install-data-source?account=[ACCOUNT_ID_HERE]&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
```

1. Después de encontrar su URL, abra una ventana de incógnito y pegue la URL simple: `https://one.newrelic.com/marketplace/install-data-source`Esta página no carga con la URL simplificada.

2. Pruebe esta URL eliminando la parte `account=[ACCOUNT_ID_HERE]` del slug. La nueva URL se verá así:

   ```
   https://one.newrelic.com/marketplace/install-data-source?&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
   ```

3. Pegue esa URL en una nueva ventana de incógnito. Lo llevará a la página correcta con su ID de cuenta único completado.

4. Confirme con otro escritor que esta URL funciona pidiéndole que abra la URL sin el número de ID de la cuenta. Deben usar un correo electrónico que no sea del trabajo.

Si la URL falla en cualquier caso, es probable que esa parte de la UI del producto no se pueda vincular en profundidad. En ese caso, vincule `one.newrelic.com` a la página **All capabilities**, luego describa la ruta según [nuestras pautas de rutas](/docs/style-guide/formatting/ui-paths).

## Vínculos externos [#hyperlinks-external]

Al crear enlaces a sitios web fuera del subdominio `docs.newrelic.com` (incluidos `newrelic.com`, `one.newrelic.com`, `discuss.newrelic.com`), el sitio de documentación incluye automáticamente código que abre el enlace en una nueva pestaña.

Además de las pautas de texto de vínculo en este documento, aquí hay algunas otras cosas a tener en cuenta al vincular a sitios externos:

* Piense en la mejor manera de preparar sus enlaces para el futuro. Si es posible, apunte a un dominio de nivel superior, pero no si esto reduce la utilidad del enlace. ¿Qué tan estable es el contenido al que enlaza? ¿Es probable que la URL cambie?
* Asegúrese de que su vínculo sea lo más útil posible. ¿Qué valor intenta agregar al documento? ¿Se puede compartir esa información de otra manera?
* Ayude al lector a entender por qué enlaza a esta fuente externa. ¿Es una referencia útil, como una lista de zonas horarias? ¿Es una forma de ahorrarle tiempo a alguien, como enlazar directamente a un archivo difícil de encontrar?
* Asegúrese de que su vínculo sea de acceso general. ¿Está vinculando a un sitio externo que requiere autenticación, como un repositorio privado de GitHub?
