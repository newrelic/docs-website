Para mantener la coherencia en el contenido de New Relic, estas son nuestras pautas generales de uso de palabras:

* Por lo general, seguimos la [Microsoft Style Guide](https://docs.microsoft.com/en-us/style-guide/welcome/), que se basa en el Chicago Manual of Style.
* Seguimos las convenciones del inglés estadounidense, en lugar de las del inglés británico.
* Nos remitimos a los nombres oficiales de los productos para las referencias a los productos. (Por ejemplo, para Amazon Web Services (AWS), consulte [aws.amazon.com/products](https://aws.amazon.com/products/)).
* Para la terminología específica de New Relic, utilizamos el [glosario del producto](/docs/using-new-relic/welcome-new-relic/getting-started/glossary).

<CollapserGroup>
  <Collapser id="account" title="cuenta">
    Cuando alguien se registra en New Relic, obtiene una organización de New Relic (representada por un ID de organización). Esa organización puede contener una o más cuentas (donde cada cuenta tiene un ID de cuenta). Para más información sobre la distinción entre `organization` y `account,`, consulte [organización y estructura de la cuenta](/docs/accounts/accounts-billing/account-structure/new-relic-account-structure).

    En el uso general, fuera de New Relic, `account` se usa a menudo en un sentido más amplio. Por ejemplo, podría usarse de la misma manera que usamos `organization,` o podría usarse para referirse al registro de usuario de alguien. Debemos intentar ser lo más precisos posible al usar estos términos. Esto es especialmente cierto cuando documentamos aspectos que se aplican solo a una cuenta de New Relic, y no a una organización de New Relic (por ejemplo, datos a nivel de cuenta y límites de consulta).

    Dicho esto, cuanto más general sea el uso, más aceptable será usar `account` como sinónimo de `organization`. Por ejemplo, New Relic a veces usa una frase como: &quot;Regístrese para obtener una cuenta de New Relic.&quot; Esta sustitución de `account` por `organization` está bien porque concuerda con la forma en que se usa comúnmente `account` y no hace referencia a algo específico de nuestra definición de `account`.
  </Collapser>

  <Collapser id="account-id" title="ID de cuenta">
    Un número único que [identifica una cuenta de New Relic en particular](/docs/accounts-partnerships/accounts/account-setup/account-id). No use `account number`.
  </Collapser>

  <Collapser id="agent" title="agente">
    Un agente de New Relic es un software instalable que se integra con múltiples tipos de tecnologías (por ejemplo, frameworks web, sistemas operativos y tipos de bases de datos) y reporta datos a New Relic, generalmente con una cadencia específica. Todos los agentes son integraciones, pero no todas las integraciones son agentes. Muchos de nuestros agentes admiten múltiples integraciones; por ejemplo, el agente de Java recopila datos de una variedad de frameworks y tecnologías de Java, o el agente de infraestructura habilita la integración de Cassandra en el host.

    Aquí hay una lista de lo que consideramos agentes de New Relic:

    * APM:

      * Agente de Go
      * Agente de Java
      * Agente .NET
      * Agente de Node.js
      * Agente PHP
      * Agente Python
      * Agente Ruby

    * Infraestructura:

      * Agente de infraestructura
      * Agente Linux
      * Agente de MacOS
      * Agente de Unix
      * Agente de Windows

    * Agente del navegador

    * Móvil:

      * agente de Android
      * agente de iOS
      * Agentes híbridos (Capacitor, Flutter, etc.)

    * Red:

      * agente ktranslate
      * Agente de flujo de red

    * Agente SNMP

      * Agente de Syslog

    * Roku

    * Elixir

      Para ver una lista de lo que consideramos integraciones, consulte la definición de [integración](#integration).
  </Collapser>

  <Collapser id="AIOps" title="AIOps">
    Abreviatura de inteligencia artificial para operaciones de TI.
  </Collapser>

  <Collapser id="ampm" title="am y pm">
    * Use el reloj de 12 horas seguido del período de tiempo (en minúsculas) am o pm.

    * No ponga un espacio después del último número en un timestamp (12:00am, no 12:00 am).

    * No incluya un 0 inicial cuando la hora sea menor que 10.

      ```
      9:30am, 12:30pm, 8:30pm
      ```
  </Collapser>

  <Collapser id="aws" title="Nombres de productos de Amazon Web Services (AWS)">
    * Generalmente se denomina en la conversación como `AWS`. Consulte `Amazon Web Services` en la primera instancia, luego puede usar `AWS` en adelante.
    * Amazon tiene varios productos como [Amazon EC2](https://aws.amazon.com/documentation-overview/ec2/) y [Amazon S3](https://aws.amazon.com/documentation-overview/s3/) a los que casi siempre se hace referencia por su nombre abreviado, en lugar de por el nombre completo. Puede abreviar en la primera instancia si Amazon lo hace.
    * Algunos productos de Amazon usan `Amazon` como prefijo (como en `Amazon EC2`), otros `AWS` (como en `AWS Amplify`). Siga el estilo del [sitio de documentación de AWS](https://aws.amazon.com/documentation).
    * Algunos nombres de productos de Amazon también se pueden usar de manera más informal para referirse a datos u opciones de configuración. Por ejemplo, para [AWS Metric Streams](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Metric-Streams.html), AWS formatea ese nombre con mayúscula inicial cuando hace referencia al producto, pero, cuando hace referencia a los datos producidos, se referirá a él de manera informal (por ejemplo, como `metric stream data` o `metric streams`). Por lo general, debemos hacer lo que hace AWS.
  </Collapser>

  <Collapser id="ampersand-details" title="ampersand (&)">
    No utilice símbolos &amp; en oraciones o encabezados, a menos que formen parte del nombre de una empresa o marca. Excepción: si el espacio es reducido (es decir, «y» no cabe), es aceptable usar un símbolo &amp;.
  </Collapser>

  <Collapser id="app-name" title="nombre de la aplicación vs. alias de la aplicación">
    El &quot;nombre de la máquina&quot; que usa el Collector para identificar de forma exclusiva una aplicación es su `app name`. El ajuste de configuración del lado del servidor que cambia el &quot;nombre&quot; visible de una aplicación sin cambiar su identificador único es su `app alias`.
  </Collapser>

  <Collapser id="Azure naming conventions" title="Convenciones de nomenclatura de Azure">
    Use las convenciones de nomenclatura de la plataforma de computación en la cloud de Microsoft Azure según lo prescrito por Microsoft; es lo que los clientes entienden y reconocen. Por ejemplo, el servicio Azure Native New Relic.
  </Collapser>

  <Collapser id="backend" title="backend">
    Ya sea que se use como adjetivo o sustantivo, esta es una sola palabra. Consulte también [`frontend`](#frontend).
  </Collapser>

  <Collapser id="black-white" title="lista negra y lista blanca">
    No use. En su lugar, use `deny list` y `allow list`; por ejemplo, &quot;agregue un nombre de host a su lista de denegación&quot;.
  </Collapser>

  <Collapser id="call-called" title="llamadas, llamando y llamado por">
    Al describir cómo una entidad se comunica o está conectada con otra, concéntrese en las llamadas y en qué dirección van. Evite usar `upstream` y `downstream` para describir estas interacciones. Por ejemplo, `service A calls service B`, `called services`, `calling services`.
  </Collapser>

  <Collapser id="caps" title="uso de mayúsculas">
    Esto es más complejo de lo que se puede cubrir en este diccionario de uso. Para obtener información detallada, consulte:

    * [Uso de mayúsculas en los encabezados](/docs/style-guide/capitalization/capitalization#heading_caps)
    * [Uso de mayúsculas en características y elementos de la UI](/docs/style-guide/capitalization/product-capability-feature-usage)
  </Collapser>

  <Collapser id="child-account" title="cuenta infantil">
    Una [cuenta principal](#parent-account) contiene una o más cuentas secundarias. Las cuentas secundarias se denominaban anteriormente &quot;subcuentas&quot;.
  </Collapser>

  <Collapser id="click" title="hacer clic">
    En general, use `click` en lugar del más vago `select`. Por ejemplo, puede hacer clic en algo en la UI, pero luego seleccionar algo de una lista.

    Tenga especial cuidado al usar `click` para describir acciones que solo tienen sentido con un mouse; por ejemplo, con un `right click` o un `click and drag`. También use `click` cuando el usuario deba hacer clic en un objeto no seleccionable (`to save your changes, click anywhere outside the dialog box`). Consulte también [pasar el mouse](#mouse-over).
  </Collapser>

  <Collapser id="collector" title="recolector vs. conectarse a New Relic">
    Al referirse a un agente que se comunica con los servidores de New Relic, descríbalo como el [recolector de New Relic](/docs/accounts-partnerships/education/getting-started-new-relic/glossary#collector). Aunque internamente el `collector` se refiere solo a partes específicas de nuestra arquitectura, lo usamos de manera más amplia en nuestra documentación para referirnos a &quot;cualquier extremo al que los clientes deban conectarse para reportar datos, para cualquier producto&quot;. Evite &quot;conectar a New Relic&quot; y no use &quot;conectar a la UI de New Relic&quot;.
  </Collapser>

  <Collapser id="contractions" title="contracciones">
    Cuando tenga sentido para la claridad, la concisión y el tono y la voz, use contracciones. Úselas donde hagan que la escritura suene más como un habla natural y donde mejoren la claridad y la accesibilidad sin sacrificar la experiencia y la autoridad.

    No existen reglas estrictas sobre qué contracciones son o no aceptables, pero lo simple y común es preferible a lo complicado y raro. Por ejemplo, `it's` para `it is` está bien, pero es mejor evitar construcciones menos comunes como `mustn't` o `wouldn't've`.

    También:

    * Al usar una contracción negativa (`don't`, `can't`, `won't`) intente proporcionar información adicional sobre qué hacer y qué se puede hacer. (Consulte la [introducción a la guía de estilo](/docs/new-relic-only/basic-style-guide/writing-guidelines/introduction-style-guide#tone) para obtener más información al respecto).
    * Hay lugares en nuestra documentación —por ejemplo, en notas y advertencias— donde escribir `do not`, `cannot` o `will not` es preferible a las contracciones para enfatizar la acción o el bloqueo que se debe evitar.
  </Collapser>

  <Collapser id="customer-vs-user" title="cliente frente a usuario">
    Cuando sea posible, use la segunda persona `you` para formar un sentido de conexión con el lector. Para los momentos en que necesite un sustantivo descriptivo en tercera persona, tenga en cuenta las siguientes pautas:

    * `customer` y `user` son adecuados según el contexto.
    * `customer` tiene más sentido cuando se habla de facturación, o de un grupo de personas o una entidad comercial. Por ejemplo, un cliente puede tener uno o más usuarios individuales que interactúan con New Relic a través de las cuentas del cliente.
    * `user` tiene más sentido como un término general para un usuario individual, o cuando se habla de usuario como un objeto en el modelo de cuenta. Por ejemplo, al discutir los modelos de cuenta, es importante ser específico sobre lo que constituye la identidad de una sola persona en nuestro sistema.
  </Collapser>

  <Collapser id="cyber words" title="palabras cibernéticas">
    No separe ni divida con guiones las palabras que comienzan con `cyber`, como `cyberattack`, `cybersecurity`, `cyberspace` y `cyberthreat`.
  </Collapser>

  <Collapser id="dashboard" title="dashboard">
    Desde el punto de vista general de la industria, `dashboard` generalmente se refiere a uno o más gráficos u otros widgets en una pantalla. Puede ver esta definición general en la [entrada de Wikipedia para dashboard](https://en.wikipedia.org/wiki/Dashboard_\(business\)).

    En New Relic, utilizamos el término `dashboard` de un par de maneras diferentes:

    * Dashboards se refiere a una característica de New Relic llamada `New Relic dashboards`, como se ve en [su página de característica](https://newrelic.com/platform/dashboards). En este contexto, `New Relic dashboards` se refiere a la capacidad de crear y usar vistas personalizadas que no están integradas en nuestras experiencias de plataforma principales (por ejemplo, la UI para APM, monitoreo de browser, OpenTelemetry y otros). Estos dashboard personalizados se encuentran en la página de la UI de **Dashboards**.
    * Los Dashboards también pueden referirse a dashboards seleccionados. Estos dashboards son vistas predeterminadas que los clientes obtienen cuando usan nuestras soluciones de plataforma principales (por ejemplo, las experiencias de UI para APM, infraestructura y monitoreo de browser).

    Nuestros dashboards personalizados incluyen los dashboards que se encuentran en las [aplicaciones de New Relic](https://opensource.newrelic.com/nerdpacks/) y en los inicios rápidos de nuestra [página de Instant Observability](https://newrelic.com/instant-observability). Por ejemplo, si observa [el inicio rápido de .NET](https://newrelic.com/instant-observability/dotnet), verá que viene con un dashboard adicional que no forma parte de nuestra experiencia seleccionada.

    Si cree que hay ambigüedad al usar el término general &apos;dashboard&apos;, le recomendamos el siguiente uso:

    * Para referirse a experiencias personalizadas que se encuentran en nerdpacks, quickstarts o dashboards creados por un cliente o su equipo, use `custom dashboards`, o `customizable dashboards`, o `quickstart dashboards`.
    * Para referirse a nuestras vistas más seleccionadas, use `curated views`, `curated dashboards`, `New Relic-built dashboards`, `APM dashboards`, `APM views` (para dar algunas ideas).

    Realmente, recomendamos ser lo más específicos posible para establecer el contexto. Si un texto ha establecido ese contexto una vez, entonces siéntase libre de usar el `dashboard` general.
  </Collapser>

  <Collapser id="data-center" title="centro de datos">
    Dos palabras (`data center`), no una (`datacenter`), lo que se desvía de la [guía de Microsoft de una palabra](https://learn.microsoft.com/en-us/style-guide/a-z-word-list-term-collections/d/datacenter). Hacemos esto para mantener la coherencia con nuestros contratos.
  </Collapser>

  <Collapser id="data-sheet" title="hoja de datos">
    Al referirse a una hoja de datos, sepárela en dos palabras para que se lea `data sheet` y no `datasheet`.
  </Collapser>

  <Collapser id="DevOps" title="DevOps">
    Abreviatura de desarrolladores de software y operaciones.
  </Collapser>

  <Collapser id="document" title="doc, documento, documentación, sitio de documentación">
    Si necesita referirse a los documentos en sí —no lo haga. Por lo general, es mejor vincular directamente al documento al que hace referencia y usar el título del documento como su texto de vínculo. Por ejemplo, `See [Install the .NET agent](URL)` en lugar de `See our [.NET agent install docs](URL)`.

    Si no hay una buena alternativa, `doc` generalmente suena más natural que `document` o `documentation`. Si tiene la tentación de usar una forma más larga, intente leerla en voz alta para ver cuál se lee mejor.

    Si debe referirse al sitio en su conjunto, llámelo `docs site` en lugar de `Docs site` o `documentation site`. Internamente, también puede referirse a toda la URL `docs.newrelic.com` para evitar ambigüedades con otras fuentes de documentación, como la documentación de la plataforma interna o la documentación del explorador de API. Para referirse a [nuestro repositorio de GitHub de documentación](https://github.com/newrelic/docs-website), use el nombre del repositorio `docs-website` o la ruta del repositorio `newrelic/docs-website`.
  </Collapser>

  <Collapser id="downstream-upstream" title="descendente y ascendente">
    No lo use para describir cómo se relacionan las entidades entre sí. La forma en que las personas interpretan downstream y upstream varía significativamente, así que concéntrese en el tipo específico de conexión como lo hacemos en el elemento de entidades relacionadas: llama, crea, aloja, mantiene, etc.

    Por ejemplo:

    * `[Service A] calls [service B]`
    * `Called services`
    * `Calling services`
    * `maintained by [repository name]`
  </Collapser>

  <Collapser id="dropdown" title="desplegable">
    Emplee `dropdown` en lugar de `drop-down` o `drop down`.

    Aunque no es de uso común, puede usar `dropdown` de forma independiente como sustantivo, sin necesidad de decir `dropdown menu` o `dropdown list`. Por ejemplo, `select a date from the **Date** dropdown`.
  </Collapser>

  <Collapser id="eg" title="p. ej. e i. e.">
    Evite estas abreviaturas latinas.

    En lugar de `e.g.`, utilice `for example` o `such as`. Sustituir `i.e.` es más complicado, porque a veces las personas lo usan para referirse a `that is`, mientras que otras veces se usa incorrectamente para referirse a `for example`. Lea el contexto para que quede claro, pero por lo general la mejor solución es reescribir para que la descripción sea clara sin necesidad de texto explicativo.
  </Collapser>

  <Collapser id="ellipses" title="puntos suspensivos">
    En el material citado, use puntos suspensivos para indicar el texto omitido. Trate los puntos suspensivos como un carácter único sin espacio entre los tres puntos. Por ejemplo, estilice los puntos suspensivos como (...) pero no (. . .) Cuando aparecen puntos suspensivos entre dos oraciones completas, use puntuación terminal al final de la primera oración, luego siga con puntos suspensivos. Por ejemplo:

    “La seguridad es importante para nosotros en New Relic. ... Nos exigimos altos estándares, manteniendo varias certificaciones, incluidas ISO 27001 y FedRAMP”.

    Tenga en cuenta que un espacio precede y sigue a los puntos suspensivos.
  </Collapser>

  <Collapser
    id="em-dash"
    title={<>raya (<InlineCode>
      —
    </InlineCode>)</>
    }
  >
    Lamentablemente, las rayas rara vez son necesarias en los documentos técnicos. Por lo general, puede lograr lo que necesita dividiendo la idea en varias oraciones o usando paréntesis. Sin embargo, en algunos casos raros, una raya puede agregar drama y un toque especial.

    Si cree que ha encontrado un caso así, asegúrese de usarlos correctamente. Una raya siempre debe usar el carácter de raya real (no un guion), y sin espacio antes ni después. Por ejemplo:

    ```
    You can sign up for New Relic fast and free—we won't even ask for a credit card number.
    ```

    Puede insertar una raya con el atajo `COMMAND+OPTION+-` o [usar la entidad HTML](https://www.w3.org/wiki/Common_HTML_entities_used_for_typography).
  </Collapser>

  <Collapser id="etc" title="etc.">
    A diferencia de las abreviaturas latinas [`e.g.`](#eg) o [`i.e.`](#ie), puede usar etc. Debe tener un punto al final (`etc.`). Sin embargo, asegúrese de tener varios ejemplos significativos antes de usarlo. Por ejemplo, `cities including Portland, Seattle, Dublin, etc.` pero no `cities including Portland, etc.`.
  </Collapser>

  <Collapser id="event" title="evento">
    Para comprender cómo escribir de manera óptima sobre los eventos, recomendamos leer:

    * La [sección de eventos en el documento de tipos de datos](/docs/data-apis/understand-data/new-relic-data-types/#event-data)

    * [La entrada del glosario para &quot;evento&quot;](/docs/glossary/glossary/#event)

      Algunas consideraciones relacionadas con el lenguaje al escribir sobre eventos:

    * Es importante comprender parte de la ambigüedad y la historia en torno a cómo a veces usamos la palabra &quot;evento&quot;. Antes del lanzamiento de nuestros otros tres tipos de datos principales de `Metric`, `Log` y `Span`, en New Relic nos referíamos a todos los objetos almacenados en NRDB como &quot;eventos&quot;. Por esta razón, internamente y a veces externamente, todavía a veces nos referimos a todos los objetos de NRDB como &quot;eventos&quot;. (Por ejemplo, en [la UI de consulta](/docs/query-your-data/nrql-new-relic-query-language/get-started/rate-limits-nrql-queries/#inspected-count-limits), todavía usamos &quot;eventos inspeccionados&quot; y esto se refiere a todos los tipos de datos de NRDB). Pero para los recursos orientados al público, debemos intentar usar &quot;evento&quot; para referirnos a los datos almacenados en NRDB **que no son** tipos de datos `Metric`, `Log` o `Span`.

    * Es importante comprender cómo el concepto de &quot;evento&quot; puede superponerse con el concepto de &quot;métrica&quot;. Ambos son términos generales amplios y, debido a eso, puede haber cierta superposición en el significado. Debido a que las métricas son solo medidas, se puede decir que todos los datos de New Relic (eventos, spans, logs) son o contienen métricas. Por ejemplo, los eventos informados por nuestro monitoreo de infraestructura contienen varias métricas, que son simplemente medidas numéricas de varios tipos ([lea más sobre los eventos de infraestructura que contienen métricas](/docs/data-apis/understand-data/new-relic-data-types/#metric-event-attributes)).
  </Collapser>

  <Collapser id="e words" title="Palabras con e, como email o ecommerce">
    Las palabras con E son palabras que usan `e` como abreviatura de electrónico, como ebook, ecommerce, email o esports. Trate las palabras con el prefijo e como sustantivos comunes que siguen el uso de mayúsculas y minúsculas de la oración. No separe con guiones las palabras con el prefijo e.
  </Collapser>

  <Collapser id="frontend" title="frontend">
    Ya sea que se use como adjetivo o sustantivo, esta es una sola palabra. Consulte también [`backend`](#backend).
  </Collapser>

  <Collapser id="generative AI" title="IA generativa">
    Escriba completo: IA generativa. Cuando el espacio no lo permite, GenAI es aceptable. La IA generativa es una aplicación de aprendizaje automático que puede crear una variedad de contenido, incluyendo texto, imágenes o audio a partir de símbolos de lenguaje natural.
  </Collapser>

  <Collapser id="home page" title="página de inicio">
    Dos palabras, no una.
