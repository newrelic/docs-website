Nuestro componente de instalación ramificada para el sitio de documentación permite a nuestros usuarios seleccionar una o más opciones, lo que luego muestra el contenido en función de esas elecciones.

## Descripción general del proceso de creación [#overview]

Antes de comenzar a trabajar con el componente de instalación de la rama, algunas cosas a considerar:

* Asegúrese de que definitivamente desea usar la instalación ramificada. Considere si su problema se puede resolver con otra solución (por ejemplo, el [componente de pestañas](/docs/style-guide/structure/intro-to-components)).
* Explore [los documentos de instalación ramificados que hemos creado](#uses) y vea lo que es posible. Seleccione uno que desee clonar para usarlo como plantilla.
* Finalice el flujo lógico de cuáles serán sus opciones y qué contenido se mostrará. Lo ideal es que sus planes de contenido estén casi terminados antes de crear una rama. Por esta razón, puede dividir el trabajo en dos o más Jiras.

Puede crear el componente de instalación ramificado de muchas maneras, y puede llevarle una buena cantidad de esfuerzo hacer que funcione, especialmente cuanto más compleja sea su estructura. Pero, dicho esto, a continuación se presenta una visión general de cómo suele ser un proceso de creación:

1. Revise los documentos de instalación ramificados, especialmente nuestros [archivos YAML de ejemplo](#yaml-examples). Conozca la estructura y la lógica de este componente.
2. Cuando esté listo para comenzar, copie el archivo YAML y las carpetas asociadas de un componente de instalación que desee emular y úselos como base para su proyecto.
3. Cambie el nombre de la carpeta de nivel superior para que coincida con su proyecto y cambie el `agentName` en el archivo YAML para que coincida. El `agentName` es lo que le indica al archivo YAML de qué carpeta extraer su contenido. (Consulte [nuestros archivos YAML de ejemplo](#yaml-examples)).
4. Para asegurarse de que las cosas funcionen, realice una compilación local.
5. Comience a agregar sus .mdx archivos y a editar el archivo yaml. Dependiendo de qué tan bien coincidan sus planes con la lógica existente, puede ser más fácil eliminar la mayor parte del contenido del archivo YAML y agregarlo poco a poco.
6. A medida que trabaje, compile con frecuencia para comprobar si todo funciona. Hacer pequeñas partes de trabajo y luego comprobar si se compila le ayudará a evitar perder tiempo en la resolución de problemas. Use el [script de verificación de YAML](/docs/style-guide/writing-docs/article-templates/branch-install-doc-reference#verify-yaml) para comprobar si hay errores.

Si se atasca, pida ayuda a alguien que haya creado uno de estos.

## Puntos de decisión importantes [#decision-points]

Hay algunos enfoques diferentes que puede adoptar con la instalación ramificada. A continuación se muestran algunos puntos de decisión importantes:

<CollapserGroup>
  <Collapser id="default-content-decision" title="¿Debo mostrar contenido antes de seleccionar una opción?">
    Esta decisión trata sobre: ¿qué ven los clientes cuando llegan por primera vez al documento? ¿Tiene sentido mostrarles algunas instrucciones incluso antes de que hayan seleccionado una opción? Si hay un único camino que tomará la mayoría de los clientes, puede tener sentido mostrarles algún contenido que luego se ajustará y cambiará dependiendo de sus selecciones de opciones. Detalles sobre esto:

    * El enfoque de &quot;contenido predeterminado&quot; se basa en el uso de los componentes `override` y `skip`. Muestra un archivo y luego dice: omita o anule este archivo cuando se elijan x opciones. (Documento de instalación que usa esto: [la instalación de Java](/install/java)).
    * Si no desea mostrar ningún contenido antes de que se seleccionen las opciones, usaría el enfoque `isCondition=true`. Ese componente dice simplemente: &quot;mostrar este archivo si se seleccionan estas opciones&quot;. (Documento de instalación que usa esto: [la instalación de .NET](/install/dotnet)).
  </Collapser>

  <Collapser id="display-all-options-decision" title="¿Debo mostrar todas las opciones? ¿O anidarlas?">
    Esta decisión trata sobre si desea mostrar inicialmente todas las opciones, o si prefiere anidarlas (por ejemplo, elegir una opción da como resultado otro cuadro de selección de opciones).

    Si su lógica de selección de opciones es bastante simple, puede tener sentido simplemente mostrar todas las opciones a los clientes a la vez. Sin embargo, si su lógica de selección de opciones es algo compleja (por ejemplo, tres o más selecciones, y algunas selecciones que afectan a selecciones posteriores), puede tener sentido anidarlas.

    Para ver un ejemplo de un conjunto de cuadros de selección de opciones completamente expuesto, consulte el \[documento de requisitos previos de seguridad de la red]. Para ver un ejemplo de un conjunto anidado de cuadros de selección, consulte \[la instalación de .NET].
  </Collapser>

  <Collapser id="guided-install-decision" title="¿Necesito la instalación guiada?">
    Este punto de decisión trata sobre si necesitará mostrar información sobre nuestra ruta de instalación guiada. Para algunos agentes, queremos mostrar algo de contenido sobre la ruta de instalación guiada (por ejemplo, puede ver el contenido de la instalación guiada en la [instalación del agente de Java](/install/java) si selecciona &quot;app server&quot; y &quot;Jetty&quot;).

    Tenemos un par de opciones para agregar el contenido de la instalación guiada:

    * Tenemos un componente `recommendedGuided: true` que puede colocar en opciones específicas donde desea que aparezca el contenido de la instalación guiada. Lo que esto hace esencialmente es mostrar el contenido del .mdx archivo que contiene ese cuadro de selección de opciones. Puede ver un ejemplo de esto en la instalación de Java, donde el contenido de la instalación guiada se encuentra en el archivo `appInfo-2`. Esta implementación no es realmente específica del contenido de la instalación guiada: podría usar esta lógica para mostrar cualquier contenido arbitrario que desee usar.
    * Como alternativa, simplemente podría agregar la instalación guiada como un archivo .mdx normal y mostrarlo como lo haría con cualquier otro archivo. La instalación de .NET adopta este enfoque. Con este enfoque, aparecerá como un paso numerado al igual que otros archivos.
  </Collapser>

  <Collapser id="config-file-decision" title="¿Necesito un archivo de configuración?">
    Algunos agentes hacen uso de un componente de archivo de configuración que permite a nuestros usuarios ingresar valores específicos del usuario directamente desde el documento de instalación. Para ver un ejemplo de esto, consulte [el documento de instalación de Java](/install/java).

    El uso de este archivo no es necesario. El uso de esto dependerá de su flujo de trabajo de instalación específico. (Por ejemplo, el documento de instalación de .NET no usa esto).
  </Collapser>
</CollapserGroup>

## Nuestra instalación ramificada utiliza [#uses]

Aquí están nuestras implementaciones de la instalación ramificada con resúmenes de las elecciones hechas para ellas. Recomendamos elegir uno que coincida con el enfoque que desea adoptar y ajustarlo según sea necesario. Intente mantener esta lista actualizada a medida que agregamos nuevos usos.

* Gestión de vulnerabilidades: [importar datos de dependabot](/install/vm/). [Vea una imagen etiquetada de este archivo YAML](#simple-yaml-example). Detalles:

  * Una implementación muy sencilla. Un cuadro de selección de una sola opción, que permite elegir entre dos archivos.
  * No hay contenido mostrado de forma predeterminada.
  * Tenga en cuenta que esto es tan simple que el componente de pestaña podría haber sido una mejor opción.

* [Instalación de la integración de MySQL](/install/mysql). Detalles:

  * Una implementación simple con solo un cuadro de selección de opciones.
  * Adopta un enfoque de contenido mostrado por defecto.

* [instalación de Java](/install/java). Detalles:

  * Adopta un [enfoque de contenido predeterminado](#default-content-decision). Esto se debe a que hay una ruta de instalación que toman la mayoría de los clientes.
  * Solo tiene dos secciones de selección de opciones: dependiendo de lo que se seleccione en la primera opción, se muestra un segundo cuadro de opciones.
  * Utiliza el componente `recommendedGuided` para mostrar la instalación guiada (contenida en el archivo `appInfo-2`).
  * Usa el componente de archivo de configuración.

* [Instalación de .NET](/install/dotnet). [Consulte una imagen etiquetada de este archivo YAML](#complex-yaml-example). Detalles:

  * Esto no muestra ningún contenido predeterminado. Se basa completamente en el enfoque [`isConditionalStep: true`](#default-content-decision). Esto se debe a que hay bastantes rutas y no hay una sola ruta que tome la mayoría de los clientes (aunque teóricamente podríamos haber elegido una).
  * Esto tiene solo dos secciones de selección de opciones: dependiendo de lo que se seleccione en la primera opción, se muestra un segundo cuadro de opciones.
  * Usa el componente `recommendedGuided` (contenido en el archivo `appInfo-2`).
  * No utiliza el componente del archivo de configuración: esto se debe a que la mayoría de los clientes editan la configuración a través de variables de entorno u otras opciones y no mediante el uso directo del archivo.

* [Instalación de Python](/install/python). Detalles:

  * No muestra contenido predeterminado. Se basa completamente en el [enfoque de`isConditionalStep: true` ](#default-content-decision). Esto se debe a que no hay una ruta principal única.
  * Esto tiene varios cuadros de selección de opciones: hasta cuatro, dependiendo de lo que se seleccione.
  * No utiliza el componente de archivo de configuración.
  * Hace uso de comentarios, lo que ayuda a comprender el código y mejora el mantenimiento.

* [extremos de monitoreo de red](/install/npm). Detalles:
  * Una implementación bastante sencilla. Tres cuadros de selección de opciones que controlan cuál de varias tablas se muestra. Un archivo que se muestra de forma predeterminada con anulaciones de reemplazo que determinan qué tabla mostrar.
