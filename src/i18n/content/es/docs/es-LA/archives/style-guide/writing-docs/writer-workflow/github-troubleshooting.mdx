¿Tiene problemas para [trabajar en un documento en GitHub](/docs/style-guide/writer-workflow/tech-writer-workflow/)? Consulte los siguientes problemas comunes.

## La compilación local arroja un error 404 [#build-fails]

### Problema

Cuando intenta compilar su localhost:8000, una o todas las páginas web arrojan un error 404.

### Soluciones

Pruebe algunas de estas soluciones para averiguar qué salió mal en su compilación local.

<CollapserGroup>
  <Collapser className="freq-link" id="troubleshoot-file" title="Solucionar problemas del archivo problemático">
    Si sabe qué archivo está causando un error, ejecute este comando para identificar el error:

    ```bash
    yarn verify-mdx path/to/file.mdx
    ```

    Este comando devuelve más información sobre el error que la salida normal de Gatsby, como el carácter específico y el número de línea que causan el error.

    <CollapserGroup>
      <Collapser className="freq-link" id="example" title="Ejemplo">
        Supongamos que he realizado cambios en varios documentos de mi rama. Cuando intento ejecutar el sitio localmente o acceder a la compilación de Netlify, obtengo el siguiente error:

        ```
        Unexpected character = (U+003D) before name, expected a character that can start a name, such as a letter, $, or _/usr/src/app/www/src/content/docs/new-relic-solutions/observability-maturity/uptime-performance-reliability/aqm-implementation-guide.mdx: Unexpected character = (U+003D) before name, expected a character that can start a name, such as a letter, $, or _
        ```

Aparte de eso, todo lo que sé es que hay un carácter `=` arruinando las cosas en alguna parte. Genial, pero este es un documento de NRQL, hay docenas de caracteres `=`.

  <Collapser className="freq-link" id="" title="Busque errores de sintaxis comunes">
    Revise los archivos modificados en busca de algunos de estos errores comunes de sintaxis de markdown:

    * Sangría inconsistente de los archivos de navegación

    * Sintaxis incorrecta del front matter
      * Si hay apóstrofos y dos puntos en los campos de frontmatter, enciérrelos entre comillas para evitar problemas.

    * Faltan corchetes o etiquetas de cierre

    * Enlaces de imágenes con formato incorrecto

      * Asegúrese de que haya una nueva línea entre cada declaración de importación de imágenes.
      * Tenga cuidado al cambiar el nombre de las imágenes y las rutas de sus nombres de archivo. Una discrepancia puede hacer que falle toda la compilación local.
      * Tenga especial cuidado al tratar con archivos de imagen que se importan.

    * Nombres de archivo de imagen incorrectos

      * Los nombres de archivo de las imágenes distinguen entre mayúsculas y minúsculas. El uso incorrecto de mayúsculas da como resultado una imagen faltante en el documento.
      * Las imágenes con valores codificados (como %) en el nombre del archivo pueden ser especialmente complicadas, así que intente evitarlas.
  </Collapser>

  <Collapser className="freq-link" id="restart-yarn" title="Detenga y reinicie yarn">
    Para detener y reiniciar yarn:

    1. En la terminal, asegúrese de estar en el directorio `/docs-website`.
    2. Presione CONTROL + C para interrumpir el proceso de yarn (si hay una terminal activa).
    3. Ejecute este comando para detener todos los servicios que se ejecutan en localhost:8000:
       ```bash
       kill -9 $(lsof -i TCP:8000 | grep LISTEN | awk '{print $2}')
       ```
    4. Ejecute este comando para reiniciar yarn:
       ```bash
       yarn clean && yarn && yarn start 
       ```
  </Collapser>

  <Collapser className="freq-link" id="check-branch" title="Identificar la rama problemática">
    Para identificar qué rama está causando problemas:

    1. En la terminal, asegúrese de estar en el directorio `docs-website`.
    2. Presione CONTROL+C para interrumpir el proceso de yarn, si es necesario.
    3. En GitHub Desktop, confirme cualquier cambio necesario en su rama y luego cambie a la rama develop.
    4. De vuelta en la terminal, ejecute `yarn && yarn start`.

    Si el sitio ahora se compila correctamente desde la rama de desarrollo, el problema está en los cambios de su rama. Detenga Yarn nuevamente, regrese a su rama y solucione el problema.
  </Collapser>

  <Collapser className="freq-link" id="clean-cache" title="Limpie su caché local">
    Ejecute `yarn clean` para borrar su caché local. Esto hará que su próxima compilación sea más lenta, ¡así que asegúrese de tener tiempo!

    1. En la terminal, asegúrese de estar en el directorio docs-website.
    2. Presione CONTROL+C para detener yarn, si es necesario.
    3. Inicie una nueva compilación ejecutando `yarn clean && yarn && yarn start`.
  </Collapser>

  <Collapser className="freq-link" id="remove-cache" title="Eliminar archivos de caché dañados">
    Puede haber ocasiones en las que su .cache directorio se haya dañado. Este directorio es ignorado por Git, lo que significa que viaja con usted de rama en rama. Este podría ser el problema si sus compilaciones locales fallan independientemente de la rama en la que se encuentre.

    Para resolver esto desde su directorio `/docs-website`, ejecute `rm -rf .cache`.
  </Collapser>

  <Collapser className="freq-link" id="start-build" title="Inicie una compilación desde cero">
    Comenzar una compilación desde cero eliminará todos sus módulos de Node, la carpeta .cache oculta y la caché local. Esto tarda mucho tiempo en ejecutarse, alrededor de 10-20 minutos.

    1. En la terminal, asegúrese de estar en el directorio docs-website.

    2. Presione CONTROL+C para detener yarn, si es necesario.

    3. Ejecute `yarn reboot` (o use el comando de Keyboard Maestro `kknuke`\*).

       \*Si usa el comando de Keyboard Maestro `kknuke`, cuando todo se complete, inicie el sitio ejecutando `yarn start`.
  </Collapser>

  <Collapser className="freq-link" id="run-incognito" title="Ejecute su compilación local en modo privado">
    A veces el sitio local se compila, pero las páginas dentro del sitio no. Para solucionar este problema, intente ejecutar la compilación local en una sesión privada o de incógnito. También puede intentar borrar la caché de su navegador.
  </Collapser>
</CollapserGroup>

## Fallan las comprobaciones de compilación requeridas [#check-fail]

### Problema

Cuando crea un PR, una de las comprobaciones de `required` no se aprueba.

<Callout variant="tip" title="Nota">
  Si falla una comprobación opcional, está bien fusionar el PR, ya que las comprobaciones opcionales no bloquean las versiones. Sin embargo, si desea investigar más a fondo la comprobación, puede enviar un mensaje al canal de ayuda para que el héroe pueda analizar el fallo.
</Callout>

### Solución

Si una comprobación falla, primero intente cerrar y volver a abrir su PR.

Luego, vuelva a ejecutar las comprobaciones:

1. Vaya al PR.
2. Haga clic en **Details &gt; Re-run jobs**.

Si esto no funciona, deberá restablecer las comprobaciones, lo que forzará una reconstrucción de la caché:

1. En su repositorio local, busque el archivo `gatsby-config.js` (o use CMD-P para saltar a él rápidamente en VSCode).

2. Intercambie la primera y la segunda línea de código (no importa en qué orden estén estas líneas, excepto para hacer que la comprobación de Gatsby Build reconstruya la caché):

   ```js
   const fs = require('fs');
   const parse = require('rehype-parse');
   ```

3. Guarde el archivo y confirme el cambio en su PR.

4. Vuelva a ejecutar las comprobaciones de compilación.

5. Espere MUUUUCHO tiempo.

## Conflictos de fusión de PR [#merge-conflict]

### Problema

Cuando intenta fusionar un PR desde su rama local, obtiene un conflicto de fusión.

### Solución

Si obtiene un conflicto de fusión, haga clic en **Resolve conflict** ya sea en Github Desktop o en el navegador y revise los conflictos línea por línea. Asegúrese de que su aprobador revise su PR después de solucionar el conflicto de fusión.

#### Evitar conflictos de fusión

A continuación se presentan algunas recomendaciones para evitar conflictos de fusión:

* Antes de fusionar con develop o main, haga clic en **Fetch origin** para asegurarse de obtener la versión más actualizada de develop o main.
* Si está trabajando en cambios de taxonomía, solucione su conflicto de fusión lo antes posible. Si su rama permanece por un tiempo, puede desactualizarse de develop bastante rápido y eso puede causar algunos problemas inesperados.
* Si obtiene un conflicto de fusión de las publicaciones de novedades, es porque el archivo `whats-new-ids.json` (que se actualiza automáticamente cuando se compila el sitio) puede desactualizarse bastante rápido. <Callout variant="caution">Nunca fusione un PR que cambie `whats-new-ids.json`. Si ve que aparecen cambios en el archivo `whats-new-ids.json` en GitHub Desktop, asegúrese de descartarlos en lugar de enviarlos a su rama. Esto hará que sea menos probable que otras personas tengan que lidiar con conflictos de fusión relacionados con este archivo.</Callout>

## El puerto 8000 no está disponible [#local-site]

### Problema

Cuando intenta ejecutar `yarn start`, el terminal responde:

```bash
[output] Something is already
[output] running at port 8000. Would you like to run the app at another port instead?
```

### Solución

Para detener todos los servicios que se ejecutan en localhost:8000, ejecute este comando en su terminal:

```bash
kill -9 $(lsof -i TCP:8000 | grep LISTEN | awk '{print $2}')
```

## El enlace de redireccionamiento arroja un error 404 [#redirect-404]

### Problema

Cuando hace clic en un enlace de redirección en su compilación local, obtiene un error 404.

### Solución

Las redirecciones tardan mucho tiempo en cargarse en una compilación local. Cuando haga clic en una redirección, espere hasta que arroje un error 404 y luego espere -1-2 minutos. Debería redirigirlo después de un tiempo. Si no lo hace, verifique la sintaxis de markdown para asegurarse de que configuró la redirección correctamente.

También puede probar las redirecciones en la compilación de Gatsby.

## La autenticación SSH falla [#authentication-fail]

### Problema

Cuando intenta enviar confirmaciones a su rama remota, obtiene un error de autenticación SSH.

### Solución

A veces, iniciar o cerrar sesión en Github Desktop puede solucionar un problema de autenticación:

1. En la barra de menú superior, vaya a **Preferencias**.
2. Cierre sesión y vuelva a iniciarla.

Si esto no funciona, intente hacer push de los commits a su rama remota. Si aún falla, intente hacer push de su PR manualmente usando la terminal. Por ejemplo, para hacer push del PR `second-kafka-pr-for-issue-11231`, ejecute este comando:

```bash
git push --set-upstream origin second-kafka-pr-for-issue-1123
```

Si tiene un problema de SSH, la terminal devolverá un mensaje de error de autenticación. Si la respuesta a este comando le solicita una frase de contraseña, su SSH se confundió de alguna manera. Al ingresar su frase de contraseña, debería volver a la normalidad. Si no puede recordar su frase de contraseña, [consulte este artículo](https://docs.github.com/en/github/authenticating-to-github/troubleshooting-ssh/recovering-your-ssh-key-passphrase).
