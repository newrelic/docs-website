El monitoreo sintético ejecuta comprobaciones automatizadas y programadas en las aplicaciones y extremos desde las ubicaciones que elija —ubicaciones públicas que New Relic opera en todo el mundo o [ubicaciones privadas](/docs/synthetics/synthetic-monitoring/guides/private-location-capabilities/) dentro de su propia red. Cada monitor realiza una solicitud real o un recorrido del usuario en un intervalo fijo y reporta el resultado, para que pueda detectar fallas, ralentizaciones y flujos interrumpidos lo antes posible.

Debido a que esas comprobaciones siempre se están ejecutando, proporcionan disponibilidad, funcionalidad y una línea de base de rendimiento para las aplicaciones (tanto extremos de API como recorridos de browser). APM y el monitoreo de browser le indican cómo se comportó el tráfico real, mientras que los monitores Sintéticos le indican si la funcionalidad crítica funciona como se espera en todo momento, incluso en regiones con poco tráfico o antes de que un lanzamiento llegue a los usuarios.

## Ejemplos de casos de uso [#sample-use-cases]

El monitoreo sintético de New Relic abarca un espectro que va desde pings de tiempo de actividad ligeros que cubren la disponibilidad de manera amplia hasta recorridos de API y navegadores completamente programados mediante scripts que ejercitan sus flujos más complejos. En los monitores programados mediante scripts que se ejecutan desde ubicaciones privadas, puede ir aún más lejos, extendiendo el tiempo de ejecución con sus propios módulos npm para verificar casi cualquier cosa accesible desde su red.

### Silbido [#ping]

La comprobación más económica que puede ejecutar es una solicitud HTTP programada que confirme que un extremo está en línea y es lo suficientemente rápido. Lo suficientemente económica como para ejecutarla con frecuencia en cientos de extremos, lo que la convierte en la base para los informes generales de disponibilidad y tiempo de actividad. Detecta interrupciones, no funcionalidades rotas, por lo que debe considerarlo como la primera señal en lugar de una prueba de que la aplicación funciona.

<CollapserGroup>
  <Collapser id="ping-use-cases" title="Consulte los ejemplos de casos de uso">
    Comprobaciones comunes:

    * **Extremo accesible:** envíe una solicitud de forma programada y confirme que devuelve un código de estado correcto (un 200, o cualquier 2xx o 3xx), sin autenticación ni script.
    * **Umbral de tiempo de respuesta:** haga fallar la comprobación cuando el extremo responda más lento que su umbral, para que las regresiones de latencia le den una alerta de forma temprana.
    * **Coincidencia de cadena en el cuerpo:** pasa solo cuando el cuerpo de la respuesta contiene una cadena esperada, como `ok` o `"status":"healthy"`.
  </Collapser>
</CollapserGroup>

Para comenzar, consulte [Agregar y editar monitores](/docs/synthetics/synthetic-monitoring/using-monitors/add-edit-monitors/) para crear uno y [Ver los resultados del monitor de ping](/docs/synthetics/synthetic-monitoring/using-monitors/view-ping-monitor-results/) para leer lo que informa.

### API con scripts [#scripted-api]

Usa Node.js con la API `$http` para encadenar requests, llevar la autenticación y el estado a través de los pasos, y usar un `assertion` en el estado, la carga y el tiempo. Úselo para codificar una transacción comercial real en la capa de servicio, o para observar una dependencia de terceros en la que confía pero que no controla. En ubicaciones privadas, use `require()` para que sus propios módulos alcancen protocolos que no sean HTTP o llamen a las API de modelo, almacén de vectores y cloud con sus SDK existentes.

<CollapserGroup>
  <Collapser id="scripted-api-use-cases" title="Consulte los ejemplos de casos de uso">
    Comprobaciones comunes:

    * **Red y protocolo:** abra una conexión que no sea HTTP y use `assert` para asegurarse de que se realice correctamente. Confirme que un puerto TCP o TLS esté abierto, resuelva un registro DNS, intercambie mensajes WebSocket o MQTT, o alcance LDAP, FTP/SFTP y SMTP.
    * **Certificados y seguridad:** llame a una API con un certificado de cliente (TLS mutuo) y use `assert` para garantizar que se autentique, valide el certificado integrado en los metadatos de SAML o verifique las IP de correo en listas de bloqueo.
    * **Integración de la nube y SaaS:** autentíquese en AWS, Azure o GCP y use `assert` para asegurarse de que un recurso esté presente, por ejemplo, confirme que existe un objeto de exportación de S3 o lea un secreto de Azure Key Vault.
    * **Rendimiento y SEO:** ejecute una auditoría de <DNT>Lighthouse</DNT> a través de la API de <DNT>PageSpeed</DNT> y registre las puntuaciones, o extraiga métricas de <DNT>Search Console</DNT> de forma programada.
    * **Datos de New Relic (NRDB/NRQL):** ejecute una consulta NRQL desde el monitor y alerte cuando el resultado cruce un umbral o se desvíe de un período anterior.
  </Collapser>
</CollapserGroup>

Para comenzar, consulte [Escribir pruebas de API sintéticas](/docs/synthetics/synthetic-monitoring/scripting-monitors/write-synthetic-api-tests/) para crear su primer script y [Importar módulos de Node.js](/docs/synthetics/synthetic-monitoring/scripting-monitors/import-nodejs-modules/) para extenderlo con bibliotecas.

### Browser sencillo [#simple-browser]

Carga la página en una instancia real de Chrome o Firefox, por lo que la comprobación ejecuta el JavaScript, los activos, la CDN y la caché, en lugar de solo el código de estado. Detecta errores de script que bloquean la representación, paquetes faltantes y etiquetas de terceros que fallan silenciosamente y que un ping nunca ve. No se requiere código, por lo que es la forma más rápida de obtener cobertura de representación real en muchas páginas.

<CollapserGroup>
  <Collapser id="simple-browser-use-cases" title="Consulte los ejemplos de casos de uso">
    Comprobaciones comunes:

    * **Disponibilidad de la página:** abra la página desde ubicaciones globales y confirme que se carga y renderiza el contenido esperado.
    * **Comprobaciones de contenido y elementos:** utilice `assert` para asegurarse de que un elemento o texto específico esté presente, como el botón “Agregar al carrito” en una página de producto.
    * **Core Web Vitals:** mida el tiempo de carga de la página y haga fallar la comprobación cuando exceda su presupuesto, por ejemplo, 3 segundos.
  </Collapser>
</CollapserGroup>

Para comenzar, consulte [Agregar y editar monitores](/docs/synthetics/synthetic-monitoring/using-monitors/add-edit-monitors/) para crear uno, y [Emulación de dispositivos](/docs/synthetics/synthetic-monitoring/using-monitors/device-emulation/) para probar las ventanas gráficas de dispositivos móviles y tabletas.

### Browser con script [#scripted-browser]

Controla un navegador real con la API `$browser` (Selenium Webdriver) a través de recorridos de varios pasos, condicionales y autenticados. Una comprobación valida toda la ruta desde el navegador hasta la capa de datos, como el inicio de sesión, la búsqueda, el pago o un flujo interno crítico. Es el monitor más lento y que consume más recursos, así que resérvelo para los recorridos que generan ingresos y confianza.

<CollapserGroup>
  <Collapser id="scripted-browser-use-cases" title="Consulte los ejemplos de casos de uso">
    Comprobaciones comunes:

    * **Browser UX y contenido:** dirija la página para rastrear sus enlaces y fallar en cualquiera que esté roto, cronometrar la descarga de un archivo o verificar el texto dentro de un PDF descargado.
    * **Integración de cloud y SaaS:** tome capturas de pantalla durante el recorrido y cárguelas en un almacenamiento en el cloud como S3.
  </Collapser>
</CollapserGroup>

Para comenzar, consulte [Introducción a los monitores de browser con script](/docs/synthetics/synthetic-monitoring/scripting-monitors/introduction-scripted-browser-monitors/) para conocer los conceptos básicos y la [referencia del browser con script](/docs/synthetics/synthetic-monitoring/scripting-monitors/synthetic-scripted-browser-reference-monitor-versions-chrome-100/) para obtener la API de `$browser` completa.

La API con script y los monitores de browser con script ejecutan el JavaScript, por lo que puede usar `require()` en sus propios módulos npm. Puede impulsar las comprobaciones de protocolo, cloud-SDK y documentos anteriores de la misma manera. En las ubicaciones privadas, esos módulos se instalan desde su propio registro y se ejecutan dentro de la red. Almacene cualquier clave o token como [credenciales seguras](/docs/synthetics/synthetic-monitoring/using-monitors/store-secure-credentials-scripted-browsers-api-tests/).

## Código personalizado y extensibilidad [#programmable-monitoring]

Los monitores programados de New Relic no son comprobadores de función fija —son programas. Si puede expresarlo en código, puede monitorearlo. Eso significa que puede crear una cadena de lógica personalizada, hacer una consulta de sus propios datos de New Relic y extender los monitores con su propio código y módulos.

### Aportar su propio código [#bring-your-own-code]

Los monitores con scripts le permiten usar `require()` en sus propios módulos. En las [ubicaciones privadas](/docs/synthetics/synthetic-monitoring/guides/private-location-capabilities/), monta un directorio que contiene un `package.json` y el administrador de trabajos ejecuta `npm install` al inicio, por lo que cualquier paquete npm o biblioteca interna se convierte en parte del monitor —lo suficiente para hablar protocolos no HTTP (TCP, WebSocket, MQTT, LDAP, SFTP, SMTP), llamar a SDK de proveedores de la nube o decodificar formatos propietarios. El alcance de los monitores es todo el ecosistema de paquetes más su propio código, no una lista de características fija —por lo que una nueva necesidad significa agregar una dependencia, no presentar una solicitud de característica.

### Ejecútelo de forma privada, dentro de su red [#run-privately]

Debido a que los monitores programados se ejecutan en el administrador de trabajos de Sintéticos, puede ejecutarlos desde [ubicaciones privadas](/docs/synthetics/synthetic-monitoring/guides/private-location-capabilities/) dentro de su propia red. Eso significa probar los sistemas internos con sus propios módulos, instalados desde su propio registro, sin exponer nada a la red pública de Internet.

### Reciba alertas sobre anomalías de telemetría [#monitor-telemetry]

Un monitor de API programado mediante scripts puede consultar sus propios datos de New Relic y alertar sobre el resultado según la lógica que defina en los scripts personalizados, proporcionando cobertura para escenarios que no encajan dentro de las condiciones de alerta, como consultar datos durante un período de tiempo más largo o comparar resultados con un período de tiempo anterior:

* **Consulte los datos:** [llame a la API de NerdGraph con `$http`](https://docs.newrelic.com/docs/synthetics/synthetic-monitoring/scripting-monitors/write-synthetic-api-tests/#get-nerdgraph-example), usando una clave de API almacenada como [credencial segura](/docs/synthetics/synthetic-monitoring/using-monitors/store-secure-credentials-scripted-browsers-api-tests/), para ejecutar una consulta NRQL.
* **Alerta sobre desviaciones:** utilice una `assertion` o una lógica similar para que la comprobación falle cuando el resultado cruce un umbral o se desvíe de un período anterior.
