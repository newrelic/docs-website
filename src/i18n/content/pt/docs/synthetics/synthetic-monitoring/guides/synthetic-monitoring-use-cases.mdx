O monitoramento sintético executa verificações automatizadas e programadas em aplicativos e endpoints a partir de localizações escolhidas — localizações públicas que a New Relic opera em todo o mundo, ou [localizações privadas](/docs/synthetics/synthetic-monitoring/guides/private-location-capabilities/) dentro da própria rede. Cada monitor realiza uma solicitação real ou jornada do usuário em um intervalo fixo e relata o resultado, para que falhas, lentidões e fluxos interrompidos sejam detectados o mais cedo possível.

Como essas verificações estão sempre em execução, elas fornecem disponibilidade, funcionalidade e uma baseline de desempenho para os aplicativos (tanto endpoints de API quanto jornadas de browser). O APM e o monitoramento de Browser informam como o tráfego real se comportou, enquanto os monitores Sintéticos informam se a funcionalidade crítica funciona conforme o esperado em todos os momentos, inclusive em regiões com pouco tráfego ou antes que uma versão chegue aos usuários.

## Exemplos de casos de uso [#sample-use-cases]

O monitoramento sintético da New Relic abrange um espectro que vai desde pings leves de tempo de operação, que cobrem a disponibilidade de forma ampla, até jornadas de API e navegador totalmente baseadas em scripts, que exercitam os fluxos mais complexos. Em monitores com scripts executados a partir de localizações privadas, é possível ir ainda mais longe, estendendo o tempo de execução com os próprios módulos npm para verificar quase tudo que seja acessível a partir da própria rede.

### Pingar [#ping]

A verificação mais econômica que pode ser executada é uma solicitação HTTP programada confirmando que um endpoint está online e rápido o suficiente. Econômica o suficiente para ser executada frequentemente em centenas de endpoints, o que a torna a base para relatórios amplos de disponibilidade e tempo de operação. Ela detecta interrupções, não funcionalidades quebradas, portanto, deve ser tratada como o primeiro sinal, em vez de prova de que o aplicativo funciona.

<CollapserGroup>
  <Collapser id="ping-use-cases" title="Ver exemplos de casos de uso">
    Verificações comuns:

    * **Endpoint acessível:** enviar uma solicitação de forma programada e confirmar que ela retorna um código de status íntegro (um 200, ou qualquer 2xx ou 3xx), sem autenticação ou script.
    * **Limite de tempo de resposta:** reprovar a verificação quando o endpoint responder mais lentamente que o limite, para que regressões de latência emitam alertas precocemente.
    * **Correspondência de string do corpo:** passar apenas quando o corpo da resposta contiver uma string esperada, como `ok` ou `"status":"healthy"`.
  </Collapser>
</CollapserGroup>

Para começar, consulte [Adicionar e editar monitores](/docs/synthetics/synthetic-monitoring/using-monitors/add-edit-monitors/) para criar um, e [Visualizar resultados do monitor de ping](/docs/synthetics/synthetic-monitoring/using-monitors/view-ping-monitor-results/) para ler o que ele relata.

### API com script [#scripted-api]

Usa Node.js com a API `$http` para criar uma cadeia de requests, transportar autenticação e estado entre as etapas e usar um `assertion` no status, na carga e no tempo. Use-o para codificar uma transação de negócios real na camada de serviço ou para observar uma dependência de terceiros na qual se confia, mas não se controla. Em localizações privadas, use `require()` para que os próprios módulos alcancem protocolos não HTTP ou chamem APIs de modelo, armazenamento de vetores e cloud com os SDKs existentes.

<CollapserGroup>
  <Collapser id="scripted-api-use-cases" title="Ver exemplos de casos de uso">
    Verificações comuns:

    * **Rede e protocolo:** abra uma conexão não HTTP e use `assert` para garantir que ela seja bem-sucedida. Confirme se uma porta TCP ou TLS está aberta, resolva um registro DNS, troque mensagens WebSocket ou MQTT, ou alcance LDAP, FTP/SFTP e SMTP.
    * **Certificados e segurança:** chame uma API com um certificado de cliente (TLS mútuo) e use `assert` para garantir que ela seja autenticada, valide o certificado incorporado nos metadados SAML ou verifique os IPs de e-mail em listas de bloqueio.
    * **Integração de nuvem e SaaS:** autentique-se na AWS, no Azure ou no GCP e use `assert` para garantir que um recurso esteja presente, por exemplo, confirmar se um objeto de exportação do S3 existe ou ler um segredo do Azure Key Vault.
    * **Desempenho e SEO:** execute uma auditoria de <DNT>Lighthouse</DNT> por meio da API <DNT>PageSpeed</DNT> e registre as pontuações, ou extraia métricas de <DNT>Search Console</DNT> de forma programada.
    * **Dados do New Relic (NRDB/NRQL):** execute uma consulta NRQL a partir do monitor e emita um alerta quando o resultado ultrapassar um limite ou desviar de um período anterior.
  </Collapser>
</CollapserGroup>

Para começar, consulte [Escrever testes de API Sintético](/docs/synthetics/synthetic-monitoring/scripting-monitors/write-synthetic-api-tests/) para criar o seu primeiro script e [Importar módulos do Node.js](/docs/synthetics/synthetic-monitoring/scripting-monitors/import-nodejs-modules/) para estendê-lo com bibliotecas.

### Browser simples [#simple-browser]

Carrega a página em uma instância real do Chrome ou Firefox, para que a verificação execute o JavaScript, os ativos, a CDN e o cache, em vez de apenas o código de status. Captura erros de script que bloqueiam a renderização, pacotes ausentes e tags de terceiros que falham silenciosamente e que um ping nunca vê. Não é necessário código, portanto, é a maneira mais rápida de obter cobertura de renderização real em várias páginas.

<CollapserGroup>
  <Collapser id="simple-browser-use-cases" title="Ver exemplos de casos de uso">
    Verificações comuns:

    * **Disponibilidade da página:** abra a página a partir de locais globais e confirme se ela carrega e renderiza o conteúdo esperado.
    * **Verificações de conteúdo e elemento:** use `assert` para garantir que um elemento ou texto específico esteja presente, como o botão &quot;Adicionar ao carrinho&quot; em uma página de produto.
    * **Core Web Vitals:** medir o tempo de carregamento da página e falhar a verificação quando exceder o orçamento, por exemplo, 3 segundos.
  </Collapser>
</CollapserGroup>

Para começar, consulte [Adicionar e editar monitores](/docs/synthetics/synthetic-monitoring/using-monitors/add-edit-monitors/) para criar um e [Emulação de dispositivo](/docs/synthetics/synthetic-monitoring/using-monitors/device-emulation/) para testar janelas de visualização de dispositivos móveis e tablets.

### Browser com script [#scripted-browser]

Conduz um navegador real com a API `$browser` (Selenium Webdriver) por meio de jornadas autenticadas, condicionais e de várias etapas. Uma verificação valida todo o caminho do navegador até a camada de dados, como login, pesquisa, checkout ou um fluxo interno crítico. É o monitor mais lento e que consome mais recursos, portanto, deve ser reservado para as jornadas que geram receita e confiança.

<CollapserGroup>
  <Collapser id="scripted-browser-use-cases" title="Ver exemplos de casos de uso">
    Verificações comuns:

    * **UX e conteúdo do Browser:** conduzir a página para rastrear seus links e falhar em qualquer um quebrado, cronometrar o download de um arquivo ou verificar o texto dentro de um PDF baixado.
    * **Integração de cloud e SaaS:** faça capturas de tela durante a jornada e faça o upload delas para o armazenamento em cloud, como o S3.
  </Collapser>
</CollapserGroup>

Para começar, consulte [Introdução ao monitor de browser com script](/docs/synthetics/synthetic-monitoring/scripting-monitors/introduction-scripted-browser-monitors/) para obter os conceitos básicos e a [referência do browser com script](/docs/synthetics/synthetic-monitoring/scripting-monitors/synthetic-scripted-browser-reference-monitor-versions-chrome-100/) para a API `$browser` completa.

A API com script e os monitores de browser com script executam o JavaScript, portanto, é possível usar `require()` nos próprios módulos npm. As verificações de protocolo, cloud-SDK e documento acima são acionadas da mesma forma. Em localizações privadas, esses módulos são instalados a partir do próprio registro e executados dentro da rede. Armazene quaisquer chaves ou tokens como [credenciais seguras](/docs/synthetics/synthetic-monitoring/using-monitors/store-secure-credentials-scripted-browsers-api-tests/).

## Código personalizado e extensibilidade [#programmable-monitoring]

Os monitores com script da New Relic não são verificadores de função fixa — eles são programas. Se for possível expressar em código, será possível monitorar. Isso significa que é possível encadear lógica personalizada, consultar os próprios dados da New Relic e estender os monitores com código e módulos próprios.

### Trazer seu próprio código [#bring-your-own-code]

Os monitores com script permitem usar `require()` nos próprios módulos. Em [localizações privadas](/docs/synthetics/synthetic-monitoring/guides/private-location-capabilities/), é montado um diretório contendo um `package.json`, e o gerenciador de trabalhos executa `npm install` na inicialização, para que qualquer pacote npm ou biblioteca interna se torne parte do monitor — o suficiente para falar protocolos não HTTP (TCP, WebSocket, MQTT, LDAP, SFTP, SMTP), chamar SDKs de provedores de nuvem ou decodificar formatos proprietários. O alcance dos monitores é todo o ecossistema de pacotes mais o próprio código, não uma lista fixa de recursos — portanto, uma nova necessidade significa adicionar uma dependência, não registrar uma solicitação de recurso.

### Execute-o de forma privada, dentro de sua rede [#run-privately]

Como os monitores com script são executados no gerenciador de trabalhos de Sintéticos, é possível executá-los a partir de [localizações privadas](/docs/synthetics/synthetic-monitoring/guides/private-location-capabilities/) dentro da própria rede. Isso significa exercitar sistemas internos com os próprios módulos, instalados a partir do próprio registro, sem expor nada à internet pública.

### Receba alertas sobre anomalia de telemetria [#monitor-telemetry]

Um monitor de API com script pode consultar os próprios dados do New Relic e emitir um alerta sobre o resultado com base na lógica definida nos scripts personalizados, fornecendo cobertura para cenários que não se enquadram na condição do alerta, como consultar dados durante um período mais longo ou comparar resultados com um período anterior:

* **Consulte seus dados:** [chame a API do NerdGraph com `$http`](https://docs.newrelic.com/docs/synthetics/synthetic-monitoring/scripting-monitors/write-synthetic-api-tests/#get-nerdgraph-example), usando uma chave de API armazenada como uma [credencial segura](/docs/synthetics/synthetic-monitoring/using-monitors/store-secure-credentials-scripted-browsers-api-tests/), para executar uma consulta NRQL.
* **Alerta sobre desvios:** recomenda-se utilizar um `assertion` ou lógica semelhante para reprovar a verificação quando o resultado ultrapassar um limite ou se desviar de um período anterior.
