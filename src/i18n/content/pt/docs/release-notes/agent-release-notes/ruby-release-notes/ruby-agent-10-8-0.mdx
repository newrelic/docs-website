## v10.8.0

* **Recurso: reportar um nome do host exclusivo para os Worker Pools e Jobs do Google Cloud Run**

  O suporte ao nome do host do Cloud Run, adicionado no [PR#3609](https://github.com/newrelic/newrelic-ruby-agent/pull/3609/), detectava o Cloud Run apenas por meio de `K_REVISION`, a variável de ambiente definida pelos **Services** do Cloud Run. O agente agora também reconhece [`CLOUD_RUN_REVISION`](https://docs.cloud.google.com/run/docs/container-contract#env-vars) (Worker Pools) e `CLOUD_RUN_EXECUTION` (Jobs), portanto, `utilization.gcp_cloud_run.use_instance_as_host` agora se aplica a todos os três tipos de recursos. Quando `utilization.gcp_cloud_run.include_revision_in_host` é `true`, o nome do host é criado a partir de qualquer uma dessas variáveis que esteja presente — por exemplo, `{CLOUD_RUN_EXECUTION}-{instance id}` para um Job. [Issue#3651](https://github.com/newrelic/newrelic-ruby-agent/issues/3651) [PR#3652](https://github.com/newrelic/newrelic-ruby-agent/pull/3652)

* **Recurso: adicionar a opção de configuração `browser_monitoring.version`**

  Os clientes agora podem fixar a versão exata do loader do agente do browser que a New Relic injeta definindo a nova opção de configuração `browser_monitoring.version`. Consulte a [política de EOL do agente do browser](https://docs.newrelic.com/docs/browser/browser-monitoring/getting-started/browser-agent-eol-policy/) para ver quais versões estão atualmente disponíveis e suportadas. [PR#3663](https://github.com/newrelic/newrelic-ruby-agent/pull/3663)

* **Recurso: adicionar span.kind às bibliotecas de trabalhos em segundo plano**

  Agora, o atributo `span.kind` será adicionado às operações `produce` e `consume` de bibliotecas de trabalhos em segundo plano. Isso inclui ActiveJob, Sidekiq, Resque e DelayedJob. [PR#3636](https://github.com/newrelic/newrelic-ruby-agent/pull/3636)

* **Correção de bug: a instrumentação do DelayedJob não se reinstala mais em cada worker no modo prepend**

  Quando a instrumentação do DelayedJob é instalada via prepend (o padrão), criar mais de um `Delayed::Worker` no mesmo processo fazia com que o agente registrasse “Installing DelayedJob instrumentation” e reinicializasse o plug-in novamente para cada worker adicional. Isso era inofensivo, mas ruidoso; agora é feito apenas uma vez por processo, correspondendo ao comportamento existente da instrumentação de cadeia. [PR#3654](https://github.com/newrelic/newrelic-ruby-agent/pull/3654)

* **Correção de bug: os valores de configuração na lista de permissões não diferenciam mais maiúsculas de minúsculas**

  Anteriormente, as opções de configuração permitidas exigiam uma correspondência exata de maiúsculas e minúsculas, de modo que um valor com uso inesperado de maiúsculas e minúsculas — como `OBFUSCATED` ou `ObFuScAtEd` para `slow_sql.record_sql` — reverteria silenciosamente para o padrão. As opções de configuração que são validadas em uma lista de permissões agora correspondem aos valores independentemente de maiúsculas e minúsculas, portanto, ambos são tratados da mesma forma que `obfuscated`. [Issue#3613](https://github.com/newrelic/newrelic-ruby-agent/issues/3613) [PR#3645](https://github.com/newrelic/newrelic-ruby-agent/pull/3645)

* **Correção de bug: a instrumentação do Puma funciona quando o Puma é carregado sob demanda**

  Com `gem "puma", require: false`, o Puma ainda não estava carregado quando a verificação de dependência do agente era executada, portanto, a instrumentação do Puma falhava ao ser instalada. O agente agora reconhece `Puma::RackHandler` como evidência de que o Puma está presente, corrigindo esse problema. [Issue#3641](https://github.com/newrelic/newrelic-ruby-agent/issues/3641) [PR#3650](https://github.com/newrelic/newrelic-ruby-agent/pull/3650)
