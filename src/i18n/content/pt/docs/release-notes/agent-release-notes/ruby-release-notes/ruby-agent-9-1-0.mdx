## v9.1.0

A versão 9.1.0 do agente oferece suporte a dois novos recursos do [Errors Inbox](https://docs.newrelic.com/docs/triage-inbox/errors-inbox/): impressão digital de erros e rastreamento de usuário, identifica o armazenamento de dados do Amazon Timestream, remove os avisos de distributed tracing dos logs do agente ao usar o Sidekiq, corrige bugs e é testada na versão recém-lançada do JRuby 9.4.2.0.

* **Recurso: impressão digital de erro - forneça seus próprios nomes de grupo do Errors Inbox**

  Suas ocorrências de erro estão mal agrupadas? Defina sua própria impressão digital de erro via uma função de retorno de chamada. Foi adicionado um novo método `set_error_group_callback` de API pública que aceitará um proc definido pelo usuário. O proc será invocado para cada erro notado e, sempre que retornar uma string, essa string será usada como o nome do grupo de erros para o erro e terá precedência sobre qualquer agrupamento no lado do servidor que ocorra com o Errors Inbox do New Relic. Isso oferece aos usuários um controle muito maior sobre o agrupamento de seus erros.

  Espera-se que o proc definido pelos clientes receba exatamente um argumento de entrada, um hash. O hash contém o seguinte:

  | Chave                | Valor                                                                            |
  | -------------------- | -------------------------------------------------------------------------------- |
  | `:error`             | A instância da classe de erro Ruby. Ofertas `#class`, `#message` e `#backtrace`  |
  | `:customAttributes`  | Quaisquer atributos personalizados definidos pelo cliente para a transação atual |
  | `:'request.uri'`     | O URI da requisição atual, se disponível                                         |
  | `:'http.statusCode'` | O código de status HTTP (200, 404, etc.), se disponível                          |
  | `:'http.method'`     | O método HTTP (GET, PUT, etc.), se disponível                                    |
  | `:'error.expected'`  | Se (verdadeiro) ou não (falso) o erro era esperado                               |
  | `:'options'`         | As opções aplicam hash passado para `NewRelic::Agent.notice_error`               |

  O retorno de chamada só precisa ser definido uma vez por inicialização do agente da New Relic.

  Exemplo de uso:

  ```
  proc = proc { |hash| "Access" if hash[:'http.statusCode'] == 401 }
  NewRelic::Agent.set_error_group_callback(proc)
  ```

* **Recurso: rastreamento de usuário - associar erros a um ID de usuário**

  Agora você pode ver o número de usuários impactados por um grupo de erros. Identifique o usuário final com um novo método de API pública `set_user_id` que aceitará uma representação de string de um ID de usuário e associará esse ID de usuário à transação atual. Transações e erros terão então um novo atributo de agente `enduser.id` associado a eles. Isso permitirá que os usuários do agente adicionem tags a transações e erros como pertencentes a determinados IDs de usuário, para dar suporte a recursos aprimorados de filtragem e alerta.

* **Identificar o Amazon Timestream quando o adaptador AR amazon\_timestream é usado**

  Quando o agente detectar a gem [activerecord-amazon-timestream-adapter](https://rubygems.org/gems/activerecord-amazon-timestream-adapter) sendo usada, ele agora identificará o armazenamento de dados como “Timestream”. Muito obrigado a [@wagner](https://github.com/wagner) por contribuir com esta melhoria! [PR n.º 1872](https://github.com/newrelic/newrelic-ruby-agent/pull/1872)

* **Correção de bug: remover avisos relacionados ao distributed tracing dos logs do agente quando os cabeçalhos não estão presentes no Sidekiq**

  Anteriormente, o agente registrava um aviso em `newrelic_agent.log` toda vez que tentava aceitar cabeçalhos de distributed tracing vazios de trabalhos do Sidekiq, o que poderia resultar em um número excessivo de avisos. Agora, o agente não criará mais esses avisos ao usar o Sidekiq. [PR#1834](https://github.com/newrelic/newrelic-ruby-agent/pull/1834)

* **Correção de bug: registrar cabeçalhos de requisição em logs de nível de depuração em vez de Objetos legíveis por humanos**

  Anteriormente, o agente às vezes recebia filhos da classe `NewRelic::Agent::HTTPClients::AbstractRequest` como argumento quando `NewRelic::Agent::Transaction::DistributedTracers#log_request_headers` era chamado. Isso fazia com que as mensagens do log de nível de depuração que imprimem os cabeçalhos da requisição mostrassem Objetos legíveis por humanos (ex. `#<NewRelic::Agent::HTTPClients::HTTPClientRequest:0x00007fd0dda983e0>`) em vez dos cabeçalhos da requisição. Agora, o hash dos cabeçalhos da requisição deve ser sempre registrado no log. [PR#1839](https://github.com/newrelic/newrelic-ruby-agent/pull/1839)

* **Correção de bug: corrigido o método indefinido `controller_path` registrado na Instrumentação do Action Controller**

  Anteriormente, o agente podia registrar um erro ao tentar determinar o nome da métrica na instrumentação do Action Controller se a classe do controlador não respondesse a `controller_path`. Isso foi resolvido e o agente não chamará mais esse método, a menos que a classe responda a ele. Agradecemos a [@gsar](https://github.com/gsar) por nos informar sobre esse problema. [PR#1844](https://github.com/newrelic/newrelic-ruby-agent/pull/1844)

* **Correção de bug: corrige a exceção de Transaction#finish e diminui o nível de log para o aviso relacionado durante transações assíncronas**

  Anteriormente, o agente gerava um erro não fatal quando um segmento sem pai estava inacabado quando a transação era concluída. Esse erro era gerado durante a construção de uma mensagem do log de nível `warn`. Agora que a instrumentação de Thread está ativada por padrão, essa mensagem do log é emitida com mais frequência e é menos preocupante. Nos casos em que vemos um segmento de Thread, Fiber ou concurrent-ruby em uma transação, a mensagem será rebaixada para um nível `debug`. Agradecemos a [@NielsKSchjoedt](https://github.com/NielsKSchjoedt) por criar o problema e a [@boomer196](https://github.com/boomer196) por testar as soluções. [PR#1876](https://github.com/newrelic/newrelic-ruby-agent/pull/1876)

* **CI: destino JRuby 9.4.2.0**

  O agente agora está sendo testado ativamente com o JRuby 9.4.2.0. OBSERVE que esta versão não contém nenhuma alteração não relacionada à CI para o JRuby. Espera-se que as versões antigas do agente ainda funcionem com JRubies mais recentes e que a versão mais recente do agente ainda funcione com JRubies mais antigos.
