## v9.13.0

A versão 9.13.0 aprimora o suporte para funções do AWS Lambda, adiciona instrumentação experimental do OpenSearch, atualiza a detecção de framework, silencia um aviso de descontinuação do Bundler, corrige a detecção do despachante do Falcon, corrige um bug com a instalação da instrumentação do Redis e resolve um problema de simultaneidade específico do JRuby.

* **Recurso: aprimorar a instrumentação da função do AWS Lambda**

Quando utilizado por meio da mais recente [camada Ruby do New Relic para AWS Lambda](https://layers.newrelic-external.com/), o agente agora oferece suporte aprimorado para a instrumentação da função do AWS Lambda.

* A instrumentação do agente para funções do AWS Lambda agora oferece suporte a distributed tracing.

* As invocações acionadas pela web agora são identificadas como sendo baseadas na &quot;web&quot; quando uma chamada do API Gateway está envolvida, com suporte para as versões 1.0 e 2.0 do API Gateway.

* As chamadas baseadas na web têm o método HTTP, o URI e o código de status registrados.

* O agente agora reconhece e informa sobre 12 recursos distintos da AWS que são capazes de acionar a invocação de uma função do Lambda: ALB, API Gateway V1, API Gateway V2, CloudFront, CloudWatch Scheduler, DynamoStreams, Firehose, Kinesis, S3, SES, SNS e SQS.

* O tipo do recurso acionador e seu ARN serão registrados para cada recurso e, para muitos deles, atributos extras específicos do recurso também serão registrados. Por exemplo, invocações da função do Lambda acionadas pela atividade do bucket do S3 agora resultarão no registro do nome do bucket do S3. [PR#2811](https://github.com/newrelic/newrelic-ruby-agent/pull/2811)

* **Recurso: adicionar instrumentação experimental do OpenSearch**

  O agente agora instrumentará automaticamente a gem `opensearch-ruby`. Estamos marcando esta instrumentação como experimental porque é necessário mais trabalho para testá-la totalmente. A instrumentação do OpenSearch fornece telemetria semelhante à do Elasticsearch. Agradecemos a [@Earlopain](https://github.com/Earlopain) por relatar o problema e a [@praveen-ks](https://github.com/praveen-ks) por um rascunho inicial da instrumentação. [Issue n.º 2228](https://github.com/newrelic/newrelic-ruby-agent/issues/2228) [PR n.º 2796](https://github.com/newrelic/newrelic-ruby-agent/pull/2796)

* **Recurso: melhorar a precisão de detecção de framework para Grape e Padrino**

  Anteriormente, os aplicativos que usavam o framework Grape definiam `ruby` como seu framework no Relatório de Ambiente. Agora, os aplicativos Grape serão definidos como `grape`. Da mesma forma, os aplicativos que usam o framework Padrino seriam definidos como `sinatra`. Agora, eles serão definidos como `padrino`. Isso ajudará nas verificações de compatibilidade do agente de segurança do New Relic. Agradecemos a [@prateeksen](https://github.com/prateeksen) por fazer essa alteração. [Issue#2777](https://github.com/newrelic/newrelic-ruby-agent/issues/2777) [PR#2789](https://github.com/newrelic/newrelic-ruby-agent/pull/2789)

* **Recurso: silenciar o aviso de descontinuação do Bundler `all_specs`**

  `Bundler.rubygems.all_specs` foi descontinuado em favor de `Bundler.rubygems.installed_specs` nas versões 2+ do Bundler, fazendo com que o agente emitisse avisos de descontinuação. O método foi atualizado quando o Bundler 2+ é detectado e os avisos agora são silenciados. Agradecemos a [@jcoyne](https://github.com/jcoyne) por relatar este problema. [Issue#2733](https://github.com/newrelic/newrelic-ruby-agent/issues/2733) [PR#2823](https://github.com/newrelic/newrelic-ruby-agent/pull/2823)

* **Correção de bug: corrigir a detecção do dispatcher do Falcon**

  Anteriormente, tentamos usar o espaço de objetos para determinar se o [servidor web Falcon](https://github.com/socketry/falcon) estava em uso. No entanto, o Falcon não é adicionado ao espaço de objetos até que o relatório de ambiente seja gerado, resultando em um dispatcher `nil`. Agora, revertemos para uma estratégia anterior que descobria o dispatcher usando `File.basename`. Agradecemos a [@prateeksen](https://github.com/prateeksen) por relatar este problema e investigar a questão. [Issue#2778](https://github.com/newrelic/newrelic-ruby-agent/issues/2778) [PR#2795](https://github.com/newrelic/newrelic-ruby-agent/pull/2795)

* **Correção de bug: correção de um erro de instrumentação do Redis quando Redis::Cluster::Client está presente**

  A instrumentação do Redis continha anteriormente um bug que causava um erro quando `Redis::Cluster::Client` estava presente, devido ao uso de um `return` do Ruby fora de um método. Agradecemos muito ao [@jdelStrother](https://github.com/jdelStrother) não apenas por relatar este bug, mas também por nos indicar a causa raiz. [Issue#2814](https://github.com/newrelic/newrelic-ruby-agent/issues/2814) [PR#2816](https://github.com/newrelic/newrelic-ruby-agent/pull/2816)

* **Correção de bug: Resolver problema de concorrência do JRuby com o acesso à configuração de aplicar hash**

  A classe de configuração interna do agente mantém um hash que ocasionalmente é reconstruído. Durante a reconstrução, certos valores de instrumentação previamente determinados de forma dinâmica são preservados para o benefício do [agente de segurança New Relic Ruby](https://github.com/newrelic/csec-ruby-agent). Após relatos de clientes do JRuby sobre problemas de concorrência relacionados ao hash sendo acessado enquanto era modificado, duas correções separadas foram incluídas na lógica de reconstrução do hash anteriormente: uma operação `Hash#dup` e um bloco `synchronize do`. Mas erros ainda foram relatados. Nós mesmos continuamos incapazes de reproduzir esses erros de concorrência, apesar de usarmos exatamente as mesmas versões do JRuby e de todos os softwares relatados. Após confirmar que o código de acesso ao hash em questão é necessário apenas para o agente de segurança Ruby (que opera apenas em ambientes dedicados de testes de segurança de não produção), introduzimos uma nova correção para clientes do JRuby que simplesmente ignorará o código problemático quando o JRuby estiver em uso, mas o agente de segurança não. [PR#2798](https://github.com/newrelic/newrelic-ruby-agent/pull/2798)
