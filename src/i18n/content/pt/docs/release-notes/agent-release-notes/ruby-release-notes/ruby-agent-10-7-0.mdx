## v10.7.0

* **Recurso: adicionar transaction\_tracer.cap\_segment\_artifacts opção de configuração**

  Transações de longa duração com muitos segmentos podem causar o aumento contínuo do uso de memória durante a vida útil da transação. O agente agora oferece uma opção de configuração `transaction_tracer.cap_segment_artifacts` opcional (o padrão é `false`). Quando ativado, assim que [`transaction_tracer.limit_segments`](https://docs.newrelic.com/docs/apm/agents/ruby-agent/configuration/ruby-agent-configuration/#transaction_tracer-limit_segments) for atingido, o agente também para de registrar o tempo exclusivo para quaisquer segmentos criados posteriormente nessa transação, reduzindo o uso de memória à custa de dados de tempo menos precisos para a transação. [PR#3615](https://github.com/newrelic/newrelic-ruby-agent/pull/3615)

* **Recurso: Adicionar instrumentação de estatísticas do servidor Puma**

  O agente agora faz a amostragem das estatísticas do servidor em todo o cluster do Puma e as relata como métricas de timeslice `Ruby/Puma/*`, incluindo `backlog`, `running`, `pool_capacity`, `max_threads` e `requests_count`. As estatísticas são amostradas no modo único e no modo em cluster quando `preload_app!` está habilitado. Esta instrumentação está desabilitada por padrão. Habilite-a definindo `disable_puma_instrumentation` como `false`. Quando habilitado, o agente inicia uma thread de relatório no processo mestre do Puma para entregar essas métricas, o que executa uma conexão adicional do agente junto com os workers do Puma. O intervalo de amostragem é configurável por meio da nova configuração `puma.sample_rate` (padrão de 60 segundos). Requer o Puma 6.6 ou posterior. Consulte [nossos documentos](https://docs.newrelic.com/docs/apm/agents/ruby-agent/instrumented-gems/puma-instrumentation/) para obter mais informações. [PR#3578](https://github.com/newrelic/newrelic-ruby-agent/pull/3578)

* **Recurso: relatar um nome do host exclusivo para instâncias do Google Cloud Run**

  O agente agora detecta o Cloud Run e relata o ID da instância do GCP como o nome do host para que instâncias individuais possam ser distinguidas. Antes dessa alteração, todos os nomes do host do Google Cloud Run eram `localhost`. Esse recurso é controlado pela nova opção de configuração `utilization.gcp_cloud_run.use_instance_as_host` (padrão `true`). `utilization.gcp_cloud_run.include_revision_in_host` (padrão `false`) deve ser definido como `true` para, em vez disso, relatar o nome do host como `{K_REVISION}-{instance id}`, em que [`K_REVISION`](https://docs.cloud.google.com/run/docs/container-contract#env-vars) é o nome da revisão do Cloud Run. [Issue n.º 3295](https://github.com/newrelic/newrelic-ruby-agent/issues/3295) [PR n.º 3609](https://github.com/newrelic/newrelic-ruby-agent/pull/3609)

* **Correção de bug: o SQL lento não é mais registrado após transaction\_tracer.limit\_segments excedido**

  Depois que uma transação excedia [`transaction_tracer.limit_segments`](https://docs.newrelic.com/docs/apm/agents/ruby-agent/configuration/ruby-agent-configuration/#transaction_tracer-limit_segments), os segmentos de armazenamento de dados criados posteriormente ainda podiam ter seu SQL lento registrado. O agente agora para de registrar SQL lento para qualquer segmento criado após o limite ser atingido. [PR#3615](https://github.com/newrelic/newrelic-ruby-agent/pull/3615)

* **Correção de bug: os planos de execução poderiam ter como destino o banco de dados errado em aplicativos Rails com vários bancos de dados (Rails &gt;= 7.2)**

  No Rails 7.2+, o agente coletou planos de explicação usando uma conexão do pool padrão/compartilhado do aplicativo, em vez de uma dedicada. Isso afetou principalmente aplicativos com vários bancos de dados. Os planos de explicação poderiam ser gerados no banco de dados errado, e uma explicação com falha poderia deixar uma conexão compartilhada em um estado ruim, afetando requests não relacionados. O agente agora usa sua própria conexão dedicada para planos de explicação, como fazia antes do Rails 7.2, e redefine ou descarta essa conexão sempre que uma tentativa de explicação falha, para que uma conexão ruim nunca seja reutilizada. [Issue#3610](https://github.com/newrelic/newrelic-ruby-agent/issues/3610) [PR#3612](https://github.com/newrelic/newrelic-ruby-agent/pull/3612)

* **Correção de bug: a instrumentação do monitoramento de Browser não falha mais com `FrozenError`**

  Quando o primeiro fragmento do corpo de uma resposta era um `String` congelado e havia vários fragmentos, a instrumentação do navegador atingia um `FrozenError` e o cabeçalho de tempo do navegador nunca era injetado. Isso começou a aparecer com o `ERB` 6.0.3+, que começou a congelar mais de suas strings compiladas. Esse problema já foi resolvido. [Issue#3624](https://github.com/newrelic/newrelic-ruby-agent/issues/3624) [PR#3625](https://github.com/newrelic/newrelic-ruby-agent/pull/3625)

* **Correção de bug: normalizar valores de configuração booleanos para permitir qualquer formato de maiúsculas e minúsculas**

  Na versão 9.x, o agente aceitava valores booleanos em maiúsculas, como &quot;FALSE&quot;, e valores com letras maiúsculas e minúsculas, como &quot;True&quot;. A versão 10.0.0 incluiu o [PR#3341](https://github.com/newrelic/newrelic-ruby-agent/pull/3341), que removeu acidentalmente o requisito de não diferenciar maiúsculas de minúsculas. Isso fez com que os usuários que tivessem qualquer uso de maiúsculas e minúsculas além de todas minúsculas tivessem suas opções de configuração revertidas para os padrões. Agora, o agente usa verificações que não diferenciam maiúsculas de minúsculas novamente. [Issue#3632](https://github.com/newrelic/newrelic-ruby-agent/issues/3632) [PR#3633](https://github.com/newrelic/newrelic-ruby-agent/pull/3633)
