Nosso componente de instalação ramificada para o site de documentação permite que nossos usuários selecionem uma ou mais opções, o que, em seguida, exibe o conteúdo com base nessas escolhas.

## Visão geral do processo de criação [#overview]

Antes de iniciar o trabalho com o componente de instalação de branch, há alguns pontos a considerar:

* Certifique-se de que deseja utilizar a instalação ramificada. Considere se o problema pode ser resolvido com outra solução (por exemplo, o [componente de aba](/docs/style-guide/structure/intro-to-components)).
* Navegue pelos [documentos de instalação ramificados que criamos](#uses) e veja o que é possível. Selecione um que deseje clonar para usar como modelo.
* Finalize o fluxo lógico de quais serão as opções e qual conteúdo será exibido. Idealmente, os planos de conteúdo devem estar quase finalizados antes da criação de uma branch. Por esse motivo, o trabalho pode ser dividido em dois ou mais Jiras.

É possível construir o componente de instalação ramificada de várias maneiras, e pode exigir um bom esforço para fazê-lo funcionar, especialmente quanto mais complexa for a estrutura. No entanto, dito isso, apresenta-se uma visão de alto nível de como costuma ser um processo de criação:

1. Revisar a documentação da instalação ramificada, especialmente nossos [arquivos YAML de exemplo](#yaml-examples). Conhecer a estrutura e a lógica deste componente.
2. Quando for o momento de começar, copiar o arquivo YAML e as pastas associadas de um componente de instalação que se deseja emular, e usá-los como base para o projeto.
3. Alterar o nome da pasta de nível superior para corresponder ao projeto e alterar o `agentName` no arquivo YAML para corresponder. O `agentName` é o que indica ao arquivo YAML de qual pasta extrair seu conteúdo. (Consultar [nossos arquivos YAML de exemplo](#yaml-examples).)
4. Para garantir que tudo esteja funcionando, realizar uma compilação local.
5. Inicie a adição dos seus arquivos .mdx e a edição do arquivo yaml. Dependendo de quão bem os seus planos correspondem à lógica existente, pode ser mais fácil remover a maior parte do conteúdo do arquivo YAML e adicionar um pouco de cada vez.
6. Durante o trabalho, compile frequentemente para testar se tudo está funcionando. Realizar pequenas partes do trabalho e, em seguida, verificar se a compilação ocorre corretamente ajudará a evitar a perda de tempo com a resolução de problemas. Utilize o [script de verificação YAML](/docs/style-guide/writing-docs/article-templates/branch-install-doc-reference#verify-yaml) para verificar se há erros.

Caso encontre dificuldades, solicite ajuda a alguém que já tenha construído um destes.

## Pontos de decisão importantes [#decision-points]

Existem algumas abordagens diferentes que podem ser adotadas com a instalação ramificada. Aqui estão alguns dos principais pontos de decisão:

<CollapserGroup>
  <Collapser id="default-content-decision" title="Deve-se exibir o conteúdo antes que uma opção seja selecionada?">
    Esta decisão é sobre: o que os clientes veem quando acessam o documento pela primeira vez? Faz sentido mostrar-lhes algumas instruções mesmo antes de selecionarem uma opção? Se houver um único caminho que a maioria dos clientes seguirá, pode fazer sentido mostrar-lhes algum conteúdo que, em seguida, se ajustará e mudará dependendo de suas seleções de opções. Detalhes sobre isso:

    * A abordagem de &quot;conteúdo padrão&quot; depende do uso dos componentes `override` e `skip`. Ele exibe um arquivo e, em seguida, diz: ignorar ou sobrescrever este arquivo quando as opções x forem escolhidas. (Documento de instalação que utiliza isto: [a instalação do Java](/install/java).)
    * Caso não deseje exibir nenhum conteúdo antes que as opções sejam selecionadas, deve-se utilizar a abordagem `isCondition=true`. Esse componente diz simplesmente: &quot;exibir este arquivo se estas opções forem selecionadas&quot;. (Documento de instalação que utiliza isto: [a instalação do .NET](/install/dotnet).)
  </Collapser>

  <Collapser id="display-all-options-decision" title="Todas as opções devem ser exibidas? Ou devem ser aninhadas?">
    Esta decisão diz respeito a se deseja exibir inicialmente todas as escolhas de opções ou se prefere aninhá-las (por exemplo, escolher uma opção resulta em outra caixa de seleção de opções).

    Se a lógica de seleção de opções for bastante simples, pode fazer sentido simplesmente expor todas as opções aos clientes de uma só vez. No entanto, se a lógica de seleção de opções for mais complexa (por exemplo, três ou mais seleções, e algumas seleções afetando seleções posteriores), pode fazer sentido aninhá-las.

    Para obter um exemplo de um conjunto totalmente exposto de caixas de seleção de opções, consulte o \[documento de pré-requisitos de segurança de rede]. Para obter um exemplo de um conjunto aninhado de caixas de seleção, consulte \[a instalação do .NET].
  </Collapser>

  <Collapser id="guided-install-decision" title="A instalação guiada é necessária?">
    Este ponto de decisão refere-se à necessidade de exibir informações sobre nosso caminho de instalação guiada. Para alguns agentes, desejamos exibir algum conteúdo sobre o caminho de instalação guiada (por exemplo, é possível ver o conteúdo da instalação guiada na [instalação do agente Java](/install/java) se &quot;app server&quot; e &quot;Jetty&quot; forem selecionados).

    Existem algumas opções para adicionar o conteúdo da instalação guiada:

    * Há um componente `recommendedGuided: true` que pode ser colocado em opções específicas onde se deseja que o conteúdo da instalação guiada seja exibido. O que isso essencialmente faz é exibir o conteúdo do .mdx arquivo que contém essa caixa de seleção de opções. É possível ver um exemplo disso na instalação do Java, onde o conteúdo da instalação guiada está localizado no arquivo `appInfo-2`. Essa implementação não é, na verdade, específica para o conteúdo da instalação guiada: é possível usar essa lógica para exibir qualquer conteúdo arbitrário que se deseje usar.
    * Como alternativa, é possível apenas adicionar a instalação guiada como um .mdx regular arquivo e exibi-lo como qualquer outro arquivo. A instalação do .NET adota essa abordagem. Com essa abordagem, ele aparecerá como uma etapa numerada, como outros arquivos.
  </Collapser>

  <Collapser id="config-file-decision" title="Preciso de um arquivo de configuração?">
    Alguns agentes fazem uso de um componente de arquivo de configuração que permite aos nossos usuários inserir valores específicos do usuário diretamente do documento de instalação. Para ver um exemplo disso, consulte [o documento de instalação do Java](/install/java).

    O uso deste arquivo não é necessário. O uso disso dependerá do fluxo de trabalho de instalação específico. (Por exemplo, o documento de instalação do .NET não usa isso.)
  </Collapser>
</CollapserGroup>

## Nossa instalação ramificada usa [#uses]

Aqui estão nossas implementações da instalação ramificada com resumos das escolhas feitas para elas. Recomendamos escolher uma que corresponda à abordagem desejada e ajustá-la conforme necessário. Gostaríamos de solicitar que esta lista seja mantida atualizada à medida que adicionamos novos usos.

* Gerenciamento de vulnerabilidades: [importar dados do dependabot](/install/vm/). [Veja uma imagem rotulada deste arquivo YAML](#simple-yaml-example). Detalhes:

  * Uma implementação muito simples. Uma caixa de seleção de opção única, que permite escolher entre dois arquivos.
  * Nenhum conteúdo exibido por padrão.
  * Note-se que isso é tão simples que o componente de guia poderia ter sido uma escolha melhor.

* [Instalação da integração do MySQL](/install/mysql). Detalhes:

  * Uma implementação simples com apenas uma única caixa de seleção de opções.
  * Adota-se uma abordagem de conteúdo padrão exibido.

* [Instalação do Java](/install/java). Detalhes:

  * Adota-se uma [abordagem de conteúdo padrão](#default-content-decision). Isso ocorre porque há um caminho de instalação que a maioria dos clientes segue.
  * Tem apenas duas seções de seleção de opções: dependendo do que for selecionado na primeira opção, uma segunda caixa de opções é exibida.
  * Ele utiliza o componente `recommendedGuided` para exibir a instalação guiada (contida no arquivo `appInfo-2`).
  * Utiliza o componente de arquivo de configuração.

* [Instalação do .NET](/install/dotnet). [Veja uma imagem rotulada deste arquivo YAML](#complex-yaml-example). Detalhes:

  * Isso não exibe nenhum conteúdo padrão. Baseia-se inteiramente na abordagem [`isConditionalStep: true`](#default-content-decision). Isso ocorre porque há vários caminhos e nenhum caminho único que a maioria dos clientes siga (embora, teoricamente, pudéssemos ter escolhido um).
  * Isso tem apenas duas seções de seleção de opções: dependendo do que for selecionado na primeira opção, uma segunda caixa de opções é exibida.
  * Utiliza o componente `recommendedGuided` (contido no arquivo `appInfo-2`).
  * Ele não usa o componente de arquivo de configuração: isso ocorre porque a maioria dos clientes edita a configuração por meio de variáveis de ambiente ou outras opções, e não pelo uso direto do arquivo.

* [Instalação do Python](/install/python). Detalhes:

  * Não exibe conteúdo padrão. Baseia-se inteiramente na [abordagem`isConditionalStep: true` ](#default-content-decision). Isso ocorre porque não há um único caminho principal.
  * Isso possui várias caixas de seleção de opções: até quatro, dependendo do que for selecionado.
  * Ele não utiliza o componente de arquivo de configuração.
  * Faz uso de comentários, o que ajuda na compreensão do código e na melhoria da manutenção.

* [endpoints de monitoramento de rede](/install/npm). Detalhes:
  * Uma implementação bastante simples. Três caixas de seleção de opções que controlam quais de várias tabelas são exibidas. Um arquivo exibido por padrão com substituições de substituição que determinam qual tabela mostrar.
