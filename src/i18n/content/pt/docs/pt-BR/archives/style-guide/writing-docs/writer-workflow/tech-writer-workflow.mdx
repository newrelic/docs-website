## 0. Configurar seu ambiente local [#set-local]

É necessário configurar o ambiente local apenas uma vez. Caso isso já tenha sido feito, é possível pular esta etapa.

Acesse aqui para obter instruções detalhadas sobre como [configurar o ambiente de compilação local](/docs/style-guide/writing-docs/writer-workflow/set-up-local).

## 1. Crie uma branch e edite os documentos [#edit-doc]

No GitHub Desktop, serão exibidas três guias rotuladas como **Repositório atual**, **Branch atual** e **Buscar origem**. O branch padrão é **Develop**, portanto, é hora de criar um branch.

1. Deve-se clicar em **Current Branch** e selecionar **New Branch**.
2. Encontre um documento que deseja editar.
   * Utilize o Finder ou o Explorador de Arquivos com o caminho do arquivo. Por exemplo, se desejasse editar um documento do agente Python, seria necessário navegar para: `~/Documents/github/docs-website/src/content/docs/agents/python-agent/hosting-services/python-agent-stackato.mdx`
3. Recomenda-se [editar o documento](https://docs.newrelic.com/docs/style-guide/writing-docs/processes-procedures/create-edit-content) no editor de texto de preferência. Os documentos devem ser escritos com a [linguagem markdown](https://www.markdownguide.org/basic-syntax).
4. Salve o arquivo com as suas edições.

Consulte o restante do nosso [guia de estilo](https://docs.newrelic.com/docs/style-guide/writing-strategies/introduction-style-guide/) para esclarecer quaisquer dúvidas sobre as diretrizes de redação.

## 2. Faça o commit das suas alterações [#commit-changes]

Mesmo que as edições tenham sido salvas, ainda é necessário fazer um commit. Um commit pode ser considerado como um ponto de verificação no fluxo de trabalho. O processo de commit começa com a preparação e termina quando as alterações são enviadas para o GitHub.

1. Navegue de volta para o GitHub Desktop e verifique a coluna esquerda. No Github Desktop, a coluna esquerda mostra:

   * Um registro de todas as novas edições feitas em quaisquer documentos
   * Um botão azul que diz **Commit to \[your-branch-name]**

2. Nomear o commit e adicionar uma descrição.

3. Clique em **Commit to \[yourbranchname]**.
   * O nome e a descrição do commit podem ser algo como `feat(PythonAgent): Renamed the section heading`

## 3. Execute o site localmente [#run-site]

Compile o site localmente usando o terminal. Embora esta etapa seja opcional, é **altamente** recomendado compilar o site localmente e visualizar as alterações antes de abrir um pull request.

Só é necessário reconstruir o site local quando ele falha, não após cada salvamento ou commit.

1. No terminal, acesse o repositório clonado, **docs-website**. Por exemplo:
   * `cd ~/Documents/github/docs-website`
2. Execute o yarn com os seguintes comandos: `yarn && yarn start`
3. O site levará alguns minutos para ser compilado. Prepare um chá ou café.
4. Após a compilação, visualize o site no Browser acessando [http://localhost:8000/](http://localhost:8000/)

## 4. Publicar seus commits [#publish-commits]

Quando as alterações forem satisfatórias, envie os commits para o GitHub. Isso os torna disponíveis para todos os outros no repositório do GitHub.

1. No GitHub desktop, clique no botão azul **Publish Branch**, se disponível.
2. Caso não veja o Publish Branch, clique no botão azul **Push Origin**.

## 5. Abra o seu pull request [#open-pr]

Embora os seus commits possam ser vistos por todos, as suas edições não serão mescladas na `develop `branch até que outro redator as tenha revisado.

Para fazer isso, abra um pull request (PR):

1. No GitHub Desktop, clique no botão azul **Create pull request**.

2. Isso abrirá o GitHub no navegador e exibirá um prompt para preencher o pull request.

   * É necessário garantir que o merge seja feito da branch de origem para a branch `develop`.
   * Rolar para baixo para revisar todos os seus commits.

3. Assim como a descrição do commit, a descrição do pull request deve ser detalhada e fornecer o contexto completo das alterações.

   * É possível adicionar qualquer contexto adicional aqui (link da issue do GitHub ou ID da issue do Jira, SMEs, etc.).
   * Solicitar uma revisão de outro redator técnico abrindo o PR, navegando até a seção **Conversation** e inserindo o nome do revisor na seção **Reviewer**.

4. O rótulo `from_tw` e quaisquer outros [rótulos relevantes](/docs/style-guide/writer-workflow/github-intro) devem ser adicionados ao PR.
   * Se `from_tw` não for adicionado, o PR não será atribuído automaticamente a outro redator para revisão.

5. Assim que o PR estiver satisfatório, deve-se clicar no botão verde **Create pull request**.

6. É possível publicar as alterações diretamente ao aprovar o pull request por conta própria, ou solicitar que outro redator técnico faça a edição.

7. Na parte inferior da página do pull request, será exibida uma seção **Checks**. Essas verificações garantem que o PR não interrompa o processo de build do site. É necessário garantir que todas as verificações marcadas como `required` sejam aprovadas antes de fazer o merge.

8. Assim que o pull request passar pelas verificações e for aprovado por outro redator técnico (ou se houver certeza de que as alterações estão prontas para serem publicadas), clique no botão verde **Merge pull request**. Isso mesclará a ramificação e os commits no repositório e iniciará o processo de compilação.

<Callout variant="important">
  Se o rótulo `from_tw` não for adicionado ao criar um PR pela primeira vez, um revisor não será atribuído automaticamente. Caso o rótulo não seja adicionado antes de abrir o PR:

  1. Adicionar o rótulo `from_tw`.
  2. Transformar o PR em um PR de rascunho.
  3. Selecione o `PR is ready for review button` na parte inferior da página para reabrir o PR. O PR agora deve ter um revisor.
</Callout>

## Pré-visualizar um documento [#preview-doc]

Existem duas maneiras principais de visualizar branches que já foram publicadas e nas quais foram executados commits:

* **Local**: mais rápido, mas requer uma quantidade semissubstancial de configuração e familiaridade com um terminal.
* **Netlify Cloud**: visualização completa do site ativo sem sobrecarga e uma maneira muito conveniente de compartilhar uma visualização do seu rascunho com um SME. O Netlify Cloud comentará no seu PR com um link para uma versão de visualização do site assim que a compilação estiver pronta. A compilação do site geralmente leva cerca de 15 minutos, mas às vezes pode demorar mais se houver muitas alterações.

## Revisar e publicar um documento [#revise-doc]

Caso haja uma notificação de que um revisor enviou uma revisão para o arquivo, deve-se acessar o PR e revisar as alterações. É possível vê-las na visão de diferenças, caso façam parte de uma revisão com comentários; caso contrário, podem aparecer como edições de texto no arquivo.

1. Responda a quaisquer comentários no arquivo. Responda com uma discussão de acompanhamento ou clique em **Resolve conversation**.
2. Quando todos os comentários estiverem resolvidos e todas as verificações automáticas forem aprovadas, será possível mesclar o pull request. Mesclar o pull request inicia o processo automatizado de build e as alterações serão publicadas em breve.

<Callout variant="tip">
  Só será possível mesclar quando o botão **Merge pull request** estiver verde. Se não estiver verde, verifique se há comentários que passaram despercebidos ou outras mensagens que indiquem por que o GitHub está bloqueando a mesclagem.
</Callout>

## Reverter o merge [#revert]

É importante lembrar que quase sempre é possível desfazer as ações. Se o merge de um PR for feito e depois for descoberto que não deveria ter sido feito, é possível desfazer o merge com o botão **Revert**.

1. Na guia de pull request no GitHub, clique em **Closed** na barra de contagem para ver todos os problemas e PRs que já foram mesclados.
2. Localize o PR que foi mesclado e localize o botão Revert.
3. Clique em Reverter. Isso cria um novo PR, que precisa ser mesclado. Se desejar reabri-lo, é necessário seguir o link de volta ao PR original e revertê-lo ou reabri-lo.

## Somente redatores: trabalhe em uma branch, não em um fork [#branch-fork]

Algumas equipes trabalham em branches, outras trabalham em forks; **a equipe de Docs trabalha em branches**. Desde que uma branch tenha sido enviada para o upstream, isso permite trabalhar de forma colaborativa e garantir que nenhum trabalho seja perdido quando alguém sair de férias.

Para criar um branch no repositório docs-website:

1. Abrir o GitHub Desktop
2. Clicar em **Current branch: xxx**
3. Clicar em **New Branch**
4. Será exibido um prompt para nomear a nova branch. Nomes descritivos são melhores. É uma excelente maneira de informar rapidamente as pessoas sobre o objetivo do trabalho. Por exemplo, ao trabalhar nas páginas What&apos;s New, a ramificação pode ser nomeada como **Whats-new-updates**.

Ao criar uma nova ramificação, não se esqueça de adicionar o ID do problema do Jira (DOC-1234) ao nome da ramificação e ao título do PR.

## Uma observação sobre as permissões do GitHub [#permissions]

Os redatores da equipe de documentação trabalham em branches, mas os colaboradores de fora da equipe de documentação usam forks. Isso também significa que colaboradores que não são da equipe de documentação não podem editar o conteúdo em uma branch diretamente, o que pode dificultar a colaboração.

As permissões do GitHub são usadas para determinar quem pode trabalhar em um branch e quem pode trabalhar em um fork. No GitHub, o acesso é determinado pelas funções da equipe e dos membros. Embora qualquer pessoa possa contribuir para o nosso repositório público, o acesso adicional é concedido por meio das funções `Write` e `Admin`. (Existem outras funções definidas que não são usadas com frequência.)

Cada membro da equipe de Docs recebe a função `Admin`, que concede acesso total ao repositório. Outros colaboradores da New Relic recebem a função `Write`, que permite atribuir usuário e abrir e fechar pull request.

Para revisar as configurações de acesso atuais, acesse o repositório `docs-website` e, em seguida, vá para **Settings &gt; Collaborators and teams** ou **Team and member roles**.
