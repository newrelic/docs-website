Sempre que possível, devem-se incluir hiperlinks onde for relevante no próprio texto. Deve-se evitar a criação de listas de links de documentos na seção **For more help**, pois é mais difícil para os futuros redatores determinarem por que eles são importantes.

<Callout variant="tip">
  Se estiver vinculando ao produto, consulte a página do guia de estilo sobre [caminhos da interface](/docs/style-guide/quick-reference/ui-paths).
</Callout>

## Sintaxe de link [#link-syntax]

O site de documentação usa a sintaxe de link inline do Markdown:

```markdown
[link text](https://example.com)
```

Ao criar um link para outra página no site de documentação, recomenda-se usar links &quot;relativos&quot; (omitindo o URL raiz `https://docs.newrelic.com` do site de documentação):

```markdown
[link text](/docs/category-path/doc-path/)
```

<Callout variant="tip">
  O Markdown [também suporta links no estilo &quot;referência&quot;](https://daringfireball.net/projects/markdown/syntax#link), em que o URL de destino é listado no final do documento. Embora funcionem e sejam renderizados corretamente, evitamos usar este estilo de link por alguns motivos:

  * É um estilo menos comum e pode ser confuso para os colaboradores.
  * Nossos documentos são muito longos, o que pode tornar a conexão de um link ao seu destino difícil para os colaboradores.
</Callout>

## Vincular texto [#hyperlinks-linktext]

Siga estas diretrizes ao escrever texto para hiperlinks:

* **Rótulos:** certifique-se de que cada link no documento tenha um rótulo de texto exclusivo e significativo. Não use a mesma sequência de texto para rotular links diferentes.
* **Localização:** incluir um rótulo de texto claro e conciso para identificar para onde o link direciona. Deve-se fornecer contexto adicional ao criar um link para um site externo. Por que enviar alguém para lá?
* **Click here:** Não se deve usar &quot;click here&quot; ou outros rótulos de link sem sentido.
* **&quot;Teste de link:&quot;** Leia apenas os links, sem o texto ao redor. Cada um pode funcionar de forma independente como uma descrição clara de para onde o link direciona, se isso for tudo o que o usuário visualizar na página?
* **Evitar prefixos de URL:** ao enviar o usuário para um endereço no qual se deseja usar o URL como vincular texto, remover os prefixos `https:` e `www.` do vincular texto. Por exemplo, `[github.com](https://github.com)` não `[https://github.com/](https://github.com)`. Ou `[github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)` não `[https://github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)`.

Recomenda-se realizar o teste de link para estes três exemplos. O último é o melhor para os leitores que buscam informações sobre a configuração do PHP, pois o link o identifica claramente, sem a necessidade de ler mais nada na página.

## Links de suporte [#support-link]

**Nunca se deve incluir um hiperlink para o endereço de e-mail do Suporte.** Isso evita spam e garante que os clientes usem o formulário de envio de ticket para criar ticket, para que recebam a prioridade de suporte correta. Se for necessário orientar os clientes a entrarem em contato com o suporte, use o seguinte:

```md
Get support at [support.newrelic.com](support.newrelic.com).
```

## Links âncora [#hyperlinks-anchor]

Caso o link inclua uma âncora (por exemplo, `#inivar-scope`), deve-se usar o caminho completo e **atual** do documento que ele utiliza. Alguns navegadores não retêm âncoras com redirecionamentos.

Ao criar ou editar um `id` HTML para um link âncora, siga estas diretrizes:

* Usar apenas letras minúsculas ao criar novos IDs.
* Use hifens `-` para separar as palavras. Não use `_` sublinhados.
* Ao reorganizar um documento, deve-se tentar preservar os links de âncora de entrada sempre que possível. Deve-se ter em mente que, ao excluir um título de nível dois `##`, quaisquer links para esse título serão quebrados.
* Deve-se evitar a alteração de um ID de âncora existente, pois o monitoramento do tráfego para ele pode estar sendo realizado a partir da conta interna da New Relic.

## Links profundos para o produto [#deep-links]

Ao direcionar os usuários para partes do produto, deve-se usar links profundos sempre que possível. O uso de links profundos incentiva os usuários a acessarem o produto e, se ainda não tiverem criado uma conta, exibe um prompt para que se inscrevam. Isso é mais eficaz do que apenas vincular a uma página de inscrição. No entanto, o uso de links profundos para a interface funciona apenas algumas vezes e requer alguma experimentação para encontrar um bom link permanente.

Aqui está um exemplo de fluxo de trabalho usando a interface de Logs:

1. A partir da conta de trabalho, deve-se acessar a parte da interface que se deseja vincular. Deve-se copiar o URL completo conforme ele aparece naturalmente.
2. Abra uma janela anônima e cole a URL.
3. Edite a URL para um estado mais limpo. Desejamos URLs simples quando possível. Para logs, o aspecto é o seguinte: `https://one.newrelic.com/logger`.
4. O New Relic exibirá um prompt para iniciar a sessão, portanto, inicie a sessão com um e-mail não corporativo.

A URL direciona para a página de logs e preenche automaticamente as informações de identificação do ID da conta. Essa página permite links diretos.

Se o URL simples não funcionar, há duas etapas extras. Aqui está um exemplo de fluxo de trabalho em que o URL simples não funciona. Este URL será usado como base:

```
https://one.newrelic.com/marketplace/install-data-source?account=[ACCOUNT_ID_HERE]&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
```

1. Após encontrar a URL, deve-se abrir uma janela anônima e colar a URL simples: `https://one.newrelic.com/marketplace/install-data-source`Esta página não carrega com a URL simplificada.

2. Este URL pode ser testado removendo a parte `account=[ACCOUNT_ID_HERE]` do slug. O novo URL ficará assim:

   ```
   https://one.newrelic.com/marketplace/install-data-source?&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
   ```

3. Cole esse URL em uma nova janela anônima. Isso direcionará para a página correta com o ID de conta exclusivo preenchido.

4. Confirme com outro redator se este URL funciona, pedindo que ele abra o URL com o número de ID da conta removido. Eles devem usar um e-mail não corporativo.

Se o URL falhar em qualquer um dos casos, é provável que essa parte da interface do produto não suporte links diretos. Nesse caso, vincule `one.newrelic.com` à página **All capabilities** e, em seguida, descreva o caminho de acordo com [nossas diretrizes de caminho](/docs/style-guide/formatting/ui-paths).

## Links externos [#hyperlinks-external]

Ao criar links para sites fora do subdomínio `docs.newrelic.com` (incluindo `newrelic.com`, `one.newrelic.com`, `discuss.newrelic.com`), o site de documentação inclui automaticamente um código que abre o link em uma nova guia.

Além das diretrizes de vincular texto neste documento, aqui estão outras coisas a ter em mente ao criar links para sites externos:

* Considere a melhor maneira de preparar os links para o futuro. Se possível, aponte para um domínio de nível superior, mas não se isso reduzir a utilidade do link. Quão estável é o conteúdo ao qual o link aponta? É provável que o URL mude?
* Certifique-se de que o link seja o mais útil possível. Qual valor se deseja adicionar ao documento? Essa informação pode ser compartilhada de outra maneira?
* Ajude o leitor a entender o motivo de incluir um link para esta fonte externa. É uma referência útil, como uma lista de fusos horários? É uma maneira de economizar o tempo de alguém, como criar um link direto para um arquivo difícil de encontrar?
* É necessário garantir que o link seja geralmente acessível. O link direciona para um site externo que requer autenticação, como um repositório privado do GitHub?
