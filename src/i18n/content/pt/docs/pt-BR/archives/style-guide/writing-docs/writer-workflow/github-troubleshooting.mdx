Há problemas ao [trabalhar em um documento no GitHub](/docs/style-guide/writer-workflow/tech-writer-workflow/)? Consulte os seguintes problemas comuns.

## O build local gera erro 404 [#build-fails]

### Problema

Ao tentar compilar o localhost:8000, uma ou todas as páginas da web apresentam um erro 404.

### Soluções

Tentar algumas destas soluções para descobrir o que deu errado na compilação local.

<CollapserGroup>
  <Collapser className="freq-link" id="troubleshoot-file" title="Solucione os problemas do arquivo problemático">
    Se souber qual arquivo está causando um erro, execute este comando para identificar o erro:

    ```bash
    yarn verify-mdx path/to/file.mdx
    ```

    Este comando retorna mais informações sobre o erro do que a saída normal do Gatsby, como o caractere específico e o número da linha que está causando o erro.

    <CollapserGroup>
      <Collapser className="freq-link" id="example" title="Exemplo">
        Suponha que foram feitas alterações em vários documentos na ramificação. Ao tentar executar o site localmente ou acessar a compilação do Netlify, ocorre o seguinte erro:

        ```
        Unexpected character = (U+003D) before name, expected a character that can start a name, such as a letter, $, or _/usr/src/app/www/src/content/docs/new-relic-solutions/observability-maturity/uptime-performance-reliability/aqm-implementation-guide.mdx: Unexpected character = (U+003D) before name, expected a character that can start a name, such as a letter, $, or _
        ```

        O erro informa que o documento com erro está em `/docs/new-relic-solutions/observability-maturity/uptime-performance-reliability/aqm-implementation-guide.mdx`. Além disso, tudo o que sei é que há um caractere `=` atrapalhando as coisas em algum lugar. Legal, mas este é um documento NRQL, há dezenas de caracteres `=`.

        Então, eu executo `yarn verify-mdx src/content/docs/new-relic-solutions/observability-maturity/uptime-performance-reliability/aqm-implementation-guide.mdx`. Isso retorna o seguinte:

        ```json

        "ruleId": "unexpected-character",
        ```

  <Collapser className="freq-link" id="" title="Verifique se há erros comuns de sintaxe">
    Verifique os arquivos alterados em busca de alguns destes erros comuns de sintaxe markdown:

    * Indentação inconsistente dos arquivos nav

    * Sintaxe incorreta do front matter
      * Se houver apóstrofos e dois-pontos nos campos do frontmatter, coloque-os entre aspas para evitar problemas.

    * Faltam colchetes ou tags de fechamento

    * Links de imagem mal formatados

      * Deve-se garantir que haja uma nova linha entre cada instrução de importação de imagem.
      * Tenha cuidado ao renomear imagens e seus caminhos de nome de arquivo. Uma incompatibilidade pode fazer com que toda a compilação local falhe.
      * Deve-se ter cuidado especial ao lidar com arquivos de imagem que são importados.

    * Nomes de arquivos de imagem incorretos

      * Os nomes de arquivos de imagem diferenciam maiúsculas de minúsculas. O uso da capitalização incorreta resulta em uma imagem ausente no documento.
      * Imagens com valores codificados (como %) no nome do arquivo podem ser especialmente complicadas, portanto, recomenda-se evitá-las.
  </Collapser>

  <Collapser className="freq-link" id="restart-yarn" title="Parar e reiniciar o yarn">
    Para parar e reiniciar o yarn:

    1. No terminal, certifique-se de estar no diretório `/docs-website`.
    2. Deve-se pressionar CONTROL+C para interromper o processo do yarn (se um terminal estiver ativo).
    3. Executar este comando para interromper todos os serviços em execução em localhost:8000:
       ```bash
       kill -9 $(lsof -i TCP:8000 | grep LISTEN | awk '{print $2}')
       ```
    4. Execute este comando para reiniciar o yarn:
       ```bash
       yarn clean && yarn && yarn start 
       ```
  </Collapser>

  <Collapser className="freq-link" id="check-branch" title="Identifique a branch problemática">
    Para identificar qual branch está causando problemas:

    1. No terminal, certifique-se de estar no diretório `docs-website`.
    2. Pressione CONTROL+C para interromper o processo do yarn, se necessário.
    3. No GitHub Desktop, faça o commit de quaisquer alterações necessárias na branch e, em seguida, alterne para a branch develop.
    4. De volta ao terminal, execute `yarn && yarn start`.

    Se o site agora for compilado corretamente a partir da ramificação develop, o problema está nas alterações da respectiva ramificação. Parar o Yarn novamente, voltar à respectiva ramificação e solucionar o problema.
  </Collapser>

  <Collapser className="freq-link" id="clean-cache" title="Limpar o cache local">
    Executar `yarn clean` para limpar o cache local. Isso tornará a próxima compilação mais lenta, portanto, é necessário certificar-se de ter tempo!

    1. No terminal, certifique-se de estar no diretório docs-website.
    2. Pode-se pressionar CONTROL + C para parar o yarn, se necessário.
    3. Inicie uma nova compilação executando `yarn clean && yarn && yarn start`.
  </Collapser>

  <Collapser className="freq-link" id="remove-cache" title="Remover arquivos de cache corrompidos">
    Pode haver momentos em que o diretório .cache tenha sido corrompido. Esse diretório é ignorado pelo Git, o que significa que ele transita de branch em branch. Esse pode ser o problema se as compilações locais estiverem falhando, independentemente da branch atual.

    Para resolver isso a partir do diretório `/docs-website`, execute `rm -rf .cache`.
  </Collapser>

  <Collapser className="freq-link" id="start-build" title="Iniciar uma compilação do zero">
    Iniciar uma compilação do zero apagará todos os módulos do Node, a pasta .cache oculta e o cache local. Isso leva muito tempo para ser executado, cerca de 10–20 minutos.

    1. No terminal, certifique-se de estar no diretório docs-website.

    2. Pode-se pressionar CONTROL + C para parar o yarn, se necessário.

    3. Deve-se executar `yarn reboot` (ou usar o comando do Keyboard Maestro `kknuke`\*).

       \*Se o comando `kknuke` do Keyboard Maestro for usado, quando tudo for concluído, inicie o site executando `yarn start`.
  </Collapser>

  <Collapser className="freq-link" id="run-incognito" title="Execute a build local em modo privado">
    Às vezes, o site local é compilado, mas as páginas dentro do site não. Para corrigir esse problema, tente executar a compilação local em uma sessão privada ou anônima. Também é possível tentar limpar o cache do navegador.
  </Collapser>
</CollapserGroup>

## Falha nas verificações de compilação obrigatórias [#check-fail]

### Problema

Ao criar um PR, uma das verificações `required` não é aprovada.

<Callout variant="tip" title="Observação">
  Se uma verificação opcional falhar, é aceitável fazer o merge do PR, uma vez que verificações opcionais não bloqueiam os lançamentos. No entanto, caso se deseje investigar a verificação mais a fundo, pode-se enviar uma mensagem no canal de ajuda para que o hero possa analisar a falha.
</Callout>

### Solução

Se uma verificação estiver falhando, primeiro tente fechar e reabrir o PR.

Em seguida, executar novamente as verificações:

1. Acesse o PR.
2. Clique em **Details &gt; Re-run jobs**.

Caso isso não funcione, será necessário redefinir as verificações, o que forçará uma reconstrução do cache:

1. No repositório local, encontrar o arquivo `gatsby-config.js` (ou usar CMD-P para acessá-lo rapidamente no VSCode).

2. Deve-se inverter a primeira e a segunda linha de código (não importa a ordem em que essas linhas estão, exceto para fazer com que a verificação do Gatsby Build reconstrua o cache):

   ```js
   const fs = require('fs');
   const parse = require('rehype-parse');
   ```

3. Salvar o arquivo e fazer o commit da alteração no PR.

4. Execute novamente as verificações de build.

5. É necessário aguardar MUITO tempo.

## Conflitos de merge de PR [#merge-conflict]

### Problema

Ao tentar fazer o merge de um PR a partir da branch local, ocorre um conflito de merge.

### Solução

Caso ocorra um conflito de mesclagem, deve-se clicar em **Resolve conflict** no GitHub Desktop ou no navegador e revisar os conflitos linha por linha. É necessário garantir que o aprovador revise o PR após a correção do conflito de mesclagem.

#### Evitar conflitos de mesclagem

A seguir, algumas recomendações para evitar conflitos de mesclagem:

* Antes de fazer o merge para a develop ou main, clique em **Fetch origin** para garantir que a versão mais atualizada da develop ou main seja baixada.
* Se estiver trabalhando em alterações de taxonomia, corrija o conflito de mesclagem o mais rápido possível. Se a ramificação permanecer por um tempo, ela pode ficar desatualizada em relação à develop muito rápido e isso pode causar alguns problemas inesperados.
* Se houver um conflito de mesclagem nas postagens de novidades, é porque o arquivo `whats-new-ids.json` (que é atualizado automaticamente quando o site é compilado) pode ficar desatualizado muito rápido. <Callout variant="caution">Nunca se deve mesclar um PR que altere `whats-new-ids.json`. Se alterações no arquivo `whats-new-ids.json` aparecerem no GitHub Desktop, é necessário descartá-las em vez de enviá-las para a ramificação. Isso tornará menos provável que outras pessoas tenham que lidar com conflitos de mesclagem relacionados a este arquivo.</Callout>

## A porta 8000 está indisponível [#local-site]

### Problema

Ao tentar executar `yarn start`, o terminal responde:

```bash
[output] Something is already
[output] running at port 8000. Would you like to run the app at another port instead?
```

### Solução

Para interromper todos os serviços em execução em localhost:8000, execute este comando no terminal:

```bash
kill -9 $(lsof -i TCP:8000 | grep LISTEN | awk '{print $2}')
```

## O link de redirecionamento retorna erro 404 [#redirect-404]

### Problema

Ao clicar em um link de redirecionamento na compilação local, ocorre um erro 404.

### Solução

Os redirecionamentos demoram muito tempo para carregar em uma compilação local. Ao clicar em um redirecionamento, é necessário aguardar até que ele retorne um erro 404 e, em seguida, aguardar cerca de 1–2 minutos. O redirecionamento deve ocorrer após algum tempo. Caso isso não ocorra, é necessário verificar a sintaxe markdown para garantir que o redirecionamento foi configurado corretamente.

Também é possível testar os redirecionamentos no build do Gatsby.

## Falha na autenticação SSH [#authentication-fail]

### Problema

Ao tentar enviar commits para a branch remota, ocorre um erro de autenticação SSH.

### Solução

Às vezes, fazer login/logout no Github Desktop pode corrigir um problema de autenticação:

1. Na barra de menus superior, acesse **Preferências**.
2. É necessário sair e entrar novamente.

Se isso não funcionar, recomenda-se fazer o push dos commits para a branch remota. Se ainda assim falhar, recomenda-se fazer o push manual do PR usando o terminal. Por exemplo, para fazer o push do PR `second-kafka-pr-for-issue-11231`, deve-se executar este comando:

```bash
git push --set-upstream origin second-kafka-pr-for-issue-1123
```

Se houver um problema de SSH, o terminal retornará uma mensagem de erro de autenticação. Se a resposta a este comando exibir um prompt solicitando uma frase secreta, o SSH ficou confuso de alguma forma. Ao inserir a frase secreta, tudo deve voltar a funcionar. Caso não seja possível lembrar a frase secreta, [confira este artigo](https://docs.github.com/en/github/authenticating-to-github/troubleshooting-ssh/recovering-your-ssh-key-passphrase).
