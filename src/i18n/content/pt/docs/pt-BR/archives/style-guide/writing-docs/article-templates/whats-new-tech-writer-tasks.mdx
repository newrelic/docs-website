Os redatores técnicos desempenham um papel importante na publicação de postagens de &quot;O Que Há de Novo&quot;. Embora nossos colaboradores sigam as [Instruções Para Criar Postagens de O Que Há de Novo](/docs/style-guide/writing-docs/article-templates/whats-new-template/), devem ser seguidas algumas etapas adicionais para ajudar os colaboradores a finalizar o trabalho deles.

## Uma visão geral do processo [#overall-process]

Uma visão geral do processo de `What's new` é a seguinte:

1. Qualquer pessoa na empresa pode enviar um pull request (PR) `What's new` para o site de documentação.
2. Vários gerentes de marketing de produto estão em rotação para revisar as postagens e fazer sugestões.
3. Quando o gerente de marketing de produto termina de revisar a postagem, ele insere um comentário de PR solicitando que a equipe de documentação técnica faça outra revisão.
4. O redator técnico conclui a revisão e publica a postagem, ou insere um comentário no PR confirmando que ela está pronta para ser publicada em uma determinada data e janela de tempo.

## Tarefas específicas de redator técnico para publicações [#specific-writing-tasks]

O herói diário tem as seguintes responsabilidades a cada dia:

* **Mesclar postagens agendadas:** verifique a coluna `Scheduled work` no quadro do Github em busca de quaisquer postagens `What's new` que já tenham sido aprovadas e estejam agendadas para mesclagem naquele dia. Por exemplo, se o hero de segunda-feira revisou e aprovou uma postagem agendada para ir ao ar no turno de hero de quarta-feira, esse PR deve ser mesclado.
* **Revisar quaisquer publicações recebidas:** quaisquer publicações `What's new` que chegarem devem ser revisadas e aprovadas durante o turno de herói. Isso inclui edições básicas de texto, garantir a formatação correta da imagem e confirmar uma compilação de visualização bem-sucedida. Editar o título para o dia em que deve ser publicado e, em seguida, mover o PR para a coluna `Scheduled work`. Ao revisar os PRs à medida que chegam, garante-se um lançamento tranquilo assim que estiverem prontos para a mesclagem.

Consulte o restante do documento para instruções mais detalhadas.

<Callout variant="tip">
  Antes de iniciar a revisão de redação, certifique-se de que ela foi revisada por um gerente de marketing de produto se a postagem for de fora desse departamento. Por exemplo, se um desenvolvedor ou gerente de produto enviar uma postagem, ela deverá ser revisada primeiro por um gerente de marketing de produto (qualquer pessoa listada no [arquivo CODEOWNERS](.github/CODEOWNERS)). Depois que um gerente de marketing de produto revisar a postagem e repassá-la ao hero, certifique-se de concluir as etapas nas seções abaixo.
</Callout>

### Gerenciar painel do GitHub [#the-board]

1. No quadro de projetos do GitHub, a postagem deve ser movida da coluna de triagem para a coluna **Scheduled work**. A postagem permanecerá lá até que seja efetivamente publicada.
2. Insira a data de publicação e a janela de tempo no título do PR para que seja fácil de reconhecer. Nossas [instruções](/docs/style-guide/writing-docs/article-templates/whats-new-template/) informam aos colaboradores que oferecemos estas janelas de publicação: manhã, meio-dia ou noite. Pode ser necessário perguntar se desejam que isso seja publicado mais cedo para garantir que esteja disponível a tempo.

### Revisar a postagem [#the-review]

1. Revise o documento usando as regras principais do nosso guia de estilo. Caso sejam encontrados problemas graves, trabalhe com o colaborador (ou com o revisor de marketing de produto); caso contrário, as alterações podem ser feitas diretamente.

2. Confirme se os URLs para o site de documentação são absolutos. Os caminhos relativos não são resolvidos na interface do produto, e é por isso que é necessário usar caminhos absolutos nas postagens.

   ```md
   * Absolute path (GOOD): [**Billing user role**](https://docs.newrelic.com/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#roles)
   * Relative path (BAD): [**Billing user role**](/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#roles)
   ```

3. Se a postagem fizer referência a alguma imagem, é necessário certificar-se de que não sejam links para imagens hospedadas em outros sites. Os arquivos de imagens devem residir em nosso repositório.

4. Verificar se a postagem possui o `isFeatured: true` no front matter. Se sim, isso significa que a postagem será fixada na parte superior da interface do produto. Deve-se remover o sinalizador correspondente na postagem em destaque anterior para que apenas uma postagem fique em destaque.

<Callout variant="tip">
  Caso não seja possível concluir a revisão de uma postagem &quot;What&apos;s new&quot; durante o turno de herói, por gentileza, alerte o herói que assumirá o próximo turno para que ele possa concluí-la.
</Callout>

### Publicar a postagem [#publish-the-post]

<Callout variant="caution">
  Antes de criar e mesclar a segunda ramificação para `main`, é necessário garantir que a [ação do GitHub que gera o ID](https://github.com/newrelic/docs-website/actions/workflows/update-whats-new-ids.yml) seja concluída.
</Callout>

Há duas mesclagens para `main` envolvidas na publicação de uma postagem &quot;What&apos;s new?&quot;.

1. Crie a ramificação de lançamento diário e mescle-a com `main` como faria normalmente.
2. Após a mesclagem para `main`, deve-se criar uma segunda ramificação de lançamento com base em `develop`. Essa segunda ramificação conterá o ID de &apos;O que há de novo?&apos;.
3. Mescle esta segunda ramificação para `main`. Este segundo merge exibe a postagem &apos;What&apos;s new?&apos; na interface. (Para os curiosos: a segunda ramificação contém um ID &apos;Whats new?&apos; que conecta a postagem do nosso site de documentos à interface. O segundo merge é responsável pelo segundo local.)
4. É necessário acompanhar e confirmar que a postagem é exibida na interface, bem como no site de documentação.

### Planejar postagens futuras [#future-posts]

Para posts a serem publicados no futuro:

* Geralmente, o herói de plantão assume a responsabilidade pela postagem no dia em que ela precisa ser publicada.
* Se uma postagem precisar ser publicada antes do horário típico das 8 ou 9 horas (horário do Pacífico dos EUA), o responsável que trabalhou nisso inicialmente deve providenciar a sua publicação.
* Em alguns casos, como em lançamentos específicos de alta visibilidade, um redator técnico pode assumir a propriedade da postagem atribuindo-se ao PR para que todos possam ver que o hero não é responsável por essa postagem.
