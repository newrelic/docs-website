Esta página é para notas de versão de software para download. Para anúncios de produtos, consulte as [Diretrizes de Estilo de Novidades](/docs/style-guide/article-templates/whats-new-style-guidelines/).

## Nova nota de versão [#new-note]

Para adicionar uma nota de versão ao site de documentação:

1. Localize a nota de versão mais recente do agente e faça uma cópia dela na mesma pasta.
2. Ao renomear a cópia, recomenda-se evitar possíveis conflitos de nomenclatura de versão utilizando um separador `-` no nome do arquivo. Por exemplo, em vez de `agent-123`, recomenda-se utilizar `agent-1-2-3` para a versão 1.2.3 e `agent-12-3` para a versão 12.3.
3. Preencha `subject`, `releaseDate` e `version`. Se aplicável, inclua o campo `downloadLink`. Certifique-se de que o campo `subject` corresponda às outras notas de versão na série que está sendo atualizada, pois diferenças de maiúsculas e minúsculas podem causar problemas com o agrupamento na navegação à esquerda.
4. Ao usar nossos cabeçalhos padrão para `New features`, `Improvements` e `Bug fixes`, deve-se adicionar informações de resumo suficientes nessas seções para [criar uma excelente nota de versão](/docs/style-guide/article-templates/create-release-notes/#guidelines). Deve-se incluir links para a documentação ou outros recursos onde seja possível aprender mais.
5. Fazer o commit das alterações e enviar um pull request. Se a versão for sensível à data, adicionar uma observação no PR.

Um herói do Tech Docs revisará o conteúdo das notas de versão e aprovará o PR para que seja publicado. Também é possível solicitar que outros membros da equipe revisem o PR.

O site de documentação é compilado e lançado algumas vezes ao dia, e às vezes as compilações podem levar algumas horas para serem concluídas. Caso o lançamento tenha prazo restrito, é necessário planejar tempo suficiente para a publicação dos documentos.

## O que torna uma nota de versão excelente? [#guidelines]

Ótimas notas de lançamento ajudam os usuários a se familiarizarem rapidamente com a atualização importante, para que saibam por que ela é relevante. Ótimas notas de lançamento também ajudam as equipes de suporte e segurança.

Ao incentivar os usuários a se manterem atualizados com o lançamento mais recente, o tempo de suporte para resolver problemas em versões desatualizadas é reduzido. Isso também mitiga riscos se quaisquer vulnerabilidades potenciais tiverem sido resolvidas com a versão mais recente.

Para escrever uma excelente nota de lançamento, deve-se ser o mais específico possível. Por exemplo:

* Deve-se descrever brevemente a nova funcionalidade. Deve-se dar um exemplo do valor que ela fornece e criar um link para informações mais detalhadas.
* Não utilizar termos vagos como &quot;várias correções de bugs.&quot; Em vez disso, indicar claramente o que foi melhorado, para que os leitores saibam se um problema que enfrentaram foi resolvido.

## Nova categoria de notas de versão [#new-category]

Esta informação destina-se principalmente ao uso da equipe de Tech Docs.

Para adicionar uma nova categoria de notas de versão, devem-se atualizar as seguintes áreas do site de documentação. (Não é necessário atualizar os arquivos `releaseNote.js` ou `releaseNoteLandingPage.js` na pasta `nav/templates`.) Antes de enviar o pull request para o site de documentação do GitHub, deve-se verificar se as páginas de destino e a nota de versão de espaço reservado são compiladas corretamente no localhost.

### Página de destino da categoria

Em `/src/content/docs/release-notes`, adicione o seguinte:

* Uma pasta para a nova categoria de notas de versão. O link do feed RSS, o formato da página e a ordem das datas para as notas de versão listadas nesta página são gerados automaticamente. Por exemplo, consulte o [formato da página de destino da categoria Go](/docs/release-notes/agent-release-notes/go-release-notes/).
* Um arquivo `index.mdx` em sua nova pasta contendo o `subject`. O `subject` é o nome que aparecerá na [página de destino das notas de versão](/docs/release-notes/).
* Uma [nota de versão de espaço reservado](/docs/style-guide/article-templates/create-release-notes/#new-note) nesta pasta para a equipe do agente preencher. Se utilizado, o campo `downloadLink` na nota de versão será formatado automaticamente na nota de versão publicada.

Antes de a nova categoria entrar no ar, verificar com o representante de Product Marketing Management (PMM) da equipe se há o desejo de incluir o link em uma próxima [postagem de novidades](/docs/style-guide/article-templates/whats-new-style-guidelines/).

### Página de destino

Em `/src/content/docs/release-notes/index.mdx`, adicione uma nova seção de bloco em ordem alfabética para a sua categoria de notas de versão.

Exemplo:

```jsx
<TechTile
  name="Logs"
  icon="logo-newrelic"
  to="/docs/release-notes/logs-release-notes"
/>
```

Os logotipos vêm de `@newrelic/gatsby-theme-newrelic/icons/logo/`. Se um logotipo ainda não existir para o novo agente, use o ícone padrão `logo-newrelic` ou uma imagem em `@newrelic/gatsby-theme-newrelic/icons/feathers.js`. Se precisar de outras opções, fale com o designer da equipe.

### Links de outras categorias

Adicione um link para a nova categoria de notas de versão na documentação do agente, normalmente em sua categoria `Get started`. Para obter mais informações, consulte nossa documentação sobre [documentos em vários menus](/docs/style-guide/processes-procedures/include-a-doc-in-multiple-menus/).

Opcional: adicionar um link no texto da página de destino do agente atualizando o arquivo `index.mdx` em sua taxonomia.
