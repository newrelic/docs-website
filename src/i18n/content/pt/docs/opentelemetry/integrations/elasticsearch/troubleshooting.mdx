Se você concluiu a [instalação da integração do Elasticsearch com OpenTelemetry](/docs/opentelemetry/integrations/elasticsearch/elasticsearch-otel-integration-install) ou a [instalação no Kubernetes](/docs/opentelemetry/integrations/elasticsearch/elasticsearch-otel-integration-k8-install) mas não vê dados no New Relic, encontre seu problema abaixo e siga as etapas de solução.

## Implantações baseadas em host [#host-troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-collector-stopped" title="O serviço do Collector parou ou falhou">
    <strong>Como verificar</strong>

    ```bash
    sudo systemctl status otelcol-contrib
    ```

    <strong>Resolução</strong>

    * Se o serviço estiver inativo, inicie-o:
      <InlineCode>
        sudo systemctl start otelcol-contrib
      </InlineCode>
    * Se o serviço falhou, corrija os erros de configuração e reinicie:
      <InlineCode>
        sudo systemctl restart otelcol-contrib
      </InlineCode>
  </Collapser>

  <Collapser id="troubleshoot-collector-logs-errors" title="Logs do Coletor relatam erros de scraping ou exportação">
    <strong>Como verificar</strong>

    ```bash
    sudo journalctl -u otelcol-contrib.service -f
    ```

    <strong>Resolução</strong>

    Analise a saída do log e resolva a causa raiz (por exemplo, problemas de conexão, falhas de autenticação ou problemas de permissão).
  </Collapser>

  <Collapser id="troubleshoot-connection-refused" title="Conexão recusada ao chamar o Elasticsearch">
    <strong>Amostra de erro</strong>: <InlineCode>
      dial tcp \[::1]:9200: connect: connection refused
    </InlineCode>

    <strong>Resolução</strong>

    * Certifique-se de que o
      <InlineCode>
        endpoint
      </InlineCode>
      em
      <InlineCode>
        config.yaml
      </InlineCode>
      corresponda ao host e à porta do Elasticsearch.
    * Confirme se o Elasticsearch está em execução e acessível a partir do host do coletor.
  </Collapser>

  <Collapser id="troubleshoot-403" title="403 Forbidden ao exportar para o New Relic">
    <strong>Amostra de erro</strong>: <InlineCode>
      permanent error: 403 Forbidden
    </InlineCode>

    <strong>Resolução</strong>

    1. Verifique <InlineCode>
         NEWRELIC\_LICENSE\_KEY
       </InlineCode> em <InlineCode>
         /etc/systemd/system/otelcol-contrib.service.d/environment.conf
       </InlineCode>.

    2. Recarregue o systemd e reinicie o coletor:

       ```bash
       sudo systemctl daemon-reload
       sudo systemctl restart otelcol-contrib
       ```
  </Collapser>

  <Collapser id="troubleshoot-permission-denied" title="Permissão negada ao coletar logs">
    <strong>Amostra de erro</strong>: <InlineCode>
      permission denied
    </InlineCode> ou <InlineCode>
      cannot open file
    </InlineCode>

    <strong>Resolução</strong>

    1. Adicione o usuário do coletor ao grupo Elasticsearch:
       ```bash
       sudo usermod -a -G elasticsearch otelcol-contrib
       ```
    2. Reinicie o coletor:
       <InlineCode>
         sudo systemctl restart otelcol-contrib
       </InlineCode>
  </Collapser>

  <Collapser id="troubleshoot-api-reachability" title="Não é possível acessar a API do Elasticsearch a partir do coletor">
    <strong>Como verificar</strong>

    ```bash
    # Unsecured cluster
    curl -I http://localhost:9200

    # With authentication
    curl -u username:password -k https://localhost:9200
    ```

    <strong>Resolução</strong>

    Verifique se o cluster está íntegro, se as credenciais são válidas e se as configurações de firewall ou segurança permitem o acesso.
  </Collapser>

  <Collapser id="troubleshoot-missing-entity" title="Entidade Elasticsearch ausente na UI do New Relic">
    <strong>Resolução</strong>

    * Garanta que o processador
      <InlineCode>
        resourcedetection
      </InlineCode>
      esteja incluído em todos os pipelines de métricas.
    * Verifique se
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      está definido via processador
      <InlineCode>
        resource/cluster_name_override
      </InlineCode>
      .
  </Collapser>

  <Collapser id="troubleshoot-logs-missing" title="Métricas presentes, mas logs ausentes">
    <strong>Resolução</strong>

    * Confirme se os caminhos do receptor
      <InlineCode>
        filelog
      </InlineCode>
      estão corretos e absolutos.
    * Verifique se o pipeline de logs inclui tanto o receptor
      <InlineCode>
        filelog
      </InlineCode>
      quanto o exportador
      <InlineCode>
        otlphttp
      </InlineCode>
      .
  </Collapser>
</CollapserGroup>

## Implantações do Kubernetes [#kubernetes-troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-k8s-no-pods-discovered" title="Nenhum pod do Elasticsearch descoberto - rótulos ausentes">
    <strong>Como verificar</strong>

    ```bash
    # Verify your Elasticsearch pods have the required label
    kubectl get pods -n <namespace> -l app=elasticsearch --show-labels
    ```

    <strong>Resolução</strong>

    Se nenhum pod for retornado, seus pods do Elasticsearch não possuem o rótulo <InlineCode>
      app=elasticsearch
    </InlineCode> obrigatório. O receiver\_creator não consegue descobrir pods sem rótulos correspondentes.

    * Para StatefulSet/Implantação, adicione o rótulo no modelo do pod:
      ```yaml
      spec:
        template:
          metadata:
            labels:
              app: elasticsearch
      ```
    * Para pods existentes, adicione o rótulo e reinicie:
      ```bash
      kubectl label pods -l <your-selector> app=elasticsearch -n <namespace>
      kubectl rollout restart statefulset/elasticsearch -n <namespace>
      ```
    * Se estiver usando rótulos personalizados, atualize a regra do receiver no values.yaml para corresponder aos seus rótulos:
      ```yaml
      rule: type == "pod" && labels["app"] == "your-custom-label"
      ```
  </Collapser>

  <Collapser id="troubleshoot-k8s-collector-not-running" title="Pods do Collector não executando ou falhando">
    <strong>Como verificar</strong>

    ```bash
    kubectl get pods -n newrelic
    kubectl describe pod <collector-pod-name> -n newrelic
    ```

    <strong>Resolução</strong>

    * Verifique os eventos do pod para erros:
      <InlineCode>
        kubectl describe pod
      </InlineCode>

    * Revise os logs do coletor:

      ```bash
      kubectl logs -n newrelic -l app.kubernetes.io/name=opentelemetry-collector
      ```

    * Verifique se o segredo existe:

      ```bash
      kubectl get secret newrelic-licenses -n newrelic
      ```

    * Verifique se os limites de recursos não estão muito baixos
  </Collapser>

  <Collapser id="troubleshoot-k8s-discovery-errors" title="O criador de receptores não consegue descobrir pods">
    <strong>Como verificar</strong>

    ```bash
    # Check collector logs for discovery errors
    kubectl logs -n newrelic -l app.kubernetes.io/name=opentelemetry-collector | grep "receiver_creator"
    ```

    <strong>Resolução</strong>

    * Verifique se as permissões RBAC estão definidas corretamente:

      ```bash
      kubectl get clusterrole | grep opentelemetry
      kubectl describe clusterrole <role-name>
      ```

    * Certifique-se de que o coletor tenha permissões para monitorar pods, nós e endpoints

    * Verifique se a extensão k8s\_observer está ativada na configuração
  </Collapser>

  <Collapser id="troubleshoot-k8s-network-connectivity" title="O Collector não consegue se conectar aos pods do Elasticsearch">
    <strong>Como verificar</strong>

    ```bash
    # Check network policies
    kubectl get networkpolicies -n <namespace>

    # Test connectivity from collector to Elasticsearch
    kubectl exec -n newrelic <collector-pod> -- curl http://<es-pod-ip>:9200
    ```

    <strong>Resolução</strong>

    * Verifique se as políticas de rede permitem o tráfego do namespace newrelic para o seu namespace Elasticsearch
    * Verifique se os pods do Elasticsearch estão expondo a porta correta (padrão: 9200)
    * Certifique-se de que nenhuma regra de firewall bloqueie a comunicação entre pods
  </Collapser>

  <Collapser id="troubleshoot-k8s-wrong-endpoint" title="403 Forbidden ou erros de autenticação no Kubernetes">
    <strong>Amostra de erro</strong>: <InlineCode>
      permanent error: 403 Forbidden
    </InlineCode>

    <strong>Resolução</strong>

    * Verifique se o segredo contém a chave de licença correta:

      ```bash
      kubectl get secret newrelic-licenses -n newrelic -o jsonpath='{.data.NEWRELIC_LICENSE_KEY}' | base64 -d
      ```

    * Certifique-se de que o endpoint OTLP esteja correto para sua região

    * Verifique se o segredo está montado no pod do coletor:

      ```bash
      kubectl describe pod <collector-pod> -n newrelic | grep -A5 "Environment"
      ```
  </Collapser>

  <Collapser id="troubleshoot-k8s-logs-not-collected" title="Logs não sendo coletados no Kubernetes">
    <strong>Resolução</strong>

    * Verifique se você está usando
      <InlineCode>
        mode: daemonset
      </InlineCode>
      (o modo de implantação não pode acessar os logs do nó)

    * Verifique se as montagens de volume estão configuradas corretamente:

      ```bash
      kubectl describe pod <collector-pod> -n newrelic | grep -A10 "Mounts"
      ```

    * Verifique se o caminho do receptor filelog corresponde aos logs do seu pod do Elasticsearch:

      ```bash
      kubectl exec -n newrelic <collector-pod> -- ls /var/log/pods/*/elasticsearch*/*.log
      ```

    * Certifique-se de que o coletor tenha permissões de leitura nos diretórios de log do host
  </Collapser>

  <Collapser id="troubleshoot-k8s-cluster-name-missing" title="Métricas sem o atributo k8s.cluster.name">
    <strong>Resolução</strong>

    * Verifique se a variável de ambiente
      <InlineCode>
        K8S_CLUSTER_NAME
      </InlineCode>
      está definida no values.yaml

    * Verifique se o processador
      <InlineCode>
        resource/cluster
      </InlineCode>
      está no pipeline de métricas

    * Consulta para verificar:

      ```sql
      FROM Metric SELECT * WHERE metricName LIKE 'elasticsearch.%' LIMIT 1
      ```

      Verifique se o atributo <InlineCode>
        k8s.cluster.name
      </InlineCode> está presente
  </Collapser>
</CollapserGroup>

## APM correlation and distributed tracing [#correlation-troubleshooting]

These issues apply when you&apos;ve set up [APM correlation with distributed tracing](/docs/opentelemetry/integrations/elasticsearch/distributed-tracing).

<CollapserGroup>
  <Collapser id="troubleshoot-no-es-spans" title="No Elasticsearch spans appear in New Relic">
    <strong>Como verificar</strong>

    ```sql
    FROM Span SELECT count(*) WHERE es.cluster.name = '<elasticsearch-cluster-name>' SINCE 30 minutes ago
    ```

    <strong>Resolução</strong>

    * Native OTLP trace export requires <strong>Elasticsearch 9.4 or later</strong>. Confirm your version with
      <InlineCode>
        curl http://localhost:9200
      </InlineCode>
      .
    * Verify all three settings are present in
      <InlineCode>
        elasticsearch.yml
      </InlineCode>
      :
      <InlineCode>
        telemetry.tracing.enabled: true
      </InlineCode>
      ,
      <InlineCode>
        telemetry.export.endpoint
      </InlineCode>
      , and
      <InlineCode>
        telemetry.tracing.sample_rate
      </InlineCode>
      .
    * Confirm the JVM system property
      <InlineCode>
        -Dtelemetry.otel.traces.enabled=true
      </InlineCode>
      is set (in
      <InlineCode>
        jvm.options
      </InlineCode>
      or
      <InlineCode>
        ES_JAVA_OPTS
      </InlineCode>
      ), then restart Elasticsearch.
    * The default
      <InlineCode>
        telemetry.tracing.sample_rate
      </InlineCode>
      is
      <InlineCode>
        0.001
      </InlineCode>
      (0.1%). Raise it while validating so spans appear quickly.
  </Collapser>

  <Collapser id="troubleshoot-traces-pipeline" title="Elasticsearch is exporting spans but they never reach New Relic">
    <strong>Resolução</strong>

    * Confirm the collector has an
      <InlineCode>
        otlp
      </InlineCode>
      receiver with the gRPC protocol enabled on
      <InlineCode>
        0.0.0.0:4317
      </InlineCode>
      , and that the endpoint is reachable from the Elasticsearch nodes.
    * Confirm a
      <InlineCode>
        traces
      </InlineCode>
      pipeline exists and includes the
      <InlineCode>
        otlp
      </InlineCode>
      receiver and the
      <InlineCode>
        otlphttp
      </InlineCode>
      exporter.
    * Check the collector logs for OTLP receiver or export errors.
  </Collapser>

  <Collapser id="troubleshoot-cluster-self-loop" title="The cluster shows a relationship to itself (calls itself)">
    <strong>Causa</strong>

    A self-loop appears when Elasticsearch spans reach New Relic that can&apos;t be attributed to a calling application. There are two common sources:

    * <strong>Parentless (root) Elasticsearch spans</strong> — spans with no parent application span, such as Kubernetes health probes or the Elasticsearch metrics receiver&apos;s own scrape calls (
      <InlineCode>
        \_nodes/stats
      </InlineCode>
      ,
      <InlineCode>
        \_cluster/health
      </InlineCode>
      , and similar). Because they aren&apos;t part of an application&apos;s trace, New Relic has no calling service and draws the relationship on the cluster itself.
    * <strong>The node&apos;s own address</strong> — Elasticsearch server spans carry
      <InlineCode>
        http.request.headers.host
      </InlineCode>
      (and
      <InlineCode>
        server.address
      </InlineCode>
      ), which New Relic resolves back to the cluster.

    <strong>Resolução</strong>

    Add both processors to the <InlineCode>
      traces
    </InlineCode> pipeline, then restart the collector. <InlineCode>
      filter/drop\_rootless\_es
    </InlineCode> drops the parentless Elasticsearch spans (application-driven spans always have a parent, so they&apos;re kept), and <InlineCode>
      transform/strip\_es\_host
    </InlineCode> removes the address attributes:

    ```yaml
    processors:
      filter/drop_rootless_es:
        error_mode: ignore
        traces:
          span:
            - 'instrumentation_scope.name == "elasticsearch" and IsRootSpan()'
      transform/strip_es_host:
        error_mode: ignore
        trace_statements:
          - context: span
            statements:
              - delete_key(attributes, "http.request.headers.host") where instrumentation_scope.name == "elasticsearch"
              - delete_key(attributes, "server.address") where instrumentation_scope.name == "elasticsearch"
    # traces pipeline: processors: [filter/drop_rootless_es, transform/strip_es_host, batch]
    ```

    Existing self-loops clear on their own once the corrected spans arrive and the previous relationship expires (this can take up to about 75 minutes).
  </Collapser>

  <Collapser id="troubleshoot-app-not-linked" title="Elasticsearch spans arrive, but applications aren't linked to the cluster">
    <strong>Resolução</strong>

    * Make sure your applications are instrumented and propagate the W3C
      <InlineCode>
        traceparent
      </InlineCode>
      header on their Elasticsearch calls. Most modern Elasticsearch clients do this automatically when the application is instrumented with OpenTelemetry.
    * Open a distributed trace that includes an Elasticsearch call and confirm the application spans and Elasticsearch spans share the same trace.
    * Give the relationship a few minutes to build. New Relic re-evaluates entity relationships periodically.
  </Collapser>

  <Collapser id="troubleshoot-name-mismatch" title="Traces and metrics resolve to different cluster entities">
    <strong>Resolução</strong>

    * The traces path keys on
      <InlineCode>
        es.cluster.name
      </InlineCode>
      (stamped by Elasticsearch on its spans) and the metrics path on
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      . The
      <InlineCode>
        elasticsearchreceiver
      </InlineCode>
      reports
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      automatically from the value Elasticsearch returns, so both derive from the same
      <InlineCode>
        cluster.name
      </InlineCode>
      and resolve to one entity — no extra collector configuration needed.
    * Don&apos;t force the metrics cluster name to a fixed value. If your collector config sets it with a
      <InlineCode>
        resource
      </InlineCode>
      processor (for example a
      <InlineCode>
        resource/cluster_name_override
      </InlineCode>
      that hardcodes the name), remove that override — otherwise metrics and traces resolve to two different entities and the correlated entity shows no metrics data.
    * Make sure your Elasticsearch
      <InlineCode>
        cluster.name
      </InlineCode>
      is unique within your New Relic account so it maps to a single, unambiguous entity.
  </Collapser>
</CollapserGroup>
