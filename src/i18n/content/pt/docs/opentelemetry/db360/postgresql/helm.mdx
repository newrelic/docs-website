Você pode instalar e configurar o monitoramento do PostgreSQL no Kubernetes usando o chart do Helm `postgresql-otel`. Opcionalmente, o chart também pode executar um job de configuração que cria a role de monitoramento, suas concessões e a extensão `pg_stat_statements` para você.

<Callout variant="tip" title="Instalação guiada">
  Para instalar pela interface da New Relic, acesse <DNT>**[one.newrelic.com &gt; Integrations &amp; Agents &gt; PostgreSQL (Database 360)](https://onenr.io/00jlEJKbdQW)**</DNT>. Esta página aborda apenas a instalação manual.
</Callout>

<Callout variant="important">
  O chart implanta o coletor como uma implantação do Kubernetes que acessa o PostgreSQL remotamente pela rede, portanto, ele relata apenas métricas do PostgreSQL: nenhuma métrica de host ou de infraestrutura para a máquina em que o PostgreSQL é executado. Ele monitora uma *instância* do PostgreSQL por release (vários *bancos de dados* nessa instância são suportados) e não configura o TLS ou provedores de credenciais `db_auth`, como a autenticação do AWS IAM.
</Callout>

  <Step>

  <Step>
    ## Pré-requisitos [#helm-prerequisites]

    * [Chave de licença](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key) da New Relic válida.

    * Helm 3.0 ou posterior, e `kubectl` configurado para acessar seu cluster do Kubernetes.

    * Conectividade de rede do seu cluster do Kubernetes para o host do PostgreSQL (ou endpoint do RDS) e porta:

      * Auto-hospedado: um caminho roteado para o host do PostgreSQL (VPN, peering ou rede compartilhada), resolução de DNS se for um nome do host, e o `pg_hba.conf` e o firewall do lado do PostgreSQL devem permitir o IP de origem real da conexão (que pode ser um gateway NAT, não o IP do próprio pod).
      * AWS RDS: emparelhamento de VPC, um transit gateway ou posicionamento em VPC compartilhada com a instância do RDS, e o grupo de segurança do RDS deve permitir a porta do PostgreSQL (`5432` por padrão) a partir da origem de saída do cluster.

    * Uma role de monitoramento que você já criou com suas concessões por banco de dados ou credenciais de administrador do PostgreSQL para que o job de configuração do chart possa criá-las para você. Veja [Configurar credenciais de monitoramento](#helm-credentials) abaixo.
  </Step>

  <Step>
    ## Crie o namespace [#helm-namespace]

    Crie o namespace onde a instalação será realizada. Ele deve existir antes da criação de qualquer secret na próxima etapa, já que `helm install --create-namespace` cria o namespace apenas durante a etapa final de instalação:

    ```bash
    kubectl create namespace newrelic
    ```

    <Callout variant="tip">
      Defina-o como o namespace padrão para o seu contexto `kubectl` atual para que não seja necessário passar `-n` em todos os comandos abaixo:

      ```bash
      kubectl config set-context --current --namespace=newrelic
      ```
    </Callout>
  </Step>

  <Step>
    ## Configure as credenciais de monitoramento [#helm-credentials]

    Decida se você deseja que o job de configuração do chart crie a role de monitoramento do PostgreSQL para você e, se não, como você fornecerá suas credenciais:

    <CollapserGroup>
      <Collapser id="helm-creds-inline" title="Sem job de configuração: nome de usuário e senha simples">
        Com este método não há job de configuração, portanto, nada aqui cria a função de monitoramento para você. Antes de instalar o chart, crie-o você mesmo como superusuário. Execute isto uma vez no nível do cluster:

        ```sql
        CREATE USER newrelic WITH LOGIN PASSWORD '<password>';
        ALTER ROLE newrelic INHERIT;   -- required on PG15+, a no-op on PG14
        ```

        Em seguida, execute isto em **cada** banco de dados que você planeja listar em `postgresql.databases`:

        ```sql
        CREATE SCHEMA IF NOT EXISTS otel;
        GRANT USAGE ON SCHEMA otel TO newrelic;
        GRANT USAGE ON SCHEMA public TO newrelic;
        GRANT SELECT ON ALL TABLES IN SCHEMA public TO newrelic;
        GRANT pg_monitor TO newrelic;
        CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
        ```

        Para obter mais detalhes, consulte a etapa **Configurar usuário e concessões do banco de dados** para [PostgreSQL auto-hospedado](/docs/opentelemetry/db360/postgresql/hosted/#database-user) ou [PostgreSQL no RDS](/docs/opentelemetry/db360/postgresql/rds/#database-user).

        Você definirá o nome de usuário e a senha de monitoramento diretamente em `values.yaml` na próxima etapa.
      </Collapser>

      <Collapser id="helm-creds-secret-nojob" title="Sem job de configuração: credenciais baseadas em segredos">
        Com este método, também não há job de configuração. Crie você mesmo a função de monitoramento e suas concessões por banco de dados primeiro, exatamente como no método de credenciais simples acima. A única diferença é onde suas credenciais ficam: em vez de texto simples em `values.yaml`, armazene-as em um secret do Kubernetes:

        ```bash
        kubectl create secret generic postgres-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        ```
      </Collapser>

      <Collapser id="helm-creds-setupjob" title="Tarefa de configuração automatizada">
        Com este método, o job de configuração do chart cria a função de monitoramento para você e, para cada banco de dados em `postgresql.databases`, cria o esquema `otel`, concede `USAGE`/`SELECT`/`pg_monitor` e cria a extensão `pg_stat_statements`. Tanto as credenciais de monitoramento quanto as de administrador devem ser fornecidas como secrets do Kubernetes: o job de configuração nunca aceita credenciais de administrador em texto simples, e habilitá-lo também requer credenciais de monitoramento baseadas em secrets.

        1. Crie um secret com o nome de usuário e a senha de monitoramento. Esta é a identidade que o job de configuração cria e com a qual o coletor se conecta:

           ```bash
           kubectl create secret generic postgres-monitor-creds \
             --from-literal=username=<MONITORING_USERNAME> \
             --from-literal=password='<MONITORING_PASSWORD>' \
             -n newrelic
           ```

        2. O job de configuração aceita apenas credenciais de administrador por meio de um secret do Kubernetes (sem nome de usuário/senha em texto simples em `values.yaml`). Essa credencial deve ser de um superusuário (auto-hospedado) ou um equivalente a `rds_superuser` (RDS), uma vez que precisa de `CREATE USER`, `CREATE SCHEMA` e `CREATE EXTENSION`:

           ```bash
           kubectl create secret generic postgres-admin-creds \
             --from-literal=username=<ADMIN_USERNAME> \
             --from-literal=password='<ADMIN_PASSWORD>' \
             -n newrelic
           ```
      </Collapser>
    </CollapserGroup>
  </Step>

    `postgresql.databases` é uma **lista obrigatória e não vazia**. Ao contrário do MySQL ou do SQL Server, o PostgreSQL não possui um modo de monitoramento de todos os bancos de dados: uma conexão tem como destino um banco de dados por vez, portanto, o receiver deve ser informado sobre quais coletar.

    Use o `values.yaml` que corresponde ao método de credencial escolhido na etapa anterior:

    <CollapserGroup>
      <Collapser id="helm-values-inline" title="Sem job de configuração: nome de usuário e senha simples">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        postgresql:
          topology: <self-hosted|rds>
          server: <YOUR_DB_HOST>
          port: <YOUR_DB_PORT>
          username: <YOUR_MONITORING_USERNAME>
          password: <YOUR_MONITORING_PASSWORD>
          databases:
            - <YOUR_DATABASE>
            - <ANOTHER_DATABASE>

        # No setup job runs, so create the monitoring role and its
        # per-database grants yourself before installing the chart.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-values-secret-nojob" title="Sem job de configuração: credenciais baseadas em segredos">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        postgresql:
          topology: <self-hosted|rds>
          server: <YOUR_DB_HOST>
          port: <YOUR_DB_PORT>
          existingSecret: postgres-monitor-creds
          databases:
            - <YOUR_DATABASE>
            - <ANOTHER_DATABASE>

        # No setup job runs, so the monitoring role referenced by
        # this secret must already exist - create it yourself
        # before installing the chart.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-values-setupjob" title="Tarefa de configuração automatizada">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        postgresql:
          topology: <self-hosted|rds>
          server: <YOUR_DB_HOST>
          port: <YOUR_DB_PORT>
          existingSecret: postgres-monitor-creds
          databases:
            - <YOUR_DATABASE>
            - <ANOTHER_DATABASE>

        setupJob:
          enabled: true
          image:
            # -- psql-capable image. No default: the official postgres
            # image bundles psql and is a reasonable choice.
            repository: postgres
            tag: "16"
            pullPolicy: IfNotPresent
          postgresAdmin:
            existingSecret: postgres-admin-creds
          # -- Also creates the otel.explain_statement SECURITY DEFINER
          # function, so the receiver can EXPLAIN write/locking queries.
          enableExplainPermissions: false
          # -- Also creates the pgvector extension in each database.
          enablePgvector: false
        ```

  <Step>
    ## (Opcional) Monitorar várias instâncias a partir de um release [#helm-multi]

    Em vez de `postgresql.*`, defina `postgresqlMulti.enabled: true` para monitorar várias instâncias do PostgreSQL (auto-hospedadas ou RDS) a partir de um único pod de coletor em uma versão. Os dois modos são mutuamente exclusivos: não defina `postgresql.server` e `postgresqlMulti.enabled: true` na mesma versão.

    As entradas são chamadas de `instances`, não de `databases`: cada instância é um servidor PostgreSQL separado e cada uma carrega sua própria lista `databases` aninhada (os bancos de dados individuais a serem monitorados nessa instância), da mesma forma que `postgresql.databases` funciona no modo de instância única.

    O modo multi-instância não possui um caminho de nome de usuário/senha simples: cada instância precisa de seu próprio secret do Kubernetes com credenciais de monitoramento. Decida se você também deseja que o job de configuração crie cada função de monitoramento para você:

    <CollapserGroup>
      <Collapser id="helm-multi-nojob" title="Sem job de configuração">
        Crie manualmente o segredo da função de monitoramento de cada instância antes da instalação (repita por instância, correspondendo ao `name` fornecido em `values.yaml`):

        ```bash
        kubectl create secret generic db1-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        # Repeat for every instance (db2-monitor-creds, ...)
        ```

        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        # EDIT the two example entries below (or add more) to match
        # your real instances - each `name` must be unique within
        # this release and match the Secret you created for it.
        postgresqlMulti:
          enabled: true
          topology: <self-hosted|rds>
          instances:
            - name: db1
              server: <YOUR_DB_1_HOST>
              port: 5432
              existingSecret: db1-monitor-creds
              databases:
                - appdb1
            - name: db2
              server: <YOUR_DB_2_HOST>
              port: 5432
              existingSecret: db2-monitor-creds
              databases:
                - appdb2

        # No admin credential is configured here since the setup
        # job is disabled - create each instance's monitoring role
        # yourself first.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-multi-setupjob" title="Tarefa de configuração automatizada">
        Cada instância precisa tanto de seu próprio secret da função de monitoramento quanto de seu próprio secret de credenciais de administrador (repita por instância):

        ```bash
        kubectl create secret generic db1-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        kubectl create secret generic db1-admin-creds \
          --from-literal=username=<ADMIN_USERNAME> \
          --from-literal=password='<ADMIN_PASSWORD>' \
          -n newrelic
        # Repeat for every instance (db2-monitor-creds, db2-admin-creds, ...)
        ```

        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        # EDIT the two example entries below (or add more) to match
        # your real instances - each `name` must be unique within
        # this release and match the Secrets you created for it.
        postgresqlMulti:
          enabled: true
          topology: <self-hosted|rds>
          instances:
            - name: db1
              server: <YOUR_DB_1_HOST>
              port: 5432
              existingSecret: db1-monitor-creds
              databases:
                - appdb1
              postgresAdmin:
                existingSecret: db1-admin-creds
            - name: db2
              server: <YOUR_DB_2_HOST>
              port: 5432
              existingSecret: db2-monitor-creds
              databases:
                - appdb2
              postgresAdmin:
                existingSecret: db2-admin-creds

        setupJob:
          enabled: true
          image:
            # -- psql-capable image. No default: the official postgres
            # image bundles psql and is a reasonable choice.
            repository: postgres
            tag: "16"
        ```
      </Collapser>

    <Callout variant="tip">
      `setupJob.enableExplainPermissions` e `setupJob.enablePgvector` são chaves únicas compartilhadas em cada banco de dados em cada instância; elas não podem ser definidas por instância. As configurações de extração (intervalo de coleta, métricas, `topQueryCollection`/`querySampleCollection`) também se aplicam de forma idêntica a cada instância em `postgresqlMulti.instances`; não há substituição por instância. Utilize `additionalReceiverConfig` para qualquer elemento que precise ser diferente. O job de configuração é executado uma vez por instância (`<release>-setup-<name>`) em vez de uma vez por versão.

  <Step>
    ## Instale o Helm chart [#helm-install]

    1. Adicione o repositório Helm da New Relic:

       ```bash
       helm repo add newrelic https://helm-charts.newrelic.com
       helm repo update
       ```

    2. Instale o chart usando seu arquivo `values.yaml`:

       ```bash
       helm upgrade --install postgresql-otel newrelic/postgresql-otel \
         -n newrelic \
         --create-namespace \
         -f values.yaml
       ```
  </Step>

  <Step>
    ## Verifique a instalação [#helm-verify]

    1. Verifique se o job de configuração foi concluído (se ativado) e se o pod do coletor está em execução:

       ```bash
       kubectl get jobs,pods -n newrelic --watch
       ```

    2. Execute esta consulta no [criador de consulta](/docs/query-your-data/explore-query-data/query-builder/introduction-query-builder/) para confirmar se os dados estão chegando:

       ```sql
       SELECT count(*) FROM Metric
       WHERE metricName LIKE 'postgresql.%'
       AND instrumentation.provider = 'opentelemetry'
       SINCE 10 minutes ago
       ```
  </Step>

  <Step>
    ## Encontre e use seus dados [#find]

    Assim que seus dados estiverem sendo coletados, você poderá acessar o monitoramento abrangente do banco de dados PostgreSQL por meio da interface do New Relic.

    Para encontrar a entidade de banco de dados PostgreSQL no New Relic:

    1. Vá para <DNT>**[one.newrelic.com](https://one.newrelic.com) &gt; All capabilities &gt; Databases**</DNT>.
    2. Na dropdown **<DNT>Entity type</DNT>**, selecione <DNT>**PostgreSQL instance**</DNT> e clique em <DNT>**Apply**</DNT>.
    3. Selecione seu banco de dados PostgreSQL na lista de entidades.
  </Step>
</Steps>
