Você pode instalar e configurar o monitoramento do banco de dados Oracle no Kubernetes usando o chart do Helm `oracle-otel`. Opcionalmente, o chart também pode executar um job de configuração que cria o usuário do banco de dados de monitoramento para você.

<Callout variant="tip" title="Instalação guiada">
  Para instalar pela interface da New Relic, acesse <DNT>**[one.newrelic.com &gt; Integrations &amp; Agents &gt; Oracle (Database 360)](https://onenr.io/0kjnebKW7Ro)**</DNT>. Esta página aborda apenas a instalação manual.
</Callout>

<Steps>
  <Step>
    ## Pré-requisitos [#prerequisites]

    * Uma [chave de licença](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key) do New Relic válida.
    * Helm 3.0 ou posterior, e `kubectl` configurado para acessar seu cluster do Kubernetes.
    * Conectividade de rede do seu cluster do Kubernetes para o host e a porta do listener do banco de dados Oracle.
    * Ou um usuário do banco de dados de monitoramento que você já criou, ou credenciais de administrador do banco de dados Oracle (usuário mestre do RDS, `SYS` ou `ADMIN`) para que o job de configuração do chart possa criar um para você. Consulte [Configure as credenciais de monitoramento](#credentials) abaixo.
  </Step>

  <Step>
    ## Crie o namespace [#namespace]

    Crie o namespace onde a instalação será realizada. Ele deve existir antes da criação de qualquer secret na próxima etapa, já que `helm install --create-namespace` cria o namespace apenas durante a etapa final de instalação:

    ```bash
    kubectl create namespace newrelic
    ```

    <Callout variant="tip">
      Defina-o como o namespace padrão para o seu contexto `kubectl` atual para que não seja necessário passar `-n` em todos os comandos abaixo:

      ```bash
      kubectl config set-context --current --namespace=newrelic
      ```
    </Callout>
  </Step>

  <Step>
    ## Configure as credenciais de monitoramento [#credentials]

    Decida se deseja que o job de configuração do chart crie o usuário de monitoramento do banco de dados Oracle para você e, caso contrário, como fornecerá suas credenciais:

    <CollapserGroup>
      <Collapser id="helm-creds-inline" title="Sem job de configuração: nome de usuário e senha simples">
        Com este método, não há job de configuração, portanto, nada aqui cria o usuário de monitoramento para você. Antes de instalar o chart, crie-o você mesmo: siga as etapas **Configurar usuário do banco de dados** e **Conceder privilégios de monitoramento** em [On-host CDB](/docs/opentelemetry/db360/oracle/host-cdb) ou [On-host PDB](/docs/opentelemetry/db360/oracle/host-pdb), dependendo do seu ambiente.

        Você definirá o nome de usuário e a senha de monitoramento diretamente em `values.yaml` na próxima etapa.
      </Collapser>

      <Collapser id="helm-creds-secret-nojob" title="Sem job de configuração: credenciais baseadas em segredos">
        Com este método, também não há job de configuração. Crie você mesmo o usuário de monitoramento primeiro, exatamente como no método de credenciais simples acima. A única diferença é onde suas credenciais ficam: em vez de texto simples em `values.yaml`, armazene-as em um secret do Kubernetes:

        ```bash
        kubectl create secret generic oracle-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        ```
      </Collapser>

      <Collapser id="helm-creds-setupjob" title="Tarefa de configuração automatizada">
        Com esse método, o job de configuração do chart cria o usuário de monitoramento para você usando credenciais de administrador do banco de dados. Tanto as credenciais de monitoramento quanto as de administrador devem ser fornecidas como secrets do Kubernetes: o job de configuração nunca aceita credenciais de administrador em texto simples, e habilitá-lo também requer credenciais de monitoramento baseadas em secrets.

        1. Crie um secret com o nome de usuário e a senha de monitoramento. Esta é a identidade que o job de configuração cria e com a qual o coletor se conecta:

           ```bash
           kubectl create secret generic oracle-monitor-creds \
             --from-literal=username=<MONITORING_USERNAME> \
             --from-literal=password='<MONITORING_PASSWORD>' \
             -n newrelic
           ```

        2. O job de configuração aceita credenciais de administrador apenas por meio de um secret do Kubernetes (sem nome de usuário/senha em texto simples em `values.yaml`). Como essa credencial pode criar usuários e conceder amplo acesso ao banco de dados, crie-a como seu próprio secret:

           ```bash
           kubectl create secret generic oracle-admin-creds \
             --from-literal=username=<ADMIN_USERNAME> \
             --from-literal=password='<ADMIN_PASSWORD>' \
             -n newrelic
           ```
      </Collapser>
    </CollapserGroup>
  </Step>

          </td>

    Use o `values.yaml` que corresponde ao método de credencial escolhido na etapa anterior:

    <CollapserGroup>
      <Collapser id="helm-values-inline" title="Sem job de configuração: nome de usuário e senha simples">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        oracle:
          topology: <cdb|pdb|rds|adb>
          endpoint: <YOUR_DB_HOST>:<YOUR_DB_PORT>
          service: <YOUR_SERVICE_NAME>
          username: <YOUR_MONITORING_USERNAME>
          password: <YOUR_MONITORING_PASSWORD>

        # No setup job runs, so create the monitoring user yourself
        # before installing the chart.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-values-secret-nojob" title="Sem job de configuração: credenciais baseadas em segredos">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        oracle:
          topology: <cdb|pdb|rds|adb>
          endpoint: <YOUR_DB_HOST>:<YOUR_DB_PORT>
          service: <YOUR_SERVICE_NAME>
          existingSecret: oracle-monitor-creds

        # No setup job runs, so the monitoring user referenced by
        # this secret must already exist - create it yourself
        # before installing the chart.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-values-setupjob" title="Tarefa de configuração automatizada">
        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        oracle:
          topology: <cdb|pdb|rds|adb>
          endpoint: <YOUR_DB_HOST>:<YOUR_DB_PORT>
          service: <YOUR_SERVICE_NAME>
          existingSecret: oracle-monitor-creds

        setupJob:
          enabled: true
          image:
            # -- Oracle Instant Client + sqlplus image. No default: pulling from container-registry.oracle.com requires accepting Oracle's license terms first. See README.
            repository: ""
            tag: ""
            pullPolicy: IfNotPresent
          oracleAdmin:
            existingSecret: oracle-admin-creds
        ```
      </Collapser>
    </CollapserGroup>

  <Step>
    ## (Opcional) Monitorar várias instâncias a partir de um release [#multi]

    Em vez de `oracle.*`, defina `oracleMulti.enabled: true` para monitorar várias instâncias do banco de dados Oracle a partir de um único pod de coletor em um release. Os dois modos são mutuamente exclusivos: não defina `oracle.endpoint` e `oracleMulti.enabled: true` no mesmo release. Cada instância em um release deve compartilhar o mesmo `oracleMulti.topology` (`cdb`, `pdb`, `rds` ou `adb`): a mistura de topologias, por exemplo, uma instância do RDS e um CDB auto-hospedado, não é suportada em um release; em vez disso, use um release separado para cada topologia.

    O modo multi-instância não possui um caminho de nome de usuário/senha em texto simples: cada instância precisa de seu próprio secret do Kubernetes com credenciais de monitoramento. Decida se você também deseja que o job de configuração crie cada usuário de monitoramento para você:

    <CollapserGroup>
      <Collapser id="helm-multi-nojob" title="Sem job de configuração">
        Crie manualmente o secret do usuário de monitoramento de cada instância antes da instalação (repita por instância, correspondendo ao `name` que você atribuir a ela em `values.yaml`):

        ```bash
        kubectl create secret generic db1-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        # Repeat for every instance (db2-monitor-creds, ...)
        ```

        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        # EDIT the two example entries below (or add more) to match
        # your real instances - each `name` must be unique within
        # this release and match the Secret you created for it.
        oracleMulti:
          enabled: true
          topology: <cdb|pdb|rds|adb>
          collectionInterval: 15s
          databases:
            - name: db1
              endpoint: <YOUR_DB_1_HOST>:<YOUR_DB_1_PORT>
              service: <YOUR_DB_1_SERVICE_NAME>
              existingSecret: db1-monitor-creds
            - name: db2
              endpoint: <YOUR_DB_2_HOST>:<YOUR_DB_2_PORT>
              service: <YOUR_DB_2_SERVICE_NAME>
              existingSecret: db2-monitor-creds

        # No admin credential is configured here since the setup
        # job is disabled - create each instance's monitoring user
        # yourself first.
        setupJob:
          enabled: false
        ```
      </Collapser>

      <Collapser id="helm-multi-setupjob" title="Tarefa de configuração automatizada">
        Cada instância precisa tanto do seu próprio secret de usuário de monitoramento quanto do seu próprio secret de credenciais de administrador (repita por instância):

        ```bash
        kubectl create secret generic db1-monitor-creds \
          --from-literal=username=<MONITORING_USERNAME> \
          --from-literal=password='<MONITORING_PASSWORD>' \
          -n newrelic
        kubectl create secret generic db1-admin-creds \
          --from-literal=username=<ADMIN_USERNAME> \
          --from-literal=password='<ADMIN_PASSWORD>' \
          -n newrelic
        # Repeat for every instance (db2-monitor-creds, db2-admin-creds, ...)
        ```

        ```yaml
        licenseKey: <YOUR_LICENSE_KEY>
        otlpEndpoint: otlp.nr-data.net:4317

        # EDIT the two example entries below (or add more) to match
        # your real instances - each `name` must be unique within
        # this release and match the Secrets you created for it.
        oracleMulti:
          enabled: true
          topology: <cdb|pdb|rds|adb>
          collectionInterval: 15s
          databases:
            - name: db1
              endpoint: <YOUR_DB_1_HOST>:<YOUR_DB_1_PORT>
              service: <YOUR_DB_1_SERVICE_NAME>
              existingSecret: db1-monitor-creds
              oracleAdmin:
                existingSecret: db1-admin-creds
            - name: db2
              endpoint: <YOUR_DB_2_HOST>:<YOUR_DB_2_PORT>
              service: <YOUR_DB_2_SERVICE_NAME>
              existingSecret: db2-monitor-creds
              oracleAdmin:
                existingSecret: db2-admin-creds

        setupJob:
          enabled: true
          image:
            repository: ""
            tag: ""
        ```
      </Collapser>
    </CollapserGroup>

    <Callout variant="tip">
      Ao contrário dos outros charts do Helm do NRDOT, o Oracle permite substituir `collectionInterval` por instância. Todas as outras configurações de scrape ainda se aplicam de forma idêntica a cada instância. Use `additionalReceiverConfig` para qualquer outra coisa que precise ser diferente. O job de configuração é executado uma vez por instância (`<release>-setup-<name>`) em vez de uma vez por release.

  <Step>
    ## Instale o Helm chart [#install]

    1. Adicione o repositório Helm da New Relic:

       ```bash
       helm repo add newrelic https://helm-charts.newrelic.com
       helm repo update
       ```

    2. Instale o chart usando seu arquivo `values.yaml`:

       ```bash
       helm upgrade --install oracle-otel newrelic/oracle-otel \
         -n newrelic \
         --create-namespace \
         -f values.yaml
       ```
  </Step>

  <Step>
    ## Verifique a instalação [#verify]

    1. Verifique se o job de configuração foi concluído e se o pod do coletor está em execução:

       ```bash
       kubectl get jobs,pods -n newrelic --watch
       ```

    2. Execute esta consulta no [criador de consulta](/docs/query-your-data/explore-query-data/query-builder/introduction-query-builder/) para confirmar se os dados estão chegando:

       ```sql
       SELECT count(*) FROM Metric
       WHERE metricName LIKE 'oracledb.%'
       AND instrumentation.provider = 'opentelemetry'
       SINCE 10 minutes ago
       ```
  </Step>
</Steps>

Para encontrar sua entidade de banco de dados Oracle no New Relic, consulte [Encontrar e usar seus dados](/docs/opentelemetry/db360/oracle/introduction/#find).
