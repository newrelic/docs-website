## Configuração passo a passo

<Steps>
<Step>
### Crie o arquivo de configuração [#create-config]

Ative a [telemetria interna](https://opentelemetry.io/docs/collector/internal-telemetry/) do coletor salvando a seguinte configuração como `internal-telemetry-config.yaml`:

```yaml
##### Example configuration for internal telemetry
# This configuration is intended to be used in conjunction with a configuration of components and pipelines. The
# collector supports config merging on startup.
##### Requirements
# - nrdot-collector (any distro) >= 1.3.0 or collector core version >= v1.35.0 / v0.129.0
##### Configuration via environment variables
# For official documentation, see: https://opentelemetry.io/docs/collector/internal-telemetry/
## Required
# - INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY
## Optional
# - INTERNAL_TELEMETRY_SERVICE_NAME: defaults to 'otel-collector'; determines entity name in New Relic
# - INTERNAL_TELEMETRY_OTLP_ENDPOINT: defaults to 'https://otlp.nr-data.net'; see https://docs.newrelic.com/docs/opentelemetry/best-practices/opentelemetry-otlp/ and https://docs.newrelic.com/docs/opentelemetry/best-practices/opentelemetry-otlp-troubleshooting/
# - INTERNAL_TELEMETRY_METRICS_LEVEL: defaults to 'detailed'; other values are 'normal', 'basic', 'none'
# - INTERNAL_TELEMETRY_LOG_LEVEL: defaults to INFO; other values are DEBUG, WARN, ERROR
# - INTERNAL_TELEMETRY_TRACE_LEVEL: defaults to 'none' (traces disabled); other value is 'basic'
# - INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO: defaults to 0.01, i.e. 1% sampling; has no effect if TRACE_LEVEL is 'none'
service:
  telemetry:
    metrics:
      level: "${env:INTERNAL_TELEMETRY_METRICS_LEVEL:-detailed}"
      readers:
        - periodic:
            exporter:
              otlp:
                protocol: http/protobuf
                endpoint: "${env:INTERNAL_TELEMETRY_OTLP_ENDPOINT:-https://otlp.nr-data.net}"
                temporality_preference: delta
                headers:
                  - name: api-key
                    value: "${env:INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY}"
    logs:
      level: "${env:INTERNAL_TELEMETRY_LOG_LEVEL:-INFO}"
      # default sampling config for reference to simplify overwrites even if not exposed via env var, e.g. --config=yaml:service::telemetry::logs::sampling::enabled::false
      sampling:
        enabled: true
        # The interval in seconds that the logger applies to each sampling.
        tick: 10s
        # The number of messages logged at the start of each sampling::tick
        initial: 10
        # Sets the sampling policy for subsequent messages after sampling::initial messages are logged. When sampling::thereafter is set to N, every Nth message is logged and all others are dropped. If N is zero, the logger drops all messages after sampling::initial messages are logged.
        thereafter: 100
      processors:
        - batch:
            exporter:
              otlp:
                protocol: http/protobuf
                endpoint: "${env:INTERNAL_TELEMETRY_OTLP_ENDPOINT:-https://otlp.nr-data.net}"
                headers:
                  - name: api-key
                    value: "${env:INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY}"
    traces:
      # traces are disabled by default due to experimental status and lack of default sampling rate that works across use cases
      level: "${env:INTERNAL_TELEMETRY_TRACE_LEVEL:-none}"
      sampler:
        parent_based:
          root:
            trace_id_ratio_based:
              ratio: ${env:INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO:-0.01}
      processors:
        - batch:
            exporter:
              otlp:
                protocol: http/protobuf
                endpoint: "${env:INTERNAL_TELEMETRY_OTLP_ENDPOINT:-https://otlp.nr-data.net}"
                headers:
                  - name: api-key
                    value: "${env:INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY}"
    resource:
      service.name: "${env:INTERNAL_TELEMETRY_SERVICE_NAME:-otel-collector}"
```
</Step>

<Step>
### Definir variáveis de ambiente [#set-env-vars]

* <DNT>`INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY`</DNT>: Chave de licença de ingestão para a conta para a qual a telemetria interna deve ser enviada. Essa chave pode ser diferente da chave que o coletor usa para enviar dados regulares para a New Relic, ou seja, <DNT>`NEW_RELIC_LICENSE_KEY`</DNT> no exemplo abaixo.
* <DNT>`INTERNAL_TELEMETRY_SERVICE_NAME`</DNT>: O padrão é `otel-collector`, determina o nome da entidade no New Relic
* <DNT>`INTERNAL_TELEMETRY_OTLP_ENDPOINT`</DNT>: O padrão é EUA `https://otlp.nr-data.net`; se estiver na UE, defina como `https://otlp.eu01.nr-data.net`; se estiver no JP, defina como `https://otlp.jp.nr-data.net`
</Step>

<Step>
### Execute o coletor com a configuração mesclada [#run-collector]

Além da configuração normal para componentes e pipelines (no exemplo a seguir `--config=/etc/nrdot-collector/config.yaml`), adicione um segundo argumento `--config` que mesclará ambas as configurações:

```bash
docker run \
  -e INTERNAL_TELEMETRY_NEW_RELIC_LICENSE_KEY='...' \
  -e NEW_RELIC_LICENSE_KEY='...' \
  -e INTERNAL_TELEMETRY_SERVICE_NAME='demo-collector' \
  -v './internal-telemetry-config.yaml:/etc/nrdot-collector/config-internal.yaml' \
  newrelic/nrdot-collector:2.8.1 --config=/etc/nrdot-collector/config.yaml \
  --config='/etc/nrdot-collector/config-internal.yaml'
```

<Callout variant="important">
A ordem dos argumentos `--config` importa se você tiver uma configuração pré-existente sob o nó `service::telemetry`. O coletor usa uma estratégia de &apos;o último vence&apos; em nível de nó ao mesclar configurações e certas partes da configuração (por exemplo, listas, nós folha) não podem ser mesclados, então são sobrescritos pelo último argumento `--config`.
</Callout>
</Step>

<Step>
### Aguarde o New Relic detectar seu coletor [#auto-detection]

Você não precisa configurar mais nada. O New Relic detecta seu coletor automaticamente e mostra a experiência do coletor para sua entidade.

Nos bastidores, a maioria das métricas internas do coletor tem nomes que começam com <DNT>`otelcol`</DNT>. Quando uma entidade emite uma métrica com esse prefixo, a New Relic marca a entidade como um coletor adicionando a tag de entidade <DNT>`otelCollector: opentelemetry`</DNT>. Isso acontece na ingestão, portanto, pode levar alguns minutos após a chegada dos primeiros dados antes que a experiência apareça.

Uma vez detectado, consulte [Visualizar seu coletor na interface](/docs/opentelemetry/collector-observability/collector-observability#view-ui) para explorar os dados do seu coletor.
</Step>

<Step>
### Opcional: personalize a configuração [#customize]

A configuração padrão expõe variáveis de ambiente adicionais no formato `INTERNAL_TELEMETRY_...` para ajustar opções comuns, como níveis de detalhe e amostragem. Consulte a [própria configuração](#create-config) para obter mais detalhes.

Recomendamos usar a configuração padrão para monitorar seu coletor. No entanto, você pode modificar a configuração de exemplo, como reduzir o nível de detalhes, a taxa de amostragem ou a taxa de coleta de dados. Consulte a [documentação oficial](https://opentelemetry.io/docs/collector/internal-telemetry/) para mais detalhes. Lembre-se de que alterações na configuração podem fazer com que certas partes da interface não exibam dados. Consulte também [o FAQ](/docs/opentelemetry/collector-observability/collector-observability-faq). As opções de configuração de telemetria interna do coletor mudam à medida que a comunidade OTel evolui. Você pode usar ou modificar os padrões fornecidos conforme necessário.
</Step>
</Steps>

## Considerações sobre sobrecarga [#overhead]

Como toda telemetria, a telemetria interna do coletor aumenta a sua ingestão de dados. A sobrecarga depende da sua carga de trabalho e configuração. Aqui estão os principais fatores a considerar:

**Métricas** Cria uma sobrecarga constante para o coletor e todos os componentes ativos, independentemente da vazão. As métricas são emitidas em um intervalo constante (60 segundos por padrão). Qualquer componente pode emitir métricas personalizadas, conforme indicado pelo respectivo [metadata.yaml](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/filterprocessor/metadata.yaml#L20), o que pode aumentar a sobrecarga.

Se você precisar reduzir a quantidade de métricas que seu coletor emite, recomendamos definir o nível de métrica para <DNT>`normal`</DNT>, por exemplo, via a variável de ambiente <DNT>`INTERNAL_TELEMETRY_METRICS_LEVEL`</DNT> na configuração de exemplo, pois apenas um subconjunto das métricas do <DNT>`detailed`</DNT> é usado pela UI e são tipicamente métricas destinadas ao ajuste fino de desempenho ou a problemas de rede, então você pode reativá-las conforme necessário.

**Logs** Os logs têm impacto mínimo durante a operação normal. Pode ocorrer uma sobrecarga maior quando os logs de erro aumentam rapidamente, mas isso é reduzido porque os logs são amostrados por padrão. O algoritmo de amostragem permite um número constante de logs por intervalo definido e, em seguida, faz a amostragem a uma taxa estática. Consulte <DNT>`service::telemetry::logs::sampling`</DNT> na [configuração](#create-config).

**Traces** Desativados por padrão, consulte [o FAQ](/docs/opentelemetry/collector-observability/collector-observability-faq#traces-disabled) para obter mais detalhes. Para experimentar com traces durante o desenvolvimento, defina <DNT>`INTERNAL_TELEMETRY_TRACE_LEVEL=basic`</DNT> e comece com uma taxa de amostragem baixa, como <DNT>`INTERNAL_TELEMETRY_TRACE_SAMPLE_RATIO=0.001`</DNT> (0,1%), enquanto monitora seu volume de ingestão e ajusta conforme necessário.
