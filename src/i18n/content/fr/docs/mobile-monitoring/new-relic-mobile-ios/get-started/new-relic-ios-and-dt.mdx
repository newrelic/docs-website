Notre agent iOS prend en charge le tracing distribué. Cela vous permet de voir comment l’activité de votre application mobile se connecte aux services associés.

## Exigences [#requirements]

Pour utiliser le tracing distribué, vous avez besoin de l&apos;agent iOS version 7.3.0 ou supérieure. Nous vous recommandons d&apos;utiliser l&apos;agent le plus récent.

## Comment configurer le tracing distribué [#setup]

Le tracing distribué est activé par défaut ; vous n’avez rien à faire pour l’activer.

Si vous préférez le désactiver, consultez [Tracing distribué](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/configure-settings/#ios-dt) dans le guide de l’API du SDK mobile, ou [Désactiver le tracing distribué](#disable) ci-dessous.

Les en-têtes de tracing distribué sont envoyés sur chaque request instrumentée, indépendamment des autres paramètres. Cependant, pour que la trace soit liée à un événement `MobileRequest` signalé (et apparaisse ainsi corrélée à l’activité réseau de votre application dans l’interface utilisateur), vous devez également activer les [Network Request Events](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/configure-settings/#ios-networking). C’est activé par défaut, cela n’a donc d’importance que si vous l’avez explicitement désactivé.

## En-têtes de tracing distribué [#headers]

À partir de la version 7.7.8 de l’agent iOS, l’agent ajoute uniquement les en-têtes [W3C Trace Context](/docs/distributed-tracing/concepts/how-new-relic-distributed-tracing-works/#headers), `traceparent` et `tracestate`, aux requests réseau sortantes. Il n’envoie plus l’en-tête propriétaire `newrelic`. Les versions antérieures de l’agent envoient les trois en-têtes.

Les agents New Relic APM qui prennent en charge W3C Trace Context utilisent ces en-têtes pour continuer la trace, afin que les requests de votre application restent connectées aux services backend qu&apos;elles appellent. W3C Trace Context est pris en charge dans ces versions d&apos;agent APM et supérieures :

## Quelles requests obtiennent automatiquement le tracing distribué [#automatic-instrumentation]

L’agent instrumente automatiquement `NSURLSession` et `NSURLConnection`, de sorte que les en-têtes de tracing distribué sont ajoutés aux requests effectuées via l’un ou l’autre sans aucune configuration requise.

<Callout variant="important">
Si votre application utilise les API `async`/`await` `URLSession` de Swift (par exemple, `data(for:)` ou `data(from:)`), elles ne sont **pas** couvertes par l’instrumentation par défaut. Vous devez explicitement activer `NRFeatureFlag_SwiftAsyncURLSessionSupport` (désactivé par défaut à partir de la version 7.4.5 de l’agent) pour que l’agent ajoute des en-têtes de tracing distribué à ces appels :

L’agent n’ajoute pas automatiquement les en-têtes de tracing distribué aux :

* `WKWebView`. Le contenu Web chargé dans un `WKWebView` effectue ses requests réseau depuis le processus WebKit, en dehors de l’instrumentation `NSURLSession`/`NSURLConnection` de l’application, de sorte que ces requests ne font pas l’objet d’une trace automatiquement. (L’instrumentation `WKWebView` distincte de l’agent, activée par défaut, couvre uniquement le temps de chargement des pages, et non les en-têtes réseau.)
* Bibliothèques réseau tierces qui ne passent pas par `NSURLSession` ou `NSURLConnection`.
* WebSockets.
* gRPC ou d’autres transports personnalisés.

Pour n&apos;importe lequel d&apos;entre eux, utilisez la propagation manuelle.

## Propager manuellement le tracing distribué [#manual]

Si vous effectuez une request via une API, l’agent ne s’auto-instrumente pas. Vous pouvez toujours ajouter des en-têtes de tracing distribué et signaler la request manuellement.

**Si un autre élément signale la request**

Certains frameworks (par exemple, une bibliothèque réseau native utilisée par un framework hybride) envoient la request et la signalent à New Relic séparément. Dans ce cas, générez les en-têtes et attachez-les vous-même. Tout élément qui signale la requête récupérera l&apos;identité de la trace à partir des en-têtes W3C.

**Si vous envoyez et signalez la request**

Si le même code envoie la request et la signale à New Relic (par exemple, un agent multiplateforme), utilisez `generateDistributedTracingContext` à la place. Il renvoie un dictionnaire avec les en-têtes W3C à définir sur la request (`traceparent`, `tracestate`) ainsi que l’identité de la trace (`trace.id`, `id`, `guid`) à restituer lorsque vous signalez la request, afin que l’événement signalé soit attribué à cette trace plutôt qu’à une nouvelle.

Passez ce même dictionnaire comme paramètre `traceHeaders` de [`noticeNetworkRequestForURL:`](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/network-request-success/) ou de [`noticeNetworkFailureForURL:`](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/network-request-failures/) (sélectionnez l’onglet iOS) lorsque vous signalez la request terminée ; consultez ces pages pour la référence complète des paramètres.

## Activer Infinite Tracing [#infinite-tracing]

Si vos applications mobiles disposent de services en aval qui utilisent notre tracing distribué en fin de workflow [Infinite Tracing](/docs/distributed-tracing/infinite-tracing/introduction-infinite-tracing), vous devez activer cette fonctionnalité pour vos applications mobiles.Cela garantit que votre span racine (l&apos;application mobile d&apos;initiation) est incluse dans le reste des spans suivis par Infinite Tracing.

Pour configurer cela, consultez les [étapes d&apos;Infinite Tracing](/docs/distributed-tracing/infinite-tracing/set-trace-observer) pour créer un observateur de trace et sélectionner les applications mobiles (sources de données) qui doivent signaler les spans.

## Rechercher des données [#find-data]

Les spans mobiles apparaissent dans toute [interface utilisateur de tracing distribué New Relic](/docs/understand-dependencies/distributed-tracing/ui-data/additional-distributed-tracing-features-new-relic-one/) où ces spans font partie d&apos;une trace.

Voici quelques conseils pour rechercher et interroger des données :

* Vous pouvez trouver la trace d&apos;origine finale de l&apos;utilisateur dans n&apos;importe quelle [interface utilisateur de tracing distribué New Relic](/docs/understand-dependencies/distributed-tracing/ui-data/additional-distributed-tracing-features-new-relic-one).
* Dans l’interface utilisateur de tracing distribué, les portées de l’utilisateur final sont indiquées par le<img title="New Relic distributed tracing mobile span icon" alt="New Relic distributed tracing mobile span icon" src="/images/mobile_icon_icon.webp" style={{height: "30px", width: "30px"}}>icône.</img>
* Pour voir l&apos;attribut d&apos;une plage, sélectionnez [une plage dans l&apos;interface utilisateur](/docs/apm/distributed-tracing/ui-data/understand-use-distributed-tracing-data#span-details).
* Les spans sont signalées sous forme [de données de span](/attribute-dictionary/?event=Span) et peuvent être [interrogées dans New Relic](/docs/using-new-relic/data/understand-data/query-new-relic-data).

Par exemple, pour trouver des spans mobiles pour une application spécifique :

```sql
SELECT count(*) FROM Span WHERE mobileApp.name = 'YOUR_APP_NAME' SINCE 1 day ago
```

Pour trouver toute trace qui connecte un span mobile à un span APM backend :

```sql
SELECT * FROM Span WHERE mobileApp.name IS NOT NULL AND appName IS NOT NULL SINCE 1 day ago
```

## Dépannage [#troubleshooting]

Si vous ne voyez pas les spans mobiles là où vous les attendez, vérifiez ces causes possibles :

* **Le tracing distribué est désactivé.** Vérifiez que vous n’avez pas appelé `disableFeatures` avec `NRFeatureFlag_DistributedTracing`. Consultez [Comment configurer le tracing distribué](#setup).
* **La request n’est pas auto-instrumentée.** Les requests effectuées via tout autre moyen que `NSURLSession` ou `NSURLConnection`, y compris les appels Swift `async`/`await` `URLSession`, nécessitent soit l’activation de `NRFeatureFlag_SwiftAsyncURLSessionSupport`, soit une [propagation manuelle](#manual). Voir [Quelles requests bénéficient automatiquement du tracing distribué](#automatic-instrumentation).
* **L&apos;agent APM backend est trop ancien.** Si l&apos;agent APM du service récepteur ne prend pas encore en charge le W3C Trace Context, il démarre une nouvelle trace au lieu de se lier à celle de votre application. Vérifiez les [versions minimales de l’agent APM](#headers).
* **Un proxy ou un gateway supprime les en-têtes.** Tout ce qui se trouve entre votre application et le backend doit transmettre `traceparent` et `tracestate` sans modification.
* **`tracestate` est rejeté car la clé de compte de confiance ne correspond pas.** Si un service backend appartient à un compte New Relic différent de celui de votre application mobile, confirmez que le compte se trouve dans la même relation de confiance, sinon l’entrée `tracestate` peut être ignorée.

Pour des problèmes plus généraux de tracing distribué, consultez [dépannage](/docs/apm/distributed-tracing/troubleshooting/troubleshooting-missing-trace-data).
