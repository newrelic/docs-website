Les agents New Relic Android <InlinePopover type="mobile" />prennent en charge le tracing distribué. Cela vous permet de voir comment l’activité de votre application mobile se connecte aux services associés.

## Exigences [#requirements]

Pour utiliser le tracing distribué, vous avez besoin au moins de la version 6.0.0 de l&apos;agent Android . Nous vous recommandons d&apos;utiliser l&apos;agent le plus récent.

## Comment configurer le tracing distribué [#setup]

Le tracing distribué est activé par défaut : vous n’avez rien à faire pour l’activer. Les en-têtes de tracing distribué sont envoyés sur chaque request auto-instrumentée, quels que soient les autres paramètres.

Si vous préférez le désactiver, consultez [Désactiver le tracing distribué](#disable) ci-dessous.

Pour voir la trace corrélée à l&apos;activité réseau de votre application dans New Relic (l&apos;événement `MobileRequest` ou `MobileRequestError` signalé), vous devez activer [AnalyticsEvents](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/configure-settings/#android-analytics-settings) ; cette option est activée par défaut et constitue un prérequis pour envoyer tout événement d&apos;analyse de votre application, et non une spécificité du tracing distribué.

## En-têtes de tracing distribué [#headers]

À partir de la version 7.8.3 de l’agent Android, l’agent ajoute uniquement les en-têtes [W3C Trace Context](/docs/distributed-tracing/concepts/how-new-relic-distributed-tracing-works/#headers), `traceparent` et `tracestate`, aux requests réseau sortantes. Il n’envoie plus l’en-tête propriétaire `newrelic`. Les versions antérieures de l’agent envoient les trois en-têtes.

Les agents New Relic APM qui prennent en charge W3C Trace Context utilisent ces en-têtes pour continuer la trace, afin que les requests de votre application restent connectées aux services backend qu&apos;elles appellent. W3C Trace Context est pris en charge dans ces versions d&apos;agent APM et supérieures :

## Quelles requests obtiennent automatiquement le tracing distribué [#automatic-instrumentation]

Le plug-in Gradle de l&apos;agent Android instrumente le bytecode de votre application au moment de la compilation, de sorte que les en-têtes de tracing distribué sont ajoutés automatiquement aux requests effectuées via :

* `OkHttp` (versions 2 et 3)
* Apache `HttpClient`
* `HttpURLConnection`
* Retrofit

Étant donné que cette instrumentation tisse directement les sites d’appel de ces bibliothèques, le code qui les encapsule (y compris les coroutines Kotlin et les fonctions de suspension) devrait également être couvert, car les sites d’appel sous-jacents sont tissés indépendamment de ce qui les appelle.

L’agent n’ajoute pas automatiquement les en-têtes de tracing distribué aux :

* Volley. L’agent ne prend pas du tout en charge Volley, les requests Volley nécessitent donc une [propagation manuelle](#manual) si vous souhaitez qu’elles soient tracées.
* `WebView`. L&apos;instrumentation `WebView` de l&apos;agent couvre le temps de chargement des pages, et non les en-têtes de requests réseau, de sorte que les requests effectuées à partir de contenu web chargé dans un `WebView` ne sont pas tracées automatiquement.
* Toute autre bibliothèque réseau tierce ou tout autre transport personnalisé qui ne passe pas par les bibliothèques listées ci-dessus.

Pour n&apos;importe lequel d&apos;entre eux, utilisez la propagation manuelle.

## Propager manuellement le tracing distribué [#manual]

Si vous effectuez une requête via une bibliothèque que l’agent n’instrumente pas automatiquement, vous pouvez toujours ajouter des en-têtes de tracing distribué et signaler la requête vous-même.

`noticeDistributedTrace` prend un argument facultatif, un `Map<String, String>` d’attributs de requête à conserver sur le contexte de trace. Passez `null` si vous n’en avez aucun. Le contexte de trace retourné expose également les ID de la requête :

* `getTraceId()` retourne l’ID de trace de 32 caractères.
* `getParentId()` retourne l’ID de span de 16 caractères pour cette requête.

Pour enregistrer ces ID en tant qu’attributs sur vos événements de requête réseau, ajoutez-les à la requête en tant qu’en-têtes supplémentaires et enregistrez ces noms d’en-têtes avec [`addHTTPHeadersTrackingFor`](/docs/mobile-monitoring/new-relic-mobile/mobile-sdk/add-tracked-headers/).

## Désactiver le tracing distribué [#disable]

```java
NewRelic.disableFeature(FeatureFlag.DistributedTracing)
```

## Activer Infinite Tracing [#infinite-tracing]

Si vos applications mobiles disposent de services en aval qui utilisent notre tracing distribué en fin de workflow [Infinite Tracing](/docs/distributed-tracing/infinite-tracing/introduction-infinite-tracing), vous devez activer cette fonctionnalité pour vos applications mobiles.Cela garantit que votre span racine (l&apos;application mobile d&apos;initiation) est incluse dans le reste des spans suivis par Infinite Tracing.

Pour configurer cela, consultez les [étapes d&apos;Infinite Tracing](/docs/distributed-tracing/infinite-tracing/set-trace-observer) pour créer un observateur de trace et sélectionner les applications mobiles (sources de données) qui doivent signaler les spans.

## Rechercher des données [#find-data]

Les spans mobiles apparaissent dans toute [interface utilisateur de tracing distribué New Relic](/docs/understand-dependencies/distributed-tracing/ui-data/additional-distributed-tracing-features-new-relic-one/) où ces spans font partie d&apos;une trace.

Voici quelques conseils pour rechercher et interroger des données :

* Vous pouvez trouver la trace d&apos;origine finale de l&apos;utilisateur dans n&apos;importe quelle [interface utilisateur de tracing distribué New Relic](/docs/understand-dependencies/distributed-tracing/ui-data/additional-distributed-tracing-features-new-relic-one).

* Dans l&apos;interface utilisateur de tracing distribué, les portées de l&apos;utilisateur final sont indiquées par le<img title="New Relic distributed tracing mobile span icon" alt="New Relic distributed tracing mobile span icon" src="/images/mobile_icon_icon.webp" style={{height: "30px", width: "30px"}}>icône.</img>

* Pour voir l&apos;attribut d&apos;une plage, sélectionnez [une plage dans l&apos;interface utilisateur](/docs/apm/distributed-tracing/ui-data/understand-use-distributed-tracing-data#span-details).

* Les spans sont signalées sous forme [de données de span](/attribute-dictionary/?event=Span) et peuvent être [interrogées dans New Relic](/docs/using-new-relic/data/understand-data/query-new-relic-data).

* Conseils de requête :

  * requête par nom en définissant `mobileApp.name` sur le nom de l&apos;application mobile.
  * requête de trace contenant au moins une application mobile avec `mobileApp.name is not null`.
  * requête de trace contenant au moins une application backend avec `appName is not null`.
  * requête de trace contenant à la fois les spans mobiles et backend en combinant les deux conditions précédentes.

Par exemple, pour trouver des spans mobiles pour une application spécifique :

```sql
SELECT count(*) FROM Span WHERE mobileApp.name = 'YOUR_APP_NAME' SINCE 1 day ago
```

Pour trouver toute trace qui connecte un span mobile à un span APM backend :

```sql
SELECT * FROM Span WHERE mobileApp.name IS NOT NULL AND appName IS NOT NULL SINCE 1 day ago
```

## Dépannage [#troubleshooting]

Si vous ne voyez pas les spans mobiles là où vous les attendez, vérifiez ces causes possibles :

* **Le tracing distribué est désactivé.** Vérifiez que vous n’avez pas appelé `disableFeature` avec `FeatureFlag.DistributedTracing`. Consultez [Comment configurer le tracing distribué](#setup).
* **AnalyticsEvents est désactivé.** Les en-têtes sont toujours envoyés, mais l’événement `MobileRequest`/`MobileRequestError` associé ne sera pas envoyé. Consultez [Comment configurer le tracing distribué](#setup).
* **La request n’est pas auto-instrumentée.** Les requests effectuées via Volley, un `WebView`, ou toute bibliothèque autre que `OkHttp`, Apache `HttpClient`, `HttpURLConnection`, ou Retrofit nécessitent une [propagation manuelle](#manual). Consultez [Quelles requests obtiennent automatiquement le tracing distribué](#automatic-instrumentation).
* **L&apos;agent APM backend est trop ancien.** Si l&apos;agent APM du service récepteur ne prend pas encore en charge le W3C Trace Context, il démarre une nouvelle trace au lieu de se lier à celle de votre application. Vérifiez les [versions minimales de l’agent APM](#headers).
* **Un proxy ou un gateway supprime les en-têtes.** Tout ce qui se trouve entre votre application et le backend doit transmettre `traceparent` et `tracestate` sans modification.
* **`tracestate` est rejeté car la clé de compte de confiance ne correspond pas.** Si un service backend appartient à un compte New Relic différent de celui de votre application mobile, confirmez que le compte se trouve dans la même relation de confiance, sinon l’entrée `tracestate` peut être ignorée.

Pour des problèmes plus généraux de tracing distribué, consultez [dépannage](/docs/apm/distributed-tracing/troubleshooting/troubleshooting-missing-trace-data).
