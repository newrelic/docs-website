Une fois que vous avez créé votre première flotte à l&apos;aide du [guide de configuration](/docs/new-relic-control/fleet-control/setup), vous effectuerez la plupart de vos tâches quotidiennes depuis l&apos;interface utilisateur <DNT>Fleet Control</DNT>. Bien que ces opérations puissent également être effectuées par programmation via l&apos;API, cette page se concentre sur les workflows de l&apos;interface utilisateur pour la gestion de vos flottes, déploiements et configurations.

## Comprendre les types de flottes

<DNT>Fleet Control</DNT> prend en charge trois types de flottes, chacune conçue pour un type d&apos;entité gérée spécifique :

* **Flottes de clusters Kubernetes :** Gérez les clusters Kubernetes où les agents sont déployés en tant que charts Helm.
* **Flottes d&apos;hôtes Linux :** Gérez les serveurs Linux sur lesquels les agents s&apos;exécutent en tant que processus basés sur l&apos;hôte. (Aperçu public)
* **Flottes d&apos;hôtes Windows :** Gérez les serveurs Windows sur lesquels les agents s&apos;exécutent en tant que services Windows ou processus basés sur l&apos;hôte. (Aperçu public)

Lorsque vous créez une flotte, vous sélectionnez son type d&apos;entité gérée. Ce choix a des implications importantes sur la façon dont vous travaillez avec cette flotte :

* **Affectation d&apos;entité :** Vous ne pouvez ajouter que des entités gérées correspondant au type de la flotte. Par exemple, une flotte d&apos;hôtes Windows ne peut contenir que des hôtes Windows et une flotte de clusters Kubernetes ne peut contenir que des clusters Kubernetes.
* **Filtrage des configurations :** Lors du déploiement, seules les configurations correspondant au type de flotte vous seront présentées. Si vous travaillez avec une flotte d&apos;hôtes Windows, seules les configurations d&apos;hôtes Windows s&apos;afficheront dans le sélecteur de configuration. Ce filtrage automatique évite les mauvaises configurations et simplifie le processus de déploiement.
* **Disponibilité de l&apos;Agent :** la liste des agents disponibles pour le déploiement sera filtrée en fonction du type de flotte et de ce qui est pris en charge pour cet environnement. Par exemple, certains agents peuvent n&apos;être disponibles que pour les environnements Kubernetes ou des systèmes d&apos;exploitation hôtes spécifiques.

Cette conception garantit la cohérence entre toutes les entités gérées d&apos;une flotte et évite les erreurs de configuration, telles que la tentative accidentelle de déployer une configuration de chart Helm Kubernetes sur un hôte Windows.

## La page des flottes

Lorsque vous accédez à <DNT>New Relic Control → Fleets</DNT>, vous arrivez sur la page principale <DNT>Fleets</DNT>, qui fournit une vue d&apos;ensemble de l&apos;intégralité de votre environnement <DNT>Fleet Control</DNT>. À partir d&apos;ici, vous pouvez :

* **Rechercher des flottes :** utilisez la barre de recherche pour trouver une flotte spécifique par nom.
* **Afficher les comptes récapitulatifs :** consultez le nombre total de votre flotte et le nombre d&apos;entités gérées non attribuées.
* **Voir la répartition du parc :** visualisez la répartition de vos parcs par type (cluster Kubernetes ou hôte).

### Actions de la flotte

Depuis la page principale des flottes, vous pouvez cliquer sur les points de suspension (`...`) à l&apos;extrême droite de n&apos;importe quelle flotte pour afficher un menu d&apos;actions :

* **Modifier les paramètres :** vous permet de modifier le nom et la description d&apos;une flotte.

* **Modifier les autorisations :** vous permet de gérer les contrôles d&apos;accès précis (FGA) de la flotte en modifiant le groupe ou le rôle associé.

* **Supprimer une flotte :** supprime définitivement la flotte. Avant qu&apos;une flotte puisse être supprimée, les conditions suivantes doivent être remplies :

  * Toutes les entités gérées doivent être retirées de la flotte.
  * La flotte ne peut avoir aucun déploiement en cours actuellement.

### Autorisations de flotte (accès précis)

<DNT>Fleet Control</DNT> utilise l&apos;accès à granularité fine (FGA) pour permettre aux administrateurs de déléguer la gestion de flottes spécifiques à certains utilisateurs ou groupes. Cela est utile lorsque vous souhaitez permettre à une équipe de gérer ses propres flottes sans lui accorder d&apos;autorisations étendues au niveau de l&apos;organisation.

La méthode principale pour déléguer l&apos;accès consiste à attribuer le rôle prédéfini <DNT>**Fleet Manager**</DNT> à un groupe d&apos;utilisateurs pour une flotte spécifique. Cela donne aux utilisateurs de ce groupe un contrôle total sur cette flotte, y compris la possibilité de créer des déploiements, de gérer les configurations et d&apos;ajouter ou de supprimer des entités gérées.

#### Prérequis pour l&apos;administrateur

Pour configurer les autorisations de flotte, vous devez disposer des rôles <DNT>Organization Manager</DNT> et <DNT>AuthDomain Manager</DNT>.

#### Configuration workflow

Le processus comprend deux étapes principales : premièrement, un administrateur crée un groupe d’utilisateurs, et deuxièmement, il attribue à ce groupe le rôle <DNT>`Fleet Manager`</DNT> pour une flotte spécifique.

**Étape 1 : Créer un groupe utilisateur**

1. Au bas du menu de navigation de gauche, cliquez sur votre nom d&apos;utilisateur, puis sélectionnez <DNT>**Administration**</DNT>.
2. Sur la page <DNT>Administration</DNT>, sélectionnez <DNT>**Access Management**</DNT>.
3. Allez dans l&apos;onglet <DNT>groups</DNT> et cliquez sur **Create a new group**.
4. Donnez au groupe un nom significatif (par exemple, `k8s-platform-team-fleet-managers`).
5. Sous la section <DNT>members</DNT>, ajoutez les utilisateurs auxquels vous souhaitez déléguer la gestion de la flotte.
6. Cliquez sur <DNT>**Add user to the group**</DNT>. Vous n&apos;avez pas besoin d&apos;attribuer de rôles au niveau du compte ou de l&apos;organisation ici. Les autorisations seront accordées au niveau de la flotte.

**Étape 2 : Attribuer un groupe et un rôle à une flotte**

Vous pouvez attribuer des autorisations soit lorsque vous créez une nouvelle flotte, soit en modifiant une flotte existante.

**Pour attribuer des autorisations à une flotte existante :**

1. Depuis la page principale <DNT>fleets</DNT>, trouvez le parc que vous souhaitez gérer.

2. Cliquez sur les points de suspension (`...`) à la fin de la ligne et sélectionnez **Edit permissions**.

3. Dans la fenêtre modale <DNT>fleet permissions</DNT> :

   * <DNT>**Select a group**</DNT>: Choisissez le groupe d&apos;utilisateurs que vous avez créé à l&apos;étape précédente.
   * **Sélectionnez un rôle :** Choisissez le rôle <DNT>`Fleet Manager`</DNT>.

4. Cliquez sur <DNT>**Save**</DNT>. Les utilisateurs du groupe sélectionné disposent désormais de permissions de gestion complètes pour cette flotte.

**Pour attribuer des autorisations lors de la création d’une flotte :**

1. Suivez les étapes de [création d&apos;une flotte dans notre guide de configuration](/docs/new-relic-control/fleet-control/setup).
2. Avant de cliquer sur **Create Fleet**, dans la section <DNT>access management authorization</DNT>, utilisez la liste déroulante pour sélectionner le **Group** souhaité et le rôle de **Fleet Manager**.
3. Cliquez sur **Create Fleet**.

## Gérer une flotte spécifique

En cliquant sur le nom d&apos;une flotte, vous accédez à sa page de gestion détaillée.

<Callout title="Important : règles de configuration de la flotte" variant="important">
  Les flottes sont conçues pour assurer la cohérence de toutes les entités gérées. Pour ce faire, trois règles importantes s&apos;appliquent :

  * **Cohérence du type d&apos;entité gérée :** Chaque flotte possède un type d&apos;entité gérée spécifique (Cluster Kubernetes, Hôte Linux ou Hôte Windows) défini lors de la création de la flotte. Vous pouvez uniquement affecter à la flotte des entités gérées correspondant à ce type. Cela garantit que toutes les entités de la flotte sont compatibles avec les mêmes configurations et stratégies de déploiement. Consultez [Comprendre les types de flottes](#understanding-fleet-types) pour plus de détails.

  * **Une configuration par type d&apos;agent :** Au sein d&apos;une même flotte, vous ne pouvez avoir qu&apos;une seule configuration pour chaque type d&apos;agent. Par exemple, si vous avez trois clusters Kubernetes dans une flotte, ils doivent tous utiliser la même configuration unique pour l&apos;agent New Relic Infrastructure. La cardinalité d&apos;un type d&apos;agent par rapport à sa configuration au sein d&apos;une flotte est toujours 1:1.

  * **Instrumentation d&apos;infrastructure exclusive :** Le système vous empêche de déployer à la fois l&apos;agent Infrastructure New Relic et la distribution New Relic du collecteur OpenTelemetry (NRDOT) sur la même flotte. Cette validation permet d&apos;éviter une double instrumentation accidentelle de vos entités gérées pour le monitoring de l&apos;infrastructure.
</Callout>

### L&apos;en-tête de flotte : tag et métadonnées

En haut de la page, l&apos;en-tête affiche le nom de la flotte ainsi que les boutons cliquables **Tags** et **Metadata**. Ils fournissent un accès rapide aux informations d&apos;identification importantes pour le parc.

* **Tags :** Cliquer ici révèle un ensemble complet de données de paires valeur-clé associées à la flotte, telles que le `accountId`, le `description` de la flotte et l&apos;horaire de création ou de mise à jour.
* **Métadonnées :** Cliquer ici affiche les principaux détails d&apos;identification de la flotte en tant qu&apos;entité New Relic, tels que ses `Entity guid`, `Account ID` et `Managed entities type`.

La page de gestion détaillée est organisée en trois onglets principaux : **Summary**, **Agents** et **Deployments**.

### L&apos;onglet Résumé

Cet onglet fournit un aperçu de l&apos;état actuel de la flotte, organisé en trois tableaux :

* <DNT>**Active deployment table:**</DNT> Affiche le nom du déploiement le plus récent, le nombre d&apos;agents/configurations inclus et la date de sa dernière mise à jour.
* <DNT>**Agents table:**</DNT> Liste les types d&apos;agents, leurs configurations et versions associées, ainsi que la date de création de la configuration.
* <DNT>**Managed entities table:**</DNT> Répertorie toutes les entités affectées à la flotte, leur compte, leur type et l&apos;état actuel de l&apos;instrumentation. Il inclut également un lien **View entity** qui vous dirige vers la page principale de l&apos;entité ailleurs dans la plateforme New Relic (par exemple, l&apos;explorateur de clusters Kubernetes).

### L&apos;onglet agents

Cet onglet fournit une vue détaillée de tous les agents exécutés sur l&apos;entité gérée au sein de la flotte. Vous pouvez utiliser la barre de recherche en haut de cet onglet pour trouver un agent spécifique par son nom ou son type.

Un détail important est que le superviseur <DNT>New Relic Agent Control</DNT> est également répertorié ici en tant que type d&apos;agent. Pour chaque agent, vous pouvez voir l&apos;entité gérée associée, le statut de l&apos;instrumentation, le statut de la configuration à distance et le moment de la dernière réception d&apos;un signal de vie.

#### Afficher la configuration effective

Une fonctionnalité clé de l&apos;onglet <DNT>agents</DNT> est la possibilité de voir la *configuration effective* de tout agent. Cliquez sur le nom d&apos;un agent pour ouvrir une vue détaillée. Ici, vous pouvez consulter des métadonnées telles que la version du chart Helm, mais surtout, vous pouvez visualiser la configuration exacte exécutée sur l&apos;agent en temps réel.

La configuration effective peut parfois différer de la configuration que vous avez utilisée, car elle prend en compte les remplacements provenant de sources telles que les variables d&apos;environnement locales. Cette vue est précieuse pour les problèmes liés à configurationdu dépannage.

### L&apos;onglet déploiement

Cet onglet contient l&apos;historique complet du déploiement de la flotte. Vous pouvez utiliser la barre de recherche pour trouver un déploiement spécifique par son nom. Le tableau répertorie le nom de chaque déploiement, son statut, le nombre d&apos;agents/configurations et la date de la dernière mise à jour. Le déploiement réussi le plus récent est marqué d&apos;une étiquette `Active` pour indiquer qu&apos;il s&apos;agit de celui actuellement appliqué sur la flotte.

Cliquer sur le nom d&apos;un déploiement vous dirige vers une vue récapitulative de ce déploiement spécifique. Cette vue est organisée en deux onglets :

#### Onglet Détails

L&apos;onglet <DNT>details</DNT> fournit un résumé du déploiement, incluant :

* déployées métadonnées (nom, type, description, heures de début/fin et un identifiant déployé pour le dépannage).
* Un tableau <DNT>**Agents**</DNT> indiquant le type d&apos;agent, l&apos;action effectuée (par exemple, installation, mise à jour) et la version de la configuration.
* Un tableau <DNT>**Managed Entities**</DNT> indiquant exactement quelles entités ont été affectées par le déploiement et si elles ont été marquées comme canaris.

#### Onglet Événements de déploiement

L&apos;onglet <DNT>deployment events</DNT> offre une visibilité granulaire au niveau des événements sur chaque action survenue pendant le déploiement. Cet onglet est essentiel pour dépanner les problèmes de déploiement et comprendre les causes racines. Vous pouvez :

* Affichez les événements atomiques avec des détails comprenant l&apos;horodatage, le statut, le nom de l&apos;entité gérée, le nom de l&apos;agent, le type d&apos;agent, le type d&apos;événement, les détails et la durée.
* Recherchez des événements spécifiques par mot-clé.
* Filtrez les événements par entité gérée pour vous concentrer sur un cluster ou un hôte spécifique (utile lors du dépannage de défaillances dans de grands parcs).
* Filtrer les événements par statut (par exemple, Terminé, Configuration appliquée, Application en cours).
* Accédez à la requête NRQL sous-jacente pour un dépannage avancé en cliquant sur le bouton à droite de l&apos;en-tête du tableau des événements.

Pour plus d&apos;informations sur l&apos;utilisation de l&apos;onglet <DNT>deployment events</DNT> pour le dépannage, consultez notre [documentation de dépannage](/docs/new-relic-control/fleet-control/troubleshooting).

## Compréhension

Un déploiement est un ensemble contrôlé d&apos;actions pouvant installer, supprimer ou mettre à jour des agents et leurs configurations sur les entités gérées de votre parc. Cette section couvre les aspects clés du cycle de vie du déploiement, y compris la compréhension des différents statuts de déploiement, le processus de mise à niveau automatique pour <DNT>Agent Control</DNT>, ainsi que l&apos;utilisation de fonctionnalités avancées telles que les déploiements brouillons et canary pour gérer les changements en toute sécurité.

### Comprendre les statuts de déploiement

L’état de chaque déploiement vous aide à comprendre son résultat. Voici les statuts possibles et ce qu&apos;ils signifient :

| Statut                             | Description                                                                                                                                                                                                                                                                                                                 |
| :--------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 🔵 <DNT>**IN PROGRESS**</DNT>      | Le déploiement est en cours de déploiement actif auprès de l&apos;entité gérée de la flotte.                                                                                                                                                                                                                                |
| 🟢 <DNT>**COMPLETED**</DNT>        | Le déploiement s&apos;est terminé avec succès et toutes les actions prévues ont été appliquées.                                                                                                                                                                                                                             |
| 🔴 <DNT>**FAILED**</DNT>           | Le déploiement est terminé, mais au moins un agent sur une entité gérée a signalé un problème. Cela peut signifier qu&apos;un agent n&apos;a pas réussi à démarrer, à s&apos;arrêter correctement ou à appliquer sa nouvelle configuration. Le déploiement peut être partiellement réussi sur d&apos;autres entités gérées. |
| 🟠 <DNT>**INTERNAL FAILURE**</DNT> | Le déploiement n&apos;a pas pu être terminé en raison d&apos;un problème inattendu au sein du système <DNT>Fleet Control</DNT>. Il ne s&apos;agit pas d&apos;une erreur de vos agents ou de vos configurations. Veuillez réessayer le déploiement et, si le problème persiste, contactez le support New Relic.              |

### Comprendre le flux d&apos;événements de déploiement

Lorsque vous consultez l&apos;onglet <DNT>deployment events</DNT>, vous voyez une série d&apos;événements représentant le cycle de vie de votre déploiement. Tous les événements de déploiement sont écrits dans le type d&apos;événement personnalisé `FleetDeployment`. Comprendre ce flux d&apos;événements vous aide à interpréter ce que vous voyez dans l&apos;onglet <DNT>deployment events</DNT> et à diagnostiquer les problèmes plus efficacement.

<DNT>Fleet Control</DNT> déploie les modifications de configuration par étapes appelées « anneaux » pour réduire les risques. Le processus de déploiement se déroule comme suit :

* **Si vous avez désigné des entités canary :** Le déploiement utilise d&apos;abord un anneau canary (contenant uniquement les entités que vous avez marquées comme canary), suivi d&apos;un anneau par défaut pour toutes les entités restantes. Chaque anneau doit se terminer avec succès avant que l&apos;anneau suivant ne commence. Si l&apos;anneau canary échoue, le déploiement s&apos;arrête avant de passer à l&apos;anneau par défaut, évitant ainsi des problèmes généralisés.
* **Si vous n&apos;avez désigné aucune entité canary :** Le déploiement utilise uniquement l&apos;anneau par défaut, qui inclut toutes les entités de la flotte. Le déploiement s&apos;exécutera jusqu&apos;à son terme sur toutes les entités de cet anneau unique.

#### Types d&apos;événements de déploiement

Les événements suivants permettent de suivre la progression d&apos;un déploiement du début à la fin :

| Événement                            | Description                                                                                |
| :----------------------------------- | :----------------------------------------------------------------------------------------- |
| Déploiement de la flotte démarré     | Un déploiement est initié pour la flotte. Les paquets de configuration sont préparés.      |
| Déploiement en anneau démarré        | Un cercle de déploiement commence (par exemple, cercle canary ou par défaut).              |
| AgentDeploymentStarted               | Le déploiement de la configuration commence pour un agent spécifique sur une entité gérée. |
| Déploiement de l&apos;agent terminé  | Un agent termine la tentative d&apos;application de la configuration.                      |
| Déploiement de l&apos;anneau terminé | Tous les agents d&apos;un anneau ont terminé ou ont expiré.                                |
| FleetDeploymentCompleted             | Le déploiement global se termine par un statut final.                                      |

#### Statuts de déploiement de l&apos;Agent

Lorsqu&apos;un agent termine sa tentative de déploiement (AgentDeploymentCompleted), il signale l&apos;un des statuts suivants :

| Statut                     | Description                                                                         |
| :------------------------- | :---------------------------------------------------------------------------------- |
| <DNT>CONFIG\_APPLIED</DNT> | L&apos;agent a appliqué avec succès la nouvelle configuration.                      |
| <DNT>FAILED</DNT>          | L&apos;agent a rencontré une erreur lors de l&apos;application de la configuration. |
| <DNT>TIMEOUT</DNT>         | L&apos;agent n&apos;a pas répondu dans le délai prévu.                              |
| <DNT>NOT\_REPORTING</DNT>  | L&apos;agent était hors ligne lorsque le déploiement a commencé.                    |

#### Comment fonctionne le flux d&apos;événements

Lorsque vous initiez un déploiement, des événements sont générés dans la séquence suivante :

1. **FleetDeploymentStarted** — Le déploiement commence pour l&apos;ensemble de la flotte.
2. **RingDeploymentStarted** — Le premier anneau (généralement canary) démarre, et tous les agents de cet anneau sont identifiés.
3. **AgentDeploymentStarted** — Pour chaque agent du cercle, un événement de déploiement est enregistré. Ces événements se produisent en parallèle pour tous les agents de l&apos;anneau.
4. **AgentDeploymentCompleted** — Chaque agent signale son statut (<DNT>CONFIG\_APPLIED</DNT>, <DNT>FAILED</DNT>, <DNT>TIMEOUT</DNT> ou <DNT>NOT\_REPORTING</DNT>).
5. **RingDeploymentCompleted** — Une fois que tous les agents de l&apos;anneau ont terminé ou ont dépassé le délai d&apos;attente, l&apos;anneau est marqué comme terminé. Si l&apos;anneau a réussi, l&apos;anneau suivant commence. En cas d&apos;échec, le déploiement s&apos;arrête.
6. **FleetDeploymentCompleted** — Une fois tous les anneaux terminés (ou si un anneau échoue), le déploiement se termine avec un statut final de <DNT>COMPLETED</DNT>, <DNT>FAILED</DNT> ou <DNT>INTERNAL\_FAILURE</DNT>.

#### Flux d&apos;événements visuel

```
FleetDeploymentStarted
│
├─▶ RingDeploymentStarted (canary)
│   │
│   ├─▶ AgentDeploymentStarted (agent 1) ──▶ AgentDeploymentCompleted ─┐
│   ├─▶ AgentDeploymentStarted (agent 2) ──▶ AgentDeploymentCompleted ─┤ [parallel]
│   ├─▶ AgentDeploymentStarted (agent 3) ──▶ AgentDeploymentCompleted ─┘
│   │
│   └─▶ RingDeploymentCompleted (canary)
│       │
│       ├─ ✓ If SUCCESS → proceed to default ring
│       └─ ✗ If FAILED → stop deployment
│
├─▶ RingDeploymentStarted (default)
│   │
│   ├─▶ AgentDeploymentStarted (agent 4) ──▶ AgentDeploymentCompleted ─┐
│   ├─▶ AgentDeploymentStarted (agent 5) ──▶ AgentDeploymentCompleted ─┤ [parallel]
│   ├─▶ AgentDeploymentStarted (agent 6) ──▶ AgentDeploymentCompleted ─┘
│   │
│   └─▶ RingDeploymentCompleted (default)
│
└─▶ FleetDeploymentCompleted
```

**Options de statut de déploiement de l&apos;agent :**

* ✅ **CONFIG\_APPLIED** — L&apos;Agent a appliqué la configuration avec succès
* ❌ **FAILED** — L&apos;Agent a rencontré une erreur
* ⏱️ **TIMEOUT** — L&apos;Agent n&apos;a pas répondu à temps
* 📡 **NOT\_REPORTING** — L&apos;agent était hors ligne lorsque le déploiement a commencé

**Identifiants clés :** `fleetId`, `deploymentId`, `ringName`

Vous pouvez visualiser tous ces événements en détail à l&apos;aide de l&apos;onglet Événements de déploiement. Consultez la [section Onglet Déploiements](#the-deployments-tab) pour plus d&apos;informations sur l&apos;accès et l&apos;utilisation des événements de déploiement pour le dépannage.

### Mises à niveau automatiques du contrôle des agents

Pour garantir que vos entités gérées bénéficient des derniers correctifs de sécurité, des améliorations de performances et des fonctionnalités, <DNT>Fleet Control</DNT> gère automatiquement le processus de mise à niveau pour Agent Control. Lorsque vous lancez un déploiement, <DNT>Fleet Control</DNT> vérifie si une version plus récente d&apos;Agent Control est disponible pour les entités gérées de votre flotte.

Si une mise à niveau est requise, elle est automatiquement incluse dans votre déploiement. Vous verrez une notification dans l&apos;interface utilisateur pendant le processus de déploiement vous informant que Agent Control sera mis à niveau. Cette mise à niveau implicite se produit parallèlement à toutes les actions de déploiement que vous effectuez (telles que l&apos;installation d&apos;agents, la suppression d&apos;agents ou la modification de la configuration d&apos;agents), garantissant que votre environnement reste à jour avec un minimum d&apos;effort.

<Callout title="Important : échec de la mise à niveau et récupération" variant="caution">
  Actuellement, il n’existe aucune restauration automatique en cas d’échec de la mise à niveau d’Agent Control. Si une mise à niveau échoue, le déploiement sera marqué comme **FAILED** et l&apos;entité gérée peut nécessiter une intervention manuelle. Pour obtenir des conseils, consultez notre documentation sur [la mise à niveau manuelle d&apos;Agent Control](/docs/new-relic-control/agent-control/upgrading).
</Callout>

## Créer et gérer des brouillons de déploiement

Vous pouvez enregistrer un déploiement en tant que brouillon pour y travailler au fil du temps sans déployer les modifications immédiatement.

### Créer et reprendre un brouillon

1. Accédez à l&apos;onglet <DNT>deployments</DNT> dans une flotte spécifique.
2. Cliquez sur <DNT>**Create deployment**</DNT>.
3. Dans le volet de déploiement, indiquez un nom obligatoire et une description facultative.
4. Apportez les modifications souhaitées, telles que l’ajout d’agents ou la mise à jour de leur configuration.
5. Au lieu de démarrer le déploiement, cliquez sur <DNT>**Save draft**</DNT>.
6. Vous pouvez ensuite fermer le volet de déploiement. Votre nouveau déploiement sera répertorié dans l&apos;onglet <DNT>deployments</DNT> avec le statut `Draft`.

Pour continuer à travailler sur le brouillon, cliquez simplement sur son nom dans le tableau de l&apos;historique de déploiement. Cela rouvrira le volet de déploiement, vous permettant de terminer vos modifications et de cliquer sur **Start deployment** lorsque vous êtes prêt.

### Supprimer un brouillon

Si vous n’avez plus besoin d’un projet de déploiement :

1. Depuis l&apos;onglet <DNT>deployments</DNT>, cliquez sur le nom du brouillon que vous souhaitez supprimer.
2. Dans le volet de déploiement qui s&apos;ouvre, cliquez sur le bouton points de suspension (`...`) à côté de <DNT>Start deployment</DNT> en haut de l&apos;écran.
3. Sélectionnez <DNT>**Delete draft**</DNT> dans le menu.
4. Le brouillon sera définitivement supprimé et vous serez redirigé vers l&apos;onglet <DNT>deployments</DNT>.

### Sélection des versions de l&apos;agent lors du déploiement

Lorsque vous ajoutez un agent à un déploiement, vous êtes invité à sélectionner une version de l&apos;agent avant de choisir une configuration :

1. Après avoir sélectionné le type d&apos;agent, un menu déroulant <DNT>**Select a version**</DNT> s&apos;affiche.

2. La dernière version est sélectionnée par défaut.

3. Vous pouvez choisir parmi d&apos;autres versions disponibles pour l&apos;installation.

4. Des métadonnées supplémentaires peuvent être affichées pour chaque version, telles que :

   * Notes de version mettant en avant les nouvelles fonctionnalités et améliorations
   * Informations sur la mise à jour de sécurité
   * Autres détails spécifiques à la version

Cette fonctionnalité de sélection de version fonctionne sur tous les types d&apos;infrastructures pris en charge (clusters Kubernetes, hôtes Linux et hôtes Windows), vous offrant un contrôle précis sur la version de l&apos;agent déployée sur vos entités gérées.

Une fois la version de votre agent sélectionnée, cliquez sur <DNT>**Next**</DNT> pour passer à la sélection de la configuration.

### Actions de l&apos;agent dans un déploiement

Lorsque vous créez ou modifiez un déploiement, le tableau **Agents** dans le volet de déploiement fournit plusieurs actions pour chaque agent. Cliquez sur les points de suspension (`...`) à droite de la ligne d&apos;un agent pour accéder aux options suivantes :

* **Modifier la configuration :** ouvre l’éditeur de configuration, vous permettant de modifier la configuration de cet agent dans le cadre du déploiement.
* **Utiliser la version la plus récente :** Si vous avez créé plusieurs versions d&apos;une configuration, cette option met automatiquement à jour le déploiement pour utiliser la dernière version de configuration enregistrée.
* **Changer la version de la configuration :** vous permet de sélectionner manuellement une version antérieure spécifique de la configuration à utiliser pour le déploiement.
* **Supprimer du déploiement :** supprime entièrement l’agent et sa configuration de ce déploiement.

<Callout title="Version de l'Agent vs version de la configuration" variant="tip">
  Il est important de distinguer deux types de versions dans <DNT>Fleet Control</DNT>:

  * **Version de l&apos;agent :** La version du logiciel de l&apos;agent lui-même (par exemple, l&apos;agent Infrastructure v1.54.0), sélectionnée lors de l&apos;étape initiale de sélection de l&apos;agent lors de l&apos;ajout d&apos;un agent à un déploiement.
  * **Version de la configuration :** La version du fichier de configuration que vous avez créé pour cet agent, gérée via le menu d&apos;actions ci-dessus.

  Lorsque vous sélectionnez &quot;Utiliser la version la plus récente&quot; ou &quot;Modifier la version de la configuration&quot;, vous gérez la version de la configuration, et non la version de l&apos;agent.
</Callout>

## Gérer les entités d&apos;une flotte

<Callout title="Important : Le principe de l'héritage de la flotte" variant="important">
  Les flottes fonctionnent selon un principe fondamental d’ **héritage**. Cela signifie que toute entité gérée affectée à une flotte sera automatiquement conforme au dernier déploiement actif de cette flotte pour garantir la cohérence de l&apos;instrumentation. Il est essentiel de comprendre ce comportement lors de l’ajout ou de la suppression d’entités, car cela peut entraîner l’installation ou la désinstallation automatique d’agents.
</Callout>

### Supprimer une entité d&apos;une flotte

1. Accédez à l&apos;onglet <DNT>summary</DNT> de la flotte qui contient actuellement l&apos;entité.
2. Dans le tableau <DNT>managed entities</DNT>, utilisez la case à cocher pour sélectionner une ou plusieurs entités que vous souhaitez supprimer.
3. Cliquez sur <DNT>Remove</DNT> qui s&apos;affiche.
4. Une fenêtre de vérification apparaîtra, listant l&apos;entité à supprimer. Pour confirmer, tapez `remove` dans le champ de texte.
5. Cliquez sur <DNT>Remove entities</DNT>. L&apos;entité est désormais désassignée de la flotte.

<Callout title="Important : retour à la configuration locale" variant="caution">
  Lorsqu&apos;une entité gérée est supprimée d&apos;une flotte, elle revient automatiquement à sa **configuration locale**d&apos;origine, c&apos;est-à-dire l&apos;état dans lequel elle se trouvait lors de la première installation d&apos;Agent Control. Cela peut entraîner la désinstallation des agents. Par exemple, si la flotte avait l&apos;infrastructure et les agents Fluent Bit installés, mais que la configuration locale de l&apos;entité inclut uniquement le contrôle des agents, les deux agents seront désinstallés lors de la suppression pour garantir qu&apos;ils correspondent à l&apos;état local.
</Callout>

### Ajouter une entité gérée non attribuée à une flotte

Vous ajoutez une entité gérée non attribuée à une flotte en créant un nouveau déploiement. Ce processus associe l&apos;entité à la flotte et à sa configuration de déploiement.

1. Accédez à la flotte où vous souhaitez ajouter l&apos;entité et cliquez sur <DNT>**Create a deployment**</DNT>.
2. Donnez au déploiement un nom et une description significatifs.
3. Dans le tableau <DNT>managed entities</DNT> en bas de l&apos;écran de déploiement, cliquez sur le bouton <DNT>**Add managed entities**</DNT>.
4. Un volet s&apos;ouvrira, affichant une liste de toutes vos entités gérées non attribuées.
5. Utilisez les cases de sélection pour choisir une ou plusieurs entités que vous souhaitez ajouter à la flotte.
6. Cliquez sur <DNT>Add to deployment</DNT>. Les entités sélectionnées apparaîtront désormais dans le tableau <DNT>managed entities</DNT> pour ce déploiement.
7. Cliquez sur <DNT>Save draft</DNT> puis sur <DNT>Start deployment</DNT> pour terminer le processus. Les entités seront désormais assignées à la nouvelle flotte.

<Callout title="Important : héritage du dernier déploiement actif" variant="important">
  Lorsque vous ajoutez une entité gérée à une flotte, un déploiement implicite s&apos;exécute en arrière-plan. Ce déploiement installe, met à jour ou supprime automatiquement l&apos;instrumentation sur la nouvelle entité pour garantir qu&apos;elle correspond parfaitement au dernier **déploiement actif** de la flotte. Par exemple, si le déploiement actif de la flotte inclut les agents Infrastructure et Fluent Bit, mais que la nouvelle entité ne disposait auparavant que de l&apos;agent OTel, l&apos;agent OTel sera supprimé et les agents <DNT>Infrastructure</DNT> et <DNT>Fluent Bit</DNT> seront installés.
</Callout>

## Utiliser le canari

<DNT>Fleet Control</DNT> vous permet de désigner une ou plusieurs entités gérées en tant que « canary » lors du processus de déploiement. Cela fournit un mécanisme de sécurité crucial pour le déploiement des modifications.

Lorsque vous créez un nouveau déploiement, vous pouvez utiliser les points de suspension (`...`) à côté de n’importe quelle entité gérée dans la liste et la désigner comme canari.

Lorsque le déploiement commence :

1. Les modifications ne s&apos;appliquent *qu&apos;à* l&apos;entité gérée marquée comme canaris.
2. Le processus de déploiement s&apos;arrête et attend que le déploiement du canari réussisse.
3. Si un déploiement Canary échoue, l’ensemble du déploiement s’arrête immédiatement et aucune autre entité gérée n’est affectée.
4. Si tous les déploiements canaris réussissent, le déploiement se poursuit vers le reste de l&apos;entité gérée dans la flotte.

<Callout title="Important : pas de restauration automatique pour les canaris ayant échoué" variant="caution">
  Si un déploiement Canary échoue, l&apos;entité gérée à laquelle il était destiné restera dans un état **Failed**. Il n’y a pas de retour automatique à la configuration précédente. Vous devrez créer un nouveau déploiement pour annuler les modifications ou résoudre le problème.
</Callout>

## La page de configuration

<Callout title="Important : les configurations sont globales" variant="important">
  Toutes les configurations que vous créez dans <DNT>Fleet Control</DNT> sont **globales**. Cela signifie qu&apos;ils sont disponibles dans l&apos;ensemble de votre organisation New Relic et peuvent être déployés sur n&apos;importe quelle flotte qui en a besoin, quel que soit le créateur de la configuration.
</Callout>

Lorsque vous accédez à <DNT>New Relic Control → Configurations</DNT>, vous arrivez sur la page principale Configurations, qui est le point central pour gérer toutes les configurations de vos agents.

### Aperçu de la page principale

Cette page fournit un aperçu de haut niveau de toutes les configurations disponibles dans votre compte. À partir d&apos;ici, vous pouvez :

* **Afficher le nombre récapitulatif :** consultez le nombre total de vos configuration.
* **Voir la distribution configuration :** affichez une répartition de votre configuration par type d&apos;agent (par exemple, New Relic Infrastructure, Fluent Bit, NRDOT collecteur).
* **Rechercher une configuration :** utilisez la barre de recherche pour trouver une configuration spécifique par son nom ou le type d’agent associé.
* **Actualiser la liste :** Si vous venez de créer une nouvelle configuration et que vous ne la voyez pas dans le tableau, cliquez sur le bouton d&apos;actualisation situé à gauche de <DNT>**Create configuration**</DNT>.

La page affiche un tableau de votre configuration avec les colonnes suivantes :

* **configuration :** Le nom de la configuration.
* **Agent :** le type d’agent auquel la configuration s’applique.
* **Révisions :** le nombre de versions existantes pour la configuration.
* **Type :** Le type d&apos;entité gérée (par exemple, Cluster Kubernetes, Hôte Linux ou Hôte Windows).
* **Dernière modification :** un horodatage de la dernière mise à jour.

### Actions de configuration

À partir du tableau de configuration principal, vous pouvez cliquer sur les points de suspension (`...`) à l&apos;extrême droite de n&apos;importe quelle configuration pour la **Edit**. Cela ouvre le volet d&apos;édition principal dans lequel vous pouvez modifier le fichier de configuration. Cette vue fournit également des boutons pour **Download** le fichier de configuration sur votre machine locale ou **Copy** son contenu dans votre presse-papiers.

### Comprendre la configuration

La structure d&apos;un fichier de configuration dépend du **Type d&apos;entité gérée** que vous sélectionnez (Cluster Kubernetes, Hôte Linux ou Hôte Windows).

* **Pour les clusters Kubernetes,** la configuration que vous créez dans l&apos;interface est un fichier `values.yaml`. Lors du déploiement, <DNT>Fleet Control</DNT> empaquette ce fichier avec le chart Helm de l&apos;agent pour le configurer sur votre cluster. Les modèles pour les agents Kubernetes sont structurés sous la forme d&apos;un fichier `values.yaml` de chart Helm canonique. Près du haut du modèle, vous trouverez un lien en commentaire vers le chart Helm de l&apos;agent dans le [dépôt GitHub New Relic Helm Charts](https://github.com/newrelic/helm-charts). Cela vous permet de consulter facilement le schéma, les valeurs disponibles et d&apos;autres documents spécifiques à l&apos;agent.
* **Pour les hôtes,** le format du fichier configuration est spécifique à l&apos;agent déployé.

<Callout title="Filtrage de la configuration dans les déploiements" variant="tip">
  Lors de la création d&apos;un déploiement pour une flotte, le système filtre automatiquement les configurations disponibles pour n&apos;afficher que celles qui correspondent au type d&apos;entité gérée de la flotte. Par exemple :

  * Une **flotte de clusters Kubernetes** affichera uniquement les configurations créées pour les clusters Kubernetes.
  * Une **flotte d&apos;hôtes Linux** n&apos;affichera que les configurations créées pour les hôtes Linux.
  * Une **flotte d&apos;hôtes Windows** n&apos;affichera que les configurations créées pour les hôtes Windows.

  Ce filtrage automatique garantit que vous ne pouvez pas déployer accidentellement une configuration incompatible sur vos entités gérées, assurant ainsi la cohérence et évitant les échecs de déploiement.
</Callout>

<Callout title="Bonne pratique de sécurité : Gestion des données sensibles dans Kubernetes" variant="important">
  Pour les déploiements Kubernetes, n&apos;incluez jamais de données sensibles telles que votre `licenseKey` directement dans les fichiers de configuration. Utilisez plutôt la gestion des secrets d&apos;Agent Control pour injecter en toute sécurité des valeurs sensibles lors de l&apos;exécution. Pour plus d&apos;informations, consultez notre [documentation sur la gestion des secrets](/docs/new-relic-control/agent-control/configuration#secrets-management).
</Callout>

### Créer une configuration

Pour créer une nouvelle configuration globale à partir de zéro :

1. Depuis la page principale Configurations, cliquez sur <DNT>**Create configuration**</DNT>.

2. Dans la fenêtre modale qui s&apos;affiche, vous devez :

   * Sélectionnez le <DNT>**managed entity type**</DNT> (Cluster Kubernetes, Hôte Linux ou Hôte Windows). Notez que la prise en charge des hôtes Linux et Windows est actuellement en préversion publique.
   * Sélectionnez le <DNT>**Agent type**</DNT> (par exemple, New Relic Infrastructure, NRDOT collector, Fluent Bit) dans le menu déroulant. Les types d&apos;agents disponibles seront filtrés en fonction du type d&apos;entité gérée que vous avez sélectionné.
   * Fournissez un <DNT>**Name**</DNT> significatif et unique pour la configuration.

3. Cliquez sur <DNT>**Continue**</DNT>. Cela ouvre la vue d&apos;édition de la configuration, qui est divisée en deux volets.

   * **Volet gauche (configuration active) :** c&apos;est ici que vous créez votre configuration. Vous pouvez taper directement dans ce volet ou coller du contenu à partir d&apos;une autre source.
   * **Volet droit (Modèle) :** ce volet contient le dernier modèle par défaut pour le type d’agent que vous avez sélectionné. Ces modèles fournissent les paramètres minimaux requis pour exécuter l&apos;agent, mais ils incluent également de nombreuses options de mise en commentaire supplémentaires. Vous pouvez utiliser ces exemples comme référence ou les supprimer des commentaires pour créer une configuration plus personnalisée.

4. Un workflow courant consiste à cliquer sur <DNT>**Copy**</DNT> dans le volet des modèles et à coller le contenu dans le volet de configuration actif à gauche pour l&apos;utiliser comme point de départ.

5. Une fois que vous êtes satisfait de votre configuration dans le volet de gauche, cliquez sur <DNT>**Save**</DNT>. La vue d’édition se fermera, vous ramenant à la page de configuration principale où vous pourrez trouver votre nouvelle configuration. Si votre organisation exige une approbation pour ce type d’agent, l’enregistrement soumet la version pour révision au lieu de la rendre disponible immédiatement — voir [Approbations de configuration](#config-approvals).

### Afficher et versionner une configuration spécifique

Pour voir plus de détails sur une configuration et gérer ses versions, cliquez sur son nom dans la liste principale. Cela ouvre un volet détaillé pour cette configuration spécifique.

Cette vue vous montre :

* Le nom de la configuration, le type d&apos;agent et une liste de ses versions disponibles.
* Le **statut de déploiement**, qui indique si la configuration a été déployée sur des flottes et, le cas échéant, lesquelles.
* L’ **état d’approbation** de chaque version, si votre organisation exige une approbation pour ce type d’agent. Voir [Approbations de configuration](#config-approvals).

À partir de ce volet, vous pouvez également effectuer plusieurs actions telles que **Download**, **Copy** et **Clone**. L’action principale ici est de créer une nouvelle version de la configuration.

Pour créer une nouvelle version :

1. Cliquez sur <DNT>**Add new version**</DNT>.
2. Cela ouvre le volet d&apos;édition dans lequel vous pouvez modifier la configuration.
3. Une fois vos modifications terminées, cliquez sur <DNT>**Save**</DNT>.
4. Vous serez redirigé vers la page principale des configurations et vous verrez que le nombre de <DNT>**revisions**</DNT> pour cette configuration a augmenté de un.

Si vous revenez à la configuration, vous pouvez désormais sélectionner la nouvelle version dans la liste pour l&apos;afficher.

Les versions existantes ne peuvent pas être modifiées. C’est en créant une nouvelle version que vous modifiez une configuration, ce qui permet de garder une trace de ce qui a changé au fil du temps et signifie qu’une version approuvée reste exactement telle qu’elle était lorsqu’elle a été examinée.

## Supprimer une configuration et ses versions

Pour supprimer une configuration, vous devez d’abord supprimer toutes ses versions individuelles. La configuration parent est automatiquement supprimée une fois sa dernière version supprimée.

<Callout title="Important : restriction de suppression" variant="caution">
  Vous ne pouvez pas supprimer une version de configuration qui fait actuellement partie d’un déploiement actif. La section d&apos;état de déploiement dans le volet des détails configuration vous indiquera à quelles flottes une version est destinée. Avant de pouvoir le supprimer, vous devez d’abord créer un nouveau déploiement pour les flottes qui utilisent une version de configuration différente.
</Callout>

Pour supprimer une version de configuration :

1. Accédez à la page de configuration.
2. Cliquez sur le nom de la configuration que vous souhaitez modifier pour ouvrir son volet de détails.
3. Sur la gauche, vous verrez une liste de toutes ses versions. Passez la souris sur la version que vous souhaitez supprimer et cliquez sur les points de suspension (...) qui apparaissent.
4. Sélectionnez <DNT>**Delete**</DNT> dans le menu.
5. Répétez ce processus pour toutes les versions restantes. Une fois la dernière version supprimée, la configuration parente sera retirée de la liste sur la page principale des configurations.

### Cloner une configuration

Le clonage est un moyen rapide de créer une nouvelle configuration basée sur une configuration existante.

1. Sur la page de configuration principale, cliquez sur le bouton points de suspension (`...`) situé à côté du <DNT>**Create configuration**</DNT> principal.
2. Dans la liste déroulante, sélectionnez la configuration existante que vous souhaitez utiliser comme point de départ pour votre clone.
3. Cela ouvre la même vue d&apos;édition à deux volets, pré-remplie avec le contenu de la configuration que vous avez sélectionnée.
4. Vous pouvez maintenant créer votre nouvelle configuration et la sauvegarder.

## Approbations de configuration

<Callout title="Informations sur le lancement de la fonctionnalité" variant="important">
  Les approbations de configuration sont désormais disponibles. L’application commence le **22 septembre 2026**.

  Avant cette date, vous pouvez configurer une politique d’approbation, et utiliser les approbations, mais les déploiements ne sont pas bloqués si votre organisation n’en a pas configuré une. À partir du 22 septembre, un <DNT>**Organization Manager**</DNT> doit configurer une politique d’approbation avant que quiconque dans votre organisation ne puisse créer de nouveaux déploiements.

  Les déploiements qui sont déjà en cours d’exécution ne sont jamais affectés, avant ou après cette date.
</Callout>

Les approbations de configuration nécessitent qu’au moins une personne autre que l’auteur approuve une version de configuration avant que cette version ne puisse être utilisée dans un déploiement. Si vous avez utilisé les révisions de demande de tirage avec un fournisseur Git, le workflow vous semblera familier : un réviseur lit la configuration, puis l’approuve, requests des modifications, ou la refuse.

La raison pour laquelle cela est important est que <DNT>Fleet Control</DNT> gère les configurations à distance. Un utilisateur peut créer une configuration, et la pousser vers l’infrastructure de production sur l’ensemble de vos parcs depuis un control plane central, plutôt que de modifier des fichiers sur des hôtes individuels. Les approbations de configuration apportent un deuxième regard sur ce chemin, de sorte qu’aucune personne seule ne puisse créer une configuration, et la déployer par elle-même.

Les approbations s&apos;appliquent aux configurations pour chaque type d&apos;agent que vous choisissez d&apos;inclure, à la fois pour l&apos;infrastructure et l&apos;APM.

### Configurez une politique d’approbation

Votre organisation n’a aucune politique d’approbation tant que quelqu’un n’en a pas créé une. La configuration d’une politique nécessite le rôle <DNT>**Organization Manager**</DNT>, ou un rôle personnalisé doté de la capacité de politique.

1. Dans la navigation de gauche, accédez à <DNT>**New Relic Control → Fleet Control Settings → Approvals**</DNT>.
2. Si votre organisation n’a jamais configuré de politique, vous verrez un prompt pour créer des politiques d’approbation pour les modifications de configuration. Cliquez pour commencer.
3. Sous <DNT>**Governance for agent types**</DNT>, sélectionnez les types d’agents qui doivent nécessiter une approbation. Tous les types d’agents qui prennent en charge les approbations sont sélectionnés pour vous par défaut, vous pouvez donc désélectionner ceux dont vous n’avez pas besoin plutôt que de créer la liste à partir de zéro.
4. Définissez le nombre minimum d’approbations. Celui-ci est défini par défaut sur `1` et peut être augmenté jusqu’à `5`. Le décompte fait référence aux approbations de personnes *autres que* l’auteur, donc un minimum de `1` signifie que deux personnes ont vu la configuration : l’auteur et un approbateur.
5. Cliquez sur <DNT>**Save**</DNT>.

Pour annuler les modifications non enregistrées, cliquez sur <DNT>**Reset**</DNT>. Cela ramène le formulaire à la politique enregistrée de votre organisation, ce qui annule vos modifications au lieu d’effacer votre politique. Si vous n’avez pas encore enregistré de politique, cela ramène le formulaire à son état initial avec chaque type d’agent sélectionné.

Si vous n’avez pas l’autorisation de créer une politique, la page vous l’indique et vous invite à contacter un administrateur. Demandez à la personne qui occupe le rôle <DNT>**Organization Manager**</DNT> dans votre organisation de terminer la configuration.

<Callout title="Nous recommandons d’exiger une approbation pour chaque type d’agent" variant="tip">
  Étant donné que les configurations <DNT>Fleet Control</DNT> sont gérées à distance plutôt que localement sur chaque hôte, tout type d’agent que vous omettez est un type qu’un seul utilisateur peut créer et déployer sans révision. Nous recommandons d’exiger une approbation pour tous, puis de l’assouplir uniquement là où vous êtes sûr de ne pas en avoir besoin.
</Callout>

Si vous laissez une intégration sur hôte non régie, l’enregistrement affiche un prompt vous invitant à reconnaître le risque avant que la modification ne prenne effet. Les intégrations sur hôte peuvent exécuter des scripts sur vos hôtes, ce qui en fait les configurations ayant le plus d’impact à laisser sans révision. NRI Flex en est l’exemple le plus largement utilisé. La reconnaissance est une étape de confirmation, et non une restriction : vous pouvez enregistrer la modification une fois que vous l’avez acceptée.

### Types d’agents exclus des approbations

Deux types de configuration sont exclus de façon permanente, pour différentes raisons :

* <DNT>**Agent Control:**</DNT> C’est le superviseur plutôt qu’un agent. <DNT>Fleet Control</DNT> fonctionne via Agent Control pour effectuer chaque opération du cycle de vie, donc exiger une approbation à son sujet bloquerait le mécanisme qui effectue toutes vos autres modifications approuvées.
* <DNT>**Pipeline Control Gateway (including Config Mode):**</DNT> <DNT>Pipeline Control</DNT> possède cette configuration. <DNT>Fleet Control</DNT> la fournit, mais elle est créée et gérée dans <DNT>Pipeline Control</DNT>.

Tout autre type d’agent disponible pour votre organisation peut être configuré pour nécessiter une approbation.

### Comprendre les états d&apos;approbation

Les versions de configuration sont immuables. La modification d’une configuration produit toujours une nouvelle version plutôt que d’en modifier une existante, ce qui signifie qu’une version approuvée reste exactement telle qu’elle était lorsqu’elle a été examinée. Chaque version est approuvée séparément.

Une version qui nécessite une approbation passe par ces états :

| État                             | Ce que cela signifie                                                                                                                                                                                                                   |
| :------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| <DNT>**Awaiting approval**</DNT> | La version a été soumise et est en attente d’examen. Elle ne peut pas encore être utilisée dans un déploiement. La bannière affiche la progression vers le nombre requis, par exemple `0 of 1 approvals`.                              |
| <DNT>**Changes requested**</DNT> | Un réviseur a demandé des modifications. Parce que les versions sont immuables, vous répondez en ajoutant une nouvelle version plutôt qu&apos;en modifiant celle-ci.                                                                   |
| <DNT>**Approved**</DNT>          | Le nombre requis d’approbations a été atteint. La version peut être utilisée dans n’importe quel déploiement.                                                                                                                          |
| <DNT>**Denied**</DNT>            | Un réviseur a bloqué cette version de façon permanente, et la version indique la raison du réviseur. Le refus est le seul état dont une version ne peut pas sortir. Pour continuer, ajoutez une nouvelle version à partir de celle-ci. |

Une version approuvée peut toujours être refusée ultérieurement. Si un réviseur approuve une configuration et remarque ensuite un problème, tel que des données sensibles qui ne devraient pas s’y trouver, la refuser empêche immédiatement quiconque de déployer cette version. C’est délibéré : cela vous permet de retirer une configuration problématique de la circulation à tout moment, et pas seulement lors de l’examen initial.

### Créer une configuration qui nécessite une approbation

Lorsque vous créez ou modifiez une configuration pour un type d’agent qui nécessite une approbation, l’éditeur vous en informe avant que vous n’enregistriez, et l’enregistrement soumet la version pour révision au lieu de la rendre immédiatement disponible.

1. Créez votre configuration comme d’habitude.
2. Cliquez sur <DNT>**Save**</DNT>. La version est enregistrée, et soumise pour examen en une seule étape. Il n’y a pas d’action de soumission distincte.
3. Sur la page principale de configuration, la configuration apparaît avec une icône de cadenas, indiquant qu’elle nécessite une approbation. Son état actuel est affiché à côté.

Vous ne pouvez pas déployer la version tant qu’elle n’a pas atteint l’état approuvé.

Pour répondre aux commentaires d’un réviseur, ajoutez une nouvelle version :

1. Cliquez sur le nom de la configuration pour l’ouvrir. Cette vue liste les versions de la configuration ainsi que leurs états d’approbation, afin que vous puissiez voir quelle version a été refusée ou a fait l’objet de demandes de modifications.
2. Cliquez sur <DNT>**Add new version**</DNT>. L’éditeur s’ouvre avec une copie de la dernière version de la configuration, de sorte qu’une demande de petite modification ne signifie pas de devoir tout recommencer.
3. Cliquez sur <DNT>**View configuration history**</DNT> pour lire ce que vos réviseurs ont dit. Cela affiche les commentaires de demande de modifications, les commentaires de refus, et l’activité d’approbation enregistrée pour la configuration au fil du temps, sur toutes ses versions.
4. Apportez vos modifications, et enregistrez la nouvelle version. Elle lance son propre examen.

Chaque configuration possède un enregistrement parent avec ses versions comme enfants. <DNT>**View configuration history**</DNT> les couvre, de sorte qu’il sert également de piste d’audit pour savoir qui a examiné quoi, et quand. Pour récupérer les identifiants pour le dépannage, utilisez <DNT>**View metadata**</DNT>, qui affiche l’ID de configuration pour le parent, et l’ID de version de configuration pour la version spécifique que vous consultez.

### Vérifiez une configuration

L’examen nécessite le rôle <DNT>**Organization Manager**</DNT>, ou un rôle personnalisé disposant de la capacité d’approbation.

Ouvrez la version de la configuration et choisissez l’une des trois actions :

* <DNT>**Approve:**</DNT> Enregistre votre approbation. Un commentaire est facultatif. Une fois que la version atteint le nombre requis d’approbations, elle peut être utilisée immédiatement dans les déploiements.
* <DNT>**Request changes:**</DNT> Demande à l’auteur de réviser. Utilisez cette option lorsque la configuration est presque prête mais nécessite des modifications spécifiques. Indiquez quelles lignes et pourquoi, car l’auteur voit votre commentaire dans l’historique de la configuration.
* <DNT>**Deny:**</DNT> Bloque la version de façon permanente. Utilisez cette option lorsque la configuration ne doit pas du tout se poursuivre plutôt que de nécessiter des modifications. L’auteur doit ajouter une nouvelle version.

Il vous sera demandé de confirmer les approbations et les refus avant qu’ils ne soient enregistrés.

<Callout title="Vous ne pouvez pas approuver votre propre configuration" variant="important">
  L’auteur d’une version ne peut pas l’approuver, même s’il possède la capacité d’approbation. Il s’agit du contrôle principal fourni par la fonctionnalité, et il est appliqué par l’API ainsi que par l’interface, de sorte qu’il ne peut pas être contourné en appelant l’API directement.

  Vos propres soumissions n’apparaissent pas dans votre file d’attente des révisions en attente.
</Callout>

Assurez-vous que suffisamment de personnes disposent de la capacité d’approbation pour couvrir les fuseaux horaires dans lesquels votre équipe travaille. Si votre nombre minimum d’approbations est supérieur au nombre d’approbateurs disponibles, les configurations resteront non révisées.

### Trouvez les configurations en attente de votre vérification

Si des configurations sont en attente de votre part, une carte en haut de la page des configurations indique combien d’entre elles nécessitent une révision. Cliquez sur <DNT>**Show pending configurations**</DNT> pour ouvrir un volet listant tout ce qui est en attente d’approbation, afin que vous puissiez voir la file d’attente en un coup d’œil, et passer directement à n’importe quel élément pour commencer la révision.

### Déléguer l’autorité d’approbation

Les deux capacités, l’approbation des versions de configuration, et la configuration de la politique d’approbation, appartiennent au rôle <DNT>**Organization Manager**</DNT> par défaut. Il n’y a pas de rôle d’approbateur prédéfini, donc si vous souhaitez que quelqu’un d’autre approuve les configurations, un gestionnaire de l’organisation crée un rôle personnalisé, et l’attribue à un groupe.

Les deux capacités sont à l’échelle de l’organisation, ce qui signifie que le rôle personnalisé doit être un [rôle à l’échelle de l’organisation](/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#role-scopes). Un rôle au niveau du compte ou de l’entité ne peut pas les contenir, et la création du rôle n’est que la moitié du travail : les permissions ne prennent pas effet tant que vous ne liez pas le rôle à un groupe avec un [octroi d’accès](/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts/#access-grants).

<Callout title="Important : ce qu’il faut savoir avant de créer un rôle personnalisé à l’échelle de l’organisation" variant="important">
  La création de rôles personnalisés est disponible pour les organisations disposant des éditions Pro ou Enterprise. Si votre organisation ne peut pas créer de rôles personnalisés, l’approbation des configurations reste limitée aux détenteurs du rôle <DNT>**Organization Manager**</DNT>.

  Les rôles personnalisés à l’échelle de l’organisation n’acquièrent pas non plus automatiquement de nouvelles autorisations. Les rôles standards reçoivent les autorisations pour les nouvelles fonctionnalités à l’échelle de l’organisation lors de leur publication, mais un rôle personnalisé ne contient jamais que ce qu’un administrateur y a ajouté. Si <DNT>Fleet Control</DNT> ajoute des capacités de gouvernance ultérieurement, quelqu’un doit les ajouter à chaque rôle personnalisé qui devrait les avoir.
</Callout>

Pour créer le rôle :

1. Au bas du menu de navigation de gauche, cliquez sur votre nom d&apos;utilisateur, puis sélectionnez <DNT>**Administration**</DNT>.

2. Sur la page <DNT>Administration</DNT>, sélectionnez <DNT>**Access Management**</DNT>, puis allez dans l’onglet <DNT>roles</DNT>.

3. Cliquez sur <DNT>**Add a role**</DNT>.

4. Pour la portée du rôle, choisissez <DNT>**Organization**</DNT>, puis cliquez sur <DNT>**Next**</DNT>.

5. Donnez au rôle un nom qui aura du sens pour quiconque le maintiendra plus tard, par exemple `Config Approver`.

6. Trouvez la section <DNT>**Fleet Control**</DNT> et développez-la.

7. Sur la ligne <DNT>**Fleets (all)**</DNT>, sous <DNT>**Other**</DNT>, sélectionnez les capacités que ce rôle doit comporter :

   * <DNT>**Approve configurations:**</DNT> Permet aux détenteurs d’agir sur les versions de configuration en attente d’examen.
   * <DNT>**Configure organization governance:**</DNT> Permet aux détenteurs de configurer et de modifier la politique d’approbation, y compris les types d’agents nécessitant une approbation et le nombre minimum d’approbations.

8. Enregistrez le rôle.

Accordez-les indépendamment en fonction des besoins de chaque groupe. Une personne qui doit examiner les configurations, mais qui ne doit pas pouvoir modifier les types d’agents nécessitant une approbation n’a besoin que de <DNT>**Approve configurations**</DNT>.

Pour attribuer le rôle :

1. Dans <DNT>**Access Management**</DNT>, accédez à l’onglet <DNT>access grants</DNT>.
2. Cliquez sur <DNT>**Create new grant**</DNT>.
3. Associez le groupe dont les membres doivent approuver les configurations au rôle que vous avez créé, en ciblant votre organisation.

Les rôles sont attribués à des groupes plutôt qu’à des utilisateurs individuels, ajoutez donc des personnes au groupe pour leur accorder l’autorité d’approbation et retirez-les pour la leur enlever.

Étant donné que l’autorité d’approbation est à l’échelle de l’organisation, un approbateur peut approuver toute version de configuration dans l’organisation. Les configurations dans <DNT>Fleet Control</DNT> sont des objets au niveau de l’organisation, plutôt que d’appartenir à un parc spécifique, de sorte qu’une version approuvée peut être utilisée dans les déploiements de n’importe quel parc. Restreindre les approbateurs à des parcs particuliers, ou définir une politique d’approbation différente par parc, n’est pas pris en charge.

## La page principale de l&apos;entité gérée

Lorsque vous naviguez vers <DNT>**New Relic Control → Managed Entities**</DNT>, vous obtenez une vue centralisée de toutes vos entités gérées, qui sont des clusters Kubernetes ou des hôtes avec Agent Control installé. Cette page sert d&apos;inventaire complet des actifs pour toute entité pouvant être gérée par <DNT>Fleet Control</DNT> et est organisée en deux onglets : <DNT>**Fleet managed**</DNT> et <DNT>**Unassigned**</DNT>.

### Onglet Gestion de flotte

Cet onglet répertorie toutes les entités gérées qui sont actuellement affectées à une flotte. Le tableau fournit les informations suivantes :

* <DNT>**Entity name:**</DNT> Cliquer sur le nom vous dirige directement vers l&apos;expérience d&apos;exploration de cette entité dans la plateforme New Relic (par exemple, l&apos;explorateur de clusters Kubernetes).
* <DNT>**Entity type:**</DNT> Le type de l&apos;entité gérée (par exemple, un cluster Kubernetes ou un hôte).
* <DNT>**Instrumentation status:**</DNT> L&apos;état de santé actuel de l&apos;instrumentation sur l&apos;entité.
* <DNT>**Fleet:**</DNT> Flotte à laquelle l&apos;entité est actuellement affectée. Vous pouvez cliquer sur le nom de la flotte pour accéder directement à la page de gestion de cette flotte.
* <DNT>**Account name:**</DNT> Le compte New Relic associé à l&apos;entité gérée.

### Onglet non attribué

Cet onglet fournit une liste de toutes les entités gérées sur lesquelles <DNT>Agent Control</DNT> est installé mais qui ne sont actuellement affectées à aucune flotte. Le tableau fournit les informations suivantes :

* <DNT>**Entity name:**</DNT> Cliquer sur le nom vous dirige directement vers l&apos;expérience explorer de cette entité dans la plateforme New Relic.
* <DNT>**Entity type:**</DNT> Le type de l&apos;entité gérée.
* <DNT>**Instrumentation status:**</DNT> L&apos;état de santé actuel de l&apos;instrumentation.
* <DNT>**Account name:**</DNT> Le compte New Relic associé à l&apos;entité gérée.

Cette vue est particulièrement utile pour identifier lesquels de vos actifs ne sont pas encore gérés par <DNT>Fleet Control</DNT>. C&apos;est une bonne pratique d&apos;attribuer toutes les entités gérées à une flotte pour garantir qu&apos;elles sont configurées et monitorées de manière cohérente.

## La page des agents principaux

Lorsque vous accédez à <DNT>**New Relic Control → Agents**</DNT>, vous obtenez une vue d&apos;ensemble de tous les agents gérés par <DNT>Fleet Control</DNT> dans votre organisation.

En haut de la page, vous trouverez des cartes récapitulatives qui donnent un aperçu rapide de la santé de votre agent, notamment :

* Un décompte de tous les agents connectés.
* Un décompte des agents déconnectés, vous aidant à identifier rapidement les agents qui peuvent nécessiter un dépannage.
* Une distribution de vos 500 principaux types d’agents.

Sous les cartes récapitulatives, un tableau complet répertorie tous vos agents gérés. Vous pouvez rechercher ce tableau par nom d&apos;agent et le filtrer par type d&apos;agent ou statut de rapport. Le tableau comprend les colonnes suivantes :

* <DNT>**Type:**</DNT> Le type de l&apos;agent (par exemple, New Relic infrastructure).
* <DNT>**Agent Name:**</DNT> Le nom spécifique de l&apos;agent.
* <DNT>**Managed Entity:**</DNT> L&apos;entité gérée à laquelle l&apos;agent est associé.
* <DNT>**Connection Status:**</DNT> Le statut actuel de la connexion de l&apos;agent.
* <DNT>**Fleet:**</DNT> La flotte dont l&apos;agent fait partie.
* <DNT>**Agent Version:**</DNT> Le numéro de version de l&apos;agent.
