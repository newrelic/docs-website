Monitorez les performances de votre base de données SQL Server avec des métriques complètes collectées par le NRDOT Collector. Par défaut, New Relic collecte les métriques et les événements au niveau des requêtes référencés dans la section [Métriques et événements par défaut](#default). Vous pouvez améliorer votre monitoring en activant les métriques souhaitées listées dans la section [Métriques de fonctionnalités complètes](#full-feature).

## Métriques et événements par défaut [#default]

### Événements de log [#log-events]

Les événements suivants sont collectés en tant qu’enregistrements de log OpenTelemetry et sont activés par défaut, à l’exception de `db.server.procedure_definition` qui est optionnel. Ils offrent une visibilité au niveau de la requête : échantillons de requêtes actives, requêtes principales, plans d’exécution, procédures stockées principales, et définitions de procédures stockées.

<Collapser id="db-server-top-query" title="Principales requêtes">
Collecte de métriques d’événements pour les N principales requêtes, filtrées en fonction du temps écoulé le plus élevé consommé au cours de l’intervalle de collecte. Cet événement est activé par défaut.

Utilisez le bloc `top_query_collection` pour ajuster son comportement :

```yaml
top_query_collection:
  lookback_time: 60s
  max_query_sample_count: 1000
  top_query_count: 250
  collection_interval: 60s
  allowed_comment_keys: [nr_service_guid]
```

<Collapser id="db-server-top-procedure" title="Principales procédures">
Métriques de performances agrégées pour les procédures stockées principales par temps écoulé, calculées sous forme de deltas sur l’intervalle de collecte. Est corrélé avec `db.server.top_query` et `db.server.query_sample` via `sqlserver.procedure_id`. Cet événement est activé par défaut.

<Callout variant="tip">
Nécessite SQL Server 2017 CU3 ou une version ultérieure, qui a introduit la prise en charge de `sys.dm_exec_procedure_stats.total_spills`. Sur les versions antérieures, cet événement n’émet pas de données et log une erreur. Les autres événements ne sont pas affectés.
</Callout>

Utilisez le bloc `top_procedure_collection` pour ajuster son comportement :

```yaml
top_procedure_collection:
  max_procedure_sample_count: 1000
  top_procedure_count: 250
  collection_interval: 60s
```
