Monitorez les performances de votre base de données MySQL avec des métriques complètes collectées par le NRDOT Collector. Par défaut, New Relic collecte les métriques et les événements au niveau des requêtes référencés dans la section [Métriques et événements par défaut](#default). Vous pouvez améliorer votre monitoring en activant les métriques souhaitées listées dans la section [Métriques de fonctionnalités complètes](#full-feature).

### demande d&apos;événement [#query-events]

Les événements suivants sont collectés en tant qu’enregistrements de log OpenTelemetry et sont activés par défaut. Ils fournissent une visibilité au niveau de la requête.

<CollapserGroup>
<Collapser id="query-sample" title="Échantillons de requêtes">
Visibilité en temps réel sur les instructions de base de données en cours d’exécution : un instantané ponctuel pris à chaque collecte, et non un log d’exécution complet. Cet événement est activé par défaut.

Utilisez le bloc `query_sample_collection` pour ajuster son comportement :

```yaml
query_sample_collection:
  max_rows_per_query: 100
  allowed_comment_keys: [nr_service_guid]
```

<Collapser id="top-query" title="Principales requêtes">
Les requêtes consommant le plus de temps d&apos;exécution, agrégées côté serveur par le propre `performance_schema.events_statements_summary_by_digest` de MySQL : un véritable compteur d&apos;exécution par digest, et non un nombre d&apos;échantillons. Cet événement est activé par défaut.

Utilisez le bloc `top_query_collection` pour ajuster son comportement :

```yaml
top_query_collection:
  lookback_time: 60
  max_query_sample_count: 5000
  top_query_count: 200
  collection_interval: 60s
  query_plan_cache_size: 1000
  query_plan_cache_ttl: 1h
  allowed_comment_keys: [nr_service_guid]
```

<Collapser id="query-plan" title="Plans de requêtes">
Plan d&apos;exécution d&apos;une instruction, signalé comme son propre événement afin que le plan puisse être filtré, routé ou supprimé indépendamment des propres statistiques de `top_query`/`query_sample`. Nécessite que `db.server.top_query` ou `db.server.query_sample` au moins soit également activé. Une fois activé, `mysql.query_plan` n&apos;est plus inclus dans les enregistrements `db.server.top_query`/`db.server.query_sample`. Consultez [Collecte des plans d&apos;exécution](#explain) pour les mécanismes de `EXPLAIN`. Cet événement est activé par défaut.

`procedure`
</td>

<td>
Passe par une procédure `SQL SECURITY DEFINER` (`<schema>.explain_statement`) afin que les instructions d’écriture (`UPDATE`/`DELETE`/`INSERT`/`REPLACE`) puissent être expliquées sans accorder de DML à l’utilisateur de monitoring. Se rabat sur `inline` si la procédure est manquante. Nécessite l’étape de configuration unique par schéma. Consultez [Plans de requête pour les instructions d’écriture](/docs/opentelemetry/db360/mysql/optional#query).
</td>
</tr>
</tbody>
</table>

<Callout variant="important">
`mysql.query_plan` est la sortie `EXPLAIN FORMAT=json` brute, enveloppée dans un éventail JSON à un élément avant la mise en cache, afin que l’ingestion de log de New Relic ne l’aplatisse pas automatiquement et ne la détruise pas. Analysez l’index `[0]` pour récupérer l’objet plan.
</Callout>
