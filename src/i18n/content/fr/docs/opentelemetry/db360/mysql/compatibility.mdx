Avant de commencer à monitorer votre MySQL avec NRDOT, assurez-vous que votre environnement répond à ces exigences.

## Prérequis [#prereq]

Avant de commencer, assurez-vous d’avoir les éléments suivants :

* Une [clé de licence](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key)New Relic valide
* Connectivité réseau entre l&apos;hôte où vous installez le Collector NRDOT et votre base de données MySQL. Si vous prévoyez d&apos;installer le Collector NRDOT sur un hôte différent de votre base de données MySQL, consultez les [exigences d&apos;accès réseau](#network).
* Connectivité réseau vers la [documentation sur les points de terminaison OTLP de New Relic](/docs/opentelemetry/best-practices/opentelemetry-otlp/)

## Exigences d&apos;accès réseau [#network]

Par défaut, NRDOT se connecte via **TCP** (`transport: tcp` dans la configuration du Récepteur, la valeur par défaut). Si le collecteur s’exécute sur le même hôte que la base de données, vous pouvez plutôt définir `transport: unix` et pointer `endpoint` vers le socket de domaine Unix de la base de données (par exemple, `/var/run/mysqld/mysqld.sock`), ce qui contourne entièrement les vérifications réseau ci-dessous. Pour tout autre déploiement (collecteur et base de données sur des hôtes, conteneurs ou VPC différents), TCP est requis.

<table>
  <thead>
    <tr>
      <th>
        déploierons
      </th>

      <th>
        Ce qu&apos;il faut vérifier
      </th>
    </tr>
  </thead>

  <tbody>
    <tr>
      <td>
        MySQL autogéré sur EC2
      </td>

      <td>
        **Groupe de sécurité**

        : ajoutez une règle entrante sur le port de la base de données (par défaut 

        `3306`

        ) depuis la source du collecteur : l’ID de son propre groupe de sécurité (même VPC, préféré à une IP brute) si le collecteur s’exécute sur une instance EC2 différente, ou aucune règle n’est nécessaire s’il s’exécute en tant que sidecar sur la même instance. Vérifiez également 

        `bind-address`

         dans 

        `my.cnf`

        : de nombreuses distributions fournissent par défaut 

        `bind-address = 127.0.0.1`

        , qui refuse toute connexion TCP non locale. Définissez-le sur l’adresse IP privée de l’instance ou sur 

        `0.0.0.0`

         avant qu’un collecteur distant ne puisse l’atteindre.
      </td>
    </tr>

    <tr>
      <td>
        Amazon RDS/Aurora pour MySQL
      </td>

      <td>
        **Groupe de sécurité VPC**

        : ajoutez une règle entrante sur le port de l’instance RDS (par défaut 

        `3306`

        ) à partir du groupe de sécurité ou de l’adresse IP privée du collecteur ; RDS n’a pas de 

        `my.cnf`

         au niveau du système d’exploitation à modifier, il s’agit donc de la seule passerelle réseau. 

        **Les droits**

         doivent provenir de l’utilisateur maître RDS. RDS n’a pas de compte 

        `root`

        . 

        **Privilèges restreints**

        : 

        `SUPER`

         et 

        `FILE`

         sont restreints ou indisponibles selon la version du moteur RDS et le groupe de paramètres. 

        **TLS**

        : les instances RDS avec l’obligation « Require SSL/TLS » nécessitent que le collecteur fasse confiance à l’autorité de certification RDS d’Amazon. Définissez 

        `tls.ca_file`

         (ou 

        `tls.ca_pem`

        ) sur le 

        [lot de certificats Amazon RDS](https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem)

         et laissez 

        `tls.insecure`

        /

        `tls.insecure_skip_verify`

         sur 

        `false`

        .
      </td>
    </tr>

    <tr>
      <td>
        Tout déploiement distant/inter-hôte
      </td>

      <td>
        MySQL traite 

        `'<user>'@'localhost'`

         et 

        `'<user>'@'%'`

         (ou un hôte/CIDR spécifique) comme des 

        **comptes différents**

        , même avec un nom d’utilisateur identique. La création de l’utilisateur de monitoring en tant que 

        `'<user>'@'localhost'`

         échoue silencieusement lors de l’authentification depuis un collecteur s’exécutant n’importe où ailleurs, avec une erreur d’accès refusé impossible à distinguer d’un mot de passe incorrect. Utilisez 

        `'<user>'@'%'`

         ou limitez-le à l’IP/CIDR privée spécifique du collecteur.
      </td>
    </tr>
  </tbody>
</table>

<Callout variant="important">
  Vérifié sur une instance Amazon RDS pour MySQL active : la famille de groupes de paramètres `mysql8.0` de RDS n’expose aucun paramètre `performance_schema_consumer_*` du tout ; seuls les paramètres de dimensionnement/tampon, plus `performance_schema`, `slow_query_log`, et `long_query_time` y sont configurables. Cela signifie que `events_waits_current` (nécessaire pour `mysql.events_waits_current.timer_wait`, et les dashboards basés sur l’attente en général) ne peut être activé qu’à l’exécution sur RDS, et qu’il ne survit pas à un redémarrage, ou à un basculement.
</Callout>

## Prochaines étapes [#next]

Une fois que vous avez vérifié que votre environnement respecte ces prérequis :

1. Choisissez votre méthode d&apos;installation :

* [Configuration auto-hébergée](/docs/opentelemetry/db360/mysql/hosted)
* [Configuration d’AWS RDS](/docs/opentelemetry/db360/mysql/rds)

2. Consultez les [métriques disponibles](/docs/opentelemetry/db360/mysql/metrics-reference) qui seront collectées
3. Consultez [Activer les informations détaillées](/docs/opentelemetry/db360/mysql/optional) pour les fonctionnalités facultatives telles que les plans de requête d’instruction d’écriture, et le suivi de la durée d’attente de verrouillage
4. Consultez notre [guide de dépannage](/docs/opentelemetry/db360/mysql/troubleshooting) pour les problèmes courants
