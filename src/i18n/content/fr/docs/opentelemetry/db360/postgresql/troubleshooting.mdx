Résoudre les problèmes courants que vous pouvez rencontrer lors du monitoring de votre PostgreSQL avec le NRDOT Collector.

## Tester la connectivité [#test-connectivity]

### Testez la connectivité réseau vers PostgreSQL [#test-network]

```bash
psql --host=<YOUR_DB_HOST> --port=<YOUR_DB_PORT> --username=<YOUR_DB_USERNAME> --dbname=<YOUR_DATABASE_NAME> --command 'SELECT 1;'
```

Une connexion et un résultat réussis confirment que l’utilisateur de monitoring, l’hôte, et le port sont accessibles avant le dépannage du collecteur lui-même.

### Tester la connectivité du point de terminaison OTLP [#test-otlp]

Vérifiez que le Collector NRDOT peut atteindre le point de terminaison OTLP de New Relic :

```bash
curl -v <YOUR_NEWRELIC_OTLP_ENDPOINT>
```

## Symptômes courants [#common-symptoms]

| Symptôme                                                                                                        | Cause probable                                                                                                                                                            |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Aucun événement `db.server.query_sample` / `db.server.top_query`                                                | Le bloc `events` n&apos;est pas activé dans la configuration du Récepteur (les deux sont désactivés par défaut)                                                           |
| `db.server.top_query` événements totalement manquants                                                           | `pg_stat_statements` Extension non créée dans cette base de données                                                                                                       |
| `db.server.query_sample` détail de session bloquante manquant                                                   | L’utilisateur de monitoring manque de `pg_monitor`                                                                                                                        |
| Requêtes longues tronquées dans `db.server.query_sample`                                                        | Par défaut `track_activity_query_size` (1024 octets) ; augmentez-le, consultez [Compatibilité et prérequis](/docs/opentelemetry/db360/postgresql/compatibility#params)    |
| `postgresql.function.calls` toujours vide, ou widget &quot;Appels de fonction/min&quot; du dashboard vide       | `track_functions` non défini sur `pl` ou `all` dans `postgresql.conf`                                                                                                     |
| Plusieurs widgets de dashboard vides malgré le flux de métriques                                                | Ces métriques sont désactivées par défaut ; voir [Référence des métriques](/docs/opentelemetry/db360/postgresql/metrics-reference#dashboard)                              |
| `db.query.comment_tags.nr_service_guid` toujours vide                                                           | `allowed_comment_keys: [nr_service_guid]` non défini sur `query_sample_collection` / `top_query_collection`; vide par défaut                                              |
| Métriques de table/index/fonction manquantes pour certaines tables                                              | L’utilisateur de monitoring ne dispose pas de `SELECT` sur ces tables/schémas ; `pg_monitor` accorde la visibilité des statistiques, et non au niveau de l’objet `SELECT` |
| `postgresql.wal.lag` / `.wal.age` manquant                                                                      | Nécessite l’activation de WAL avec au moins un réplica connecté ; omis silencieusement sur les instances autonomes / sources uniquement, non mis à zéro                   |
| L’entité PostgreSQL n’apparaît pas, ou la relation app→PostgreSQL ne se résout pas dans l’Explorateur d’entités | `server.address`/`server.port` n’est pas présent sur la ressource ; le Récepteur seul n’émet pas ces éléments sous le modèle de ressource par défaut (legacy)             |

## Les données n&apos;apparaissent pas dans New Relic [#data-not-flowing]

* Pour vérifier les problèmes liés à la limitation de débit, exécutez :

  ```sql
  SELECT * FROM NrIntegrationError
  ```

* Si les données ne circulent toujours pas, vérifiez si des règles de suppression sont définies sur vos événements de métrique et de log. Consultez [Supprimer les données de log avec des règles de filtre de suppression](/docs/logs/ui-data/drop-data-drop-filter-rules/) et [Contrôle du Pipeline](/docs/new-relic-control/pipeline-control/overview/).
