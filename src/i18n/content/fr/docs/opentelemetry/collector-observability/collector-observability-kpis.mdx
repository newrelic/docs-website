La [page de résumé de l’observabilité du Collector](/docs/opentelemetry/collector-observability/collector-observability#summary-page) s’ouvre avec six tuiles de KPI (indicateurs de performances clés) qui vous donnent un aperçu rapide de la santé de votre collecteur. Cliquez sur n’importe quelle tuile pour ouvrir une vue détaillée avec le graphique sous-jacent, ainsi qu’un ensemble de graphiques de télémétrie associés qui vous aident à analyser un changement inattendu du KPI. Dans la plupart des cas, la télémétrie associée peut être segmentée par type de signal, ou par composant (exportateur/Processeur/Récepteur) lors de la sélection d’un type de signal spécifique. Cette page explique ce que signifie chaque KPI, et pourquoi chacun de ses graphiques de télémétrie associés est présent.

## Éléments reçus [#items-received]

Quantité de télémétrie entrant dans le collecteur via ses Récepteurs. Les causes courantes d’un changement inattendu sont des problèmes clients en amont (moins ou plus d’applications instrumentées envoyant des données) ou un Récepteur qui ne parvient pas à récupérer les données qu’il est configuré pour extraire.

Télémétrie associée :

* <DNT>**Receiver accepted**</DNT>: décompose le total par signal ou Récepteur, afin que vous puissiez déterminer d’où provient exactement le changement.
* <DNT>**Receiver refused**</DNT>: indique si une partie de la baisse provient de la télémétrie refusée (voir aussi [Récepteur refusé](#receiver-refused)) plutôt que d’une baisse du trafic en amont.
* <DNT>**Memory limiter drop ratio**</DNT>: le refus de données par les récepteurs pourrait finalement être dû au blocage du [memorylimiter](https://github.com/open-telemetry/opentelemetry-collector/tree/v0.161.0/processor/memorylimiterprocessor).

## Éléments envoyés [#items-sent]

Télémétrie envoyée avec succès par les exportateurs du collecteur vers les destinations en aval. Les causes courantes d’un changement inattendu sont des problèmes en amont (processeurs abandonnant des données, récepteurs refusant des données, ou clients fournissant moins de données au collecteur), ou des défaillances de l’exportateur.

Télémétrie associée :

* <DNT>**Exporter sent**</DNT>: décompose le total par signal, ou exportateur, afin que vous puissiez déterminer d’où provient exactement le changement.
* <DNT>**Exporter failures**</DNT>: met en évidence les échecs de l&apos;exportateur (voir [Taux d&apos;échec de l&apos;exportation](#export-failure-rate)) comme cause de l&apos;envoi d&apos;un nombre réduit d&apos;éléments.
* <DNT>**Exporter queue saturation**</DNT>: indique si une file d’attente d’envoi saturée (voir [Saturation de la file d’attente](#queue-saturation)) empêche l’envoi d’éléments.

## Saturation de file d’attente [#queue-saturation]

Le niveau de remplissage de la file d’attente d’envoi de chaque exportateur ; une file d’attente pleine entraîne une perte de données. Les causes courantes d’un pic de saturation sont des défaillances de l’exportateur qui encombrent la file d’attente ou un pic de trafic atteignant une file d’attente sous-dimensionnée.

Télémétrie associée :

* <DNT>**Exporter send failures**</DNT>: les exportations en échec prennent souvent plus de temps, par ex. délais d’attente, et ils entraînent de nouvelles tentatives qui provoquent une accumulation dans la file d’attente.
* <DNT>**Exporter queue size vs. capacity**</DNT>: indique la taille brute de la file d’attente par rapport à sa capacité configurée, afin que vous puissiez déterminer si la saturation est causée par un pic de trafic, ou si la file d’attente est simplement sous-dimensionnée.

## Récepteur refusé [#receiver-refused]

Télémétrie en amont que les récepteurs rejettent activement. Cela devrait normalement être égal à zéro ; tout taux soutenu est une anomalie à diagnostiquer via les logs.

Télémétrie associée :

* <DNT>**Memory limiter drop ratio**</DNT>: les Récepteurs commencent à refuser la télémétrie une fois que le Processeur [memorylimiter](https://github.com/open-telemetry/opentelemetry-collector/tree/v0.161.0/processor/memorylimiterprocessor) bloque, ce qui serait la véritable cause première.
* <DNT>**Process memory RSS**</DNT>: contextualise les métriques du memorylimiter en affichant l’utilisation de la mémoire du collecteur.
* <DNT>**Process runtime heap allocated**</DNT>: un tas Go grandissant peut entraîner une récupération de mémoire défaillante, ce qui peut à son tour nuire au débit du collecteur.

## Taux d’échec d’exportation [#export-failure-rate]

Le pourcentage de requests d&apos;exportateur qui échouent, et sont réessayés, si configuré. Les causes courantes sont des problèmes de réseau, ou une mauvaise configuration de l&apos;exportateur, ou des destinations.

Télémétrie associée :

* <DNT>**Exporter failures**</DNT>: indique le nombre absolu d&apos;échecs (numérateur) par signal, ou exportateur, afin que vous puissiez déterminer où exactement les échecs se produisent.
* <DNT>**Exporter sent**</DNT>: affiche le nombre absolu d’exportations (dénominateur) pour mettre les échecs et le taux en perspective.

## Rejets de file d’attente [#queue-drops]

Télémétrie que le collecteur n’a pas pu mettre en file d’attente pour l’exportation parce que la file d’attente était pleine. Les données qui n’ont pas été mises en file d’attente sont rejetées, c’est-à-dire une perte de données confirmée.

Télémétrie associée :

* <DNT>**Exporter enqueue failures**</DNT>: détaille la perte de données confirmée par signal, ou exportateur.
* <DNT>**Exporter queue size vs. capacity**</DNT>: indique si la file d&apos;attente s&apos;est remplie rapidement, par ex. pic de trafic, ou progressivement, par ex. collecteur sous-dimensionné, file d&apos;attente sous-dimensionnée, ou accumulation d&apos;échecs persistants.
* <DNT>**Exporter failures**</DNT>: les échecs d’exportation engorgent souvent la file d’attente jusqu’à ce qu’elle soit pleine, ce qui aide donc à confirmer si c’est la cause première.
