Si vous avez terminé [l’installation de l’intégration OpenTelemetry Elasticsearch](/docs/opentelemetry/integrations/elasticsearch/elasticsearch-otel-integration-install) ou [l’installation Kubernetes](/docs/opentelemetry/integrations/elasticsearch/elasticsearch-otel-integration-k8-install) mais que vous ne voyez pas de données dans New Relic, trouvez votre problème ci-dessous et suivez les étapes de résolution.

## Déploiements basés sur l&apos;hôte [#host-troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-collector-stopped" title="Service du collecteur arrêté ou en échec">
    <strong>Comment vérifier</strong>

    ```bash
    sudo systemctl status otelcol-contrib
    ```

    <strong>Résolution</strong>

    * Si le service est inactif, démarrez-le :
      <InlineCode>
        sudo systemctl start otelcol-contrib
      </InlineCode>
    * Si le service a échoué, corrigez les erreurs de configuration et redémarrez :
      <InlineCode>
        sudo systemctl restart otelcol-contrib
      </InlineCode>
  </Collapser>

  <Collapser id="troubleshoot-collector-logs-errors" title="Les logs du Collecteur signalent des erreurs de scraping ou d'exportation.">
    <strong>Comment vérifier</strong>

    ```bash
    sudo journalctl -u otelcol-contrib.service -f
    ```

    <strong>Résolution</strong>

    Examinez la sortie des logs et résolvez la cause première (par exemple, problèmes de connexion, échecs d&apos;authentification ou problèmes d&apos;autorisation).
  </Collapser>

  <Collapser id="troubleshoot-connection-refused" title="Connexion refusée lors de l'appel à Elasticsearch">
    <strong>Exemple d&apos;erreur</strong>: <InlineCode>
      dial tcp \[::1]:9200: connect: connection refused
    </InlineCode>

    <strong>Résolution</strong>

    * Assurez-vous que le
      <InlineCode>
        endpoint
      </InlineCode>
      dans
      <InlineCode>
        config.yaml
      </InlineCode>
      correspond à l&apos;hôte et au port Elasticsearch.
    * Confirmez qu&apos;Elasticsearch est en cours d&apos;exécution et accessible depuis l&apos;hôte du collecteur.
  </Collapser>

  <Collapser id="troubleshoot-403" title="403 Forbidden lors de l'exportation vers New Relic">
    <strong>Exemple d&apos;erreur</strong>: <InlineCode>
      permanent error: 403 Forbidden
    </InlineCode>

    <strong>Résolution</strong>

    1. Vérifier <InlineCode>
         NEWRELIC\_LICENSE\_KEY
       </InlineCode> dans <InlineCode>
         /etc/systemd/system/otelcol-contrib.service.d/environment.conf
       </InlineCode>.

    2. Rechargez systemd et redémarrez le collecteur :

       ```bash
       sudo systemctl daemon-reload
       sudo systemctl restart otelcol-contrib
       ```
  </Collapser>

  <Collapser id="troubleshoot-permission-denied" title="Permission refusée lors de la collecte des logs">
    <strong>Exemple d&apos;erreur</strong>: <InlineCode>
      permission denied
    </InlineCode> ou <InlineCode>
      cannot open file
    </InlineCode>

    <strong>Résolution</strong>

    1. Ajoutez l&apos;utilisateur du collecteur au groupe Elasticsearch :
       ```bash
       sudo usermod -a -G elasticsearch otelcol-contrib
       ```
    2. Redémarrez le collecteur :
       <InlineCode>
         sudo systemctl restart otelcol-contrib
       </InlineCode>
  </Collapser>

  <Collapser id="troubleshoot-api-reachability" title="Impossible d'atteindre l'API Elasticsearch depuis le collecteur">
    <strong>Comment vérifier</strong>

    ```bash
    # Unsecured cluster
    curl -I http://localhost:9200

    # With authentication
    curl -u username:password -k https://localhost:9200
    ```

    <strong>Résolution</strong>

    Vérifiez que le cluster est sain, que les identifiants sont valides et que les paramètres du pare-feu ou de sécurité autorisent l&apos;accès.
  </Collapser>

  <Collapser id="troubleshoot-missing-entity" title="Entité Elasticsearch manquante dans l'interface New Relic">
    <strong>Résolution</strong>

    * Assurez-vous que le processeur
      <InlineCode>
        resourcedetection
      </InlineCode>
      est inclus dans chaque pipeline de métriques.
    * Vérifier que
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      est défini via le processeur
      <InlineCode>
        resource/cluster_name_override
      </InlineCode>
      .
  </Collapser>

  <Collapser id="troubleshoot-logs-missing" title="Métriques présentes mais logs manquants">
    <strong>Résolution</strong>

    * Confirmez que les chemins du récepteur
      <InlineCode>
        filelog
      </InlineCode>
      sont corrects et absolus.
    * Vérifiez que le pipeline de logs inclut le récepteur
      <InlineCode>
        filelog
      </InlineCode>
      et l&apos;exportateur
      <InlineCode>
        otlphttp
      </InlineCode>
      .
  </Collapser>
</CollapserGroup>

## Déploiements Kubernetes [#kubernetes-troubleshooting]

<CollapserGroup>
  <Collapser id="troubleshoot-k8s-no-pods-discovered" title="Aucun pod Elasticsearch découvert - étiquettes manquantes">
    <strong>Comment vérifier</strong>

    ```bash
    # Verify your Elasticsearch pods have the required label
    kubectl get pods -n <namespace> -l app=elasticsearch --show-labels
    ```

    <strong>Résolution</strong>

    Si aucun pod n’est renvoyé, vos pods Elasticsearch ne possèdent pas l’étiquette <InlineCode>
      app=elasticsearch
    </InlineCode> requise. Le receiver\_creator ne peut pas découvrir de pods sans étiquettes correspondantes.

    * Pour un StatefulSet/déploiement, ajoutez l’étiquette dans le modèle de pod :
      ```yaml
      spec:
        template:
          metadata:
            labels:
              app: elasticsearch
      ```
    * Pour les pods existants, ajoutez l’étiquette et redémarrez :
      ```bash
      kubectl label pods -l <your-selector> app=elasticsearch -n <namespace>
      kubectl rollout restart statefulset/elasticsearch -n <namespace>
      ```
    * Si vous utilisez des étiquettes personnalisées, mettez à jour la règle du récepteur dans values.yaml pour qu’elle corresponde à vos étiquettes :
      ```yaml
      rule: type == "pod" && labels["app"] == "your-custom-label"
      ```
  </Collapser>

  <Collapser id="troubleshoot-k8s-collector-not-running" title="Les pods du Collector ne s'exécutent pas ou plantent">
    <strong>Comment vérifier</strong>

    ```bash
    kubectl get pods -n newrelic
    kubectl describe pod <collector-pod-name> -n newrelic
    ```

    <strong>Résolution</strong>

    * Vérifiez les événements du pod pour détecter des erreurs :
      <InlineCode>
        kubectl describe pod
      </InlineCode>

    * Consultez les logs du collecteur :

      ```bash
      kubectl logs -n newrelic -l app.kubernetes.io/name=opentelemetry-collector
      ```

    * Vérifiez que le secret existe :

      ```bash
      kubectl get secret newrelic-licenses -n newrelic
      ```

    * Vérifiez que les limites de ressources ne sont pas trop basses
  </Collapser>

  <Collapser id="troubleshoot-k8s-discovery-errors" title="Le créateur de Récepteur ne peut pas découvrir les pods">
    <strong>Comment vérifier</strong>

    ```bash
    # Check collector logs for discovery errors
    kubectl logs -n newrelic -l app.kubernetes.io/name=opentelemetry-collector | grep "receiver_creator"
    ```

    <strong>Résolution</strong>

    * Vérifiez que les autorisations RBAC sont correctement définies :

      ```bash
      kubectl get clusterrole | grep opentelemetry
      kubectl describe clusterrole <role-name>
      ```

    * Assurez-vous que le collecteur dispose des permissions pour surveiller les pods, les nœuds, et les points de terminaison

    * Vérifiez que l’extension k8s\_observer est activée dans la configuration
  </Collapser>

  <Collapser id="troubleshoot-k8s-network-connectivity" title="Collector ne peut pas se connecter aux pods Elasticsearch">
    <strong>Comment vérifier</strong>

    ```bash
    # Check network policies
    kubectl get networkpolicies -n <namespace>

    # Test connectivity from collector to Elasticsearch
    kubectl exec -n newrelic <collector-pod> -- curl http://<es-pod-ip>:9200
    ```

    <strong>Résolution</strong>

    * Vérifiez que les stratégies réseau autorisent le trafic depuis l’espace de nommage newrelic vers votre espace de nommage Elasticsearch
    * Vérifiez si les pods Elasticsearch exposent le port correct (par défaut : 9200)
    * Assurez-vous qu’aucune règle de pare-feu ne bloque la communication inter-pod
  </Collapser>

  <Collapser id="troubleshoot-k8s-wrong-endpoint" title="Erreurs 403 Forbidden ou d’authentification dans Kubernetes">
    <strong>Exemple d&apos;erreur</strong>: <InlineCode>
      permanent error: 403 Forbidden
    </InlineCode>

    <strong>Résolution</strong>

    * Vérifiez que le secret contient la bonne clé de licence :

      ```bash
      kubectl get secret newrelic-licenses -n newrelic -o jsonpath='{.data.NEWRELIC_LICENSE_KEY}' | base64 -d
      ```

    * Assurez-vous que le point de terminaison OTLP est correct pour votre région

    * Vérifiez que le secret est monté dans le pod du collecteur :

      ```bash
      kubectl describe pod <collector-pod> -n newrelic | grep -A5 "Environment"
      ```
  </Collapser>

  <Collapser id="troubleshoot-k8s-logs-not-collected" title="Les logs ne sont pas collectés dans Kubernetes">
    <strong>Résolution</strong>

    * Vérifiez que vous utilisez
      <InlineCode>
        mode: daemonset
      </InlineCode>
      (le mode de déploiement ne peut pas accéder aux log des nœuds)

    * Vérifiez que les montages de volumes sont correctement configurés :

      ```bash
      kubectl describe pod <collector-pod> -n newrelic | grep -A10 "Mounts"
      ```

    * Vérifiez que le chemin du Récepteur filelog correspond à vos logs de pod Elasticsearch :

      ```bash
      kubectl exec -n newrelic <collector-pod> -- ls /var/log/pods/*/elasticsearch*/*.log
      ```

    * Assurez-vous que le collecteur dispose des droits de lecture sur les répertoires de log de l’hôte
  </Collapser>

  <Collapser id="troubleshoot-k8s-cluster-name-missing" title="Métriques sans l’attribut k8s.cluster.name">
    <strong>Résolution</strong>

    * Vérifiez que la variable d’environnement
      <InlineCode>
        K8S_CLUSTER_NAME
      </InlineCode>
      est définie dans values.yaml

    * Vérifiez que le Processeur
      <InlineCode>
        resource/cluster
      </InlineCode>
      se trouve dans le pipeline de métriques

    * Requête à vérifier :

      ```sql
      FROM Metric SELECT * WHERE metricName LIKE 'elasticsearch.%' LIMIT 1
      ```

      Vérifiez si l’attribut <InlineCode>
        k8s.cluster.name
      </InlineCode> est présent
  </Collapser>
</CollapserGroup>

## Corrélation APM et tracing distribué [#correlation-troubleshooting]

Ces problèmes s’appliquent lorsque vous avez configuré [la corrélation APM avec le tracing distribué](/docs/opentelemetry/integrations/elasticsearch/distributed-tracing).

<CollapserGroup>
  <Collapser id="troubleshoot-no-es-spans" title="Aucun span Elasticsearch n’apparaît dans New Relic">
    <strong>Comment vérifier</strong>

    ```sql
    FROM Span SELECT count(*) WHERE es.cluster.name = '<elasticsearch-cluster-name>' SINCE 30 minutes ago
    ```

    <strong>Résolution</strong>

    * L’exportation native de trace OTLP nécessite <strong>Elasticsearch 9.4 ou version ultérieure</strong>. Confirmez votre version avec
      <InlineCode>
        curl http://localhost:9200
      </InlineCode>
      .
    * Vérifiez que les trois paramètres sont présents dans
      <InlineCode>
        elasticsearch.yml
      </InlineCode>
      :
      <InlineCode>
        telemetry.tracing.enabled: true
      </InlineCode>
      ,
      <InlineCode>
        telemetry.export.endpoint
      </InlineCode>
      , et
      <InlineCode>
        telemetry.tracing.sample_rate
      </InlineCode>
      .
    * Confirmez que la propriété système JVM
      <InlineCode>
        -Dtelemetry.otel.traces.enabled=true
      </InlineCode>
      est définie (dans
      <InlineCode>
        jvm.options
      </InlineCode>
      ou
      <InlineCode>
        ES_JAVA_OPTS
      </InlineCode>
      ), puis redémarrez Elasticsearch.
    * Le
      <InlineCode>
        telemetry.tracing.sample_rate
      </InlineCode>
      par défaut est
      <InlineCode>
        0.001
      </InlineCode>
      (0,1 %). Augmentez-le lors de la validation afin que les spans apparaissent rapidement.
  </Collapser>

  <Collapser id="troubleshoot-traces-pipeline" title="Elasticsearch exporte des spans, mais ils n’atteignent jamais New Relic">
    <strong>Résolution</strong>

    * Confirmez que le collecteur dispose d&apos;un récepteur
      <InlineCode>
        otlp
      </InlineCode>
      avec le protocole gRPC activé sur
      <InlineCode>
        0.0.0.0:4317
      </InlineCode>
      , et que le point de terminaison est accessible depuis les nœuds Elasticsearch.
    * Confirmez qu’un pipeline
      <InlineCode>
        traces
      </InlineCode>
      existe et inclut le récepteur
      <InlineCode>
        otlp
      </InlineCode>
      et l’exportateur
      <InlineCode>
        otlphttp
      </InlineCode>
      .
    * Vérifiez les logs du collecteur pour les erreurs de récepteur OTLP ou d&apos;exportation.
  </Collapser>

  <Collapser id="troubleshoot-cluster-self-loop" title="Le cluster montre une relation avec lui-même (s'appelle lui-même)">
    <strong>Cause</strong>

    Une boucle sur elle-même apparaît lorsque des spans Elasticsearch atteignent New Relic sans pouvoir être attribués à une application appelante. Il existe deux sources courantes :

    * <strong>Spans Elasticsearch sans parent (racine)</strong> : spans sans span d’application parent, tels que les sondes d’intégrité Kubernetes ou les propres appels de scraping du récepteur de métriques Elasticsearch (
      <InlineCode>
        \_nodes/stats
      </InlineCode>
      ,
      <InlineCode>
        \_cluster/health
      </InlineCode>
      et similaires). Parce qu’ils ne font pas partie de la trace d’une application, New Relic n’a pas de service appelant et établit la relation sur le cluster lui-même.
    * <strong>L&apos;adresse propre du nœud</strong> : les spans du serveur Elasticsearch contiennent
      <InlineCode>
        http.request.headers.host
      </InlineCode>
      (et
      <InlineCode>
        server.address
      </InlineCode>
      ), que New Relic résout vers le cluster.

    <strong>Résolution</strong>

    Ajoutez les deux processeurs au pipeline <InlineCode>
      traces
    </InlineCode>, puis redémarrez le collecteur. <InlineCode>
      filter/drop\_rootless\_es
    </InlineCode> rejette les spans Elasticsearch sans parent (les spans pilotés par l’application ont toujours un parent, ils sont donc conservés), et <InlineCode>
      transform/strip\_es\_host
    </InlineCode> supprime les attributs d’adresse :

    ```yaml
    processors:
      filter/drop_rootless_es:
        error_mode: ignore
        traces:
          span:
            - 'instrumentation_scope.name == "elasticsearch" and IsRootSpan()'
      transform/strip_es_host:
        error_mode: ignore
        trace_statements:
          - context: span
            statements:
              - delete_key(attributes, "http.request.headers.host") where instrumentation_scope.name == "elasticsearch"
              - delete_key(attributes, "server.address") where instrumentation_scope.name == "elasticsearch"
    # traces pipeline: processors: [filter/drop_rootless_es, transform/strip_es_host, batch]
    ```

    Les auto-boucles existantes s’effacent d’elles-mêmes une fois que les spans corrigés arrivent et que la relation précédente expire (cela peut prendre jusqu’à environ 75 minutes).
  </Collapser>

  <Collapser id="troubleshoot-app-not-linked" title="Les spans Elasticsearch arrivent, mais les applications ne sont pas liées au cluster">
    <strong>Résolution</strong>

    * Assurez-vous que vos applications sont instrumentées et propagent l’en-tête W3C
      <InlineCode>
        traceparent
      </InlineCode>
      lors de leurs appels Elasticsearch. La plupart des clients Elasticsearch modernes le font automatiquement lorsque l’application est instrumentée avec OpenTelemetry.
    * Ouvrez une trace distribuée qui inclut un appel Elasticsearch, et confirmez que les spans d’application et les spans Elasticsearch partagent la même trace.
    * Laissez quelques minutes à la relation pour s&apos;établir. New Relic réévalue périodiquement les relations entre les entités.
  </Collapser>

  <Collapser id="troubleshoot-name-mismatch" title="Les traces et les métriques se résolvent en différentes entités de cluster">
    <strong>Résolution</strong>

    * Le chemin des traces se base sur
      <InlineCode>
        es.cluster.name
      </InlineCode>
      (estampillé par Elasticsearch sur ses spans) et le chemin des métriques sur
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      . Le
      <InlineCode>
        elasticsearchreceiver
      </InlineCode>
      rapporte
      <InlineCode>
        elasticsearch.cluster.name
      </InlineCode>
      automatiquement à partir de la valeur renvoyée par Elasticsearch, de sorte que les deux dérivent du même
      <InlineCode>
        cluster.name
      </InlineCode>
      et se résolvent en une seule entité : aucune configuration de collecteur supplémentaire n’est nécessaire.
    * Ne forcez pas le nom du cluster de métriques à une valeur fixe. Si la configuration de votre collecteur le définit avec un Processeur
      <InlineCode>
        resource
      </InlineCode>
      (par exemple un
      <InlineCode>
        resource/cluster_name_override
      </InlineCode>
      qui code le nom en dur), supprimez cette surcharge — sinon les métriques et les traces se résolvent en deux entités différentes et l’entité corrélée n’affiche aucune donnée de métriques.
    * Assurez-vous que votre
      <InlineCode>
        cluster.name
      </InlineCode>
      Elasticsearch est unique au sein de votre compte New Relic afin qu’il corresponde à une seule entité sans ambiguïté.
  </Collapser>
</CollapserGroup>
