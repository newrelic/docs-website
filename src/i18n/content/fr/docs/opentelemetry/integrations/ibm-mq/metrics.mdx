Cette référence couvre les métriques et attributs IBM MQ collectés via OpenTelemetry : les métriques que l’exportateur [mq-metric-samples](https://github.com/ibm-messaging/mq-metric-samples) publie et que le collecteur transfère à New Relic. Il s’applique à la fois aux déploiements d’ [hôte Linux](/docs/opentelemetry/integrations/ibm-mq/host) et [Kubernetes](/docs/opentelemetry/integrations/ibm-mq/kubernetes) ; la forme de la métrique est identique.

## Collecte des métriques [#collection]

Toutes les métriques conservent la forme brute de Prometheus que l&apos;exportateur émet : les **noms avec trait de soulignement** (`ibmmq_*`) et les étiquettes brutes **`qmgr`**, **`queue`** et **`channel`**, plus l&apos;attribut d&apos;identité `target.name` et le tag `cluster.name` facultatif que le collecteur attache. La synthèse d&apos;entité IBM MQ de New Relic dépend de cette forme, le collecteur transfère donc les noms et les étiquettes sans modification.

<Callout variant="important">
  **Activez les statistiques MQI sur chaque gestionnaire de files d’attente, sinon les métriques de débit et de temps resteront vides.** La santé du gestionnaire de files d’attente, la profondeur de la file d’attente et le statut du canal sont disponibles d’emblée, mais les métriques d’activité MQI (les tables de [débit de la file d’attente](#metrics-queue-throughput) et d’ [activité MQI du gestionnaire de files d’attente](#metrics-qmgr-mqi) — `ibmmq_queue_mqput_count`, `ibmmq_queue_average_queue_time_seconds`, etc.) nécessitent que la collecte des statistiques soit **activée**, ce qui est **désactivé par défaut**. Activez-la une fois par gestionnaire de files d’attente avec MQSC — par exemple `ALTER QMGR STATMQI(ON) STATQ(ON)`, puis `ALTER QLOCAL(...) STATQ(ON)` pour toute file d’attente sur laquelle vous souhaitez des statistiques par file d’attente (ou fiez-vous à la valeur par défaut `STATQ` du gestionnaire de files d’attente). Sans cela, l’exportateur est sain et l’entité apparaît, mais ces panneaux s’affichent vides. Consultez la [documentation de mq-metric-samples](https://github.com/ibm-messaging/mq-metric-samples) pour connaître les statistiques exactes dont dépend chaque métrique.
</Callout>

<Callout variant="tip">
  Les métriques de statut renvoient des valeurs **enum** numériques, et non `1`/`0` — consultez la [référence des codes de statut](#status-codes) ci-dessous avant de configurer des alertes à leur sujet. Les compteurs sont convertis en temporalité delta par le collecteur, utilisez donc `sum()` / `rate()` sur une fenêtre plutôt que `latest()` pour les représenter graphiquement.
</Callout>

Les tableaux ci-dessous regroupent les métriques OpenTelemetry par domaine. Pour lister chaque métrique remontant actuellement dans votre compte, exécutez :

```sql
FROM Metric SELECT uniques(metricName, 2000) WHERE metricName LIKE 'ibmmq_%' SINCE 1 day ago
```

  <Collapser id="status-codes" title="Référence des codes d'état MQ">
    Les métriques d&apos;état IBM MQ signalent des valeurs d&apos;énumération numériques, et **non** `1`/`0` — et la valeur saine (« running ») diffère selon la métrique (`2` pour l&apos;état au niveau du gestionnaire de files d&apos;attente, `3` pour l&apos;état du canal). Alertez sur l&apos;*inégalité* par rapport à la valeur d&apos;exécution (par exemple, `ibmmq_qmgr_status != 2`) :

    | métrique                              | Valeur saine | Signification                                                         |
    | ------------------------------------- | ------------ | --------------------------------------------------------------------- |
    | `ibmmq_qmgr_status`                   | `2`          | Le gestionnaire de files d&apos;attente est en cours d&apos;exécution |
    | `ibmmq_qmgr_command_server_status`    | `2`          | Le serveur de commandes est en cours d&apos;exécution                 |
    | `ibmmq_qmgr_channel_initiator_status` | `2`          | L&apos;initiateur de canal est en cours d&apos;exécution              |
    | `ibmmq_channel_status`                | `3`          | Le canal est en cours d&apos;exécution                                |

    Toute autre valeur (ou un point de données manquant) signifie que le composant n&apos;est pas dans son état d&apos;exécution.
  </Collapser>

## Détails de la collecte des métriques [#collection-details]

### Fréquence de collecte

* **Intervalle par défaut**: 60 secondes (le `scrape_interval` du collecteur). Il doit être supérieur ou égal au `pollInterval` propre à l&apos;exportateur mq-metric-samples.
* **Configurable**: ajustez `IBMMQ_SCRAPE_INTERVAL` (Linux) ou `scrape_interval` dans le `values.yaml` Helm (Kubernetes).

### Source des données

Toutes les métriques proviennent de l&apos;exportateur [mq-metric-samples](https://github.com/ibm-messaging/mq-metric-samples), qui interroge chaque gestionnaire de files d&apos;attente via PCF et republie les statistiques sous forme de métriques Prometheus sur un point de terminaison HTTP `/metrics`. Le récepteur `prometheus` du collecteur scrape ce point de terminaison.

### types métriques

* **Jauges** — valeurs ponctuelles telles que `ibmmq_qmgr_status`, `ibmmq_queue_depth` et `ibmmq_channel_status`. Graphique avec `latest()`.
* **Compteurs** — totaux cumulés tels que `ibmmq_queue_mqput_count`. Le Processeur `cumulativetodelta` du collecteur les convertit en temporalité delta, donc créez des graphiques avec `sum()` ou `rate()` plutôt qu&apos;avec `latest()`.
