Avant de commencer à monitorer votre MySQL avec NRDOT, assurez-vous que votre environnement répond à ces exigences.

## Prérequis [#prereq]

Avant de commencer, assurez-vous d’avoir les éléments suivants :

* [Clé de licence](/docs/apis/intro-apis/new-relic-api-keys/#ingest-license-key)New Relic valide
* Connectivité réseau entre l&apos;hôte où vous installez le Collector NRDOT et votre base de données MySQL. Si vous prévoyez d&apos;installer le Collector NRDOT sur un hôte différent de votre base de données MySQL, consultez les [exigences d&apos;accès réseau](#network).
* Connectivité réseau vers la [documentation sur les points de terminaison OTLP de New Relic](/docs/opentelemetry/best-practices/opentelemetry-otlp/)
* Cette intégration est disponible dans le cadre du programme de préversion publique de New Relic. Vérifiez auprès de votre responsable d’organisation pour vous inscrire depuis la page [Préversions et essais](https://one.newrelic.com/admin-portal/promotion-management/home).

## Exigences d&apos;accès réseau [#network]

Par défaut, NRDOT se connecte via **TCP** (`transport: tcp` dans la configuration du Récepteur, la valeur par défaut). Si le collecteur s&apos;exécute sur le même hôte que la base de données, vous pouvez plutôt définir `transport: unix` et pointer `endpoint` vers le socket de domaine Unix de la base de données (par exemple, `/var/run/mysqld/mysqld.sock`), ce qui contourne entièrement les vérifications réseau ci-dessous. Pour tout autre déploiement — collecteur et base de données sur des hôtes, conteneurs ou VPC différents — TCP est requis.

<table>
  <thead>
    <tr>
      <th>
        déploierons
      </th>

      <th>
        Ce qu&apos;il faut vérifier
      </th>
    </tr>
  </thead>

  <tbody>
    <tr>
      <td>
        MySQL autogéré sur EC2
      </td>

      <td>
        **Groupe de sécurité**

        : ajoutez une règle entrante sur le port de la base de données (par défaut 

        `3306`

        ) à partir de la source du collecteur — son propre ID de groupe de sécurité (même VPC, préféré à une adresse IP brute) si le collecteur s&apos;exécute sur une instance EC2 différente, ou aucune règle n&apos;est nécessaire s&apos;il s&apos;exécute en tant que sidecar sur la même instance. Vérifiez également 

        `bind-address`

         dans 

        `my.cnf`

        : de nombreuses valeurs par défaut de distribution incluent 

        `bind-address = 127.0.0.1`

        , qui refuse toute connexion TCP non locale — définissez-la sur l&apos;adresse IP privée de l&apos;instance ou sur 

        `0.0.0.0`

         avant qu&apos;un collecteur distant ne puisse l&apos;atteindre.
      </td>
    </tr>

    <tr>
      <td>
        Amazon RDS/Aurora pour MySQL
      </td>

      <td>
        **Groupe de sécurité VPC**

        : ajoutez une règle entrante sur le port de l&apos;instance RDS (par défaut 

        `3306`

        ) à partir du groupe de sécurité ou de l&apos;adresse IP privée du collecteur ; RDS n&apos;a pas de 

        `my.cnf`

         au niveau du système d&apos;exploitation à modifier, c&apos;est donc la seule passerelle réseau. Les 

        **autorisations**

         doivent provenir de l&apos;utilisateur maître RDS — RDS n&apos;a pas de compte 

        `root`

        . 

        **Privilèges restreints**

        : 

        `SUPER`

         et 

        `FILE`

         sont restreints ou indisponibles selon la version du moteur RDS et le groupe de paramètres. 

        **TLS**

        : les instances RDS avec l&apos;application de la règle « Require SSL/TLS » nécessitent que le collecteur fasse confiance à l&apos;autorité de certification RDS d&apos;Amazon — définissez 

        `tls.ca_file`

         (ou 

        `tls.ca_pem`

        ) sur le 

        [groupe de certificats Amazon RDS](https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem)

         et laissez 

        `tls.insecure`

        /

        `tls.insecure_skip_verify`

         sur 

        `false`

        .
      </td>
    </tr>

    <tr>
      <td>
        Tout déploiement distant/inter-hôte
      </td>

      <td>
        MySQL traite 

        `'<user>'@'localhost'`

         et 

        `'<user>'@'%'`

         (ou un hôte/CIDR spécifique) comme des 

        **comptes différents**

        , même avec un nom d&apos;utilisateur identique — la création de l&apos;utilisateur de monitoring en tant que 

        `'<user>'@'localhost'`

         échoue silencieusement à s&apos;authentifier à partir d&apos;un collecteur s&apos;exécutant n&apos;importe où ailleurs, avec une erreur d&apos;accès refusé indiscernable d&apos;un mot de passe incorrect. Utilisez 

        `'<user>'@'%'`

         ou limitez-le à l&apos;IP/CIDR privé spécifique du collecteur.
      </td>
    </tr>
  </tbody>
</table>

<Callout variant="important">
  Vérifié sur une instance Amazon RDS pour MySQL active : la famille de groupes de paramètres `mysql8.0` de RDS n’expose aucun paramètre `performance_schema_consumer_*` — seuls les paramètres de dimensionnement/tampon ainsi que `performance_schema`, `slow_query_log` et `long_query_time` y sont configurables. Cela signifie que `events_waits_current` (nécessaire pour `mysql.events_waits_current.timer_wait` et les dashboards basés sur l’attente en général) ne peut être activé qu’à l’exécution sur RDS, et qu’il ne survit pas à un redémarrage ou à un basculement.
</Callout>

## Configuration côté serveur recommandée [#server]

Configurez ces paramètres de serveur MySQL pour vous assurer que le Récepteur peut collecter toutes les métriques et plans de requête disponibles. Le tableau suivant répertorie les paramètres et leurs valeurs recommandées :

  <thead>
    <tr>
      <th>

        `1024`

        octets
