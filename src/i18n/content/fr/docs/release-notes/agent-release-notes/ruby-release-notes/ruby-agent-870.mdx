## v8.7.0

* **Transfert de logs des logs en contexte APM activé par défaut**

  Le transfert automatique de logs d’application est désormais activé par défaut. Cette version de l’agent enverra automatiquement des logs d’application enrichis à New Relic. Pour en savoir plus sur cette fonctionnalité, cliquez [ici](https://docs.newrelic.com/docs/apm/new-relic-apm/getting-started/get-started-logs-context/), et des options de configuration supplémentaires sont disponibles [ici](https://docs.newrelic.com/docs/logs/logs-context/configure-logs-context-ruby). Pour savoir comment activer ou désactiver l’ingestion de logs par compte, cliquez [ici](https://docs.newrelic.com/docs/logs/logs-context/disable-automatic-logging).

* **Amélioration de la prise en charge asynchrone et de l&apos;instrumentation des threads**

  Auparavant, l’agent n’était pas en mesure d’enregistrer les événements, et les métriques dans les Threads créés au sein d’une transaction déjà en cours d’exécution. Cette sortie comprend 2 nouvelles options de configuration pour prendre en charge les applications multithreads afin d’instrumenter automatiquement les threads. Une nouvelle option de configuration,`instrumentation.thread.tracing` (désactivée par défaut), a été introduite, et, lorsqu’elle est activée, elle permettra à l’agent d’insérer le tracing New Relic dans tous les Threads créés par une application. Pour prendre en charge les applications qui souhaitent uniquement que certains threads soient instrumentés par New Relic, une nouvelle classe est disponible, `NewRelic::TracedThread`, qui créera un thread incluant l’instrumentation New Relic ; consultez notre [documentation de l’API](https://www.rubydoc.info/gems/newrelic_rpm/NewRelic) pour obtenir plus de détails.

* **Dépréciation de la prise en charge de Ruby 2.2**

  Ruby 2.2 a atteint sa fin de vie le 31 mars 2018. L’agent a déprécié la prise en charge de Ruby 2.2 et apportera des modifications majeures pour cette version lors de sa prochaine sortie majeure.

  Pour les gems avec des versions obsolètes, nous ne testerons plus ces versions dans notre suite multiverse. Elles peuvent, cependant, toujours être compatibles avec l&apos;agent. Nous ne traiterons plus les rapports de bugs pour les problèmes rencontrés avec ces versions de la gem.

* **Exploiter en interne `Object.const_get`, et `Object.const_defined?`**

  Lorsque vous recherchez dynamiquement une constante de classe à partir d’une chaîne, ou que vous en obtenez une référence, utilisez les méthodes intégrées de la classe `Object` dans la mesure du possible pour bénéficier d’opérations plus simples, et plus performantes. Tous les JRubies, et CRubies v2.5, et versions antérieures ont besoin d’un peu d’aide au-delà de ce que `Object` peut fournir, étant donné que ces Rubies peuvent renvoyer une constante indésirable provenant d’un espace de nommage différent de celui qui a été spécifié. Mais pour tous les autres Rubies, et même pour ces Rubies dans des contextes où nous pouvons faire confiance à 100 % à la valeur de la chaîne entrante, utilisez les méthodes de la classe `Object`, et profitez de leurs avantages.

* **Clarifier la documentation pour la configuration de `rake.tasks`**

  La description de `rake.tasks` dans le fichier `newrelic.yml` par défaut et la [documentation de configuration de l’agent Ruby New Relic](https://docs.newrelic.com/docs/apm/agents/ruby-agent/configuration/ruby-agent-configuration#rake-tasks) ont été mises à jour pour clarifier son comportement et son utilisation. La documentation indique désormais :

  > Spécifiez un éventail de tâches Rake à instrumenter automatiquement. Cette option de configuration convertit l’éventail en une liste RegEx. Si vous souhaitez autoriser toutes les tâches par défaut, utilisez `rake.tasks: [.+]`. Les tâches Rake ne seront pas instrumentées à moins qu’elles ne soient ajoutées à cette liste. Pour plus d’informations, consultez la (documentation sur l’instrumentation New Relic Rake)\[/docs/apm/agents/ruby-agent/background-jobs/rake-instrumentation].

  Nous remercions @robotfelix d’avoir suggéré ces modifications.

* **Activez le paramètre des variables d’environnement permettant aux configurations d’éventail d’être converties en éventails**

  Avant ce changement, lorsque des listes séparées par des virgules étaient passées comme variables d’environnement, une erreur était émise vers le `newrelic_agent.log`, et un String était défini comme valeur. Désormais, les éventails seront convertis avec précision.

* **Correction de bug : permet aux TransactionEvents d’être échantillonnés au taux attendu**

  La valeur de capacité `transaction_events.max_samples_stored` dans le TransactionEventAggregator ne correspondait pas à son intervalle de cycle de collecte attendu, provoquant un suréchantillonnage des TransactionEvents. Ce correctif s’appuie sur les mises à jour effectuées dans [#952](https://github.com/newrelic/newrelic-ruby-agent/pull/952) afin que l’intervalle et la capacité se comportent comme prévu pour les options de configuration `transaction_events*` renommées.

* **Correction de bug : attributs manquants pour les événements d’erreur créés en dehors d’une transaction**

  Auparavant, l’agent n’attribuait pas de priorité aux événements d’erreur qui étaient créés en appelant notice\_error en dehors de la portée d’une transaction. Cela causait des problèmes d’échantillonnage lorsque le tampon de l’événement d’erreur était plein, entraînant un `NoMethodError: undefined method '<' for nil:NilClass` dans le newrelic\_agent.log. Cette correction de bug garantit qu’une priorité est toujours attribuée aux événements d’erreur afin que l’agent soit capable d’échantillonner correctement ces événements d’erreur. Nous remercions @olleolleolle d’avoir porté ce problème à notre attention.
