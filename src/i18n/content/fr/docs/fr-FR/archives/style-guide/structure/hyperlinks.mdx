Dans la mesure du possible, incluez des hyperliens pertinents dans le texte lui-même. Évitez de créer des listes de liens vers des documents dans la section **Pour plus d’aide**, car il est plus difficile pour les futurs rédacteurs de déterminer pourquoi ils sont importants.

<Callout variant="tip">
  Si vous créez un lien vers le produit, consultez notre page de guide de style sur les [chemins d’interface utilisateur](/docs/style-guide/quick-reference/ui-paths).
</Callout>

## Syntaxe de lien [#link-syntax]

Le site de documentation utilise la syntaxe des liens en ligne Markdown :

```markdown
[link text](https://example.com)
```

Si vous créez un lien vers une autre page du site de documentation, vous devez utiliser des liens « relatifs » (en omettant l’URL racine `https://docs.newrelic.com` du site de documentation) :

```markdown
[link text](/docs/category-path/doc-path/)
```

<Callout variant="tip">
  Markdown [prend également en charge les liens de style « référence »](https://daringfireball.net/projects/markdown/syntax#link), où l&apos;URL de destination est répertoriée à la fin du document. Bien qu&apos;ils fonctionnent et s&apos;affichent correctement, nous évitons d&apos;utiliser ce style de lien pour quelques raisons :

  * C’est un style moins courant, et il peut être déroutant pour les contributeurs.
  * Nos documentations sont très longues, ce qui peut rendre la connexion d&apos;un lien à sa destination peu pratique pour les contributeurs.
</Callout>

## Texte de lien [#hyperlinks-linktext]

Suivez ces directives lorsque vous rédigez du texte pour des hyperliens :

* **Libellés :** assurez-vous que chaque lien dans le document a un libellé textuel unique et significatif. N&apos;utilisez pas la même chaîne de texte pour libeller différents liens.
* **Emplacement :** Incluez une étiquette de texte claire et concise pour identifier la destination du lien. Donnez du contexte supplémentaire si vous faites un lien vers un site externe. Pourquoi y envoyez-vous quelqu&apos;un ?
* **Cliquez ici :** n&apos;utilisez pas « cliquez ici » ou d&apos;autres libellés de lien sans signification.
* **« Test de lien : »** Lisez uniquement les liens, sans le texte environnant. Chacun peut-il se suffire à lui-même comme description claire de la destination du lien si c’est tout ce que l’utilisateur regarde sur la page ?
* **Évitez les préfixes d’URL :** si vous envoyez les utilisateurs vers une adresse où vous souhaitez utiliser l’URL comme texte de lien, supprimez les préfixes `https:` et `www.` du texte de lien. Par exemple, `[github.com](https://github.com)` et non `[https://github.com/](https://github.com)`. Ou `[github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)` et non `[https://github.com/newrelic/docs-website](https://github.com/newrelic/docs-website/)`.

Faites le test de lien pour ces trois exemples. Le dernier est le meilleur pour les lecteurs cherchant des informations sur la configuration de PHP, car le lien l’identifie clairement, sans avoir à lire quoi que ce soit d’autre sur la page.

## Liens d’assistance [#support-link]

**N&apos;incluez jamais de lien hypertexte vers l&apos;adresse e-mail du support.** Cela évite le spam et garantit que les clients utilisent le formulaire de soumission de ticket pour créer des tickets afin de recevoir la priorité de support appropriée. Si vous devez indiquer aux clients de contacter le support, utilisez plutôt ceci :

```md
Get support at [support.newrelic.com](support.newrelic.com).
```

## Liens d’ancrage [#hyperlinks-anchor]

Si votre lien inclut une ancre (par exemple, `#inivar-scope`), utilisez le chemin de document complet et **actuel** qu&apos;il utilise. Certains navigateurs ne conservent pas les ancres avec les redirections.

Lors de la création ou de la modification d’un `id` HTML pour un lien d’ancrage, suivez ces directives :

* N’utilisez que des minuscules lors de la création de nouveaux ID.
* Utilisez des traits d&apos;union `-` pour séparer les mots. N&apos;utilisez pas de traits de soulignement `_`.
* Lors de la réorganisation d’un document, essayez de conserver les liens d’ancrage entrants dans la mesure du possible. Gardez à l’esprit que lorsque vous supprimez un en-tête de niveau deux `##`, cela rompra tous les liens vers cet en-tête.
* Évitez de modifier un ID d’ancrage existant, car nous pourrions monitorer le trafic vers celui-ci depuis notre compte New Relic interne.

## Liens profonds vers le produit [#deep-links]

Lorsque vous dirigez les utilisateurs vers des parties du produit, vous souhaitez utiliser un lien profond lorsque cela est possible. L&apos;utilisation de liens profonds encourage les utilisateurs à accéder au produit et, s&apos;ils n&apos;ont pas encore créé de compte, les prompt à s&apos;inscrire. Cela est plus efficace que de simplement créer un lien vers une page d&apos;inscription. Cependant, l&apos;utilisation de liens profonds dans l&apos;interface utilisateur ne fonctionne que parfois et il faut un peu d&apos;expérimentation pour trouver un bon permalien.

Voici un exemple de workflow utilisant l&apos;interface utilisateur de log :

1. Depuis votre compte professionnel, accédez à la partie de l&apos;interface utilisateur que vous souhaitez lier. Récupérez l&apos;URL complète telle qu&apos;elle apparaît naturellement.
2. Ouvrez une fenêtre de navigation privée et collez l’URL.
3. Modifiez l&apos;URL pour un état plus propre. Nous voulons des URL simples si possible. Pour les logs, cela ressemble à ceci : `https://one.newrelic.com/logger`.
4. New Relic affichera un prompt pour vous connecter, connectez-vous donc avec une adresse e-mail non professionnelle.

L&apos;URL vous renvoie à la page de log et remplit automatiquement les informations d&apos;identification de l&apos;ID de compte. Cette page est accessible par un lien profond.

Si l’URL simple ne fonctionne pas, vous avez deux étapes supplémentaires. Voici un exemple de workflow où l’URL simple ne fonctionne pas. Nous utiliserons cette URL comme base de travail :

```
https://one.newrelic.com/marketplace/install-data-source?account=[ACCOUNT_ID_HERE]&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
```

1. Après avoir trouvé votre URL, ouvrez une fenêtre de navigation privée et collez l’URL simple : `https://one.newrelic.com/marketplace/install-data-source`Cette page ne se charge pas avec l’URL simplifiée.

2. Testez cette URL en supprimant la partie `account=[ACCOUNT_ID_HERE]` du slug. La nouvelle URL ressemblera à ceci :

   ```
   https://one.newrelic.com/marketplace/install-data-source?&begin=168917[…]APPLICATION%27%29&state=1ecc7248-ff69-a838-0c8e-d5eaa8bc5431
   ```

3. Collez cette URL dans une nouvelle fenêtre de navigation privée. Cela vous amènera à la page correcte avec votre ID de compte unique renseigné.

4. Confirmez avec un autre rédacteur que cette URL fonctionne en lui demandant d’ouvrir l’URL avec le numéro d’ID de compte supprimé. Ils doivent utiliser un e-mail non professionnel.

Si l’URL échoue dans l’un ou l’autre cas, il est probable que cette partie de l’interface utilisateur du produit ne puisse pas faire l’objet d’un lien profond. Dans ce cas, liez `one.newrelic.com` à la page **All capabilities**, puis décrivez le chemin selon [nos directives de cheminement](/docs/style-guide/formatting/ui-paths).

## Liens externes [#hyperlinks-external]

Lors de la création de liens vers des sites Web en dehors du sous-domaine `docs.newrelic.com` (y compris `newrelic.com`, `one.newrelic.com`, `discuss.newrelic.com`), le site de documentation inclut automatiquement du code qui ouvre le lien dans un nouvel onglet.

En plus des directives sur le texte de lien dans ce document, voici d’autres éléments à garder à l’esprit lors de la création de liens vers des sites externes :

* Réfléchissez à la meilleure façon de pérenniser vos liens. Si possible, pointez vers un domaine de premier niveau, mais pas si cela réduit l’utilité du lien. Dans quelle mesure le contenu vers lequel vous créez un lien est-il stable ? L’URL est-elle susceptible de changer ?
* Assurez-vous que votre lien est aussi utile que possible. Quelle valeur essayez-vous d&apos;ajouter au document ? Ces informations peuvent-elles être partagées d&apos;une autre manière ?
* Aidez le lecteur à comprendre pourquoi vous créez un lien vers cette source externe. Est-ce une référence utile, comme une liste de fuseaux horaires ? Est-ce un moyen de faire gagner du temps à quelqu&apos;un, par exemple en créant un lien direct vers un fichier difficile à trouver ?
* Assurez-vous que votre lien est généralement accessible. Faites-vous un lien vers un site externe qui nécessite une authentification, tel qu&apos;un référentiel (repository) GitHub privé ?
