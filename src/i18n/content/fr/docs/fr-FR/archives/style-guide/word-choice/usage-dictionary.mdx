Pour des raisons de cohérence dans le contenu de New Relic, voici nos directives générales d&apos;utilisation des mots :

* Nous suivons généralement le [Microsoft Style Guide](https://docs.microsoft.com/en-us/style-guide/welcome/), qui est basé sur le Chicago Manual of Style.
* Nous suivons les conventions de l&apos;anglais américain, plutôt que celles de l&apos;anglais britannique.
* Nous nous en remettons aux noms officiels des produits pour les références aux produits. (Par exemple, pour Amazon Web Services (AWS), consultez [aws.amazon.com/products](https://aws.amazon.com/products/).)
* Pour la terminologie spécifique à New Relic, nous utilisons le [glossaire du produit](/docs/using-new-relic/welcome-new-relic/getting-started/glossary).

<CollapserGroup>
  <Collapser id="account" title="compte">
    Lorsque quelqu&apos;un s&apos;inscrit à New Relic, il obtient une organisation New Relic (représentée par un ID d&apos;organisation). Cette organisation peut contenir un ou plusieurs comptes (chaque compte ayant un ID de compte). Pour en savoir plus sur la distinction entre `organization` et `account,`, voir [organisation et structure du compte](/docs/accounts/accounts-billing/account-structure/new-relic-account-structure).

    Dans l&apos;usage général, en dehors de New Relic, `account` est souvent utilisé dans un sens plus large. Par exemple, il pourrait être utilisé de la même manière que nous utilisons `organization,` ou il pourrait être utilisé pour désigner l&apos;enregistrement d&apos;utilisateur de quelqu&apos;un. Nous devrions essayer d&apos;être aussi précis que possible lors de l&apos;utilisation de ces termes. Cela est particulièrement vrai lorsque nous documentons des aspects qui s&apos;appliquent uniquement à un compte New Relic, et non à une organisation New Relic (par exemple, les données au niveau du compte et les limites de requête).

    Cela dit, plus l&apos;utilisation est générale, plus il est acceptable d&apos;utiliser `account` comme synonyme de `organization`. Par exemple, New Relic utilise parfois une expression comme « Inscrivez-vous pour obtenir un compte New Relic ». Cette substitution de `account` à `organization` est acceptable car elle correspond à la façon dont `account` est couramment utilisé et ne fait pas référence à un élément spécifique à notre définition de `account`.
  </Collapser>

  <Collapser id="account-id" title="ID de compte">
    Un numéro unique qui [identifie un compte New Relic particulier](/docs/accounts-partnerships/accounts/account-setup/account-id). N’utilisez pas `account number`.
  </Collapser>

  <Collapser id="agent" title="agent">
    Un agent New Relic est un logiciel installable qui s’intègre à plusieurs types de technologies (par exemple, des frameworks web, des systèmes d’exploitation et des types de bases de données) et rapporte des données à New Relic, généralement à une cadence spécifique. Tous les agents sont des intégrations, mais toutes les intégrations ne sont pas des agents. Beaucoup de nos agents prennent en charge de multiples intégrations ; par exemple, l’agent Java collecte des données à partir d’une variété de frameworks et de technologies Java, ou l’agent d’infrastructure active l’intégration Cassandra sur l’hôte.

    Voici une liste de ce que nous considérons comme des agents New Relic :

    * APM :

      * Agent Go
      * Agent Java
      * Agent .NET
      * Agent Node.js
      * Agent PHP
      * Agent Python
      * Agent Ruby

    * Infrastructure :

      * Agent d&apos;infrastructure
      * Agent Linux
      * Agent MacOS
      * Agent Unix
      * Agent Windows

    * Agent Browser

    * Applications mobiles :

      * Agent Android
      * Agent iOS
      * Agents hybrides (Capacitor, Flutter, etc.)

    * Réseau :

      * Agent ktranslate
      * Agent de flux réseau

    * Agent SNMP

      * Agent Syslog

    * Roku

    * Elixir

      Pour voir une liste de ce que nous considérons comme des intégrations, consultez la définition d&apos;[intégration](#integration).
  </Collapser>

  <Collapser id="AIOps" title="AIOps">
    Abréviation d&apos;intelligence artificielle pour les opérations informatiques.
  </Collapser>

  <Collapser id="ampm" title="am et pm">
    * Utilisez l’horloge de 12 heures suivie de la période (en minuscules) am ou pm.

    * Ne mettez pas d&apos;espace après le dernier chiffre dans un horodatage (12:00am, et non 12:00 am).

    * N’incluez pas de 0 au début lorsque l’heure est inférieure à 10.

      ```
      9:30am, 12:30pm, 8:30pm
      ```
  </Collapser>

  <Collapser id="aws" title="Noms de produits Amazon Web Services (AWS)">
    * Généralement appelé `AWS` dans la conversation. Référez-vous à `Amazon Web Services` en première instance, puis vous pourrez utiliser `AWS` par la suite.
    * Amazon propose un certain nombre de produits comme [Amazon EC2](https://aws.amazon.com/documentation-overview/ec2/) et [Amazon S3](https://aws.amazon.com/documentation-overview/s3/) qui sont presque toujours désignés par leur nom abrégé, plutôt que par leur nom complet. Vous pouvez abréger dans la première instance si Amazon le fait.
    * Certains produits Amazon utilisent `Amazon` comme préfixe (comme dans `Amazon EC2`), d&apos;autres `AWS` (comme dans `AWS Amplify`). Faites correspondre au [site de documentation AWS](https://aws.amazon.com/documentation).
    * Certains noms de produits Amazon peuvent également être utilisés de manière plus informelle pour faire référence à des données ou à des options de configuration. Par exemple, pour les [flux de métriques AWS](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Metric-Streams.html), AWS formate ce nom avec une majuscule initiale lorsqu’il fait référence au produit, mais lorsqu’il fait référence aux données produites, il y fait référence de manière informelle (par exemple, en tant que `metric stream data` ou `metric streams`). Nous devrions généralement faire ce que fait AWS.
  </Collapser>

  <Collapser id="ampersand-details" title="esperluette (&)">
    N’utilisez pas d’esperluettes dans les phrases ou les en-têtes, à moins qu’elles ne fassent partie d’un nom d’entreprise ou de marque. Exception : si l’espace est restreint (c’est-à-dire que « et » ne rentre pas), il est acceptable d’utiliser une esperluette.
  </Collapser>

  <Collapser id="app-name" title="nom de l’application vs alias de l’application">
    Le « nom de la machine » que le Collector utilise pour identifier de manière unique une application est son `app name`. Le paramètre de configuration côté serveur qui modifie le « nom » visible d’une application sans modifier son identifiant unique est son `app alias`.
  </Collapser>

  <Collapser id="Azure naming conventions" title="Conventions de nommage Azure">
    Utilisez les conventions de nommage de la plateforme de cloud computing Microsoft Azure telles que prescrites par Microsoft ; c&apos;est ce que les clients comprennent et reconnaissent. Par exemple, Azure Native New Relic Service.
  </Collapser>

  <Collapser id="backend" title="backend">
    Qu&apos;il soit utilisé comme adjectif ou comme nom, il s&apos;agit d&apos;un seul mot. Voir aussi [`frontend`](#frontend).
  </Collapser>

  <Collapser id="black-white" title="liste noire et liste blanche">
    N’utilisez pas. Utilisez plutôt `deny list` et `allow list`; par exemple, « Ajoutez un nom d’hôte à votre liste de refus. »
  </Collapser>

  <Collapser id="call-called" title="appels, appelant et appelé par">
    Lors de la description de la façon dont une entité communique ou est connectée à une autre, concentrez-vous sur les appels et sur la direction qu’ils prennent. Évitez d’utiliser `upstream` et `downstream` pour décrire cette interaction. Par exemple, `service A calls service B`, `called services`, `calling services`.
  </Collapser>

  <Collapser id="caps" title="Capitalisation">
    Cela est plus complexe que ce qui peut être couvert dans ce dictionnaire d&apos;utilisation. Pour des informations détaillées, voir :

    * [Capitalisation des en-têtes](/docs/style-guide/capitalization/capitalization#heading_caps)
    * [Majuscules des fonctionnalités et des éléments de l&apos;interface utilisateur](/docs/style-guide/capitalization/product-capability-feature-usage)
  </Collapser>

  <Collapser id="child-account" title="compte enfant">
    Un [compte parent](#parent-account) contient un ou plusieurs comptes enfants. Les comptes enfants étaient auparavant appelés « sous-comptes ».
  </Collapser>

  <Collapser id="click" title="Cliquez">
    En général, utilisez `click` plutôt que le terme plus vague `select`. Par exemple, vous pourriez cliquer sur quelque chose dans l&apos;interface utilisateur, puis sélectionner quelque chose dans une liste.

    Faites particulièrement attention à utiliser `click` pour décrire des actions qui n’ont de sens qu’avec une souris ; par exemple, avec un `right click` ou un `click and drag`. Utilisez également `click` lorsque l’utilisateur doit cliquer sur un objet non sélectionnable (`to save your changes, click anywhere outside the dialog box`). Voir aussi [survol de la souris](#mouse-over).
  </Collapser>

  <Collapser id="collector" title="collecteur vs se connecter à New Relic">
    Lorsque vous faites référence à un agent communiquant avec les serveurs de New Relic, décrivez-le comme le [collecteur New Relic](/docs/accounts-partnerships/education/getting-started-new-relic/glossary#collector). Bien qu&apos;en interne le `collector` ne fasse référence qu&apos;à des parties spécifiques de notre architecture, nous l&apos;utilisons plus largement dans notre documentation pour signifier « tout point de terminaison auquel un client doit se connecter pour rapporter des données, pour n&apos;importe quel produit. » Évitez « se connecter à New Relic » et n&apos;utilisez pas « se connecter à l&apos;UI de New Relic ».
  </Collapser>

  <Collapser id="contractions" title="contractions">
    Lorsque cela est judicieux pour des raisons de clarté, de concision, de ton et de voix, utilisez des contractions. Utilisez-les là où elles donnent à l&apos;écriture un son plus proche du langage naturel, et là où elles améliorent la clarté et l&apos;accessibilité sans sacrifier l&apos;expertise et l&apos;autorité.

    Il n’y a pas de règles strictes quant aux contractions qui sont ou ne sont pas acceptables, mais ce qui est simple et courant est préférable à ce qui est compliqué et rare. Par exemple, `it's` pour `it is` convient, mais il est préférable d’éviter les constructions moins courantes comme `mustn't` ou `wouldn't've`.

    Aussi :

    * Lors de l&apos;utilisation d&apos;une contraction négative (`don't`, `can't`, `won't`), essayez de fournir des informations supplémentaires sur ce qu&apos;il faut faire et ce qui peut être fait. (Consultez l&apos;[introduction du guide de style](/docs/new-relic-only/basic-style-guide/writing-guidelines/introduction-style-guide#tone) pour en savoir plus à ce sujet.)
    * Il y a des endroits dans notre documentation — par exemple, dans les notes et les avertissements — où il est préférable d’écrire `do not`, `cannot` ou `will not` en toutes lettres plutôt que d’utiliser des contractions pour souligner l’action ou le blocage à éviter.
  </Collapser>

  <Collapser id="customer-vs-user" title="clients vs utilisateur">
    Lorsque cela est possible, utilisez la deuxième personne `you` pour créer un sentiment de connexion avec le lecteur. Pour les moments où vous avez besoin d&apos;un nom descriptif à la troisième personne, gardez les consignes suivantes à l&apos;esprit :

    * `customer` et `user` sont tous deux appropriés selon le contexte.
    * `customer` prend plus de sens lorsque l’on parle de facturation, ou d’un groupe de personnes ou d’une entité commerciale. Par exemple, un client peut avoir un ou plusieurs utilisateurs individuels qui interagissent avec New Relic via le ou les comptes du client.
    * `user` a plus de sens en tant que terme général pour un utilisateur individuel, ou lorsque l&apos;on parle des utilisateurs en tant qu&apos;objet dans le modèle de compte. Par exemple, lors de la discussion sur les modèles de compte, il est important d&apos;être précis sur ce qui constitue l&apos;identité d&apos;une seule personne dans notre système.
  </Collapser>

  <Collapser id="cyber words" title="Mots cyber">
    Ne séparez pas et ne mettez pas de trait d’union aux mots qui commencent par `cyber`, tels que `cyberattack`, `cybersecurity`, `cyberspace` et `cyberthreat`.
  </Collapser>

  <Collapser id="dashboard" title="dashboard">
    D’un point de vue général de l’industrie, `dashboard` fait généralement référence à un ou plusieurs graphiques ou autres widgets sur un écran. Vous pouvez voir cette définition générale dans l’ [entrée Wikipédia pour dashboard](https://en.wikipedia.org/wiki/Dashboard_\(business\)).

    Chez New Relic, nous utilisons le terme `dashboard` de quelques manières différentes :

    * Dashboards fait référence à une fonctionnalité de New Relic appelée `New Relic dashboards`, comme on peut le voir sur [sa page de fonctionnalité](https://newrelic.com/platform/dashboards). Dans ce contexte, `New Relic dashboards` fait référence à la capacité de créer et d&apos;utiliser des vues personnalisées qui ne sont pas intégrées aux expériences de base de notre plateforme (par exemple, l&apos;interface utilisateur pour APM, le monitoring de navigateurs, OpenTelemetry, et d&apos;autres). Ces dashboards personnalisés se trouvent sur la page de l&apos;interface utilisateur **Dashboards**.
    * Les Dashboards peuvent également faire référence à des dashboards organisés. Ces dashboards sont des vues par défaut que les clients obtiennent lorsqu&apos;ils utilisent nos solutions de plateforme principales (par exemple, les expériences d&apos;interface utilisateur pour l&apos;APM, l&apos;infrastructure et le monitoring de navigateurs).

    Nos dashboards personnalisés incluent les dashboards trouvés dans les [applications New Relic](https://opensource.newrelic.com/nerdpacks/), et dans les quickstarts sur notre [page Instant Observability](https://newrelic.com/instant-observability). Par exemple, si vous regardez [le quickstart .NET](https://newrelic.com/instant-observability/dotnet), vous voyez qu’il est fourni avec un dashboard supplémentaire qui ne fait pas partie de notre expérience organisée.

    Si vous pensez qu&apos;il y a une ambiguïté lors de l&apos;utilisation du terme général « dashboard », nous recommandons l&apos;utilisation suivante :

    * Pour faire référence aux expériences personnalisées trouvées dans les nerdpacks, les démarrages rapides ou les dashboards créés par des clients ou leur équipe, utilisez `custom dashboards`, `customizable dashboards` ou `quickstart dashboards`.
    * Pour faire référence à nos vues organisées, utilisez `curated views`, `curated dashboards`, `New Relic-built dashboards`, `APM dashboards`, `APM views` (pour donner quelques idées).

    En réalité, nous recommandons d’être aussi spécifique que possible pour établir le contexte. Si un texte a établi ce contexte une fois, n’hésitez pas à utiliser le `dashboard` général.
  </Collapser>

  <Collapser id="data-center" title="data center">
    Deux mots (`data center`), et non un seul (`datacenter`), s&apos;écartant des [recommandations de Microsoft d&apos;un seul mot](https://learn.microsoft.com/en-us/style-guide/a-z-word-list-term-collections/d/datacenter). Nous faisons cela par souci de cohérence avec nos contrats.
  </Collapser>

  <Collapser id="data-sheet" title="fiche technique">
    Lorsque vous faites référence à une fiche technique, séparez-la en deux mots pour qu&apos;elle se lise `data sheet` et non `datasheet`.
  </Collapser>

  <Collapser id="DevOps" title="DevOps">
    Abréviation de développeurs de logiciels et opérations.
  </Collapser>

  <Collapser id="document" title="doc, document, documentation, site de documentation">
    Si vous avez besoin de faire référence à la documentation elle-même — ne le faites pas. Généralement, il est préférable de créer un lien direct vers la documentation à laquelle vous faites référence et d’utiliser le titre de la documentation comme texte de lien. Par exemple, `See [Install the .NET agent](URL)` plutôt que `See our [.NET agent install docs](URL)`.

    S’il n’y a pas de bonne alternative, `doc` semble généralement plus naturel que `document` ou `documentation`. Si vous êtes tenté d’utiliser une forme plus longue, essayez de la lire à haute voix pour voir laquelle rend le mieux.

    Si vous devez faire référence au site dans son ensemble, appelez-le le `docs site` plutôt que `Docs site` ou `documentation site`. En interne, vous pouvez également faire référence à l&apos;URL complète `docs.newrelic.com` pour éviter toute ambiguïté avec d&apos;autres sources de documentation comme la documentation de la plateforme interne ou la documentation de l&apos;explorateur d&apos;API. Pour faire référence à [notre référentiel (repository) GitHub de documentation](https://github.com/newrelic/docs-website), utilisez le nom du référentiel (repository) `docs-website` ou le chemin du référentiel (repository) `newrelic/docs-website`.
  </Collapser>

  <Collapser id="downstream-upstream" title="en aval et en amont">
    Ne l’utilisez pas pour décrire comment les entités sont liées les unes aux autres. La façon dont les gens interprètent l’aval et l’amont varie considérablement, concentrez-vous donc sur le type de connexion spécifique comme nous le faisons dans l’élément des entités liées : appelle, crée, héberge, maintient, etc.

    Par exemple:

    * `[Service A] calls [service B]`
    * `Called services`
    * `Calling services`
    * `maintained by [repository name]`
  </Collapser>

  <Collapser id="dropdown" title="liste déroulante">
    Utilisez `dropdown` au lieu de `drop-down` ou `drop down`.

    Bien que ce ne soit pas d&apos;usage courant, vous pouvez utiliser `dropdown` indépendamment comme un nom, sans avoir besoin de dire `dropdown menu` ou `dropdown list`. Par exemple, `select a date from the **Date** dropdown`.
  </Collapser>

  <Collapser id="eg" title="par ex. et c.-à-d.">
    Évitez ces abréviations latines.

    Au lieu de `e.g.`, utilisez `for example` ou `such as`. Remplacer `i.e.` est plus délicat, car parfois les gens l’utilisent pour désigner `that is`, tandis qu’à d’autres moments, il est utilisé à tort pour désigner `for example`. Lisez le contexte pour plus de clarté, mais la meilleure solution est généralement de réécrire afin que la description soit claire sans nécessiter de texte explicatif.
  </Collapser>

  <Collapser id="ellipses" title="Points de suspension">
    Dans les citations, utilisez des points de suspension pour indiquer le texte omis. Traitez les points de suspension comme un caractère unique sans espace entre les trois points. Par exemple, stylisez des points de suspension comme (...) mais pas (. . .) Lorsque des points de suspension apparaissent entre deux phrases complètes, utilisez la ponctuation finale à la fin de la première phrase, puis faites suivre de points de suspension. Par exemple :

    « La sécurité est importante pour nous chez New Relic. … Nous nous imposons des normes élevées, en maintenant plusieurs certifications, notamment ISO 27001 et FedRAMP. »

    Notez qu’un espace précède et suit les points de suspension.
  </Collapser>

  <Collapser
    id="em-dash"
    title={<>tiret cadratin (<InlineCode>
      —
    </InlineCode>)</>
    }
  >
    Les tirets cadratins sont rarement nécessaires dans la documentation technique, malheureusement. Vous pouvez généralement accomplir ce dont vous avez besoin en divisant la pensée en plusieurs phrases ou en utilisant des parenthèses. Dans de rares cas, cependant, un tiret cadratin peut ajouter du drame et du piquant.

    Si vous pensez avoir trouvé un tel cas, assurez-vous de les utiliser correctement. Un tiret cadratin doit toujours utiliser le vrai caractère de tiret cadratin (pas un trait d&apos;union), et aucun espace avant et après. Par exemple :

    ```
    You can sign up for New Relic fast and free—we won't even ask for a credit card number.
    ```

    Vous pouvez insérer un tiret cadratin avec le raccourci `COMMAND+OPTION+-` ou [utiliser l&apos;entité HTML](https://www.w3.org/wiki/Common_HTML_entities_used_for_typography).
  </Collapser>

  <Collapser id="etc" title="etc.">
    Contrairement aux abréviations latines [`e.g.`](#eg) ou [`i.e.`](#ie), vous pouvez utiliser etc. Il doit se terminer par un point (`etc.`). Assurez-vous cependant d’avoir plusieurs exemples significatifs avant de l’utiliser. Par exemple, `cities including Portland, Seattle, Dublin, etc.` mais pas `cities including Portland, etc.`.
  </Collapser>

  <Collapser id="event" title="événement">
    Pour comprendre comment écrire de manière optimale sur les événements, nous vous recommandons de lire :

    * La [section sur les événements dans le document sur les types de données](/docs/data-apis/understand-data/new-relic-data-types/#event-data)

    * [L’entrée du glossaire pour « événement »](/docs/glossary/glossary/#event)

      Quelques considérations linguistiques lorsque vous écrivez sur les événements :

    * Il est important de comprendre une part de l&apos;ambiguïté et de l&apos;histoire autour de la façon dont nous utilisons parfois le mot « événement ». Avant le déploiement de nos trois autres types de données de base que sont `Metric`, `Log` et `Span`, chez New Relic, nous faisions référence à tous les objets stockés dans NRDB en tant qu&apos;« événements ». Pour cette raison, en interne et parfois en externe, nous faisons encore parfois référence à tous les objets NRDB en tant qu&apos;« événements ». (Par exemple, dans [l&apos;interface utilisateur de requête](/docs/query-your-data/nrql-new-relic-query-language/get-started/rate-limits-nrql-queries/#inspected-count-limits), nous utilisons toujours « événements inspectés » et cela fait référence à tous les types de données NRDB). Mais pour les ressources destinées au public, nous devrions essayer d&apos;utiliser « événement » pour faire référence aux données stockées dans NRDB **qui ne sont pas** de types de données `Metric`, `Log` ou `Span`.

    * Il est important de comprendre comment le concept d’« événement » peut chevaucher le concept de « métrique ». Les deux sont des termes généraux larges et, de ce fait, il peut y avoir un certain chevauchement de sens. Parce que les métriques ne sont que des mesures, on peut dire que toutes les données New Relic (événements, spans, logs) sont ou contiennent des métriques. Par exemple, les événements signalés par notre monitoring d’infrastructure contiennent diverses métriques, qui sont simplement des mesures numériques de divers types ([en savoir plus sur les événements d’infrastructure contenant des métriques](/docs/data-apis/understand-data/new-relic-data-types/#metric-event-attributes)).
  </Collapser>

    Pour une explication de la façon dont le mot `metric` est utilisé dans l&apos;industrie et comment il est utilisé chez New Relic, consultez [Types de données](/docs/data-apis/understand-data/new-relic-data-types/#metrics).

    * Notez que le mot « métriques » est un concept vaste et général et que chez New Relic, nous avons [un certain nombre de types de données et de méthodes de reporting des données qui sont appelés « métriques »](/docs/data-apis/understand-data/new-relic-data-types/#metrics-new-relic).

    * Le meilleur format de données de métrique est celui des données de métrique dimensionnelles, alias le type de données `Metric`. Ces données sont signalées via l&apos;API de métrique. Ce sont les données de « métrique » auxquelles nous faisons principalement référence lorsque nous parlons des « métriques » dans nos quatre types de données « MELT » de base : métriques, événements, logs et traces.

    * Notre format de données de métrique d&apos;origine est appelé données d’intervalle de temps métrique. Ceci est toujours signalé par l&apos;APM, le monitoring de navigateurs et le monitoring des applications mobiles. Il s&apos;agissait d&apos;une forme très simple de données de métrique et elle n&apos;était pas stockée dans NRDB, elle ne pouvait donc pas faire l&apos;objet d&apos;une requête en NRQL. Actuellement, les données d’intervalle de temps métrique APM sont mises en miroir dans NRDB et [peuvent donc faire l&apos;objet d&apos;une requête via NRQL](/docs/data-apis/understand-data/metric-data/query-apm-metric-timeslice-data-nrql).

      Quelques recommandations liées au style :

    * **Préférez parler de « métriques » en général et n’entrez pas dans les détails de la structure des données et du processus de reporting**. En général, que vous parliez de métriques dimensionnelles (le type de données `Metric`) ou de données d’intervalle de temps métrique ou de métriques rapportées comme attributs d’événement d’infrastructure, vous pouvez simplement utiliser « métriques » ou « données métriques ». On pense que dans la plupart des cas dans la documentation et l’interface utilisateur, un client n’aura pas souvent besoin de savoir exactement de quel type de données il s’agit. Mais si l’on pense qu’il serait utile de connaître le type de données (par exemple, lorsque l’on parle de la façon d’effectuer une requête sur ces données), vous pouvez donner plus de détails sur le type de données.

    * Lorsque vous souhaitez clarifier le type de données de métrique de manière simple, vous pouvez créer un lien vers une section réductible de type de données de métrique spécifique dans [cette section](/docs/data-apis/understand-data/new-relic-data-types/#metrics-new-relic). Par exemple, vous pourriez faire quelque chose comme ceci : « Cette intégration rapporte des [données de métrique](/docs/data-apis/understand-data/new-relic-data-types/#dimensional-metrics) ».
  </Collapser>

Ne les écrivez pas en un seul mot comme timeseries, à moins de faire référence à la valeur NRQL `TIMESERIES` ou `timeseries`.
  </Collapser>

  <Collapser id="update" title="mise à jour vs mise à niveau">
    Utilisez `update` lorsque les utilisateurs doivent modifier la version de ce qu’ils utilisent. Aucun argent ou paiement n’est nécessaire pour une mise à jour.

    Utilisez `upgrade` chaque fois que de l&apos;argent ou un paiement peut être impliqué, comme la mise à niveau vers la version Pro d&apos;un produit. Le nouveau modèle de tarification rend peu probable que vous ayez besoin d&apos;utiliser cela.
  </Collapser>

  </Collapser>

  <Collapser id="username" title="nom d’utilisateur, pas nom d’usager">
    Un seul mot (`username`), pas deux. [Il s&apos;agit de l&apos;utilisation la plus courante](https://trends.google.com/trends/explore?geo=US&q=%22user%20name%22,%22username%22) et elle est recommandée par les guides de style de Microsoft et Google.
  </Collapser>

  <Collapser id="version" title="références de numéro de version">
    Lorsque vous faites référence à plusieurs numéros de version, utilisez `or higher` ou `or lower`. N’utilisez pas `and higher` (c’est plus ambigu que `or`), ni les mots `greater` ou `later`. N’utilisez pas non plus de ponctuation, comme dans `version 1.2+` ou `<version 1.2`. Évitez les références de style `1.2.X` et utilisez plutôt les numéros de version exacts. Par exemple :

    ```
    Foo requires Ruby agent version 1.2.3 or higher
    ```

    ```
    Bar is compatible with ActiveMerchant version 4.5.6 or lower
    ```

    Vous constaterez que `version` et `versions` fonctionnent tous les deux selon le contexte ; essayez de le lire à voix haute si vous n&apos;êtes pas sûr.

    Autres notes d’utilisation :

    * Dites aux utilisateurs d&apos;utiliser le `latest version` et non une version `up-to-date` ou `current`.
    * Pour abréger le mot `version`, utilisez un `v` minuscule sans espace avant le nombre ; par exemple, `v2` ou `v1.2.3`.
    * Utilisez `update` et non `upgrade` lorsque vous parlez des versions d&apos;agent, comme dans « Pour mettre à jour vers la dernière version… »
    * Envisagez d&apos;utiliser `in earlier agent versions` lorsque vous faites référence à des versions de manière plus vague.
  </Collapser>

  <Collapser id="we" title="nous">
    Dites `we` et `our` lorsque cela s&apos;intègre bien au flux de votre écriture. Évitez de surcharger les paragraphes avec des mentions de `New Relic`, ou reformulez de manière à ce que l&apos;accent soit mis sur l&apos;utilisateur, et non sur New Relic. Par exemple, évitez d&apos;écrire quelque chose comme ceci :

    ```
    New Relic recommends setting a startup timeout.
    ```

    Écrivez plutôt quelque chose comme ceci :

    ```
    Recommendation: To help with troubleshooting, include a startup timeout in your configuration.
    ```

    OU

    ```
    We recommend setting a startup timeout.
    ```
  </Collapser>

  <Collapser id="web page" title="page web">
    Deux mots, pas un.
  </Collapser>

  <Collapser id="x" title="x">
    Utilisez un x minuscule pour signifier « fois ». Par exemple :

    * L’adoption du cloud peut augmenter le nombre d’hôtes de 2 à 50 fois.
    * Jusqu’à 10 fois la durée maximale par requête et 3 fois la limite maximale de requêtes.
  </Collapser>

  <Collapser id="you" title="vous">
    Nous utilisons `you` et `your` généreusement dans notre documentation. S’adresser directement au lecteur permet d’obtenir des phrases plus simples et plus claires. Cela a également tendance à exposer les utilisations paresseuses de la construction passive, et cela aide les utilisateurs à comprendre les procédures.
  </Collapser>
