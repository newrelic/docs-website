## 0. Configurer votre environnement local [#set-local]

Vous n&apos;avez besoin de configurer votre environnement local qu&apos;une seule fois. Si vous l&apos;avez déjà fait, vous pouvez ignorer cette étape.

Rendez-vous ici pour obtenir des instructions détaillées sur la façon de [configurer votre environnement de build local](/docs/style-guide/writing-docs/writer-workflow/set-up-local).

## 1. Créez une branche et modifiez les documents [#edit-doc]

Dans GitHub Desktop, vous verrez trois onglets intitulés **Référentiel actuel**, **Branche actuelle** et **Fetch origin**. La branche par défaut est **Develop**, il est donc temps de créer une branche.

1. Cliquez sur **Current Branch** et sélectionnez **New Branch**.
2. Trouvez un document que vous souhaitez modifier.
   * Utilisez le Finder ou l’Explorateur de fichiers avec le chemin d’accès au fichier. Par exemple, si vous vouliez modifier un document de l’agent Python, vous navigueriez vers : `~/Documents/github/docs-website/src/content/docs/agents/python-agent/hosting-services/python-agent-stackato.mdx`
3. [Modifiez le document](https://docs.newrelic.com/docs/style-guide/writing-docs/processes-procedures/create-edit-content) dans l&apos;éditeur de texte de votre choix. Vous devez rédiger les documents avec le [langage markdown](https://www.markdownguide.org/basic-syntax).
4. Enregistrez le fichier avec vos modifications.

Consultez le reste de notre [guide de style](https://docs.newrelic.com/docs/style-guide/writing-strategies/introduction-style-guide/) pour toute question concernant les directives de rédaction.

## 2. Commitez vos modifications [#commit-changes]

Même si vous avez enregistré vos modifications, vous devez toujours effectuer un commit. Vous pouvez considérer un commit comme un point de contrôle dans votre workflow. Le processus de commit commence par la simulation et se termine lorsque vous poussez vos modifications vers GitHub.

1. Retournez dans GitHub Desktop et consultez la colonne de gauche. Dans Github Desktop, la colonne de gauche affiche :

   * Un historique de toutes les nouvelles modifications apportées à tous les documents
   * Un bouton bleu indiquant **Commit to \[your-branch-name]**

2. Nommez votre commit et ajoutez une description.

3. Cliquez sur **Commit to \[yourbranchname]**.
   * Le nom et la description du commit pourraient ressembler à `feat(PythonAgent): Renamed the section heading`

## 3. Exécutez le site localement [#run-site]

Construisez le site localement en utilisant le terminal. Bien que cette étape soit facultative, il est **fortement** recommandé de construire le site localement et de prévisualiser les modifications avant d’ouvrir une demande de tirage.

Vous n’avez besoin de reconstruire le site local que lorsqu’il plante, pas après chaque sauvegarde ou validation.

1. Dans votre terminal, accédez à votre référentiel (repository) cloné, **docs-website**. Par exemple :
   * `cd ~/Documents/github/docs-website`
2. Exécutez yarn avec les commandes suivantes : `yarn && yarn start`
3. La génération du site prendra quelques minutes. Préparez-vous un thé ou un café.
4. Une fois construit, prévisualisez le site dans votre navigateur en accédant à [http://localhost:8000/](http://localhost:8000/)

## 4. Publier vos commits [#publish-commits]

Une fois que vous êtes satisfait de vos modifications, poussez vos commits vers GitHub. Cela les rend disponibles pour tous les autres utilisateurs dans le référentiel GitHub.

1. Sur GitHub Desktop, cliquez sur le bouton bleu **Publish Branch** s&apos;il est disponible.
2. Si vous ne voyez pas la branche de publication, cliquez sur le bouton bleu **Push Origin**.

## 5. Ouvrez votre demande de tirage [#open-pr]

Bien que vos commits soient visibles par tout le monde, vos modifications ne seront pas fusionnées dans la branche `develop `avant qu’un autre rédacteur ne les ait révisées.

Pour ce faire, vous ouvrez une demande de tirage (PR) :

1. Sur GitHub Desktop, cliquez sur le bouton bleu **Create Pull Request**.

2. Cela ouvrira GitHub dans votre navigateur et un prompt vous invitera à remplir votre demande de tirage.

   * Assurez-vous de fusionner votre branche dans la branche `develop`.
   * Faites défiler vers le bas pour passer en revue tous vos commits.

3. Tout comme la description de votre commit, la description de votre demande de tirage doit être détaillée et donner le contexte complet de vos modifications.

   * N&apos;hésitez pas à ajouter tout contexte supplémentaire ici (lien vers le ticket GitHub ou ID du ticket Jira, experts en la matière, etc.)
   * Demandez une révision à un autre rédacteur technique en ouvrant la PR, en accédant à la section **Conversation** et en saisissant le nom du réviseur dans la section **Réviseur**.

4. Ajoutez l’étiquette `from_tw` et toute autre [étiquette pertinente](/docs/style-guide/writer-workflow/github-intro) à votre PR.
   * Si vous n’ajoutez pas `from_tw`, la PR ne sera pas automatiquement assignée à un autre rédacteur pour révision.

5. Une fois que vous êtes satisfait de votre PR, cliquez sur le bouton vert **Create pull request**.

6. Vous pouvez soit publier les modifications directement en approuvant la demande de tirage vous-même, soit demander à un autre rédacteur technique de la réviser.

7. Au bas de la page de la demande de tirage, vous verrez une section **Checks**. Ces vérifications garantissent que votre PR ne casse pas le processus de build du site. Assurez-vous que toutes les vérifications marquées `required` réussissent avant de fusionner.

8. Une fois que la demande de tirage a passé les vérifications et qu&apos;elle a été approuvée par un autre rédacteur technique (ou que vous êtes certain que les modifications sont prêtes à être publiées), cliquez sur le bouton vert **Merge pull request**. Cela fusionnera votre branche et vos validations dans le référentiel et commencera le processus de compilation.

<Callout variant="important">
  Si vous n’ajoutez pas l’étiquette `from_tw` lors de la première création d’une demande de tirage, aucun réviseur ne sera automatiquement attribué. Si vous oubliez d’ajouter l’étiquette avant d’ouvrir la demande de tirage :

  1. Ajoutez le label `from_tw`.
  2. Transformez la PR en une PR brouillon.
  3. Sélectionnez le `PR is ready for review button` au bas de la page pour rouvrir la demande de tirage. La demande de tirage devrait maintenant avoir un réviseur.
</Callout>

## Prévisualiser un document [#preview-doc]

Il existe deux manières principales de prévisualiser les branches que vous avez déjà publiées et sur lesquelles vous avez exécuté des commits :

* **Local**: plus rapide, mais nécessite une configuration assez importante et une familiarité avec un terminal.
* **Netlify Cloud**: aperçu complet du site en direct sans surcharge, et un moyen très pratique de partager un aperçu de votre brouillon avec un expert métier. Netlify Cloud commentera votre PR avec un lien vers une version d’aperçu du site une fois que le build sera prêt. La construction du site prend généralement environ 15 minutes, mais peut parfois prendre plus de temps s’il y a beaucoup de modifications.

## Révisez et publiez un document [#revise-doc]

Si vous êtes informé qu’un réviseur a soumis une révision à votre fichier, accédez à votre PR et passez en revue les modifications. Vous pourriez les voir dans la vue DIFF, s’ils font partie d’une révision avec des commentaires ; sinon, ils pourraient apparaître comme des modifications de texte dans le fichier.

1. Répondez à tous les commentaires dans le fichier. Soit vous répondez par une discussion de suivi, soit vous cliquez sur **Resolve conversation**.
2. Lorsque vous avez résolu tous les commentaires et que toutes les vérifications automatiques ont réussi, vous pouvez fusionner la demande de tirage. La fusion de la demande de tirage déclenche le processus de compilation automatisé et vos modifications seront publiées sous peu.

<Callout variant="tip">
  Vous ne pourrez fusionner que lorsque le bouton **Fusionner la demande de tirage** sera vert. S’il n’est pas vert, vérifiez s’il y a des commentaires que vous avez manqués, ou d’autres messages qui indiquent pourquoi GitHub vous empêche de fusionner.
</Callout>

## Annuler la fusion [#revert]

N&apos;oubliez pas que vous pouvez presque toujours annuler les choses. Si vous fusionnez une demande de tirage, puis découvrez que vous n&apos;auriez pas dû, vous pouvez annuler la fusion avec le bouton **Revert**.

1. Dans l&apos;onglet demande de tirage dans GitHub, cliquez sur **Closed** dans la barre de décompte pour voir tous les tickets et PR qui ont déjà été fusionnés.
2. Localisez la demande de tirage que vous avez fusionnée, et localisez le bouton Revert.
3. Cliquez sur Rétablir. Cela crée une nouvelle PR, qui doit être fusionnée. Si vous souhaitez la rouvrir, vous devez suivre le lien vers la PR d&apos;origine et soit la rétablir, soit la rouvrir.

## Rédacteurs uniquement : travaillez sur une branche, pas sur un fork [#branch-fork]

Certaines équipes travaillent sur des branches, d&apos;autres travaillent sur des forks ; **l&apos;équipe de documentation travaille sur des branches**. Tant qu&apos;une branche a été poussée en amont, cela nous permet de travailler en collaboration et de nous assurer qu&apos;aucun travail n&apos;est jamais perdu lorsque quelqu&apos;un part en vacances.

Pour créer une branche sur le référentiel (repository) docs-website :

1. Ouvrir GitHub Desktop
2. Cliquez sur **Current branch : xxx**
3. Cliquez sur **New Branch**
4. Un prompt vous invitera à nommer votre nouvelle branche. Les noms descriptifs sont les meilleurs. C’est un excellent moyen d’indiquer rapidement aux gens en quoi consiste votre travail. Par exemple, si vous travaillez sur les pages What’s New, vous pourriez nommer la branche **Whats-new-updates**.

Lorsque vous créez une nouvelle branche, n&apos;oubliez pas d&apos;ajouter l&apos;ID du ticket Jira (DOC-1234) au nom de la branche et au titre de la demande de tirage.

## Une remarque sur les autorisations GitHub [#permissions]

Les rédacteurs de l’équipe de documentation travaillent dans des branches, mais les contributeurs externes à l’équipe de documentation utilisent des forks. Cela signifie également que les contributeurs n’appartenant pas à l’équipe de documentation ne peuvent pas modifier directement le contenu d’une branche, ce qui peut rendre la collaboration délicate.

Les autorisations GitHub sont utilisées pour déterminer qui peut travailler sur une branche et qui peut travailler sur un fork. Sur GitHub, l’accès est déterminé par les rôles des équipes et des membres. Bien que n’importe qui puisse contribuer à notre référentiel public, un accès supplémentaire est accordé via les rôles `Write` et `Admin`. (Il existe d’autres rôles définis qui ne sont pas souvent utilisés.)

Chaque membre de l&apos;équipe Docs se voit attribuer le rôle `Admin`, qui accorde un accès intégral au référentiel. Les autres contributeurs de New Relic se voient attribuer le rôle `Write`, qui permet d&apos;affecter des utilisateurs et d&apos;ouvrir et de fermer des demandes de tirage.

Pour vérifier les paramètres d&apos;accès actuels, accédez au référentiel (repository) `docs-website`, puis allez dans **Settings &gt; Collaborators and teams** ou **Team and member roles**.
