Ce document explique les styles requis et les formulations recommandées pour la documentation relative aux rôles d’utilisateur et aux autorisations.

## Note sur les modèles d’utilisateur

Ce guide de style s’applique principalement à la rédaction concernant les utilisateurs sur notre nouveau modèle d’utilisateur, et non sur notre modèle d’utilisateur d’origine. Bien que les deux modèles d’utilisateur partagent certains termes (tels que **Admin**), il s’agit d’un modèle d’utilisateur entièrement différent avec une structure, des formulations recommandées et un style entièrement différents. Pour comprendre les différences entre les modèles d’utilisateur, consultez [Présentation des modèles d’utilisateur](/docs/accounts/original-accounts-billing/original-product-based-pricing/overview-user-models).

Le modèle d’utilisateur d’origine sera de plus en plus déprécié, nous ne devrions donc pas avoir besoin de beaucoup penser à ce modèle d’utilisateur ou de mettre à jour cette documentation très souvent.

## Directives pour documenter les autorisations/rôles des utilisateurs [#user-language-philosophy]

Il y a deux facteurs principaux affectant la capacité d&apos;un utilisateur New Relic à accéder à une fonctionnalité New Relic :

* Type d&apos;utilisateur : nous limitons presque entièrement les informations sur le type d&apos;utilisateur au [document sur le type d&apos;utilisateur](/docs/accounts/accounts-billing/new-relic-one-user-management/user-type).

* Rôles et capacités : nous limitons presque entièrement les informations à ce sujet aux documents dédiés à la gestion des utilisateurs :

  * [Documentation originale du modèle de l&apos;utilisateur](/docs/accounts/original-accounts-billing/original-users-roles/users-roles-original-user-model)
  * [Documents plus récents sur le modèle utilisateur](/docs/accounts/accounts-billing/new-relic-one-user-management/introduction-managing-users)

En d’autres termes, **nous ne plaçons pas d’informations sur le type d’utilisateur et les rôles/capacités dans les documents liés aux fonctionnalités du produit**, à l’exception des cas suivants :

* Pour le type d’utilisateur : pour la plupart des fonctionnalités du produit, il est évident pour un utilisateur que quelque chose est interdit en raison du type d’utilisateur (par exemple, il voit un message dans l’interface utilisateur concernant le type d’utilisateur). S’il n’est pas évident que quelque chose est interdit en raison du type d’utilisateur, vous pouvez le documenter dans la section des exigences du document de la fonctionnalité. Par exemple, il ne sera pas immédiatement évident pour un utilisateur de NerdGraph de comprendre pourquoi il ne peut pas effectuer certaines requests, c’est donc une situation où nous documenterions le type d’utilisateur dans le document principal de NerdGraph.
* Pour les rôles et les autorisations : s&apos;il y a une raison spécifique d&apos;inclure le type d&apos;utilisateur ou les rôles/autorisations dans la section des exigences d&apos;un document de fonctionnalité, vous pouvez l&apos;inclure. Par exemple : si une [autorisation](/docs/accounts/accounts-billing/new-relic-one-user-management/user-permissions) qui contrôle l&apos;accès à une fonctionnalité n&apos;est pas évidente d&apos;après le nom des autorisations (comme les [autorisations de Gestion des niveaux de service](/docs/service-level-management/faqs-slm#permissions)), nous devons la documenter.
* Pour les permissions de gestion de l&apos;organisation et des utilisateurs, nous documentons les rôles requis. Cela s&apos;explique par le fait qu&apos;il y en a peu, et aussi parce que les permissions qui les régissent ne sont pas exposées dans l&apos;interface utilisateur des rôles et permissions et sont donc moins évidentes pour les clients.

## Considérations pour documenter à la fois le modèle utilisateur original et le nouveau [#user-model-requirements]

Si vous devez inclure des exigences concernant les rôles ou les autorisations du nouveau modèle d’utilisateur, vous devrez probablement inclure également des détails sur le modèle d’utilisateur d’origine (en supposant que cette fonctionnalité soit disponible pour ce public). Voici un exemple de la façon de procéder :

```md
Permissions requirements differ depending on your user model:

* For users on the [original user model](/docs/accounts/original-accounts-billing/original-product-based-pricing/overview-user-models): the [**Data retention manager** role](/docs/accounts/original-accounts-billing/original-users-roles/users-roles-original-user-model/#roles).
* For users on [our newer user model](/docs/accounts/original-accounts-billing/original-product-based-pricing/overview-user-models): the [**Billing** administration setting](/docs/accounts/accounts-billing/new-relic-one-user-management/user-management-concepts#admin-settings).
```
