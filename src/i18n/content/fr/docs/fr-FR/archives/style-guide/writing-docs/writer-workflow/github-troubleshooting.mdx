Rencontrez-vous des problèmes en [travaillant sur un document sur GitHub](/docs/style-guide/writer-workflow/tech-writer-workflow/)? Consultez les problèmes courants suivants.

## La compilation locale renvoie une erreur 404 [#build-fails]

### Problème

Lorsque vous essayez de compiler votre localhost:8000, une ou toutes les pages web renvoient une erreur 404.

### Solutions

Essayez certaines de ces solutions pour comprendre ce qui s’est mal passé dans votre build local.

<CollapserGroup>
  <Collapser className="freq-link" id="troubleshoot-file" title="Dépanner le fichier problématique">
    Si vous savez quel fichier provoque une erreur, exécutez cette commande pour identifier l&apos;erreur :

    ```bash
    yarn verify-mdx path/to/file.mdx
    ```

    Cette commande renvoie plus d’informations sur l’erreur que la sortie normale de Gatsby, telles que le caractère spécifique et le numéro de ligne à l’origine de l’erreur.

    <CollapserGroup>
      <Collapser className="freq-link" id="example" title="Exemple">
        Imaginons que j’ai apporté des modifications à plusieurs documents dans ma branche. Lorsque j’essaie d’exécuter le site localement ou d’accéder au build Netlify, j’obtiens l’erreur suivante :

        ```
        Unexpected character = (U+003D) before name, expected a character that can start a name, such as a letter, $, or _/usr/src/app/www/src/content/docs/new-relic-solutions/observability-maturity/uptime-performance-reliability/aqm-implementation-guide.mdx: Unexpected character = (U+003D) before name, expected a character that can start a name, such as a letter, $, or _
        ```

        L’erreur m’indique bien que la documentation contenant une erreur se trouve dans `/docs/new-relic-solutions/observability-maturity/uptime-performance-reliability/aqm-implementation-guide.mdx`. À part cela, tout ce que je sais, c’est qu’il y a un caractère `=` qui pose problème quelque part. Super, mais il s’agit d’une documentation NRQL, il y a des dizaines de caractères `=`.

        Donc, j&apos;exécute `yarn verify-mdx src/content/docs/new-relic-solutions/observability-maturity/uptime-performance-reliability/aqm-implementation-guide.mdx`. Cela renvoie ce qui suit :

        ```json
        reading src/content/docs/new-relic-solutions/observability-maturity/uptime-performance-reliability/aqm-implementation-guide.mdx
        {
          "message": "Unexpected character `=` (U+003D) before name, expected a character that can start a name, such as a letter, `$`, or `_`",
          "name": "284:227",
          "reason": "Unexpected character `=` (U+003D) before name, expected a character that can start a name, such as a letter, `$`, or `_`",
          "line": 284,
          "column": 227,
          "location": {
            "start": {
              "line": 284,
              "column": 227,
              "offset": 19129,
              "index": 1
            },
            "end": {
              "line": null,
              "column": null
            }
          },
          "source": "remark-mdx",
          "ruleId": "unexpected-character",
          "fatal": true
        }
        ```

        Dans ce cas, les informations pertinentes sont :

        ```json
        "line": 284,
        "column": 227,
        ```

        et

        ```json
        "source": "remark-mdx",
        "ruleId": "unexpected-character",
        "fatal": true
        ```

        Cela m&apos;indique qu&apos;il y a un caractère inattendu à la ligne 284, colonne 227. Ensuite, je peux aller à cette section du document, et poursuivre le dépannage, en sachant exactement d’où vient l’erreur. Dans ce cas, j’ai probablement juste besoin d’entourer un exemple NRQL de guillemets.
      </Collapser>
    </CollapserGroup>

  <Collapser className="freq-link" id="" title="Vérifiez les erreurs de syntaxe courantes">
    Vérifiez les fichiers modifiés pour certaines de ces erreurs de syntaxe markdown courantes :

    * Indentation incohérente des fichiers de navigation

    * Syntaxe de front matter incorrecte
      * S’il y a des apostrophes et des deux-points dans les champs du frontmatter, entourez-les de guillemets pour éviter les problèmes.

    * Crochets fermants ou tags manquants

    * Liens d&apos;images mal formatés

      * Assurez-vous qu&apos;il y a une nouvelle ligne entre chaque instruction d&apos;importation d&apos;image.
      * Soyez prudent lorsque vous renommez des images et leurs chemins de fichiers. Une incohérence peut entraîner l&apos;échec de l&apos;ensemble du build local.
      * Soyez particulièrement prudent lorsque vous traitez des fichiers d’image qui sont importés.

    * Noms de fichiers d&apos;image incorrects

      * Les noms de fichiers d&apos;image sont sensibles à la casse. L&apos;utilisation d&apos;une mauvaise majuscule entraîne l&apos;absence d&apos;une image dans la documentation.
      * Les images avec des valeurs encodées (comme %) dans le nom de fichier peuvent être particulièrement délicates, essayez donc de les éviter.
  </Collapser>

  <Collapser className="freq-link" id="restart-yarn" title="Arrêtez et redémarrez yarn">
    Pour arrêter et redémarrer yarn :

    1. Dans le terminal, assurez-vous que vous êtes dans le répertoire `/docs-website`.
    2. Appuyez sur CONTROL+C pour interrompre le processus yarn (si un terminal est actif).
    3. Exécutez cette commande pour arrêter tous les services s&apos;exécutant sur localhost:8000 :
       ```bash
       kill -9 $(lsof -i TCP:8000 | grep LISTEN | awk '{print $2}')
       ```
    4. Exécutez cette commande pour redémarrer yarn :
       ```bash
       yarn clean && yarn && yarn start 
       ```
  </Collapser>

  <Collapser className="freq-link" id="check-branch" title="Identifier la branche problématique">
    Pour identifier la branche qui cause des problèmes :

    1. Dans le terminal, assurez-vous que vous êtes dans le répertoire `docs-website`.
    2. Appuyez sur CONTROL + C pour interrompre le processus yarn, si nécessaire.
    3. Dans GitHub Desktop, validez toutes les modifications nécessaires sur votre branche, puis passez à la branche develop.
    4. De retour dans le terminal, exécutez `yarn && yarn start`.

    Si le site se compile désormais correctement à partir de la branche develop, le problème vient des modifications apportées à votre branche. Arrêtez de nouveau Yarn, retournez sur votre branche et résolvez le problème.
  </Collapser>

  <Collapser className="freq-link" id="clean-cache" title="Nettoyez votre cache local">
    Exécutez `yarn clean` pour supprimer votre cache local. Cela rendra votre prochain build plus lent, alors assurez-vous d&apos;avoir le temps !

    1. Dans le terminal, assurez-vous d’être dans le répertoire docs-website.
    2. Appuyez sur CONTROL+C pour arrêter yarn, si nécessaire.
    3. Commencez un nouveau build en exécutant `yarn clean && yarn && yarn start`.
  </Collapser>

  <Collapser className="freq-link" id="remove-cache" title="Supprimez les fichiers de cache corrompus">
    Il peut y avoir des moments où votre répertoire .cache a été corrompu. Ce répertoire est ignoré par Git, ce qui signifie qu&apos;il voyage avec vous de branche en branche. Cela pourrait être le problème si vos builds locaux échouent, quelle que soit la branche sur laquelle vous vous trouvez.

    Pour résoudre ce problème depuis votre répertoire `/docs-website`, exécutez `rm -rf .cache`.
  </Collapser>

  <Collapser className="freq-link" id="start-build" title="Démarrer un build à partir de zéro">
    Démarrer un build de zéro supprimera tous vos modules node, le dossier .cache caché, et le cache local. Cela prend beaucoup de temps à s’exécuter, environ de 10 à 20 minutes.

    1. Dans le terminal, assurez-vous d’être dans le répertoire docs-website.

    2. Appuyez sur CONTROL+C pour arrêter yarn, si nécessaire.

    3. Exécutez `yarn reboot` (ou utilisez la commande Keyboard Maestro `kknuke`\* ).

       \* Si vous utilisez la commande Keyboard Maestro `kknuke`, lorsque tout est terminé, démarrez le site en exécutant `yarn start`.
  </Collapser>

  <Collapser className="freq-link" id="run-incognito" title="Exécutez votre build local en mode privé">
    Parfois, le site local se compile, mais pas les pages du site. Pour résoudre ce problème, essayez d&apos;exécuter la compilation locale dans une session privée ou incognito. Vous pouvez également essayer de vider le cache de votre navigateur.
  </Collapser>
</CollapserGroup>

## Échec des vérifications de build requises [#check-fail]

### Problème

Lorsque vous créez une PR, l&apos;une des vérifications `required` échoue.

<Callout variant="tip" title="Note">
  Si une vérification facultative échoue, vous pouvez fusionner la PR, car les vérifications facultatives ne bloquent pas les sorties. Cependant, si vous souhaitez examiner la vérification plus en détail, vous pouvez envoyer un message sur le canal d’aide afin que le héros puisse se pencher sur l’échec.
</Callout>

### Solution

Si une vérification échoue, essayez d’abord de fermer et de rouvrir votre PR.

Ensuite, relancez les vérifications :

1. Accédez à la PR.
2. Cliquez sur **Details &gt; Re-run jobs**.

Si cela ne fonctionne pas, vous devrez réinitialiser les vérifications, ce qui forcera une reconstruction du cache :

1. Dans votre référentiel (repository) local, trouvez le fichier `gatsby-config.js` (ou utilisez CMD-P pour y accéder rapidement dans VSCode).

2. Échangez la première et la deuxième ligne de code (l’ordre de ces lignes n’a pas d’importance, sauf pour que la vérification Gatsby Build reconstruise le cache) :

   ```js
   const fs = require('fs');
   const parse = require('rehype-parse');
   ```

3. Enregistrez le fichier et validez la modification dans votre PR.

4. Relancez les vérifications de build.

5. Attendez TRÈS longtemps.

## Conflits de fusion de PR [#merge-conflict]

### Problème

Lorsque vous essayez de fusionner une PR à partir de votre branche locale, vous obtenez un conflit de fusion.

### Solution

Si vous rencontrez un conflit de fusion, cliquez sur **Resolve conflict** dans Github Desktop ou dans le navigateur et examinez les conflits ligne par ligne. Assurez-vous de demander à votre approbateur de revoir votre PR après avoir résolu le conflit de fusion.

#### Éviter les conflits de fusion

Voici quelques recommandations pour éviter les conflits de fusion :

* Avant de fusionner vers develop ou main, cliquez sur **Fetch origin** pour vous assurer de récupérer la version la plus à jour de develop ou main.
* Si vous travaillez sur des modifications de taxonomie, résolvez votre conflit de fusion dès que possible. Si votre branche stagne pendant un certain temps, elle peut rapidement devenir obsolète par rapport à develop et cela peut causer des problèmes inattendus.
* Si vous obtenez un conflit de fusion à partir des articles sur les nouveautés, c’est parce que le fichier `whats-new-ids.json` (qui est automatiquement mis à jour lors de la compilation du site) peut devenir obsolète assez rapidement. <Callout variant="caution">Ne fusionnez jamais une PR qui modifie `whats-new-ids.json`. Si vous voyez des modifications apportées au fichier `whats-new-ids.json` apparaître dans GitHub Desktop, assurez-vous de les annuler plutôt que de les pousser vers votre branche. Cela réduira la probabilité que d’autres personnes aient à gérer des conflits de fusion liés à ce fichier.</Callout>

## Le port 8000 est indisponible [#local-site]

### Problème

Lorsque vous essayez d&apos;exécuter `yarn start`, le terminal répond :

```bash
[output] Something is already
[output] running at port 8000. Would you like to run the app at another port instead?
```

### Solution

Pour arrêter tous les services en cours d’exécution sur localhost:8000, exécutez cette commande dans votre terminal :

```bash
kill -9 $(lsof -i TCP:8000 | grep LISTEN | awk '{print $2}')
```

## Le lien de redirection renvoie une erreur 404 [#redirect-404]

### Problème

Lorsque vous cliquez sur un lien de redirection dans votre build local, vous obtenez une erreur 404.

### Solution

Les redirections prennent beaucoup de temps à se charger dans un build local. Lorsque vous cliquez sur une redirection, attendez qu’elle renvoie une erreur 404, puis attendez environ 1 à 2 minutes. Elle devrait vous rediriger après un certain temps. Si ce n’est pas le cas, vérifiez la syntaxe markdown pour vous assurer que vous avez correctement configuré la redirection.

Vous pouvez également tester les redirections dans le build Gatsby.

## L’authentification SSH échoue [#authentication-fail]

### Problème

Lorsque vous essayez de pousser des commits vers votre branche distante, vous obtenez une erreur d’authentification SSH.

### Solution

Parfois, se connecter/déconnecter de Github Desktop peut résoudre un problème d’authentification :

1. Dans la barre de menus supérieure, allez dans **Préférences**.
2. Déconnectez-vous et reconnectez-vous.

Si cela ne fonctionne pas, essayez de pousser les commits vers votre branche distante. Si cela échoue toujours, essayez de pousser manuellement votre PR en utilisant le terminal. Par exemple, pour pousser la PR `second-kafka-pr-for-issue-11231`, exécutez cette commande :

```bash
git push --set-upstream origin second-kafka-pr-for-issue-1123
```

Si vous rencontrez un problème SSH, le terminal renverra un message d’erreur d’authentification. Si la réponse à cette commande affiche un prompt vous demandant une phrase secrète, votre SSH était en quelque sorte confus. En saisissant votre phrase secrète, vous devriez pouvoir reprendre vos activités. Si vous ne vous souvenez pas de votre phrase secrète, [consultez cet article](https://docs.github.com/en/github/authenticating-to-github/troubleshooting-ssh/recovering-your-ssh-key-passphrase).
