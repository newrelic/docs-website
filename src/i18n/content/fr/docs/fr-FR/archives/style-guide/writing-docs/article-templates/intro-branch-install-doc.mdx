Notre composant d&apos;installation ramifiée pour le site de documentation permet à nos utilisateurs de sélectionner une ou plusieurs options, ce qui affiche ensuite le contenu en fonction de ces choix.

## Aperçu du processus de création [#overview]

Avant de commencer à travailler avec le composant d’installation de branche, voici quelques éléments à prendre en compte :

* Assurez-vous que vous souhaitez vraiment utiliser l’installation par branche. Vérifiez si votre problème peut être résolu avec une autre solution (par exemple, le [composant d’onglet](/docs/style-guide/structure/intro-to-components)).
* Parcourez [les documents d’installation ramifiés que nous avons créés](#uses) et voyez ce qu’il est possible de faire. Sélectionnez-en un que vous souhaitez cloner pour l’utiliser comme modèle.
* Finalisez le flux logique de ce que seront vos options et du contenu qui sera affiché. Idéalement, vous souhaitez que vos plans de contenu soient presque définitifs avant de créer une branche. Pour cette raison, vous pourriez diviser le travail en deux ou plusieurs Jiras.

Vous pouvez construire le composant d’installation ramifié de nombreuses façons, et cela peut vous demander beaucoup d’efforts pour le faire fonctionner, surtout si votre structure est complexe. Mais, cela dit, voici un aperçu de haut niveau de ce à quoi ressemblera souvent un processus de création :

1. Passez en revue la documentation d&apos;installation branchée, en particulier nos [fichiers YAML d&apos;exemple](#yaml-examples). Familiarisez-vous avec la structure et la logique de ce composant.
2. Lorsque vous êtes prêt à commencer, copiez le fichier YAML et les dossiers associés d’un composant d’installation que vous souhaitez émuler, et utilisez-les comme base pour votre projet.
3. Modifiez le nom du dossier de niveau supérieur pour qu’il corresponde à votre projet, et modifiez le `agentName` dans le fichier YAML pour qu’il corresponde. Le `agentName` est ce qui indique au fichier YAML de quel dossier extraire son contenu. (Voir [nos exemples de fichiers YAML](#yaml-examples).)
4. Pour vous assurer que tout fonctionne, effectuez un build local.
5. Commencez à ajouter vos fichiers .mdx et à modifier le fichier yaml. Selon la mesure dans laquelle vos plans correspondent à la logique existante, il peut être plus facile de supprimer la majeure partie du contenu du fichier YAML, et d&apos;en ajouter un peu à la fois.
6. Pendant que vous travaillez, compilez fréquemment pour tester si les choses fonctionnent. Faire de petites portions de travail puis vérifier si la compilation réussit vous aidera à éviter de perdre du temps en dépannage. Utilisez le [script de vérification YAML](/docs/style-guide/writing-docs/article-templates/branch-install-doc-reference#verify-yaml) pour rechercher des erreurs.

Si vous êtes bloqué, demandez de l’aide à quelqu’un qui en a construit un.

## Points de décision importants [#decision-points]

Il y a quelques approches différentes que vous pouvez adopter avec l’installation par branche. Voici quelques points de décision majeurs :

<CollapserGroup>
  <Collapser id="default-content-decision" title="Dois-je afficher le contenu avant qu’une option ne soit sélectionnée ?">
    Cette décision concerne : que voient les clients lorsqu’ils arrivent pour la première fois sur la documentation ? Est-il judicieux de leur montrer des instructions avant même qu’ils n’aient sélectionné une option ? S’il existe un chemin unique que la majorité des clients emprunteront, il peut être judicieux de leur montrer un contenu qui s’ajustera et changera ensuite en fonction de leurs sélections d’options. Détails à ce sujet :

    * L&apos;approche de « contenu par défaut » repose sur l&apos;utilisation des composants `override` et `skip`. Il affiche un fichier et indique ensuite : ignorer ou remplacer ce fichier lorsque x options sont choisies. (Document d&apos;installation qui utilise ceci : [l&apos;installation Java](/install/java).)
    * Si vous ne souhaitez afficher aucun contenu avant que les options ne soient sélectionnées, vous utiliseriez l’approche `isCondition=true`. Ce composant dit simplement : « affichez ce fichier si ces options sont sélectionnées. » (Document d’installation qui utilise ceci : [l’installation .NET](/install/dotnet).)
  </Collapser>

  <Collapser id="display-all-options-decision" title="Dois-je afficher toutes les options ? Ou les imbriquer ?">
    Cette décision concerne le fait de savoir si vous souhaitez afficher initialement tous les choix d’options, ou si vous préférez les imbriquer (par exemple, le choix d’une option entraîne une autre boîte de sélection d’option).

    Si votre logique de sélection d’options est assez simple, il peut être judicieux d’exposer simplement toutes les options aux clients en même temps. Cependant, si votre logique de sélection d’options est plutôt complexe (par exemple, trois sélections ou plus, et certaines sélections affectant les sélections ultérieures), il peut être judicieux de les imbriquer.

    Pour un exemple d&apos;un ensemble de cases de sélection d&apos;options entièrement exposé, consultez le \[document sur les prérequis de sécurité réseau]. Pour un exemple d&apos;un ensemble imbriqué de cases de sélection, consultez \[l&apos;installation .NET].
  </Collapser>

  <Collapser id="guided-install-decision" title="Ai-je besoin de l'installation guidée ?">
    Ce point de décision concerne la nécessité d&apos;afficher des informations sur notre chemin d&apos;installation guidée. Pour certains agents, nous voulons afficher du contenu sur le chemin d&apos;installation guidée (par exemple, vous pouvez voir le contenu de l&apos;installation guidée dans l&apos;[installation de l&apos;agent Java](/install/java) si vous sélectionnez « app server » et « Jetty »).

    Nous avons quelques options pour ajouter le contenu de l’installation guidée :

    * Nous avons un composant `recommendedGuided: true` que vous pouvez placer sur des options spécifiques où vous souhaitez que le contenu de l&apos;installation guidée s&apos;affiche. Ce que cela fait essentiellement, c&apos;est afficher le contenu du fichier .mdx qui contient cette boîte de sélection d&apos;options. Vous pouvez en voir un exemple dans l&apos;installation Java, où le contenu de l&apos;installation guidée se trouve dans le fichier `appInfo-2`. Cette implémentation n&apos;est pas vraiment spécifique au contenu de l&apos;installation guidée : vous pourriez utiliser cette logique pour afficher n&apos;importe quel contenu arbitraire que vous souhaitez utiliser.
    * Sinon, vous pouvez simplement ajouter l&apos;installation guidée comme un fichier .mdx normal et l&apos;afficher comme vous le feriez pour n&apos;importe quel autre fichier. L&apos;installation .NET adopte cette approche. Avec cette approche, il apparaîtra comme une étape numérotée comme les autres fichiers.
  </Collapser>

  <Collapser id="config-file-decision" title="Ai-je besoin d’un fichier de configuration ?">
    Certains agents utilisent un composant de fichier de configuration qui permet à nos utilisateurs de saisir des valeurs spécifiques à l’utilisateur directement depuis le document d’installation. Pour un exemple de cela, consultez [le document d’installation Java](/install/java).

    L’utilisation de ce fichier n’est pas nécessaire. Son utilisation dépendra de votre workflow d’installation spécifique. (Par exemple, le document d’installation .NET ne l’utilise pas.)
  </Collapser>
</CollapserGroup>

## Notre installation ramifiée utilise [#uses]

Voici nos implémentations de l&apos;installation ramifiée avec des résumés des choix effectués pour celles-ci. Nous vous recommandons d&apos;en choisir une qui correspond à l&apos;approche que vous souhaitez adopter, et de l&apos;ajuster si nécessaire. Veuillez essayer de maintenir cette liste à jour à mesure que nous ajoutons de nouvelles utilisations.

* Gestion des vulnérabilités : [Importer les données dependabot](/install/vm/). [Voir une image étiquetée de ce fichier YAML](#simple-yaml-example). Détails :

  * Une implémentation très simple. Une boîte de sélection à option unique, qui vous permet de choisir entre deux fichiers.
  * Aucun contenu affiché par défaut.
  * Notez que c&apos;est si simple que le composant d&apos;onglet aurait pu être un meilleur choix.

* [Installation de l’intégration MySQL](/install/mysql). Détails :

  * Une implémentation simple avec une seule boîte de sélection d&apos;option.
  * Il adopte une approche de contenu affiché par défaut.

* [Installation de Java](/install/java). Détails :

  * Il adopte une [approche de contenu par défaut](#default-content-decision). Cela s’explique par le fait qu’il existe un chemin d’installation que la plupart des clients empruntent.
  * Il ne comporte que deux sections de sélection d&apos;options : selon ce qui est sélectionné dans la première option, une deuxième boîte d&apos;options s&apos;affiche.
  * Il utilise le composant `recommendedGuided` pour afficher l’installation guidée (contenue dans le fichier `appInfo-2`).
  * Il utilise le composant de fichier de configuration.

* [Installation de .NET](/install/dotnet). [Consultez une image annotée de ce fichier YAML](#complex-yaml-example). Détails :

  * Cela n’affiche aucun contenu par défaut. Cela repose entièrement sur l’approche [`isConditionalStep: true`](#default-content-decision). C’est parce qu’il y a pas mal de chemins et aucun chemin que la majorité des clients empruntent (bien que théoriquement nous aurions pu en choisir un).
  * Cela ne comporte que deux sections de sélection d’options : selon ce qui est sélectionné dans la première option, une deuxième boîte d’option s’affiche.
  * Il utilise le composant `recommendedGuided` (contenu dans le fichier `appInfo-2`).
  * Il n’utilise pas le composant de fichier de configuration : c’est parce que la plupart des clients modifient la configuration via des variables d’environnement ou d’autres options et non par l’utilisation directe du fichier.

* [Installation de Python](/install/python). Détails :

  * Il n’affiche pas le contenu par défaut. Il repose entièrement sur [l’approche`isConditionalStep: true` ](#default-content-decision). C’est parce qu’il n’y a pas de chemin principal unique.
  * Ceci comporte plusieurs boîtes de sélection d&apos;options : jusqu&apos;à quatre, selon ce qui est sélectionné.
  * Il n’utilise pas le composant de fichier de configuration.
  * Il utilise des commentaires, ce qui aide à la compréhension du code et améliore la maintenance.

* [points de terminaison de monitoring réseau](/install/npm). Détails :
  * Une implémentation assez simple. Trois boîtes de sélection d’options qui contrôlent laquelle de plusieurs tables est affichée. Un fichier affiché par défaut avec des remplacements qui déterminent quelle table afficher.
