Les introductions ressemblent beaucoup aux amuse-bouches d’un dîner — elles préparent le terrain pour le plat principal. Si vous consacrez un peu plus de travail à l’introduction, vos lecteurs seront prêts pour le plat principal.

Lorsque vous rédigez des introductions, vous incluez généralement ces trois ingrédients :

* Informations qui définissent le sujet
* Des idées qui captent l&apos;intérêt de l&apos;utilisateur
* Accroches qui indiquent au lecteur ce qu&apos;il peut attendre du document

Les deux premiers ingrédients semblent simples, mais lorsqu&apos;il s&apos;agit de dire aux lecteurs ce à quoi ils peuvent s&apos;attendre, nous nous appuyons souvent sur des phrases répétitives et figées. La façon dont nous gérons cela soulève quelques questions : qui parle ? Est-ce que cela fait autorité ? Est-ce collaboratif ? Est-ce la meilleure façon d&apos;aider les utilisateurs à apprendre et à résoudre leurs problèmes ?

Nous examinerons quelques conseils généraux sur les introductions, mais nous nous concentrerons sur la façon dont vous indiquez à vos lecteurs ce qu’ils peuvent attendre du document. Si vous préférez ignorer la discussion de fond, vous pouvez passer directement aux [Exemples d’amorces](#example-lead-ins) présentant des introductions qui évitent les phrases toutes faites et vont au cœur du sujet de la page.

## Conseils pour des introductions plus actives [#tips]

Nous avons un certain nombre de pages sur notre site qui ont un en-tête suivi d’une phrase d’introduction `This document is about`. Cette phrase reformule souvent l’en-tête. Lorsque vous lisez plus loin, il y a généralement un paragraphe qui fournit une meilleure introduction. Nous vous recommandons d’éviter d’utiliser le `this document is about` et d’aller directement à l’information que l’utilisateur recherche.

Nous examinerons diverses alternatives à ce type de construction tout au long du document. Avant d&apos;explorer ces alternatives, considérez ces façons de rédiger des introductions plus percutantes :

* Concentrez-vous tout de suite sur l’utilisateur. Au lieu de commencer par expliquer de quoi traite le document, parlez de ce que l’utilisateur pourrait vouloir savoir ou faire (pensez aux [Cinq questions](/docs/style-guide/writing-strategies/five-questions-help-write-docs)).
* Demandez-vous quelles informations sont manquantes ou implicites : vous pourriez avoir à définir un terme ou un concept. Par exemple, nous avons une page de documentation qui se concentre sur l’utilisation de Gradle, mais elle ne dit jamais ce qu’est Gradle. Ou, dans la page Observability for Good, nous commençons par faire référence à OfG, mais nous ne disons pas ce que c’est.
* Déterminez quel est le véritable but de la page et assurez-vous de l’inclure dans l’introduction. Ces informations se trouvent généralement juste après la phrase d’introduction plate « Cette page parle de ceci ». Mais vous devrez peut-être vraiment regarder la page pour trouver l&apos;accentuation.

Pour trouver de nouvelles façons d’atteindre votre lecteur, explorez des approches alternatives pour les introductions.

## Envisagez différentes approches [#what-about]

De quoi traite votre document ? La façon dont vous répondez à cette question affecte vos lecteurs et vos chances de les engager. Si vous utilisez la même construction dans tous vos documents, ils peuvent être prévisibles, mais ils pourraient également être répétitifs au point que les utilisateurs cessent de voir ces phrases.

La phrase toute faite a tendance à être un obstacle aux bons détails, et elle a tendance à répéter les informations déjà fournies dans le titre de la page. Souvent, en remontant les informations pertinentes dans l’introduction, vous pouvez indiquer au lecteur de manière plus précise et intéressante de quoi traite la page.

Voici un exemple d&apos;introduction qui résume un problème et attire l&apos;attention des lecteurs :

```
Clogged drains account for 60 percent of calls to professional plumbers. You may be able to solve this problem yourself and avoid the expense.
```

Quel type de troisième phrase pourriez-vous ajouter à ce paragraphe pour indiquer aux lecteurs de quoi traite le reste de ce document ? Les sections ci-dessous contiennent des tableaux avec diverses options pour votre troisième et dernière phrase de plomberie.

### Approche 3 : utiliser la première personne [#first-person]

Lorsque vous utilisez la première personne `we` dans un document procédural, le `we` fait référence à vous en tant que rédacteur ainsi qu’au lecteur. Vous parcourez tous les deux les étapes ensemble.

<Callout variant="tip">
  Il s&apos;agit d&apos;une utilisation différente de `we` par rapport à l&apos;usage plus général où `we` peut faire référence à New Relic. Vous pouvez utiliser `we` comme substitut de New Relic lorsqu&apos;il ne fait pas référence à l&apos;auteur et au lecteur ensemble. Par exemple, « NerdGraph est l&apos;API que **nous** recommandons pour interroger les données New Relic et pour effectuer certaines configurations spécifiques (en savoir plus sur les fonctionnalités). »
</Callout>

La première personne est probablement mieux utilisée dans le contexte de tutoriels où une relation personnelle est explicite. Par exemple, si vous avez un blog ou un cours, et que vous guidez les utilisateurs à travers une procédure. Chez New Relic, nous n’avons pas souvent ce contexte, mais nous pouvons avoir certains cas où cela convient.

Si vous avez un contexte où la première personne est appropriée, évitez les cas où la première personne envoie le message que l&apos;entreprise observe secrètement l&apos;utilisateur ou ses données. Par exemple, vous ne voudriez pas avoir une utilisation à la première personne comme celle-ci : « Nous voyons que votre agent est obsolète. Souhaitez-vous le mettre à jour ? »

## L’introduction par rapport aux sections « Pourquoi c’est important » [#why-matters]

Une fois que vous avez un éventail d&apos;options pour construire votre introduction, veillez à ne pas diluer votre introduction avec une section ultérieure « Pourquoi c&apos;est important ».

Pour créer une introduction plus centrée sur les utilisateurs actifs, vous pourriez vouloir inclure des informations que vous mettriez normalement dans une section de type « Why it matters ». Vous devriez ! Nous voulons absolument que les utilisateurs sachent pourquoi le sujet est important pour eux dès que possible.

Voici pourquoi l&apos;utilisation de « Pourquoi c&apos;est important » comme section et comme titre pose problème :

* Souvent, nous attendons pour partager les informations les plus importantes pour un utilisateur jusqu’à la section « Pourquoi c’est important ». Notre objectif devrait être d’aider les utilisateurs à apprendre rapidement ce qu’une fonctionnalité les aidera à accomplir. N’hésitez donc pas à supprimer cette section dédiée si vous en parlez déjà aux utilisateurs dans l’introduction ou dans d’autres sections du document.
* La valeur doit être associée au sujet d&apos;un document. Vous devez inclure des déclarations de valeur partout où elles sont pertinentes. Vous pourriez avoir une valeur de haut niveau dans l&apos;introduction, par exemple, puis des déclarations de valeur plus spécifiques lorsque vous discutez d&apos;un autre aspect du sujet de la page.
* N’utilisez pas « Why it matters » comme en-tête, quoi qu’il en soit. C’est une autre phrase répétitive qui ressemble à une documentation stéréotypée. Si vous consacrez de l’espace pour aborder cette question, créez un en-tête qui fournit des informations sur la valeur, plutôt que d’utiliser l’en-tête standard « Why it matters ».

## Exemples d’introductions [#example-lead-ins]

Jetez un œil à ces introductions qui évitent les phrases toutes faites et vont au cœur du sujet de la page. Ce sont des réécritures de contenu existant.

### Exemple 1 : [Critères d’éligibilité](/docs/accounts/accounts-billing/new-relic-one-pricing-billing/eligibility-guidelines-new-relic-nonprofit-program/) [#eligibility]

```
Non-profits and New Relic

This document provides New Relic's Observability for Good program eligibility guidelines for nonprofit, charitable, and NGO organizations.

Exceptions

Many global nonprofit, charity and NGO organizations are eligible for Observability for Good if the organization has a recognized legal status in their respective country equal to 501(c)(3) status under the United States Internal Revenue Code, with certain exceptions. In addition, all organizations must be verified by TechSoup or the local TechSoup partner.
```

Voici comment vous pourriez réécrire ceci :

```
If your organization is a global nonprofit, charity, or NGO, it might qualify for Observability for Good, a New Relic program that provides expansive, free access to New Relic. To qualify, your organization must have a recognized legal status in your respective country equal to 501(c)(3) status under the United States Internal Revenue Code. And, it must be verified by TechSoup or the local TechSoup partner.

To get started:

  1. Check that your organization is not in one of the ineligible categories (link). 
  2. Submit a New Relic application (link).
  3. Get qualified with TechSoup (link).
```

Cette révision comporte ces modifications :

* Définit Observability for Good immédiatement. Allez directement au but de la page, sans avoir à dire quel est le but.
* Remplace les premières phrases passives par un point de vue plus actif à la deuxième personne : « Si votre organisation est une organisation à but non lucratif, une association caritative ou une ONG mondiale » au lieu de « De nombreuses organisations à but non lucratif, associations caritatives et ONG mondiales… »
* Garde l’accent sur « vous », le lecteur et les bénéficiaires potentiels de ce programme.
* Supprime le terme négatif « exceptions » et le remplace par des détails sur la façon de se qualifier et de s&apos;appliquer.

### Exemple 2 : [Modifier votre mot de passe](https://docs.newrelic.com/docs/accounts/accounts/account-maintenance/change-passwords-user-preferences/) [#change-password]

```
This document contains information on New Relic password requirements.

Change your password

New Relic account passwords don't expire. However, users can change their own password and other personal account information anytime.
```

Voici comment vous pourriez réécrire ceci :

```
New Relic account passwords don't expire. However, you can change your own password and other personal account information anytime. You can also request a password reset if you forget your password.
```

Cette révision comporte ces modifications :

* Supprime la ligne « this document contains » et le premier H2.
* Commence par l’information qui importera le plus à un utilisateur : les mots de passe n’expirent pas. Vous pouvez changer votre mot de passe quand vous le souhaitez.
* Permet d&apos;utiliser « vous » au lieu de « utilisateurs ».
* Il s’agit d’une page courte et l’introduction peut rapidement aborder les informations essentielles. De plus, les H2 doivent fournir un aperçu des informations qui seront couvertes.

### Exemple 3 : [Installer l’agent Java](/docs/apm/agents/java-agent/additional-installation/install-java-agent-using-gradle/) [#install-java-agent]

```
This document explains how to install the Java agent using Gradle. For information on manually installing the Java agent, see "Install the Java agent" and "Java agent configuration: Config file."
```

Voici comment vous pourriez réécrire ceci :

```
Gradle is a highly flexible build automation tool that can help you install the Java agent across many instances quickly and consistently.

If you’d like to manually install the Java agent instead, see Install the Java agent and "Java agent configuration: Config file."
```

Cette révision comporte ces modifications :

* Définit Gradle (vous permet d’automatiser l’installation).
* Ensuite, lorsque vous faites référence à l&apos;approche manuelle, elle est en contraste direct avec l&apos;outil d&apos;automatisation.
* Si vous devez préciser que vous n’allez couvrir qu’un sous-ensemble d’informations liées à une chose, par exemple, une seule façon parmi d’autres d’automatiser l’installation avec Gradle, vous pourriez dire ceci : « Ici, nous fournissons la façon la plus courante d’automatiser votre installation avec Gradle. » Beaucoup de choses dépendent du contexte.

### Exemple 4 : [attributs de l&apos;agent Java](/docs/apm/agents/java-agent/attributes/java-agent-attributes/) [#agent-attributes]

```
New Relic attributes are key-value pairs containing information that determines the properties of an event or transaction. These key-value pairs can help you gain greater insight into your application and annotate the data when you query it. You can also automatically forward user information to New Relic.

Both default and custom attributes are visible in APM transaction traces, distributed traces, and error analytics; APM events and Browser events in dashboards. You can customize exactly which attributes will be sent to each of these destinations.

This document describes the Java agent attributes, details how to enable or disable attributes, and describes the rules the agent follows to determine which attributes to include or exclude for a destination.
```

Pour améliorer cela, vous pourriez conserver les trois premiers paragraphes, mais ajouter ce qui suit au dernier paragraphe :

```
Before you start creating custom attributes, familiarize yourself with existing Java agent attributes and how to enable or disable them. In addition, learn the rules for which attributes the agent includes or excludes for a destination. 
```
