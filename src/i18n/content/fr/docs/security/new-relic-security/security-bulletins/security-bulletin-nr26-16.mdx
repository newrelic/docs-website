<DNT>**Vulnerability Identifier:**</DNT> NR26-16

<DNT>**Priority:**</DNT> Critique

## Résumé

Une vulnérabilité critique de corruption de la mémoire (CVE-2026-114938) a été divulguée dans le décodeur Base64 accéléré par le matériel de la machine virtuelle Java HotSpot OpenJDK (JVM). Lorsqu’une application Java affectée traite une entrée codée en Base64 spécialement conçue (telle que des en-têtes d’autorisation HTTP, des JWT, des jetons SAML, ou des téléchargements de fichiers), un dépassement de capacité par valeur inférieure d’un entier peut déclencher une écriture dans le tas hors limites. Une exploitation réussie peut provoquer des plantages de l’application (déni de service), exposer la mémoire de tas sensible, ou permettre une exécution de code à distance (RCE) non authentifiée.

## Éléments d&apos;action

### Aucune action requise

New Relic ne fournit pas d’environnement d’exécution Java avec l’agent Java New Relic. Aucune action des clients n’est requise pour les services hébergés par New Relic, y compris les emplacements publics Synthetics.

Une action des clients est requise dans les cas suivants.

### Sites privés Synthetics (Synthetics Job Manager et environnement d&apos;exécution ping)

Le Synthetics Job Manager (SJM) et l’environnement d’exécution ping pour les sites privés incluent un environnement d’exécution Java. Des images mises à jour contenant un environnement d’exécution Java corrigé ont été publiées le 19 novembre 2026.

* Mettez à niveau le Synthetics Job Manager vers la version [release-659](https://hub.docker.com/layers/newrelic/synthetics-job-manager/release-659/images/sha256-11fa4a7b78d7a7d708b1f5efec790dc066ab6c02d3b3f02c7a59a8b885913828), ou ultérieure, et l’environnement d’exécution ping vers la version [1.89.0](https://hub.docker.com/layers/newrelic/synthetics-ping-runtime/1.89.0/images/sha256-33da2eb67b404b09f19e1ea232e80be22d403e97abbeaf2b0f26bc95d2eae646), ou ultérieure.
* Si votre configuration fixe l’environnement d’exécution ping à une version spécifique, mettez-le à jour vers la version 1.89.0 ou ultérieure. S’il utilise le tag `latest`, redémarrez le Synthetics Job Manager pour récupérer l’environnement d’exécution mis à jour.
* Si vous exécutez une version de Synthetics Job Manager antérieure à la [sortie-655](https://hub.docker.com/layers/newrelic/synthetics-job-manager/release-655/images/sha256-c587a634136aeed4179ebd216d993c9aea4b50a6a88f977fc5099fb164b42c57), il n&apos;existe pas de chemin de mise à niveau sur place vers la sortie actuelle. Planifiez une migration vers la dernière version, et validez-la d&apos;abord dans un environnement hors production. Pour obtenir des instructions d&apos;installation, voir [Installer le Synthetics Job Manager](/docs/synthetics/synthetic-monitoring/private-locations/install-job-manager).
* Si vous ne pouvez pas mettre à niveau le Synthetics Job Manager immédiatement, définissez l’option JVM `JAVA_TOOL_OPTIONS="-XX:-UseBASE64Intrinsics"` sur le conteneur du Synthetics Job Manager. Sur les hôtes x86-64 uniquement, vous pouvez utiliser `-XX:UseAVX=2` à la place. Les JVM sur ARM ne reconnaissent pas cette option, et ne parviendront pas à démarrer. Cette option ne s’applique pas aux conteneurs de l’environnement d’exécution ping dont le Synthetics Job Manager effectue le lancement ; vous devez donc quand même mettre à jour l’image de l’environnement d’exécution ping pour corriger complètement le problème.

### Vos applications Java, y compris celles monitorées par l’agent Java New Relic

Vos applications Java sont concernées uniquement lorsque toutes les conditions suivantes sont remplies :

* L’application s’exécute sur une distribution OpenJDK basée sur HotSpot, version 17.0.6 ou ultérieure (mais antérieure à la mise à jour critique de correctifs de novembre 2026). Les exemples incluent Oracle Java SE, Amazon Corretto, Eclipse Temurin, Azul Zulu, Red Hat OpenJDK et Microsoft Build of OpenJDK.
* L&apos;hôte dispose d&apos;un processeur x86-64 avec prise en charge AVX-512 VBMI (Intel Xeon Ice Lake ou plus récent, ou AMD Zen 4 ou plus récent). Les processeurs ARM64, y compris AWS Graviton, ne sont pas concernés.
* L’application traite une entrée non fiable qui peut atteindre le décodeur Base64 de Java.

**Correctif :** mettez à jour votre environnement d’exécution Java vers la sortie de sécurité de novembre 2026 de votre fournisseur, en commençant par les systèmes exposés sur Internet. Pour plus de détails, consultez la [Mise à jour critique de sécurité](https://www.oracle.com/security-alerts/cspunov2026.html) d’Oracle (novembre 2026), l’ [Avis de vulnérabilités](https://openjdk.org/groups/vulnerability/advisories/2026-11-17) d’OpenJDK (17/11/2026), ou l’avis du fournisseur de votre JDK.

## Questions fréquemment posées

1. **Cela affecte-t-il les agents de New Relic ?**

   L’agent Java New Relic n’intègre ni ne distribue d’environnement d’exécution Java (JDK/JVM). Il instrumente les applications Java en utilisant l’environnement d’exécution Java disponible dans l’environnement de l’application.

2. **Dois-je mettre à jour l’agent Java New Relic ?**

   Non. L&apos;agent Java New Relic n&apos;inclut pas d&apos;environnement d&apos;exécution Java, et aucune mise à jour de l&apos;agent Java n&apos;est requise pour cette vulnérabilité.

3. **Quels systèmes sont concernés ?**

   Seuls les processeurs x86-64 prenant en charge AVX-512 VBMI. Les processeurs ARM64 ne sont pas affectés. OpenJDK et Oracle ont publié des correctifs.

4. **Comment puis-je savoir si mes environnements d&apos;exécution Java pour mes applications sont concernés ?**

   Vérifiez la version de Java, et le CPU. Pour les applications monitorées par New Relic APM, la version de la JVM est affichée sur la page Environnement du service. Consultez [Obtenir des données d’environnement sur votre application APM](/docs/apm/agents/manage-apm-agents/troubleshooting/get-environment-data-about-your-apm-app) pour plus de détails, et assurez-vous de sélectionner vos hôtes. Sinon, sur un hôte, exécutez `java -version`.

   Sous Linux, vérifiez le processeur avec :

   ```bash
   grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'
   ```

   Le CPU n’est affecté que si les quatre indicateurs apparaissent.

5. **Comment puis-je corriger la vulnérabilité ?**

   Mettez à jour votre environnement d’exécution Java vers la sortie de sécurité de novembre 2026 de votre fournisseur, en commençant par les systèmes exposés sur Internet. Pour plus de détails, consultez la [Mise à jour critique de sécurité](https://www.oracle.com/security-alerts/cspunov2026.html) d’Oracle (novembre 2026), l’ [Avis de vulnérabilité](https://openjdk.org/groups/vulnerability/advisories/2026-11-17) d’OpenJDK (17/11/2026), ou l’avis du fournisseur de votre JDK.

6. **Que puis-je faire si je ne peux pas appliquer le correctif immédiatement ?**

   Démarrez la JVM avec `JAVA_TOOL_OPTIONS="-XX:-UseBASE64Intrinsics"` comme mesure d&apos;atténuation temporaire. Sur les hôtes x86-64 uniquement, vous pouvez utiliser `-XX:UseAVX=2` à la place. Les JVM sur ARM ne reconnaissent pas cette option, et ne parviendront pas à démarrer. Les deux options sont temporaires, et ne remplacent pas l&apos;application de correctifs.

7. **New Relic a-t-il constaté des preuves d&apos;exploitation ?**

   Nous n’avons pas identifié d’indicateurs d’exploitation de cette vulnérabilité dans notre environnement.

8. **Que faire si j’ai des questions ?**

   Pour tout besoin d’assistance lié à cette communication, ouvrez un ticket d’assistance via l’assistance intégrée à l’application.
