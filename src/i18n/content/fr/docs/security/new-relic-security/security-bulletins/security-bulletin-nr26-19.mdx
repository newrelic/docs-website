<DNT>**Vulnerability Identifier:**</DNT> NR26-19

<DNT>**Priority:**</DNT> Critique

## Résumé

Le 18 novembre 2026, nginx a divulgué des vulnérabilités dans son module HTTP/2, connues conjointement sous le nom de « nginx2root ». F5 évalue les deux problèmes principaux à 9,2 (Critique) selon CVSS v4.0.

CVE-2026-123007 affecte nginx 1.9.5 à 1.31.8. Lorsque nginx traite un trafic HTTP/2 spécialement conçu, sa fenêtre de contrôle de flux peut dépasser la limite autorisée, ce qui peut provoquer un dépassement de tampon de tas. Un attaquant non authentifié peut faire planter le processus de travail nginx ou corrompre sa mémoire. Si l’ASLR est désactivé ou si l’attaquant peut le contourner, l’attaquant peut également exécuter du code.

CVE-2026-123633 affecte nginx 1.19.7 à 1.31.8 lorsque nginx accepte les connexions clientes HTTP/2 et transmet les requests à un backend. Une requête spécialement conçue peut provoquer un use-after-free dans un processus de travail venant à manquer de `worker_connections`. Cela peut conduire à un déni de service ou, avec un contournement de l&apos;ASLR, à l&apos;exécution de code.

Les correctifs pour les deux vulnérabilités sont dans nginx 1.30.7 (stable) et 1.31.9 (mainline), et dans NGINX Plus PLS.37.0.8.1 et PLS.37.3.0.1. La même sortie corrige plusieurs autres vulnérabilités de nginx, dont certaines n’impliquent pas HTTP/2. Une sortie ultérieure, nginx 1.30.8 et 1.31.10, corrige également CVE-2026-132779. Les détails de l’[exploit public](https://github.com/sfewer-r7/CVE-2026-123007?utm_source) sont disponibles. Au 24 novembre 2026, le catalogue des vulnérabilités exploitées connues de la CISA ne liste pas ces vulnérabilités.

**Les agents et intégrations New Relic, y compris l&apos;intégration nginx de New Relic (nri-nginx), n&apos;incluent pas nginx et ne sont pas affectés.** New Relic a mis à jour nginx sur ses services exposés sur Internet qui l&apos;utilisent. New Relic n&apos;a pas identifié de preuve d&apos;exploitation dans son environnement.

## Action recommandée

Aucune action n’est requise pour vos services New Relic ou pour les agents et l’intégration New Relic que vous avez installés. Néanmoins, New Relic encourage vivement les clients qui exécutent nginx avec HTTP/2 activé sur leur propre environnement à mettre à niveau vers la dernière sortie de nginx (1.30.8 stable ou 1.31.10 mainline), vers NGINX Plus PLS.37.0.8.1 ou PLS.37.3.0.1 ou ultérieur, ou vers un package de distribution Linux qui inclut les correctifs.

### Recommandations

* Mettez d’abord à niveau les serveurs exposés à Internet avec HTTP/2 activé. HTTP/2 est activé lorsqu’une directive `listen` inclut `http2` ou lorsque `http2 on;` est défini.
* Redémarrez nginx après la mise à niveau afin que le binaire corrigé s’exécute.
* Reconstruisez et redéployez les images de conteneur qui incluent nginx. L&apos;application de correctifs sur l&apos;hôte ne met pas à jour nginx à l&apos;intérieur des conteneurs.
* **Packages de distribution Linux :** les distributions ajoutent souvent des correctifs sans modifier le numéro de version en amont. Ubuntu a publié des packages corrigés pour toutes les sorties prises en charge le 19 novembre 2026. Pour les autres distributions, consultez l’avis de votre fournisseur pour CVE-2026-123007 et CVE-2026-123633.
* Produits qui intègrent nginx, tels que les contrôleurs d’entrée Kubernetes, les gateways et les appliances : vérifiez auprès du fournisseur ou du projet pour une sortie qui inclut les correctifs.
* Si vous avez déployé l’une des applications d’exemple ou de démonstration que New Relic publie sur GitHub et qu’elle utilise l’image nginx publique, reconstruisez-la à partir d’une image nginx actuelle.

## Atténuation temporaire

Seule une mise à niveau corrige entièrement ces vulnérabilités, ainsi que les autres corrigées dans la même sortie. En attendant de pouvoir mettre à niveau :

* Désactivez HTTP/2 sur les écouteurs affectés et rechargez nginx. Les deux vulnérabilités nécessitent HTTP/2. Pour le désactiver, supprimez `http2` des directives `listen` ou définissez `http2 off;`. Les clients reviennent à HTTP/1.1.

## Questions fréquemment posées

1. **Cela affecte-t-il les agents ou les intégrations de New Relic ?**

   Non. Les agents et l’intégration New Relic n’incluent pas nginx. L’intégration nginx de New Relic (nri-nginx) collecte des métriques à partir du serveur nginx que vous exécutez. Elle n’inclut pas nginx.

2. **Dois-je mettre à jour l’intégration New Relic nginx ?**

   Non. Mettez à niveau nginx lui-même.

3. **Certains charts Helm de New Relic font référence à une image nommée `ingress-nginx/kube-webhook-certgen`. Est-elle affectée ?**

   Non. Cette image est un utilitaire de génération de certificats du projet Kubernetes ingress-nginx et ne contient pas nginx.

4. **Comment puis-je savoir si mon nginx est affecté ?**

   Tout d&apos;abord, vérifiez si HTTP/2 est activé : exécutez `nginx -T | grep http2`. Ensuite, vérifiez la version :

   * Si vous avez installé nginx depuis nginx.org ou si vous l’avez compilé vous-même, exécutez `nginx -v`. Vous êtes affecté si la version est 1.9.5 ou ultérieure et antérieure à 1.30.7 (stable) ou 1.31.9 (mainline).
   * Si vous avez installé nginx à partir de votre distribution Linux, le numéro de version seul ne vous indique pas si vous êtes protégé. Comparez la version du package installée (par exemple, `dpkg -l | grep nginx` ou `rpm -q nginx`) avec l’avis de votre distribution.

5. **Comment puis-je savoir si mes systèmes ont été ciblés ?**

   Le trafic HTTP/2 malveillant n’apparaît pas comme des requests normales dans les logs d’accès. Les tentatives d’exploitation font généralement planter un processus de travail nginx. Surveillez le log d’erreurs nginx pour les processus de travail qui se terminent sur le signal 11 (une erreur de segmentation). Si vous transférez les logs nginx à New Relic, vous pouvez [créer une alerte](/docs/tutorial-create-alerts/create-an-alert/) sur ce message. Recherchez également les processus de travail nginx qui démarrent des shells ou d’autres processus enfants inattendus.

6. **New Relic a-t-il constaté des preuves d&apos;exploitation ?**

   Nous n’avons pas identifié d’indicateurs d’exploitation de ces vulnérabilités dans notre environnement.

7. **J’ai des questions sur ces vulnérabilités. Qui dois-je contacter ?**

   Si vous avez des questions sur ces vulnérabilités liées à vos services New Relic, [ouvrez un dossier d’assistance](/docs/new-relic-solutions/solve-common-issues/find-help-get-support/#file-ticket) via l’assistance intégrée à l’application ou contactez votre représentant de compte New Relic.
