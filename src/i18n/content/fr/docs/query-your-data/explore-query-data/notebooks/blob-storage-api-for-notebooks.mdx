<Callout title="Aperçu public">
  La <DNT>Blob Storage API</DNT> pour les notebooks est actuellement en version préliminaire publique. Cette fonctionnalité est fournie conformément à nos [politiques de version préliminaire](/docs/licenses/license-information/referenced-policies/new-relic-pre-release-policy).
</Callout>

L’API New Relic <DNT>Notebooks</DNT> vous permet de créer, lire, mettre à jour et supprimer des notebooks par programmation, y compris le contenu complet de leurs blocs (<DNT>NRQL</DNT> requêtes, texte). Les notebooks sont stockés sous forme de blobs versionnés, ce qui signifie que chaque sauvegarde produit une nouvelle révision immuable que vous pouvez récupérer plus tard.

Utilisez cette API pour :

* Automatiser la création de notebooks à partir de modèles d&apos;incident, de runbooks ou de pipelines CI/CD
* Synchroniser le contenu du notebook à partir du contrôle de version ou d&apos;outils de création externes
* Créer des intégrations qui remplissent les notebooks de manière programmatique lors des investigations

<Callout variant="important">
  **<DNT>Notebooks</DNT> utiliser plusieurs API**

  La surface de l’API <DNT>Notebooks</DNT> est divisée entre deux systèmes :

  * **<DNT>Blob Storage API</DNT>** gère le contenu des notebooks (blocs, historique des versions)
  * **<DNT>NerdGraph</DNT>** gère les opérations au niveau de l&apos;entité (liste, renommage, tags, métadonnées d&apos;organisation)

  Cette séparation est intentionnelle. Le <DNT>Blob Storage API</DNT> est optimisé pour le transfert de contenu de fichiers et le versioning ; <DNT>NerdGraph</DNT> est optimisé pour les requêtes d&apos;entité structurées et les mutations.
</Callout>

## Prérequis [#prerequisites]

* Un [compte<DNT>New Relic</DNT> ](https://newrelic.com/signup)avec une clé d&apos;API utilisateur
* Votre ID d’organisation <DNT>New Relic</DNT>
* Les [permissions](/docs/accounts/accounts-billing/new-relic-one-user-management/user-permissions/) appropriées pour gérer les notebooks

## Authentification [#authentication]

Toutes les requêtes d&apos;API <DNT>Notebooks</DNT> nécessitent une authentification à l&apos;aide d&apos;une clé d&apos;API utilisateur <DNT>New Relic</DNT>.

**Générer une clé d&apos;API :**

1. Allez sur [one.newrelic.com](https://one.newrelic.com)
2. Cliquez sur votre nom dans le coin supérieur droit
3. Select <DNT>**API Keys**</DNT>
4. Créez une clé <DNT>**User**</DNT> (et non une clé Browser ou clé de licence)

**Inclure dans les en-têtes de requête :**

```shell
Api-Key: NRAK-YOUR-USER-API-KEY
```

<Callout variant="tip">
  Le <DNT>Blob Storage API</DNT> prend également en charge le contexte de connexion, de sorte que lors de l’appel de l’API depuis une interface utilisateur authentifiée en tant qu’utilisateur <DNT>New Relic</DNT>, l’en-tête `Api-Key` n’est pas requis.
</Callout>

  <Collapser id="retrieve-versions" title="Récupérer les versions précédentes">
    <DNT>Notebook</DNT> les versions sont conservées pendant **1 jour**. Pour récupérer une révision précédente, listez d’abord les versions récentes via <DNT>NRQL</DNT>, puis récupérez le blob spécifique.

    ### Étape 1 — lister les 5 dernières versions [#retrieve-list-versions]

    Exécutez cette requête <DNT>NRQL</DNT> dans le générateur de requêtes pour rassembler les ID de blob et les horodatages des 5 dernières modifications :

    ```sql
    FROM Entity
    SELECT uniques(tuple(updatedAt, content.id))
    WHERE id = '<entity guid>'
    SINCE 1 day ago
    LIMIT 5
    ```

    ### Étape 2 — Récupérer une version spécifique [#retrieve-specific-version]

    Utilisez le `content.id` du résultat <DNT>NRQL</DNT> pour récupérer le contenu de cette version :

    ```bash
    curl -X GET \
      https://blob-api.service.newrelic.com/v1/blobs/<content.id> \
      -H 'Api-Key: NRAK-YOUR-API-KEY'
    ```
  </Collapser>

## Opérations sur les entités (NerdGraph) [#entity-operations]

Les opérations au niveau de l’entité telles que le listage, le renommage et le tag utilisent <DNT>NerdGraph</DNT> plutôt que <DNT>Blob Storage API</DNT>.

### Lister tous les notebooks [#list-notebooks]

```graphql
query listAllNotebooks {
  actor {
    entityManagement {
      entitySearch(query: "type='NOTEBOOK'") {
        entities {
          id
          name
        }
      }
    }
  }
}
```

<Callout variant="tip">
  La création d’entité est entièrement transactionnelle, un notebook est donc immédiatement disponible via l’API. Cependant, si vous listez les notebooks via la requête `actor.entitySearch` legacy, il peut y avoir un court délai de propagation entre la création et l’apparition du notebook dans les résultats de la liste.
</Callout>

### Renommer un notebook [#rename-notebook]

```graphql
mutation changeNotebookName {
  entityManagementUpdateNotebook(
    id: "<entity guid>"
    notebookEntity: { name: "<new name>" }
  ) {
    entity {
      name
    }
  }
}
```

### Mettre à jour les tags du notebook [#update-tags]

<Callout variant="important">
  Les mises à jour de tags sont une opération de **remplacement**. Vous devez inclure l’ensemble complet des tags, même ceux qui ne changent pas — tout tag omis de la mutation sera supprimé.
</Callout>

```graphql
mutation updateNotebookTags {
  entityManagementUpdateNotebook(
    id: "<entity guid>"
    notebookEntity: {
      tags: [
        { key: "<key>", values: "<value>" }
        { key: "<key>", values: "<value>" }
      ]
    }
  ) {
    entity {
      name
      tags {
        key
        values
      }
    }
  }
}
```

## Meilleures pratiques [#best-practices]

* **Stockez les GUID d’entité :** enregistrez le `entityGuid` renvoyé par les opérations de création. Vous en aurez besoin pour lire, mettre à jour et supprimer des notebooks.
* **Valider le JSON avant le téléversement :** assurez-vous que la charge de votre notebook est un JSON valide et conforme au schéma `version` avant l’envoi.
* **Utilisez des noms descriptifs :** les noms de notebooks doivent être uniques au sein d’une organisation, choisissez donc des noms qui indiquent clairement leur objectif (par exemple, `prod-checkout-investigation` plutôt que `notebook-1`).
* **Inclure tous les tags lors de la mise à jour :** les mises à jour de tags remplacent l&apos;ensemble complet de tags. Lisez toujours les tags existants avant de les modifier.
* **Récupérez rapidement :** l&apos;historique des versions n&apos;est conservé que pendant 1 jour. Si vous avez besoin d&apos;un historique à long terme, archivez le contenu du notebook dans votre propre stockage à chaque mise à jour.
* **Sécurisez votre clé d&apos;API :** N&apos;exposez jamais votre clé d&apos;API utilisateur dans du code côté client ou des dépôts publics.
* **Vérifiez les codes d&apos;état HTTP :** L&apos;API renvoie 2xx pour les opérations réussies, 404 pour non trouvé, et d&apos;autres codes d&apos;état pour les erreurs.
